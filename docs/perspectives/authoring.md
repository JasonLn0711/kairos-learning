# 觀點 Perspectives：文章撰寫與編輯規範

採用日期：2026-11-01。適用於 Learn「觀點」專欄的選題、撰稿、AI 協作、翻譯、校閱與更正。本文是本專欄寫作規則的主要依據；技術教材的既有規範由[教材內容指南](../content-authoring.md)承接。

## 1. 專欄目的與文章定位

從真實事件、技術問題與實作經驗出發，白話理解資工、AI 與資安，記錄我們的實作、思考與判斷。文章應讓讀者帶走一個可以解釋、辨認或運用的概念。

Learn 承接具教學價值的議題解讀、實作手記與觀點反思；主站承接個人研究與專案論述。每篇完整中英雙語，公開 JSON 是正式內容來源。私人對話、識別資料及原始證據保存在忽略的 `.local/`，公開文件只保留適合公開的摘要。

開始撰稿前，用一句話確認讀者與成果：

> 這篇文章要幫助＿＿＿讀者，理解＿＿＿問題，並能夠＿＿＿。

例如：這篇文章要幫助協助維護網站的初學者，理解憑證安裝與公開連線的關係，並能判斷更新後還需要驗證哪些項目。

## 2. 正面、主動且有依據的語氣

### 撰寫要求

- 從讀者收穫、核心觀察、判斷或可採取的行動開始，直接說明價值與理由。
- 使用主動句，寫清楚誰做了什麼、觀察到什麼，以及接下來如何確認。
- 用具體條件表達適用範圍：環境、版本、時間、服務種類與已取得的證據。
- 尚待確認的地方，交代目前線索、待取得的資料及確認方法；有具體責任分工時，說明負責角色。
- 刪除沒有提供資訊的自我辯護、道歉、免責聲明與空泛退縮句，例如「僅供參考」「我們只是提出一種想法」「可能有一定程度的幫助」。
- 避免反覆以「不是 X，而是 Y」或「不能保證」組織段落，優先直接說明本文要建立的理解。

語氣的自信來自把事情說清楚。對不確定的判斷，仍使用「可能」「待確認」等準確措辭，並接上理由與查證方法。這些詞不作機械式禁用；已證實的事實也不必反覆加上「似乎」「或許」。

### 改寫示例

以下為編輯示例，不表示本專欄已完成相應操作。

| 原句 | 建議寫法 | 改寫目的 |
| --- | --- | --- |
| 本文僅供參考，不保證適用所有環境。 | 本文以小型團隊的 NAS 維護情境為例，說明如何盤點版本、核對公告與安排更新。 | 以適用情境取代泛用免責句。 |
| 我們不能保證更新後就安全。 | 更新後，接著核對套件版本、服務功能與存取設定，確認這次變更的結果。 | 將籠統保留轉成驗證步驟。 |
| 可能是前面的設備有問題。 | 公開端與後端提供不同憑證，下一步應核對連線入口、憑證綁定及前置設備設定。 | 連接觀察與下一步，不預先認定原因。 |
| 我們只是提出一種想法。 | 我們提出這個方案，目的是讓遠端存取具備明確的身分驗證與權限管理。 | 清楚表達方案目的。 |
| 操作風險請自行負責。 | 操作前先確認備份、維護窗口與還原方式；完成後核對服務功能與存取結果。 | 提供有用的準備與驗收條件。 |

正面語氣保留必要的安全指示。例如「請勿公開私鑰」「僅對已獲授權的目標操作」具有明確目的，應直接寫出。法規、資安警告與精確引用依原意保留；不能為了語氣而弱化要求或將未驗證結果寫成成功。

## 3. 臺灣慣用語的繁體中文

以臺灣讀者自然閱讀技術文章的方式撰寫。使用短而完整的句子，直接連接動作、對象與結果；專業術語依讀者需要解釋，不逐字翻譯英文句型。

| 優先用語 | 統一方式 |
| --- | --- |
| 軟體、硬體 | 避免混用不同地區的同義詞。 |
| 伺服器、網路、資料庫 | 首次出現可補英文，後續保持一致。 |
| 程式碼、原始碼 | 視內容區分一般程式文字與來源程式。 |
| 帳號、登入、使用者 | 與產品介面原文有差異時，同時標示方便尋找。 |
| 設定、預設值、品質、效能 | 使用臺灣常見技術表達。 |
| 資訊安全、資安、維運 | 首次交代完整名稱，後續可使用常見簡稱。 |

「部署」「驗證」「授權」等具明確技術意義的詞可以使用，並在初學者首次需要時說明用途。產品名稱、命令、程式碼、版本、CVE 編號、路徑及介面原文保留原樣；不要將識別字全形化或翻譯掉。

句型示例：

- 「進行對系統的更新操作」→「更新系統」。
- 「實現對存取的控制」→「管理誰可以存取」。
- 「透過這個部分來進行相關的確認」→「比對公開端與後端的憑證序號」。

使用「我們」時應有明確對象：作者的觀察、團隊已確認的行動或正在討論的方案。不要將受訪者的回報改寫成作者親自驗證。

## 4. 白話文教學：從問題走到原理與驗證

預設讀者有一般電腦使用經驗，但第一次接觸本文主題。先交代問題與用途，再介紹名稱與細節。重要概念依需要回答：

1. 它是什麼？
2. 這個情境為什麼需要它？
3. 它如何運作？
4. 讀者如何辨認、觀察或驗證？

例如介紹 TLS 終結：

> 瀏覽器連上網站時，會先和某個服務端建立加密連線。負責接收並解開這段加密資料的位置，就稱為「TLS 終結點」。網站前方如果設有代理設備，瀏覽器看到的憑證可能由代理設備提供。因此，更新後端憑證後，還要確認公開入口實際送出哪一張憑證。

比喻用來建立第一層理解，再接回實際機制。例如把憑證比喻為網站的身分證明後，接著說明網站名稱、公開金鑰與簽發者各自的角色；當比喻會影響判斷時，簡短交代它涵蓋的範圍。

- 一次引入理解當前問題所需的術語；英文縮寫首次出現補上名稱、中文與用途。
- 用具體例子展示判斷過程，讓讀者看見從輸入、觀察到結論的連接。
- 避免用「很簡單」「大家都知道」「只要這樣就好」跳過步驟。
- 操作教學交代環境與先備條件、操作步驟、預期輸出、判讀方法，以及適用時的清理或還原方式。
- 紙上推演、合成範例與實際執行結果分開標示，命令區塊旁說明它會讀取或改動什麼。

## 5. 一篇文章集中回答一個主要問題

先寫讀者目標與一句主要主張，再安排證據和章節。每一段都應推進該問題；額外議題以延伸閱讀或另一篇文章承接。

主要主張示例：憑證置換的驗收，需要同時核對管理端安裝結果與使用者實際連線端點。

推薦閱讀順序為「緣起 → 核心問題 → 白話原理 → 實際處理與判斷 → 結果與下一步」。這是編輯思考順序，不是每篇都必須照抄的標題。文章長度由解釋完整度決定，不以篇幅或固定小節數充當品質。

| 形式 | 重點 |
| --- | --- |
| 議題解讀 | 發生什麼事、為什麼值得理解、原理與影響如何連接。 |
| 實作手記 | 當時有哪些資訊、如何選擇、實際觀察與後續結果。 |
| 觀點反思 | 主張、支持理由、適用條件，以及哪些新證據會改變判斷。 |

## 6. 事實、回報、推論與行動的區分

在敘事中自然交代資訊來源與狀態。只在讀者容易混淆的地方明確提示，不必每段貼上分類標籤。

| 表達 | 資訊角色 |
| --- | --- |
| 管理者回報已拔除網路線。 | 他人回報；尚未等同實機查驗。 |
| 我們在該次測試中取得舊憑證。 | 指定時間與測試環境的直接觀察。 |
| 這個差異讓我們優先檢查前置連線入口。 | 根據觀察形成的判斷。 |
| 下一步核對入口設備的憑證綁定。 | 準備採取的行動。 |

草稿、方案、操作嘗試、系統成功回應、獨立驗收與正式發布，各自記錄實際狀態。寫作時選擇與證據相符的動詞，例如「提出」「嘗試」「回報」「觀察」「核對」「確認」。成果句說明確認了哪個範圍，避免將局部結果延伸為整體完成。

## 7. 從個人經驗提煉可帶走的理解

實作手記除了紀錄做了什麼，也要回答：

- 當時為什麼這樣判斷？
- 哪項資訊改變了我們的想法？
- 哪個小測試最有助於釐清問題？
- 讀者遇到類似情境，可以先檢查什麼？

保留關鍵決策與必要時間順序，刪除無助理解的流水帳。NAS 案例可以從收到警訊後暫停連線切入，帶出設備盤點、漏洞適用性與恢復服務的順序；憑證案例則聚焦管理端與公開端觀察的連接。案例尚在處理時，可以發表當前階段的理解，清楚交代觀察截止時間與下一步。

## 8. 來源、時效與更正

新聞、漏洞、版本、產品能力與研究結果優先引用官方公告、技術文件、原始研究或可追溯的第一手材料。將來源放在它支撐的技術說法附近，交代必要的版本與查核日期。

- 私人材料支持案例內部核對；公開文章只引用可公開內容與去識別化摘要。
- 區分事件發生日期、觀察截止時間、文章發布日期與更新日期。
- 正文避免單獨使用容易過期的「今天」「最近」「最新版」；可搭配明確日期或版本。
- 網頁無法讀取、原始警訊缺失或測試尚未執行時，在編輯企劃記下待補證據；公開結論維持在現有資料支持的範圍。
- 新結果補入更新紀錄，保留原始觀察的時間背景。影響技術判斷的更正寫明修改內容與理由。
- 來源查核日期與驗證範圍依實際情況記載；作者參與及協作分工留在編輯工作紀錄，不填入未發生的人工作業。

## 9. 標題、段落、圖表與行動收尾

標題直接呈現問題或收穫，例如「NAS 已經斷網，接下來該確認什麼？」與「憑證更新後，如何確認公開連線已經生效？」避免誇大的保證、恐嚇式措辭或超過本文證據的成功宣告。

摘要用數句說明情境、本文問題與讀者收穫。正文以連貫段落為主，一段發展一個重點；步驟用編號、平行事項用清單、比較用表格、流程與關係用圖。

每張圖表都應回答具體問題，旁邊的文字解釋如何閱讀及可以得到什麼結論。圖中文字需能隨版面閱讀，符合既有響應式規範；箭頭說明方向或關係，條件性架構與已確認架構有所區別。統計圖需有資料依據。

結尾指出讀者接下來可以檢查、練習或深入學習的項目，連到相關教材。文章不必加上重複前文的口號式總結。

## 10. 尊重案例中的人與公開範圍

聚焦資訊、技術條件與處理選擇，讓反思指向可以改善的步驟。描述問題時，說清楚哪個資料需要補齊、哪個設定需要確認、哪個角色可以接手。

- 以去識別化摘要承接對話，保留與技術問題相關的部分。
- 組織、姓名、網域、IP、帳號、內部截圖與原始紀錄依已確認公開範圍處理。
- 教學範例採適合示意的名稱與位址，例如 `example.com`；原始材料與合成資料分開保存。
- 公開 Git 中的 draft 仍是公開資料，未發布標記不提供保密。

## 11. 雙語與 AI 協作

繁體中文與英文各自完整可讀；翻譯保留相同主張、證據強度、時間與下一步。英文採自然表達，不要求逐字或段落數完全相同，章節 ID 與順序依資料模型對齊。

逐項比對數字、單位、版本、CVE、命令、來源與結論。當中文保留條件或不確定性時，英文也保留，避免翻譯擴大主張。

AI 可以協助擬大綱、解釋概念、改寫、翻譯與檢查一致性。編輯者仍需核對來源、事實與公開範圍。AI 不補造對話、實測輸出、作者經驗、來源、日期或完成狀態；缺少材料時，列出具體待補項目。

公開署名依 [WRITE-07](../article-standards.md#必須遵循的規則)，僅填作者或品牌名稱，例如 `CS Kairos Learn`。中英文文章、摘要與資訊列均不附加 AI 撰稿、翻譯或來源查核的固定說明，也不另設同義句。協作分工留在編輯工作紀錄，持續完成來源查核。

可直接用於協作的指示：

> 依本指南撰寫觀點文章。先確認目標讀者、核心問題與一句主要主張，再以臺灣慣用的繁體中文白話解釋。從讀者收穫與具體觀察切入，採正面、主動且有依據的語氣。將回報、觀察、推論與下一步自然區分；有不確定性時說明查證方法。只採用提供或已核對的材料，引用支持主張的來源。完成後檢查語氣、術語、邏輯、證據、公開範圍與中英一致性，將待補資料留在編輯清單。

## 12. 撰寫流程與發布前檢查

1. 使用[文章企劃與撰稿模板](writing-template.md)填寫讀者、核心問題、主張與來源。
2. 整理資料，確認公開範圍、觀察截止時間與待核項目。
3. 先完成中文敘事，再校閱術語、例子與判斷依據；依需要加入圖表。
4. 完成英文版本，對照技術內容與主張強度。
5. 依 [JSON 模板](template.json)整理正式來源；Markdown 作編輯工作稿，不自動發布。
6. 完成下列內容檢查及既有工程檢查，確認稿件後才變更發布狀態。

### 內容檢查

- [ ] 開頭明確說明讀者收穫，全文集中回答一個主要問題。
- [ ] 語氣直接積極；適用條件與待核問題具體，無空泛自我辯護。
- [ ] 使用臺灣慣用繁體中文，術語與用詞一致。
- [ ] 初次出現的關鍵術語有白話解釋，例子連回技術機制。
- [ ] 重要主張有觀察、來源或清楚的推理支撐。
- [ ] 他人回報、直接觀察、推論、方案與驗收結果各有準確表達。
- [ ] 日期、版本、來源與觀察範圍已核對；待確認事項有具體下一步。
- [ ] 程式碼與操作說明交代環境、影響及判讀方法；實測與示意明確。
- [ ] 圖表有閱讀目的，手機仍可閱讀，條件性關係標示清楚。
- [ ] 案例已去識別化，公開署名僅含作者或品牌名稱，實際協作分工留在編輯工作紀錄。
- [ ] 中英版本的數字、識別字、命令、條件與結論一致。
- [ ] 文末提供有用的下一步或相關教材。

### 交付檢查

- [ ] JSON 欄位與關聯符合內容驗證器，未混入編輯待辦或私人定位資訊。
- [ ] 發布日期與狀態經確認；draft／未來日期仍由共同發布機制排除。
- [ ] 完成適用的內容、型別、靜態與瀏覽器檢查，記錄實際結果。
- [ ] 將稿件完成、本機驗收與正式上線分開記錄；部署依本次授權範圍進行。

規則用於提高文章品質，不以禁詞掃描代替編輯判斷。若來源精確用詞與風格偏好不同，優先保留原意，並在敘事中補上讀者需要的解釋。

## 本機操作

`npm run preview:perspectives` 建立隔離副本並在 localhost:4179 提供合成文章。正式 content 不加入測試文章。`npm run preview:perspectives -- --build-only` 僅建置隔離預覽。

正式內容參照本目錄 template.json，填入完整雙語、署名、來源、日期與相關教材 ID，完成內容校對後才改為 published。沒有文章時列表呈現空狀態。日期到達後仍需要另一次授權建置。

連接埠已被使用時，預覽會在重建前停止，避免覆蓋正在閱讀的預覽；可用 `PERSPECTIVES_PORT=4180 npm run preview:perspectives` 選擇其他埠。`--build-only` 仍會更新隔離建置，請等建置完成再重新整理頁面。

## 瀏覽器驗收

執行 `npm run test:browser:perspectives`：先建立正常網站及隔離合成預覽，再以 Playwright 啟動獨立無介面 Chrome。需本機已安裝 Google Chrome；測試不使用既有瀏覽器設定檔，不控制個人分頁。測試伺服器只綁定 127.0.0.1 的 4186／4187 埠，結束自動關閉。

結果與失敗 trace 位於 `.local/perspectives-browser/`；完整頁面截圖位於其 `screenshots/` 子目錄。涵蓋中英雙語四種寬度、鍵盤焦點與捲動、無 JavaScript、搜尋索引失敗與恢復、觸控模擬及正式空狀態。瀏覽器模擬不等於實體手機或完整螢幕閱讀器認證。

## 全站共同規範

所有教學頁面遵循[文章與響應式閱讀規範](../article-standards.md)。既有歷史規則有差異時，以共同規範的閱讀品質與收合要求為準；資料契約及原始教材保留要求持續適用。

## 可重用的響應式圖解

章節可加入 `diagram`，資料契約與驗證在 [perspective-diagrams.ts](../../src/lib/perspective-diagrams.ts)，渲染由 [TeachingDiagram.svelte](../../src/lib/components/TeachingDiagram.svelte)承接。參考 [NAS 正式雙語資料](../../content/perspectives/nas-offline-recovery.json)。

每張圖包含穩定 `id`、`caption`、`description`、`note` 與 `groups`。群組的 `mode` 使用 `flow` 表示有向順序、`cards` 表示平行角色；每個節點包含 `title`、`body`、受限的 `icon` 和 `tone`。以節點文字寫明關係和前提，窄版重排後不依賴位置猜測連線。模型不接受任意 HTML、SVG 路徑或外部圖示。

修改雙語圖解後執行 `npm run generate:perspective-diagrams`，檢閱 `site/images/perspectives/` 的 SVG，再執行內容、型別及單元測試。匯出與搜尋共用正式內容；單元測試核對 NAS 圖解下載檔與產生器逐位元組一致。靜態目錄會公開，只有確認可公開的已發布文章才匯出；未來日期素材也要按公開資產審核。

`npm run test:browser:nas` 使用現有 `build/`，涵蓋兩種語言、四種尺寸、鍵盤下載、200% 文字、無 JavaScript 與導覽。先完成建置再執行；`NAS_BASE_URL` 可指定公開站驗收。瀏覽器模擬及文字倍增檢查與實體手機、完整輔助工具驗收分別記錄。

文章日期與版本資訊列依共同規範 [WRITE-06](../article-standards.md#原發布版本與修訂日期write-06)；原發布日保留，`updatedOn` 對應目前修訂，觀察截止日期獨立呈現。


## 文章語意版本

依 [WRITE-06](../article-standards.md#原發布版本與修訂日期write-06)，每篇觀點必填 `contentVersion`（例如 `1.0.1`），公開顯示 `v1.0.1`。初版 `1.0.0`；閱讀改善升 patch，新增範圍升 minor，重大變更升 major。同步維護 `updatedOn`、雙語 `updates` 及內部 `revision`，原發布日保持；驗證器拒絕缺漏或整數版本，頁面不可回退顯示 revision。NAS 本次遷移與誤標更正見 [發布回執](../releases/2026-11-01-nas-perspective.md#nas-semver-correction)。


NAS 漏洞公告的八圖範例見[內容設計](nas-cve-content-design.md)與[驗收回執](../releases/2026-11-01-nas-cve-patching.md)。執行 `npm run generate:perspective-diagrams` 同步下載檔；建置後 `npm run test:browser:nas-cve` 驗證兩語、尺寸、放大、鍵盤、無 JavaScript、搜尋及雙向閱讀連結。正式站使用 `NAS_CVE_BASE_URL=https://learn.cs-kairos.com npm run test:browser:nas-cve`，證據另存 `.local/nas-cve/live/`。
