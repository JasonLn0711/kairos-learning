| AES遴選 | [NIST 2001遴選報告](https://csrc.nist.gov/pubs/journal/2001/06/report-on-the-development-of-the-aes/final)摘要 | 五決選者含MARS、RC6、Rijndael、Serpent、Twofish；最後採Rijndael。128-bit區塊／最高256-bit金鑰／決選者這些共同條件不足以排除Rijndael。 |
| GCM語意 | [NIST SP 800-38D正式版及PDF](https://csrc.nist.gov/pubs/sp/800/38/d/final) §5.2.1、5.2.2、7.2、8及附錄A | AES-GCM是AES配GCM模式。發送端在選定秘密金鑰後，以明文、IV及AAD產生並列密文C與標籤T；AAD被認證但保持明文。接收端須有同一秘密金鑰、IV、AAD、C、T，認證解密輸出P或FAIL。失敗拒絕資料，不把未驗證明文交給應用程式使用。 |
| GCM IV與版本 | 同上§8；[Rev.1第二次pre-draft徵詢](https://csrc.nist.gov/pubs/sp/800/38/d/r1/2prd) | 同一金鑰的IV必須符合唯一性要求；重用可能嚴重破壞機密性與標籤認證。2026-06-01徵詢頁明示尚無實際草稿，僅是出版流程階段，意見期於07-31截止；不把徵詢內容當作取代2007正式版的新規定。 |
| 生日界限 | [IETF RFC 7146附錄A及§2.2](https://www.rfc-editor.org/rfc/rfc7146.html#appendix-A) | 針對同一金鑰處理資料的模式相關風險，64-bit區塊的量級為2^32區塊＝2^35 bytes＝32GiB；128-bit區塊為2^64區塊量級。此量級不是安全處理額度、精確50%門檻或達到即破解的保證；不同模式／協定另有更嚴格限制，也不能把AES的2^64直接當GCM用量上限。 |
| Sweet32 | [原研究者網站](https://sweet32.info/)及其2016年論文入口 | 研究針對長連線、同一金鑰、已知／重複明文等特定條件的64-bit CBC碰撞攻擊；以TLS 3DES與OpenVPN Blowfish示範，非任何Blowfish資料一到32GiB就必然被解密。原網站的當時產品預設不作2026現況引用。 |

## 本機獨立計算

以Python標準函式計算，假設365天等機率且每人生日互相獨立，23人至少兩人同生日的機率為 `1 − product((365−i)/365, i=0..22) = 0.5072972343239857`。教學可寫約50.7%；現實生日分布與閏日不在此簡化模型。

以整數獨立核算 `2**32 * 8 = 34359738368 bytes = 32 * 2**30 bytes`，故32GiB正確。供稿中的LaTeX雙重跳脫只作格式正規化，公式與單位保留；正文應有可選取的文字／程式區塊，不能留下失效的跳脫語法或只放圖片。
