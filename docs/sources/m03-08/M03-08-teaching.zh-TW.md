# M03-08｜防火牆與 IDS／IPS 如何影響掃描：用證據確認防護

## 一、先記住今天的結論

掃描結果、設備告警與真正擋下連線，是三種不同證據。看到 filtered，只能先記錄這次掃描無法確定入口是否開啟；看到告警，要核對是否實際阻擋；沒有告警，則要先確認監測設備看得到這段流量。

本單元回答一個問題：當掃描結果受到網路防護影響時，怎麼分辨「被觀察到」「被阻擋」與「還不知道」？前一單元學會保存掃描設定與輸出，這次把掃描端的紀錄接到防護端及服務端，建立可以交叉核對的說明。

## 二、從大樓的門禁、監視器與保全理解

想像你獲准檢查一棟大樓。大門門禁決定哪些人能進入；監視器記錄有人接近門口；保全發現異常時，可以攔下訪客。這是三種工作，不是每棟大樓都一定依同一順序配置三台設備。

- Firewall（防火牆）：依政策控制網路流量能否通過，像門禁。政策可能看來源、目的地、通訊協定、連接埠或連線狀態，實際能力依產品與設定而定。
- IDS，Intrusion Detection System（入侵偵測系統）：分析它看得到的活動並產生告警，像監視器加異常提醒。單純被動監測不等於流量一定經過它，也不等於它能直接攔截。
- IPS，Intrusion Prevention System（入侵防禦系統）：具備採取防護動作的能力，例如在流量通過的位置丟棄符合阻擋條件的封包，像能攔人的保全。

Packet（封包）是網路傳送的一小單位資料。Inline（串接式）表示流量需要經過設備；流量鏡像則是把副本送去監看。產品可以整合多種功能，所以要看部署位置、運作模式及規則動作，不能只看盒子上寫 IDS 或 IPS。[NIST 防火牆指南](https://csrc.nist.gov/pubs/sp/800/41/r1/final)、[NIST IDPS 指南](https://csrc.nist.gov/pubs/sp/800/94/final)

## 三、防火牆如何改變你看到的入口狀態

先把 TCP 想成建立連線前需要交換確認訊息的通訊方式。SYN 是要求開始連線的旗標；RST 是重設或拒絕連線的訊號。掃描器根據收到的回覆、沒有收到回覆及掃描方式，推論連接埠狀態。

防火牆常見處理包括 Allow（允許）、Drop（直接丟棄）與 Reject（拒絕並回覆）。若封包被無聲丟棄，掃描器可能只看到等待逾時；若設備回覆拒絕訊息，掃描器就多了一項可觀察證據。但逾時也可能來自丟包或回程問題，因此不能只憑一行輸出指定是哪台設備擋住。

- open（開啟）：依這次方法與回覆，掃描器判定該入口可接受對應通訊；不代表已登入或取得權限。
- closed（關閉）：掃描器收到支持「此入口未接受該連線」的回覆；仍須注意中間設備可能代送 TCP RST。
- filtered（受過濾影響）：掃描器無法確定入口是否開啟；不是「服務已關閉」的同義詞。
- open|filtered（開啟或受過濾）：兩種狀態仍無法區分；中間的直線表示「或」，不是兩項結論都成立。

同一服務從內網看是 open，從外網看是 filtered，兩份紀錄可以同時成立，因為來源與路徑不同。只有外網 filtered，也不能直接證明防火牆整體設定正確。[Nmap 狀態定義](https://nmap.org/book/man-port-scanning-basics.html)、[中間設備回覆的判讀限制](https://nmap.org/book/determining-firewall-rules.html)

## 四、偵測到、發出告警、阻擋成功，分別怎麼確認

Signature（特徵規則）可理解為「已知行為的比對條件」；Anomaly（異常）則是「偏離預期模式」。比對規則與觀察基準不同，就可能對同一活動做出不同判斷。告警是調查的起點，還不是入侵成功的證明。

False Positive（誤報）是把正常活動判為需要處理的異常；False Negative（漏報）是該偵測的異常沒有被報出。獲准掃描也可能符合掃描特徵，因此「這是授權活動」不會自動讓告警消失。應拿核准的來源、時段與範圍核對，而不是為了測試方便關掉監測。

具體讀規則時，要找 Action（動作）。以 Suricata 官方文件為例，alert 表示產生告警，drop 表示丟棄並告警，reject 會發送拒絕訊息；真正效果仍取決於運作模式與部署。畫面出現「掃描偵測」標題，不足以推斷已執行 drop。[Suricata 規則動作](https://docs.suricata.io/en/latest/rules/intro.html)

Threshold（門檻）與告警頻率設定，也會影響你看到的通知。為避免重複通知而限制告警數量，不一定等於停止封包處理。要分別查規則條件、告警限制及阻擋動作，不拿「只有一則告警」推論「只有一個封包」。本文只解釋判讀，不提供規避門檻的操作。[Suricata 門檻說明](https://docs.suricata.io/en/latest/rules/thresholding.html)

這兩份 Suricata 頁面查核時標示 9.0.0-dev，屬開發版文件；本文沒有假定你的設備使用該版本，實際規則語法與行為必須回查已安裝版本。

## 五、沒有告警時，先找可見範圍與紀錄缺口

Visibility（可見範圍）就是感測器實際看得到哪些活動。例如監視器只拍大門，不能用「大門畫面沒人」證明後門沒有活動。網路也是如此：流量可能走另一條路，鏡像可能缺少部分封包，感測器或紀錄傳送可能異常，加密也可能使它無法直接檢視應用內容。

調查可以從四個問題開始：這段流量經過哪裡？該處是否真的有感測器資料？規則是否啟用且適用這段活動？告警是否成功送到你正在看的介面？每一個回答都應附時間及來源，而不是看到空畫面就填「沒有攻擊」。

在正式環境，補足觀測應經過管理者確認，不為了看流量而自行解密他人通訊、變更網路路徑或停用防護。NIST 的 IDPS 指南可用來理解監測位置與偵測限制；其正式版為 2007 年，2012 年修訂草案後來撤回，並不是新的正式版本。[NIST 文件狀態與適用背景](https://csrc.nist.gov/pubs/sp/800/94/final)

## 六、完整例子：同一台測試服務，兩種來源

以下全部是原創、人工編寫的桌上演練紀錄，不是你的設備、不是真實掃描輸出，也沒有操作第三方目標。假設管理者核准在隔離實驗環境比對測試服務 TCP 8443；事先政策是「管理網段可用，測試外網不可用」。兩次測試採相同方法，時間相近；不提供可直接套到真實目標的命令。

- 09:00：管理網段的測試電腦 A 回報 open；服務端有對應連線紀錄。
- 09:02：測試外網的電腦 B 回報 filtered；邊界防火牆記錄 B 到該服務的封包遭 Drop，並附規則代號 FW-17。
- 09:02：監測介面出現「疑似連接埠探查」告警，規則動作是 alert。
- 09:02：服務端沒有找到 B 的對應連線紀錄；已核對本次查詢時間與紀錄來源，但仍保留紀錄完整性的限制。

先分開寫觀察：A 看得到服務，B 沒取得可判定入口的回覆；防火牆記錄了拒絕通過；監測介面告警了。再寫推論：這些相互對得上的紀錄，支持本次 B 的測試流量由 FW-17 阻擋，而不是因 IDS 的 alert 才被擋。

這個例子的合理結論是：「在本次來源、時間、方法及 TCP 8443 的範圍內，結果符合內部允許、外部限制的預期。」不能擴大寫成「所有連接埠都安全」「IPS 完全有效」或「沒有入侵」。

如果只有 B 的 filtered，沒有防火牆紀錄，也沒有服務端證據，就把原因寫成待確認。若防火牆時間差了幾分鐘、來源位址經過轉換，還要先核對時區、校時與 NAT（網路位址轉換），才知道是不是同一段流量。

## 七、防護工作的重點：降低暴露、保留偵測、驗證效果

掃描防護不是把結果藏起來就結束。可以先盤點哪些服務有業務需求、哪些來源真的需要連入，再由管理者關閉不必要服務、限制必要入口、維持修補與身分驗證。可用性也要保留，不能只確認外部被擋，卻讓合法使用者無法工作。

一份可採用的驗證計畫，應包含核准來源、目的服務、時間窗、允許的測試方式、預期允許與拒絕結果、停止條件、責任人及復原方式。若目的是驗證偵測，就保留正常偵測設定；若刻意加入測試例外，應另記條件，不能拿例外下的結果代表一般防護能力。

建議把證據依序整理：核准範圍與預期政策 → 掃描端原始結果 → 防護端規則與動作 → 服務端紀錄 → 有範圍限制的結論。這是調查整理順序，不是封包一定走過的設備順序。

可用一份簡單紀錄留下：測試時間與時區、來源與目的、協定與連接埠、工具版本與設定、實際回覆、防護規則及動作、服務紀錄、缺口與下一步。去識別化後再分享；真實位址、帳號與日誌細節依授權範圍保存。

## 八、安全練習：只讀上面的人工紀錄

環境是這份教材與空白筆記，不需安裝工具、掃描設備或更改設定。

第一步，將第六節各行標記為掃描端、防護端或服務端證據。第二步，找出哪一行支持「阻擋動作」，哪一行只支持「發出告警」。第三步，寫一句包含來源、時間、服務與限制條件的結論，再列一項仍需核對的證據。

預期成果是一段能追溯到紀錄的說明，而不是宣告整個系統安全。完成後保留你的練習筆記即可；因為沒有建立服務或更動環境，沒有系統清理步驟，也不需刪除任何正式紀錄。

## 九、小檢核

1. B 回報 filtered，同時 IDS 顯示 alert。這兩項是否已足以證明「IDS 把連線擋掉」？你還會找哪一項證據？
2. 同一個 TCP 入口，A 看是 open、B 看是 filtered。為什麼不必先認定其中一份結果錯誤？
3. 沒有任何告警時，請提出兩個應先檢查的觀測或紀錄問題。
4. 若測試計畫寫「對所有測試流量停用防護，再證明防護有效」，這個設計哪裡有問題？
