# CEH M04-07｜SNMP 列舉：為什麼查得到設備資料，卻不代表看得到全部？

這一課最重要的概念是：

SNMP 是讓電腦向網路設備詢問管理資訊的機制。但是，你查到的資料，只代表「你用這個身分、這種操作，在這次授權範圍內看得到什麼」，不代表設備裡只有這些資料。

我們用一間公司的網路設備來理解整堂課。

## 一、SNMP 是什麼？為什麼需要它？

想像你在一家醫院擔任資訊工程師。醫院有 100 台交換器（Switch）、20 台路由器（Router），還有許多伺服器。

今天主管問你：

「我們醫院現在有沒有交換器故障？哪些網路介面斷線了？設備運作多久了？」

你總不能每天跑到每台交換器旁邊，接上鍵盤或管理線，一台一台確認。

所以工程師需要一個「中央監控系統」，讓它可以遠端詢問設備。

這就是 SNMP（Simple Network Management Protocol） 的用途。

簡化示意：一個管理端，可以向多種網路設備查詢狀態。設備是否回答、回答哪些欄位，仍由設定與權限決定。

例如，監控系統可以定期詢問：

「交換器 A，你叫什麼名字？」

「交換器 B，你的第 3 個網路介面現在正常嗎？」

「路由器 C，你目前記錄的流量計數是多少？」

透過 SNMP，設備就可以回傳相應資訊。

這裡要分清楚：SNMP 不是遠端桌面，也不是一般的 SSH 登入。它主要透過一套標準化的管理物件，讀取狀態，並在支援與授權的情況下修改某些設定。

## 二、Manager、Agent、MIB、OID 到底是什麼？

這四個名詞很容易混淆，我們繼續用醫院比喻。

| 專有名詞    | 白話文               | 在醫院的比喻     |
| ------- | ----------------- | ---------- |
| Manager | 發出管理要求的系統         | 醫院中央管理室    |
| Agent   | 設備上負責處理要求的程式      | 每棟樓的設備管理員  |
| MIB     | 定義有哪些管理物件、資料型別及意義 | 管理資料的欄位規格書 |
| OID     | 指定某個管理物件的數字編號     | 每個欄位的編號    |

注意，這裡的 Agent 不等於 AI Agent。它是設備上的管理協定程式。

### 1. MIB：欄位規格書

假設醫院管理室制定了一份表格：

| 欄位          | 意義                     | 範例              |
| ----------- | ---------------------- | --------------- |
| sysName     | 設備名稱                   | lab-switch-01   |
| sysLocation | 設備所在位置                 | training-room   |
| sysUpTime   | SNMP 網路管理部分重新初始化後的經過時間 | 60000 TimeTicks |

MIB 就像這份表格的「規格定義」。

它說明 sysName 是什麼、資料類型是什麼、可以怎麼被存取。

但是 MIB 不是設備實際資料的完整副本。

如同你有醫院的人事資料欄位規格書，不代表你已取得全部員工的個人資料。

### 2. OID：精確指出你想查哪個欄位

電腦怎麼知道你要詢問 sysName，而不是 sysLocation？

靠 OID（Object Identifier）。

例如：

`1.3.6.1.2.1.1.5.0`

這串數字就是 `sysName.0` 的 OID。

三個常見的 SNMP 物件實例

sysUpTime.0

1.3.6.1.2.1.1.3.0

管理部分運作了多久？

sysName.0

1.3.6.1.2.1.1.5.0

設備叫什麼名字？

sysLocation.0

1.3.6.1.2.1.1.6.0

設備被設定在哪個位置？

你會發現，這三個數字幾乎一樣，只有後段不同。

原因是 OID 使用樹狀階層，像電腦的資料夾路徑。

在這三個純量物件中，最後的 `.0` 代表指定實例；如果是網路介面表格，則可能是介面索引，例如 `.1`、`.2`。

所以不能認為所有 OID 都要加 `.0`。




## 三、GET、GETNEXT、WALK、SET：四種不同的查詢觀念

當我們知道要查哪個 OID，接下來就要決定怎麼查。

GET

指定查詢某個欄位

像問櫃檯：「請告訴我 A 設備的名稱。」

如果有權限且資料存在，就取得該值。

GETNEXT

查下一個可存取的欄位

像問櫃檯：「按照資料編號，下一項我能查的資料是什麼？」

不一定是數字直接加一，也可能跳過無權讀取的欄位。

WALK

沿一段 OID 範圍連續查詢

像請櫃檯依序提供某一類設備的可查資料。

WALK 是工具執行多次查詢的方式，不是獨立的 SNMP 訊息種類。

SET

要求修改資料

像跟櫃檯說：「請把 A 設備的位置改成另一個房間。」

是否能修改，取決於物件實作與目前授權。不能因為 GET 成功，就認為 SET 也可以。

補充：Net-SNMP 的 `snmpwalk` 使用 GETNEXT；`snmpbulkwalk` 使用 GETBULK 批次取得資料。兩者都是沿 OID 範圍取得一系列值的工具。




最重要的是：

GET 成功只證明能讀。WALK 取得清單只證明這次可見。SET 是另一種需要額外權限的操作。

通訊埠也可以順便記下來：SNMP 查詢端點通常使用 UDP 161，Trap／Inform 通知的接收端通常使用 UDP 162。這是慣例，不代表所有環境都只能這樣配置。




## 四、SNMPv1、v2c、v3：為什麼版本會影響資安？

假設你是一位醫院網路管理員。

你每天都要透過網路向交換器查詢資訊。這時有兩個完全不同的問題：

第一個是：「設備如何確定你有資格詢問？」

第二個是：「詢問過程中，別人是否可能看到你傳送的資訊？」

這就帶到 SNMP 的版本與安全機制。

### SNMPv1／v2c：像拿著通關口令問櫃檯

早期的 SNMP 常使用一組叫做 `community string` 的字串。

例如 `public`、`private`，或管理者自行設定的字串。

設備可以根據字串及相關設定決定如何處理要求。

但有一個問題：傳統 SNMPv1／v2c 本身不會加密這些字串和管理內容。

所以具備適當網路觀察位置的人，有機會從封包看到相關資訊。

而且不要被名稱誤導：`public` 不是必然允許全世界讀取，`private` 也不是必然有修改權限。實際權限由設定決定。

### SNMPv3：把驗證身分與保護內容分開

SNMPv3 常見的 USM 安全模型有三個安全層級。

noAuthNoPriv

無認證、無加密

authNoPriv

有認證、無加密

authPriv

有認證、有加密

authNoPriv 的認證機制也提供受保護訊息的完整性檢查；authPriv 再增加內容機密性保護。三種層級都不能直接代表可讀寫哪些管理物件。

再用寄信解釋：

noAuthNoPriv 就像沒有可靠身分驗證，也沒有密封保護的信件。

authNoPriv 就像寄件者身分可以驗證，信件是否遭修改也有檢查機制，但內容仍可能被旁人閱讀。

authPriv 則再把內容放進加密信封中。

所以：

SNMPv3 不一定有加密。必須進一步確認實際安全層級，例如 authPriv，以及所使用的演算法與設定。




但這裡還有另一個重要觀念：即使使用 authPriv，也不能推論使用者可以存取所有設備資料。傳輸保護和存取權限是兩件事。

## 五、MIB view：為什麼兩個人查同一台設備，結果卻不同？

這是 M04-07 最關鍵的部分。

假設醫院有一台交換器，裡面有三項資料：

- 設備名稱：`lab-switch-01`
- 設備位置：`training-room`
- 管理部分經過時間：`60000 TimeTicks`

現在有兩位經過授權的工作人員。

同一台交換器：lab-switch-01

monitor-a

日常監控身分

設備名稱

管理經過時間

設備位置

admin-b

額外獲准讀取位置

設備名稱

管理經過時間

設備位置

示意：圖中只比較讀取權限，不代表 admin-b 有任何寫入權限。

假設 monitor-a 問：

「設備位置在哪裡？」

設備不提供該物件。

但 admin-b 問一模一樣的問題，卻得到 `training-room`。

你能說第一位使用者查不到，是因為設備根本沒有設定位置嗎？

不能。

因為資料實際存在，只是第一位使用者沒有讀取權限。

這就是 MIB view（管理物件可存取範圍） 的意義。

它不是控制畫面長什麼樣子，而是控制指定身分的操作能接觸哪些管理物件。

### VACM 是什麼？

VACM（View-based Access Control Model）就是處理這種存取控制的機制之一。

它可能根據使用者的安全身分、群組、安全模型、安全層級、context（要查詢的管理資料集合），以及執行什麼操作，選擇對應權限。

其中有三個很重要的範圍：

| 權限範圍        | 白話意思         |
| ----------- | ------------ |
| Read view   | 允許讀哪些資料      |
| Write view  | 允許改哪些資料      |
| Notify view | 哪些物件可納入傳送的通知 |

這三個範圍不是同一回事。




再延伸一個重點：假設 MIB 定義 `sysName` 是 `read-write`，這只是規格上允許讀寫該類物件，不是說 monitor-a 就能修改它。

你可以想像一份醫院的人事表格，本來設計成可以修改員工電話，但不代表任何能打開表格的人都有編輯權限。

## 六、noSuchObject、noSuchInstance、endOfMibView 和 timeout 有什麼不同？

在 CEH 的列舉過程中，我們不能只看「有沒有查到」，還要看「設備究竟回覆了什麼」。

| 回覆               | 白話文意思                  | 能不能證明設備沒有這項資料？ |
| ---------------- | ---------------------- | -------------- |
| `noSuchObject`   | 這次可存取範圍內，找不到相符的物件      | 不能             |
| `noSuchInstance` | 有對應的物件類型，但指定的實例找不到     | 不能推論整個物件不存在    |
| `endOfMibView`   | 順著 OID 往後找，已沒有下一項可存取資料 | 不能             |
| `timeout`        | 沒等到設備回覆                | 不能，連原因都還不確定    |

前三者是 SNMPv2c／v3 操作中會見到的回覆例外；timeout 則是請求沒有在預期時間取得回應，不是一樣的協定回覆。




用圖書館來理解：

`noSuchObject` 像查詢系統說：「在你能檢索的目錄裡，找不到這個書目。」

`noSuchInstance` 像系統認得這一類書目，但你指定的那個編號沒有對應項目。

`endOfMibView` 像你沿著目錄順序查找，已經沒有下一筆可以提供的紀錄。

`timeout` 則像你打電話給圖書館，但沒有人接電話。你根本不知道是電話線壞掉、圖書館休息，還是對方拒絕接聽。

### 為什麼這很重要？

因為資安人員需要區分三件事：

沒有看到、沒有權限看到，以及確認不存在，是不同的證據狀態。

這個觀念不只適用 SNMP，也適用你前面學過的 SMB、NFS，甚至未來的 LDAP／Active Directory 列舉。

## 七、完整解讀教材的合成案例

我們把以下四筆查詢紀錄放在一起看。

模擬 SNMP 查詢紀錄

紙上案例

身分：monitor-a｜SNMPv3 authNoPriv

GET sysName.0

lab-switch-01

GET sysUpTime.0

60000 TimeTicks

GET sysLocation.0

noSuchObject

另一個已獲准讀取位置的身分

GET sysLocation.0

training-room

我們應該怎麼推理？

第一，monitor-a 能查到名稱和時間，代表它在這次條件下可以取得這兩項管理資料。

第二，monitor-a 查不到位置，原本存在多種可能性。但是管理者核對權限設定，發現位置被排除在 monitor-a 的 read view 之外。再由另一個獲准身分查到位置，便提供了資料存在且不對 monitor-a 開放的證據。

第三，monitor-a 沒有 write view，兩位使用者也都沒執行 SET。因此這份紀錄不能證明誰有能力修改名稱、位置或其他資料。

第四，authNoPriv 代表有訊息認證及完整性保護，但內容沒有加密。

### 為什麼 60000 TimeTicks 不能直接說設備重開機？

因為 TimeTicks 的單位是百分之一秒。

60000 ÷ 100 = 600 秒 = 10 分鐘

問題是 `sysUpTime` 量測的是設備的網路管理部分最後重新初始化之後經過的時間。

因此它可能與設備重新開機有關，也可能是管理部分重新初始化。單靠這個數字無法證明整台設備在 10 分鐘前重開機。這是 RFC 3418 對該物件的正式定義。




## 八、CEH 的觀點：我們到底在列舉什麼？

從 CEH M04 Enumeration（列舉）的角度來看，SNMP 是另一個能提供系統資訊的服務。

在明確授權的資安盤點或測試中，可以透過它理解設備名稱、管理介面、某些版本資訊及網路狀態等。

但列舉取得資訊，不代表取得控制權，更不代表已經找到可利用的弱點。

例如查到設備的韌體版本，只能把它當作後續漏洞查核的線索。還需要比對產品型號、受影響版本、修補情況以及實際配置，才能判定漏洞是否適用。

### 如果你是醫院資安負責人，應該怎麼防護？

防護重點不是把所有 SNMP 都關閉，而是先確認是否有監控需求，再限制管理來源與權限。

需要 SNMP 時，優先評估使用適當設定的 SNMPv3 authPriv，並限制誰能連線、哪些 OID 能讀取、哪些可以寫入。一般監控帳號通常不需要寫入權限。

驗收時應在授權範圍內確認正常的查詢可成功，受限制的物件沒有洩露，使用的安全層級符合要求。也要保留查核證據，但不要把 community string、認證密碼或金鑰放進公開紀錄。

這裡有一個很重要的資安思維：

好的權限設計，不是每個人都看得到所有資料，而是每個人只取得完成工作所需要的資訊。

## 九、用一個框架記住整堂課

SNMP 安全性可以分成四個層次來判斷：

01

能否連線？

網路路徑、服務、UDP 埠與相關設定

02

通訊有沒有保護？

SNMP 版本、認證、完整性與加密

03

能讀取哪些資料？

身分、context、read view 與實作

04

能不能修改資料？

物件可寫性、write view 與實際授權

這四層要分開判讀，不能因為其中一層成立，就推論後面幾層全部成立。

## 十、理解檢核：換你當資安工程師

情境一：某設備使用 SNMPv3 authNoPriv，管理者說「我們已經使用 v3，所以管理資料一定加密」。你同意嗎？為什麼？

想想版本和 security level 的差別。

情境二：帳號 A 查不到設備位置，帳號 B 卻查得到。你認為應檢查什麼設定，才能確認原因？

想想身分、context 與 read view。

情境三：MIB 標示 sysName 為 read-write，而帳號 A 可以 GET sysName。這能證明它可以 SET 修改名稱嗎？

想想規格能力與實際寫入授權。

你可以整理這三題的答案，帶到教學討論中請老師批改。此頁不會傳送或儲存作答。

這一課最值得帶到下一單元的能力，是學會區分實際觀察到的結果、權限造成的限制，以及還沒有證據支持的推論。這也是後續理解 LDAP／Active Directory 列舉時的重要基礎。
