# CEH M01-04｜Attack Surface、Attack Vector
## 攻擊面與攻擊向量：先看有哪些接觸點，再看可能怎麼出事

Module 01：Introduction to Ethical Hacking（道德駭客入門）

這一課先記住一句話：**攻擊面是在看「有哪些地方可能被接觸、影響或拿走資料」；攻擊向量是在看「攻擊者可能透過什麼途徑與方式下手」。**

兩者有關，但不是同一件事。**有入口，不等於有漏洞；有漏洞，不等於攻擊成功。**

前面 M01-02 在問「什麼值得保護、可能受什麼傷害」，M01-03 確認「誰允許我們測、可以測到哪裡」。現在才往下看：在授權範圍內，哪些接觸點需要被檢查？

以下都是虛構教學情境，不涉及真實網站、帳號或測試操作。

## 一、先用一間店理解：門窗清單，跟闖入方式不一樣

想像你開了一間咖啡廳，有正門、後門、外送取餐窗口，還有接聽訂單的電話。

這些地方都是店裡與外界互動的接觸點。店必須營業，所以有門、有窗口本身並不是錯誤。

現在有兩種可能的危害：

- 有人趁後門沒鎖，進到只有員工能進的區域。
- 有人打電話假冒店長，騙員工把當天營業款轉出去。

第一個案例透過實體入口，第二個案例透過人員與作業流程。它們下手的方法不同，造成的後果也不同。

對照到資訊系統：

- **攻擊面（Attack Surface）**：需要盤點與保護的接觸點集合。
- **攻擊向量（Attack Vector）**：攻擊者可能採用的途徑或方法。
- **弱點（Vulnerability）**：這個途徑中可能被利用的防護不足，例如門鎖壞了，或付款前沒有核對身分。

這只是幫助理解的比喻。真正的系統除了「進去」，還可能被干擾而無法服務，或透過輸出介面讓資料流出去，因此不能只盯著登入入口。

## 二、Attack Surface：不是只有公開網站，也不是漏洞清單

NIST 將攻擊面描述為系統、元件或環境邊界上的一組接觸點；攻擊者可能從這些地方嘗試進入、造成影響或取出資料。重點是**可能接觸到哪裡**，不是已經證實哪裡被攻破。[NIST：Attack Surface](https://csrc.nist.gov/glossary/term/attack_surface)

以一個線上教材平台來說，你可以從幾個角度看：

- **網站與應用程式**：登入、忘記密碼、檔案上傳、搜尋、資料匯出，以及 API。API 可以先理解成「讓程式跟另一個程式交換資料或提出要求的介面」。
- **網路與設備**：對外服務、遠端管理入口、內部檔案伺服器、員工筆電。
- **身分與權限**：一般使用者、老師、管理員、第三方整合程式，各自能使用哪些功能。
- **人員、實體與流程**：客服收件匣、帳號復原流程、訪客進出、可接觸的設備與外接媒體。

這是本課方便盤點的分類，不是唯一的官方分類表。OWASP 的應用程式攻擊面分析特別提醒，要看資料與命令的進出路徑，也要看不同角色與權限；只列出網站首頁，通常不夠。[OWASP：Attack Surface Analysis](https://cheatsheetseries.owasp.org/cheatsheets/Attack_Surface_Analysis_Cheat_Sheet.html)

### 1. 對外攻擊面與內部攻擊面

「從網際網路可以接觸」與「必須先進入內部網路或登入帳號才能接觸」，是不同條件。

例如，公開登入頁屬於對外接觸點；只有登入後才能使用的教師匯出功能，也仍然要保護。攻擊者可能取得某個帳號，或本來就是具有部分權限的人。

所以，**不對外公開，不等於沒有攻擊面；已經登入，也不等於可以使用所有功能。**

### 2. 攻擊面會隨著改動而改變

新增一個「讓老師上傳教材」的功能，可能同時新增檔案接收、儲存、預覽與下載流程。即使網站的網域沒有增加，應用程式需要檢查的範圍仍然可能變大。

反過來，移除不用的舊管理介面，可以減少需要維護的接觸點。但不能只用「入口數量」評斷安全：一個能操作全部學員資料的管理入口，可能比十個公開圖片頁更值得優先保護。

## 三、Attack Vector：要說清楚「怎麼下手」，以及成立條件

英國 NCSC 用攻擊者取得未授權存取的方法來說明 Attack Vector。你可以把它記成：**不是只指出門在哪，而是描述可能怎麼利用這個入口。**[NCSC：資安術語表](https://www.ncsc.gov.uk/section/advice-guidance/glossary)

幾個辨認例子：

- 員工信箱是接觸點；透過假冒通知，引導員工到假登入頁輸入帳密，是一種可能的攻擊向量。
- 對外網站是接觸點；利用網站某項已確認的軟體漏洞取得未授權能力，是另一種可能的攻擊向量。
- 帳號復原流程是接觸點；假冒帳號持有人，騙客服重設登入方式，也可能是攻擊向量。

看到這些描述時，不要直接補成「一定會成功」。要繼續問：

1. **接觸得到嗎？** 是網際網路可達、僅內網可達，還是必須到設備現場？
2. **需要什麼身分？** 不用登入、一般帳號，或已經需要管理權限？
3. **需要誰做什麼？** 例如是否需要使用者開啟檔案、輸入資訊或同意某個要求？
4. **依賴什麼弱點？** 是軟體漏洞、錯誤權限，還是未核實身分的流程？
5. **現有防護是否阻斷？** 例如額外驗證、權限限制、隔離或內容檢查。

這些條件是在幫你把「聽起來有可能」變成可以查證的假設。**描述可能向量，不等於已證明該向量在這個環境可行。**

另外，一個接觸點可能有不只一種向量；一條完整攻擊路徑也可能串起多個接觸點與方法。不能把整個事件硬塞成「一個入口只對應一個攻擊」。

## 四、把信任邊界一起看，才知道哪裡該重新檢查

**信任邊界（Trust Boundary）**，可以先理解成：「資料或操作要求跨過這裡後，不能沿用原本的信任，必須依另一側的規則重新檢查。」

例如：

- 使用者的瀏覽器 → 平台伺服器：使用者送來的資料不能直接當成可信資料。
- 一般學員 → 教師功能：有登入身分，不代表具有教師權限。
- 平台 → 第三方服務：合作關係不代表可以交換所有資料。

OWASP 的威脅建模會把資料流、元件與信任邊界畫出來，幫助找出需要驗證與防護的位置。[OWASP：Threat Modeling](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html)

用一個最直覺的例子來看：網頁上把「管理員按鈕」藏起來，不代表伺服器已經限制管理員操作。按鈕是畫面；真正收到要求的系統，仍要核對目前使用者是否有權執行。

這也連到兩個你後面會常看到的詞：

- **Authentication（身分驗證）**：你是誰？
- **Authorization（權限授權）**：以你的身分，可以對這筆資料做什麼？

不能只檢查「是否已登入」，就跳過「是否有權存取這份資料」。OWASP 建議對每個請求檢查權限，並以最小權限與預設拒絕作為設計原則。[OWASP：Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

## 五、完整例子：Northstar 的學員報告下載功能

假設虛構的 Northstar 教材平台有三個功能：公開課程介紹、學員登入、個人學習報告下載。

規則很清楚：每位學員只能下載自己的報告；教師只能下載被授權班級的報告。

### 第一步：辨認資產與攻擊面

需要保護的資產，是學員的私人學習報告。

報告下載功能及其後端介面，是需要檢查的攻擊面之一。它必須存在，才能提供正常服務；**功能存在本身不是弱點。**

### 第二步：提出可能的攻擊向量

評估人員提出一個假設：如果一般學員向下載功能要求另一位學員的報告，伺服器會不會只看「已登入」，卻沒有檢查「這份報告是不是你有權讀的」？

如果缺少這項檢查，就可能透過下載介面進行未授權讀取。

注意，目前這是待驗證的假設，不是已經發現漏洞，更不是已經發生外洩。

### 第三步：在明確授權的測試環境驗證

假設團隊已批准使用測試帳號 A、B，以及不含真人資料的合成報告：

- A 下載自己的報告：應成功。
- A 要求 B 的報告：應被拒絕，而且回應不能帶出 B 的報告內容。
- B 下載自己的報告：應成功。

如果 A 真的取得 B 的合成報告，這才提供了「在這個測試條件下，物件存取授權失效」的證據。這類問題會在後面的 Broken Access Control、IDOR／BOLA 再詳細說明；現在先抓住「每份資料都要檢查你能不能看」。

即使測試成功重現，也不能直接說「所有正式學員資料都已被偷走」。測試證明的是特定條件下的防護問題；歷史上是否有人利用、受影響範圍多大，仍要另外調查。

### 第四步：修正並驗證沒有破壞正常服務

防護不是把下載按鈕藏起來，而是在伺服器端，依目前帳號與報告的授權關係決定是否提供資料。

修正後，重新確認 A 能取自己的報告、不能取 B 的報告，教師也只能取得授權範圍內的資料。這同時在確認：**該擋的有擋住，該提供的服務仍然可用。**

## 六、防護與證據：不是把所有門關掉就算完成

防護可以分成三種思考方向：

**第一，減少不必要的接觸點。**

停用不再使用的服務、移除舊測試介面、收回不再需要的帳號或整合權限。先確認用途與依賴，避免把正常業務一起關掉。

**第二，保護仍然需要的接觸點。**

例如更新軟體、逐筆檢查權限、限制高權限管理功能的存取條件。身分入口可採用合適的多因素驗證（MFA）；較能抵抗釣魚的驗證方式，能降低帳密被騙走後遭冒用的風險，但不能代替資料權限檢查。[CISA：Implementing Phishing-Resistant MFA](https://www.cisa.gov/sites/default/files/2023-01/fact-sheet-implementing-phishing-resistant-mfa-508c.pdf)

**第三，保留能驗證防護的證據。**

對 Northstar 這個案例，合理的證據包括：

- 哪個測試帳號、哪個權限角色，在什麼時間提出什麼要求。
- 系統允許或拒絕的結果，以及是否真的回傳報告內容。
- 修正前後的設定或程式變更紀錄。
- 正常功能與越權情境的複測結果。

紀錄要足以追溯，但不必為了「證明問題」蒐集真人報告、密碼或登入憑證；使用合成資料並遮蔽不必要資訊即可。

最後把證據界線記清楚：

- **看得到介面**：只能證明某種暴露或可達性。
- **測試重現未授權行為**：支持這個測試條件下存在防護問題。
- **有事件紀錄與其他佐證**：才進一步分析實際是否被利用及造成什麼影響。

只看到「拒絕存取」也不能替整個平台背書；只看不到異常日誌，也不能保證從未發生問題。結論要跟證據的範圍一樣大。

本課的記憶口訣是：**先盤點面，再分析路；交代條件，用證據下結論。**

## 七、一題小檢核

一家公司的員工信箱可以正常收信。某員工收到假冒 IT 部門的信件，要求到另一個網站輸入公司帳密；目前只知道信件已寄達，沒有證據顯示員工點擊、輸入資料或遭人登入。

**請用自己的話說明：這個情境中的攻擊面與可能的攻擊向量各是什麼？現在能不能直接判定帳號已被入侵？**

不用背定義，用你自己的說法就可以。這題等你實際回答後，再確認哪些部分已理解；收到教材本身不等於已完成。
