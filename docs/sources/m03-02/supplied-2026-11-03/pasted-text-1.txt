# CEH M03-02｜主機探索：ICMP、ARP 白話文教學

**這一課最重要的觀念是：網路探索（Host Discovery）不是在證明一台電腦「存在或不存在」，而是在特定條件下，觀察某個網路位址有沒有回應，以及這個回應代表什麼。**

這是從 CEH M03-01 的 IP、TCP、UDP、Port，進入真正的網路掃描（Network Scanning）之前，必須建立的判斷能力。

本次依照你提供的 [CS Kairos M03-02 教材](https://learn.cs-kairos.com/courses/ceh/v13/m03/concepts/m03-02/?utm_source=chatgpt.com)，解釋第 2～5 節。

## 一、先建立整體概念：找人、確認回應、找到下一站

想像今天你要去一棟大樓找朋友。

你已經知道朋友住在哪個地址，但你還不知道：

1. 這個地址目前是否有人可以聯絡？
2. 如果打電話過去沒人接，是不是代表朋友不在？
3. 如果朋友住在同一棟大樓，怎麼找到他的房間？
4. 如果朋友住在另一棟大樓，應該先把東西交給誰？

這四個問題，正好對應到今天的網路概念。

| 概念 | 白話理解 | 真正要解決的問題 |
|---|---|---|
| Host Discovery | 確認一個地址有沒有活動跡象 | 哪些目標值得進一步確認？ |
| ICMP | 網路通訊的狀態通知 | 網路上的通訊有沒有回應或出現問題？ |
| Timeout | 等了一段時間，沒有收到預期回覆 | 為什麼沒有收到？目前能下什麼結論？ |
| ARP | 詢問本地網路中某個 IPv4 位址對應的 MAC | 如何把資料交給本地網路上的下一站？ |

注意：

**ICMP 與 ARP 並不是兩種功能完全相同的主機掃描技術。**

ICMP 主要提供 IP 通訊相關的控制與診斷訊息；ARP 則負責在常見的 IPv4 乙太網路環境中，解析本地下一站的鏈路層位址。

我們從這個差別開始理解。

# 2｜探索的成果：一筆有情境的觀察

## 2.1 什麼是 Host Discovery（主機探索）？

Host 是主機。

在網路環境中，主機通常指可以透過網路通訊的設備，例如你的 Ubuntu 電腦、NAS、伺服器或印表機。

Host Discovery 就是：

**透過特定的網路探測方式，尋找可能正在活動或具有可達性的網路位址。**

例如，你正在管理一間實驗室。

實驗室裡有：

- 一台 Synology NAS。
- 一台 Ubuntu AI 伺服器。
- 一台網路印表機。
- 一台網路路由器。

你希望了解哪些設備目前有回應。

如果你已經獲得網路管理授權，可以從指定的測試電腦，對核准的設備進行探測。

這個動作就屬於主機探索。

但是，這裡有一個重要問題：

**收到網路回覆，是否就代表設備一切正常？**

答案是：不一定。

例如，NAS 可能會回應 ICMP，但 DSM 管理介面已經故障。

或者一台印表機正在正常列印，但因為安全政策而不回應 ICMP Echo Request。

因此，主機探索通常只能提供有限的網路狀態證據。

## 2.2 為什麼不能只記錄「有回應」或「沒回應」？

假設你有兩份檢查紀錄。

第一份：

> 192.168.1.50：沒回應，疑似離線。

第二份：

> 2026-11-03 10:00（台灣時間），從測試電腦 192.168.1.10，向 192.168.1.50 發送 4 次 ICMP Echo Request；每次等待 1 秒，未收到預期的 Echo Reply。待查核 ICMP 政策、網路連線及設備狀態。

哪一份比較具有專業價值？

顯然是第二份。

因為第二份明確告訴我們：

- **從哪裡測試：** 192.168.1.10。
- **測試誰：** 192.168.1.50。
- **如何測試：** ICMP Echo Request。
- **什麼時候測試：** 2026-11-03 10:00。
- **測試條件：** 4 次、每次等待 1 秒。
- **實際觀察：** 沒有收到 Echo Reply。
- **目前未知：** 為什麼沒有回覆。
- **下一步：** 查核其他證據。

這裡有一個非常重要的資安調查原則：

**觀察（Observation）、推論（Inference）與結論（Conclusion）必須分開。**

例如：

| 層次 | 寫法 | 是否適當 |
|---|---|---|
| 觀察 | 4 次 ICMP Echo 探測均未收到回覆 | ✓ |
| 推論 | 可能是防火牆限制 ICMP | ✓，但尚待確認 |
| 推論 | 可能是設備關機 | ✓，但尚待確認 |
| 結論 | 這台設備確定不存在 | ✗，證據不足 |

你可以把主機探索理解成資安調查中的第一個步驟：

**先保存可重現的事實，再逐步排除其他可能性。**

這正是原始教材強調的「一筆有情境的觀察」，也符合 Nmap 官方文件對主機探索用途的說明：主機探索有助於辨識值得進一步檢查的目標，而不只是單純得到一份絕對可靠的線上設備名單。[CS Kairos Learning](https://learn.cs-kairos.com/courses/ceh/v13/m03/concepts/m03-02/?utm_source=chatgpt.com)

# 3｜ICMP：IP 網路的狀態回報

## 3.1 ICMP 究竟是什麼？

ICMP 的全名是 Internet Control Message Protocol（網際網路控制訊息協定）。

我們先回想 M03-01。

上一課學到，IP 負責網路定址與封包轉送。

但是，IP 有一個特點：

**IP 本身採用盡力傳送（Best-effort Delivery），並不保證封包一定能成功抵達。**

假設你寄出一個包裹。

物流公司可能遇到地址無法到達、轉送失敗，或者包裹超出某些傳送限制等情況。

如果物流系統能夠提供狀態通知，就可以讓寄件者知道部分問題發生在哪裡。

ICMP 的用途有點類似。

它負責提供與 IP 通訊有關的控制及診斷訊息，例如目的地無法到達，或者封包在轉送過程中超過允許的跳數。

但要注意：ICMP 並不能保證所有網路錯誤都一定會產生通知。[RFC Editor](https://www.rfc-editor.org/info/rfc792/?utm_source=chatgpt.com)

## 3.2 Ping 是什麼？跟 ICMP 有什麼關係？

你可能在 Terminal 使用過：

```bash
ping 192.168.1.1
```

Ping 是一個網路診斷工具。

它最常見的運作方式，是透過 ICMP 傳送 Echo Request（回音請求），並等待 Echo Reply（回音回覆）。

假設你使用的電腦為：

`192.168.1.10`

想測試的設備為：

`192.168.1.20`

你可以想像以下對話。

**第一步：你的電腦發送 Echo Request。**

意思是：

「192.168.1.20，你能收到我的訊息嗎？」

**第二步：目標設備收到訊息。**

如果設備允許並正常處理這類請求，就可能回傳 Echo Reply。

意思是：

「我收到了，這是對應的回音回覆。」

**第三步：你的電腦收到回覆並計算時間。**

例如：

```text
64 bytes from 192.168.1.20:
icmp_seq=1 ttl=64 time=2.15 ms
```

這是示意輸出，不是實際測試結果。

我們可以拆成幾個部分理解：

| 欄位 | 白話意思 |
|---|---|
| `192.168.1.20` | 回覆封包所顯示的來源 IP |
| `icmp_seq=1` | 第幾次 Echo 探測的序號 |
| `ttl=64` | 回覆封包抵達時剩餘的 TTL 值 |
| `time=2.15 ms` | 這次請求與回覆的往返時間 |

其中 `time=2.15 ms` 就是 RTT（Round-Trip Time，往返時間）。

簡單來說：

**從送出請求，到收到對應回覆，總共花了多少時間。**

你可以透過連續幾次 Ping，觀察當時的 RTT 與封包遺失情形。

不過，少量 Ping 結果不代表整體網路效能，也不能直接判斷網站的實際服務品質。

### 進一步理解：Echo Request 與 Echo Reply 如何區分？

在 IPv4 ICMP 中，常見的類型如下：

| ICMP Type | 名稱 | 用途 |
|---|---|---|
| 8 | Echo Request | 發送回音請求 |
| 0 | Echo Reply | 回覆回音請求 |
| 3 | Destination Unreachable | 回報目的地無法到達等問題 |
| 11 | Time Exceeded | 回報封包超出特定傳送限制 |

ICMP 訊息還有 Code（代碼），用來進一步描述特定類型的原因。

例如，Destination Unreachable 並不是只有一種原因。

不同 Code 可以表示網路無法到達、主機無法到達，或連接埠無法到達等情況。

這些定義來自 ICMP 的原始標準 RFC 792。[RFC Editor](https://www.rfc-editor.org/rfc/rfc792.html?utm_source=chatgpt.com)

## 3.3 為什麼 ICMP 沒有 TCP/UDP 的 Port？

這裡要把上一課的內容串起來。

TCP 與 UDP 都有來源 Port 和目的 Port。

但是 ICMP 沒有 TCP/UDP 那樣的連接埠欄位。

原因是它們負責的工作不同。

TCP/UDP 主要提供傳輸層的通訊介面，而 ICMP 是用來交換 IP 網路的控制與診斷訊息。

我們可以用下面這張概念圖理解：

```text
           應用程式
       HTTP、SSH、DNS 等
               │
        ┌──────┴──────┐
        ▼             ▼
       TCP           UDP
     有 Port        有 Port
        │             │
        └──────┬──────┘
               ▼
              IP
               ▲
               │
             ICMP
      IP 控制與診斷訊息
```

這是功能關係示意，並不是完整協定堆疊圖。

技術上，ICMPv4 訊息直接承載在 IPv4 封包中，並不需要先經過 TCP 或 UDP。

所以當你在 Wireshark 看到 ICMP 封包時，應該分析的是 ICMP Type、Code、識別碼與序號等欄位，而不是尋找 TCP/UDP Port。

# 4｜如何讀懂「有回覆」與「等待逾時」

這是本課最需要建立資安判斷能力的部分。

因為網路診斷最常見的錯誤之一，就是：

**看到 Ping 沒回應，就認定目標設備已經關機。**

實際上，這是證據不足的結論。

## 4.1 ICMP 探測可能出現哪些結果？

我把常見結果整理成一張圖。







:chatgpt-content-reference{index="10"}[下載圖 1：ICMP 三種結果 SVG 向量圖](sandbox:/mnt/data/ceh_m03_02_icmp_outcomes.svg)

我們逐一理解。

### 情況一：收到 Echo Reply

假設你執行：

```bash
ping -c 4 192.168.1.20
```

結果收到：

```text
64 bytes from 192.168.1.20: icmp_seq=1 ttl=64 time=1.50 ms
64 bytes from 192.168.1.20: icmp_seq=2 ttl=64 time=1.35 ms
64 bytes from 192.168.1.20: icmp_seq=3 ttl=64 time=1.42 ms
64 bytes from 192.168.1.20: icmp_seq=4 ttl=64 time=1.31 ms
```

這代表什麼？

表示你的電腦收到了對應的 ICMP Echo Reply。

在一般網路環境中，這是目標 IP 當時具有回音通訊可達性的證據。

但是，它不代表：

網站一定可以打開、SSH 一定能登入、資料庫一定正常，或者所有應用程式都能運作。

例如，一台 NAS 的作業系統仍然能處理 ICMP，但 DSM 的 Web 管理服務可能已經停止。

這時候 Ping 仍可能成功。

所以：

**Ping 成功，代表這次 ICMP 回音通訊成功；不代表設備上的所有服務都正常。**

### 情況二：收到 Destination Unreachable

假設你想把資料送到某個網路位址。

但是沿途的路由器無法找到可用的轉送路徑，或者主機無法完成特定交付。

這時候，你可能收到 ICMP Destination Unreachable。

例如：

```text
From 192.168.1.1:
Destination Host Unreachable
```

這段訊息的重要資訊，是 `From 192.168.1.1`。

它表示這個錯誤訊息的來源。

假設 `192.168.1.1` 是你的路由器，那麼你目前知道的是：

路由器回報某種無法到達的情況。

**這不是遠端目標主機親自告訴你「我已經關機」。**

而且，Destination Unreachable 也可能由本機網路堆疊產生，或由其他網路設備回報，必須依實際來源與 Code 判斷。

因此，分析時不能只看「Unreachable」，還要看是誰回報，以及回報哪一種錯誤。

### 情況三：收到 Time Exceeded

假設 IP 封包從台灣傳送到海外。

它可能需要經過好幾台路由器。

為了避免封包因路由問題而無止境地在網路中循環，IPv4 使用 TTL（Time To Live）欄位限制封包能經過的路由跳數。

每經過一次正常的路由轉送，TTL 至少會減少 1。

當 TTL 在轉送過程中減少到 0 時，路由器會丟棄該封包，並可能回傳 ICMP Time Exceeded。

這裡很容易產生誤解。

雖然名稱叫 Time Exceeded，但對一般 IPv4 路由轉送而言，它通常與 **TTL 跳數耗盡**有關。

並不是說封包經過了 5 秒或 10 秒，就自動產生這個訊息。

這個機制也是 Traceroute／Tracepath 類型工具能夠協助探索網路路徑的重要基礎。

### 情況四：Timeout（等待逾時）

假設你執行 Ping。

結果：

```text
4 packets transmitted, 0 received, 100% packet loss
```

你可能會認為：

「這台電腦不存在。」

但我們目前真正能確認的只有：

**在這次測試條件下，四次請求都沒有收到符合預期的 Echo Reply。**

為什麼會這樣？

可能有不同原因。

| 可能原因 | 實際情況 |
|---|---|
| 目標設備關機 | 無法處理請求 |
| 防火牆限制 ICMP Echo | 設備可能仍在線上 |
| 路由設定有問題 | 請求可能無法抵達 |
| 網路封包遺失 | 請求或回覆可能在途中遺失 |
| 設備休眠 | 暫時無法回應 |
| ICMP 受到限速 | 部分請求可能不會獲得回覆 |
| 回覆路徑有問題 | 請求可能抵達，但回覆無法返回 |

請注意，**Timeout 與 ICMP Time Exceeded 不是同一件事。**

Timeout 是測試工具等待預期回覆，但在設定期限內沒有等到。

ICMP Time Exceeded 則是一種實際收到的 ICMP 錯誤訊息。

這兩個概念在 CEH 與網路除錯中必須清楚區分。

## 4.2 為什麼防火牆可以讓 Ping 失敗，但網站仍然正常？

假設你有一台伺服器：

```text
IP：192.168.1.50
```

伺服器的安全政策是：

| 流量 | 政策 |
|---|---|
| ICMP Echo Request | 阻擋 |
| TCP/443 | 允許 |
| TCP/22 | 限制指定管理來源 |

這時候，可能發生：

```text
測試 ICMP：

電腦 ── Echo Request ──► 伺服器
                         │
                     防火牆阻擋
                         │
                      沒有回覆


測試 HTTPS：

電腦 ── TCP/443 ────────► 伺服器
                         │
                    允許連線
                         │
電腦 ◄──── HTTPS 回應 ────┘
```

因此，你可能無法 Ping 到伺服器，但可以正常開啟網站。

這個例子也說明了：

**主機探索（Host Discovery）與服務可用性測試（Service Availability Check）不能視為同一件事。**

對 CEH 來說，這個觀念非常重要。

因為下一個階段的 Port Scanning，就是要從「這個 IP 的活動跡象」繼續研究「哪些服務端點可能可達」。

# 5｜ARP：在本地找到下一站的 MAC 位址

## 5.1 為什麼已經知道 IP，還需要 MAC 位址？

現在我們要學習另一個很重要的概念：ARP。

ARP 是 Address Resolution Protocol（位址解析協定）。

要理解 ARP，先想像一個情境。

你的電腦想把資料傳給同一個區域網路內的 NAS。

你的電腦：

`192.168.1.10`

NAS：

`192.168.1.20`

你已經知道 NAS 的 IP 了。

那為什麼還需要 ARP？

因為 IP 位址與 MAC 位址，在網路中負責的事情不同。

我們先用一個生活例子理解。

### IP 像是郵寄地址，MAC 像是本地交付時使用的識別資訊

假設你有一份文件要寄到某棟辦公大樓。

你知道目的地地址，但文件到了當地配送網路後，仍然需要知道這一段實際要交給哪個收件端點。

在常見的 IPv4 乙太網路環境中：

IP 負責描述封包的網路目的地。

乙太網路則使用 MAC 位址標示每一段訊框（Frame）的來源和目的端點。

因此，當電腦準備把 IP 封包交給本地乙太網路上的下一站時，需要取得相應的 MAC 位址。

**ARP 的工作，就是協助取得下一站 IPv4 位址所對應的 MAC 位址。** [RFC Editor](https://www.rfc-editor.org/rfc/rfc826?utm_source=chatgpt.com)

## 5.2 MAC 位址究竟是什麼？

MAC 是 Media Access Control（媒體存取控制）。

在常見乙太網路中，MAC 位址通常是 48 位元。

例如：

```text
02:00:00:00:00:20
```

這是示範用的 MAC 位址。

MAC 位址可以用來識別特定鏈路上的網路介面。

例如，你的 Ubuntu 桌機有乙太網路介面，也有 Wi-Fi 介面，兩個介面可能具有不同的 MAC 位址。

但是，MAC 位址不一定永遠固定。

現在許多裝置支援 MAC 隨機化，也可以在特定環境中修改或偽造 MAC 位址。

所以：

**MAC 位址是網路通訊所使用的鏈路層識別資訊，不應直接當成不可偽造的設備身分證明。**

## 5.3 ARP 如何找到對應的 MAC 位址？

假設你的電腦 A：

```text
IP：192.168.1.10
MAC：02:00:00:00:00:10
```

另一台設備 B：

```text
IP：192.168.1.20
MAC：02:00:00:00:00:20
```

兩台電腦位於同一本地乙太網路。

A 想把資料傳給 B。

整個過程可以分成四個階段。

**第一步：A 先查詢自己的 ARP Cache。**

ARP Cache（ARP 快取）是電腦保存的 IP 與 MAC 對應資訊。

如果電腦已經有可用的對應紀錄，可能直接使用，不必重新發送 ARP Request。

**第二步：如果需要解析，A 發送 ARP Request。**

A 會在本地廣播範圍內詢問：

「誰使用 192.168.1.20？請告訴我你的 MAC 位址。」

一般 ARP Request 會以乙太網路廣播訊框發送。

廣播目的 MAC 為：

```text
ff:ff:ff:ff:ff:ff
```

這代表在該鏈路的廣播範圍內傳送，而不是指定單一接收端。

**第三步：B 回覆 ARP Reply。**

B 收到詢問後，如果自己正是被詢問的 IP 使用者，就可以回覆：

「192.168.1.20 對應的 MAC 是 02:00:00:00:00:20。」

**第四步：A 使用取得的 MAC 建立乙太網路訊框。**

A 便可以把要傳給 B 的 IP 封包放入乙太網路訊框中，並將 B 的 MAC 設為該訊框的目的 MAC。

之後再由本地網路設備完成交付。

這就是基本的 ARP 運作流程。

### ARP 與 ICMP 的差異

ARP 和 ICMP 雖然都可能協助我們了解網路設備，但工作位置不同。

```text
ICMP：

電腦 A
   │
   │ IP 封包內承載 ICMP
   ▼
目的 IP／中途網路設備
   │
   └── 回報控制或診斷訊息


ARP：

電腦 A
   │
   │ 本地鏈路上的 ARP Request
   ▼
同一廣播範圍
   │
   └── 詢問下一站 IPv4 對應的 MAC
```

這裡有個重要的技術差異：

ICMPv4 訊息承載在 IPv4 封包中。

而 ARP 訊息通常直接透過乙太網路訊框傳送，並不封裝在 IPv4 封包裡。

這會影響你將來使用 Wireshark 觀察封包時，應該從哪個協定層次分析資料。

## 5.4 ARP 是找目的地的 MAC，還是路由器的 MAC？

這是整個 ARP 單元最重要的問題。

**正確答案：ARP 解析的是本地下一站的 MAC，這個下一站不一定是最終目的地。**

請看這張對照圖。







:chatgpt-content-reference{index="12"}[下載圖 2：ARP 本地下一站 SVG 向量圖](sandbox:/mnt/data/ceh_m03_02_arp_nexthop.svg)

### 情境 A：兩台電腦在同一本地網路

假設：

你的電腦是 `192.168.1.10/24`。

NAS 是 `192.168.1.20/24`。

兩台設備位於同一條可直接通訊的本地乙太網路鏈路。

你的電腦透過路由表，判斷目的地屬於直接相連網路。

因此，這次下一站就是 NAS 本身。

所以要查詢的是：

`192.168.1.20` 對應的 MAC。

這時：

```text
IP 最終目的地：
192.168.1.20

Ethernet Frame 目的 MAC：
NAS 的 MAC
```

### 情境 B：你要連接另一個網路的伺服器

假設你的電腦仍然是：

`192.168.1.10/24`

預設閘道為：

`192.168.1.1`

但你想連線的遠端伺服器是：

`203.0.113.20`

這時候，你的電腦發現遠端 IP 不屬於直接相連的網路。

依照這個案例的路由設定，它會選擇把封包先交給預設閘道。

所以這次 ARP 要查的是什麼？

答案是：

**192.168.1.1，也就是閘道的 MAC。**

因為你的電腦需要先把這一段乙太網路訊框交給閘道，再由閘道依照路由資訊轉送。

因此：

```text
IP 最終目的地：
203.0.113.20

第一段 Ethernet Frame 目的 MAC：
192.168.1.1 所對應的 MAC
```

這裡的 `203.0.113.20` 是保留的文件示範位址。

實際運作中，路由選擇還會受到路由表、VLAN、介面設定及其他網路機制影響。

但核心觀念不變：

**IP 描述封包最後要送到哪裡；本地訊框的目的 MAC 則描述這一段要交給哪個鏈路端點。**

這個差別也是為什麼 ARP 無法直接跨越一般路由器，去取得網際網路上任意遠端設備的 MAC 位址。

## 5.5 ARP Cache 為什麼重要？

在 Ubuntu 中，系統會保存鄰居位址資訊。

例如：

```text
192.168.1.1 dev enp3s0 lladdr 02:00:00:00:00:01 REACHABLE
```

可以拆開解讀：

| 欄位 | 意思 |
|---|---|
| `192.168.1.1` | 鄰居的 IPv4 位址 |
| `enp3s0` | 本機使用的網路介面 |
| `lladdr` | Link-layer Address，鏈路層位址 |
| `02:00:00:00:00:01` | 對應的 MAC |
| `REACHABLE` | 核心鄰居狀態機目前認為該鄰居可達 |

除了 `REACHABLE`，你可能還看到：

`STALE`、`INCOMPLETE`、`FAILED`。

其中：

`STALE` 表示系統保存著對應資訊，但最近沒有足夠的新證據確認可達性。

`INCOMPLETE` 表示解析尚未完成。

`FAILED` 表示目前這次鄰居解析或可達性確認已失敗。

注意：

**看到 STALE，不表示設備確定離線；看到快取中的 MAC，也不表示這個對應關係剛剛才被確認。**

這些是 Linux 鄰居資訊管理中的狀態，而不是設備健康狀況的完整證明。[man7.org](https://man7.org/linux/man-pages/man8/ip-neighbour.8.html?utm_source=chatgpt.com)

## 5.6 ARP 有什麼資安風險？

這部分可以呼應後續 CEH 的 Sniffing 與 Man-in-the-Middle（中間人攻擊）。

ARP 的基本設計本身沒有提供足夠的密碼學身分驗證。

因此，在某些本地網路環境中，攻擊者可能偽造 ARP 資訊，讓其他設備建立錯誤的 IP 與 MAC 對應關係。

這就是 ARP Spoofing（ARP 欺騙）的基礎概念。

例如：

```text
正常情況：

電腦 A
  │
  └── 192.168.1.1 → 真正閘道的 MAC


受到 ARP 欺騙時：

電腦 A
  │
  └── 192.168.1.1 → 攻擊者聲稱的 MAC
```

如果錯誤對應被接受，部分流量可能被導向非預期設備。

因此，管理網路時不能只依賴 ARP 回覆判定設備身分，還需要搭配交換器管理紀錄、資產資料，以及適當的網路存取控制機制。

IPv6 則有另一套重要機制。

**IPv6 不使用 IPv4 的 ARP 進行鄰居位址解析，而是使用 Neighbor Discovery（ND）。**

ND 使用 ICMPv6 訊息完成鄰居探索、位址解析等功能。[RFC Editor](https://www.rfc-editor.org/info/rfc4861/?utm_source=chatgpt.com)

# 六、實際操作：在 Ubuntu 上觀察 ICMP 與 ARP

接下來用三個安全且容易重現的練習，將概念連接到真實系統。

## 實驗一：觀察 ICMP Echo

先測試自己的電腦：

```bash
ping -4 -c 4 -W 1 127.0.0.1
```

參數說明：

| 參數 | 作用 |
|---|---|
| `-4` | 使用 IPv4 |
| `-c 4` | 傳送 4 次 Echo Request |
| `-W 1` | 設定等待回覆的逾時參數為 1 秒 |
| `127.0.0.1` | 本機回送位址 |

這個測試可以檢查本機 IPv4／ICMP 回送功能。

它不會測試外部設備，也不需要透過乙太網路 ARP 尋找其他主機。[man7.org](https://man7.org/linux/man-pages/man8/ping.8.html?utm_source=chatgpt.com)

## 實驗二：觀察路由器與 ARP Cache

先輸入：

```bash
ip -br -4 addr
```

查看自己的 IPv4 位址。

接著輸入：

```bash
ip -4 route
```

查看路由表。

你可能看到：

```text
default via 192.168.1.1 dev enp3s0
192.168.1.0/24 dev enp3s0 proto kernel scope link
```

這是示意輸出。

第一行代表預設路由的下一站是 `192.168.1.1`。

第二行表示系統有一個直接相連的 `192.168.1.0/24` 網路。

接著輸入：

```bash
ip -4 neigh show
```

查看本機 IPv4 鄰居快取。

假設你自己管理的路由器確實是 `192.168.1.1`，而且允許進行測試，可以執行：

```bash
ping -4 -c 2 -W 1 192.168.1.1
```

再執行：

```bash
ip -4 neigh show
```

觀察是否出現閘道的 IPv4／MAC 對應資訊。

即使路由器不回覆 Ping，只要系統需要在本地乙太網路上與它通訊，仍可能完成 ARP 解析。

## 實驗三：觀察跨網段時的下一站

輸入：

```bash
ip -4 route get 203.0.113.20
```

這個指令會詢問 Linux 核心：

「假設我要送資料到這個目的 IP，目前路由會怎麼選？」

它只查詢路由決策，不會真的對該目標發送 Ping。

如果你的電腦有預設路由，可能出現：

```text
203.0.113.20 via 192.168.1.1 dev enp3s0 src 192.168.1.10
```

這表示：

最終目的地是 `203.0.113.20`，但本地下一站是 `192.168.1.1`。

這正好能夠驗證上一節的觀念：

**遠端 IP 不變，但第一段本地乙太網路交付所需的 MAC，通常是閘道的 MAC。**

# 七、把今天的概念接回 CEH 網路掃描

現在我們把這兩堂課串起來。

```text
主機探索 Host Discovery
        │
        ├── ICMP
        │   觀察 IP 通訊回應
        │
        └── ARP
            解析本地 IPv4 下一站
        │
        ▼
記錄觀察、限制與不確定性
        │
        ▼
確認哪些目標需要進一步檢查
        │
        ▼
Port Scanning
        │
        ▼
Service Detection
        │
        ▼
依授權範圍進行更深入的安全檢查
```

下一單元 M03-03 將進入 TCP Connect、SYN 與 UDP 掃描。

你會發現，之後的掃描其實是沿用這一堂建立的原則：

不能只因為沒有回覆，就直接判定目標不存在。

也不能只因為收到某種回覆，就認定所有服務都正常。

這是將掃描結果轉換成可靠資安證據的基礎。

## 最後整理：ICMP 與 ARP 的差別

| 問題 | ICMP | ARP |
|---|---|---|
| 主要目的 | IP 通訊的控制與診斷 | IPv4 本地下一站的位址解析 |
| 主要使用資訊 | IP、ICMP Type／Code | IPv4、MAC |
| 常見訊息 | Echo Request／Reply | ARP Request／Reply |
| 能否經路由器轉送到遠端 | ICMP 訊息可透過 IP 路由 | 一般 ARP 廣播不跨越路由器 |
| 收到回應的意義 | 取得特定 IP 通訊狀態證據 | 取得特定 IPv4／MAC 對應資訊 |
| 沒回應代表設備關機嗎？ | 不能直接判定 | 不能直接判定 |
| 常用 Ubuntu 工具 | `ping` | `ip neigh` |

**今天最重要的三句話：**

1. **ICMP 讓我們觀察 IP 通訊的狀態，但不能保證所有網路問題都會收到回報。**
2. **Timeout 代表指定條件下沒有收到預期回覆，不等於設備不存在。**
3. **ARP 協助解析本地下一站的 MAC；跨網段時，這個下一站通常是路由器。**
