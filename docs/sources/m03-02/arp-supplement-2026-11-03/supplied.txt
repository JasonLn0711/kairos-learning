# CEH M03-02｜主機探索：ICMP 與 ARP 白話文完整教學
**涵蓋第 2～6 節：探索紀錄、ICMP、回應判讀、ARP、同網段與跨網段**

## 一、先建立最重要的觀念：找得到電腦，不代表能使用它的服務

上一課 M03-01，我們認識了 IP、TCP、UDP 和 Port。

這一課要解決另一個問題：

**當你知道一台電腦的 IP 位址時，怎麼知道它是否真的存在、能不能連線，以及封包應該怎麼送過去？**

我們先想像一個生活情境。

假設你要寄送一份文件給另一棟大樓的朋友。

整個過程需要解決四個問題：

| 問題 | 生活中的例子 | 網路中的概念 |
|---|---|---|
| 我要找誰？ | 朋友住在哪個地址？ | IP Address |
| 文件先交給誰？ | 直接交給朋友，還是交給物流站？ | MAC Address、ARP、Gateway |
| 對方有沒有回應？ | 打電話確認對方是否接到通知 | ICMP、Ping |
| 對方能不能提供服務？ | 對方雖然接電話，但是否能幫我辦事？ | TCP、UDP、Port、Application |

這四件事情彼此有關係，但不能混為一談。

例如，你知道朋友家的地址，不代表朋友在家；朋友接了電話，也不代表他能夠幫你處理文件。

同樣地：

- 知道 IP，不代表設備目前在線。
- Ping 得到回覆，不代表網站服務正常。
- Ping 沒有回覆，不代表設備一定關機。
- 查得到 MAC 位址，不代表已經確認設備身分。

**這堂課的核心，就是學會區分「觀察到什麼」與「能夠證明什麼」。** [CS Kairos](https://learn.cs-kairos.com/courses/ceh/v13/m03/concepts/m03-02/?utm_source=chatgpt.com)

## 2｜探索的成果：一筆有情境的觀察

### 2.1 什麼是 Host Discovery（主機探索）？

假設你是公司的資訊工程師。

今天主管請你確認：

「實驗室有 20 台電腦，請幫我確認現在有哪幾台可以透過網路取得回應。」

你可以使用一些網路工具，向這 20 個 IP 位址發送探測訊息。

例如：

```text
你的電腦
192.168.1.10
      │
      ├────→ 192.168.1.20  有回覆
      │
      ├────→ 192.168.1.21  沒有回覆
      │
      ├────→ 192.168.1.22  有回覆
      │
      └────→ 192.168.1.23  沒有回覆
```

這個過程就叫做 **Host Discovery（主機探索）**。

但問題來了。

當你發現 `192.168.1.21` 沒有回覆，你可以直接向主管報告：

「192.168.1.21 已經關機」嗎？

**不行。**

因為你實際觀察到的只有：

「我發送了某種探測訊息，但沒有在指定時間內收到預期回覆。」

它可能關機，也可能是防火牆擋住了探測訊息。

這兩件事完全不同。

### 2.2 什麼是 Probe 與 Response？

我們先認識兩個英文名詞。

**Probe（探測訊息）**：你主動發送一個訊息，試著了解目標的狀態。

**Response（回應）**：目標設備或其他網路設備對探測訊息作出的回應。

例如：

```text
      你的電腦                     目標電腦
    192.168.1.10                192.168.1.20
         │                            │
         │──── Probe（探測）────────→│
         │                            │
         │←─── Response（回應）──────│
         │                            │
```

這個概念非常重要。

因為未來學習 Nmap、弱點掃描或滲透測試時，你會反覆使用同一個邏輯：

**發送特定訊息 → 觀察回應 → 根據證據推論狀態。**

### 2.3 為什麼不能只記錄「有」或「沒有」？

假設你今天使用 Ping，得到以下結果：

```text
192.168.1.20：有回覆
192.168.1.21：沒有回覆
```

這樣的紀錄還不夠。

比較專業的紀錄會是：

| 紀錄欄位 | 範例 |
|---|---|
| 探測來源 | 192.168.1.10 |
| 探測目標 | 192.168.1.20 |
| 探測方法 | ICMP Echo Request |
| 探測時間 | 2026-11-03 11:00（UTC+8） |
| 等待時間 | 每次最多等待 2 秒 |
| 探測次數 | 3 次 |
| 回應結果 | 3 次皆收到 Echo Reply |
| 平均延遲 | 2.3 ms |
| 初步結論 | 本次 ICMP Echo 往返通訊成功 |
| 下一步 | 檢查是否有需要驗證的應用程式服務 |

以上數值都是假設的教學資料。

為什麼這樣記錄比較好？

因為你的同事明天可以用相同條件重新測試。

如果結果不一樣，就能進一步比較：

究竟是設備狀態改變、網路路由改變，還是防火牆政策改變？

這叫做**可重現的觀察（Reproducible Observation）**。

### 2.4 這與 CEH 有什麼關係？

在 CEH 的網路掃描階段，我們希望逐步回答：

```text
有哪些 IP 位址？
       ↓
哪些位址有活動跡象？
       ↓
哪些 Port 有回應？
       ↓
哪些服務正在運作？
       ↓
這些服務是否存在安全問題？
```

這不是一次掃描就能全部證明的事情。

每個階段都需要不同證據。

例如，Nmap 的 `-sn` 可以用來執行主機探索，省略一般連接埠掃描；但主機探索不一定只使用 ICMP，也可能使用 ARP、TCP 或其他探測方式。[Nmap](https://nmap.org/book/man-host-discovery.html?utm_source=chatgpt.com)

**第 2 節最重要的觀念：**

> 網路探索不是急著宣稱「這台電腦存在或不存在」，而是準確記錄「我從哪裡、使用什麼方法，在什麼時間觀察到什麼結果」。

## 3｜ICMP：IP 網路的狀態回報

### 3.1 ICMP 到底是什麼？

ICMP 的全名是：

**Internet Control Message Protocol（網際網路控制訊息協定）**

我們先不要背這個英文。

想像郵局正在幫你送包裹。

正常情況下，郵局就是負責運送包裹。

但運送過程中，可能遇到一些問題：

包裹無法送達、找不到目的地，或者運送途中超出了允許的轉送限制。

這時候，郵局就需要一套機制，把這些狀態回報給寄件者。

**ICMP 就很像 IP 網路的狀態通知機制。**

它不是主要用來傳送網站內容，而是協助傳遞網路控制與診斷資訊。

需要特別注意：ICMP 能提供錯誤或狀態訊息，但不保證每次傳送失敗都一定會收到 ICMP 通知。[RFC Editor](https://www.rfc-editor.org/rfc/rfc792?utm_source=chatgpt.com)

### 3.2 Ping 和 ICMP 是什麼關係？

你可能已經使用過：

```bash
ping 192.168.1.1
```

這個指令是在測試與目標 IP 的網路回應情況。

以一般 IPv4 Ping 為例，它會使用兩種 ICMP 訊息。

**第一種：Echo Request（回音請求）**

意思是：

「192.168.1.1，你有收到我的訊息嗎？」

**第二種：Echo Reply（回音回覆）**

意思是：

「收到了，我回覆你。」

整個過程如下：

```text
        電腦 A                       電腦 B
     192.168.1.10                192.168.1.20
          │                            │
          │                            │
          │──── ICMP Echo Request ───→│
          │         Type 8             │
          │                            │
          │←──── ICMP Echo Reply ─────│
          │         Type 0             │
          │                            │
          │    往返時間 RTT = 2 ms     │
          │                            │
```

這裡的 Type 是 ICMP 用來區分訊息種類的欄位。

在 IPv4 ICMP 中：

| ICMP Type | 名稱 | 白話意思 |
|---|---|---|
| 8 | Echo Request | 我送出訊息，請你回覆 |
| 0 | Echo Reply | 我收到你的訊息了 |
| 3 | Destination Unreachable | 目的地或指定通訊無法到達 |
| 11 | Time Exceeded | 封包超過允許的限制 |

這些 Type 值是 IPv4 ICMP 的定義，不能直接套用到 ICMPv6。[RFC Editor](https://www.rfc-editor.org/rfc/rfc792?utm_source=chatgpt.com)

### 3.3 RTT 是什麼？為什麼 Ping 會顯示 ms？

假設你對目標電腦執行：

```bash
ping -c 3 192.168.1.1
```

其中：

`ping`：發送回音探測訊息。

`-c 3`：總共發送 3 次。

`192.168.1.1`：目標 IP 位址。此處只是範例，實際操作請換成你有權測試的設備 IP。

假設出現：

```text
64 bytes from 192.168.1.1: icmp_seq=1 ttl=64 time=2.1 ms
64 bytes from 192.168.1.1: icmp_seq=2 ttl=64 time=2.3 ms
64 bytes from 192.168.1.1: icmp_seq=3 ttl=64 time=2.0 ms

3 packets transmitted, 3 received, 0% packet loss
```

我們逐一看懂：

`icmp_seq=1`：這是第 1 次探測的序號。

`ttl=64`：收到的 IP 封包所剩的 TTL 值。

`time=2.1 ms`：這次探測測得的往返時間。

`0% packet loss`：三次探測都收到了對應回覆。

其中最容易誤解的是 `time=2.1 ms`。

它不是指封包從 A 到 B 單程花了 2.1 毫秒。

而是：

**A 發送訊息 → B 收到並回覆 → A 收到回覆，整個往返過程花費的時間。**

這個數值稱為 RTT（Round-Trip Time，往返時間）。

### 3.4 ICMP 不只有 Ping，還能告訴你封包出了什麼問題

假設你的電腦要把資料傳送到另一個網路。

```text
電腦 A
   │
   ▼
路由器 R1
   │
   ▼
路由器 R2
   │
   ▼
目標電腦 B
```

在傳送過程中，可能發生以下狀況。

**情況 A：Destination Unreachable**

假設路由器無法將封包送到指定目的地，而且會產生對應錯誤訊息。

它可能回報：

```text
Destination Unreachable
```

意思是：

「這個封包無法依照目前條件送到指定目的地。」

這種訊息可能由中間的路由器產生，不一定來自你要找的目標電腦。

**情況 B：Time Exceeded**

每個 IPv4 封包都有 TTL（Time To Live）欄位。

你可以先把 TTL 想成：

**封包最多還能經過多少次路由轉送。**

例如：

```text
電腦 A 發出封包：TTL = 3
         │
         ▼
路由器 R1：TTL 變成 2
         │
         ▼
路由器 R2：TTL 變成 1
         │
         ▼
路由器 R3：TTL 減至 0
         │
         ▼
       丟棄封包
         │
         └──→ 可能回傳 ICMP Time Exceeded
```

這個例子採用簡化的逐跳模型。

這裡要理解的是：TTL 雖然叫做 Time To Live，但在現代 IPv4 路由的實務判讀中，主要表現為路由跳數限制，而不是拿秒錶計算存活時間。

為什麼需要 TTL？

因為網路設定如果發生錯誤，封包可能在路由器之間不斷繞圈。

TTL 可以避免封包無限制地循環。

未來學習 `traceroute` 時，就會再次遇到 TTL 和 ICMP Time Exceeded。

**第 3 節最重要的觀念：**

> ICMP 不是單純的「Ping 協定」，而是一套讓 IP 網路回報控制與診斷訊息的機制。Ping 只是最常見的應用之一。

## 4｜如何讀懂「有回覆」與「等待逾時」

這一節是網路故障排除與資安掃描中非常重要的基礎。

### 4.1 Ping 有回覆，代表什麼？

假設你執行：

```bash
ping -c 3 192.168.1.20
```

結果：

```text
3 packets transmitted
3 received
0% packet loss
```

你可以得到什麼結論？

**可以說：**

「在這次測試期間，192.168.1.20 的 ICMP Echo 往返通訊成功。」

但是，不能因此認定：

「這台電腦的所有服務都正常。」

為什麼？

假設你有一台網站伺服器：

```text
網站伺服器：192.168.1.20

ICMP Echo    有回覆
TCP Port 22  無法建立 SSH 連線
TCP Port 80  沒有提供 HTTP 服務
TCP Port 443 HTTPS 服務發生錯誤
```

這完全有可能。

因為 ICMP 和 TCP 服務是不同的通訊機制。

你可以把它想像成：

**你打電話給餐廳，確認有人接電話，不代表餐廳現在有提供內用服務。**

同樣地，Ping 成功只能提供部分網路可達性的證據。

### 4.2 Ping 等待逾時，代表什麼？

假設結果變成：

```text
3 packets transmitted
0 received
100% packet loss
```

這代表你沒有在等待時間內收到預期的回音回覆。

但我們不能直接判斷目標電腦不存在。

因為可能有幾種情況。

**情況 A：目標電腦真的沒有開機。**

```text
你的電腦 ─── Ping ───→ 目標電腦
                         X
                       已關機
```

這是可能的原因之一。

**情況 B：防火牆擋住 ICMP。**

```text
你的電腦 ─── Ping ───→ 防火牆 ──X──→ 目標電腦
```

即使目標正常開機，也可能因為防火牆政策而沒有回覆。

**情況 C：封包在網路中途遺失。**

```text
你的電腦
    │
    ▼
路由器 A
    │
    X  封包遺失
    │
    ▼
路由器 B
    │
    ▼
目標電腦
```

也可能是回程封包遺失，而不是去程封包遺失。

**情況 D：目標不提供 ICMP Echo Reply。**

例如公司有一台印表機。

你能正常透過網路列印文件，但是 Ping 它卻沒有收到回覆。

原因可能是設備或管理政策沒有允許 Echo 回應。

這代表：

**同一台設備可以不回應 Ping，卻仍然正常提供其他服務。**

### 4.3 哪些是事實？哪些只是推論？

這是我建議在 CEH 學習時建立的習慣。







:chatgpt-content-reference{index="11"}[下載高解析度 SVG 向量圖](sandbox:/mnt/data/CEH_M03-02_主機探索證據判讀.svg)

這張圖有三個重要判斷：

收到 ICMP Echo Reply，代表本次 Echo 往返成功，但不代表網站、SSH 等服務正常。

ICMP Echo 等待逾時，代表沒有在指定時間收到預期回覆，但不代表主機一定關機。

收到 ARP Reply，表示有設備在本地鏈路提供 IP／MAC 對應，但不代表已經驗證對方的真實身分。

這正是 Nmap 官方文件強調多種主機探索方法的原因：只依靠 ICMP，可能遺漏沒有回應此類探測的設備。[Nmap](https://nmap.org/book/man-host-discovery.html?utm_source=chatgpt.com)

### 4.4 如果收到 Destination Unreachable 呢？

假設你看到：

```text
From 192.168.1.1:
Destination Host Unreachable
```

這與單純的 Timeout 不一樣。

它表示某個網路節點回報了無法到達的問題。

其中 `192.168.1.1` 可能是你的路由器。

這時候應該先檢查路由設定、下一跳與網路連線，而不是直接認定目標電腦已經關機。

**第 4 節最重要的觀念：**

> 有回覆，代表特定探測有得到回應；沒有回覆，代表這次沒有取得預期證據。兩者都不能直接代表整台設備的完整狀態。

## 5｜ARP：在本地找到下一站的 MAC 位址

現在我們要認識一個非常重要的問題：

**我們明明已經知道對方的 IP 位址，為什麼還需要 MAC 位址？**

### 5.1 先分清楚 IP 與 MAC 的工作

假設你要把包裹送給台北的朋友。

包裹上面寫著：

「台北市某某地址。」

這是最終目的地。

但是包裹要離開你所在的地區，可能必須先交給附近的物流站。

這就有兩種不同的地址概念。

IP Address：你最終想把資料送到哪裡。

MAC Address：在目前這一段本地網路中，應該把資料交給哪個網路介面。

所以你可以先這樣理解：

**IP 負責描述要送往哪裡，MAC 負責協助完成本地鏈路的交付。**

在常見的乙太網路中，實際傳送的單位稱為 Ethernet Frame（乙太網路訊框）。

你可以把它想成一個信封。

```text
┌─────────────────────────────────────┐
│ Ethernet Frame（乙太網路訊框）      │
│                                     │
│ 目的 MAC：下一站的網路介面          │
│ 來源 MAC：目前發送端的網路介面      │
│                                     │
│  ┌───────────────────────────────┐  │
│  │ IPv4 Packet（IP 封包）        │  │
│  │                               │  │
│  │ 來源 IP                       │  │
│  │ 目的 IP                       │  │
│  │                               │  │
│  │ 例如：ICMP Echo Request       │  │
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘
```

注意這是 IPv4 封包在乙太網路中傳送的簡化示意。

IP 封包可以放在乙太網路訊框裡，但 ARP 訊息本身是由乙太網路直接承載，不是放在 IPv4 封包裡。

### 5.2 ARP 到底在做什麼？

ARP 全名：

**Address Resolution Protocol（位址解析協定）**

它的主要工作是：

在常見的 IPv4 乙太網路中，找出本地下一跳 IP 位址所對應的 MAC 位址。[RFC Editor](https://www.rfc-editor.org/rfc/rfc826?utm_source=chatgpt.com)

假設：

```text
電腦 A
IP：192.168.1.10
MAC：AA:AA:AA:AA:AA:AA

電腦 B
IP：192.168.1.20
MAC：BB:BB:BB:BB:BB:BB
```

兩台電腦在同一個可直接通訊的本地網路。

A 想傳送資料給 B。

可是 A 目前只知道 B 的 IP，不知道 B 的 MAC。

怎麼辦？

### 5.3 第一步：ARP Request（ARP 請求）

A 會先檢查自己的鄰居快取是否已有 B 的 MAC 對應。

假設沒有，A 就會發送 ARP Request。

它想問的是：

「誰使用 192.168.1.20？請告訴 192.168.1.10。」

一般情況下，這個請求會透過 Broadcast（廣播）發送。

你可以把廣播想成：

**在同一個教室裡向所有人發問。**

```text
                電腦 A
             192.168.1.10
                  │
                  │ ARP Request
                  │
                  ▼
          本地廣播範圍
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
      電腦 B     電腦 C     電腦 D
    .1.20       .1.30       .1.40

問題：
「誰有 192.168.1.20？」
```

同一個廣播範圍裡的其他設備可能都會收到這個問題。

但一般情況下，真正使用 `192.168.1.20` 的設備才會回覆。

### 5.4 第二步：ARP Reply（ARP 回覆）

電腦 B 發現有人正在詢問自己的 IP。

於是 B 回覆：

「192.168.1.20 是我，我的 MAC 是 BB:BB:BB:BB:BB:BB。」

```text
電腦 A                            電腦 B
192.168.1.10                     192.168.1.20
    │                                │
    │────── ARP Request ────────────→│
    │                                │
    │←───── ARP Reply ──────────────│
    │      MAC = BB:BB:...           │
    │                                │
```

一般的 ARP Reply 會以單播方式回覆詢問者。

接著 A 就知道：

「如果我要直接把乙太網路訊框送給 B，目的 MAC 應該填什麼。」

### 5.5 第三步：ARP Cache（ARP 快取）

但是，每次傳送資料都要重新詢問 MAC，不是很浪費時間嗎？

因此作業系統會暫時記住查詢結果。

這個地方稱為 ARP Cache（ARP 快取）。

假設你查到：

```text
192.168.1.20 → BB:BB:BB:BB:BB:BB
```

下一次要傳送資料時，系統就可以使用仍有效的快取，不必每次重新廣播 ARP Request。

在 Ubuntu 中，可以使用：

```bash
ip -4 neigh show
```

查看 IPv4 鄰居表。

你可能看到類似：

```text
192.168.1.20 dev enp3s0 lladdr bb:bb:bb:bb:bb:bb REACHABLE

192.168.1.1 dev enp3s0 lladdr aa:bb:cc:dd:ee:ff STALE
```

這裡：

`dev enp3s0`：使用的網路介面。

`lladdr`：鏈路層位址，在這個例子中是 MAC。

`REACHABLE`：鄰居可達性狀態目前被系統認定為有效。

`STALE`：系統有舊的對應紀錄，但尚未重新確認近期的可達性。

要注意：**ARP Cache 是快取資訊，不是即時在線設備清冊。**

尤其不能把 `STALE` 直接解讀為設備離線，也不能把存在某個 IP／MAC 對應解讀為設備身分已經驗證。[Man7.org](https://linuxman7.org/linux/man-pages/man8/ip-neighbour.8.html?utm_source=chatgpt.com)

### 5.6 ARP 跟資安有什麼關係？

這裡可以連結到後面的 CEH 網路嗅探與攻擊防護課程。

因為 ARP 原本沒有完善的身分驗證機制。

假設電腦 A 問：

「誰是 192.168.1.1？」

但有一台惡意設備試圖冒充：

「我是 192.168.1.1，我的 MAC 是 XX:XX:XX:XX:XX:XX。」

如果設備接受了錯誤的 ARP 對應，就可能將原本要交給閘道的流量送往錯誤的網路介面。

這類風險與 **ARP Spoofing（ARP 欺騙）或 ARP Poisoning（ARP 毒化）** 有關。

因此，ARP 回覆提供的是位址對應的觀察，不能直接當成可信的身分證明。

**第 5 節最重要的觀念：**

> ARP 是 IPv4 本地鏈路中的位址解析機制，用來找出下一站的 MAC 位址。它能協助交付封包，但不能保證對方身分可信。

## 6｜同網段與跨網段：ARP 到底在問誰？

這一節是整堂課最值得理解透徹的部分。

因為我們即將把 IP、MAC、ARP、Subnet、Gateway 與 Routing 串成完整的運作流程。

### 6.1 先理解什麼叫同網段

假設有三台設備：

```text
電腦 A：192.168.10.10/24

電腦 B：192.168.10.20/24

路由器：192.168.10.1/24
```

這裡的 `/24` 是 CIDR 前綴長度。

對 IPv4 而言，它對應的子網路遮罩是：

```text
255.255.255.0
```

在這個例子中，網路範圍是：

```text
192.168.10.0/24
```

我們先假設這些設備都接在同一個允許直接通訊的區域網路，且路由設定正常。

那麼：

`192.168.10.10` 和 `192.168.10.20` 就屬於同一個本地網段。

相對而言：

```text
10.20.30.40
```

則不屬於這個 `/24` 網段。

**但實務上是否直接交付，最終仍要看作業系統的路由表，而不能只靠肉眼比較 IP。**

### 6.2 情境一：同網段，電腦 A 要傳資料給 B

假設：

```text
電腦 A：192.168.10.10

電腦 B：192.168.10.20
```

A 要傳資料給 B。

作業系統先檢查路由表。

發現：

「192.168.10.20 屬於我可以直接到達的網路。」

所以 A 接下來要做的是：

**查詢電腦 B 的 MAC。**

```text
電腦 A
192.168.10.10
     │
     │ ARP Request
     │ 誰有 192.168.10.20？
     ▼
電腦 B
192.168.10.20
     │
     │ ARP Reply
     │ 我的 MAC 是 BB:BB:...
     ▼
電腦 A
     │
     │ 封裝 Ethernet Frame
     │
     │ IP 目的地：192.168.10.20
     │ MAC 目的地：電腦 B 的 MAC
     ▼
電腦 B
```

注意：

A 不需要先把這個封包交給預設閘道。

因為路由表已經指出，B 可以在本地直接到達。

### 6.3 情境二：跨網段，電腦 A 要傳送資料到遠端

現在情況改變了。

假設：

```text
電腦 A：192.168.10.10/24

預設閘道：192.168.10.1

遠端電腦 B：10.20.30.40
```

A 想傳送資料給 B。

作業系統檢查路由表後，發現：

「10.20.30.40 不在我的本地網段，而且應該經由預設閘道送出。」

所以問題來了：

**A 應該 ARP 查詢 10.20.30.40，還是 192.168.10.1？**

答案是：

**查詢 192.168.10.1，也就是下一跳閘道的 MAC。**

原因很簡單。

A 現在無法直接把本地乙太網路訊框交給遠端 B。

它必須先交給路由器，再由路由器轉送。

完整示意：







:chatgpt-content-reference{index="13"}[下載高解析度 SVG 向量圖](sandbox:/mnt/data/CEH_M03-02_同網段與跨網段.svg)

### 6.4 為什麼 IP 目的地和 MAC 目的地會不同？

這是理解整個網路運作的關鍵。

假設：

```text
來源：
192.168.10.10

最終目的地：
10.20.30.40

下一跳閘道：
192.168.10.1
```

那麼，電腦 A 送出的第一段乙太網路訊框會是：

```text
┌──────────────────────────────────────┐
│ Ethernet Frame                       │
│                                      │
│ 來源 MAC：電腦 A 的 MAC              │
│ 目的 MAC：閘道的 MAC                 │
│                                      │
│ ┌──────────────────────────────────┐ │
│ │ IP Packet                        │ │
│ │                                  │ │
│ │ 來源 IP：192.168.10.10           │ │
│ │ 目的 IP：10.20.30.40             │ │
│ └──────────────────────────────────┘ │
└──────────────────────────────────────┘
```

為什麼？

因為最終要去的是 `10.20.30.40`，但目前這一段必須先把封包交給閘道。

所以：

**IP 目的地：遠端 B。**

**MAC 目的地：下一跳閘道。**

等到閘道收到封包，準備轉送到下一段乙太網路時，路由器會根據路由表決定新的下一跳，並使用適當的鏈路層封裝。

因此，MAC 位址通常會隨著不同的網路鏈路而改變。

IP 的最終目的地通常仍保持為原本的遠端電腦，但若途中存在 NAT 等位址轉換機制，就可能發生例外。

### 6.5 為什麼 ARP 不能直接查到網際網路上任何一台電腦的 MAC？

假設你的電腦在台灣，想連線到遠端的一台網站伺服器。

那你能不能直接發送 ARP Request：

「誰有遠端網站伺服器的 IP？請告訴我 MAC！」

一般情況下，不行。

因為 ARP 的廣播範圍通常受到本地第二層網路限制。

路由器不會把一般 ARP 廣播像 IP 封包一樣轉送到整個網際網路。

你可以想像：

你在宜蘭的辦公室裡大喊：

「台北某公司的資訊工程師在哪裡？」

聲音不會因為你喊得很大聲，就傳到台北的辦公室。

ARP 廣播也是類似的道理。

它只能在對應的本地鏈路範圍內發揮作用。

因此：

**跨網段時，通常不是使用 ARP 去查詢遠端目標的 MAC，而是查詢本地下一跳的 MAC。**

### 6.6 有兩個重要例外需要知道

**第一個：VLAN（虛擬區域網路）。**

即使兩台設備的 IP 看起來屬於相同子網路，也不保證它們處在相同的第二層廣播範圍內。

例如網路管理員可能使用 VLAN，把辦公室設備和實驗室設備分開。

如果兩台設備位於不同、未互通的 VLAN，原本的 ARP 廣播就不能直接抵達另一台設備。

因此，「IP 看起來是同網段」與「實際能夠直接通訊」不是完全相同的事情。

**第二個：Proxy ARP（代理 ARP）。**

某些路由器可以代替其他設備回答 ARP Request。

這表示：

你收到一筆 ARP Reply，也不代表實際發送回覆的設備，就是你想尋找的最終目標。

這在主機探索與資安資產盤點時，尤其值得注意。

另外，以上 ARP 說明主要針對 IPv4；IPv6 的鄰居位址解析通常使用 Neighbor Discovery（ND），而不是 ARP。[CS Kairos](https://learn.cs-kairos.com/courses/ceh/v13/m03/concepts/m03-02/?utm_source=chatgpt.com)

**第 6 節最重要的觀念：**

> 同網段時，通常 ARP 查詢目標設備的 MAC；跨網段時，通常 ARP 查詢本地下一跳閘道的 MAC。真正的下一跳應由路由表決定。

# 七、Ubuntu 實際操作：親自看見 IP、路由與 ARP

如果你想把今天的觀念變成實際能力，我建議在自己的 Ubuntu 電腦上完成以下練習。

先使用純查詢指令，不需要修改任何網路設定。

### 步驟一：查看自己的 IP 位址

```bash
ip -br -4 addr
```

假設結果：

```text
lo       UNKNOWN  127.0.0.1/8
enp3s0   UP       192.168.10.10/24
```

表示：

你的 `enp3s0` 介面有 IPv4 位址：

```text
192.168.10.10/24
```

這是後續判斷本地網段的起點。

### 步驟二：查看路由表

```bash
ip -4 route
```

假設結果：

```text
default via 192.168.10.1 dev enp3s0

192.168.10.0/24 dev enp3s0
```

第一行表示：

當沒有其他更適合的路由時，封包會透過 `192.168.10.1` 這個預設閘道送出。

第二行表示：

`192.168.10.0/24` 是透過 `enp3s0` 直接連接的網路。

### 步驟三：請系統告訴你，封包應該走哪一條路

這是我特別建議記住的指令：

```bash
ip -4 route get 10.20.30.40
```

假設結果：

```text
10.20.30.40 via 192.168.10.1 dev enp3s0 src 192.168.10.10
```

你可以把它翻譯成：

「如果要把封包送往 10.20.30.40，我會從 enp3s0 送出去，並且先交給 192.168.10.1。」

其中：

`via` 就是指定的下一跳。

`dev` 是輸出網路介面。

`src` 是系統為這條路由選定的來源 IP。

這個指令可以查詢核心預計採用的路由，而且**不需要真的發送封包到目標**。[man7.org](https://man7.org/linux/man-pages/man8/ip-route.8.html?utm_source=chatgpt.com)

### 步驟四：查看 MAC 位址對應

```bash
ip -4 neigh show
```

假設結果：

```text
192.168.10.1 dev enp3s0 lladdr aa:bb:cc:dd:ee:ff REACHABLE
```

這個時候，你就可以把前面學到的觀念串起來。

你的電腦想把 IP 封包送到 `10.20.30.40`。

路由表說：

「先交給 192.168.10.1。」

而鄰居表告訴你：

「192.168.10.1 的 MAC 對應目前是 aa:bb:cc:dd:ee:ff。」

因此，電腦就具備建立第一段乙太網路訊框所需的位址資訊。

這時你應該可以開始在腦中建立完整的畫面：

```text
我要送到哪裡？
      │
      ▼
查 IP 目的地
      │
      ▼
查 Routing Table
      │
      ▼
決定下一跳
      │
      ▼
查 Neighbor / ARP Cache
      │
      ├── 有可用對應 ─────────┐
      │                       │
      └── 需要解析 MAC        │
              │               │
              ▼               │
       發送 ARP Request       │
              │               │
              ▼               │
       取得 ARP Reply         │
              │               │
              └───────────────┤
                              ▼
                      封裝 Ethernet Frame
                              │
                              ▼
                      交付給本地下一站
```

需要注意，這是一般 IPv4 乙太網路的簡化流程。實際發送、快取狀態與鄰居確認機制還存在更多細節。

如果你想進一步直接觀察 ARP 封包，下一階段可以在自己管理、已獲授權的實驗網路中，使用 Wireshark 或 tcpdump。

# 八、將這堂課與 CEH 前後章節串起來

我們把前面的知識整理成一張整體地圖。

| CEH 概念 | 主要回答的問題 | 代表性工具或方法 |
|---|---|---|
| M02 偵察 | 目標有哪些已知資訊？ | DNS、WHOIS、公開資訊查詢 |
| M03 IP | 資料要送到哪個網路位址？ | IP 位址、路由表 |
| M03 ARP | 本地這一段要交給誰？ | `ip neigh`、ARP |
| M03 ICMP | 網路有沒有提供回應或錯誤資訊？ | `ping`、`traceroute` |
| M03 TCP／UDP | 目標的哪些通訊端點有回應？ | TCP／UDP 探測 |
| M03 Port | 哪個程式入口正在提供服務？ | 連接埠掃描、服務識別 |
| M04 列舉 | 能從服務取得哪些更詳細的資訊？ | SMB、LDAP 等授權查詢 |
| M08 網路嗅探 | 網路中有哪些封包與協定互動？ | Wireshark、tcpdump |

以後學習 Nmap 的 TCP SYN Scan、UDP Scan 或服務版本識別時，你會更容易理解：

為什麼不能因為 Ping Timeout，就直接排除某個目標。

也會開始理解，為什麼主機探索與連接埠掃描是兩個需要區分的工作階段。

# 九、五個觀念，濃縮今天的學習成果

| 概念 | 一句話理解 |
|---|---|
| **Host Discovery** | 找出哪些位址具有可觀察的網路活動跡象 |
| **ICMP** | 提供 IP 網路的控制、狀態與診斷訊息 |
| **Timeout** | 在指定等待時間內，沒有收到預期回覆 |
| **ARP** | 在 IPv4 本地鏈路中，解析下一跳的 MAC 位址 |
| **Gateway** | 當目的地需要跨網段轉送時，通常由閘道負責下一段傳遞 |

我建議特別記住這個關係：

**IP 決定最終目的地；Routing 決定下一跳；ARP 協助找出本地下一跳的 MAC；ICMP 協助觀察網路通訊狀態。**

這四件事串在一起，就能解釋一台電腦如何開始把資料送往另一個 IP 位址，以及你應該如何判讀探測結果。

## 十、理解檢核：你能解釋下面這個網路情境嗎？

假設你正在管理一個實驗室網路：

```text
你的電腦 A
IP：192.168.10.10/24

印表機 B
IP：192.168.10.20/24

預設閘道
IP：192.168.10.1

遠端伺服器 C
IP：10.20.30.40
```

你進行以下觀察：

第一，你對印表機 B 執行 Ping，結果全部 Timeout。

第二，你使用 ARP，取得了聲稱對應印表機 B 的 MAC 位址。

第三，你要連線到遠端伺服器 C。

請試著回答：

**問題 1：** 印表機 B 的 Ping 全部 Timeout，是否代表它已關機？你還需要什麼證據？

**問題 2：** 既然印表機 B 沒有回覆 Ping，為什麼你仍可能收到它的 ARP Reply？

**問題 3：** 當你要連線到遠端伺服器 C 時，你的電腦需要 ARP 查詢哪個 IP 的 MAC？為什麼不是直接查詢 C？

**問題 4：** 在送往 C 的第一段乙太網路訊框中，IP 目的地與 MAC 目的地分別屬於誰？

這四題能檢查你是否真正理解 ICMP、ARP、路由與網段之間的關係，而不只是記住名詞。
