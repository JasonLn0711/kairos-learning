# CEH M09-06｜獨立驗證與反釣魚控制

Module 09：Social Engineering（社交工程）
路線原名：Independent Verification & Anti-Phishing Controls。建議閱讀 10～15 分鐘。

## 一、先說結論：不要讓可疑要求，自己提供「它是真的」的唯一證明

有人傳訊息說：「我是主管，請把資料傳到這個新網址。不放心就打下面這支電話確認。」你真的打了電話，對方也說沒問題。這樣算查證完成嗎？

**不一定。因為要求、電話和回答，可能都由同一個人安排。**

今天要學的不是把每個人都當成騙子，而是：**重要行動之前，從原本就可信的來源，確認「誰提出、究竟要做什麼、是否獲得授權」；再用多層控制，讓單一失誤不至於直接造成重大損害。**

上一課 M09-05 提醒我們，合法帳號不代表每項行為都合法。本課把這個判斷變成可以執行的流程，也收束整個社交工程章節。

## 二、圖1：先把「要求」與「證明」放在不同的信任範圍

**Independent Verification（獨立驗證）**：查證所使用的依據，不完全依賴正在被懷疑的訊息或對方提供的管道。

像是收到「銀行帳號異常」訊息，你不必點它的連結，而是自行開啟原本安裝、已確認的官方 App，或使用自己先前確認過的官方聯絡方式查詢。FTC 也建議使用已知真實的電話或網站，而非可疑信件提供的聯絡資訊。[FTC：辨識與避免釣魚](https://consumer.ftc.gov/articles/how-recognize-avoid-phishing-scams)

**Trust Boundary（信任邊界）**，白話就是：這一邊的內容，還不能直接被另一邊當成可信指令。圖1把「收到的說法」與「有權執行的行動」分開；中間必須有查證與授權。

「獨立」不是只換一個 App，也不是只多問一次：

| 做法 | 是否補上獨立依據？ | 原因 |
| --- | --- | --- |
| 回覆原信問「真的是你嗎？」 | 通常沒有 | 原信帳號若被接管，回答仍由同一方控制 |
| 打信裡新提供的電話 | 通常沒有 | 聯絡資訊本身尚未核實 |
| 用原有通訊錄的電話回撥 | 有助於獨立查證 | 聯絡資訊不是從這封可疑訊息取得，但仍須確認具體要求 |
| 開啟既有官方系統，看核准單 | 有助於獨立查證 | 查的是既有流程中的紀錄，還要核對範圍及有效性 |

**獨立不是絕對安全保證。** 如果原通訊錄已遭竄改，或另一個管道也被控制，仍可能失敗。所以高風險工作需要適當的核准、權限與紀錄，而不是把回撥電話當成萬靈丹。

圖中的虛線框是查核區，箭頭表示通過查核後才進入執行流程，不是網路封包一定走這條路。

## 三、圖2：確認的是特定行動，不只是「這是不是你的帳號」

我們用一個虛構例子，完整走一次。

Northstar 教材中心的行政同仁小安，收到一封看似合作廠商寄來的信：「請把學員名單改傳到新資料夾，今天就要完成。」信件附上新電話與上傳連結。

**第一步：先暫停不可逆或敏感的行動。** 暫時不要上傳名單，也不要輸入密碼、驗證碼或安裝遠端控制軟體。暫停不等於判定對方詐騙，而是目前的依據還不夠。

**第二步：從既有可信來源找聯絡管道。** 小安使用原有合作紀錄中的聯絡方式，不使用這封信新提供的電話。若找不到可信管道，就交給既有負責人或支援流程確認；不是隨便搜尋一個看起來像官方的廣告就算完成。

**第三步：核對具體要求。** 不只問「你有寄信嗎？」而是確認：

- 哪一份資料？為什麼需要？
- 要傳到哪個已核准的目的地？誰能存取？
- 這次變更由誰核准？是否在合作與職務範圍內？
- 要做的是查閱、下載、上傳，還是變更權限？

**第四步：再檢查授權。** Authentication（身分驗證）與 Authorization（授權）不是同一關。就算真的是合作廠商，也不代表他有權取得全部學員名單。確認身分，只解決部分問題。

**第五步：依結果分流。** 確認要求與授權都成立，才在必要範圍執行；若對方否認、資料不一致或仍不清楚，就先保留、通報，不自行猜測後放行。真的急件，應走組織既有緊急核准流程，不是免除所有檢查。

圖2的時間由上往下，箭頭是互動先後。向既有管道查詢的箭頭，刻意不回到可疑訊息提供的新電話。這正是整張圖的重點。

## 四、圖3：反釣魚不是一個按鈕，而是互補的防護

**Anti-Phishing Controls（反釣魚控制措施）**，是降低釣魚訊息到達、降低誤操作機會、限制後果，以及支援偵測與應變的一組措施。

這接回 M01-06 的 Defense in Depth（縱深防禦）：不同層處理不同問題。只靠「員工要小心」，會把整套安全壓在一個人當下有沒有看出破綻上。NCSC 建議多層防護，也強調不能期待人員辨識每一封釣魚訊息。[NCSC：組織反釣魚防護](https://www.ncsc.gov.uk/guidance/phishing)

| 控制放在哪裡 | 具體例子 | 不能過度推論什麼？ |
| --- | --- | --- |
| 訊息進入之前 | 郵件網域驗證、垃圾信與惡意連結過濾 | 通過過濾不等於要求合法 |
| 人準備行動時 | 獨立查證、敏感變更核准、清楚的通報入口 | 真人確認不等於所有操作都有授權 |
| 登入時 | 抗釣魚驗證、保護帳號復原流程 | 登入成功不等於付款或資料轉移已核准 |
| 行動影響範圍 | 最小權限、必要資料、適當複核 | 權限縮小不代表風險歸零 |
| 異常發生後 | 通報、日誌、撤銷遭濫用的存取 | 沒告警不代表從未發生攻擊 |

圖3是「控制位置圖」，不是每次釣魚都照順序發生的固定攻擊階段。某封信可能完全不要求登入，只要求你用自己的合法帳號做錯事。

### 4.1 郵件上的三個英文縮寫，分別查什麼？

先把 Domain（網域）理解成網路名稱，例如教學用的 `northstar.example`。寄件顯示名稱寫「資訊部」，只是畫面文字，不是身分證明。

- **SPF（Sender Policy Framework，寄件者政策框架）**：讓接收端檢查寄信來源主機，是否獲得相關寄件網域授權。它檢查的是郵件傳送層的身分，不直接保證你看到的 From 欄就是主管本人。
- **DKIM（DomainKeys Identified Mail，網域金鑰識別郵件）**：透過數位簽章，讓接收端檢查某個簽章網域及受簽署內容的完整性。不是把信件加密，也不是替內容的誠實性背書。
- **DMARC（Domain-based Message Authentication, Reporting, and Conformance，網域式郵件驗證、回報與一致性機制）**：把通過的 SPF 或 DKIM 身分，與可見 From 的網域做 Alignment（對齊）檢查，並提供失敗處理政策與回報機制。**不是只要任意一個網域 SPF 通過就算 DMARC 通過。** [NCSC：郵件防冒充](https://www.ncsc.gov.uk/collection/email-security-and-anti-spoofing)、[IETF RFC 9989：DMARC](https://www.rfc-editor.org/rfc/rfc9989.html)

對齊可依規則採嚴格或寬鬆方式；這堂先掌握「檢查的網域關係必須對得上」，不要求背 DNS 設定。

若攻擊者用自己控制的相似網域寄信，他也可能把自己的驗證設定好；若真正信箱被接管，信件也可能通過驗證。因此，**DMARC pass 不是「內容安全」或「主管已核准」的證書。**

同樣地，HTTPS（加密的網頁連線）保護與目前網站之間的傳輸，不表示這個網站就是你原本想找的組織。釣魚網站也可能有有效憑證。不要只看鎖頭或頁面商標。

### 4.2 為什麼「有 MFA」還不夠？

**MFA（Multi-Factor Authentication，多因素驗證）**用不同種類的證明降低帳號被冒用的風險。但密碼加上手動輸入的 **OTP（One-Time Password，一次性密碼）**，仍可能被假登入頁即時轉交給真正服務。

**Phishing-Resistant Authentication（抗釣魚身分驗證）**的重點，是用協定將驗證與正確服務綁定，而不是只期待使用者看出假網站。**WebAuthn（網頁驗證標準）**搭配適當的 **FIDO2（快速線上身分驗證規格）**驗證器，是這類方法的例子。相似假網域不能直接拿真網站的驗證材料來完成同一驗證。[NIST SP 800-63B-4，3.2.5](https://pages.nist.gov/800-63-4/sp800-63b.html#phishres)

這不是「裝了就不可能被騙」。它主要保護身分驗證；不會自動阻止使用者在已登入的真網站上，依假主管指示把資料交出去。帳號復原、端點安全、登入後工作階段及業務核准，仍需保護。回到圖3：每一層有自己的工作，也有自己的邊界。

## 五、圖4：看到一個成功訊號，別把結論放大

用證據推理時，先問「這個控制究竟證明了什麼？」

| 觀察到的事 | 可以支持的判斷 | 還不能直接推出 |
| --- | --- | --- |
| 可信接收系統記錄 DMARC pass | 該信符合相應網域驗證與對齊條件 | 信件內容真實、無惡意、要求已核准 |
| 登入系統記錄 MFA 成功 | 系統接受了這次驗證 | 每一項後續操作都是本人意願且有權執行 |
| 原有聯絡窗口否認新要求 | 該要求與這次獨立查證結果不一致 | 已確定是誰發動攻擊或用哪種技術 |
| 系統沒有告警 | 目前未觀測到告警；須另查產生、收集與傳遞 | 沒有釣魚、沒有外洩、沒有漏報 |

讀郵件驗證結果，也要知道它由誰產生；不是看到信件內文自稱「已通過安全驗證」就相信。圖4逐組列出觀察與補查問題，用紅色「不等於」標出過度推論，提醒你證據有範圍。

## 六、如果已經點了、填了，下一步怎麼辦？

不要因為不好意思而拖延，也不要為了確認再點一次。先記下實際做到哪一步：只有開網頁、輸入帳密、提供驗證碼、下載執行檔案，還是已傳出資料？不同情況需要不同處置，**點擊本身不能直接當成已遭入侵的證明**。

透過既有可信管道通報；保留原訊息、時間與必要來源，避免改動證據。若驗證材料可能外洩，使用可信入口依流程更改密碼、檢查復原資訊，並由適當管理者處理有效登入狀態與異常存取。只改密碼，不應直接假設所有既有登入狀態已撤銷。

若曾執行不明程式或傳出敏感資料，交由有權人員依事件應變流程處理。不要自行轉寄可疑附件給全體同事，也不要查閱無關個人資料。這是把 M01-07 的事件應變，接到本章實際情境。

我們這次只用虛構情境推理，不對第三方寄測試釣魚信，也不收集任何真實密碼或驗證碼。

## 七、看圖推理：三個小檢核

1. 對方傳來新電話，你照著回撥，對方確認要求。圖1中哪條信任關係還沒建立？你會改用什麼依據？
2. 一封信 DMARC 通過，登入又使用抗釣魚驗證，為什麼仍不能直接把名單上傳到信裡的新位置？請指出圖3還需要哪一類控制。
3. 小安已輸入密碼，但尚未確認有異常登入。現在能確認什麼、不能確認什麼？你會先採取哪兩項行動，而不是等待損害出現？

參考解答另備供網站預設收合區；公布答案不代表你已作答或學會。

## 八、把本章收成一句話

**信任不能取代驗證；驗證不能取代授權；任何單一控制，也不能取代整體防護。**

M09-01～05 教你辨識不同信任濫用；M09-06 把查證、技術防護與證據界線接成可執行流程。下一個路線單元 M02-01 會進入被動與主動偵察：同樣要問資料從哪裡來、能支持什麼判斷，以及哪些活動需要授權。
