# CEH M04-02｜DNS 列舉：查到名稱與位址，不等於服務可用

DNS Enumeration · 新版第二課

上一課把「發現入口、取得資訊、實際存取」分開了。今天沿著同一個原則，學會讀 DNS：**它回了什麼資料？這份回覆能支持什麼結論？還有哪些事不能直接推論？**

你先前接觸過的 DNS 教材與觀察紀錄會保留。這一課按新版順序重新串成完整的基礎，不會把舊資料直接當成新版已學完或已通過。

## 一、DNS 比較像通訊錄，不是網站的健康檢查

DNS，全名 Domain Name System，網域名稱系統。人比較容易記住名稱，軟體要連線時常需要 IP 位址；DNS 可以提供這種對應，也能提供郵件、權威名稱伺服器等其他資訊。

假設公司網站的名稱是 www.example.test，你向 DNS 查到它對應兩個 IPv4 位址。

這代表「這次 DNS 回覆提供了兩筆位址資料」，不代表：

- 兩個位址現在都能連線。
- 網站頁面正常、憑證正確，或登入功能可用。
- 兩個位址就是兩台實體主機。
- 這些位址都是公司自己的源站，而非代管或 CDN 節點。
- 你因此取得對這些設備進行其他測試的許可。

**DNS 告訴你的是名稱相關的資料；連線與應用程式是否正常，要用另外的證據確認。** 這正是 M04-01「知道資訊，不等於能存取」在 DNS 上的應用。[DNS 概念與運作原理](https://www.rfc-editor.org/rfc/rfc1034.html)

本課所有指令與輸出都是合成教學案例，沒有對真實目標執行。example.test 是預留測試名稱；192.0.2.x 是文件示例位址。這些名稱與位址只用來表示情境，不是可直接照打就有結果的公共服務。若另做實作，請換成已獲授權、實際配置的實驗室 DNS 位址與測試區域。[預留測試名稱](https://www.rfc-editor.org/rfc/rfc2606.html)、[文件示例 IPv4 位址](https://www.rfc-editor.org/rfc/rfc5737.html)

## 二、你問的 DNS 伺服器，不一定就是保管答案的人

先分清三個角色：

1. **用戶端／Stub Resolver**：你電腦上提出名稱查詢的部分，通常把問題交給指定的解析器。
2. **遞迴解析器（Recursive Resolver）**：替用戶端找答案，也可能從快取直接回覆，或把問題轉給上游解析器。
3. **權威名稱伺服器（Authoritative Name Server）**：對某個 DNS 區域負責，提供那個區域的權威資料。

可以把遞迴解析器想成幫你查資料的服務台，權威伺服器則是負責維護特定資料的單位。服務台回答你，不表示它自己就是資料的管理者。

在一般公共 DNS 的冷快取情境，解析器可能依序從根名稱伺服器、頂級網域的伺服器取得指引，再問到負責目標區域的權威伺服器。但已有快取、使用轉送器或查詢內部區域時，不必每次都走完整條路。本課的 .test 只是本地練習區域，不是在公共 DNS 上實際走這條路。

還有兩個容易混在一起的詞：

- **網域（Domain）**：DNS 名稱樹中的某個範圍。
- **區域（Zone）**：由一組權威伺服器管理的資料範圍。子網域若被委派出去，就可能屬於另一個區域。

所以，拿到一個區域的資料，不等於拿到整家公司所有網域與子網域的資料。[DNS 角色與區域定義](https://www.rfc-editor.org/rfc/rfc9499.html)

## 三、DNS 列舉在問什麼？先認識常見紀錄

DNS 資料通常以資源紀錄（Resource Record，RR）表示。同一個名稱可以有不同類型的紀錄；查 A 與查 MX，是不同的問題。

先把最常遇到的幾種分成三組：

**找位址或另一個名稱：**

- A：名稱對應的 IPv4 位址。
- AAAA：名稱對應的 IPv6 位址。查不到 AAAA，不會自動推翻已查到的 A。[AAAA 紀錄](https://www.rfc-editor.org/rfc/rfc3596.html)
- CNAME：這個名稱是另一個名稱的別名。它是 DNS 名稱關係，不是瀏覽器收到的 HTTP 轉址。
- PTR：常用於反向查詢，從反向 DNS 名稱取得另一個名稱。正反向結果一致，也不等於完成身分驗證。

**找區域與郵件配置：**

- NS：這個區域的權威名稱伺服器名稱，不是「我的電腦目前用哪個遞迴解析器」。
- SOA：區域管理資訊，包含序號與一些計時參數。序號可用於區域版本管理，不能當作主機在線時間。
- MX：負責接收這個網域郵件的主機名稱與優先順序。數字較小者優先，不是流量百分比，也不是使用者信箱清單。
- TXT：文字資料，可用於服務驗證與郵件政策等用途；看見文字不代表已證明那項政策部署正確，更不應把密碼放進公開 TXT。

這些紀錄提供的是不同用途的線索，不是「一筆 DNS 紀錄就證明一套服務正常」。[基本資源紀錄格式](https://www.rfc-editor.org/rfc/rfc1035.html)

**找服務入口線索：**

- SRV：可描述特定服務的目標主機、連接埠、優先順序與權重。例如目錄服務可能使用它協助找伺服器。SRV 中出現某個服務，也不等於服務目前能連線或允許你登入。[SRV 紀錄](https://www.rfc-editor.org/rfc/rfc2782.html)

這裡的「列舉」就是透過查詢，把名稱、位址、服務角色等具體資訊整理出來。直接送出 DNS 查詢會與解析服務互動；不能因為紀錄是公開的，就把所有查詢一律叫被動蒐集。

## 四、先看懂一條 dig 指令

dig 是 DNS 查詢工具。它不是網站測速工具，也不會因為查到 IP，就替你測完 HTTP、HTTPS 或登入權限。

以下用文件位址代表授權練習環境中的 DNS 伺服器：

```text
dig @192.0.2.53 www.example.test A
```

拆開看：

- dig：執行查詢工具。
- @192.0.2.53：把 DNS 問題送給這台伺服器。
- www.example.test：要查詢的名稱。
- A：這次問 IPv4 位址。

若省略 @server，dig 通常依系統的解析器設定選擇伺服器。因此兩個人輸入同一個名稱，不保證問到同一台解析器或得到同一份快取資料。

一般傳統 DNS 同時使用 **UDP 53 與 TCP 53**。TCP 也能承載一般查詢，不是只有區域傳送才會用它。大型回覆等情況可能需要 TCP，因此把 TCP 53 全擋掉不一定是正確防護。[dig 官方使用說明](https://bind9.readthedocs.io/en/stable/manpages.html#dig-dns-lookup-utility)、[DNS over TCP](https://www.rfc-editor.org/rfc/rfc7766.html)

## 五、讀懂一次回覆：把「答案」與「回答者」分開

以下是合成輸出，省略了版本、查詢時間等非本段重點欄位：

```text
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 40202
;; flags: qr rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 0

;; QUESTION SECTION:
;www.example.test.        IN A

;; ANSWER SECTION:
www.example.test.  300    IN A 192.0.2.10
www.example.test.  300    IN A 192.0.2.11

;; SERVER: 192.0.2.53#53(192.0.2.53) (UDP)
```

先抓五個閱讀重點：

**1. 我問了什麼？**

QUESTION 表示名稱與類型。這次問的是 www.example.test 的 A，不是所有紀錄，也不是這個網域所有子名稱。

**2. 它回了什麼？**

ANSWER 有兩筆 A，資料是 192.0.2.10 與 192.0.2.11。IN 是 Internet 類別；名稱最後的點表示完整名稱已到 DNS 根，不是網址句號。

**3. 回覆的狀態是什麼？**

NOERROR 表示這份回覆的回應碼沒有回報 DNS 錯誤。仍要看 ANSWER 裡是否有你要的資料，不能把它讀成「網站正常」。

**4. 誰直接回答了這次查詢？**

SERVER 是你這次問到的 DNS 端點 192.0.2.53，不是網站位址。ANSWER 裡的兩個位址與 SERVER 扮演不同角色。

若在使用 systemd-resolved 的 Linux 上看到 SERVER: 127.0.0.53，那通常是本機的 DNS stub，不是網站在你的電腦裡，也不會單靠這一行就顯示最終使用了哪個上游伺服器。[systemd-resolved 官方說明](https://www.freedesktop.org/software/systemd/man/latest/systemd-resolved.service.html)

**5. 旗標與其他區塊告訴我什麼？**

- qr：這是回覆。
- rd：查詢要求遞迴處理。
- ra：伺服器宣告可提供遞迴服務。它不證明這次實際走過哪些上游。
- aa：若出現，表示回覆宣告具有權威性；這個旗標本身不是密碼學上的真偽驗證。
- AUTHORITY 與 ADDITIONAL：可提供權威資訊、轉介或其他輔助資料。要依整份回覆判讀，不能一律把它們當成網站位址清單。

以上欄位必須一起讀，不能只看 ANSWER 的筆數。[DNS 訊息與旗標](https://www.rfc-editor.org/rfc/rfc1035.html)

300 是 TTL，單位為秒。對快取回覆來說，你可能看到的是剩餘可快取時間，不是主機存活了 300 秒，也不是保證「所有人的 DNS 最晚 300 秒後必然一致」。[DNS 快取與 TTL](https://www.rfc-editor.org/rfc/rfc1034.html)

## 六、沒有查到答案，至少要分清五種情況

假設你接著查同一個名稱的 AAAA。不能看到空白，就寫「這個網域不存在」。

**NOERROR，但沒有所問類型的答案：**

可能是常說的 NODATA 類型回覆，也可能需要辨認轉介等其他情況。NODATA 不是 dig 的另一個 status 回應碼，而是要從回覆內容判斷的狀態。典型否定回答可能在 AUTHORITY 裡附上 SOA。

**NXDOMAIN：**

表示回覆報告相關名稱不存在。若有 CNAME 鏈，還要辨認否定的是原查詢名稱還是鏈的終點；不要把它擴張成「整家公司沒有這個網域」。

**SERVFAIL：**

解析過程失敗，例如上游問題或 DNSSEC 驗證失敗等。它不是「已證明沒有這個名稱」。

**REFUSED：**

伺服器拒絕處理這個要求，可能與存取政策有關。拒絕回答，不等於資料不存在。

**Timeout：**

你在等待時間內沒收到可用回覆。可能是網路、過濾、伺服器或其他原因；這不是 DNS 伺服器回覆的「不存在」。[否定回覆與快取](https://www.rfc-editor.org/rfc/rfc2308.html)、[DNS 回應碼](https://www.rfc-editor.org/rfc/rfc1035.html)

補一個避免背錯的現代細節：有些 DNSSEC「精簡不存在證明」機制，會把不存在名稱表達成 NOERROR、空 ANSWER 的形式。因此，**不要只靠 NOERROR 加空 ANSWER，就絕對斷言名稱存在。** 今天不必背這套機制，只要記得保留整份回覆與判斷條件。[RFC 9824：精簡不存在證明](https://www.rfc-editor.org/rfc/rfc9824.html)

## 七、把零散查詢整理成線索，而不是把猜測寫成事實

沿用前面的文件位址示意，不同類型的問題可以寫成：

```text
dig @192.0.2.53 example.test NS
dig @192.0.2.53 example.test MX
dig @192.0.2.53 www.example.test AAAA
```

這不是要求你現在執行，也不需要為了這堂課去測真實公司的網域。先能讀懂問題與證據就可以。

如果合成 MX 答案是：

```text
example.test.  300 IN MX 10 mail.example.test.
```

你可以記錄：「回覆把 mail.example.test 列為郵件接收主機，優先值為 10。」

不能直接記錄：「郵件伺服器目前正常、支援任意寄信、有哪些員工信箱、一定由公司自建。」這些都還缺其他證據。MX 指向主機名稱，郵件投遞還需要後續解析與連線流程。[SMTP 的 MX 使用規則](https://www.rfc-editor.org/rfc/rfc5321.html#section-5)

同樣地，如果看到 vpn、dev 或 admin 之類的名稱，只能先當作命名線索；名稱可能過時、共用、用於測試，或指向代管服務。不要只憑名稱替設備認定用途。

另外，dig 的 +short 適合快速查看精簡結果，但會拿掉許多判讀需要的欄位。調查時先保留完整回覆，比只留下兩個 IP 更有價值。[dig 輸出選項](https://bind9.readthedocs.io/en/stable/manpages.html#dig-dns-lookup-utility)

## 八、ANY 不是「全部給我」，AXFR 才是另一種工作

**ANY 查詢不能當成整份區域清單。**

它不是「列出所有子網域」的指令，也不能保證某名稱的全部紀錄都會回來。伺服器可以採用精簡回覆策略。想回答具體問題，應針對所需的紀錄類型查詢。[ANY 的精簡回覆](https://www.rfc-editor.org/rfc/rfc8482.html)

**AXFR 是區域傳送（Zone Transfer）。**

它的正常用途是讓獲准的 DNS 伺服器取得區域資料，維持副本。AXFR 使用 TCP，與一般查一筆 A 或 MX 的範圍不同。

如果不受信任的來源能取得原本不該開放的完整區域資料，可能暴露主機名稱與配置，值得依政策檢查。但「AXFR 成功」本身不自動等於漏洞：授權的次要伺服器成功同步，本來就是正常功能。

反過來，AXFR 被拒絕也不表示區域裡沒有紀錄。即使拿到一個區域，也不保證涵蓋已委派子區域、其他 DNS 視圖或整個組織的所有名稱。

本課先學會辨認用途與風險，不對任何真實伺服器嘗試傳送。實作前要另確認目標、來源與區域傳送是否在授權範圍內。[AXFR 規範](https://www.rfc-editor.org/rfc/rfc5936.html)

## 九、三個安全觀念：快取、DNSSEC、加密傳輸各管不同事

**快取不是某個人的瀏覽紀錄。**

解析器可能供很多人或系統共用，快取也可能受其他查詢與服務機制影響。就算有線索顯示某筆資料曾被快取，也不能直接認定某個人曾造訪某網站，更不能據此推論他的意圖。[DNS 快取與解析器角色](https://www.rfc-editor.org/rfc/rfc9499.html)

**DNSSEC 主要處理資料來源驗證與完整性，不是把內容藏起來。**

有效驗證可以提升對 DNS 資料的信任，但不表示網站內容安全，也不表示服務可用。單純在 dig 加上 +dnssec，主要是請求相關 DNSSEC 資料，不等於工具已替你完成整條信任鏈驗證。[DNSSEC 安全目標](https://www.rfc-editor.org/rfc/rfc4033.html)、[dig 與驗證工具的差別](https://bind9.readthedocs.io/en/stable/manpages.html#dig-dns-lookup-utility)

**加密 DNS 傳輸保護的是特定連線。**

例如 DNS over HTTPS（DoH）可保護用戶端與 DoH 服務之間的傳輸，但你選用的解析服務仍需要處理查詢。它不是「任何人都不知道我查了什麼」，也不替代 DNSSEC 的資料驗證。[DoH 的隱私考量](https://www.rfc-editor.org/rfc/rfc8484.html#section-8)

## 十、防守不是讓 DNS 永遠不回答，而是限制不必要的暴露

對外網站需要別人能查到必要的 DNS 資料。防守重點是讓不同用途有清楚邊界：

1. **檢查公開紀錄內容。** 移除失效或不必要的項目，不把密碼、金鑰與不該公開的內部資訊放進紀錄。
2. **限制區域傳送。** 依架構只允許需要同步的對象，並採用適當身分驗證，例如 TSIG。TSIG 提供訊息驗證與完整性，不等於加密區域內容。[TSIG 規範](https://www.rfc-editor.org/rfc/rfc8945.html)
3. **限制遞迴與快取查詢的服務對象。** 公開權威回答與替任意外部來源做遞迴解析，是不同功能；不能把其中一項開放誤認成另一項也必須開放。
4. **保留可核對的日誌與設定。** 依授權範圍確認查詢來源、拒絕原因、異常頻率與實際政策，避免只憑一筆結果宣布安全或不安全。[BIND 查詢、遞迴與傳送存取控制](https://bind9.readthedocs.io/en/stable/reference.html)

CDN、分區 DNS（不同來源看到不同視圖）與快取，都可能讓不同地點、時間的答案不一樣。遇到差異時，先記下條件，不要馬上判定其中一方遭到攻擊。

建議的觀察紀錄可以很簡單：

```text
查詢時間與時區：
查詢來源／授權範圍：
使用的 DNS 伺服器：
查詢名稱與紀錄類型：
回應碼、旗標與相關區塊：
答案與 TTL：
這份回覆能支持的結論：
仍需要另外確認的事：
```

保存原始回覆，並把「觀察」與「推論」分開。若任務要驗證網站可用性，再依授權另外測連線、TLS 或 HTTP；不要把那些結果補寫成 DNS 已經證明的事。

## 十一、今天先記住這一條線

**我向哪個 DNS 端點，詢問哪個名稱的哪種紀錄；它回了什麼，而這些資料還不能證明什麼。**

你不需要今天就背完所有紀錄類型。先能把 A、AAAA、MX、NS 的用途分開，讀懂 QUESTION、ANSWER、SERVER，並避免把 NOERROR、空答案或兩個 IP 解讀過頭，就抓住這堂課的重點。

下一課會進到 FTP／SMTP 列舉，繼續區分「服務願意回覆資訊」與「你被允許做什麼」。

**最後只做一個小確認：**

在同一個合成情境裡，A 查詢回了兩個 IPv4 位址；AAAA 查詢顯示 NOERROR、ANSWER 為 0，目前沒有保留其他區塊。有人因此說：「這證明網站正常，而且已經確定沒有 IPv6。」

你會怎麼用一兩句話修正這個結論？
