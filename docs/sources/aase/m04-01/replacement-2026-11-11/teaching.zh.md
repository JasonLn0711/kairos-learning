# M04-01｜HCI、UI、UX 到底有什麼不同？

這堂課最重要的一句話：設計系統的目的，不是讓使用者欣賞介面，而是讓使用者能夠理解系統、正確操作，最後順利完成自己真正想做的事情。

本課從日常生活、醫療、銀行、物流、政府服務及 AI 軟體開發等情境學習。

## 一、先用一個生活例子理解三者

想像今天你到醫院看診，必須使用醫院的自助報到機。

你走到機器前，插入健保卡，確認掛號資料，完成報到，再前往診間候診。

這件看似簡單的事情，其實包含三種不同的設計問題。

@figure1

這個例子最重要的地方在於：

報到機的 UI 可以很好看、操作也很簡單，但整體 UX 依然可能很糟糕。

原因是使用者真正要完成的工作，是順利就醫，而不是成功操作報到機。

這也是 Nielsen Norman Group 對 UX 的經典觀點：使用者經驗涉及使用者與產品、服務及組織互動的整體過程，不能只用介面好不好看來判斷。

## 二、三個概念究竟有什麼差別？

先比較各自關注的問題與方法，再判斷要蒐集什麼證據。

| 比較項目 | HCI 人機互動    | UI 使用者介面   | UX 使用者經驗    |
| ---- | ----------- | ---------- | ----------- |
| 核心問題 | 人怎麼理解、操作科技？ | 介面如何呈現與回應？ | 整段經驗是否符合需求？ |
| 主要關注 | 認知、行為、互動能力  | 畫面、控制元件、提示 | 工作流程、結果、感受  |
| 常見方法 | 行為觀察、認知研究   | 介面設計、原型製作  | 使用者研究、旅程分析  |
| 成功例子 | 知道下一步怎麼做    | 找得到並能操作按鈕  | 完成任務，順利取得服務 |

需要特別澄清：HCI、UI、UX 不是三個完全分開的工作階段，也不是誰一定包含誰。

HCI 是跨領域的研究與設計領域；UI 是人與系統互動的接觸介面；UX 是使用者經驗的整體品質。三者有很大的交集。

@figure2

Figma 的概念示意圖：HCI、UI 與 UX 彼此重疊，而 Interaction Design（互動設計）涉及三者的交會。這是理解關係的示意，不是嚴格的學術集合分類。

還有一個容易誤解的地方：UI 不一定是螢幕。語音助理的語音提示、車輛的實體控制面板、ATM 的操作按鍵，都可以是使用者介面。

## 三、HCI：為什麼使用者會誤解系統？

HCI 是三者之中最值得深入理解的基礎之一，因為軟體工程師知道系統怎麼運作，不代表使用者也知道。

舉例來說，一個銀行系統顯示「審核完成」。

工程師的意思可能是：「系統已完成資料完整性檢查。」

但是銀行職員可能理解成：「這筆貸款已經通過審核。」

同樣四個字，雙方卻有完全不同的理解。

這涉及 HCI 的一個重要概念：Mental Model（心智模型）。

### 1. Mental Model：每個人心中都有自己的系統操作地圖

你第一次使用陌生的洗衣機，可能會根據過去的經驗，猜測「開始」按鈕按下去後會立刻洗衣。

但這台洗衣機可能先要求你選擇水量、洗程和溫度。

這就是使用者心中的預期，與系統實際運作方式不一致。

良好的人機互動設計，應該盡量讓系統行為符合使用者的合理預期，或提供足夠資訊協助使用者形成正確理解。

### 2. Feedback：操作之後，系統必須回應

假設你在購物網站按下「付款」。

結果畫面完全沒有反應。

你不知道付款是否成功，於是又按了一次，可能造成重複訂單。

這是典型的 Feedback（回饋）問題。

好的系統需要告訴你目前狀態，例如「正在處理付款」、「付款成功，訂單編號為……」或「付款失敗，尚未扣款」。

### 3. Error Prevention：避免使用者犯錯，而不只是事後顯示錯誤

例如藥局系統允許藥師將藥品加入領藥清單。

如果某筆處方的藥品劑量異常，系統不應只在最後出現模糊的「錯誤代碼 203」。

更好的做法可能包括明確標示異常內容、協助核對原始處方，並依專業規範要求適當確認。

這些設計涉及人如何理解資訊、做出決策，以及如何減少操作失誤。

上述三種概念，都與 Nielsen 的可用性設計原則相符，包括系統狀態可見性、使用者熟悉的語言，以及錯誤預防。

## 四、用六個不同行業的例子加深理解

以下均為假設情境，用來練習從不同角度找問題。

| 行業與任務   | UI 問題     | HCI 問題           | UX 問題             |
| ------- | --------- | ---------------- | ----------------- |
| 醫療：線上預約 | 日期選擇器不清楚  | 病人誤認為選日期就已掛號     | 預約後到現場仍找不到報到位置    |
| 銀行：貸款申請 | 送出按鈕不明顯   | 客戶分不清資料檢查與核貸通過   | 線上申請後還須臨櫃重填       |
| 物流：查詢包裹 | 配送狀態字太小   | 「配送中」的意義讓人誤解     | 包裹送達錯誤地點，申訴困難     |
| 教育：線上學習 | 章節導覽難找    | 學生不知道是否完成測驗      | 課程完成後仍不知道如何應用     |
| 製造：產線控制 | 警報訊息不明顯   | 操作員搞不清警報優先順序     | 排除異常後無法順利復工       |
| AI：語音助理 | 錄音狀態提示不清楚 | 使用者不知道 AI 是否正在聆聽 | AI 正確辨識語音，卻無法完成預約 |

注意，這張表不是在說每個問題只能歸入一種分類。

例如「配送中」的文字可能同時是 UI 的資訊呈現問題、HCI 的理解問題，以及 UX 的配送期待落差。

實際設計時，三者是互補的分析視角，不是互斥的問題類別。

## 六、Usability（易用性）又是什麼？

這是另一個容易與 UX 混淆的名詞。

Usability 通常翻成「易用性」或「可用性」，重點是特定使用者在特定情境下，能否有效、有效率且滿意地完成目標。

根據 ISO 9241-11:2018，可以從三個面向理解。

| 面向                | 白話說明       | 可以怎麼量測     |
| ----------------- | ---------- | ---------- |
| Effectiveness 有效性 | 有沒有正確完成？   | 任務完成率、錯誤率  |
| Efficiency 效率     | 需要花費多少資源？  | 完成時間、操作次數  |
| Satisfaction 滿意度  | 使用時是否符合期待？ | 問卷、訪談與主觀評價 |

例如設計一台自助售票機，單純測量「買票要多久」還不夠。

如果操作速度很快，但部分使用者容易買錯車票，就不能說設計成功。

如果所有人都能買對車票，但第一次使用需要花十五分鐘，也可能有改善空間。

此外，還要考慮 Accessibility（無障礙使用）：例如是否能只透過鍵盤操作、是否支援輔助科技、文字是否容易閱讀。這些需求不應只被當作介面美化的附屬項目。

## 七、實際案例：重新設計一個收件系統

回到正式教材的情境。

假設我們正在設計政府機關的申請案件收件系統，承辦人必須確認申請資料，再匯出檢查報告。

### 先從 HCI 找原因

使用者看到「成功」時，腦中想到的是什麼？

我們可以請使用者直接回答：「你覺得現在這筆申請案處於什麼狀態？」

如果他認為已經送件，就表示系統表達的狀態和使用者理解的狀態不同。

### 接著透過 UI 提出修改

不只是放大字體，而是明確區分「欄位齊全」、「檢查完成」、「正式送件」和「正式受理」等不同狀態，並提供下一步指引。

但要注意：如果後端系統根本沒有區分這些狀態，只改提示文字仍不足以解決問題。

### 最後從 UX 檢查完整工作

就算承辦人順利匯出了報告，如果下一個承辦人拿到報告後，仍然需要重新查詢和填寫所有資料，整體工作仍然不順暢。

因此不能只測試「按鈕能不能按」，還要測試整段工作能否完成。

## 八、如何證明我們真的改善了 UX？

這一節是從設計走向工程驗證的關鍵。

我們不能因為 AI 說「已優化 UX」，就認為 UX 真的改善。

可以採取以下流程：

1. 定義使用者與任務：例如第一次使用系統的承辦人，需要找出缺少的資料並完成補正。
2. 觀察既有問題：記錄找不到欄位、看不懂提示、誤認為已經送件等具體情況。
3. 提出修改假設：在缺件欄位旁提供具體說明，應有助於使用者找到並修正問題。
4. 設計可比較的測試：讓具代表性的使用者在相近情境下操作既有版本與候選版本。
5. 評估結果：比較任務完成率、錯誤、完成時間及使用者解釋狀態的正確程度。

這裡有個重要區分：程式的單元測試能確認檢查邏輯是否符合規格，但不能直接證明真人看得懂訊息。

NIST 對 Usability Testing（易用性測試）的描述，也是讓具代表性的使用者執行具代表性的任務，再蒐集成功率、時間、錯誤及主觀感受等證據。

## 九、AI 協作軟體工程：怎麼把這堂課真正用起來？

未來請 AI Agent、ChatGPT 或其他 Coding Agent 設計介面時，應該避免只說：

> 幫我設計一個現代化、簡潔、漂亮的介面，UX 要很好。

因為這種描述沒有定義真正要解決的工作問題。

比較好的需求包含五個元素：

### 1. 誰使用

第一次使用的承辦人

### 2. 要做什麼

在案件資料中找出缺漏並完成修正

### 3. 遇到什麼困難

只看到「資料錯誤」，不知道哪個欄位有問題

### 4. 要如何改善

在對應欄位顯示具體錯誤、原因與修正方法

### 5. 如何證明有效

讓使用者處理一個缺件案例，觀察能否自行理解並完成補正

如果要交給 AI 實作，可以使用這樣的指令：

### AI 設計需求範例

以下指令先要求可檢查的設計稿，再列出真人測試假設。

```text

請設計一個供第一次使用的承辦人檢查與補正案件資料的網頁介面。

使用者任務：找出缺少的必要欄位並完成補正。
現有問題：系統只顯示「資料錯誤」，使用者不知道哪裡有問題。

設計假設：在欄位旁顯示具體錯誤原因與修正建議，可協助使用者自行完成補正。

要求：
- 區分欄位檢查完成、已送件、已受理等系統狀態。
- 提供清楚的下一步。
- 考慮鍵盤操作及錯誤復原。

請先產出文字線框稿、介面狀態與互動流程，不要直接開始寫程式。

最後列出需要透過真人任務測試驗證的假設，不得宣稱已改善 UX。
```

這就是本課要建立的工程觀念：AI 不只是幫我們產生介面，也必須依照可觀察的使用問題進行設計，並讓結果能夠接受驗證。
