# AASE M04-01｜HCI、UI、UX 到底有什麼不同？

這堂課最重要的觀念是：

設計一套系統，不是為了讓畫面漂亮，而是要讓使用者能理解系統、正確操作，最後完成真正的工作。

HCI、UI、UX 就是從三個不同角度，檢查這件事情有沒有做好。

想像你到麥當勞，使用自助點餐機。

你希望的是什麼？不是欣賞點餐機的設計，而是能夠快速點到想吃的東西、付錢、拿到餐點。

但這個簡單的過程，其實可以分成三個問題。

1\. UI：畫面怎麼呈現？

點餐機上的漢堡圖片、價格、數量、結帳按鈕、返回上一頁，都是 UI（User Interface）。

例如，結帳按鈕太小、字體看不清楚、價格藏在不明顯的位置，這些就是 UI 設計問題。

2\. HCI：人如何理解和操作機器？

假設你看到一個「完成」按鈕。

你可能以為按下去就完成付款，但實際上只是完成餐點選擇。

這時問題不只是按鈕長得如何，而是：為什麼使用者會這樣理解？

HCI（Human–Computer Interaction）研究人的認知、行為、操作能力與技術之間的互動。

例如，老人家看得懂嗎？使用輪椅的人能不能碰到按鈕？使用者是否知道下一步要做什麼？

3\. UX：整段過程到底好不好？

假設你非常順利地點完餐、付款成功，卻不知道去哪裡領餐。

這時候點餐機可能非常好用，整體體驗卻很差。

UX（User Experience）要考慮的不只是點餐機，還包含進店、點餐、付款、等待、領餐，甚至遇到問題如何處理。

## 二、用一張表記住三者的差別

| 概念       | 白話解釋         | 最重要的問題          |
| -------- | ------------ | --------------- |
| HCI 人機互動 | 研究人怎麼理解、使用科技 | 人為什麼會這樣操作？      |
| UI 使用者介面 | 人看得到、操作得到的介面 | 按鈕、文字、提示應該怎麼設計？ |
| UX 使用者經驗 | 從開始到完成的整體體驗  | 最後有沒有順利完成工作？    |

要特別注意：這不是三個互不相關的盒子。

HCI 是跨領域的研究與設計領域；UI 是人與系統互動的接觸介面；UX 則是整體使用經驗。三者彼此重疊、互相影響。

## 三、回到我們正在設計的收件系統

假設現在要開發一個簡單的網頁，讓承辦人員檢查資料是否齊全，再匯出報告。

原本流程是：

填寫資料

系統檢查

顯示成功

匯出報告

現在出現一個問題：承辦人看到「成功」，以為案件已經正式受理。

但系統其實只確認三個必要欄位已填寫。

這就是很典型的設計問題。

HCI：研究為什麼會誤解

使用者心目中的「成功」是什麼意思？他是否知道欄位齊全和正式受理不同？

可以請他直接說明畫面意思，而不是由開發者自行猜測。

UI：修改畫面上呈現的資訊

不要只顯示「成功」，而要說明具體完成了什麼。

例如：「三個必要欄位已齊全，尚未正式送件。」

同時提供清楚的下一步操作。

UX：確認整段工作是否順利

即使畫面讓人看懂了，承辦人匯出報告後，究竟應該交給誰？接手者能不能使用？

如果接手者還得重新輸入全部資料，整體工作流程仍然有問題。

匯出檢查報告

明確說明狀態，以及接下來能做什麼。

這個修改看起來比較清楚，但有一個非常重要的科學觀念：

設計者覺得比較清楚，不代表使用者真的理解得比較好。

所以還需要驗證。

## 五、如何證明真的改善了？

把「改善 UX」當成一項需要證據的設計工作。

| 要驗證的問題          | 可以怎麼測試                |
| --------------- | --------------------- |
| 使用者看懂「欄位齊全」嗎？   | 請他用自己的話解釋目前狀態         |
| 使用者知道如何補件嗎？     | 給他一個缺件情境，觀察是否能找到欄位並修正 |
| 不使用滑鼠能操作嗎？      | 實際用鍵盤 Tab、Enter 等完成操作 |
| 接手者拿到報告後能繼續工作嗎？ | 讓接手角色用報告完成指定的後續任務     |

這裡還有一個差別：

- 功能正確： 程式有沒有照規則運作？
- 易用性（Usability）： 使用者能不能有效、有效率地完成指定任務？
- UX： 包含使用前、使用中、使用後，整體感受與結果如何？

例如，100 次缺件測試全部成功擋住，能支持程式在這些案例下的檢查邏輯正確，卻不能證明 100 位使用者都能理解錯誤提示。

## 六、以後請 AI 設計介面，應該怎麼提需求？

以前可能只會說：

> 請幫我把這個網頁做得更漂亮，改善 UX。

這種指令會讓 AI 自行決定什麼叫改善，可能只是換顏色、增加動畫和陰影。

比較好的做法，是描述五件事：

一個可驗證的設計需求

誰使用 → 做什麼 → 遇到什麼困難 → 要如何修改 → 怎麼驗證

使用者： 第一次使用系統的承辦人

任務： 找出缺少的文件類型並補正

問題： 不知道哪個欄位缺漏

候選修改： 在欄位旁顯示具體錯誤與修正指引

驗證方法： 指定缺件情境，觀察使用者是否能自行修正

這就是從「要求 AI 美化」轉成「要求 AI 解決可驗證的使用問題」。

在還沒測試之前，只能稱為設計假設，不能說已經驗證有效。

## 七、這一課與下一課有什麼關係？

今天 M04-01 學的是用 HCI、UI、UX 三個角度發現問題。

下一課 M04-02「Task Analysis（任務分析）」則會更進一步，把真正的工作拆開：

使用者收到案件

尋找必要資料

填寫表單

發現缺漏並修正

檢查與匯出報告

交給下一位承辦人

任務分析不是一開始就畫畫面，而是先問：每一步是誰做的、需要什麼資訊、如何判斷成功，以及出了問題該怎麼辦？

理解這些之後再設計線框稿（Wireframe），才比較不容易做出「畫面很好看，但實際工作無法完成」的系統。
