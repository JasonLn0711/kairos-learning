## cycle｜先定義正確，再讓程式達到要求


這一節最重要的觀念是：不要等程式全部寫完才檢查有沒有問題，而是先定義什麼叫「正確」，再讓程式逐步達到要求。

TDD（Test-Driven Development，測試驅動開發）的核心流程只有三步：

1. Red（紅燈）： 先寫測試，證明目前程式還做不到某項要求。
2. Green（綠燈）： 用最少的修改，讓測試通過。
3. Refactor（重構）： 在不改變既有行為的前提下，把程式整理得更清楚、更容易維護。

接著再挑下一個要求，重複這三個步驟。

這種開發方法把需求、程式實作與驗證連接起來。




## analogy｜一、先用一張圖理解 TDD

你可以把 TDD 想成「先決定怎麼驗收，再開始施工」。

例如，你請裝潢師傅製作一扇自動門。

傳統的做法可能是：師傅先安裝整套系統，完成後才測試能不能正常開門。

TDD 的思考方式則是：

- Red：先規定「有人靠近時，門必須自動開啟」，並設計測試。現有系統做不到。
- Green：先完成感測器與開門功能，讓測試通過。
- Refactor：把感測器和控制器的程式整理好，再測試一次，確定門仍然正常開啟。

之後再處理「有人站在門口時不能關門」、「停電後如何復原」等下一批要求。

關鍵是每次只處理一個明確、可驗證的小目標，而不是一開始就把整個系統寫完。

## red-meaning｜二、為什麼要先讓測試失敗？這不是很奇怪嗎？

這是 TDD 最容易讓初學者困惑的地方。

一般人會想：「我不是應該努力讓程式成功嗎？為什麼還要故意讓它失敗？」

因為 Red 的目的不是製造錯誤，而是確認測試真的有能力發現錯誤。

假設你製造了一台能夠自動辨識不良品的機器。

你把一件明顯不良的產品送進去，機器卻判定合格。這就證明目前檢驗能力不足。

如果你從來沒有拿不良品測試，只拿合格品去測，即使每次都顯示「通過」，也不能證明這台機器有能力辨識不良品。

軟體測試也是這個道理。

### 但要注意：不是所有紅燈都有意義

| 測試結果            | 代表什麼？                      |
| --------------- | -------------------------- |
| 缺少必要資料，程式卻允許匯出  | 正確的 Red：抓到需求缺失             |
| 找不到 `pytest` 套件 | 環境問題，不是業務規則失敗              |
| Python 程式語法錯誤   | 程式無法正常執行                   |
| 系統顯示找不到任何測試     | 根本沒有執行有效測試                 |
| 測試原本就通過         | 需要確認功能是否早已存在，或測試沒有檢查到真正的要求 |

Red 必須是「因為目前程式不符合預期行為而失敗」，而不是隨便出現一個錯誤就算成功。 這也是原教材特別強調的要求。


## industries｜三、TDD 可以用在哪些產業？

TDD 是軟體開發方法，但幾乎所有包含「明確規則」的產業軟體，都能用它來開發或驗證功能。

| 產業   | 必須符合的規則       | 可以先寫的測試                  |
| ---- | ------------- | ------------------------ |
| 銀行   | 餘額不足不能提款      | 餘額 100 元，提款 150 元，必須拒絕   |
| 醫療   | 已記錄的藥物過敏不能被忽略 | 開立被標記過敏的藥物時，系統必須依設定阻擋或警示 |
| 電商   | 庫存不足不能完成訂單    | 只剩 2 件，購買 3 件，系統必須拒絕或調整  |
| 教育   | 未完成的測驗不能標記合格  | 必答題尚有空白時，不能產生完成狀態        |
| 政府行政 | 缺少必要文件不能結案    | 缺少簽署文件時，不能標記審查完成         |

這些都是 Business Rules（業務規則）。

TDD 的好處之一，就是能把原本寫在需求文件裡的要求，變成可以由電腦反覆執行的測試。

例如銀行提款的要求，可以先用 Given–When–Then 描述：

Given（已知）：帳戶餘額是 100 元。

When（當）：使用者嘗試提款 150 元。

Then（那麼）：系統必須拒絕提款，且帳戶餘額仍然是 100 元。

這裡有兩個要測的結果：提款被拒絕，以及原本的餘額沒有被改變。

當我們把這兩個要求寫成自動化測試，就能開始進行 TDD。

## requirement｜四、實際操作：從錯誤程式走到正確程式

接下來按照原教材的「文件匯出」例子，用 Python 演練完整的 Red、Green、Refactor。

### 需求是什麼？

我們正在開發一套文件報告產生系統。

它有一項規則：

> 如果「文件類型」（`document_type`）缺漏或無效，就不能產生標示為 `complete` 的報告。

例如，文件類型是「合成申請表」，系統可以產生報告。

但文件類型是空字串、只有空格、`None` 或數字，就應該拒絕。

## red-stage｜第一階段：Red，先寫測試

假設現有程式是：

```
def build_report(record):
    return {"status": "complete", "data": dict(record)}
```

注意，這段程式完全沒有檢查文件類型。

只要有人要求產生報告，它就回答 `complete`。

因此我們先寫一個測試檔案 `test_export_gate.py`：

```
import pytest
from export_gate import build_report


@pytest.mark.parametrize("value", ["", "   ", None, 42])
def test_missing_document_cannot_be_complete(value):
    with pytest.raises(ValueError, match="缺少文件類型"):
        build_report({"document_type": value})


def test_valid_document_matches_contract():
    result = build_report({"document_type": "合成申請表"})
    assert result == {"status": "complete", "data": {"document_type": "合成申請表"}}
```

這裡有三個需要理解的專業術語。

`pytest` 是 Python 的自動化測試工具。

`@pytest.mark.parametrize` 稱為參數化測試（Parameterized Testing），意思是同一個測試可以套用多組資料，不必重複寫四次程式。


`pytest.raises(ValueError)` 則表示：「我預期這段程式應該拋出 `ValueError` 這種例外（Exception），而且訊息要符合指定內容。」

如果程式沒有拋出這個例外，測試就會失敗。

執行：

```
python -m pytest -q
```

這時會發現四個無效輸入都沒有被拒絕，所以四項測試失敗；正常文件的測試則通過。

這才是我們想觀察的 Red。

## green-stage｜第二階段：Green，修改最少的程式

現在知道錯誤在哪裡了：缺少輸入檢查。

我們只要加上必要的判斷即可。

```
def build_report(record):
    value = record.get("document_type")
    if not isinstance(value, str) or not value.strip():
        raise ValueError("缺少文件類型")
    return {"status": "complete", "data": {**record, "document_type": value.strip()}}
```

這段程式的意思是：

首先取得文件類型，然後判斷它是不是文字，以及去掉首尾空白後是否還有內容。

如果不合格，就用 `raise ValueError(...)` 告訴呼叫端：「輸入資料不符合要求。」

如果合格，就回傳完整報告。

這時再次執行完全相同的測試。

四個無效案例應該被正確拒絕，而有效案例仍然可以成功產生報告。

這就是 Green。

特別要注意，Green 不是修改測試標準讓自己過關，而是修正程式，讓原本的驗收標準得到滿足。

## refactor-stage｜第三階段：Refactor，整理而不改變行為

雖然程式通過了測試，但我們可能發現，文件類型驗證邏輯以後會被其他功能重複使用。

所以可以把它獨立出來。

```
def require_document_type(value):
    if not isinstance(value, str) or not value.strip():
        raise ValueError("缺少文件類型")
    return value.strip()


def build_report(record):
    document_type = require_document_type(record.get("document_type"))
    return {"status": "complete", "data": {**record, "document_type": document_type}}
```

這個版本把原本混在一起的兩種責任分開了。

`require_document_type()` 專門負責驗證文件類型。

`build_report()` 專門負責組合報告。

未來其他功能如果需要檢查文件類型，也可以重用驗證函式。

但要特別注意：Refactor 不應偷偷改變原本對外的行為，也不等於一定要抽取函式。 如果程式已經夠清楚，過度拆分反而可能讓程式更難理解。

修改完成後，再次執行測試，確認整理程式沒有破壞既有功能。

## evidence｜實際執行結果與證據範圍

供稿回報：在獨立 Python 環境中，Red 為 4 項失敗／1 項通過；Green 為 5 項全部通過；Refactor 加入三項測試後為 8 項全部通過。下圖呈現這組回報，不代表讀者已完成實作。

重構階段另外加入「缺少欄位鍵」、「移除首尾空白」、「不修改原輸入資料」三項測試。供稿回報的執行環境為 pytest 9.0.2，與原教材指定的 8.4.2 不同。本次重現結果與環境另記於版本驗收紀錄，不將來源回報當成本次實測。

本版另以 Python 3.11.15，分別在 pytest 8.4.2 與 9.0.2 的獨立環境實跑正文程式：Red 都是 4 失敗／1 通過；Green 與 Refactor 在原五項測試皆為 5 通過，加入三項回歸案例後兩版本皆為 8 通過。這能區分測試集合增加與重構保留行為，仍只涵蓋本例的文件類型規則。

這三個階段留下的證據，能回答不同問題：

Red 證明我們的測試可以抓到特定錯誤；Green 證明程式已修正這個錯誤；Refactor 則確認我們整理程式後，已測試的功能仍然正確。

## comparison｜五、TDD 與一般測試最大的不同

一般測試與 TDD 並不是兩種互相排斥的工具。

它們的主要差別，是測試在開發過程中扮演什麼角色。

| 比較   | 先寫程式再測試    | TDD           |
| ---- | ---------- | ------------- |
| 起點   | 先思考怎麼實作    | 先思考預期行為       |
| 測試時間 | 常在實作後      | 實作前先寫一個測試     |
| 發現缺陷 | 可能等功能完成才發現 | 每個小循環立即回饋     |
| 設計方式 | 程式架構可能先定型  | 讓需求與測試逐步影響設計  |
| 重構   | 依靠既有測試與審查  | 每輪以已通過的測試保護重構 |

但不能因此推論 TDD 一定比所有其他開發流程更快、錯誤更少。效果取決於測試品質、開發者能力、系統類型與維護成本。Agile Alliance 對實證成效也保留了一定程度的審慎態度。


## agent-workflow｜六、TDD 與 AI Coding Agent 有什麼關係？

當我們開始使用 AI Agent 寫程式時，TDD 特別值得掌握。

因為 AI 很擅長快速產生程式碼，但產生程式碼不代表完成了需求驗證。

如果只告訴 Agent：

「幫我做一個報告產生功能。」

它可能產生一套看起來正常的程式，但漏掉文件類型驗證。

改用 TDD，可以把協作方式調整為：

1. 人定義要求與驗收條件
2. Agent 撰寫測試，執行並展示預期失敗
3. Agent 修改實作，再執行相同測試
4. 確認測試結果，重構並再次驗證

你可以要求 AI Coding Agent：

> 依照需求規格，先挑選一項最小可驗證行為，建立 pytest 測試。先執行並說明預期的失敗原因，不要在這個階段修改測試來迎合現有程式。接著進行最小修正，保留相同測試的通過結果。最後進行必要的重構、執行回歸測試，並報告哪些要求已驗證、哪些仍未驗證。

這樣有助於把 AI 產出轉換成可審查的實作過程。

但還要防範一個問題：如果同一個 Agent 同時誤解了需求、寫錯測試、又寫出剛好通過錯誤測試的程式，TDD 仍然無法保證結果正確。因此，重要驗收條件仍應由人員或獨立驗證機制確認。

## quality｜七、測試全部通過，代表軟體品質沒有問題嗎？

不代表。

例如，我們剛才已確認文件類型驗證正確，但尚未驗證：

| 驗證層次                   | 還需要回答的問題            |
| ---------------------- | ------------------- |
| 單元測試（Unit Test）        | 各項欄位與業務規則是否正確？      |
| 整合測試（Integration Test） | 文件處理與資料庫整合是否正常？     |
| 端對端測試（End-to-End Test） | 使用者能否從上傳一路完成匯出？     |
| 安全測試（Security Test）    | 使用者能否讀取不屬於自己的文件？    |
| 易用性測試（Usability Test）  | 使用者是否理解錯誤訊息、知道怎麼修正？ |

因此，TDD 是建立品質證據的工具，但不是整個品質保證體系。

原教材也特別指出：這次練習只涵蓋一項文件類型規則，不能因為這項測試通過，就宣稱整個軟體、所有欄位或資安控制已經完成。


## applicability｜八、什麼時候最值得使用 TDD？

我會優先將 TDD 用在規則明確、可以重複執行、錯誤代價較高的功能上，例如金額計算、權限判斷、資料驗證、狀態轉移、API 契約，以及已經發生過的 Bug 修復。

如果是在探索全新的視覺設計、使用者偏好或尚不清楚的產品需求，通常需要先透過原型、訪談或探索式測試理解問題，再把已確認的行為轉成自動化測試。

TDD 擅長回答「我們有沒有正確實作這項要求」，但不會自動回答「這項要求本身是不是對的」。

這正好能與前面學過的需求工程、Given–When–Then 和規格驅動開發（SDD）連起來。
