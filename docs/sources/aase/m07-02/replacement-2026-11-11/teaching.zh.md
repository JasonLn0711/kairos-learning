## 一、先用一句白話理解

AI Agent 就像一個能力很強、動作很快，但可能自行補充假設的工作夥伴。你不能只告訴它要做什麼，還必須交代哪些事情不能做、遇到什麼情況要停下來，以及做完後要拿什麼證明。

例如，你請裝潢師傅：

「幫我把廚房整理得更好用。」

師傅可能覺得應該拆牆、換水管、重新做櫥櫃，甚至連客廳都一起改。

但你真正的需求可能只是：

「在現有廚房增加兩個收納抽屜，不更動水電，預算不超過兩萬元，施工前先確認尺寸，完成後檢查抽屜能否正常開關。」

兩種指令的差別，就是這一節要教你的核心：從模糊的委託，變成有邊界、有驗收標準、有停止條件的工作契約。

這不只適用於 Coding Agent，也適用於文件整理、研究分析、金融作業、醫療行政，以及其他需要 AI 協助執行的工作。

## 二、整個觀念其實只有一條主線

1. 人類確認規格（Specification）

定義什麼才算做對、哪些規則已被確認

2. 訂定工作契約（Task Contract）

明確指定任務範圍、工具、驗收與停止條件

3. AI Agent 執行

在實際授予的權限內操作，保留紀錄

4. 提供證據（Evidence）

呈現檔案差異、測試結果、未完成事項

5. 人類審查與驗收

接受成果、退回修正，或先釐清需求

這是一個閉環：AI 不只是接收指令和交出成果，而是必須讓負責人有辦法檢查它究竟做了什麼。這也符合教材所強調的「可核對的委派閉環」。

## 三、工作契約需要交代哪些內容？

可以把每次交給 Agent 的任務，拆成八個要素。

| 要素       | 白話解釋        | 例子          |
| -------- | ----------- | ----------- |
| 1. 目標    | 這次到底要完成什麼？  | 建立三欄輸入表單    |
| 2. 依據    | 要按照哪份資料做？   | 已確認的需求文件    |
| 3. 範圍    | 哪些事情可以改？    | 只能修改表單程式    |
| 4. 禁止事項  | 哪些事情不要碰？    | 不新增登入與資料庫   |
| 5. 工具與權限 | 能使用哪些工具及資源？ | 只能操作測試專案    |
| 6. 驗收標準  | 怎樣才算做成功？    | 三欄可輸入，能顯示內容 |
| 7. 停止條件  | 何時不能擅自決定？   | 業務規則不明確時先詢問 |
| 8. 完成證據  | 如何證明真的做到了？  | 修改紀錄、測試結果   |

其中最容易被忽略的是最後三項：驗收、停止、證據。

因為一般人很習慣交代工作目標，卻很少交代「哪些事沒有權力自己決定」。

舉例來說，假設銀行要 AI 協助製作徵信報告。

你只說「幫我產生一份完整報告」，AI 可能自己發明評分標準，並填入看似合理的財務判斷。

但是銀行內部的風險分類和授信標準是正式業務規則。AI 不應該靠猜測決定。

正確的委派方式是：使用已核准的資料和模板；遇到未定義的評估規則，就標示待確認；不能自己編造一項銀行政策。

這個觀念稱為 Human-in-the-Loop（人在決策迴路中）：AI 可以完成被授權的工作，但重要決策仍由具責任與權限的人確認。

## 四、為什麼一定要把大任務拆小？

教材提到一個重要概念：垂直切片（Vertical Slice）。

假設你要開發餐廳訂位系統。

你可以一口氣要求 AI：

「幫我做一套完整的餐廳訂位平台。」

這樣很容易產生大量功能，包括會員登入、桌位安排、付款、簡訊通知、後台管理，甚至可能有根本沒經過確認的訂位規則。

更穩定的方法，是一次完成一個可以獨立驗收的小成果。

| 切片  | 本次只做什麼       | 如何驗收       |
| --- | ------------ | ---------- |
| 第一片 | 姓名、人數、日期輸入介面 | 可以正確輸入與顯示  |
| 第二片 | 日期、人數資料檢查    | 錯誤輸入會被拒絕   |
| 第三片 | 查詢可預訂桌位      | 只顯示符合條件的桌位 |
| 第四片 | 送出訂位         | 成功建立一筆訂位紀錄 |

注意：每一片不只是某個技術元件，而是能展示一段有意義的使用者行為。

如果第一片就出錯，你只需要調查輸入表單，而不是同時檢查付款、資料庫、通知與所有訂位邏輯。

教材 M07-02 也是如此：本次只做表單，後續課程再分別建立資料檢核和匯出功能。

## 五、實際上要怎麼向 Coding Agent 下指令？

教材使用四份重要的專案文件。

| 文件                | 主要用途                 |
| ----------------- | -------------------- |
| `problem.md`      | 說明為什麼需要這套系統、要解決什麼問題  |
| `spec.md`         | 定義應有的功能、行為與驗收規則      |
| `architecture.md` | 說明系統結構、元件及技術邊界       |
| `AGENTS.md`       | 說明 Agent 在這個專案中的協作規則 |

這些檔案不是要讓 AI 自己發明制度，而是讓不同次執行都能依據相同的專案知識工作。

以下是依照教材精神整理的實際任務範例。

```
你是協助開發本機資料檢核工具的 Coding Agent。

【先閱讀】
problem.md
spec.md
architecture.md
AGENTS.md

如果檔案不存在或無法讀取，請如實回報，
不要宣稱已經閱讀。

【本次目標】
只完成第一個垂直切片：
建立三個有標籤的資料輸入欄位，
讓使用者可以查看目前輸入內容。

【允許修改】
app.py
tests/

【禁止修改與新增】
不得修改 reference/
不得新增登入、資料庫、報告下載或外部 API。
不得使用真實個資。

【驗收標準】
1. 三個欄位均可輸入。
2. 可以查看目前輸入內容。
3. 畫面明確標示「尚未檢核」。
4. 不得呈現「資料完整」等未經驗證的結論。

【停止條件】
如遇到規格未定義的必要欄位或正式業務規則，
不得自行假設。
請提出具體問題，停止受影響的修改。

【完成回報】
1. 實際修改了哪些檔案
2. 每個檔案修改了什麼
3. Diff 的重點
4. 實際執行了哪些測試命令
5. 測試結果及失敗原因
6. 尚未驗證的事項
```

注意，這是給 Agent 的工作說明，不是已經執行成功的紀錄；檔名與測試命令應依實際專案調整。

### 文字約束與技術約束

告訴 AI「不能修改某個檔案」，不代表它在技術上真的沒有修改權限。

這要區分兩種約束：

| 層次   | 作用                                |
| ---- | --------------------------------- |
| 文字約束 | 讓 AI 理解哪些行為不被允許                   |
| 技術約束 | 用檔案權限、沙箱（Sandbox）、工具白名單等機制，實際限制行為 |

就像公司交代新進員工「不能進財務室」，這是管理規則；而財務室需要門禁卡才能開門，才是技術控制。

兩者應同時存在。OWASP 對 AI Agent 的安全建議也強調最小權限（Least Privilege）及高影響操作的人類審核。

## 六、遇到問題時，Agent 該自行修正，還是停下來？

Agent 應依問題性質決定是否需要人類介入。

要區分「需求歧義」與「實作錯誤」。

情境 A：需求歧義（Requirement Ambiguity）

一間學校要建立學生請假系統，但沒有說明請假超過三天是否需要額外核准。

AI 不應該自行訂定校規，而要提出問題，請負責人確認。

處理：暫停受影響功能，確認規則後再繼續。

情境 B：實作錯誤（Implementation Error）

規格已經要求顯示「請假開始日期」，但畫面卻顯示「入學日期」。

這不是需要重新決定規則的問題，而是程式寫錯。

處理：Agent 可在授權範圍內修正，並驗證修改。

因此，停止條件的設計不能過度僵硬。

如果只是修正拼字或既定範圍內的程式錯誤，不需要每次都停下來要求核准。

但如果會新增正式政策、擴大資料存取、產生支出、刪除重要資料或部署到正式環境，就應該依事先定義的權限和核准規則處理。

## 七、AI 說「已完成」，為什麼還不能直接相信？

假設 AI 告訴你：

「系統已經完成，所有功能均已正常運作。」

這句話本身只是聲明，不是證據。

真正應該確認的是：

| AI 的聲明   | 應有的證據       |
| -------- | ----------- |
| 已經修改程式   | 檔案變更清單、Diff |
| 已經執行測試   | 測試命令及原始結果   |
| 表單可以使用   | 實際操作結果      |
| 符合所有規格   | 逐項對照的驗收紀錄   |
| 沒有新增其他功能 | 檔案差異及依賴變更審查 |

這裡的 Diff，就是修改前後的差異，例如程式增加了哪些內容、刪除了哪些內容。

而測試又有不同層次。單元測試通過，只能證明特定測試案例符合預期，不能自動證明整個系統沒有問題。

例如要驗證表單，可檢查欄位是否可以輸入、鍵盤能否操作、錯誤資料是否被拒絕，以及資料是否被不當外送。

Anthropic 的 Agent 工程指引也強調，要使用工具執行的真實回饋來判斷進度，並設定停止條件與適當的人類審查。

## 八、從不同行業理解這個方法

| 行業   | AI 可以執行   | 必須特別約束        |
| ---- | --------- | ------------- |
| 醫療行政 | 整理病歷欄位及文件 | 不得憑空補寫診斷      |
| 金融   | 整理客戶財務資料  | 不得自行定義核貸規則    |
| 製造   | 分析設備異常紀錄  | 未核准不得直接停機     |
| 法律   | 彙整判決與法規資料 | 不得杜撰判決或法條     |
| 教育   | 產生題目及練習   | 不得擅改正式評分標準    |
| 研究   | 執行資料清理及分析 | 不得改動原始資料或捏造結果 |
| 軟體開發 | 修改程式與測試   | 不得任意擴張功能與權限   |

共同原則是：

AI 可以負責執行、分析、整理及提出建議，但不應自行取得原本沒有被授予的決策權。

這也是為什麼規格、權限、驗收和追溯性必須一起設計。

## 九、最容易犯的四個錯誤

| 常見錯誤                  | 正確做法             |
| --------------------- | ---------------- |
| 指令只說「幫我做好」            | 定義可觀察的成果及驗收標準    |
| 一次交付整套複雜系統            | 拆成可驗收的垂直切片       |
| 以為 `AGENTS.md` 就能保護檔案 | 同時設定真正的執行權限      |
| AI 說測試通過就當作成功         | 檢查實際命令與結果，保留未驗事項 |

讓 AI 在已確認的邊界內自主工作，並在必要時回到人類決策，可以兼顧執行效率與負責人的決策權。

## 十、理解檢核：你會如何設計這份工作契約？

某家醫院希望讓 AI Agent 開發一套「門診資料整理系統」。

第一階段只要求輸入病患編號、看診日期、科別，以及預覽輸入內容。

但在執行途中，Agent 主動提議：「為了讓功能完整，我順便加入診斷建議、電子病歷資料庫及自動寄送報告功能。」

請你回答：

1. 這次真正應該交付的垂直切片是什麼？
2. 你會明確禁止 Agent 做哪兩件事？
3. 哪一種情況必須停止相關修改並詢問人類？
4. 最後，你會要求提供哪些證據，才能決定是否接受成果？

請用自己的話回答，依任務邊界、權限控制、停止條件、驗收證據四個面向核對；閱讀參考解析不代表已提交作答或通過實作驗收。
