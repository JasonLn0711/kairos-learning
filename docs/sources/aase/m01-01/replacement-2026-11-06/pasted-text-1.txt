# AI 協作軟體工程｜M01-01 白話文教學

第一課：先看成品，從問題到成果

這堂課最重要的觀念是：軟體工程不是把程式寫出來，而是用程式解決一個問題，並且證明這個問題真的被解決了。

以前我們可能認為，軟體開發就是工程師寫程式，寫完能執行，就算完成。

但在 AI 時代，AI 可能只要幾分鐘就能產生一個有畫面、有按鈕、有功能的網站。這時候真正困難的事情，反而變成：

「我們怎麼知道 AI 做出來的東西，真的是使用者需要的？」

這就是本課的核心。

## 一、寫出網站，不代表解決問題

假設今天有一位承辦人，每天都要收到許多申請文件。

有些人忘記填申請編號，有些人忘記填文件類型。承辦人必須逐一檢查，既浪費時間，也可能漏看。

現在我們請 AI 幫忙。

做一個能攔截缺漏的工具

缺少必填資料時，清楚提示並阻止錯誤匯出。

兩個網站可能看起來都很漂亮，但只有第二個真正針對承辦人的問題設計。

這裡涉及軟體工程的一個基礎概念：Problem Definition（問題定義）。

我們要先知道：

- Who（誰）：誰會使用這個系統？
- Problem（問題）：他目前遇到什麼困難？
- Outcome（成果）：什麼情況下，才算把困難解決？

以這個例子來說，目標不是「增加一個檢查按鈕」，而是「避免承辦人把未填齊的申請誤認為完整」。

為什麼重要？ 因為 AI 能夠產生程式，但 AI 並不一定知道真實的業務需求。沒有清楚的問題定義，AI 很可能把錯誤的方向做得非常精緻。

## 二、什麼叫做真的做對？我們直接操作看看

假設規定申請編號、申請人代號、文件類型都是必填欄位。

這裡有兩個情境，你可以點選比較。

互動示範：申請資料檢查

情境 A：資料缺漏情境 B：資料齊全

申請編號

SYN-001

申請人代號

DEMO-A

文件類型

尚未填寫

檢查未通過

缺少必填欄位「文件類型」。請補齊後重新檢查。

匯出完整報告此時匯出完整報告的操作必須被阻止。

你應該注意到一件事：

「欄位檢查通過」與「正式申請核准」完全是兩回事。

想像醫院掛號系統，病患姓名、生日、電話都填了，並不代表病患身分已經確認，更不代表醫療服務已經完成。

所以，系統中的「成功」、「完整」、「完成」等文字，都應有明確定義。

這其實也是 UI／UX 與 HCI（Human–Computer Interaction，人機互動）的重要觀念：系統顯示的狀態，必須讓使用者產生正確的理解，而不是錯誤的信心。

## 三、如何把想法變成軟體？理解四類重要文件

你可以把軟體開發想像成蓋一棟房子。

蓋房子之前，我們要知道住戶需求，接著有設計圖，再由工人施工，最後還要驗收。

軟體工程也是一樣。

軟體工程的證據鏈（Traceability）

發現問題

problem.md

為什麼要做？

定義規格

spec.md

怎樣才算做對？

實作程式

app.py

實際怎麼運作？

驗證與交接

tests/ + README

如何證明並讓別人接手？

我們用最白話的方式理解：

problem.md：問題說明書。 它告訴團隊為什麼需要開發這個工具。例如：「承辦人經常收到資料缺漏的申請，人工檢查容易遺漏。」

spec.md：規格說明書。 它把需求變成明確規則。例如：「只要文件類型空白，就必須顯示錯誤訊息，且禁止匯出完整報告。」

app.py：實際執行的程式。 它把上述規則寫進軟體。當使用者點下檢查，程式就判斷欄位是否符合要求。

tests/：測試。 它檢查程式是不是真的遵守規格，而不只是看起來有這個功能。

README：使用與維護說明書。 它告訴其他工程師這個軟體怎麼安裝、怎麼啟動、怎麼測試，以及有哪些限制。

請特別記住：文件並非為了增加工作量，而是為了讓每個人的理解可以互相核對。

如果規格說不能匯出，但程式卻允許匯出，那就是程式沒有符合規格。

如果程式能攔下缺漏，但測試從來沒有檢查過這個情境，就缺少了對應的測試證據。

## 四、AI 說完成了，等於真的完成嗎？

不一定。

這裡要建立一個非常重要的工程觀念：軟體完成有不同層次。

| 層次                     | 白話解釋          | 需要的證據             |
| ---------------------- | ------------- | ----------------- |
| 1. 展示 Demo             | 我自己的電腦跑得起來    | 啟動與實際操作           |
| 2. 驗證 Verification     | 程式符合事先寫好的規格   | 測試結果              |
| 3. 驗收 Validation / UAT | 真正的使用者能完成工作   | 使用者實際操作及驗收紀錄      |
| 4. 正式上線 Production     | 可以提供真實環境使用並維護 | 部署、權限、安全、備份、監控等檢查 |

其中，第二與第三層尤其容易混淆。

Verification：我們有沒有把東西做對？

例如規格要求「文件類型缺漏不得匯出」，測試確認程式確實阻止匯出。

Validation：我們有沒有做出真正需要的東西？

例如承辦人使用後，是否能比原來更準確地發現缺漏，而且不會把「欄位檢查通過」誤解為「正式核准」。

一個系統可以通過所有預先寫好的測試，卻仍然不符合使用者需求。因為最初的需求或規格本身可能就有問題。

這也解釋了為什麼只看 AI 的測試結果，還不能完全取代人類驗收。

### Streamlit AppTest 能做什麼？

Streamlit 是使用 Python 製作互動式應用的工具；AppTest 則可以模擬使用者輸入及操作，檢查程式產生的結果。

例如讓程式自動檢查：當文件類型空白時，是否顯示缺漏提示。

但 AppTest 不能僅靠程式測試就證明承辦人理解這個提示，更無法單靠它證明整個系統已符合正式環境的資安要求。

另外還有一個工程細節：就算畫面上的「匯出」按鈕被停用，也不代表後端一定安全。真正的匯出功能仍應在伺服器端重新確認權限與資料狀態，避免有人繞過畫面直接呼叫 API。

## 五、AI Coding Agent 與人類應該怎麼分工？

你可以把 Coding Agent 想成一位能寫程式、修改檔案和執行測試的工程助手。

但我們不能只說「幫我做一個系統」，然後把所有決策都交給 AI。

比較可靠的工作流程是：

人類確認需求與業務規則

決定哪些欄位必填、什麼情況可以匯出、哪些資料不能使用。

AI 根據規格實作與測試

在允許的檔案範圍內寫程式、執行測試、報告通過與失敗的結果。

人類審查 Diff 與測試證據

Diff 是修改前後的差異。確認 AI 沒有改到不該改的地方，也沒有自行改寫需求。

人類決定是否驗收與上線

確認使用者任務、資料安全、維護責任與部署條件，而不只依賴 AI 的完成宣告。

這不代表人類必須親自寫每一行程式，而是即使把實作交給 AI，仍然要保有定義目標、檢查證據及決定是否接受成果的能力。

## 六、這堂課與往後軟體工程知識有什麼關係？

M01-01 是整門課的起點，因為它建立了一條可以延伸到各個領域的主軸：

| 後續學習領域                        | 與本課的關係                  |
| ----------------------------- | ----------------------- |
| Requirements Engineering 需求工程 | 怎麼知道真正要解決什麼問題           |
| UI／UX／HCI                     | 怎麼讓使用者正確理解與操作           |
| Software Design 軟體設計          | 怎麼規劃程式結構與功能             |
| Testing 軟體測試                  | 怎麼提出證據證明程式符合規格          |
| Cybersecurity 資安              | 怎麼防止越權、資料外洩及不安全操作       |
| DevOps／Deployment 部署維運        | 怎麼讓軟體可靠地提供他人使用          |
| AI Agent Governance 代理治理      | 怎麼限制 AI 的行動權限、審查修改及追蹤責任 |

你會發現，這些領域都不是獨立存在的。它們共同處理的是同一件事：如何讓一個軟體成果從想法走向可信任、可使用、可維護的系統。

## 七、理解檢核：用實際情境判斷

某位同事使用 AI 做了一個申請資料檢查系統。

AI 回報：「已經完成！網站可以開啟，表單可以輸入，按鈕也可以點擊。」

但你還沒有看過測試報告，也沒有請承辦人實際操作。

請問，此時最合理的工程判斷是什麼？

A. 系統已經完成，可以正式提供同事使用。

B. 系統至少可以展示，但還要檢查規格與使用者任務。

C. 因為 AI 說已完成，所以 AI 應負責全部驗收。

D. 只要畫面沒有錯字，就可以認定測試通過。

提交答案並查看解析

本課最值得記住的三個字是「可驗證」。 不只要能展示功能，還要說清楚功能符合哪一項需求、用什麼方法檢查，以及哪些事情尚未驗證。

當你能清楚區分「AI 寫好了」、「程式跑起來」、「符合規格」、「使用者驗收通過」與「可以正式上線」，就已經掌握 AI 協作軟體工程最重要的基本判斷能力。
