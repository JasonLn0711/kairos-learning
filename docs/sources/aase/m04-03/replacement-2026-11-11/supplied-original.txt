# AASE M04-03｜資訊架構與視覺優先序：讓使用者不用猜，就知道該做什麼

本課對應：[M04-03｜資訊架構與視覺優先序](https://learn.cs-kairos.com/courses/aase/v1/m04/concepts/m04-03/?utm_source=chatgpt.com)

這一課最重要的觀念是：好的介面，不只是把資訊放在畫面上，而是讓使用者知道資訊在哪裡、現在應該注意什麼，以及下一步可以做什麼。

假設你走進一家醫院，要完成掛號、看診、批價與領藥。

醫院可能設備先進、裝潢漂亮，但如果掛號櫃檯沒有清楚標示、領藥窗口與繳費窗口混在一起、指示牌充滿看不懂的縮寫，你仍然會感到困惑。

軟體介面也是如此。

設計介面之前，必須先解決三個不同的問題：

| 核心觀念                    | 白話解釋             | 解決的問題         |
| ----------------------- | ---------------- | ------------- |
| 資訊架構（IA）                | 東西應該如何分類、命名與建立關係 | 我需要的東西在哪裡？    |
| 導覽（Navigation）          | 用什麼方式讓人找到它       | 我要怎麼過去？       |
| 視覺優先序（Visual Hierarchy） | 哪些東西應該先被注意到      | 現在應該先看什麼、做什麼？ |

這三者彼此相關，但不能混為一談。教材也特別強調：應該先整理資訊關係，再決定側邊欄、分頁、按鈕等外觀。

## 一、資訊架構（IA）：先把東西整理好，再談怎麼展示

### 1. 用超市理解資訊架構

想像一家大型超市。

沒有合理分類

牛奶、洗衣精、餅乾與電池混在一起，需要不斷尋找。

[A lot of good shrink reduction is store layout.  Where you put your products determines how much gets stolen.  High-theft items near the entrance mean someone can grab them and run out in the blink… | Mac Bolak](https://images.openai.com/static-rsc-4/jriOcfALDSeP2lZszc1L7HWzdWe5YJ1qvp0Jj3mb0zwikpH-FlKAtQbQwIEC3H_c8mfB31utvBICyofTRuF32cATONjkAJx7KCAY3LmRxrufZEfe2XAVkUZLxP56K69oR8Aitax48yoFYRIFEQZBwnAuZCH4_G0joEuQnxDXf0g?purpose=inline)

依顧客需求分類

生鮮、飲料、清潔用品各有區域，顧客可以預測商品位置。

真正改善購物效率的，不只是把貨架換新或改善燈光，而是建立合理的商品分類與擺放關係。

網站也一樣。

假設我們要設計一個大學的學生服務網站，裡面有以下功能：

選課、繳學費、獎學金申請、成績查詢、停車證申請、教授研究計畫、教室借用、畢業離校。

一種分類方法是按照學校行政單位：

- 教務處
- 學務處
- 總務處
- 研究發展處

這是按照組織內部架構分類。

另一種方法是按照學生希望完成的工作：

- 課業與成績
- 學費與獎助
- 校園生活與設施
- 研究與畢業

這是按照使用者的任務分類。

哪種一定比較好？

不一定。假如使用者主要是行政職員，按照權責單位分類可能合理；但如果服務對象是第一次入學的學生，按照任務分類通常是更值得測試的起點。

因此，IA 有一個很重要的設計原則：

資訊應該盡量依照使用者理解世界的方式組織，而不是直接照搬開發團隊或行政組織的內部分工。

### 2. IA 不等於網站地圖

IA 還包括內容盤點、內容品質檢查、使用者研究、分類命名等。

## 二、導覽（Navigation）：讓人知道怎麼找到東西

如果資訊架構是超市的商品分類，導覽就是超市裡的指示牌與通道。

例如，電商網站把商品分為「服飾、家電、食品、居家用品」。這是資訊架構。

但消費者要怎麼找到這些分類？

可以透過頂端選單、側邊欄、搜尋框、商品篩選器，或首頁的分類入口。

這些都是導覽元件。

[The Mysteries of UX Design: A Haphazard Journey - uxax](https://images.openai.com/static-rsc-4/QbPBx9TiFreQNQx6noii_W4PphdDLyDxTWYbHx8CtGgbOXFr4Ajsl-uWjcotXq-r83vm4rslk2QO98VhMGPypQAQVX9vnl0g_hpYbv_hcnYB_sN1PfkDhceb_bzrdl4WrbDdFAKTRXDma6Y_3t98_aXHlYqHs_UHBmrdVwTR1Tk?purpose=inline)

[uxax.org](https://www.uxax.org/post/the-mysteries-of-ux-design-a-haphazard-journey?utm_source=chatgpt.com)

你可以看到，網站地圖描述的是內容之間的關係。真正使用網站時，我們不一定會看到整張地圖，而是透過選單、搜尋或連結來移動。

### 為什麼不能一開始就決定要做側邊欄？

假設你要製作一個線上報名系統，只需要三步：

1. 輸入個人資料。
2. 確認報名資訊。
3. 完成報名。

這時候，做成一個簡單的三步驟介面可能就足夠了。

如果為了看起來像專業系統，硬是加入左側選單、上方分頁、右側工具列，反而讓操作更複雜。

但如果是一個有數百項功能的企業管理平台，就可能需要側邊欄、搜尋功能與多層導覽。

導覽形式應該由資訊複雜度、使用者任務和使用情境決定，而不是由設計師喜歡哪種外觀決定。

## 三、視覺優先序（Visual Hierarchy）：讓重要的事情先被看見

想像飛機駕駛艙。

飛行員面前有許多儀表，但是正在飛行時，飛行高度、速度、警告訊息等資料的重要程度，與座椅調整設定完全不同。

如果所有資訊都用一樣大的字體、一樣鮮豔的顏色呈現，就會增加辨認重點的困難。

介面設計也有同樣的問題。

視覺優先序，就是透過大小、位置、間距、對比與分組，讓使用者在視覺上更容易分辨資訊的重要程度。

Nielsen Norman Group 將視覺優先序列為重要的視覺設計原則之一。

### 看看兩種不同的資訊安排

安排 A｜所有事情都很重要

管理系統

進階設定

下載報告

查看結果

開始檢查

狀態：INVALID

資料、說明、紀錄、診斷、輸出混在一起。

問題：使用者不清楚現在該做哪件事。

安排 B｜依照工作任務呈現

申請資料檢查

請確認三項必要資料。

申請編號：A1024

申請人代號：P008

文件類型：未填寫

&#x20;尚缺少文件類型

補填文件類型

改善方向：錯誤、修正方式與下一個動作有清楚關聯。

以上是說明性草圖，不是經過使用者測試的正式設計，也沒有可操作功能。

兩種安排包含類似的功能，但第二種讓使用者更容易回答三個問題：

- 我現在處於什麼狀態？
- 有什麼問題需要處理？
- 下一步應該做什麼？

這就是視覺優先序真正要達到的目的。

### 視覺優先序的五種常用方法

| 方法           | 白話說明              | 使用例子          |
| ------------ | ----------------- | ------------- |
| 大小（Scale）    | 更重要的標題通常更醒目       | 頁面主標題大於補充說明   |
| 位置（Position） | 把當前需要的資訊放在容易發現的地方 | 付款總額靠近確認付款動作  |
| 對比（Contrast） | 用視覺差異區分不同重要性      | 主要操作與次要操作不同   |
| 間距（Spacing）  | 相關資訊靠近，不相關的適度分開   | 訂單金額與付款按鈕形成群組 |
| 分組（Grouping） | 相同任務的資訊放在一起       | 病人資料與檢查結果分為兩區 |

這裡有一個很重要的反直覺觀念：

不是所有重要資訊都要放大、加粗或使用鮮豔顏色。

如果畫面上每個按鈕都很醒目，使用者仍然不知道哪一個最重要。

好的視覺優先序，是讓不同資訊有適當的層次。

## 四、主要動作（Primary Action）：不同狀態下，最重要的事會改變

這是本課很值得深入理解的部分。

想像你在機場使用自助報到機。

尚未輸入訂位資料時，主要動作是「查詢訂位」。

找到訂位後，主要動作可能變成「確認航班與旅客」。

完成報到後，才出現「列印登機證」。

系統不能在任何狀態下，都把「查詢訂位」「確認報到」「列印登機證」三個按鈕放得一樣顯眼，卻不解釋各自的使用條件。

因為操作有先後關係。

例：資料完整性檢查系統的狀態與主要動作

1. 尚未檢查

   使用者需要確認輸入內容，主要動作是「檢查資料」。
2. 檢查中

   顯示檢查進度，避免重複提交，並說明目前正在處理。
3. 發現缺件

   明確指出缺少什麼，主要動作改為「補填資料並重新檢查」。
4. 完整性檢查通過

   顯示當次檢查結果，必要時才提供「預覽」與「匯出報告」。

這是示範用的四狀態設計。完整性檢查通過不代表正式審核或核准。

這裡的關鍵是：主要動作跟隨使用者目前的狀態改變，而不是讓使用者自己從許多按鈕中猜測。

不過，也不能為了介面簡潔，就把重要錯誤隱藏。

例如，醫療系統顯示某項檢驗仍缺資料，即使這種情況不常發生，也應該明確告知，而不是把它藏到「進階設定」。

## 五、手機與電腦：畫面可以改變，但資訊的意思不能改變

這裡涉及一個重要術語：

Responsive Design（響應式設計）：同一套介面隨著螢幕尺寸與操作方式改變呈現。

假設電腦版把「資料輸入」放左邊、「注意事項」放右邊。

在手機上，左右並排通常會改成上下排列。

但如果注意事項說「請先確認檢查條件，才能送出」，那麼重新排列後，注意事項就不應該落在使用者已完成送出操作之後。

桌面版

1\. 任務與注意事項

2\. 輸入資料

3\. 輸入說明

4\. 檢查與結果

手機版

1\. 任務與注意事項

2\. 輸入資料

3\. 輸入說明

4\. 檢查與結果

示意：視覺位置可以改變，但有意義的資訊先後關係必須保留。

W3C 的 WCAG 2.2「Meaningful Sequence」（有意義的順序）規定：當內容順序會影響理解時，程式必須能判定合理的閱讀順序。

並不是所有獨立卡片都只能有一種排列方式；重要的是，不要讓重新排版破壞原本的意思。

### 還有一個常被忽略的細節：欄位名稱

假設一個輸入框裡寫：

`請輸入申請編號`

這稱為 Placeholder（輸入提示文字）。

問題在於使用者開始輸入後，提示通常就消失了。

比較可靠的做法是讓「申請編號」成為持續可見的 Label（欄位標籤），再另外提供格式範例。

而且在程式中，還需要讓這個標籤與輸入控制項正確關聯，讓螢幕閱讀器等輔助科技能辨認。

[image](https://www.google.com/s2/favicons?domain=https://www.w3.org\&sz=32)

W3C



所以，介面設計不只是讓眼睛看起來舒服，也要讓不同能力、不同裝置的使用者都能正確理解與操作。

## 六、從不同行業看，怎麼應用這些觀念

| 行業   | 資訊架構問題            | 視覺優先序應該突出什麼        |
| ---- | ----------------- | ------------------ |
| 醫療   | 病人資料、檢驗、用藥、處置如何分組 | 當前需要處理的臨床資訊與重要警示   |
| 電商   | 商品如何分類與篩選         | 商品價格、規格、庫存、購買動作    |
| 銀行   | 帳戶、轉帳、投資與貸款如何組織   | 金額、收款對象、交易確認與風險提醒  |
| 製造業  | 設備、工單、維修與品質資料如何組織 | 異常設備、待處理工單、停機警報    |
| 教育   | 課程、教材、作業、測驗如何分組   | 目前進度、下一個學習任務、待完成事項 |
| 政府服務 | 申請、查詢、補件、進度追蹤如何分類 | 目前案件狀態、期限與下一步處理方式  |

這些例子有共同原則，但沒有一種固定排版能適用所有產業。

例如醫療儀表板與電商網站，都需要視覺優先序，但兩者對於錯誤提醒、資訊密度及操作限制的要求可能完全不同。

## 七、真正要設計一個介面，應該如何開始？

我建議把本課觀念轉成一套可以反覆使用的設計流程。

從使用者任務到可測試介面的工作流程

1\. 定義使用者與工作任務

誰來使用？想完成什麼？

2\. 盤點所有內容與功能

需要哪些資料、按鈕、錯誤與結果？

3\. 建立 IA：分類、命名與關係

哪些資訊應該放在一起？

4\. 定義狀態、導覽與視覺優先序

每個狀態下，該先看什麼、做什麼？

5\. 畫 Wireframe（線框稿）並驗證

檢查桌面、手機、鍵盤及真實工作任務

其中，Wireframe 就是先用簡單的方框、文字和排列方式，畫出介面如何運作。暫時不需要處理精緻的圖示、配色與動畫。

如果要讓這套流程更有科學依據，還可以使用兩種研究方法：

Card Sorting（卡片分類法）：把功能名稱寫成卡片，請使用者依照自己的理解分組。目的是發現使用者心中可能的分類方式。

Tree Testing（樹狀結構測試）：先建立分類結構，再請使用者完成尋找任務，例如「請找到停車證申請」。觀察他們能否在不依賴美觀版面的情況下找到正確位置。

前者用來探索分類方式，後者用來評估已建立的架構。

### 將成果記錄成 `wireframe-notes.md`

以下是一個可直接用在練習專案的簡化模板：

```

# M04-03 畫面資訊與線框規劃

## 1. 使用者與任務
使用者：案件承辦人
目標：檢查三項必要資料是否完整

## 2. 內容清單
- 申請編號
- 申請人代號
- 文件類型
- 必填說明
- 檢查動作
- 缺漏與修正方式
- 當次檢查結果
- 預覽與匯出

## 3. 資訊分組
- 任務與限制
- 資料輸入
- 檢查動作與結果
- 次要說明及診斷

## 4. 主要動作
- 未檢查：檢查資料
- 檢查中：顯示處理狀態
- 缺件：補填並重新檢查
- 完整：預覽、匯出當次結果

## 5. 閱讀順序
任務 → 必要資料 → 檢查 → 結果

## 6. 待驗證事項
- 使用者能理解分類與欄位名稱嗎？
- 錯誤是否有文字說明及修正方法？
- 手機閱讀順序是否合理？
- 鍵盤能否依合理順序操作？
- Label 是否與輸入控制項正確關聯？

```

這樣做的好處是，你還沒有花時間寫前端程式，就已經把內容、流程、狀態與驗證條件整理出來。

之後交給人類工程師或 AI Coding Agent 實作，也比較容易明確溝通需求。

## 八、本課最容易犯的五個錯誤

1. 先畫漂亮畫面，再思考使用者需求。 可能出現視覺好看但工作流程不合理的介面。
2. 把資訊架構誤認成選單設計。 選單只是資訊架構的一種呈現方式。
3. 所有按鈕都同樣醒目。 缺乏明確的主要動作，增加判斷負擔。
4. 只靠顏色表示錯誤。 應以文字說明問題及修正方式，而不是只有紅色提示。
5. 只測試電腦的視覺排版。 忽略手機、鍵盤、螢幕閱讀器與實際操作順序。
