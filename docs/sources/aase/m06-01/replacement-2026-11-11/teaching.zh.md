# M06-01｜User Flow 不等於系統架構：白話文完整教學

這一課最重要的觀念是：使用者怎麼操作軟體，跟軟體內部怎麼運作，是兩件不同的事。

- User Flow（使用者流程）：描述一個人怎麼完成任務。
- System Architecture（系統架構）：描述有哪些軟體組件、各自負責什麼、如何互相溝通，以及資料存放在哪裡。

本課的目標是把使用者流程與系統架構分別畫清楚，並讓兩者互相對照。

- 結帳時是誰計算金額？
- 如果刷卡機故障，怎麼處理？

外面看起來做一樣的事情，裡面可能是完全不同的系統。

先分清各自要回答的問題，再選擇圖中的元素與驗證方法。

| 比較面向 | User Flow   | System Architecture  |
| ---- | ----------- | -------------------- |
| 核心問題 | 使用者如何完成任務？  | 系統如何支援任務？            |
| 主要對象 | 使用者、產品設計師   | 工程師、架構師、維運人員         |
| 描述內容 | 步驟、決策、錯誤與回復 | 程序、服務、儲存、通訊與責任       |
| 主要元素 | 畫面、操作、判斷    | 前端、後端、模組、資料庫         |
| 典型問題 | 按錯怎麼返回？     | 程式故障如何復原？            |
| 驗證方法 | 能否順利完成操作？   | 組件是否正確協作，且符合品質與安全要求？ |

兩者不是二選一，而是彼此補充。

### 把兩張圖連起來

用同一個操作逐列對照處理位置。

| 使用者的操作 | 系統裡實際需要發生的事情      |
| ------ | ----------------- |
| 填寫資料   | 瀏覽器收集輸入，應用程式管理狀態  |
| 按下檢查   | Python 執行驗證邏輯     |
| 發現缺漏   | 系統產生驗證結果，介面顯示提示   |
| 修改後重查  | 使用更新後的輸入重新驗證      |
| 下載結果   | 程式產生 JSON，瀏覽器提供下載 |

每個有意義的操作，都應該能追蹤到負責處理它的軟體部分。

## 四、理解幾個經常混淆的技術觀念

判讀架構時，請分別核對檔案、執行程序與資料生命週期，並依使用規模檢查責任。

### 1. 程式檔案不等於獨立服務

假設有以下兩個 Python 檔案：

```python
# rules.py
def validate(data):
    return bool(data.get("name"))

```

```python
# app.py（與 rules.py 放在同一目錄）
from rules import validate
result = validate({"name": "Alice"})
print(result)
```

在 Python 3 環境把上例分成 rules.py 與 app.py，執行 python3 app.py，預期印出 True。完成後可刪除這兩個練習檔及 __pycache__；不要刪除工作坊原始程式。這個最小例子只檢查 name 的真假值，不等於工作坊三欄位的完整驗證規則。

這通常只是同一個 Python 程序中的模組呼叫，不代表有兩台伺服器。

要稱為獨立服務，通常需要有自己的執行邊界，可能透過 HTTP、訊息佇列等方式與其他服務溝通。

### 2. 沒有資料庫，不等於沒有資料

想像你在網站填寫資料，但沒有按儲存。

資料可能仍然存在瀏覽器或伺服器的記憶體中。你下載的檔案也可能長期留在電腦裡。

因此，架構設計必須問的不只是「有沒有資料庫」，還包括「資料在哪裡、存多久、誰能存取、什麼事件會使資料消失」。

### 3. 本機執行，不等於已經安全

假設一個程式原本只有一個人使用，現在要給十名員工使用。

介面可能完全不用修改，但架構需要重新思考登入驗證、權限、不同使用者的資料隔離、同時執行的資源使用，以及伺服器失敗後如何復原。

換句話說，User Flow 不變，並不代表 System Architecture 不需要改變。

## 五、不同產業的實際運用

下列情境用來練習分辨操作問題與結構問題，並非特定機構的實際架構。

| 產業    | User Flow 的問題   | Architecture 的問題   |
| ----- | --------------- | ------------------ |
| 醫療    | 病患如何掛號、查詢、取消？   | 掛號系統怎麼連接醫院資料庫？     |
| 銀行    | 客戶如何申請貸款？       | 誰計算信用評分？資料送去哪裡？    |
| 物流    | 客戶如何查詢包裹進度？     | 掃碼資料如何傳送、保存與更新？    |
| AI 應用 | 使用者如何上傳檔案並取得摘要？ | 文件解析、模型推論與儲存在哪裡執行？ |
| 電子商務  | 消費者如何下單及退款？     | 如何協調訂單、庫存、金流與退款？   |

同一個 User Flow 可能有許多種技術實作。選擇架構時，要根據資料量、使用人數、安全需求、成本與維運能力，而不是只根據介面看起來有多少功能。

## 七、實際應用：如何要求 AI 幫你設計？

以後當你要使用 AI Coding Agent 開發軟體時，可以使用這樣的順序：

1. 先定義使用者要完成什麼任務，以及成功條件。
2. 畫出 User Flow，涵蓋正常操作、判斷分支與錯誤復原。
3. 根據功能、資料與非功能需求提出 System Architecture。
4. 把每個重要操作對應到實際處理的模組與資料位置。
5. 區分「已實作」、「設計提案」與「待確認」，再檢查安全邊界。

對既有專案尤其重要：不要讓 AI 憑想像畫一張漂亮的架構圖，而要讓它檢查程式碼、設定與部署環境，說明每個架構元素的證據。
