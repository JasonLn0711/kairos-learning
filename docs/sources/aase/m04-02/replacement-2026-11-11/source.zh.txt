# AASE M04-02｜Task Analysis（任務分析）與操作流程：如何設計真正幫助人完成工作的系統？

這一課最重要的觀念是：設計軟體時，不要先想畫面上要放哪些按鈕，而要先理解使用者究竟想完成什麼工作。

例如，假設一家醫院想開發掛號系統。

工程師可能一開始就想到：「我們需要搜尋醫師的功能、日期選擇器、掛號按鈕及確認頁面。」

但病人的想法可能完全不同：

「我身體不舒服，想找到適合的醫師，確認有沒有可以就診的時間，成功掛到號，而且知道接下來該去哪裡。」

這兩種思考的差別，就是本課的核心。

本節依據 [AASE M04-02 正式教材](https://learn.cs-kairos.com/courses/aase/v1/m04/concepts/m04-02/?utm_source=chatgpt.com)，並延伸 Nielsen Norman Group 的 Task Analysis 方法。

## 一、先建立整體觀念：Task Analysis 到底在分析什麼？

Task Analysis 中文叫做「任務分析」。

白話來說，就是把一件人想完成的工作，拆解成一系列可以理解、執行與檢查的小任務。

我們希望回答五個問題：

1. 目標（Goal）： 使用者究竟想完成什麼？
2. 動作（Action）： 為了完成目標，需要做哪些事情？
3. 判斷（Decision）： 什麼時候需要選擇、比較或決定？
4. 資訊與回饋（Information & Feedback）： 人需要知道什麼？系統又必須告訴人什麼？
5. 例外與回復（Exception & Recovery）： 如果中途出錯、缺少資料或想改變決定，怎麼辦？

任務分析的核心思考架構

使用者目標 Goal

最終要得到什麼成果？

動作 Action

需要做什麼？

判斷 Decision

依什麼條件決定？

資訊與回饋

需要知道什麼？

例外與回復

失敗後怎麼繼續？

可驗證的完成結果

怎麼證明工作真的完成？

注意：任務分析不只是把事情排列成步驟，更重要的是找出那些看不見的思考、需要的資訊，以及可能失敗的地方。

### 用餐廳點餐來理解

假設你要幫五位同事訂午餐。

從操作畫面的角度來看，可能只有：

打開網站 → 選餐點 → 按下訂購。

但真正的工作包含：確認五個人各想吃什麼、是否有人不能吃辣、餐點是否售完、費用是否符合預算、外送是否來得及，以及訂單有沒有真正成立。

甚至訂購完成後，店家突然通知某種餐點售完，你還得知道怎麼修改訂單。

如果你只設計了「選餐點」和「提交訂單」，卻沒有「缺貨後如何處理」，那這套系統可能看起來很簡單，卻無法協助使用者順利完成工作。

所以 Task Analysis 的核心不是研究使用者按了什麼，而是研究使用者如何達成目標。

## 二、如何真正把一件工作拆開？

我們先回到教材中的主要案例：「收件資料完整性檢查」。

假設某個行政單位收到一筆申請資料，系統需要檢查資料是否完整，並產生一份報告。

如果你直接要求 AI：

「幫我製作一個資料輸入頁面，包含送出、修改和下載按鈕。」

AI 很可能幫你產生一個能操作的網頁，但不一定知道業務真正需要什麼。

更好的方式是先拆解任務。

### 第一步：明確定義工作的起點與終點

| 要素   | 定義                |
| ---- | ----------------- |
| 使用者  | 負責檢查申請資料的人員       |
| 目標   | 取得與最新資料一致的完整性報告   |
| 前置條件 | 有待檢查的資料，以及明確的欄位規則 |
| 起點   | 開始處理這筆資料          |
| 成功終點 | 確認檢查通過，取得正確的當次報告  |
| 其他終點 | 明確取消，或因資料不足而暫停    |

這裡有一個關鍵：

按下「下載」不代表成功。

如果使用者先完成檢查，再修改資料，卻下載到修改前的舊報告，那系統雖然正常執行了下載功能，使用者的工作仍然失敗。

這就是為什麼任務分析必須先定義「什麼才算成功」。

### 第二步：把大任務拆成子任務

我們可以得到下列拆解。

| 子任務     | 人需要做什麼      | 系統應提供什麼      |
| ------- | ----------- | ------------ |
| 1. 準備資料 | 確認資料及規則     | 欄位說明、必填條件    |
| 2. 執行檢查 | 輸入資料並啟動檢查   | 明確的檢查結果      |
| 3. 處理缺漏 | 找到缺件、取得正確資料 | 缺件提示、保留原有資料  |
| 4. 核對結果 | 確認報告與最新輸入一致 | 最新結果及有效狀態    |
| 5. 完成任務 | 匯出報告或取消     | 完成確認、錯誤與取消回饋 |

注意第三項「處理缺漏」。

它不是每個人都必須執行的步驟。如果原本就沒有缺件，應直接跳過。

這帶出下一個重要概念。

## 三、階層式任務分析 HTA：拆解工作，不等於規定執行順序

HTA 是 Hierarchical Task Analysis，中文叫做「階層式任務分析」。

它把一個大目標分成小目標，小目標又可以再分成更小的操作。

例如：

0\. 完成收件完整性檢查

1\. 準備資料

2\. 執行檢查

3\. 處理缺件

4\. 核對結果

5\. 匯出或退出

其中「3. 處理缺件」還可以細分為：辨識缺漏 → 取得資料 → 補填資料。這些是任務的層次，不代表每次都會執行。

HTA 除了描述子任務，還需要 Plan（執行計畫），交代什麼條件下執行哪些步驟。

舉例來說，正常情況可以是：

準備 → 檢查 → 核對 → 匯出。

如果發現缺件，就需要：

準備 → 檢查 → 補件 → 重新檢查 → 核對 → 匯出。

這兩條路線都可以達成目標，但執行條件不同。

NN/g 的研究方法也特別區分階層、順序、頻率、認知需求及不同使用者的操作方式。

### 把任務變成真正的操作流程

下面這張是根據教材情境整理的示範流程圖。它不是聲稱所有實際機關都採用此流程。

輸入資料 → 執行完整性檢查

資料有缺漏嗎？

有缺漏

指出缺件並保留資料

能取得正確資料？

能：補填並重新檢查

不能：暫停或取消

無缺漏

預覽目前檢查結果

資料又修改了嗎？

有：使舊結果失效並重查

沒有：確認並匯出

這裡最重要的不是方框怎麼畫，而是你有沒有定義清楚每一個判斷點（Decision Point）與回復路徑（Recovery Path）。

例如，「資料有缺漏嗎？」就是一個判斷點。

「找到正確資料後，回去重新檢查」就是一條回復路徑。

如果沒有這些設計，使用者一遇到錯誤就可能卡住。

## 四、人的工作負擔，不只有點滑鼠的次數

這也是 M04-02 很值得深入理解的部分。

我們可以把工作負擔區分成兩大類：

| 工作負擔                                | 白話說明               | 例子                    |
| ----------------------------------- | ------------------ | --------------------- |
| 操作負擔（Physical / Interaction Effort） | 人需要實際執行多少操作        | 點擊、打字、捲動、切換頁面         |
| 認知負擔（Cognitive Load）                | 人需要記住、理解、比較及判斷多少事情 | 記住錯誤欄位、判斷資料是否正確、思考下一步 |

### 例子：報稅系統

假設你在報稅網站填寫資料，畫面最下方顯示：

「你有三個錯誤，請修正。」

但是它沒有告訴你錯在哪裡。

你必須回到上方，重新找幾十個欄位，猜測哪裡不對。

工程師可能會說：

「使用者只要再按一次送出就好了，沒有增加太多操作。」

但使用者其實必須進行大量思考：回憶填過什麼、辨識錯誤、比較資料、記住需要修正的地方。

這就是認知負擔。

改善方法可以是讓錯誤訊息出現在相關欄位旁邊，說明錯誤原因，並保留已經填好的內容。

但要特別注意：這些只是有理論依據的設計假設，不代表已證明能縮短使用時間。 真正的改善效果需要透過使用者測試來驗證。

### AI 系統尤其要注意「假裝完成」

例如 AI 幫忙審查文件，發現缺少文件類型。

錯誤的設計是讓 AI 自己猜一個類型，然後顯示「檢查通過」。

正確的設計方向是呈現資料不足，讓有權限的人補充或確認，再繼續檢查。

這是任務設計與資訊可靠性的交會點：不能為了讓流程順暢，就犧牲結果的真實性。

## 五、把 Task Analysis 應用到不同產業

任務分析並不是軟體工程才需要。凡是有人要按照一定程序完成工作，就可以使用。

| 產業   | 使用者真正的目標          | 容易忽略的判斷與例外            |
| ---- | ----------------- | --------------------- |
| 醫療   | 安全地完成門診預約         | 找不到適合科別、名額已滿、預約後需要改期  |
| 金融   | 完成貸款申請並掌握審核狀態     | 文件不足、需要補件、資料修改後必須重審   |
| 製造業  | 確認產品符合出貨品質要求      | 檢驗異常、產品隔離、修復後重新檢驗     |
| 電子商務 | 順利退貨並取得退款         | 不符合退貨條件、物流失敗、退款狀態不明   |
| 資訊安全 | 完成資安事件處理並確認風險受到控制 | 證據不足、誤判警報、隔離失敗、需要升級通報 |

我們選製造業深入看一次。

假設工廠有一套品質檢查系統，檢查員需要確認產品能否出貨。

最表面的設計只有兩個按鈕：「合格」、「不合格」。

但如果深入分析，就會發現檢查員需要取得檢查標準、執行測量、判斷結果、記錄證據。如果不合格，可能需要隔離產品、安排修復或報廢；修復後還需要重新檢查。

甚至同一產品可能要經過多道檢查，由不同人負責。

這時我們又會接觸另一種分析方法：Workflow Analysis（工作流程分析）。

Task Analysis 著重單一使用者如何達成目標；Workflow Analysis 則更著重跨越不同人員、角色或部門的工作如何銜接。 兩者可以相互配合。

## 六、Task Analysis 與其他設計方法的關係

這幾個概念容易混淆，可以這樣區分：

| 方法                       | 主要回答的問題             |
| ------------------------ | ------------------- |
| Task Analysis（任務分析）      | 為了完成工作，人需要做什麼、思考什麼？ |
| HTA（階層式任務分析）             | 大任務包含哪些小任務？各自如何執行？  |
| User Flow（使用者流程）         | 使用者在系統裡可能走哪些路線？     |
| UI Design（介面設計）          | 畫面應如何讓人執行操作並取得回饋？   |
| Usability Testing（易用性測試） | 真實使用者能否順利完成任務？      |

你可以把這些方法理解成一個設計過程：

01

需求工程

定義使用者問題與成功條件

02

Task Analysis

找出工作、判斷、資訊及例外

03

User Flow 與 UI 設計

安排操作路徑、介面和回饋

04

系統實作

把業務規則與操作行為做成軟體

05

測試與驗證

確認功能正確，使用者也能完成工作

這是理解軟體設計時的概念順序，實際專案通常需要在各階段之間反覆修正，不是只能往前走。

## 七、實際練習：如何自己完成一份 Task Analysis？

現在你可以不依賴任何專門軟體，只用文字編輯器，完成一份真正能交給設計師與 AI Coding Agent 使用的任務分析。

以教材中的資料完整性檢查為例，建立一個 `wireframe-notes.md`，寫入以下內容：

```

# Task Analysis：資料完整性檢查

## 1. 工作目標
取得與最新輸入資料一致的完整性報告。

## 2. 使用者
負責檢查申請資料的人員。

## 3. 前置條件
- 已取得待檢查資料
- 已定義必填欄位與檢查規則

## 4. 起點與終點
起點：開始處理資料
成功終點：確認結果有效並匯出報告
其他終點：明確取消或暫停待補資料

## 5. 子任務
T1 準備並輸入資料
T2 啟動完整性檢查
T3 辨識缺件並補填（條件式）
T4 重新檢查並確認最新結果
T5 匯出報告或退出

## 6. 條件與例外
E1 缺少必要資料：
   提示缺件，不允許完整匯出。

E2 使用者修改已檢查資料：
   原檢查結果變成過期狀態，
   必須重新檢查。

E3 找不到必要資料：
   顯示待確認，不自行猜測值。

E4 使用者取消：
   明確結束，不能標示為完成。

## 7. 必要介面回饋
- 顯示必填欄位
- 錯誤提示靠近對應欄位
- 保留已輸入的有效資料
- 區分有效、缺件、過期結果
- 顯示清楚的完成或退出狀態

## 8. 待確認問題
文件類型應由誰提供？
如果無法取得，誰有權決定後續處理？

## 9. 驗證方式
使用合成資料進行紙上走讀。
再以實作原型進行功能測試及使用者測試。
不將紙上推測當作真實使用者量測。

```

這份文件有三個實用價值。

第一，它可以讓設計師知道畫面必須支援哪些工作，而不只是有哪些元件。

第二，它可以讓工程師知道功能背後的條件與規則。

第三，它可以讓測試人員知道哪些例外情況一定要測試。

### 進一步轉換成 AI Coding Agent 的工作規格

當任務分析完成後，你就不必只對 AI 說「幫我做一個表單」。

你可以把任務分析交給 AI，要求它根據規則設計功能與測試。

例如以下三項驗收條件：

測試 A：資料缺漏

如果使用者缺少必要欄位並執行檢查，系統必須指出缺件，不能顯示完整通過或提供完整報告匯出。

測試 B：結果過期

如果使用者在檢查通過後修改資料，原有檢查結果必須失效，重新檢查前不得以舊結果當作最新結果。

測試 C：明確取消

如果使用者取消任務，系統不可將取消記錄為成功完成。

這也是任務分析與軟體測試的重要連結：

Task Analysis 描述人應該如何完成工作；Acceptance Criteria（驗收條件）把這些需求轉換成可以檢查的系統行為。

不過，這些功能測試即使全部通過，也還不代表真實使用者一定能輕鬆完成任務。

因此，還要邀請符合目標族群的使用者實際操作，觀察他們是否能理解訊息、找到下一步、處理錯誤，以及成功完成工作。

這符合 NN/g 建議的兩階段做法：先蒐集真實任務資料，再分析任務的結構與複雜度。

## 八、理解檢核：換個產業，你能自己做任務分析嗎？

假設一家物流公司準備開發給配送司機使用的 App。

司機需要在送達包裹後，請收件人簽收並回報配送結果。

但現實中可能遇到收件人不在、地址錯誤、手機沒有網路，或簽收後發現輸入了錯誤的收件資訊。

問題 1：司機真正的工作目標是什麼？

問題 2：請拆出至少三個子任務，並指出需要哪些資訊。

問題 3：如果收件人不在或網路中斷，應如何設計回復路徑？

提交答案並取得解析&#x20;

本課最值得帶走的一句話：

優秀的軟體設計，不是讓使用者順利按完所有按鈕，而是讓使用者在正常、異常與需要修正的情況下，都能正確、可靠地完成真正的工作。
