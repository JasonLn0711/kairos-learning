# M03-04｜MVP、範圍與不做清單：如何決定第一版究竟要做多少？

本課最重要的一句話：MVP 不是把產品做到最陽春，而是用最小的工作量，完成一件真正有用、可以驗證的事情。

你正在學習的這一課，其實是在教一項非常重要的軟體工程能力：決定什麼應該做、什麼暫時不做，以及怎麼知道已經完成。

這項能力甚至比寫程式還重要。因為如果一開始就選錯工作範圍，即使使用很強的 AI Coding Agent，也可能只是更快地做出不需要的功能。

本課沿用原 M03-04 v1.0.2 教材的範圍方法，以下以白話案例逐步說明。

## 一、先用開餐廳理解 MVP

假設你想開一間餐廳，最終目標是提供 100 道料理。

你有兩種開發方式。

做法 A：一次做完所有事情。

先設計 100 道菜、會員系統、訂位系統、外送系統、點數制度。半年後才真正讓第一位客人吃到東西。

做法 B：先做好一種便當。

先選擇一種便當，建立訂餐、確認、製作、缺貨處理及交付流程，然後請客人實際購買。

這就是 MVP 的核心精神。

@figure1

注意：第二種做法雖然只賣一種便當，但是顧客仍然能順利完成購買。

反過來說，如果你做了漂亮的菜單，卻無法真正出餐，就不是一個可以驗證完整取餐任務的 MVP。

所以：

MVP = 最小的必要功能 + 完整的核心流程 + 可以驗證的結果。

## 二、MVP 究竟在驗證什麼？

這裡有一個觀念很容易被忽略。

MVP 不是單純為了節省開發時間，而是為了降低不確定性。

假設你想做一個 AI 文件處理系統。

你的想法可能有：

- AI 自動讀取文件。
- 辨認缺少的資料。
- 自動產生報告。
- 多人共用。
- 歷史案件查詢。
- 自動寄送電子郵件。

這些功能都有價值，但你可能還不知道使用者最需要哪一項。

因此第一步不是問：

「我們能做出多少功能？」

而是問：

「我們最需要先證明什麼事情？」

例如：

使用者能不能在匯出報告之前，發現缺少哪些資料、補齊資料，最後取得正確報告？

只要這個問題還沒回答，先做會員系統、統計圖表、進階 AI 模型，都不一定能降低最重要的風險。

這也是 MVP 和單純的功能清單最大的不同。

## 四、需求應該如何分類？

教材提出三種範圍狀態，我們可以把它理解成三個箱子。

| 分類                 | 白話意思            | 範例                 |
| ------------------ | --------------- | ------------------ |
| 第一版（In scope）      | 現在必須做           | 資料檢查、缺漏修正、報告匯出     |
| 延後（Deferred）       | 以後可能做，但要有重新啟動條件 | 多人共用、歷史查詢          |
| 本版不做（Out of scope） | 這次明確不承擔         | 正式受理、使用真實個資、自動對外通知 |

這裡最值得學習的是「延後」和「不做」的差異。

「延後多人共用」不代表下個版本一定要做，而是等到確認使用者角色、權限、資料隔離和維運需求之後，再重新決定。

「本版不做正式受理」，則代表這次專案沒有承擔正式業務的責任。如果有人要求加入，就可能需要重新定義專案。

這可以避免一種常見的軟體開發問題：Scope Creep（範圍蔓延），也就是開發過程中不斷加入新要求，卻沒有重新評估時間、成本和風險。

## 五、當別人一直要求新增功能，怎麼辦？

假設你已經把第一版規劃完成，現在有人說：

「我們能不能順便加上一次上傳 100 份文件？」

聽起來只需要增加一個「批次匯入」按鈕。

但實際上你還要考慮：

如果第 37 份文件有問題怎麼辦？是全部停止，還是繼續處理？錯誤如何回報？可不可以重新執行？會不會產生重複報告？

因此，新增一個功能不是只增加一個按鈕，而是可能增加一整條工作流程。

你可以用下面這個簡單的決策模型。

新增需求的決策矩陣

| 判斷問題          | 建議處理          |
| ------------- | ------------- |
| 沒有它，核心任務無法完成？ | 納入第一版必要範圍     |
| 有幫助，但不影響本次驗證？ | 延後並記錄啟動條件     |
| 會涉及新的安全或業務責任？ | 重新評估範圍及授權     |
| 新增它，原定時間會不夠？  | 提出取捨，由範圍負責者決定 |

例如增加批次匯入，就應該同時說明：「如果這次要做批次匯入，可能需要延後其他功能，或是增加開發與測試時間。」

不能因為要趕進度，就偷偷刪除缺件檢查或必要測試。

## 六、什麼叫作 MVP 已經完成？

不是 AI Agent 告訴你「程式寫好了」，也不是網站可以打開，就代表完成。

應該先定義 Acceptance Criteria（驗收條件），讓任何人都可以用一致的方法檢查。

例如：

| 測試情境        | 預期結果            |
| ----------- | --------------- |
| 三個必要欄位全部完整  | 允許產生正確報告        |
| 有一個必要欄位缺漏   | 顯示缺漏提示，不允許完整匯出  |
| 使用者補齊缺漏     | 重新檢查後可以匯出       |
| 使用者預覽後修改資料  | 舊結果失效，必須重新檢查    |
| 使用者不知道如何補資料 | 觀察提示是否足夠清楚，記錄問題 |

前四項主要檢查系統行為；最後一項則是在觀察使用者是否真的能順利操作。

兩者都重要，但不能混為一談。

這些是設計的驗收案例，不代表已經實際執行並通過測試。

## 七、我們實際要寫出什麼文件？

教材要求產生的成果是 `problem.md`。

它不是程式，而是一份讓開發者、AI Agent 和需求負責者都能理解的規劃文件。

以下是可以直接練習的簡化範例：

```
# MVP 範圍定義

## 核心問題
使用者能否在匯出前發現並修正必要欄位缺漏？

## 第一版
- 輸入必要欄位
- 檢查缺漏
- 提示並允許修正
- 重新檢查
- 預覽與匯出

## 必要約束
- 缺件不得完整匯出
- 修改資料後舊結果必須失效

## 延後
- 歷史查詢
  - 重新啟動條件：確認保存與刪除規則
- 多人共用
  - 重新啟動條件：確認角色、權限及資料隔離

## 本版不做
- 正式受理
- 處理真實個資
- 自動對外通知

## 完成條件
- 缺件測試通過
- 補齊重查測試通過
- 修改後重查測試通過
- 完成使用者操作觀察
```

這份文件的價值在於：以後當你要請 AI Coding Agent 開發時，它不必完全靠猜測來判斷什麼功能才算完成。

但也要注意，`problem.md` 是這一課的需求整理成果，並不能取代後續完整的技術規格、測試設計或安全審查。

## 八、再往深一層：MVP、Prototype、PoC 有什麼差別？

這三個概念常一起出現，但關注的問題不同。

| 概念           | 最主要想回答的問題               |
| ------------ | ----------------------- |
| Prototype 原型 | 這個設計看起來、操作起來是否合理？       |
| PoC 概念驗證     | 關鍵技術是否可行？               |
| MVP 最小可行產品   | 用最少的完整能力，能否提供價值並驗證關鍵假設？ |

三者可以重疊。例如，你可以用一個可操作的原型測試 MVP 的工作流程；但技術 PoC 成功，不等於使用者真的需要這個產品。

而這門 M03-04 課程，是把 MVP 的「最小完整範圍」方法用於教學原型，並不是宣稱完成一個課堂 Demo，就等於正式產品已經獲得市場驗證。

## 九、本課的真正核心

把前面所有內容整合起來，其實只要記住一條決策順序：

先問要證明什麼 → 選出最小完整流程 → 保留必要約束 → 明確記錄不做什麼 → 定義驗收證據 → 再開始開發。

對你未來用 Svelte、SvelteKit、Rust，或者 AI Coding Agent 開發軟體，都適用這條原則。

技術選型回答的是「如何實作」，而 MVP 範圍決策回答的是「這一版究竟值得做什麼」。兩者不要顛倒。

現在有四個候選開發方向。

A. 優先做漂亮的首頁及登入介面

B. 完成上傳、缺漏檢查、修正與重新驗證的流程

C. 一次加入多模型、多人協作及批次處理
