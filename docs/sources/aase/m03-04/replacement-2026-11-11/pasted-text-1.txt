# AASE M03-04｜MVP、範圍與不做清單：如何把一個大構想，變成真正做得出來的產品？

這一課最重要的觀念：做產品，不是先把所有想要的功能做出來，而是先找出最值得驗證的問題，用最小的成本完成一件有價值的事，並取得證據，決定下一步。

這個觀念不只適用於軟體開發，也適用於餐飲業、醫療、金融、製造業、教育、政府服務，甚至學術研究。

本課對應 [CS Kairos AASE M03-04 正式教材](https://learn.cs-kairos.com/courses/aase/v1/m03/concepts/m03-04/?utm_source=chatgpt.com)。教材特別強調：第一版必須保留從輸入到結果的完整流程、必要的錯誤處理，以及能證明任務完成的驗收方式。

## 一、先理解 MVP：為什麼不是功能越多越好？

想像你想開一家餐廳。

你的理想是經營一間大型餐廳，具備以下服務：

- 中餐、西餐、日式料理、甜點。
- 內用、外帶、外送。
- 線上訂位、會員制度、點數回饋。
- 自動訂貨、庫存管理、財務分析。

但是，你還不知道附近居民喜不喜歡你的料理，也不知道他們願意付多少錢。

這時候有兩種做法。

做法 A：先打造完整餐廳。

租大店面、聘請廚師、設計菜單、開發會員系統，投入大量資金後才正式營業。

如果最後發現顧客根本不喜歡你的料理，前面的投資就可能白費。

做法 B：先賣一款便當。

先選擇一種最有把握的便當，建立一條完整的服務流程：

最小完整服務流程

顧客點餐

確認訂單

製作餐點

處理異常

交付餐點

顧客能完成購買，你也能知道這門生意是否值得繼續。

你可以觀察：

1. 顧客願不願意購買？
2. 顧客認為價格合理嗎？
3. 顧客會不會再次購買？
4. 每賣出一份便當，扣除成本後還有沒有合理利潤？

這樣就能在投入大量資源之前，取得比較有價值的資訊。

這就是 MVP 的基本精神。

### MVP 到底是什麼？

MVP 是 Minimum Viable Product（最小可行產品）。

把三個英文拆開：

| 英文      | 白話意思                  |
| ------- | --------------------- |
| Minimum | 只做回答核心問題所需的最少部分       |
| Viable  | 在限定情境下真的能運作、具有驗證價值    |
| Product | 可以讓目標使用者實際體驗或操作的產品或服務 |

MVP 概念的重要推廣者 Eric Ries 強調，核心是用最少努力取得最多經過驗證的學習（Validated Learning），而不是單純製造一個功能很少的產品。

[image](https://www.google.com/s2/favicons?domain=https://leanstartup.co\&sz=32)

Lean Startup Co.



所以：

MVP ≠ 做得很陽春的產品。

MVP = 用最小投入，驗證最重要假設的產品或實驗。

要特別區分：在原始的 Lean Startup 脈絡中，MVP 著重真實顧客與市場假設；而 AASE 這一課將概念用在教學原型，重點先放在「能否完成一個可驗證的工作流程」。完成課堂原型，還不能直接宣稱市場需求已被證實。

## 二、最小，不代表可以只做一半

這是本課最容易誤解、也是實務上最重要的地方。

假設你準備開一家洗衣店，第一版只提供「一般衣物洗滌」。

這是合理的範圍縮小。

但是，如果你只提供收衣服務，顧客把衣服交給你後，你沒有洗衣、取衣或異常通知流程，這就不是完整服務。

比較如下：

| 可以合理縮小    | 不應省略的核心部分    |
| --------- | ------------ |
| 只提供一種便當   | 食物安全、訂單交付    |
| 只提供一般洗衣   | 衣物遺失或無法交付的處理 |
| 只提供一種報告格式 | 必要欄位檢查、錯誤處理  |
| 只支援一種機器   | 異常停機與安全保護    |
| 只處理一種預約情境 | 預約衝突檢查       |

你可以減少「服務的種類」，卻不能任意刪掉「這項服務要能正確完成的必要步驟」。

軟體工程稱這種做法為 最小端到端流程（Minimum End-to-End Flow），也常用 Vertical Slice（垂直切片） 來描述：不必先完成所有功能，但是要讓選定的一小段功能，從前端到必要的後端處理與結果都能跑通。

例如，一套訂單系統：

有價值的第一版

輸入訂單 → 檢查庫存 → 確認訂單 → 產生結果

缺貨時必須有明確回應，不能假裝訂購成功

不完整的第一版

精美首頁 → 選擇商品 → 按下購買

沒有確認庫存，也沒有可信的訂單結果

第二個系統雖然看起來比較漂亮，卻沒有完成使用者真正想做的事情。

這裡要記住一句話：

第一版可以很小，但必須對它承諾完成的事情負責。

## 三、開始做之前，先找出「最危險的假設」

很多專案失敗，不是因為工程師不會寫程式，而是因為一開始就把某些未經證實的想法當成事實。

例如，某公司打算開發 AI 客服系統。

主管可能認為：

「只要 AI 能理解客人的問題，就能減少客服人力。」

但是這句話其實包含好幾個尚未確認的假設。

| 假設            | 如果不成立，會發生什麼事？ |
| ------------- | ------------- |
| AI 能理解客戶問題    | 回答錯誤，甚至誤導客戶   |
| 客戶願意使用 AI     | 系統完成後沒人使用     |
| AI 能處理真正高頻的問題 | 無法有效減少人工工作量   |
| AI 能辨識無法回答的問題 | 亂回答，造成客訴      |
| 公司有權使用相關資料    | 可能涉及法規或資料治理問題 |

如果你花三個月打造漂亮的 AI 客服介面，最後才發現公司根本沒有整理好的客服知識，這三個月可能就沒有解決最關鍵的風險。

因此，應該先問：

「這個計畫裡面，哪一個假設如果錯了，其他工作可能全部白做？」

這類假設可稱為高風險假設（Riskiest Assumption）。

英國政府的 Government Digital Service 在 Alpha 階段的官方指南，也強調應先測試最具風險的假設，不必為了驗證想法，就先做出完整產品。

### 不同行業怎麼找高風險假設？

以下都是假設性的教學案例。

| 行業    | 最需要先確認的問題         | 第一個小實驗            |
| ----- | ----------------- | ----------------- |
| 餐飲    | 顧客是否願意付費？         | 少量販售一種餐點          |
| 金融    | AI 產出的報告是否符合必要規則？ | 使用合成資料產生一種報告，人工核對 |
| 醫療    | 使用者是否能正確操作？       | 使用虛構病人資料測試單一預約流程  |
| 製造    | 能否在缺料前可靠預警？       | 用歷史或模擬資料驗證一條產線    |
| 教育    | 新方法能否改善學習成果？      | 小規模前後測與對照評估       |
| 物流    | 新派車方式是否真的比較有效率？   | 比較特定區域的模擬路線       |
| AI 研究 | 新方法是否勝過既有基準？      | 先在固定資料集上做受控比較     |

注意：每個例子的 MVP 都不同，因為要驗證的核心問題不同。

而且 MVP 不一定要寫程式。如果用紙本流程、人工服務或可操作原型就能有效驗證假設，未必需要先開發完整系統。

## 四、如何決定哪些功能現在做、以後做、不做？

M03-04 教材提出三種範圍狀態（Scope States），這是本課最值得實際使用的方法。

第一版

現在就要完成，並提供驗收證據

延後

可能需要，但先滿足重新討論條件

本版不做

明確排除，不承諾提供這種能力

這三種分類不是必須依序推出的產品階段。「延後」也不代表已經承諾一定會做。

### 用一個醫院掛號系統來理解

假設你要設計一套教學用的診間預約系統，第一階段目的是驗證：

「行政人員能不能用系統完成一筆預約，並且避免重複預約？」

你可以這樣分類：

| 功能        | 決定   | 理由            |
| --------- | ---- | ------------- |
| 選擇日期與時段   | 第一版  | 預約必要流程        |
| 檢查是否有空位   | 第一版  | 不可發生重複占用      |
| 預約成功或失敗提示 | 第一版  | 使用者必須知道結果     |
| 取消與重新選時段  | 第一版  | 核心異常回復        |
| 跨院區預約     | 延後   | 要先確認不同院區的管理規則 |
| 整合正式病歷系統  | 延後   | 涉及整合、身分與個資治理  |
| 自動診斷疾病    | 本版不做 | 超出掛號系統的責任範圍   |

這不是說「跨院區預約」不重要，而是目前尚不需要透過它來驗證核心問題。

### 「延後」為什麼一定要寫啟動條件？

假設主管說：

「未來一定要支援十間醫院共同使用。」

如果只寫「第二版再做」，這句話其實沒有提供足夠資訊。

應該記錄：

> 跨院區預約：延後。當確認各院區的角色權限、預約規則、資料隔離及正式整合要求後，重新評估範圍、架構與驗收條件。

差別在於，前者是模糊的承諾；後者是一個有條件的決策。

這可以避免一個很常見的問題：

原本只是為了測試而做的小工具，卻在沒有重新設計的情況下，被逐漸當成正式營運系統。

## 五、MVP 可以省功能，但不能省必要的品質與安全

這一節特別重要。

想像一家食品工廠準備測試新型自動包裝機。

為了節省成本，第一版可以只包裝一種產品。

但是能不能因此取消安全防護裝置？

不行。

因為「只包裝一種產品」是在縮小範圍，而「取消必要安全防護」是在破壞系統成立的基本條件。

軟體也一樣。

在需求工程中，我們可以把這些不可任意犧牲的條件叫作必要約束（Constraints）或必須維持的系統不變條件（Invariants）。

例如 AASE 正式教材的合成收件案例：

使用者輸入三個必要欄位，系統檢查缺漏、提示修正，最後產出報告。

其中有兩項非常重要的約束：

約束一：必要欄位不完整時，不得產生標示為完整的報告。

約束二：使用者修改資料後，先前的檢查結果必須失效，不能直接使用舊結果匯出。

第二個尤其容易被忽略。

假設使用者原本輸入：

一次容易被忽略的錯誤

1\. 使用者輸入三個必要欄位

資料完整，通過檢查

2\. 使用者刪掉其中一個必要欄位

原本通過的檢查結果已不再適用

錯誤：系統仍允許用舊結果匯出

使用者看到成功訊息，實際報告卻不符合目前資料狀態

正確：要求重新檢查才能匯出

讓驗證結果與目前的輸入資料保持一致

這個問題跟 AI 模型有沒有接上、介面漂不漂亮，完全是兩回事。

即使是最簡單的程式，也應該遵守核心業務規則。

## 六、主管突然要求增加功能，應該怎麼辦？

在實務開發中，這種情況非常常見。

假設你與團隊原本規劃兩週內完成訂單系統的 MVP。

做到一半，主管說：

「既然可以輸入訂單，那順便加上 Excel 批次匯入吧！」

聽起來可能只是多一個按鈕，但實際上可能需要解決：

檔案格式錯誤、重複訂單、資料欄位對應、部分成功部分失敗、匯入後的確認、錯誤資料如何修正等問題。

這類新增要求可能造成範圍蔓延（Scope Creep），也就是專案的工作範圍逐漸擴大，卻沒有同步調整時間、資源或承諾。

### 一個簡單的變更決策框架

收到新功能要求

它是否為驗證核心問題所必需？

是

評估交換範圍或調整資源

更新規格、測試、時程與責任

否

列入延後或本版不做

記錄理由及重新討論條件

由範圍負責角色確認決定

保留變更紀錄，讓開發、規格與驗收一致

這裡有一項重要原則：

不可以為了增加新功能，就偷偷刪掉原本必要的測試、資料檢查或安全限制。

如果時間固定，新增工作就必須伴隨明確的取捨；如果工作都不能刪，就要重新討論時程或資源。

## 七、怎樣才能證明 MVP 真的做完？

「程式可以啟動」不代表「任務可以完成」。

「AI 說程式寫好了」也不代表「功能通過驗收」。

因此，我們需要驗收條件（Acceptance Criteria）。

它的意思是：

在什麼條件下，看到什麼結果，我們才願意承認這項工作已經完成？

可以用 Given–When–Then 的方式描述：

Given：已經處於什麼狀態。

When：使用者進行什麼操作。

Then：系統必須產生什麼結果。

以前面的報告系統為例：

| 測試情境         | 預期結果           |
| ------------ | -------------- |
| 必要欄位缺漏       | 顯示缺漏欄位，不允許完整匯出 |
| 使用者補齊欄位並重新檢查 | 檢查通過，可產生當次報告   |
| 通過檢查後再次修改輸入  | 舊檢查失效，要求重新檢查   |
| 使用者不理解錯誤提示   | 記錄操作困難，改善提示設計  |

前三項主要測試功能正確性。

第四項則涉及易用性（Usability），需要觀察實際使用者能否理解和完成工作。

兩者應分開保存證據，因為程式功能正確，不代表使用者一定會用。

### 還需要釐清四個常見名詞

| 名詞                         | 主要想回答的問題             |
| -------------------------- | -------------------- |
| PoC（Proof of Concept，概念驗證） | 技術上是否做得到？            |
| Prototype（原型）              | 這種設計或操作方式是否合理？       |
| MVP（最小可行產品）                | 用最小投入，能否驗證核心價值或重要假設？ |
| Pilot（試點）                  | 在有限、受控的真實環境中，能否有效運作？ |

這些類型可以重疊，不一定要依固定順序進行。例如，一個 MVP 也可能同時包含原型與 PoC 的實驗。

對醫療、金融、政府等高責任領域尤其要注意：使用合成資料完成 MVP，只能支持對應的原型結論；不能自動推論已能安全合法地處理真實資料。

## 八、把這些觀念轉成真正能執行的專案文件

這一課要留下的成果不是一大堆程式碼，而是一份可供團隊討論、交付給 AI Coding Agent、並用來驗收的範圍文件。

以下是可以參考的 `problem.md` 合成範例。

```

# 專案：設備巡檢異常回報原型

## 1. 核心問題

現場人員能否在巡檢後，正確記錄一項設備
異常，並知道該異常是否已成功提交？

## 2. 高風險假設

現場人員能理解異常分類，
且系統能保存完整的當次回報。

## 3. 第一版範圍

- 選擇一台測試設備
- 輸入異常類型及說明
- 檢查必要欄位
- 提示並修正缺漏
- 確認與提交模擬回報
- 顯示提交結果

## 4. 必要約束

- 缺少必要資訊不可成功提交
- 提交失敗不能顯示成功
- 修改資料後必須更新檢查結果
- 只使用模擬設備及合成資料

## 5. 延後功能

- 多廠區共用
  啟動條件：確認角色、權限與資料隔離

- AI 自動判斷故障
  啟動條件：取得適當驗證資料，
  定義誤判風險及人工覆核流程

## 6. 本版不做

- 正式維修派工
- 真實設備控制
- 自動停機指令

## 7. 完成證據

- 正常輸入可以成功提交
- 缺漏資料會被阻止
- 提交失敗有明確回應
- 修改資料後重新檢查
- 使用者能完成指定任務

## 8. 變更管理

任何新增功能都要記錄：
變更原因、影響範圍、取捨、
負責決策者與新增驗收條件。

```

這份文件的用途，是把原本模糊的「幫我開發一個設備巡檢系統」，變成有明確責任邊界、完成條件和可驗證結果的工作。

尤其在 AI 協作開發中，它能減少 AI 自行添加沒有被要求的功能，也能避免把 AI 產生的程式碼數量誤當成專案進度。

## 九、整堂課的核心知識地圖

1\. 定義問題（Problem）

我們究竟想解決什麼？

2\. 找出高風險假設（Assumption）

哪件事如果判斷錯誤，影響最大？

3\. 設計 MVP（Minimum Viable Product）

什麼是回答核心問題的最小完整流程？

4\. 確定範圍（Scope）

第一版、延後、本版不做；哪些約束不可破壞？

5\. 執行驗證（Validation）

用測試、觀察與可核對的資料取得證據

6\. 決定下一步（Decision）

繼續、調整、擴大，或停止

這個流程的關鍵不是「每次都要做出產品」，而是讓每一輪投入都能產生下一步決策所需要的知識。

它也銜接下一課 M03-05：有了最小範圍之後，我們就必須問，用什麼成功指標，證明這個最小產品確實帶來價值？

## 十、理解檢核：模擬一個真實專案決策

情境：一家物流公司想導入 AI 派車系統

公司原本由調度員每天手動安排貨車路線。主管希望你在三週內打造 AI 派車系統。

他提出五項要求：自動建議路線、即時 GPS 追蹤、司機手機 App、跨區域協作，以及異常訂單處理。

目前團隊尚未證明 AI 建議的路線能比人工排程更好，而且不能讓測試結果直接影響正式派車。

問題一｜你會把哪個假設定為最優先驗證的高風險假設？為什麼？

想一想：如果這項假設不成立，其他功能還有沒有開發價值？

問題二｜如果只能做最小完整流程，你會保留哪些步驟？哪些延後、哪些本版不做？

注意不能只是顯示地圖；還需要讓使用者完成任務。

問題三｜請提出兩項必要約束，以及三個可以客觀核對的驗收情境。

分別考慮正確結果、異常情況與正式營運邊界。

問題四｜第二週主管突然要求加入司機手機 App，你會如何處理？

思考工作量、取捨、決策責任與對原有驗證的影響。

提交回答並取得逐題解析&#x20;

這四題會一起檢驗你是否真正掌握 MVP 的核心：以問題決定範圍、以風險決定優先順序、以約束保障正確性，以及以證據判斷完成。
