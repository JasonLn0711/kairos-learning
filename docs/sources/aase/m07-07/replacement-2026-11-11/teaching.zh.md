## 一、這一章到底在教什麼？

核心觀念：程式出問題時，不要急著重寫，而是先搞清楚「什麼條件下出錯、為什麼出錯」，再用最小的修改解決，並證明沒有破壞其他功能。

想像你是一位汽車維修技師。 客人告訴你：「我的車怪怪的。」 你會直接把引擎拆掉重裝嗎？當然不會。 你會先詢問什麼時候發生、觀察是否可以重現，接著檢查電瓶、啟動馬達、供油或感測器，再根據證據修理。

軟體工程也是一樣。 尤其是 AI Coding Agent，當你告訴它「這個程式壞掉了，幫我修」，它可能同時修改十幾個檔案、重構程式架構，甚至順手更換套件。結果原本只有一個小問題，卻產生更多問題。

## 二、什麼叫「重現問題」？

假設你開發一套銀行徵信資料檢查系統。 使用者填寫三個欄位：客戶名稱、統一編號、文件種類。全部填妥後，系統顯示「檢查通過」，並允許下載報告。

但是使用者把「文件種類」刪掉之後，畫面居然仍然顯示「檢查通過」，還可以下載之前的報告。 這就是本章教材所使用的「舊報告沒有失效」問題。

@figure2

這個例子真正的問題不是「下載按鈕顏色不對」，而是： 系統把舊資料的檢查結果，錯誤地當成目前資料的檢查結果。

這叫做 Stale State（過期狀態），也可以理解為「舊狀態沒有正確失效」。 即使目前程式執行完全沒有當機，系統仍然可能提供錯誤結果。這類錯誤比單純的程式當機更容易被忽視。

## 三、除錯第一件事：確認是哪一種錯誤

程式壞掉，不代表一定是程式邏輯有問題。 本章特別強調分辨三種不同層次的故障：

| 錯誤類型                        | 白話解釋             | 可能的處理          |
| --------------------------- | ---------------- | -------------- |
| Environment Error（環境錯誤）     | 工具、套件或執行環境沒準備好   | 檢查安裝、版本、路徑     |
| Test Error（測試設定錯誤）          | 測試本身無法正確執行       | 檢查測試設定、匯入、測試資料 |
| Functional Regression（功能回歸） | 原本應該正常的功能，修改後壞掉了 | 重現功能錯誤並找到根因    |

例如你在測試 Python 專案時：

### 情境 A：測試套件不存在

`No module named pytest`

這通常是執行環境問題，不能據此判斷表單功能壞掉。

### 情境 B：測試找不到程式

`ModuleNotFoundError: No module named 'app'`

先檢查專案結構、執行目錄、Python 匯入路徑等因素。

### 情境 C：測試成功執行，但斷言失敗

`AssertionError: stale report still visible`

這時才有直接證據顯示預期行為與實際行為不一致，應追查功能邏輯，同時核對斷言是否正確表達需求。

最重要的區別是：測試執行失敗，不等於測試成功發現功能錯誤。

## 四、怎麼把模糊問題變成可修復問題？

專業工程師會使用 Minimal Reproducible Example（最小可重現案例）。 意思是：找出最少需要哪些條件與操作，才能穩定讓錯誤再次發生。

以本章的舊報告問題為例：

| 階段         | 要做什麼              |
| ---------- | ----------------- |
| Given（前提）  | 三個欄位都已填寫，並完成資料檢查  |
| When（動作）   | 使用者把文件種類清空        |
| Then（預期）   | 舊檢查結果應失效，不可匯出完整報告 |
| Actual（實際） | 畫面仍顯示成功，舊下載功能還存在  |

這四列比「下載怪怪的」更有價值。 因為現在你知道了故障的起點、觸發動作、正確行為和錯誤行為，也能交給另一位工程師或 AI Agent 重演。

### 為什麼要讓測試先失敗？

這個觀念叫 Regression Test（回歸測試）：建立一個測試，避免已修好的問題將來再出現。

以本章的 Python 專案為例，可以先執行：

```
python -m pytest -q tests/test_app.py
```

這會執行指定的介面測試檔案；`-q` 是簡潔輸出模式。`pytest` 的官方文件也支援使用 `python -m pytest` 執行測試。

另一個容易忽略的陷阱：如果你故意把程式弄壞，測試卻還是綠燈，代表測試可能根本沒有涵蓋這個錯誤。不能把「測試通過」誤認成「功能一定正確」。

Streamlit 的 `AppTest` 可以模擬應用程式、修改輸入值並檢查畫面結果，適合本章的這類介面測試。修改 widget 值後，需明確呼叫 `run()` 重新執行，再檢查結果。

## 五、找到原因後，怎麼修才安全？

以舊報告為例，根本問題是「目前輸入」與「過去已驗證的輸入」沒有正確區分。 可以使用三道防護：

1. 輸入變更時讓舊結果失效： 使用者修改欄位後，舊報告不再視為有效。
2. 顯示前確認資料一致： 畫面呈現成功訊息或下載按鈕之前，確認目前輸入與已檢查的資料相符。
3. 匯出時再次驗證： 即使畫面出了問題，後端仍不能讓無效資料通過匯出檢查。

下面是簡化的 Python 邏輯示範，不是教材原始碼：

```python
def valid(form):
    required = ("name", "tax_id", "doc_type")
    return all(str(form.get(k, "")).strip() for k in required)


def check(form):
    if not valid(form):
        return None
    return {"snapshot": form.copy()}


def can_export(form, result):
    return (
        result is not None
        and form == result["snapshot"]
        and valid(form)
    )


def test_changed_input_cannot_export():
    form = {
        "name": "甲公司",
        "tax_id": "12345678",
        "doc_type": "財務報表",
    }
    result = check(form)
    assert can_export(form, result)
    form["doc_type"] = ""
    assert not can_export(form, result)
```

這段程式的重要設計是 `snapshot`（快照）。 你可以把快照想成：「這張報告當初究竟根據哪一份資料做出來？」 如果使用者改了輸入，那就不能繼續拿以前的結果當作最新結果。

此處 `form.copy()` 適用於這個僅有字串的簡化範例；若資料有巢狀結構，需要適當的深層複製、不可變資料或版本識別機制。實務上還要驗證真正的業務規則，而非只檢查欄位有沒有值。

## 六、跨產業案例：同一個原理可以用在哪裡？

以下五個假設案例，用來比較輸入變更與結果失效的關係。

| 產業   | 錯誤情境                   | 正確的設計                    |
| ---- | ---------------------- | ------------------------ |
| 醫療   | 醫師修改處方劑量後，列印的仍是舊處方     | 處方內容變更後，舊確認狀態失效，簽署前重新核對  |
| 電商   | 客戶修改數量後，付款仍使用舊金額       | 結帳前重新計算，並核對目前購物車版本       |
| 物流   | 地址修改後，系統仍下載舊地址標籤       | 標籤與目前訂單版本綁定，異動後重產        |
| 教育   | 教師修改成績後，成績單仍顯示舊分數      | 成績版本變更後重新計算及匯出           |
| 科學研究 | 研究人員換了資料集，圖表卻仍沿用上一版的分析 | 結果記錄資料版本、參數及運算版本，變更時重新計算 |

這些都是假設案例，但背後有相同的系統設計原理： 只要結果依賴某份輸入，輸入改變時，就必須重新判斷結果是否仍然有效。

這也與 Cache Invalidation（快取失效）、資料一致性（Data Consistency）及版本控制有密切關係。

## 七、復原（Recovery）不是把所有修改全部刪掉

假設 AI Agent 修改了 `app.py`，造成下載錯誤。 可是另一位工程師也在同一個檔案裡改善了鍵盤操作。 如果你直接把整份檔案恢復成昨天的版本，就會連其他人的改善一起刪掉。

所以復原要看「變更範圍」，而不只是檔名。 可以先觀察：

```
git status --short
git diff -- app.py
```

確認哪些部分改變。如果已備份現況，且 `HEAD` 確實是要參考的版本，可以視情況使用：

```
git restore -p --source=HEAD -- app.py
```

其中 `-p` 是互動式選擇修改區塊，讓你逐段確認是否回復，而不是不加區分地覆蓋整份檔案。但被選中的區塊仍可能丟失未保存修改，且跨區塊變更不一定能安全拆分，務必先備份與審查。

本章不鼓勵把 `git reset --hard` 或全專案 `git restore .` 當成萬用修復方法，因為它們可能破壞無關工作。

## 九、本章實作的真正驗收標準

依照原教材，你應在自己的練習副本中，刻意製造舊報告未失效的錯誤，讓測試抓到它，再修回正常狀態。這是受控的合成故障練習，不代表教師提供的參考程式本來就有這個 Bug。

最後需要留下 `debugging-notes.md`，其中應包括故障條件、重現步驟、失敗證據、根本原因、修正內容、測試結果，以及尚未驗證的範圍。

這些紀錄讓下一位工程師、下一個 AI Agent，甚至幾個月後的你，都能知道當初發生什麼事，以及為何採取這個修正方式。

問題 3： AI Agent 的修正與同事的新功能混在同一檔案，你發現 Agent 的修改有問題，應如何處理？

A. 直接恢復整個專案到上個版本
