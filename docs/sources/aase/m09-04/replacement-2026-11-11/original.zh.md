# M09-04｜技術變動與不變的工程責任：白話教學

這一課最重要的觀念，可以濃縮成一句話：

工具可以一直換，但你對成果的品質、安全與正確性所負的責任，不會因為換了工具而消失。

例如，你今天使用 ChatGPT 寫程式，明天改用 Claude Code，後天換成其他 AI Coding Agent。工具可能越來越厲害，但你仍然要確認：程式有沒有做對、資料有沒有外洩、權限有沒有失控，以及發生問題時能不能恢復。

這正是 [M09-04 原始教材](https://learn.cs-kairos.com/courses/aase/v1/m09/concepts/m09-04/?utm_source=chatgpt.com) 要教的核心。

## 一、先用生活例子理解

假設你是一家餐廳的老闆。

原本廚房使用傳統瓦斯爐，後來改用最新的智慧電磁爐。

新設備可能更快、更省能源，也能自動控制溫度。

但有三件事不能因此改變：

- 顧客點的餐仍然要正確。
- 食物仍然必須符合衛生與安全要求。
- 如果新設備壞掉，餐廳仍然需要有辦法處理訂單。

所以：

換設備 ≠ 重新定義什麼叫做一間好的餐廳。

軟體工程也是同樣的道理。

今天換了程式語言、AI 模型、開發框架或雲端平台，不代表以前確認過的使用者需求、資料安全與驗收標準，就能全部重新來過。

## 二、哪些東西可以變？哪些東西要保留？

右邊的內容也可能因新需求而調整，但必須經過明確決策、更新規格並重新驗證，不能讓工具自行決定。

例如醫院原本規定只有授權醫師可以查看特定病歷。

某天醫院更換了新的 AI 醫療系統。

即使新系統非常先進，也不能因為新工具操作方便，就允許所有員工查看病歷。

工具的能力與系統的授權，是兩回事。

## 三、不同的技術變動，需要不同的檢查

這是本課最有實務價值的地方。

工程師不能把所有的工具更新，都視為同一種事情。

| 變動類型               | 白話例子               | 特別要重新確認                   |
| ------------------ | ------------------ | ------------------------- |
| 更換 AI Coding Agent | 從工具 A 換成工具 B 幫忙寫程式 | AI 能碰哪些檔案、執行哪些命令、修改是否符合規格 |
| 更換 UI 框架           | 網站介面從 Vue 改為 React | 按鈕、輸入、畫面狀態、下載、鍵盤操作、部署     |
| 單人系統變多人系統          | 個人記帳工具改成公司多人共用     | 登入身分、不同人的資料隔離、授權、稽核紀錄     |

### 例子 A：更換 AI Coding Agent

假設你用 AI 開發銀行貸款試算系統。

原本的工具 A 能正確計算每月還款金額。現在你想改用工具 B。

不應只問：「工具 B 寫程式是不是更快？」

還需要問：

工具 B 是否讀取了正確需求？會不會修改不應修改的核心公式？能不能保留程式碼變更紀錄（Diff）？會不會偷偷呼叫外部服務，傳出敏感資料？

這代表換 AI 開發工具，重點是檢查開發流程、工具權限與實際產出的修改。

如果只是換了工具，但根本沒有重新執行程式，也不能宣稱「新工具已經通過驗收」。

### 例子 B：更換前端 UI 框架

假設你有一個學校成績查詢網站。

原本用 Vue 開發，現在改用 React。

計算學期平均成績的公式沒有改，但網站仍可能發生這些問題：

- 學生按下查詢卻沒有反應。
- 成績畫面顯示了上一位學生的資料。
- 匯出 PDF 的按鈕失效。
- 手機上的畫面無法正常操作。

因此，即使平均分數的單元測試全部通過，也不能代表網站遷移成功。

這牽涉到一個重要名詞：

回歸測試（Regression Testing），就是確認「以前正常的功能，經過修改後還是正常」。

更換 UI 框架，就要重新測試受影響的 UI 行為，而不只是原來的計算公式。

### 例子 C：從單人系統變成多人系統

假設你原本寫了一個個人記帳工具，只有自己使用。

現在你想提供給一百家企業使用。

原本的程式即使功能完全正確，也不能直接拿去上線。

因為你現在需要處理新的問題：

甲公司的員工是否能看到乙公司的帳本？公司主管能否查看員工私人資料？離職員工的權限何時撤銷？資料操作是否留下稽核紀錄？

這不是單純增加登入頁面。

它代表系統的身分管理、授權模型與資料治理都發生了改變。

## 四、真正的遷移流程：不要先換工具，先定義成功

我們可以用一個通用流程，處理任何產業的技術替換。

1

說清楚為什麼要換

改善速度、成本、品質或安全

2

確認哪些行為不能變

需求、業務規則、資料及權限

3

分析影響範圍

程式、介面、資料、環境、操作

4

設定測試與通過標準

正常案例、錯誤案例、權限檢查

5

小範圍遷移並實測

保留紀錄，比較新舊差異

6

決定接受或復原

驗收通過才擴大，失敗就停止

特別注意兩個概念。

驗收條件（Acceptance Criteria）：你要先講清楚，什麼情況才算成功，而不是做完才決定標準。

例如一個新的客服 AI，至少必須能完成指定的客戶任務、正確處理不知道的問題，且不得洩漏其他客戶資料。可以進一步設定正確率、延遲及成本門檻。

復原（Rollback）：如果新版本失敗，能不能安全退回上一個可用版本？

例如新電商系統上線後，突然不能付款，就應當依事先規劃切回穩定版本，而不是讓顧客持續碰到故障。

但要注意，若資料庫結構或資料內容已改變，單靠 Git 還原程式碼可能不夠，還需要資料相容性與復原方案。

## 五、AI 再強，人類為什麼仍要負責？

假設一家保險公司使用 AI Agent，自動分析理賠申請。

AI 告訴你：「這一筆理賠不符合規定，建議拒絕。」

但是問題來了：

這個規定是誰定義的？AI 是否使用正確版本的條款？如果判錯，誰能修改決策？誰負責處理客戶申訴？

所以工程責任至少包括：

業務負責人決定規則與可接受結果；技術負責人確保系統按照規格實作；資料與安全負責人確認存取及風險控制；驗收負責人根據測試證據決定是否接受。

一個人可以兼任數個角色，但責任不能消失。

教材提到的 NIST AI Risk Management Framework（AI RMF），就是協助組織辨識、評估、治理與管理 AI 風險的框架。採用它不等於取得資安認證，也不代表所有控制措施都已真正落實。

## 六、實際練習：幫一家公司制定工具遷移計畫

假設一家零售公司要把原本的客服聊天機器人，從 AI 模型 A 改成模型 B，原因是希望降低成本。

我們可以先寫出這份簡短的遷移計畫。

| 項目      | 遷移計畫內容                    |
| ------- | ------------------------- |
| 變更目的    | 降低每次客服對話成本                |
| 不變的需求   | 能查詢訂單、解釋退貨政策、必要時轉真人       |
| 不變的安全規則 | 不得取得其他客戶的訂單資料             |
| 正常案例    | 顧客能查到自己已授權的訂單             |
| 負向案例    | 顧客提供別人的訂單編號，AI 不應洩漏資訊     |
| 驗收標準    | 核心任務達既定品質門檻、安全測試通過、成本確有改善 |
| 停止條件    | 出現跨客戶資料洩漏、重大錯誤或核心功能失效     |
| 復原方式    | 保留原模型、設定和路由，必要時切回         |
| 目前狀態    | 計畫已完成，尚未執行測試              |

最後一列尤其重要。

寫好計畫，不代表已經成功更換模型。跑過幾次測試，也不代表已完成正式驗收。

成熟的工程實務必須區分：

計畫完成 → 實作完成 → 測試通過 → 驗收完成 → 正式交付

每個階段都應有相對應的證據。

## 七、這一課與整個軟體工程的關係

你可以把整個 AASE 系列理解成一條完整的責任鏈：

問題與需求：到底要解決什麼？

設計與規格：應該怎麼運作？

系統實作：用什麼技術做出來？

測試驗收：如何證明真的能用？

交付與改善：如何持續可靠地運作？

其中技術實作那一層可以經常替換，但替換時必須檢查對其他層的影響。

因此，長期真正值得累積的能力，不只是熟悉某個模型或框架，而是能夠定義問題、制定規格、評估技術變更、驗證結果、控制風險，並交付能持續維護的系統。

## 八、理解檢核

假設你接手了一家診所的預約系統。原本使用單一 AI Agent 與傳統網站，現在公司希望改成多個 Agent 協作，並重新製作前端介面。

請思考以下三個問題：

1\. 這次更換技術時，你認為哪一種做法最合理？

A. 新模型比較強，直接替換即可

B. 保留既有需求與權限契約，先分析影響再遷移

C. 把所有規格清空，讓 AI 重新決定

2\. 如果舊版預約規則測試全部通過，是否代表新版 UI 已驗收完成？

A. 是，核心規則沒壞就夠了

B. 否，仍需測試操作流程、畫面狀態與部署等變更

C. 是，只要使用知名 UI 框架就可以

3\. 如果新的 AI Agent 自行決定擴大病歷存取權限，應該怎麼處理？

A. 接受，因為 AI 是為了完成任務

B. 只要運作正常就不必記錄

C. 停止未授權變更，由負責人確認權限與規格

提交答案並請你批改

這一課最終希望你建立的判斷習慣是：不要只問「新技術能做什麼」，還要問「替換後，原本承諾的事情，如何證明仍然做得到」。
