# Prompt 與 Spec 的不同責任

Prompt 告訴 AI 這次要做什麼；Spec 定義系統必須符合的行為、限制與驗收條件。兩者可以互相引用，差別在責任，不在字數或檔名。

## 一、先用蓋房子理解 Prompt 與 Spec

假設你打算蓋一棟房子，找來一位工地主任。

你對工地主任說：

> 今天先把浴室做好，請先安裝馬桶、洗手台，完成後拍照給我。暫時不要動廚房。

這就很像 Prompt（工作指令）。

但如果你說：

> 浴室地板必須有適當排水坡度、防水工程必須符合約定標準、排水測試不得漏水，電路必須符合適用安全規範。

這就很像 Spec（Specification，規格）。

Prompt：交辦工作

今天做什麼、誰來做、允許改哪裡、完成後如何回報。

Spec：定義標準

成品必須具備哪些特性、遵守哪些限制、如何檢查是否合格。

請用換人的情境檢查兩者的差別：

假設明天換了一位工地主任，今天的施工指令可能全部改變，但浴室不能漏水這個要求，會不會跟著改變？

當然不會。

這就是為什麼軟體工程需要獨立的規格：讓系統的正確性，不依賴某次聊天、某個 AI 模型或某一位工程師。

## 二、Prompt 與 Spec 到底差在哪裡？

| 比較項目 | Prompt（指令）             | Spec（規格）        |
| ---- | ---------------------- | --------------- |
| 核心問題 | 這次要 AI 做什麼？            | 系統必須符合什麼要求？     |
| 主要對象 | AI、Coding Agent、執行任務的人 | 開發者、測試者、使用者、驗收者 |
| 內容   | 工作範圍、順序、工具、回報方式        | 功能、限制、例外、驗收條件   |
| 有效期間 | 通常針對一次任務               | 持續有效，直到正式修訂     |
| 如何確認 | 檢查任務執行與回報              | 檢查實際系統行為與測試證據   |

特別注意：不是寫得很長就叫 Spec，也不是存在 `spec.md` 裡就一定是合格規格。

例如：

「請 AI 做一套非常好用、安全又快速的系統。」

這是一段模糊指令。即使將它寫進 `spec.md`，仍然無法讓不同的人客觀判斷什麼叫「非常好用」。

## 三、用不同產業的例子理解

假設我們利用 AI 開發三種系統。

| 產業   | Prompt：本次工作        | Spec：系統必須做到                  |
| ---- | ------------------ | ---------------------------- |
| 醫療院所 | 幫我開發病患預約頁面，先處理日期選擇 | 不允許預約已被占用的時段，失敗時必須清楚告知       |
| 電子商務 | 修改結帳頁面的運費計算功能      | 系統必須按照已核定的運費規則計算，並在付款前顯示最終金額 |
| 製造業  | 建立工廠品質檢驗表單         | 超出已定義允收範圍的測量值，不能標記為合格        |

發現共同點了嗎？

Prompt 通常隨著開發進度而改變。今天處理表單，明天處理資料庫，後天修改測試。

但只要業務需求沒有變，Spec 的承諾就應該持續成立。

## 四、從模糊要求到可以真正驗收的 Spec

假設現在有一家物流公司，希望 AI 開發收件資料檢查系統。

老闆說：

「我要一套好用的系統，幫我檢查客戶的收件資料，不要出錯。」

這是一個合理的願望，但工程師會遇到很多問題：

- 哪些欄位一定要填？
- 沒填完整，系統應該警告還是直接拒絕送出？
- 使用者修正資料後，要不要重新檢查？
- 所謂的「完成」，代表資料格式完整，還是代表收件地址真的存在？

如果沒有定義，AI 就可能自行做出各種假設。

### 用五個問題寫出一條規格

| 必須確認           | 白話意思     | 收件系統例子     |
| -------------- | -------- | ---------- |
| 輸入（Input）      | 系統接收什麼？  | 收件人、電話、地址  |
| 條件（Condition）  | 什麼情況下適用？ | 任一必要欄位空白   |
| 結果（Output）     | 系統應該怎麼做？ | 顯示缺漏欄位     |
| 限制（Constraint） | 不能發生什麼事？ | 不能將資料標記為完整 |
| 驗收（Acceptance） | 怎麼證明有做到？ | 實際輸入空白資料檢查 |

整理後可以寫成以下的 `spec.md`：

```

# 收件資料檢核規格（教學範例）

## R-01：必要欄位
收件人、電話、地址均為必填欄位。

## R-02：缺漏處理
如果任一必要欄位為空白，或去除
首尾空白後沒有內容：
- 顯示對應欄位錯誤
- 禁止標記為資料完整

## R-03：資料修改
使用者修改已檢查資料後，
先前的完成狀態必須失效，
並要求重新檢查。

## R-04：業務界線
通過檢核只代表必要欄位完整，
不代表電話有效、地址存在，
也不代表正式受理。

## 驗收情境
T-01：三個欄位都有值時，可通過完整性檢核。
T-02：地址空白時，顯示錯誤且不得標記完整。
T-03：地址只含空白字元時，比照缺漏處理。
T-04：修改已檢核資料後，舊完成狀態失效。

```

這份規格還可以繼續擴充，例如電話格式、地址驗證和資料保留政策。但在這個教學階段，我們先把「欄位完整性」定義清楚。

規格最重要的是可驗證（Verifiable）：工程師、測試者和使用者，應該可以根據相同輸入，判斷實際結果是否符合要求。

這也是 NASA 需求工程文件強調的重要原則：需求應該明確、無歧義、可追溯，並有可驗證的方法。

## 五、有了 Spec，還需要 Prompt 嗎？

需要，因為 Spec 不會自動安排 AI 工作。

假設規格已經確定，現在我們要交代 Coding Agent 實作。

可以這樣寫：

### Agent 工作指令範例

請先閱讀專案中的 `spec.md`，確認 R-01 至 R-04 的要求。

本次任務只實作必要欄位檢核與測試，不處理登入、資料庫或介面重新設計。

請先列出預計修改的檔案及影響範圍，再進行實作。

完成後執行 T-01 至 T-04 對應測試，提供 Diff、實際測試結果及尚未驗證的項目。

如果規格有矛盾、需要新增依賴，或必須修改未授權的資料邊界，請停止相關修改並列出待確認事項。

這裡面出現了幾個重要術語。

Coding Agent：能夠利用工具讀取程式碼、修改檔案、執行命令及測試的 AI 協作系統。

Diff：程式碼的變更差異。讓你知道 AI 究竟新增、刪除或修改了哪些內容。

停止條件（Stop Condition）：預先規定 AI 遇到哪些情況不能繼續自行決定，例如規格矛盾、權限不足或需修改敏感資料處理方式。

尤其是最後這點，很重要。

我們不是希望 AI 遇到所有問題都自行猜測答案，而是希望它能辨識哪些事情必須交由人類決策。

## 六、把整個軟體開發流程串起來

Problem：問題陳述

我們到底要解決什麼問題？

Spec：系統規格

系統應該做到什麼？什麼不能做？

Prompt：工作交辦

這次交給 AI 做哪一部分？有哪些權限和限制？

Implementation：實作

AI 或工程師實際撰寫、修改程式

Verification：驗證

用規格與測試證據確認結果是否合格

發現問題時，回到適當階段修訂、重新實作與測試

這是方便初學者理解的流程圖，實際工程並非只能依序進行。開發、規格澄清與測試可以反覆進行。

這裡也連結到 BDD（Behavior-Driven Development，行為驅動開發）。

BDD 強調不同角色透過具體情境建立共同理解，再把情境轉化為可檢查的系統行為。

例如：

- Given（假設）：使用者已填寫收件人與電話，但沒有地址。
- When（當）：使用者要求完成資料檢核。
- Then（則）：系統顯示地址缺漏，且不能標記為完整。

這個情境之後可以對應成自動化測試。

## 七、三個常見錯誤

錯誤一：以為 Prompt 越長，系統就越可靠。

一萬字的指令如果含有互相矛盾的規則，仍然無法保證正確。

錯誤二：把 AI 說「完成了」當成真正驗收。

AI 宣稱已完成，只是工作回報。還需要檢查程式變更、實際測試結果，以及沒有執行的測試。

錯誤三：把 Spec 當成永遠不能修改的法律。

規格可能不完整，也可能寫錯。當業務需求改變時，應由有權決策的人確認，修訂規格、記錄理由，再同步調整測試。若 Prompt 和 Spec 互相矛盾，不應直接採用最後一句話，也不應讓 AI 擅自挑選。

## 八、這一章真正要帶走的觀念

不要把 AI 對話當成軟體系統唯一的需求來源。

對個人小工具而言，直接下 Prompt 可能足夠。但當系統必須能夠交接、由多人維護、持續修改，甚至面對稽核時，就需要讓「要求、執行、證據」各自有清楚的紀錄。

最實用的做法，是先把一條模糊要求改寫成可觀察、可測試的規格承諾，再寫一段引用這份規格的 Agent 工作指令。

## 九、理解檢核

請先作答，再展開參考答案核對理由。

第一題：辨識 Prompt 與 Spec

下列哪句話屬於系統規格？

A. 系統發現訂單金額異常時，必須阻止付款並顯示原因

B. 請 AI 先修改付款模組，再執行測試

C. 請完成後回報程式碼差異

第二題：規格與指令矛盾

`spec.md` 寫著「缺漏地址不得完成訂單」，但新 Prompt 要求「先跳過地址檢查」。應該怎麼處理？

A. 直接按照最新 Prompt 修改

B. 先確認規則變更的決策權與理由，必要時正式修訂規格和測試

C. 讓 AI 自己決定比較容易的做法
