# AASE M05-02｜User Story、功能需求與非功能需求：從「我想要什麼」到「怎樣才算做對」

已找到正確教材：[M05-02｜User Story、功能與非功能需求](https://learn.cs-kairos.com/courses/aase/v1/m05/concepts/m05-02/?utm_source=chatgpt.com)。

這一章是「規格驅動軟體開發」（Specification-Driven Development, SDD）的重要基礎。

今天最重要的一句話：使用者告訴你他想解決什麼問題，不代表你已經知道軟體應該怎麼做，更不代表你知道怎樣才算完成。

這就是為什麼軟體工程需要區分四件事：

- User Story（使用者故事）： 誰需要這個東西？他想完成什麼？為什麼？
- Functional Requirements（功能需求，FR）： 系統具體要做哪些事情？
- Non-Functional Requirements（非功能需求，NFR）： 系統做這些事情時，應該具備什麼品質？
- Constraints（約束條件）： 開發與使用過程中，有哪些限制不能違反？

## 一、先從餐廳點餐理解這四件事

假設你準備開一家餐廳，想委託廚師幫你設計午餐。

你對廚師說：

「我希望上班族中午可以吃到一份健康、方便、快速的午餐。」

這個需求有錯嗎？

沒有。可是廚師會遇到很多問題：

要提供哪些餐點？什麼叫健康？多快才算快速？客人有沒有食物過敏？價格有沒有限制？

因此，我們必須逐步把模糊的想法轉成可以執行的要求。

User Story｜我為什麼需要它？

上班族希望午休能快速吃到合適的餐點，以便準時回去工作

FR｜要做什麼？

提供點餐、客製化、付款與訂單查詢

NFR｜做得如何？

流程易懂、回應穩定、操作方便

Constraints｜有哪些限制？

遵守已確認的食材限制、預算及設備條件

Acceptance Criteria｜如何確認有做到？

指定情境下能正確點餐、處理過敏限制、完成付款與查詢；品質指標也經過測試

這個流程的關鍵不在文件名稱，而在於逐步減少歧義，讓不同人可以對「完成」有相同理解。

餐廳廚師、軟體工程師、AI Coding Agent，面對模糊需求時都會有同樣的困難：如果沒有明確要求，就只能自己猜。

## 二、User Story：先說清楚使用者的真正目的

User Story 常見的表達方式是：

> 身為某種使用者（As a），我希望能夠完成某件事（I want），以便獲得某種價值（So that）。

我們從不同產業來看：

| 產業 | User Story 範例                   |
| -- | ------------------------------- |
| 醫療 | 身為護理師，我希望給藥前能查看病人的過敏紀錄，以降低用藥風險。 |
| 電商 | 身為消費者，我希望結帳前知道運費，以便決定是否購買。      |
| 教育 | 身為學生，我希望看到自己常答錯的觀念，以便安排複習。      |
| 金融 | 身為徵信人員，我希望快速找出報告缺少的資料，以便完成審核準備。 |
| 製造 | 身為產線主管，我希望及時知道設備異常，以便安排檢查，減少停機。 |

仔細看，這些故事都沒有先指定 Python、React、資料庫或 AI 模型。

為什麼？

因為 User Story 首先回答的是使用者價值（User Value），而不是工程師要使用哪個工具。

例如，「學生希望知道自己的弱點」可以透過錯題列表、能力圖、推薦複習清單等方式實現，不一定需要 AI。

### 最常見的錯誤

「身為使用者，我希望畫面有一個藍色按鈕，以便按下它。」

這句話雖然套用了 Story 句型，但沒有真正說明使用者的工作目的。

更好的寫法是：

「身為收件人員，我希望提交資料前能檢查必要欄位，以免將不完整的資料交給下一個處理者。」

至於是否用藍色按鈕來實現，通常是後續設計問題。

還要注意：User Story 是溝通和需求探索的起點，不是完整規格，也不需要把所有需求都硬塞進固定句型。

## 三、功能需求（FR）：系統到底要做什麼？

假設你準備開發一個醫院掛號系統。

你收到的 User Story 是：

「身為病人，我希望能在線上掛號，以便不必親自到醫院排隊。」

這段話有說明價值，但沒有告訴工程師完整的工作規則。

功能需求就是將它進一步拆解，例如：

| 編號    | 功能需求           | 如何確認          |
| ----- | -------------- | ------------- |
| FR-01 | 病人可以查詢可預約門診    | 指定日期後顯示可預約診次  |
| FR-02 | 病人可以預約仍有名額的診次  | 預約成功後產生預約紀錄   |
| FR-03 | 病人可以取消自己的預約    | 取消後狀態正確更新     |
| FR-04 | 額滿的診次不得再接受一般預約 | 模擬額滿後確認無法超額預約 |

這裡有一個非常重要的觀念：

功能需求不只描述「系統應該允許什麼」，也要描述「系統應該拒絕什麼」。

例如，醫院剩下一個掛號名額，卻有兩個病人同時按下預約。

系統不能因為兩個人都看到還有名額，就同時接受兩筆預約，除非院方明確允許超額掛號。

因此，規格還要回答同時操作、資料更新、錯誤處理等問題。

這也是為什麼只讓 AI「做出線上掛號功能」遠遠不夠。

## 四、非功能需求（NFR）：功能能用，不代表系統好用

想像有兩家銀行提供相同的網路轉帳功能。

### 銀行 A

功能存在，但品質欠佳

轉帳常需要等待很久，偶爾當機，錯誤訊息不清楚。

### 銀行 B

功能與品質都經過設計

回應時間可預期，失敗時狀態清楚，能避免重複扣款。

兩家銀行都能提供轉帳，但使用體驗與風險不同。

這就是非功能需求的重要性。

常見品質面向包括：

| 品質面向                 | 白話意思        | 實際例子               |
| -------------------- | ----------- | ------------------ |
| Performance 效能       | 做事要多快       | 查詢大量資料時，回應時間在約定門檻內 |
| Reliability 可靠性      | 能否持續正確運作    | 服務中斷後，交易狀態仍正確      |
| Accessibility 可近用性   | 不同能力的人能否操作  | 不使用滑鼠也能完成主要工作      |
| Usability 易用性        | 操作是否容易理解    | 使用者清楚知道怎麼修正錯誤      |
| Maintainability 可維護性 | 未來能否容易修改    | 新增欄位不必大幅修改其他功能     |
| Security 安全性         | 能否防止不當存取與操作 | 未授權者無法讀取他人紀錄       |

### 為什麼「系統要很快」不是好的需求？

假設你委託工程師製作購物網站。

你說：「這個網站一定要很快。」

工程師回覆：「完成了，我覺得很快。」

你怎麼證明他有沒有達成？

沒有辦法。因為你們對「快」沒有共同定義。

我們可以採用以下方式將要求具體化：

模糊需求

「商品搜尋要很快。」

可驗證需求的寫法（示範數值，尚非正式門檻）

「在指定測試設備、固定資料集與 50 位模擬同時使用者的條件下，從伺服器收到搜尋請求到回傳完整結果，95% 的請求應在 2 秒內完成。」

這裡的 95% 通常可以用 p95 latency（第 95 百分位延遲）表達。

但為什麼要用 50 人、2 秒？

這些數字必須經過使用情境、負載測試、成本與利害關係人確認，不能隨便填入，就當作正式需求。

如果還沒有證據，正確做法是留下待確認事項（TBR，To Be Resolved），明確指定誰來確認、何時確認，以及要蒐集哪些量測資料。

NASA 的需求工程指引強調需求必須清楚、一致、可追溯、可驗證，並避免單獨使用「快速、容易、安全」這類無法直接檢驗的形容詞。

## 五、Constraints：有哪些不能跨越的界線？

約束條件不一定是系統功能，也不完全等同品質。

例如你正在做一套學校的學生資料分析系統。

校方可能要求：

「第一階段只能用去識別化測試資料，不准連正式學生資料庫。」

這代表即使你做出非常好的資料分析功能，只要直接連到正式資料庫，就違反了這一階段的要求。

其他例子包括必須在離線環境執行、只能使用指定硬體、預算不得超過核准額度，或不得把特定資料傳送給外部服務。

要特別注意，FR、NFR、Constraints 並不是完全互斥的三個盒子。

例如「只有經授權的醫師才能查看指定病歷」，可以拆成具體的存取控制功能、授權判斷規則、稽核要求與資料治理約束。

分類只是幫助團隊討論；真正重要的是每個條件都能夠被理解、實作與驗證。

## 六、最重要的實作：把四種需求整合成一份規格

現在回到教材的合成收件資料案例。

假設你要開發一套收件系統，收件人員會收到包含姓名、案件編號與聯絡方式的測試資料。

我們從最初的 User Story 一步步寫到可以驗收的規格。

S-01

User Story

身為收件人員，我希望在匯出前知道哪些必要欄位沒有填寫，以便補齊後再交接。

FR-01

檢查缺漏

必要欄位不存在、為空字串或只有空白字元時，系統應將它列為缺漏。

FR-02

防止錯誤匯出

未通過完整性檢查時，不得產生標示為「完整」的匯出報告。

NFR-01

鍵盤可操作性

使用者應能只用鍵盤完成填寫、檢查、修正與匯出；操作焦點必須可辨識，且不應陷入無法離開的操作區域。

C-01

資料與使用範圍

本次原型只處理合成資料，採單人本機操作，不連接真實收件系統，也不宣稱具有正式業務受理能力。

這裡對應的 W3C WCAG 2.2 鍵盤操作原則，要求一般功能可以透過鍵盤介面操作；但只寫下這條規格，不代表產品已通過可近用性測試。

### 下一步：把需求連到驗收測試

我們以 FR-01 與 FR-02 為例，寫出兩種情境。

正常情境：

```
Given 所有必要欄位都已完整填寫
When 使用者按下「檢查」
Then 系統顯示檢查通過
And 允許匯出完整報告
```

異常情境：

```
Given 案件編號只有空白字元
When 使用者按下「檢查」
Then 系統指出案件編號缺漏
And 不允許匯出完整報告
```

這種 Given／When／Then 的寫法，就是下一章 M05-03 要深入學習的驗收情境表達方式。

還有一個容易遺漏的情境：

假設你剛剛完成檢查，之後又把案件編號刪掉，系統能不能直接沿用先前的檢查通過結果？

不應該。因為資料已經改變，舊結果可能失效。

因此還需要補充規則：資料修改後，既有的完整性檢查結果必須失效，重新檢查通過後才能完整匯出。

這正是軟體工程真正困難的地方：問題常常不是程式不會寫，而是需求沒有把例外與狀態變化想清楚。

## 七、為什麼這件事在 AI Coding Agent 時代更重要？

過去你找工程師開發軟體，工程師可能會主動追問需求。

現在你可以直接告訴 AI：

「幫我做一個資料檢查網站。」

AI 可能很快產生一個漂亮、可以操作的網站，但它可能沒有正確處理空白欄位、過期檢查結果、匯出限制，甚至沒有定義何謂完整。

所以正確的 AI 協作流程應是：

1. 先寫 User Story：確認使用者與目的。
2. 補 FR、NFR、Constraints：定義功能、品質及界線。
3. 補 Acceptance Criteria：寫出正常、錯誤及邊界情境。
4. 交給 AI Coding Agent 實作：要求依照規格開發，不自行假定重要業務規則。
5. 執行測試並保留證據：檢查結果是否符合需求，未測試的項目不得宣稱通過。

每一個需求最好都有穩定編號，能追溯到相應的驗收情境及測試結果。例如：

`S-01 → FR-01 → AC-01 → TEST-01 → PASS / FAIL`

這叫做 Traceability（可追溯性）。

將來需求改變時，你可以知道哪條規格要更新、哪些測試要重跑，而不是只憑 AI 說「已修改完成」。這也是 NASA 需求指引強調的核心特性之一。

## 八、動手練習：寫一份最小規格

本章不需要先寫程式。可以使用 `spec.md` 記錄如下內容：

```
# S-01 使用者故事
角色：
目標：
理由：

# Functional Requirements
FR-01：
FR-02：

# Non-Functional Requirements
NFR-01：

# Constraints
C-01：

# Acceptance Criteria
AC-01 正常情境：
AC-02 異常情境：

# Verification
驗證方法：
實際結果：待驗

# Open Questions
尚待確認的規則：
確認負責人：
```

建議先選一個很小的業務工作，而不是一口氣規劃整套大型系統。完成規格後，應能讓另一位工程師或另一個 AI Agent 根據同一份內容，產出外部行為一致、可以獨立驗收的系統。

## 九、理解檢核

以下是三個情境題。先自行判斷，我會依你的答案分析哪些觀念已掌握、哪些需要補強。

1\. 某主管說：「我要一套好用又安全的人事系統。」目前最欠缺的是什麼？

A. 指定使用哪一種前端框架

B. 補充使用者目的、具體行為、品質條件、約束與驗收方式

C. 先讓 AI 把全部畫面做出來

D. 把句子改寫成英文

2\. 系統必須禁止員工查看其他部門的機密紀錄。這比較適合如何處理？

A. 只要放在非功能需求即可，不必測試

B. 只要有登入畫面就已完成

C. 寫出授權規則與拒絕行為，並設計測試驗證

D. 只需要加密資料庫

3\. AI 已根據規格產生程式碼，並表示所有功能都已完成。接下來最合理的作法是？

A. 直接上線

B. 只確認畫面是否美觀

C. 逐項執行對應的正常、異常與品質驗收，記錄測試證據

D. 改成另一個 AI 模型重新生成

提交答案並取得解析

本章最值得記住的結論是：User Story 定義價值，FR 定義行為，NFR 定義品質，Constraints 定義界線，而 Acceptance Criteria 讓這一切變得可以驗證。
