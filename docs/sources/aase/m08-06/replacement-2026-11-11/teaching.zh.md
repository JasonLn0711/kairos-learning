## 用白話理解負向測試與回歸證據

這一課最重要的觀念是：

一個系統不只要在使用者做對事情時能夠正常運作，也要在使用者做錯事情、輸入異常資料，甚至有人試圖越權操作時，能夠正確拒絕，而且不造成新的問題。

例如：

- 銀行系統能正常轉帳，不代表它能阻止未授權轉帳。
- 醫院系統能查詢病歷，不代表它會阻止員工查看無權存取的病歷。
- AI 系統能產生正確報告，不代表它不會洩漏額外輸入的敏感資料。
- 資安漏洞修好了，不代表修補程式沒有破壞其他正常功能。

這就是本課的核心：負向測試（Negative Testing）＋回歸測試（Regression Testing）＋可核對的證據（Evidence）。

本課以本機單人「資料檢核與報告匯出系統」說明負向測試與回歸證據。多人授權保留為未實作、未驗證的後續需求。




## 一、先搞懂：正向測試與負向測試差在哪裡？

假設你開了一間銀行，設計了一套 ATM 提款系統。

### 正向測試（Positive Testing）

你想知道正常客戶能不能順利領錢。

> 插入有效提款卡 → 輸入正確密碼 → 帳戶餘額足夠 → 領取 3,000 元 → 成功。

這項測試通過，代表系統在這個正常情境下可以使用。

### 負向測試（Negative Testing）

接著，你要確認系統遇到不合理的要求時會怎麼處理。

| 測試情境                      | 你期待系統怎麼做 |
| ------------------------- | -------- |
| 密碼輸入錯誤                    | 拒絕提款     |
| 帳戶只有 1,000 元，要求領取 5,000 元 | 拒絕提款     |
| 提款金額輸入負數                  | 拒絕異常金額   |
| 已登出的客戶要求提款                | 拒絕操作     |
| A 客戶試圖存取 B 客戶帳戶           | 拒絕未授權存取  |

這些負向測試的目的，不是故意讓系統故障，而是確認：

系統碰到不該成功的事情時，能不能以預期、安全、可控制的方式處理？

注意，拒絕不一定代表程式當機或顯示錯誤。好的拒絕應當讓交易停止、不產生不當副作用，並提供適當訊息。

這樣的測試才有清楚的目的與驗收標準。

## 三、教材的三個核心案例

教材使用一個「資料檢核與報告匯出系統」作為示範。這三種負向情境，剛好代表三種不同的保護目標。




### 案例一：必要資料沒有填完，系統不能匯出完整報告

假設一家保險公司要用系統產生理賠報告。

必須填寫被保險人、事故日期、理賠金額。

如果缺少理賠金額，系統卻產生一份標記為「完整」的報告，就有可能造成後續作業錯誤。

所以我們要測試：

- 正常：資料完整，允許匯出。
- 異常：必要欄位空白，拒絕匯出。
- 異常：日期欄輸入錯誤資料型態，拒絕或要求修正。
- 異常：輸入超過規格允許長度，安全拒絕。

尤其要注意：不只是畫面上的匯出按鈕不能按，直接呼叫匯出函式時，也必須拒絕。

為什麼？因為按鈕只是其中一條操作途徑。如果底層函式仍然允許匯出，就沒有真正守住資料規則。

### 案例二：系統收到額外欄位，不能把不該輸出的資料帶出去

假設一家物流公司有一個出貨 API，合法輸出只有三個欄位：

```
{
  "order_id": "A001",
  "product": "筆記型電腦",
  "quantity": 2
}
```

但輸入資料裡面多了一個：

```
{
  "order_id": "A001",
  "product": "筆記型電腦",
  "quantity": 2,
  "debug_note": "內部測試紀錄"
}
```

如果程式只是把所有收到的欄位直接轉成報告，就可能連 `debug_note` 一起輸出。

這時候我們應該採取一種叫做 Allowlist（允許清單） 的做法。

意思是：報告明確只允許 `order_id`、`product`、`quantity` 三個欄位，其餘欄位不進入輸出。

測試時就要檢查產生的 JSON 是否只有這三個鍵，而不是只檢查報告能否成功建立。

這樣的測試能證明輸出欄位受到約束，但不能直接證明系統的日誌、資料庫或其他出口都沒有洩漏資料。

### 案例三：資料已經改變，舊的成功結果不能繼續有效

這個案例比較容易被忽略。

假設你在電商平台結帳：

1. 購物車有兩件商品。
2. 系統計算總金額 2,000 元。
3. 畫面顯示「訂單檢查完成」。
4. 你把其中一件商品刪掉。
5. 系統卻仍然保留舊的 2,000 元結帳結果。

這就是一種過期狀態（Stale State） 問題。

放到教材的報告系統，就是使用者原本把欄位填完整，系統顯示成功並提供下載；之後使用者把必要欄位清空，但畫面仍保留「成功」和舊的下載按鈕。

正確設計應該讓舊的結果失效，要求重新檢查；後端也不能接受不再符合規格的資料。

這裡要測試的不只是輸入是否合法，而是狀態改變後，系統是否重新判斷原本的結果還能不能使用。

## 四、為什麼「畫面上看不到」不代表真正安全？

這是這一課最值得深入理解的安全觀念。

假設公司內部有兩個員工：小明與小華。

小明登入之後，畫面只顯示自己的報告。工程師認為已經完成權限隔離。

但小明可能直接要求後端 API 讀取小華的報告：

```
GET /api/reports/102
```

如果後端只檢查「小明有沒有登入」，卻沒有檢查「小明有沒有權限讀取 102 號報告」，那麼即使畫面上完全沒有小華的資料，仍可能發生越權存取。

這就是為什麼必須分清楚：

| 觀念                   | 白話解釋            |
| -------------------- | --------------- |
| Authentication（身分驗證） | 你是誰？            |
| Authorization（授權）    | 你可以做什麼？         |
| Access Control（存取控制） | 系統如何實際執行這些權限限制？ |

在安全的多人系統裡，授權必須在可信任的伺服器端或資料存取邊界執行，而不能只靠瀏覽器隱藏按鈕。OWASP 也建議採取預設拒絕（Deny by Default），並對每次受保護的存取請求進行適當的授權檢查。




### 把需求寫成 Given／When／Then

```
Given：
使用者 A 已登入，
但未獲授權讀取使用者 B 的報告。

When：
A 透過 API 請求 B 的報告。

Then：
伺服器拒絕存取，
不回傳 B 的報告內容，
也不產生未授權的資料變更。
```

這樣我們就把抽象的「權限要安全」，變成可執行、可觀察的測試。

不過教材特別強調：目前示範的是本機單人原型，還沒有真正的帳號、多人身分與資料庫隔離。

因此，多人授權測試應標記為「未實作、未驗證」，不能寫個假函式模擬 A 和 B，就宣稱正式的存取控制已經通過測試。




## 五、回歸測試：修好一個問題，為什麼還需要重新測試？

Regression Testing 的白話意思是：

確認這一次的修改，沒有讓原本正常的功能退步。

例如，一家餐廳的線上訂餐系統發現優惠券可以重複使用。

工程師修好這個問題之後，不能只確認「同一張優惠券不能重複使用」。

還要確認：

- 合法優惠券仍然可以使用一次。
- 沒有優惠券的客戶仍然可以結帳。
- 金額計算依然正確。
- 原本的折扣與付款流程沒有被意外破壞。

換句話說，修正之後至少要重新測試兩件事：

第一，原本失敗的負向情境現在通過了嗎？

第二，原本正常的功能還能正常使用嗎？

這就是負向測試與回歸測試之間的關係。

一個常見錯誤是為了讓測試通過，乾脆放寬規則或刪除失敗的測試。這樣並沒有真正解決問題，只是讓檢查工具不再發出警告。

## 六、實際寫程式時，怎麼做這些測試？

以 Python 為例，你可以用 `pytest` 建立可重複執行的自動化測試。

先看一個簡化的報告函式：

```
# report.py
ALLOWED = ("customer", "date", "amount")


def export_report(data):
    for key in ALLOWED:
        value = data.get(key)
        if not isinstance(value, str) or not value.strip():
            raise ValueError(f"{key} 無效")
    return {key: data[key] for key in ALLOWED}
```

這段程式只有兩個重點：必要欄位必須有有效字串；輸出只能包含允許的三個欄位。

接著寫測試：

```
# test_report.py
import pytest
from report import export_report


def test_missing_amount():
    data = {"customer": "A", "date": "2026-11-11", "amount": ""}
    with pytest.raises(ValueError):
        export_report(data)


def test_extra_field():
    data = {
        "customer": "A", "date": "2026-11-11", "amount": "100",
        "debug_note": "PRIVATE",
    }
    result = export_report(data)
    assert set(result) == {"customer", "date", "amount"}
    assert "debug_note" not in result


def test_valid_report():
    data = {"customer": "A", "date": "2026-11-11", "amount": "100"}
    assert export_report(data) == data
```

將以上兩個檔案存入同一個空資料夾，在虛擬環境安裝 `pytest` 後執行：

```
python -m venv .venv
source .venv/bin/activate
python -m pip install pytest
python -m pytest -q
```

這三個測試分別確認缺漏被拒絕、額外欄位不輸出，以及正常報告仍然可用。

`pytest.raises(ValueError)` 的意思是：我們預期函式會主動拋出指定錯誤。如果沒有拋出，這個測試反而失敗。




以上是獨立的簡化教學示範，僅檢查非空字串與輸出允許清單；它與工作坊第三切片的欄位及完整規格不同。日期字串尚未驗證日曆格式，金額尚未驗證數字格式，也未涵蓋長度上限、過期 UI 狀態、檔案寫入副作用或真正的帳號授權。前三個核心案例中，這段程式只示範前兩個；過期結果仍須在 UI 狀態層另測。

### 不同問題，要在哪一層測試？

| 測試層次            | 主要檢查什麼                 |
| --------------- | ---------------------- |
| 單元測試（Unit Test） | 函式是否正確拒絕不合法輸入          |
| API／整合測試        | 系統是否在資料存取時真正執行規則與權限    |
| 介面測試（UI Test）   | 資料變更後，成功狀態與下載操作是否更新    |
| 端到端測試（E2E Test） | 從使用者操作到後端處理的完整路徑是否符合預期 |

教材的 Streamlit 系統可以使用 `AppTest` 模擬畫面上的操作與狀態變化，再搭配實際瀏覽器測試確認真實互動。




## 七、什麼叫做「回歸證據」？

想像你是一位主管，工程師向你報告：

> 昨天發現的問題已經修好了。

你可能會追問：修了哪一版？測試了什麼？原本的問題是否真的消失？其他功能有沒有受到影響？

所以工程師不能只有一句「修好了」，而應該留下可核對的紀錄。

以下是範例格式，不是已執行的測試結果：

| 證據欄位  | 紀錄內容示例                 |
| ----- | ---------------------- |
| 風險編號  | RISK-03                |
| 測試案例  | NEG-03：修改必要欄位後，舊下載結果失效 |
| 預期結果  | 舊成功狀態和下載操作失效           |
| 測試方式  | AppTest＋瀏覽器            |
| 實際結果  | 執行後填入                  |
| 程式版本  | Git Commit Hash        |
| 測試環境  | Python、套件版本、作業系統       |
| 回歸測試  | 記錄原案例及受影響正常案例結果        |
| 未驗證事項 | 多人授權、真實部署安全性           |

有了這些資料，其他工程師就能知道當時怎麼測試、測試的是哪個版本，以及哪些保護還沒有證據。

這不等於數學上證明系統絕對安全，而是建立一組可重現、可稽核的品質證據。

## 八、跨產業延伸：同一套方法可以用在哪裡？

| 產業       | 負向測試                  | 修正後的回歸測試     |
| -------- | --------------------- | ------------ |
| 金融       | 非帳戶持有人嘗試提款            | 合法提款仍然成功     |
| 醫療       | 未授權人員嘗試讀取病歷           | 有授權的醫護人員仍能讀取 |
| 電商       | 重複套用同一張限用一次的折價券       | 合法折價券依然可用    |
| 物流       | 出貨報告含額外內部欄位           | 合法出貨資料仍完整輸出  |
| 教育       | 學生嘗試修改其他學生的成績         | 教師仍能依授權更新成績  |
| AI Agent | Agent 嘗試執行超出授權範圍的工具操作 | 合法工具呼叫仍正常完成  |

這些例子背後是同一個原理：系統要同時證明「應該允許的能完成」與「應該禁止的被阻止」，而且每次修改都不能破壞既有保護。

要注意，通過這些測試只代表特定情境已經驗證。其他尚未測試的漏洞、部署設定、依賴套件或操作環境風險，仍須另外評估。

## 九、理解檢核：一個整合情境

假設某學校正在開發一套成績查詢系統。

目前系統只有簡單的成績查詢畫面，未來要讓 30 位老師共同使用。每位老師原則上只能查閱自己有權限管理的學生資料。

有一天，工程師發現：老師 A 雖然看不到老師 B 的學生名單，卻可以透過修改 API 請求中的 `student_id`，讀取老師 B 管理的學生資料。

問題 1：這個問題最根本的原因可能是什麼？

A. 畫面設計不夠美觀

B. 後端沒有正確檢查資源授權

C. 資料庫查詢速度不夠快

D. 使用者沒有重新整理畫面

問題 2：修復漏洞後，最合理的測試方式是什麼？

A. 只確認 A 看不到 B 的資料

B. 只確認系統可以正常登入

C. 確認未授權存取被拒絕，且合法查詢仍可執行

D. 直接刪除原本的測試

問題 3：如果系統目前沒有真正的登入與授權功能，該怎麼記錄驗收狀態？

A. 預設通過

B. 標記未實作、未驗證，保留後續驗收需求

C. 用假帳號測試後宣告正式安全

可在頁末「理解檢核」逐題展開參考解析；展開答案不會提交作答或記錄學習完成。

本課最重要的結論： 資安驗證不是讓所有測試都顯示綠燈，而是用可靠的測試證據，清楚說明系統已經守住哪些邊界、哪些修正沒有造成退步，以及哪些安全需求仍未完成。
