## 一、先用一句話理解這堂課

pytest 就是一個可以幫程式自動考試的工具，而業務規則測試，就是檢查程式有沒有確實遵守我們訂下的規定。

想像你開了一家銀行，有一項規定：

「申請貸款的人，年齡必須滿 18 歲。」

你請工程師寫好系統，他告訴你：「系統已經完成，按鈕也可以使用。」

但這並不代表系統真的符合規定。

你至少要檢查：

- 17 歲的人，系統是否正確拒絕？
- 18 歲的人，系統是否正確接受？
- 19 歲的人，系統是否正確接受？
- 沒有填年齡，系統會怎麼處理？
- 有人填「十八歲」而不是數字，系統會怎麼處理？

如果每次都要找人打開網站、填表單、按按鈕，效率會非常低。

pytest 讓我們把這些情境寫成測試程式，每次修改系統時，都能重新執行，確認原本正確的規則沒有被破壞。

這堂教材的核心，就是學會將規格（Specification）轉換成能自動檢查的測試（Automated Tests）。

## 三、什麼是業務規則（Business Rules）？

業務規則就是「這個系統必須遵守的規定」。

它不是程式語法，而是來自真實世界的業務需求。

例如：

| 行業 | 業務規則             | 系統必須做到             |
| -- | ---------------- | ------------------ |
| 電商 | 消費滿 1,000 元免運費   | 999 元收運費，1,000 元免運 |
| 醫療 | 缺少必要檢體資訊不能送出檢驗申請 | 阻止送出並指出缺漏          |
| 銀行 | 申請資料必須填寫必要欄位     | 缺欄位不能完成申請          |
| 教育 | 成績必須介於 0～100 分   | 拒絕負分或超過 100 分      |
| 物流 | 寄件重量不得超過特定上限     | 超重時拒絕或轉其他服務        |
| 人資 | 特休天數依適用制度及年資計算   | 依正確規則計算假別額度        |

這些只是示範規則，並不代表各行業實際法規。

### 為什麼不只測試畫面？

假設一個電商網站，把購物金額的輸入框限制成不得輸入負數。

看起來沒問題，對吧？

但有些資料不一定經過畫面進入系統。例如其他系統透過 API 直接送資料，或程式內部呼叫同一個函式。

如果後端沒有檢查，仍然可能收到 `-500` 這種不合理的訂單金額。

因此我們應該區分：

- 介面驗證（UI Validation）：在畫面上提前提醒使用者。
- 業務規則驗證（Business Rule Validation）：無論資料從哪裡來，系統都遵守規定。

這也是本課為什麼要直接測試 `rules.py`，而不是只用滑鼠操作介面。

## 四、pytest 如何幫程式自動考試？

我們用電商免運費的例子，實際寫一次。

假設規格已經確認：

- 訂單滿 1,000 元免運費。
- 不滿 1,000 元收 60 元。
- 金額不得為負數，也必須是整數。

第一步：撰寫業務程式 `rules.py`

```
def delivery_fee(total: int) -> int:
    if type(total) is not int or total < 0:
        raise ValueError("訂單金額必須是非負整數")
    if total >= 1000:
        return 0
    return 60
```

把它翻譯成白話：

「如果金額不是整數，或者金額小於零，就拒絕。如果金額大於或等於 1,000 元，運費就是零，否則運費是 60 元。」

這裡有幾個專有名詞：

`def` 是定義函式，`return` 是回傳結果，`raise ValueError` 是主動告知呼叫者「你給我的值不符合要求」。

第二步：撰寫測試程式 `test_rules.py`

```
import pytest
from rules import delivery_fee

@pytest.mark.parametrize("amount, expected", [(0, 60), (999, 60), (1000, 0), (1001, 0)])
def test_delivery_fee(amount, expected):
    assert delivery_fee(amount) == expected

@pytest.mark.parametrize("bad", [-1, 1.5, "1000", True])
def test_invalid_amount(bad):
    with pytest.raises(ValueError):
        delivery_fee(bad)
```

這段程式的意思非常簡單：

「請 pytest 用四筆不同資料呼叫同一個函式，看看運費是不是我們預先規定的答案。」

@figure2

### `assert` 是什麼？

`assert` 稱為「斷言」。

白話就是：「我認定這個條件應該成立；如果不成立，就代表測試失敗。」

例如：

```
assert delivery_fee(999) == 60
```

意思是「999 元的訂單，運費應該是 60 元」。

如果程式錯誤地回傳零元，pytest 就會回報失敗，幫你找出規格與實作不一致的地方。

## 五、參數化測試：不用寫十幾份相同的考卷

本課最重要的技巧之一，是 `@pytest.mark.parametrize`。

它的英文名稱是 Parameterization，中文叫「參數化」。

你可以把它想成一位老師：

老師不用為每位學生重新寫一份考卷，而是拿同一套評分標準，檢查不同學生的答案。

程式測試也一樣。

假設銀行申請表有三個必填欄位：

- `application_id`：申請編號。
- `applicant_code`：申請人代號。
- `document_type`：文件類型。

教材規定每個欄位去除首尾空白後，必須是非空字串，而且長度不能超過 80 字元。這是教學用的合成規格。

如果每個欄位都要測六種不合法輸入：

| 無效資料       | 為什麼要測？         |
| ---------- | -------------- |
| `""`       | 完全沒有輸入         |
| `"   "`    | 看似有輸入，其實只有空白   |
| `"\t\n"`   | 只有 Tab、換行等空白字元 |
| `None`     | 沒有提供有效值        |
| `42`       | 輸入型別錯誤，應是文字    |
| `"x" * 81` | 超過允許長度         |

三個欄位乘以六種情境，就是 18 個測試案例。

我們不需要寫 18 個函式。

```
import pytest
from rules import validate, export_report

GOOD = {"application_id": "SYN-001", "applicant_code": "DEMO-A", "document_type": "合成申請表"}

@pytest.mark.parametrize("field", ["application_id", "applicant_code", "document_type"])
@pytest.mark.parametrize("bad", ["", "   ", "\t\n", None, 42, "x" * 81])
def test_invalid_field(field, bad):
    record = {**GOOD, field: bad}
    assert validate(record)
    with pytest.raises(ValueError):
        export_report(record)
```

這段範例已建立有效的 `GOOD` 字典並匯入工作坊 `rules.py` 的兩個函式。電商與三欄申請案例使用不同的 `rules.py`，請分別在自己的目錄執行。

`{**GOOD, field: bad}` 的意思是：複製一份原本正確的資料，僅將這次要測的欄位換成不合法的值。

`with pytest.raises(ValueError)` 的意思是：「這個操作按規定應該拒絕輸入，並產生指定類型的錯誤。」

如果不合法資料居然順利匯出，測試反而要判定失敗。

這項機制是 pytest 官方支援的測試能力。

## 六、為什麼要特別測試邊界（Boundary Testing）？

假設規格要求「最多 80 字元」。

你會測哪些長度？

如果只測 10 字元和 100 字元，雖然分別測到正常與異常資料，卻不一定能發現最容易發生的錯誤。

例如工程師不小心把條件寫成：

```
if len(value) >= 80:
    raise ValueError()
```

這樣剛好 80 字元也會被拒絕。

正確規則應該是在超過 80 字元時才拒絕。

@figure3

這個觀念適用於任何有門檻的系統，例如銀行交易限額、學校成績、重量上限、購物折扣，以及 API 請求數量限制。

重點是：先從規格找出臨界點，再設計臨界點前後的測試。

## 七、輸出契約測試：不只檢查能不能做，還要檢查做出什麼

這堂課還強調一件很重要的事：Output Contract（輸出契約）。

假設系統產生一份 JSON 報告，規定只能輸出三個核准欄位。

但是原始資料裡，還有一個額外的內部備註欄位：

```
{
    "application_id": "A001",
    "applicant_code": "U001",
    "document_type": "申請表",
    "debug_note": "internal"
}
```

我們必須確認三件事：

1. 有效資料能產生報告。
2. 報告只包含允許匯出的欄位。
3. 執行匯出不會意外修改原始輸入。

這類檢查不只涉及功能品質，在某些情境也能降低意外輸出額外資料的風險；但不能取代存取控制與完整的資安測試。

教材使用 `json.loads()` 解析匯出結果，再以 `assert` 檢查 JSON 結構與內容。

## 八、測試結果通過，為什麼還不能說系統完全正確？

這裡要理解不同測試的責任範圍。

| 測試類型                   | 主要回答的問題         |
| ---------------------- | --------------- |
| Unit Test（單元測試）        | 個別規則算得對不對？      |
| Integration Test（整合測試） | 不同元件接在一起是否正常？   |
| UI Test（介面測試）          | 畫面和操作是否正確？      |
| Usability Test（易用性測試）  | 真實使用者能否順利完成任務？  |
| Security Test（資安測試）    | 系統是否適當防範已識別的風險？ |

舉例來說，某銀行的利息計算公式通過了 100 個單元測試，但這不表示使用者能在網頁上成功提交資料，也不表示其他人無法存取這筆資料。

尤其要注意兩種測試缺陷：

第一，測試的預期答案本身可能錯誤。 如果你把程式目前算出來的答案直接當成正確答案，程式與測試可能一起犯錯。正確答案應優先來自已確認的規格。

第二，測試只驗證你有寫到的情境。 100% 通過率，並不代表所有可能輸入、操作及攻擊情境都受過驗證。

因此要把「已驗證哪些條件」與「尚未驗證哪些條件」記錄清楚。

## 九、實際上要怎麼執行 pytest？

假設有以下專案：

```
my-project/
├── rules.py
└── tests/
    └── test_rules.py
```

在已安裝 pytest 的 Python 環境裡，進入專案根目錄後執行：

```
python -m pytest -q
```

`python -m pytest` 表示使用目前 Python 環境執行 pytest；`-q` 表示使用較精簡的輸出。pytest 會依預設規則尋找符合命名方式的測試檔案。

上述電商範例含四筆正常及四筆無效金額測試。以下是八例全部通過時的輸出示意；請保存自己實際執行的結果：

```
........
8 passed
```

其中每個 `.` 表示一個通過的測試。

如果未通過，應依序確認是測試環境或匯入錯誤、測試預期不正確，還是程式實際違反規格。不要為了讓測試顯示綠燈，就任意修改正確的驗收標準。

## 十、這堂課最重要的五個原則

1. 先有規格，再有測試。 沒有正確答案，就無法可靠地判斷程式是否正確。
2. 每次盡量只改變一個測試條件。 這樣失敗時比較容易知道是哪個規則出了問題。
3. 同時測正常、異常與邊界。 不能只有「應該成功」的案例。
4. 檢查失敗的方式是否正確。 有些規格要求拒絕操作或拋出特定例外，不是任何錯誤都算通過。
5. 把測試當成可重複的證據，不是絕對保證。 系統修改後要重新執行，並保留尚未涵蓋的風險。

## 十一、理解檢核：用真實情境來判斷

假設你正在替一家醫院設計檢驗申請系統，已確認以下規格：

- 檢驗申請必須有病歷代碼。
- 檢驗項目代碼必須是核准清單中的值。
- 申請數量必須是 1～10 的整數。
- 資料不合法時禁止送出。
- 匯出的報告不得含內部除錯欄位。

請你試著回答：

問題 1： 針對「申請數量必須是 1～10」，你會設計哪些正常、無效與邊界案例？至少列出六筆。

問題 2： 如果使用者在畫面上無法輸入 11，但是後端 API 直接收到 11，系統仍接受。這反映了什麼測試或實作問題？

問題 3： 如果程式正確拒絕了非法資料，卻拋出 `TypeError` 而不是規格要求的 `ValueError`，測試應該如何判定？

問題 4： 假設所有業務規則測試都通過，是否可以宣布整個醫院系統完成驗收？為什麼？

請先自行作答，再展開本頁參考答案逐題核對。

只要你能獨立把一份業務規格轉成「有效資料、無效資料、邊界條件、預期例外、輸出契約」五類測試，就已掌握這堂課最重要的實務能力。
