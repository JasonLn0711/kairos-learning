## 規則寫對之後，如何驗證使用者操作？

程式的規則寫對了，不代表使用者操作畫面時，系統就一定會做對。例如，銀行申請系統規定「資料不完整，不可以產生報告」。後端函式已能拒絕缺漏，畫面與狀態管理仍可能出錯：

1. 使用者沒有填完資料。
2. 畫面卻顯示「檢查成功」。
3. 使用者補齊資料後，畫面沒有更新。
4. 使用者又把資料刪掉，卻仍然可以下載之前產生的報告。

這些是介面與狀態管理的錯誤，不一定是業務規則本身的錯誤。Streamlit 的 AppTest 能自動模擬操作，檢查畫面和程式狀態是否符合預期。讀圖時，請把每個斷言連回前一次輸入與重新執行。

@figure1

每次修改輸入，都要確認新操作造成的結果，避免沿用上一次的狀態。本課延續 M08-03 的規則測試，進一步檢查使用者任務如何經由介面完成。

## 一、為什麼需要 AppTest？用餐廳點餐理解

想像你經營一家餐廳，推出自助點餐機。點餐系統有三條規則：

- 沒有選餐點，不能送出訂單。
- 選好餐點、數量和付款方式，才能確認訂單。
- 訂單確認後，如果顧客修改內容，原本的確認結果必須失效。

你可以分別測試規則與操作。業務規則測試（Business Rule Testing）直接呼叫檢查函式，傳入沒有餐點的訂單，確認它會拒絕；上一課 M08-03 的 pytest 主要在做這件事。

介面測試（UI Testing）則模擬顧客使用點餐機：

1. 不選餐點，按下送出。
2. 檢查畫面是否出現「請選擇餐點」。
3. 選好餐點，再按送出。
4. 檢查畫面是否顯示成功。
5. 改變餐點，檢查舊訂單的確認狀態是否消失。

AppTest 讓 Python 自動重演這些操作，省去每次人工重複點擊的工作。它模擬 Streamlit 程式，並未真正操作 Chrome 或 Firefox；排版、焦點與實際下載另做瀏覽器驗證。

## 二、先掌握整張地圖：軟體測試有不同層次

不同層次回答不同問題，應依任務一起安排。

| 測試層次 | 白話理解 | 想確認什麼 |
| --- | --- | --- |
| Unit Test 單元測試 | 單獨檢查一項規則 | 金額計算對不對？ |
| UI AppTest | 模擬操作軟體介面 | 輸入後，提示與按鈕有沒有正確更新？ |
| Browser E2E Test | 在真實瀏覽器走完整流程 | 點擊下載後，檔案真的下載了嗎？ |
| Usability Test 易用性測試 | 找真實使用者完成任務 | 使用者看得懂提示嗎？ |
| Security Test 安全測試 | 測試安全邊界與不當操作 | 未授權的人是否能取得其他人的資料？ |

這些測試互相補充。例如 AppTest 顯示「下載按鈕存在」，只證明模擬測試看到了該元件，不能證明使用者的電腦已收到正確檔案。就像點餐機顯示「訂單成功」，還需要另行確認廚房真的收到訂單。

## 三、本課最重要的三階段測試

本課以「收件資料檢核系統」為例，填寫案件編號、申請人代碼、文件類型。圖中三個階段是同一次情境的連續操作；向下箭頭表示修改輸入後再檢查結果。

@figure2

第三階段容易被忽略：系統曾產生正確結果，使用者後來卻改變輸入。舊結果若沒有失效，就可能下載到和目前畫面不一致的資料，這叫過期狀態（Stale State）。

> 凡是某個結果依賴一組輸入，只要那組輸入改變，就必須重新判斷舊結果是否仍然有效。

本例採用「欄位變更就清除成功狀態與報告」的策略，要求重新檢查。相同原則也適用於金融審批、醫療報告、研究資料處理與物流調度；各系統仍須依自己的規格決定何時重新驗證。

## 四、理解 AppTest 的六個核心名詞

先分清楚輸入元件、跨重跑保存的資料，以及測試明確執行的動作。

| 名詞 | 白話意思 |
| --- | --- |
| Streamlit | 用 Python 快速建立互動式網頁應用的框架 |
| Widget | 輸入框、按鈕、選單等操作元件 |
| AppTest | 模擬執行 Streamlit App、設定輸入並檢查結果的測試工具 |
| Session State | 替目前使用工作階段記住資料與狀態 |
| run() | 明確重新執行程式，讓新輸入產生新畫面 |
| assert | 宣告條件必須成立，不成立就讓測試失敗 |

Session State 可以用購物車理解：你把三樣商品加入購物車，切換頁面後，網站仍記得購物車裡的內容。這個比喻說明跨操作保留資料，實際保存範圍與生命週期仍取決於系統實作。

Streamlit 的元件操作會引起程式重新執行，Session State 能讓資料跨重跑保留。AppTest 則要求測試程式明確呼叫 run()；設定輸入值之後，先重跑，再觀察新畫面。

## 五、動手實作：建立一個可以自動測試的應用程式

這個教學用簡化範例延續三欄合成資料，展示缺漏阻擋與過期結果失效。正式收件或審批系統還需要符合自身規格的授權、資料隔離與後端驗證。

```text
my-project/
├── app.py
└── tests/
    └── test_app.py
```

### 第一步：寫出應用程式 app.py

將下列完整程式存為 app.py。三個欄位使用穩定 key，測試可依 key 找到元件；檢查按鈕也有自己的 key。

@app

on_change=invalidate 表示輸入欄位的值改變時，先執行 invalidate()，清除過去的確認結果。pop("checked", None) 表示有該狀態就刪除，沒有就不做任何事；report 也以相同方式清除。

按下檢查後，程式先去除欄位前後空白，找出缺少的資料。缺漏時清除舊結果並顯示錯誤；完整時把本次資料序列化成 JSON，保存報告並設定 checked。成功與下載區放在按鈕條件之外，讓後續重跑仍能依目前狀態顯示；輸入一變動，回呼便使舊報告失效。

### 第二步：使用 AppTest 模擬操作

將下列測試存為 tests/test_app.py。Path 依測試檔的位置找到 app.py，讓測試不依賴啟動 shell 的偶然目錄。

@tests

第一階段只填兩欄，確認錯誤提到文件類型、已填資料保留，且成功與下載元件都不存在。第二階段補齊第三欄再按檢查，確認成功、下載元件及 checked/report 狀態。第三階段再次清空第三欄，確認舊成功、下載、checked 與 report 全部消失。

測試檢查每次操作後的畫面與狀態是否符合規格。Streamlit 1.51.0 沒有獨立的 at.download_button 操作 API，本課使用 at.get("download_button") 檢查元件存在；這不代表實際下載成功。範例固定使用此版本，升級時應重新核對 API 與測試結果。

### 第三步：執行測試

在專案根目錄使用獨立 Python 虛擬環境，安裝教材指定版本，再執行測試。

```sh
python -m venv .venv
source .venv/bin/activate
python -m pip install streamlit==1.51.0 pytest
python -m pytest -q tests/test_app.py
```

測試通過，代表這次執行的自動化斷言成立。仍需啟動真實程式，重演相同操作，檢查下載檔名 report.json、中文資料、status 與欄位內容是否對應目前輸入。

```sh
python -m streamlit run app.py
```

瀏覽器中先填兩欄並按檢查，應看到缺漏提示；補齊並檢查後下載 JSON；接著清空文件類型並離開欄位，舊成功與下載入口應消失。也用 Tab、Shift+Tab、Enter 與 Space 檢查焦點和按鈕操作。用 Ctrl+C 停止自己啟動的服務，執行 deactivate 離開虛擬環境。

## 七、AppTest 在其他行業可以測試什麼？

換一個產業時，先找出哪個結果依賴哪些輸入，再設計變更後的斷言。

| 行業 | 介面操作情境 | 重要斷言 |
| --- | --- | --- |
| 醫療 | 病患預約後改變預約日期 | 舊預約摘要不得冒充新日期的確認結果 |
| 電商 | 顧客使用折價券後修改購物車 | 應重新計算金額，不保留失效折扣 |
| 人資 | 員工修改請假日期 | 舊天數與舊核准狀態不得錯誤沿用 |
| 物流 | 倉庫人員修改出貨數量 | 舊運費與出貨確認結果必須重新判斷 |
| 教育 | 學生修改報名資料 | 資料不完整時，舊的完成狀態必須失效 |

這些情境共用「輸入資料 → 驗證 → 產生結果 → 輸入改變 → 舊結果失效」的判斷流程。辨識這條依賴關係，就能把相同測試思維套用到其他系統；實際欄位與有效性條件仍由各系統規格定義。

## 八、AppTest 的能力邊界：最容易犯的四個錯誤

讀測試結果時，請同時說明已執行的情境與還需要的證據。

| 常見誤解 | 正確觀念 |
| --- | --- |
| 測試全部通過，代表軟體沒有 Bug | 只代表已執行的測試情境通過 |
| 有下載按鈕，代表下載成功 | 還必須確認實際檔案及內容 |
| 修改輸入後，不必重新執行測試 | AppTest 需要明確 run() |
| 畫面正常就代表安全 | 還需要權限、資料隔離、後端驗證等測試 |

假設使用者 A 和 B 都能登入。測試 A 能下載自己的報告，不能推論 A 絕對無法下載 B 的報告；必須另外設計授權驗證與跨使用者隔離測試。AppTest 可檢查部分可見介面行為，後端安全控制仍須有對應驗證。

請在下方「理解檢核」先選答案，思考理由，再展開各題的參考解析。三題分別檢查 run()、過期狀態與實際下載的證據界線；本頁使用原生展開功能，選答與閱讀解析不作為學習完成紀錄。
