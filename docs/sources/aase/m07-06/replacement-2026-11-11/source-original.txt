# M07-06｜審查 Diff、工具紀錄與決策：如何知道 AI Agent 真的把事情做好？

這一節最重要的觀念是：

AI Agent 說「我已經完成」，不代表它真的完成；程式能執行，也不代表它符合你的要求。

我們必須學會檢查三件事情：

1. 規格（Specification）： 原本要求它做什麼？
2. 變更（Diff）： 它實際修改了什麼？
3. 證據（Evidence）： 有什麼測試或操作結果，證明修改符合要求？

最後，才決定接受、要求修正，或延後處理。

## 一、先用生活案例理解：為什麼不能只相信「做完了」？

假設你請裝潢公司幫你重新裝修廚房。

你提出三項要求：

- 更換水龍頭。
- 修復漏水的水管。
- 不可以動到原本的電線配置。

三天後，師傅告訴你：

「全部完成了，而且我們測試過，沒有問題。」

你會直接付款驗收嗎？

一般不會。因為你還需要確認：

- 水龍頭是不是真的換了？
- 水管是否真的不再漏水？
- 師傅有沒有擅自修改電線？
- 所謂「測試過」，到底測試了什麼？

這與 AI Coding Agent 完全相同。

一個完整的驗收流程

規格

應該做什麼

Diff

實際改了什麼

證據

是否真的有效

人的審查與決策

接受／要求修正／延後

這個流程適用於很多產業。

| 產業       | 規格        | 變更         | 驗證證據        |
| -------- | --------- | ---------- | ----------- |
| 建築       | 設計圖與合約    | 施工變更紀錄     | 檢驗與試運轉      |
| 醫療行政     | 病歷處理規則    | 系統設定變更     | 合成測試資料與稽核結果 |
| 銀行       | 徵信作業規範    | 審核邏輯修改     | 測試案例及覆核     |
| 軟體開發     | 功能需求與驗收條件 | Git Diff   | 自動測試及實際操作   |
| AI Agent | 任務與授權範圍   | 程式、檔案、設定變動 | 工具紀錄與實測結果   |

這裡有一個很重要的轉變：

我們不是在評估 AI 的回答寫得多漂亮，而是在評估它交付的成果是否有足夠證據支持。

## 二、什麼是 Diff？為什麼 AI 開發一定要看？

Diff 是 Difference 的縮寫，意思是「差異」。

假設你請 AI 修改一段 Python 程式，原本規定每次匯出報告之前，都必須檢查資料。

原始程式：

```
def export_report(record):    validate(record)    return create_report(record)
```

AI 修改後：

```
def export_report(record):    return create_report(record)
```

程式變短了，而且可能仍然可以執行。

但仔細看，AI 把 `validate(record)` 刪掉了。

也就是說，資料即使不完整，也可能被匯出。

這就是 Diff 審查（Diff Review） 的價值。

Git 能把前後版本的差異顯示出來：

```
 def export_report(record):
-    validate(record)
     return create_report(record)
```

這裡的 `-` 代表該行被刪除，`+` 則代表新增的內容。沒有標記的行通常是供你理解的上下文。

因此，審查時不能只問「程式有沒有執行成功」，還要問「修改是否破壞了原本的規則」。

更重要的是，改動的行數不等於風險大小。刪掉一行安全驗證，可能比新增一千行介面程式更危險。

## 三、Git 的三個位置：工作區、暫存區、版本紀錄

這是本節最需要建立的技術基礎。

想像你正在寫一份重要研究報告。

你有一份正式保存的版本、一份準備送出的版本，以及桌面上正在修改的草稿。

Git 的運作概念非常接近。

Working Tree（工作區）

你目前正在編輯的實際檔案，就像桌上的草稿。

git add（選擇要放入下一版的內容）

Staging Area / Index（暫存區）

已挑選、準備提交的檔案內容，就像整理好的送件版本。

git commit（正式建立版本紀錄）

Repository / HEAD（版本紀錄）

Git 保存的提交歷史；HEAD 通常指向目前所在分支的最新提交。

注意，這是方便理解的簡化圖。Git 的實際比較機制並不是單向流程，因為你可以分別修改工作區與暫存區。

此外，還有一種容易被忽略的檔案：

Untracked File（未追蹤檔案），就是新建立、但 Git 尚未納入追蹤的檔案。

例如 AI 自行建立了一個 `tests/test_export.py`，但沒有執行 `git add`，一般 `git diff` 不會顯示該檔案的完整內容。

### 四個重要指令

| Git 指令               | 用白話說明                     |
| -------------------- | ------------------------- |
| `git status --short` | 查看哪些檔案被修改、暫存或尚未追蹤         |
| `git diff`           | 查看工作區相對暫存區、尚未暫存的修改        |
| `git diff --cached`  | 查看暫存區相對最新提交、準備送出的修改       |
| `git diff HEAD`      | 查看目前檔案相對最新提交的差異；仍不涵蓋未追蹤檔案 |

這些比較方式也可在 [Git 官方 git-diff 文件](https://git-scm.com/docs/git-diff?utm_source=chatgpt.com) 中核對。

### 實際操作示範

假設 AI 完成程式修改，你在專案目錄執行：

```
git status --short
```

可能得到：

```
 M app.py
M  rules.py
?? tests/
```

這些符號可以這樣理解：

` M app.py` 代表工作區中的 `app.py` 已修改，但尚未暫存。

`M  rules.py` 代表 `rules.py` 有修改已經放進暫存區。

`?? tests/` 代表 `tests/` 目錄內存在未追蹤檔案。

現在你只執行：

```
git diff
```

可能只看得到 `app.py` 的修改。

如果因此認為 `rules.py` 與 `tests/` 沒問題，就會漏掉尚未審查的內容。

所以完整的基本審查應包含：

```
# 查看狀態
git status --short

# 查看尚未暫存的修改
git diff

# 查看已暫存的修改
git diff --cached

# 查看最新提交以來的已追蹤檔案差異
git diff HEAD
```

還需要打開未追蹤檔案，檢查內容。

如果 Agent 已經自行提交，工作區可能完全乾淨。這時還要檢查提交紀錄，例如 `git log` 與 `git show`，不能把「沒有未提交變更」誤認成「Agent 沒改過東西」。

## 四、工具紀錄：AI 說測試成功，究竟測試了什麼？

這是第二個容易犯錯的地方。

假設你請 AI 建立一套線上報名系統，包含表單填寫、資料檢查和報名證明下載。

AI 回覆：

> 功能已完成，測試全部通過。

但你打開工具執行紀錄，發現的是：

```
工作目錄：/project/slices/01-form

執行命令：
python -m pytest -q

退出碼：0

輸出：
4 passed in 0.18s
```

以上為假設的教學紀錄，不是實際執行結果。

這份紀錄能證明什麼？

它能證明在該目錄執行的 pytest 命令成功結束，而且有四個測試通過。

但它不能證明下載功能正確，因為這個目錄可能只有表單測試，沒有任何匯出測試。

這裡需要認識四個概念：

| 專有名詞              | 白話解釋                         |
| ----------------- | ---------------------------- |
| Command           | 實際執行的命令                      |
| Working Directory | 命令在哪個資料夾執行                   |
| Exit Code         | 程式結束時回傳的狀態碼，通常 0 表示命令成功      |
| Test Coverage     | 測試涵蓋到哪些程式或行為；通過測試不代表所有需求都已驗證 |

因此，真正要確認的是「證據是否支持 AI 所提出的主張」。

證據強度的差別

| AI 說法  | 實際證據               | 可合理判斷     |
| ------ | ------------------ | --------- |
| 程式已完成  | 只有文字摘要             | 尚未證實      |
| 測試成功   | 表單測試 4 passed      | 僅證明該批測試通過 |
| 匯出功能正確 | 匯出測試通過，且實際下載內容核對正確 | 有較直接的支持證據 |

想想看，這和科學研究非常接近。

研究者說「我的方法有效」，你不能只看結論，而要確認實驗條件、資料集、指標和結果。

AI Agent 的工具紀錄，其實就像研究實驗中的執行紀錄。

## 五、超出任務範圍的修改，為什麼也是問題？

假設你經營一間診所，請工程師修改預約系統的日期顯示。

原本要求很單純：把日期從美式格式改成臺灣常用格式。

但 AI 修改程式時，順便加入了一個外部分析 API，將預約資料傳送到第三方服務。

即使日期顯示正確，也不能直接接受。

因為外部 API 並不是你授權的功能，而且可能產生資料外傳風險。

這涉及兩個原則。

Scope（工作範圍）： AI 只能在本次核准的任務邊界內工作。合理的實作細節可以審查後接受，但新增資料傳輸、權限或業務行為應另行核准。

Least Privilege（最小權限）： AI 應只有完成任務需要的工具、資源與權限，而不是可以任意修改所有系統。

OWASP 的 AI Agent Security 指南，也將工具權限、人工核准、敏感資料保護與可觀測性列為重要控制。

[image](https://www.google.com/s2/favicons?domain=https://cheatsheetseries.owasp.org\&sz=32)

OWASP Cheat Sheet Series



這裡還有一個容易忽略的問題。

發現 AI 修改了不該修改的內容時，不應立即使用可能清除所有未提交工作的命令，例如：

```
git reset --hard
git clean -fd
```

這些命令具有破壞性，可能連其他人尚未保存的工作也一起清除。

較安全的方向是先確認哪些內容屬於本次 Agent 新增，再針對特定檔案或修改範圍處理，保留無關工作。

## 六、實際建立一套 AI Agent 審查流程

把前面的觀念整合起來，你可以在每次 AI Coding Agent 完成任務後，依照下面的流程進行。

1. 核對規格

   確認這次要完成的功能、驗收條件、不允許修改的範圍。
2. 檢查檔案變更

   查看工作區、暫存區、未追蹤檔案，必要時還要查看 Agent 已建立的提交紀錄。
3. 檢查工具紀錄

   確認實際執行的命令、所在目錄、退出碼、輸出與未執行事項。
4. 獨立驗證行為

   執行與需求直接相關的正常、錯誤及邊界測試，必要時進行人工操作。
5. 留下決策紀錄

   寫下接受、要求修正或延後的理由，以及尚未解決的風險。

review-notes.md — 範例

&#x20;複製

以下內容全為示例，不能視為已實測結果。

任務： 資料檢核與報告匯出

驗收要求： 缺漏資料不得產生完整報告。

修改檔案： `app.py`、`rules.py`、`tests/`

實際工具結果： 在表單切片執行 pytest，4 個測試通過。

發現問題： 匯出時的重新驗證被移除；尚無證據顯示下載內容經過驗證。

決策：要求修正

理由： 不符合驗收規格，而且現有測試不足以證明匯出功能正確。

這份紀錄的目的不是增加文書工作，而是讓下一位接手的人能直接知道：哪些事情已證實、哪些尚未驗證，以及決策的根據。

## 七、再深入一層：AI Agent 審查的三種決策

| 決策           | 適用條件                | 後續行動        |
| ------------ | ------------------- | ----------- |
| 接受（Accept）   | 符合規格、修改範圍合理、關鍵測試通過  | 進入提交或交付流程   |
| 要求修正（Revise） | 核心規格未達成、測試不足或包含不當修改 | 限定範圍重新修改、驗證 |
| 延後（Defer）    | 發現新需求，但不屬於本次核准範圍    | 記錄為新的需求或任務  |

這裡最重要的觀念，是不要把「發現新需求」與「修復原本承諾的功能」混在一起。

例如你請 AI 做一個餐廳訂位系統，它發現可以順便加上會員推薦功能。

會員推薦可能是一個很好的想法，但不是這一次訂位系統的驗收條件。

因此可以將推薦功能延後，而不是因為 AI 已經實作就直接接受。

## 八、五個常見誤區

| 常見想法                  | 正確理解                        |
| --------------------- | --------------------------- |
| `git diff` 沒輸出，所以沒有修改 | 還可能有已暫存、未追蹤或已提交的變更          |
| 測試全綠，代表整套系統沒問題        | 只能支持測試實際涵蓋的範圍               |
| 只改一行，風險應該很小           | 一行就可能關閉重要驗證                 |
| AI 多做功能代表更好           | 多做的內容可能超出授權與需求              |
| Git 沒有顯示變更，代表系統沒有副作用  | 程式也可能修改資料庫、呼叫外部 API 或影響遠端服務 |

最後一點尤其值得注意：Git 主要追蹤版本控制範圍內的檔案內容，不會自動替你記錄所有外部系統的變化。

因此，風險較高的 Agent 不只要審查程式差異，還需要適當的執行紀錄、權限控制與外部操作稽核。

## 九、理解檢核：你會如何審查這個 Agent？

假設你請 AI 修改一套保險理賠系統，需求為：

「如果申請人缺少必要證明文件，系統不得產生顯示『審核完成』的報告。」

AI 回覆：「功能已完成，所有測試通過。」

你調查後得到這些資訊：

```
git status --short

 M app.py
M  rules.py
?? tests/
```

工具紀錄顯示：

```
工作目錄：/project/slices/01-form
命令：python -m pytest -q
結果：5 passed
```

另外，你在 `rules.py` 的 Diff 中發現，原本匯出前的 `validate()` 被移除。

第一題：你會先檢查哪些 Git 位置？為什麼只執行 git diff 不夠？

第二題：5 passed 能否證明報告匯出正確？你還需要什麼證據？

第三題：你會接受、要求修正還是延後？請說明具體原因。

提交回答並取得逐題解析&#x20;

這一節的核心可以濃縮成一句話：

AI Agent 交付的是一項待驗收的工作，而不是一個應該直接相信的答案。規格說明承諾，Diff 呈現變更，工具與測試提供證據，最後由負責人做出可追溯的決策。
