# AASE M05-03｜Given／When／Then 與負向驗收：如何確認軟體真的符合需求？

你提供的網址有一個路徑錯誤：`M05-03` 應該放在 `m05`，而不是 `m04` 目錄。

正確教材：[M05-03｜Given／When／Then 與負向驗收](https://learn.cs-kairos.com/courses/aase/v1/m05/concepts/m05-03/?utm_source=chatgpt.com)。

這堂課屬於「規格驅動軟體開發」（Specification-Driven Development）。它要解決一個軟體開發中很常見的問題：

我們明明告訴工程師或 AI 要做什麼，為什麼做出來的系統，卻不一定是我們真正想要的？

原因之一，是我們常常只描述「要有哪些功能」，卻沒有清楚定義「怎樣才算正確，以及什麼情況下必須拒絕」。

這堂課的核心，就是學會把模糊的需求，轉成任何工程師、AI Coding Agent 或測試人員都能共同理解、實際執行的驗收條件。

## 一、先理解 Given／When／Then 到底是什麼

想像你去餐廳點餐。

你告訴服務生：「我要一份牛排，不要洋蔥。」

餐點送來後，你發現牛排有洋蔥。服務生說：「可是牛排確實做出來了。」

這時候，問題不在於餐廳有沒有完成「製作牛排」這個功能，而在於餐廳沒有遵守你真正提出的條件。

軟體開發也是如此。

我們不能只說「做一個訂餐系統」，還必須說清楚，當使用者做出某種操作時，系統在特定條件下應該產生什麼結果。

這就是 Given／When／Then 的用途。

Given — 假設／前置條件

開始前

顧客已選擇牛排，但尚未填寫外送地址。

When — 當／觸發動作

操作時

顧客按下「確認訂單」。

Then — 那麼／預期結果

操作後

系統提示「請填寫外送地址」，不得建立正式訂單，且保留已選餐點。

這三個關鍵字其實就是在問三件事：

| 關鍵字   | 白話意思      | 要回答的問題       |
| ----- | --------- | ------------ |
| Given | 原本是什麼情況？  | 系統開始時具備哪些條件？ |
| When  | 發生了什麼事？   | 誰做了什麼操作？     |
| Then  | 應該產生什麼結果？ | 怎樣才算成功或正確拒絕？ |

這種描述方式常用於 BDD（Behavior-Driven Development，行為驅動開發）。其中 Gherkin 是用來描述這些行為情境的結構化語法；Cucumber 則是能把情境連結到自動化測試程式的工具之一。

## 二、為什麼不能只寫「系統要正常運作」？

假設你請 AI 做一個銀行匯款系統。

你提出的需求是：

「讓客戶可以轉帳，系統要安全。」

這樣的要求看似合理，但不夠明確。

如果 AI 做出一個按下轉帳就顯示「成功」的畫面，究竟算不算完成？沒有真的扣款呢？扣款兩次呢？餘額不足還是允許轉帳呢？

因此，我們需要把需求變成可判斷的規則。

以一個簡化的示範匯款系統為例：

```
Scenario: 餘額不足時不得轉帳

Given 我的帳戶有 1,000 元
When 我要求轉帳 1,500 元
Then 系統應拒絕這筆轉帳
And 顯示「餘額不足」
And 我的帳戶餘額仍為 1,000 元
And 收款人帳戶不得增加 1,500 元
```

這裡又多了 `And`，意思是「而且」，可以補充其他必須同時成立的條件。

你會發現，一個簡單的轉帳要求，至少包含四個驗收重點：拒絕交易、顯示原因、不得扣款、不得入帳。

好的驗收情境，不只是說系統應該做什麼，也要明確說出不應該發生什麼。

## 三、正向驗收與負向驗收的差別

這是本課最重要的概念。

正向驗收（Positive Acceptance）就是檢查：條件都正確的時候，系統能不能完成工作。

負向驗收（Negative Acceptance）則是檢查：條件不正確、資料有問題或權限不足的時候，系統能不能安全地拒絕、阻止或處理異常。

| 行業       | 正向驗收        | 負向驗收             |
| -------- | ----------- | ---------------- |
| 電子商務     | 庫存足夠時成功下單   | 庫存不足時不得承諾出貨      |
| 銀行       | 餘額足夠時完成合法轉帳 | 餘額不足時不得扣款或入帳     |
| 醫療       | 合格人員可讀取授權病歷 | 未授權人員不得取得病歷內容    |
| 人力資源     | 員工可查看自己的薪資單 | 不得查看其他員工的薪資      |
| 教育       | 達到修課條件可完成選課 | 未修完先修課程不得選入限制課程  |
| AI Agent | 合法工作指令可執行   | 超出工具權限時不得執行受保護操作 |

負向驗收並不是故意讓系統失敗，而是在確認系統遇到不正確情況時，仍然遵守規則。

### 特別重要：顯示錯誤，不代表真的阻止錯誤

假設某醫療系統不允許一般行政人員下載完整病歷。

當行政人員按下下載時，系統畫面顯示：

「您沒有權限。」

但如果檔案已經透過 API 回傳，只是前端沒有顯示下載按鈕，這樣仍然是不安全的。

因為我們真正需要驗證的是：

- 使用者沒有取得檔案內容。
- 伺服器確實拒絕了未授權的要求。
- 不得透過其他介面繞過授權檢查。

所以，負向驗收要同時觀察兩個層面：使用者看到的結果，以及受保護的動作是否真的被阻止。

## 四、教材的四大驗收情境

現在回到原本 M05-03 的教學重點。

教材採用一個合成的收件檢核系統，假設表單有三個必要欄位：申請編號、申請人代號、文件類型。

它設計四個不同情境。

[image](https://www.google.com/s2/favicons?domain=https://learn.cs-kairos.com\&sz=32)

CS Kairos Learn



情境 A：完整資料

三個欄位都有有效內容，使用者按下檢查。系統應通過完整性檢核，允許預覽與匯出同一筆資料的報告。

情境 B：缺少必要欄位

文件類型沒有填寫。系統必須指出缺漏，禁止匯出標記為完整的報告，同時保留使用者已填的資料。

情境 C：輸入只有空白字元

申請人代號輸入了三個空格。雖然文字欄位不一定是空字串，但清除前後空白後沒有有效內容，仍應視為缺漏。

情境 D：先前通過，但資料後來改變

使用者先通過檢查，之後卻刪除了文件類型。原本通過的結果應立即失效，不得直接使用舊的成功狀態匯出。

其中情境 D 很值得深入理解。

假設一筆銀行徵信資料，上午 10 點經過檢核，符合所有條件；上午 10 點 5 分有人修改了重要欄位；10 點 10 分另一個人準備匯出報告。

如果系統仍然沿用 10 點的檢核結果，這個結果可能已經不適用。

因此，系統應有機制讓檢核結果與被檢核的資料版本相對應，在匯出時重新確認其有效性。

這也涉及軟體安全中常見的 TOCTOU（Time-of-Check to Time-of-Use，檢查與使用之間的時間差）問題。它的核心是：某件事情在檢查時成立，不代表在真正使用時仍然成立。

## 五、如何把驗收情境交給 AI Coding Agent？

這個概念和 AI 協作開發非常有關係。

不好的指令可能是：

> 幫我做一個資料檢查功能，讓使用者可以匯出報告。

這種指令讓 AI 有很大的自行解釋空間。

比較好的做法，是先把需求與驗收情境寫進 `spec.md`。

以下是簡化的文件範例：

```
# 收件完整性檢核規格

## 業務規則
三個必要欄位都必須有非空白值，
才能將報告標記為完整並匯出。

## Scenario A：資料完整
Given 三個必要欄位皆有有效值
When 使用者要求檢查並匯出
Then 顯示完整性通過
And 允許匯出目前資料的報告

## Scenario B：資料缺漏
Given 文件類型為空
When 使用者要求匯出
Then 顯示文件類型缺漏
And 不得匯出完整報告
And 保留其他已填資料

## Scenario C：空白輸入
Given 申請人代號僅含空白字元
When 使用者按下檢查
Then 將此欄位視為缺漏
And 不得標記完整

## Scenario D：檢核結果過期
Given 先前的資料已通過檢核
And 使用者後來清空文件類型
When 使用者要求匯出
Then 原先的檢核結果不得繼續使用
And 必須檢查目前的資料
And 不得匯出完整報告
```

接著可以要求 AI：

「請依據 `spec.md` 實作這個功能，為四個情境建立相對應的測試。不要自行放寬必要欄位的規則，完成後提供實際測試結果與程式碼差異。」

這時 `spec.md` 就像工程師與 AI 共同遵守的契約。

不過要注意，寫出 Gherkin 或 Markdown 情境，不代表測試已經自動執行。如果要使用 Cucumber 自動測試，還需要 Step Definitions（步驟定義），把自然語言連接到實際測試程式。也可以用 pytest、介面測試等方式實作相同的驗收要求。

## 六、如何判斷驗收條件寫得好不好？

用下面這個判斷表即可。

| 品質檢查    | 不好的例子     | 較好的例子          |
| ------- | --------- | -------------- |
| 是否具體    | 系統必須好用    | 缺漏時明確指出欄位      |
| 是否可觀察   | 系統正確處理請求  | 回傳拒絕結果，且不建立訂單  |
| 是否含禁止行為 | 顯示錯誤文字    | 不得匯出完整報告       |
| 是否能重演   | 當使用者資料有問題 | 當文件類型為空字串      |
| 是否與實作分離 | 第三個按鈕要變綠  | 檢查通過時允許匯出      |
| 是否有證據   | 測試應該成功    | 記錄測試名稱、執行結果與版本 |

最後一個尤其重要。

即使你寫了十條驗收情境，也只能證明你定義了應該如何驗收，不能證明系統已經通過驗收。

實務上，應建立：

需求（Requirement）

驗收情境（Acceptance Scenario）

測試案例（Test Case）

執行結果（Test Result）

可查核證據（Evidence）

例如，規格要求不得匯出不完整報告，對應的測試就必須實際嘗試匯出，並確認沒有產生或交付被標記為完整的報告。證據應記錄測試的版本、命令與結果，而非只有 AI 說「測試通過」。

這就是從「我們希望系統正確」走向「我們有證據支持系統符合要求」。

## 七、理解檢核：用一個新的產業情境練習

某醫院開發了一套 AI 輔助檢查報告系統。

醫師可以上傳檢查資料，由 AI 產生報告草稿。醫院規定，AI 草稿必須經過合格醫師確認，才可以成為正式報告。

目前工程師提出這條驗收：

```
Given AI 已產生檢查報告
When 使用者按下送出
Then 系統顯示成功
```

問題一：這條驗收最嚴重的缺陷是什麼？

沒有確認正式報告是否經過合格醫師核准。

沒有指定按鈕應該使用什麼顏色。

沒有指定 AI 必須使用哪一個語言模型。

沒有指定報告必須使用 PDF 格式。

問題二：請自行寫一條負向驗收的 Then。

提交答案並請你批改

這堂課最值得記住的一句話是：

寫程式是在告訴電腦怎麼做；寫驗收情境是在告訴所有參與者，什麼結果才算做對，以及什麼錯誤絕不能發生。

當這些條件寫清楚，無論採用哪種程式語言、框架，或更換哪個 AI Coding Agent，都能依據相同的外部行為要求來驗證成果。
