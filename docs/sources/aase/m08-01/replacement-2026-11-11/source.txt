# M08-01｜能執行，不代表已驗證：如何證明軟體真的完成了？

AASE · M08 測試、品質與安全驗證

這一節最重要的觀念是：

「程式能跑」只代表它可以執行；「程式完成」則需要證據，證明它在指定條件下符合需求。

舉例來說，你請 AI 幫你開發一套醫院掛號系統。AI 告訴你：「已經完成，網站可以正常開啟。」

但這並不能證明病人真的能順利掛號、醫師不會重複預約、病歷不會被其他病人看到。

本節要學的，就是如何從「相信程式能用」，進步到「拿出可以核對的證據」。

假設你買了一輛新車，業務員發動引擎，對你說：「車子完成檢查了，可以放心上路。」

你應該會有疑問：

- 引擎能啟動，但煞車有效嗎？
- 煞車正常，但下雨天會打滑嗎？
- 車輛正常行駛，但發生撞擊時能保護乘客嗎？
- 所有零件正常，駕駛是否看得懂儀表板？

這些都是不同的問題，必須用不同方式驗證。

軟體也是一樣。

AI 幫你產生一千行程式碼，沒有發生錯誤，網站也能打開，不代表程式符合你的需求。

這就帶出本節第一個核心觀念：

每一種品質主張，都要有對應的驗證證據。不能用一種測試通過，代替其他測試。

## 二、軟體品質要從五個面向檢查

這是整堂課最值得記住的架構。

需求規格（Specification）

先說清楚：軟體應該做到什麼？

01

啟動驗證

程式能不能運行？

02

規則驗證

計算和判斷對不對？

03

介面驗證

操作、提示和輸出正確嗎？

04

任務驗證

真人能完成工作嗎？

05

安全驗證

不應該發生的事情，系統有沒有阻止？

五個面向是互補關係，不代表必須照圖示順序測試，也不能相互取代。

### 第一層：啟動驗證（Smoke Test）

這是最基本的檢查。

例如，你開發了一家餐廳的線上訂位系統，測試人員打開網頁，發現：

- 網站正常顯示。
- 伺服器沒有當機。
- 可以看到日期及訂位按鈕。

可以說：「系統在這個測試環境成功啟動。」

但不能說：「訂位系統已經完成。」

因為你還不知道，兩個客人同時預訂最後一個位置時，會不會重複訂位。

### 第二層：規則驗證（Business Rule Testing）

這一層檢查的是業務邏輯。

以網路購物為例：

假設規格寫著：「訂單金額滿 1,000 元，運費免費。」

測試人員就必須驗證：

| 購物金額    | 預期運費   |
| ------- | ------ |
| 999 元   | 依規定收運費 |
| 1,000 元 | 免費     |
| 1,001 元 | 免費     |

為什麼特別測 999、1,000、1,001？

因為這是邊界值測試（Boundary Value Testing）。

錯誤經常發生在條件交界處。例如工程師把「大於或等於 1,000」寫成「大於 1,000」，剛好購買 1,000 元的客人就被收取運費。

這些規則測試可以用 `pytest` 等工具自動執行，但測試的好壞取決於案例是否真正涵蓋重要需求，而不是通過了多少題。

[image](https://www.google.com/s2/favicons?domain=https://docs.pytest.org\&sz=32)

pytest documentation



### 第三層：介面驗證（UI Testing）

即使後端計算正確，前端也可能出錯。

例如銀行轉帳系統：

後端正確判斷餘額不足，拒絕轉帳；但前端卻顯示「轉帳成功」。

這就是後端規則正確、介面行為錯誤的典型例子。

因此要檢查：使用者看見什麼訊息、按鈕何時可以使用、資料修改後畫面是否同步更新，以及下載檔案的內容是否正確。

教材提到的 Streamlit AppTest，可以模擬 Streamlit 應用程式的互動、檢查介面元件狀態。不過，AppTest 測到下載按鈕存在，不等於真實瀏覽器的下載流程及檔案內容已通過驗證。

[image](https://www.google.com/s2/favicons?domain=https://docs.streamlit.io\&sz=32)

Streamlit Docs



### 第四層：使用者任務驗證（Task-based Usability Testing）

這層最容易被技術人員忽略。

假設你設計了一套醫院掛號系統，所有程式測試都通過。

但你請一位第一次使用系統的病人完成掛號，發現他不知道：

- 要先選科別還是醫師。
- 為什麼掛號按鈕無法點擊。
- 掛號完成後，在哪裡查詢結果。

這些問題不一定是程式 Bug，而是\*\*易用性（Usability）\*\*問題。

因此，任務測試不是問使用者「這套系統好不好看」，而是指定一個真實目標，觀察他能不能完成、在哪裡卡住、是否需要別人協助。

GOV.UK 的使用者研究指引也強調透過觀察實際任務理解使用障礙。

[image](https://www.google.com/s2/favicons?domain=https://www.gov.uk\&sz=32)

GOV.UK



### 第五層：安全驗證（Security Testing）

假設你做了一套學生學習平台。

學生 A 登入後，可以看到自己的成績。這代表正常功能可能運作了。

但是，如果 A 只要修改網址中的學生編號，就能看到學生 B 的成績，代表系統存在授權控制問題。

這裡需要分清楚兩個專有名詞：

- Authentication（身分驗證）：確認你是誰，例如登入帳號。
- Authorization（授權）：確認你有沒有權限看這筆資料。

通過登入檢查，不代表有權限查看每一筆資料。OWASP 建議以最小權限、預設拒絕，以及針對每次請求檢查授權等方式建立控制。

[image](https://www.google.com/s2/favicons?domain=https://cheatsheetseries.owasp.org\&sz=32)

OWASP Cheat Sheet Series



而且，不能只是「測試沒有被攻破」就宣稱完全安全。必須說明測試過哪些情境、哪些防護已實作、哪些風險仍然待驗。

## 三、最重要的思考方式：主張、證據、限制

以「發票自動記帳系統」為例。

假設工程師報告：「發票功能已經完成。」

這句話太模糊了。

你應該拆成可以驗證的具體主張。

範例證據矩陣（以下均是假設情境，不是實際測試結果）

| 完成主張     | 應該提供的證據     | 不能據此證明     |
| -------- | ----------- | ---------- |
| 系統可以啟動   | 啟動紀錄、畫面     | 金額計算正確     |
| 發票金額正確   | 對照已知答案的規則測試 | 介面沒有錯誤     |
| 遺漏欄位不能記帳 | 缺漏資料被拒絕的測試  | 所有異常均已涵蓋   |
| 使用者能修正錯誤 | 實際操作的任務紀錄   | 所有人都容易操作   |
| 他人不能讀取發票 | 跨帳號存取遭拒的測試  | 所有安全風險均不存在 |

這張表非常重要，因為它讓系統品質從「個人感覺」變成「可以審查的證據」。

我們可以進一步把它濃縮成一個原則：

完成主張 → 對應規格 → 驗證方法 → 實際結果 → 尚未涵蓋的範圍。

## 四、把課程觀念轉換成實際開發流程

教材使用 `spec.md`、測試結果，以及 `verification-notes.md` 來管理驗證紀錄。

假設我們正在開發一套文件上傳系統。

### 步驟一：先寫明確的驗收規格

不要只寫：

「使用者可以上傳文件。」

應該改成：

「當必要欄位缺漏時，系統必須顯示缺漏原因，不得產生完整報告。」

這樣才知道要測什麼。

### 步驟二：設計正常及異常情境

使用 Given–When–Then：

- Given：使用者上傳的文件缺少身分識別欄位。
- When：使用者按下「匯出報告」。
- Then：系統拒絕匯出，並提示缺漏欄位。

接著，再補上完整資料、空白資料、格式錯誤、過期資料等情境。

### 步驟三：執行測試並記下實際結果

不要只記「通過」。

至少記錄：

- 測試的程式版本（Commit）。
- 使用的環境。
- 輸入資料與預期結果。
- 真正觀察到的輸出。
- 測試狀態。

這樣其他人才能重新執行並核對。

### 步驟四：誠實區分三種狀態

通過（Pass）

已執行，結果符合預期，但只適用於已測試的版本及條件。

失敗（Fail）

已執行，但觀察結果不符合預期，應保留失敗證據。

待驗（Not Tested）

沒有執行，或缺少足夠證據，不能自行假設通過。

### 步驟五：建立驗證紀錄

你可以在 `verification-notes.md` 中，留下這樣的紀錄：

```

# 驗證紀錄

## 驗收項目
必要欄位缺漏時，不得匯出完整報告。

## 測試環境
版本：commit abc123（示例）
環境：本機測試環境

## 測試輸入
缺少身分識別欄位的合成文件。

## 預期結果
系統拒絕匯出，顯示缺漏原因。

## 實際結果
待執行測試後填寫。

## 狀態
待驗

## 下一步
執行規則測試、介面測試，
並以真實瀏覽器確認下載行為。

```

這份紀錄最有價值的地方，不是文件寫得漂亮，而是不論誰接手，都能知道目前已經證明什麼、還缺少什麼證據。

## 五、為什麼 AI Coding 特別需要這套方法？

傳統軟體開發中，工程師可能親自編寫每一行程式，對其邏輯有一定程度的掌握。

但使用 AI Coding Agent 時，你可能只下達一段需求：

「請幫我完成發票辨識、金額核算及資料匯出功能。」

Agent 很快就修改十幾個檔案，並回答：

> Implementation completed. All tests passed.

這不等於你的需求已經驗證完成。

至少有四種可能：

1. Agent 只測試自己新增的功能，沒有測試既有功能是否壞掉。
2. 測試案例由 Agent 自己編寫，但測試沒有涵蓋真正的業務需求。
3. 測試只使用理想資料，沒有檢查異常、邊界與惡意輸入。
4. 測試在 Agent 的開發環境通過，正式環境卻存在不同設定與權限。

所以 AI 協作開發真正值得建立的是：

人類定義需求與驗收標準

AI Agent 實作程式與測試

工具與真人蒐集驗證證據

依據證據決定是否驗收、修正或保留待驗

這也是 M08-01 與前面 M05（規格驅動開發）及 M07（AI Coding Agent 協作）的關鍵連結：

Spec 決定什麼叫完成；Agent 負責實作；Verification 負責提出可以檢查的完成證據。

## 六、再補一個進階觀念：Verification 與 Validation

這兩個詞容易混淆。

Verification（符合規格的驗證）：我們是否把規格要求的東西做對了？

Validation（需求適切性的確認）：我們做出來的東西，是否真的滿足使用情境與使用者需求？

例如物流公司開發路線規劃系統：

系統依照規格，找出距離最短的路線。演算法測試全部通過，這是符合規格的證據。

但實際司機發現，最短路線經常有大型貨車無法通行的巷道。

因此，即使 Verification 通過，Validation 仍然可能失敗。

這不表示前面的測試毫無價值，而是說明原始需求可能沒有涵蓋真正重要的使用條件。

這個觀念能幫助我們避免一個重大陷阱：把錯誤的規格實作得非常完美。

最後記住一句話：

測試不是為了證明自己做得很好，而是為了清楚知道哪些事情已被證明、哪些事情還不能保證。
