# M04-05｜漸進揭露、極簡與必要狀態

這一課最重要的觀念：好的使用者介面，不是把資訊減到最少，而是讓使用者在正確的時間，看見正確的資訊，做出正確的決定。

想像你到醫院掛號、使用 ATM 提款，或在購物網站付款。你通常不想知道系統內部有幾台伺服器、資料庫如何運作、程式有哪些參數。你只想知道：

- 我現在需要做什麼？
- 系統目前正在做什麼？
- 有沒有問題？問題該怎麼解決？
- 我究竟完成了沒有？

這正是本課的三個核心觀念：Progressive Disclosure（漸進揭露）、Minimalist Design（極簡設計）和 Visibility of System Status（系統狀態可見性）。

原始教材以資料檢核網站為例，要求完成四種狀態的 Wireframe（介面線框圖），並透過實際任務觀察檢查設計。

## 二、極簡設計（Minimalist Design）不是把東西全部藏起來

想像你在機場看登機資訊螢幕。

你需要知道登機門、起飛時間，以及航班有沒有延誤。假如設計師認為畫面越乾淨越好，把「航班延誤」隱藏在詳細資訊頁面，你可能就會錯過重要通知。

這就是錯誤的極簡設計。

正確的極簡設計，是減少對當前任務無用的資訊，而不是減少所有資訊。

用下面這個判斷表：

| 資訊類型           | 應該怎麼呈現？   |
| -------------- | --------- |
| 目前任務不可缺少的資訊    | 直接顯示      |
| 影響安全、風險或下一步的資訊 | 直接顯示、明確提示 |
| 少數情境才需要的功能     | 放在進階設定    |
| 系統內部診斷或開發資訊    | 放在管理或除錯介面 |

例如線上銀行轉帳，收款帳號、金額、手續費及轉帳結果應該清楚呈現。資料庫連線池、API Timeout 設定等開發資訊，則不需要出現在一般使用者畫面上。

這也符合 Nielsen Norman Group 的「Aesthetic and Minimalist Design」原則：不相關的資訊會與真正重要的資訊爭奪使用者注意力。

記憶口訣：不影響當下決策的資訊可以延後；影響使用者判斷、風險或行動的資訊不能隨便隱藏。

## 三、必要狀態：使用者必須知道系統現在發生什麼

這是整堂課最容易被低估、但非常重要的部分。

假設你去 ATM 提款，按下「提款 5,000 元」之後，螢幕完全沒有反應。

你會怎麼想？

你可能懷疑自己沒有按到，於是再按一次。或者以為機器故障，準備離開。

真正的問題不一定是系統沒有處理，而是系統沒有告訴你正在處理。

這就是 Visibility of System Status（系統狀態可見性）。

一個介面至少要讓使用者理解「目前狀態、操作結果、可以採取的下一步」。

@figure5

這裡有兩個重要細節。

第一，資料缺漏與系統故障不是同一件事。缺少文件類型，應提示補資料；如果是伺服器無法連線，應提示系統檢查失敗、如何安全重試，而不是誤導使用者重新填寫資料。

第二，「完成」一定要說清楚完成了什麼。資料檢核通過，不代表政府機關正式收件；銀行文件生成成功，不代表授信審核通過；AI 診斷報告產生完成，也不代表醫師已經確認。

這是 UX 與系統業務規則（Business Rules）必須一致的地方。

## 四、跨產業比較：同一原理可以怎麼應用？

先看六種產業的當前決策，再比較哪些資訊可延後。

| 產業情境    | 主要資訊（必須看得到）       | 可以延後的資訊        |
| ------- | ----------------- | -------------- |
| 電商購物    | 商品價格、運費、付款結果、訂單狀態 | 商品內部編碼、進階推薦設定  |
| 醫療掛號    | 科別、日期、看診號碼、掛號是否成功 | 系統連線診斷、管理者設定   |
| 銀行轉帳    | 收款人、帳號、金額、交易結果    | API 診斷、系統日誌    |
| 工廠設備    | 運作狀態、危險警報、緊急停止    | 非必要的細部診斷參數     |
| AI 文件分析 | 上傳狀態、分析進度、缺漏、結果   | 模型溫度、除錯日誌、輪詢參數 |
| 網路資安    | 重大告警、風險、待處置事項     | 低階封包細節、開發偵錯資訊  |

不過，有一個例外非常重要：資訊是否重要，取決於使用者的角色與當前任務。

對一般銀行客戶而言，API 診斷資訊不重要；但對正在排查轉帳系統故障的工程師而言，它可能是主畫面最重要的資訊。

因此，不能用同一套極簡介面服務所有角色。你必須先問：「這個畫面給誰用？他現在需要做什麼決定？」

## 五、兩種容易混淆的設計：漸進揭露與分階段揭露

這裡再補充一個原教材沒有大篇幅展開，但實務上很容易混淆的觀念：Staged Disclosure（分階段揭露）。

| 比較面向           | 漸進揭露           | 分階段揭露          |
| -------------- | -------------- | -------------- |
| 核心思想           | 先顯示常用功能，隱藏次要功能 | 把必要工作分成多個步驟    |
| 例子             | 列印時展開進階設定      | 網購時依序填地址、付款、確認 |
| 使用者一定要展開後續畫面嗎？ | 通常不用           | 通常需要           |
| 主要目的           | 降低功能複雜度        | 降低單一步驟的資訊負荷    |

兩者可以同時使用。例如購物網站把結帳分成三步驟，並且在運送設定那一步，額外提供「特殊配送選項」。

這種分法來自 Nielsen Norman Group 對兩類設計的區別。

## 六、進階但非常重要：使用者修改資料後，舊結果怎麼辦？

這是從 UI 設計進入軟體工程的關鍵。

假設使用者完成文件檢核，系統已顯示「三個欄位都完整」。但他之後把文件類型刪掉了。

此時如果畫面仍然顯示「檢核通過」，甚至仍然允許匯出，便出現一個問題：

畫面上的成功結果，已經不代表目前資料的真實狀態。

用流程圖來看：

在軟體工程裡，這涉及狀態一致性（State Consistency）及驗證結果是否仍然有效。

一個實用的實作策略是：

```
currentVersion = 3
validatedVersion = 3
→ 可以匯出

使用者修改資料：
currentVersion = 4
validatedVersion = 3
→ 不可直接匯出，需要重新檢核
```

但要特別注意：前端把「匯出」按鈕隱藏，不等於資料真正安全。

如果有人直接呼叫後端 API，後端仍必須檢查資料是否完整、是否有權匯出，以及驗證結果是否對應到當前資料版本。

這也是原教材要求把「輸入變更後舊結果失效」寫進 `spec.md`，並加入測試的原因。

## 七、易用與可近用：不能只靠顏色、圖示和提示字

假設一個表單把錯誤欄位框成紅色，卻沒有說明文字。

有些人可能看不清楚顏色差異；有些人使用螢幕閱讀器；也有些人根本不知道紅框代表什麼。

因此：

不好的設計： 紅框加上一個驚嘆號。

比較好的設計： 在「文件類型」欄位附近顯示「必填欄位，請選擇文件類型」，必要時再搭配紅框。

同樣地，`placeholder`（欄位內的範例提示字）不能取代持續可見的欄位名稱（Label）。使用者開始輸入後，placeholder 往往就消失了。

W3C 的 WCAG 規範也要求不能只用顏色傳達資訊；對於會動態更新的系統狀態，還應讓輔助科技適當得知變化。

## 八、如何驗證介面真的變好？不要只問「好不好看」

這一節最重要的實作觀念，是將主觀印象轉換成可觀察的行為。

假設你做出文件檢核網站的 Wireframe，找一位不熟悉系統的人，給他一筆故意缺少文件類型的模擬資料。

請他完成這個任務：

「確認這份資料能不能交接。如果不能，請修正後匯出。」

在他操作時，你不要直接告訴他錯誤在哪裡，而是觀察他是否自行發現問題、會不會亂點設定、能否理解完成結果，以及修改資料後是否知道需要重新檢查。

可以用以下驗收矩陣，把抽象的 UX 品質轉成實際測試：

| 驗收項目  | 示範驗收標準         |
| ----- | -------------- |
| 狀態辨識  | 能用自己的話說明目前進度   |
| 錯誤修正  | 不需指引就能找到缺漏並修正  |
| 操作保留  | 修正一個欄位不必重填全部   |
| 結果正確性 | 資料變更後不能沿用舊檢核結果 |
| 可近用性  | 不靠顏色或滑鼠懸停也能理解  |

這些是可供試驗的驗收條件，不是已實測的成果。一次同儕測試能發現問題，卻不能證明所有使用者都會有相同體驗。

## 九、這一課實際要完成什麼成果？

原始 M04-05 的交付要求，是四狀態 Wireframe，以及至少一項有觀察依據的介面修正。

最小完成版本可以是一份包含四個畫面的 SVG、Figma 設計稿或紙本草圖。每個畫面都應回答：使用者現在看見什麼、知道什麼、下一步可以做什麼。同時要說明資料變更如何讓舊結果失效，並留下修正前後的比較和匿名觀察紀錄。

你不必在這個階段先把完整前後端寫好。這一課的核心能力是：先確認互動與資訊安排是否合理，再投入軟體實作。

## 十、理解檢核

先不看答案，請嘗試下面三個問題。

問題一｜概念辨識

一個 AI 文件處理系統，主畫面有「上傳檔案、正在處理、處理失敗、模型溫度設定」。如果要採用漸進揭露，哪些內容應直接顯示？哪些可以延後？為什麼？

問題二｜情境應用

銀行轉帳畫面顯示「轉帳完成」，但其實只是請求送到銀行伺服器，交易尚未確認。這違反了什麼設計原則？你會如何修改畫面？

問題三｜工程實務

一份 AI 分析報告檢核通過後，使用者修改了原始資料，但系統仍允許下載舊報告。除了修改 UI，你還需要在後端或測試加入什麼機制？

最後記住這堂課的核心：

極簡設計，是減少不必要的負擔；漸進揭露，是安排資訊出現的時機；必要狀態，是讓使用者永遠知道自己處於什麼情況，以及下一步該怎麼做。

這三件事需要一起設計，才能讓一個軟體不只是「看起來簡單」，而是真正容易理解、操作與信任。
