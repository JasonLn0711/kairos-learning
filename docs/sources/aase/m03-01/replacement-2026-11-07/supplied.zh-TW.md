# AASE M03-01｜從模糊要求寫出問題陳述：白話文完整教學

這一課最重要的觀念是：

不要一聽到別人說想做什麼系統，就立刻開始設計系統。要先搞清楚他究竟遇到了什麼問題。

舉例來說，有人跟你說：

「我想做一個 AI 系統，幫我們提高工作效率。」

這句話聽起來像需求，但其實我們還不知道：

- 誰的工作需要改善？
- 他每天究竟在做什麼？
- 哪個環節讓他感到困難？
- 困難是什麼原因造成的？
- 改善後怎麼知道真的有效？

這就是為什麼軟體工程需要 Problem Statement（問題陳述）。

## 一、問題陳述就像醫生看診：先診斷，再開藥

想像今天有一位病人走進診間，跟醫生說：

「醫生，我想要吃抗生素。」

如果醫生立刻開藥，這是不是很奇怪？

因為醫生根本不知道病人哪裡不舒服，也不知道是不是細菌感染。

專業的醫生會先問：

「你哪裡不舒服？什麼時候開始？有哪些症狀？嚴重程度如何？」

軟體工程也一樣。

醫療診斷

病人說：「我要抗生素。」

先找出症狀與病因，才決定治療方式。

軟體工程

使用者說：「我要 AI 系統。」

先找出工作困難，才決定是否需要 AI。

共同原則：問題先於解決方案（Problem Before Solution）

所以，「我要 AI 系統」是對某種解決方案的期待，不等於已經把問題定義清楚。

而且，最後也許發現根本不需要 AI，只要把原本混亂的表單與檢查規則整理好，問題就能改善。

這也是需求工程（Requirements Engineering）很重要的價值：避免努力做出一個漂亮、卻沒有解決真正問題的系統。

## 二、用五個問題，把模糊要求變成清楚的問題

我們延續課程中的「申請文件收件系統」。

原本有人說：

「我想要一個更好用的 AI 收件系統。」

這時先不要寫程式，而是問五個問題。

PROBLEM STATEMENT FRAMEWORK

1. Who｜誰遇到問題？

   負責交接申請文件的收件人員。
2. When｜什麼時候發生？

   在把文件交給下一位同仁之前。
3. As-Is｜現在怎麼做？

   透過人工清單逐一核對必填欄位。
4. Problem｜究竟有什麼困難？

   可能因為漏看欄位，導致文件交接後才需要補件。這是尚待驗證的假設。
5. Outcome｜希望改善到什麼程度？

   讓收件人員在交接之前，就能找到並修正缺漏。

這五個問題整合後，就可以形成一份初步的問題陳述：

> 收件人員在交接申請文件之前，需要確認必要欄位是否填寫完整。目前透過人工清單檢查，可能存在漏看欄位的情況，造成後續補件。我們希望協助收件人員在交接前辨識並修正缺漏，並透過測試確認改善效果。

請注意，這份問題陳述並沒有規定一定要使用 AI、建立網站或使用哪種程式語言。

這是刻意的。

因為現在要先定義「要解決什麼」，而不是太早決定「要怎麼做」。

## 三、最容易犯的錯：把猜測當成事實

這是本課特別重要的一個概念。

假設你正在觀察收件人員使用系統。

你發現：

「文件類型沒有填寫，但使用者仍然按下匯出。」

這時你可能會認為：

「使用者一定沒有看懂畫面。」

但這真的有證據嗎？

未必。

也許他只是想測試一下系統會不會阻止匯出。

因此，我們需要分成三個層次。

| 層次             | 白話解釋       | 案例                |
| -------------- | ---------- | ----------------- |
| Observation 觀察 | 眼睛實際看到什麼   | 欄位空白，使用者按下匯出      |
| Inference 推論   | 你認為原因可能是什麼 | 他可能不知道欄位沒有填完整     |
| Validation 驗證  | 如何確認猜測是否正確 | 詢問當時想法，或調整提示後重新測試 |

三個層次不能混為一談。

這不只適用於軟體工程，也和科學研究非常相似：

觀察現象 → 提出假說 → 設計實驗 → 取得證據 → 修正假說。

因此，專業的問題陳述不只需要記錄問題，也要說明哪些是已知事實，哪些仍需要驗證。

## 四、什麼叫做「成功」？不能只說效率提高

假設你要求 AI：

「請做一個可以提升效率的收件系統。」

AI 很可能真的做出一套系統。

但你怎麼判斷它成功了？

「看起來很好用」並不是足夠的驗收證據。

我們至少要分成兩個方向。

功能驗收（Functional Acceptance）

確認系統有沒有按照規則運作。例如文件類型空白時，系統必須提示缺漏，並禁止匯出標記為完整的正式報告。

使用者驗收（User Acceptance）

確認使用者實際能不能完成任務。例如收件人員能找到錯誤提示、知道要補什麼，而且能自行完成修正。

兩者都重要。

可能發生一種情況：程式功能完全正常，卻沒有人知道該怎麼使用。

這時候，技術測試可能全部通過，但產品仍然沒有有效解決問題。

另外，如果你要聲稱「效率提升 30%」，就必須有改善前的基準資料、改善後的實測資料，以及合理的比較方法。不能由 AI 自己編一個數字。

## 五、As-Is 與 To-Be：把問題畫成流程

這兩個專有名詞非常常見。

- As-Is：現在實際如何工作。
- To-Be：希望未來如何工作。

As-Is｜目前工作流程

填寫資料

人工檢查

交接文件

假設的痛點：人工核對可能遺漏必填欄位。

To-Be｜期待的新流程

填寫資料

系統檢查必填欄位

有缺漏就提示並修正

預覽、匯出與交接

這樣畫流程的好處，是可以直接看到：我們究竟準備改變哪一個工作環節。

而且 To-Be 只是預期設計，並不是已經證明它比較有效。仍需要後續測試。

## 六、MVP：第一次不要做一個巨大系統

MVP（Minimum Viable Product）可以白話理解成：

先做一個範圍很小，但是能完整走完核心工作，而且足以驗證需求的產品版本。

假設你要做一套收件系統。

你可能會想到要加入 AI、帳號管理、雲端資料庫、權限控制、行動版介面、簽核流程、分析儀表板。

但第一版有必要全部完成嗎？

不一定。

我們先區分：

| 第一版先做   | 第一版暫時不做     |
| ------- | ----------- |
| 填寫合成資料  | 正式業務資料      |
| 必填欄位檢查  | AI 自動判斷文件內容 |
| 缺漏提示與修正 | 多人帳號管理      |
| 預覽與匯出   | 正式簽核、正式部署   |

為什麼？

因為我們現在最想確認的假設是：

「讓收件人員在交接前看到明確的缺漏提示，是否能改善缺漏處理？」

只要能測試這件事，第一版就有價值。

如果後來證實真正的問題是「部門之間對必填欄位的定義不一致」，那麼繼續增加 AI 功能可能沒有幫助，反而要先整理業務規則。

## 七、problem.md 與 spec.md 有什麼差別？

這一部分要和你在 M02 學過的 Coding Agent 接起來。

想像你要讓 AI 幫你開發軟體，最好先準備兩份不同用途的文件。

problem.md

問題文件

為什麼需要做？

誰遇到困難？目前如何工作？想改善什麼？哪些假設還沒證實？

spec.md

規格文件

系統具體要做什麼？

有哪些欄位？如何檢查？錯誤怎麼呈現？如何測試？

例如：

`problem.md` 寫的是：

「收件人員需要在交接前找出缺漏欄位。」

`spec.md` 則可以寫：

「當文件類型欄位為空白時，畫面顯示『請選擇文件類型』，並禁止使用者匯出標記為完整的報告。」

這兩份文件是相互銜接的。

problem.md

定義問題

spec.md

定義行為

Implementation + Tests

實作程式，執行測試並檢查證據

對 Coding Agent 而言，這個順序也很重要。

如果沒有 `problem.md`，AI 可能會自行假設使用者的需求。

如果沒有 `spec.md`，AI 可能知道大概目的，卻不知道具體應該如何實作和驗收。

但即使兩份文件都有，仍然需要人類檢查規格是否正確，以及實際測試結果是否符合需求。

## 八、實際練習：從零建立一份 problem.md

以下是一份精簡的示範，你可以直接看出問題文件大概長什麼樣子。

```
# Problem Statement

## 1. 主要使用者
負責交接申請文件的收件人員。

## 2. 工作情境
在把申請文件交給下一位同仁之前，
需要確認必要欄位是否填寫完整。

## 3. 目前流程（As-Is）
收件人員使用人工清單逐項核對。

## 4. 目前困難
假設：人工檢查可能遺漏必填欄位，
導致交接後仍需要補件。

狀態：尚待訪談確認。

## 5. 期待結果
在交接前發現並修正缺漏資料。

## 6. MVP 範圍
- 輸入合成資料
- 檢查必要欄位
- 顯示缺漏提示
- 修正資料
- 預覽及匯出

## 7. 驗收方向
- 欄位缺漏時正確顯示提示
- 缺漏時不能匯出完整報告
- 資料正確時可預覽和匯出
- 試用者能理解提示並完成修正

## 8. 不包含
- 真實個人資料
- 正式業務簽核
- 多人帳號與權限
- 正式部署

## 9. 待確認問題
- 誰負責制定必填欄位規則？
- 漏填是否確實造成補件？
- 使用者最常在哪個步驟遇到困難？

## 10. 資料來源
課程合成案例，非真實訪談。
```

這份文件最大的價值，不是格式漂亮，而是讓其他人接手時，可以知道：

這個系統為什麼存在、哪些事情已確認、哪些仍是假設，以及第一版做到哪裡就足夠。

往後訪談或測試有新證據，也可以持續修訂。

## 九、這堂課如何連到整個軟體工程？

從 M01 到 M03，可以整理成一條完整的學習主線：

1. M01｜理解軟體工程的目的

   重點是讓使用者完成真正需要的工作，而不只是寫出程式。
2. M02｜理解 AI 如何協助完成工作

   認識 LLM、Context、Tools、Agent Harness、測試與可觀測性。
3. M03｜先定義清楚要做的工作

   將模糊想法變成能訪談、能驗證、能開發的問題與需求。
4. 後續開發與驗收

   依規格實作、測試，並根據證據確認是否解決原本的問題。

這裡有一個更深層的重要觀念：

AI 讓「產生程式」變得更容易，但並沒有自動解決「判斷應該開發什麼」的問題。

甚至因為產生程式太容易，團隊可能更快地做出一大堆其實不需要的功能。

因此，學會問題定義，不是開發前的行政程序，而是避免投入錯誤方向的重要技術能力。

## 十、理解檢核：換你當需求工程師

這裡設計一個小案例，讓你實際練習，而不是只背專有名詞。

案例：一位主管希望建立 AI 報表系統

主管說：「我們每天整理報表太麻煩了，請幫我做一個 AI 自動報表系統，最好有漂亮的 Dashboard。」

問題 1：你應該先做什麼？

先問清楚誰在整理、哪個步驟困難、目前流程如何運作

立刻請 AI 產生 Dashboard

先挑選準確率最高的 LLM

問題 2：主管說「大家都覺得報表很難整理」，你應該如何記錄？

已經證實所有同仁都有相同困難

主管的說法是一項待查證的線索，需要訪談與觀察

代表系統必須使用 AI

問題 3：第一版系統應該怎麼決定範圍？

把 Dashboard、AI、自動化、多部門權限一次完成

先找出核心困難，做足以驗證的最小完整流程

只做漂亮畫面即可，不需要測試

延伸思考：你最想問這位主管的第一個問題是什麼？

提交答案，請你幫我評改&#x20;

這一課的核心成果，就是學會先把「我要一套 AI 系統」轉化成「誰在什麼情境遇到哪個具體問題，我們打算如何驗證改善效果」。

下一課 M03-02 就可以在這個基礎上，進一步辨認 Stakeholders（利害關係人），了解不同角色對同一項工作可能有不同的需求。
