# AASE M01-04｜學員調查也是需求訪談：白話文完整教學

這一課最重要的觀念是：

不要一開始就問別人「你想要什麼功能」，而是先了解「你現在怎麼工作、哪裡遇到困難，以及為什麼困難」。

因為使用者告訴你的，不一定是真正的需求；有時候，他只是描述一個症狀，甚至直接提出一個未必有效的解法。

舉例來說，有人說「我希望有 AI 幫我檢查文件」，我們不能直接認定他需要 AI。真正的問題可能只是：系統沒有設定必填欄位。

## 一、先理解：為什麼要做需求訪談？

想像你是一位醫生。

病人走進診間，告訴你：「醫生，我需要吃抗生素。」

你會直接開抗生素嗎？

當然不應該。因為抗生素是病人認為的「解決方法」，卻不是診斷結果。

你應該先問他：「哪裡不舒服？從什麼時候開始？有沒有發燒？之前發生過嗎？」

軟體工程其實非常相似。

醫師看診

病人：「我要吃抗生素。」

醫師先了解症狀、病史與檢查結果，再決定治療方式。

需求訪談

使用者：「我要一套 AI 系統。」

工程師先了解工作流程與困難，再決定是否需要 AI。

共同原則：先診斷問題，再決定解法。

所以，需求訪談（Requirements Interview）的目標，不是蒐集一張「大家希望增加哪些功能」的購物清單。

真正的目標是了解：誰在什麼情況下，想完成什麼工作，遇到了什麼阻礙？

## 二、問卷、訪談、觀察，有什麼不同？

假設你要替一個有 100 位員工的單位改善文件收件系統。

你可以使用三種方式蒐集資訊：

| 方法             | 白話意思      | 最適合回答的問題    |
| -------------- | --------- | ----------- |
| 問卷 Survey      | 向多人提出相同問題 | 哪些問題值得優先研究？ |
| 訪談 Interview   | 找人深入聊真實經驗 | 問題為什麼發生？    |
| 觀察 Observation | 看人實際執行工作  | 人實際上怎麼做？    |

例如問卷顯示有 40 位受訪者說「處理文件很慢」。這只代表這些受訪者有這樣的感受。

你找其中幾位訪談後，才知道有人在等系統載入，有人在重複輸入資料，還有人在等主管簽核。

接著，你實際觀察操作流程，發現員工經常在三個畫面之間來回切換、複製相同資料。

這時候，你才逐漸掌握真正的問題。

簡單來說：問卷讓你知道可能有什麼問題；訪談讓你理解原因；觀察幫助你核對實際行為。

## 三、為什麼「怎麼問」，會影響答案？

下面是兩種問法。

不好的問法

「如果我們開發 AI 自動檢查系統，是不是就可以大幅改善你們的效率？」

這叫引導式提問（Leading Question）。它預設 AI 有效，還暗示受訪者應該回答「是」。

比較好的問法

「你上一次發現文件資料有缺漏時，從發現到完成補件，實際發生了什麼事情？」

這是開放式、以經驗為基礎的問題。受訪者可以描述真正的工作狀況，而不需要先同意某種技術解法。

受訪者可能回答：「上次交接時，發現承辦人漏填文件種類。我打電話找他，結果他正在開會，隔天才補好。」

現在你就得到更有價值的線索：問題不只在於漏填欄位，也包含補件通知、等待時間，以及交接流程。

## 四、需求訪談最重要的五個步驟

① 聽到原話

「我們的系統很慢。」

② 追問真實經過

「最近一次慢，是在哪個步驟？」

③ 定義真正的需求

「希望減少重複填寫相同資料。」

④ 提出改善假設

「讓資料自動帶入，可能減少工作量。」

⑤ 實際驗證

「試用原型，比較操作時間和錯誤次數。」

這五個步驟最容易犯錯的地方，是直接從第一步跳到第四步。

例如有人說「系統很慢」，工程師馬上決定升級 GPU、換資料庫，甚至改用更快的 AI 模型。

但「系統很慢」至少有四種不同情況：

| 真正的問題        | 可能的改善方向            |
| ------------ | ------------------ |
| 按鈕按下去要等 20 秒 | 檢查伺服器、網路、資料庫及程式效能  |
| 相同資料要輸入三次    | 自動帶入資料、減少重複步驟      |
| 不知道下一步該按哪裡   | 改善 UI／UX、資訊架構及操作引導 |
| 必須等主管批准兩天    | 改善簽核流程、通知與代理機制     |

你會發現：四種問題都叫「慢」，但解決方式完全不同。

這也是為什麼軟體工程不能只懂程式，還需要理解人如何工作。

## 五、完整案例：替單位設計文件缺漏檢查工具

我們來看一份假想訪談記錄。

使用者說：「每次到交接時，我才發現有人沒填文件類型，常常又要打電話去問。」

工程師應該把資料分開記錄：

原始事實｜受訪者說了什麼

「交接時才發現文件類型沒填，要再問一次送件者。」

待確認的解釋｜工程師怎麼理解

可能是送件階段缺少檢查，也可能是交接前沒有複核。

改善假設｜不代表已經有效

在交接前提醒缺漏欄位，可能減少來回補件。

驗證計畫｜怎麼知道有沒有改善

先確認必填規則，再製作簡單原型，觀察使用者能否找到缺漏、理解提示、完成修正，並比較前後流程。

注意，這個例子不一定需要 AI。

如果文件類型就是固定的必填欄位，只需要設定表單驗證規則，就可能解決問題。

例如：

```
if (!documentType) {
  showError("請選擇文件類型");
  return;
}
```

這段簡單的程式可能就足夠了。沒有必要為了看起來先進，硬加入大型語言模型（LLM）。

但如果必填規則會因文件內容、案件類型或特殊情境而改變，就可能需要進一步研究規則引擎、文件解析，甚至 AI 輔助判斷。

需求決定技術，不是技術決定需求。

## 六、做出功能，還不代表解決需求

這裡要區分兩種測試：

\*\*功能測試（Functional Testing）\*\*是確認程式有沒有按照規格執行。例如文件類型未填時，畫面確實出現錯誤提示。

\*\*易用性測試（Usability Testing）\*\*則是確認真正的使用者能不能理解並完成工作。例如提示出現後，他是否知道要去哪裡修改，以及能不能自行完成交接。

兩者都通過後，還可以進一步做成效驗證（Outcome Evaluation）：實際補件次數是否減少？平均處理時間是否縮短？是否反而產生新的錯誤？

因此有三個不同層次：

系統正確

功能是否按規則運作？

人能使用

使用者是否能理解、操作並完成任務？

工作改善

錯誤、等待或工作成本是否實際下降？

尤其在 AI 協作開發裡，Coding Agent 告訴你「功能已完成」，通常只能表示它認為已經完成某些開發任務，不能證明使用者的問題被解決。

## 七、調查結果要怎麼解讀，才不會過度推論？

假設你辦了一場課程，100 位學員裡面只有 3 位填寫問卷，而且這 3 位都說希望學 AI Coding。

你能得到什麼結論？

可以說：「三位回覆者都對 AI Coding 有興趣，值得進一步了解。」

不能說：「100 位學員都希望學 AI Coding，因此我們已經證明這是最受歡迎的課程。」

因為另外 97 位沒有回答，而且這 3 位可能剛好都是已經有程式背景的人。

這涉及樣本偏差（Sampling Bias）。調查結果可能受到誰願意回答、誰有機會回答、回覆者屬於哪一類人的影響。

同樣地，問卷沒有填名字，也不能自動視為匿名。若內容包含特殊職務、案件日期或具體工作事件，仍可能辨識當事人。

所以正式訪談要留意資料用途、告知與同意、紀錄權限、保存期限，以及個人資訊最小化。課堂練習則可以直接使用合成案例。

## 八、把 M01-03 與 M01-04 接起來

上一課 M01-03 告訴我們：

從個人工具變成多人共用系統，必須思考權限、資料、協作、錯誤處理，以及誰負責維護。

這一課 M01-04 接著告訴我們：

這些事情不能全靠工程師想像，必須向實際使用的人確認。

例如設計一個文件收件系統時，送件者、承辦人、複核人、主管及系統管理員可能都有不同需求。

如果只訪談主管，可能做出管理者喜歡、但第一線人員很難操作的系統。

因此，需求訪談也是一種跨角色的工作流程調查。
