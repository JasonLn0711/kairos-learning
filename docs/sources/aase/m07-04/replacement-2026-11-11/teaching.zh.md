## 一、這一課最重要的觀念

畫面不讓使用者輸入錯誤資料，不代表系統真的具備資料驗證能力。

這一課要教的是：把「什麼資料才算合格」的判斷規則，從畫面中獨立出來，做成可以重複使用、獨立測試的程式。

想像你開了一家銀行。

銀行櫃員會先幫客戶確認申請書有沒有填寫完整。但銀行不能只靠櫃員的目視檢查，就認定所有進入系統的資料一定正確。

因為資料還可能來自網路 API、其他銀行系統、批次匯入，甚至是 AI Agent 自動產生的內容。

## 二、為什麼叫做「垂直切片二」？

先理解 Vertical Slice（垂直切片）。

假設你要開一間餐廳，完整的營運系統包括點餐、廚房、收款、外送、庫存及會員。

你有兩種開發方式。

第一種：水平開發（Horizontal Development）

先做完全部畫面，再做全部後端，最後才串接。問題是，即使每一層都完成一部分，可能還沒有任何一道菜能真正從點餐走到出餐。

第二種：垂直切片（Vertical Slice）

先完成一個小而完整、可以實際操作的功能，例如「點一份餐點並成功送出訂單」，讓它穿過必要的介面、邏輯及資料層。

接著逐次增加功能。

對照這套 AASE 教材：

| 階段          | 實際完成什麼                 |
| ----------- | ---------------------- |
| M07-03 第一切片 | 建立三個輸入欄位，能看見輸入內容，但尚未檢核 |
| M07-04 第二切片 | 建立資料檢核規則，辨識有效與無效資料     |
| M07-05 第三切片 | 根據符合規則的當次資料，提供預覽與匯出    |

這樣做的好處是，每一次交付都能回答：「目前到底完成了什麼？有什麼證據？」而不是等到整個系統完成才開始測試。

### 1. 建立規則函式

以下是符合這堂課規則的簡化實作。工作坊現有 rules.py 將缺鍵、非字串及空白合併提示為「缺少…」；此處示範細分錯誤原因，並另外拒絕非 dict 輸入。兩者的三欄文字規則一致，訊息與輸入契約不同。

```python
# rules.py
FIELDS = {
    "application_id": "申請編號",
    "applicant_code": "申請人代號",
    "document_type": "文件類型",
}


def validate(record):
    errors = []
    if not isinstance(record, dict):
        return ["資料格式必須是字典"]
    for key, label in FIELDS.items():
        if key not in record:
            errors.append(f"缺少{label}")
            continue
        value = record[key]
        if not isinstance(value, str):
            errors.append(f"{label}必須是文字")
            continue
        cleaned = value.strip()
        if not cleaned:
            errors.append(f"{label}不可為空白")
        elif len(cleaned) > 80:
            errors.append(f"{label}不可超過80字元")
    return errors
```

逐段用白話解釋：

`FIELDS` 是檢查清單，告訴程式需要哪些資料。

`isinstance(value, str)` 是檢查這筆資料是不是文字。例如 `123` 是整數，而 `"123"` 是文字，兩者不相同。

`strip()` 是移除文字前後的空白。例如 `"  DEMO-A  "` 處理後會是 `"DEMO-A"`。但這裡只是拿處理後的文字做判斷，沒有直接修改原始資料。

`len(cleaned)` 是計算處理後字串的長度。

`errors.append(...)` 是把發現的問題加入清單。

最後，`return errors` 把所有發現的問題交還給呼叫者。如果清單是空的 `[]`，代表本次資料通過這組規則。

這個函式最重要的特點是：完全沒有使用 Streamlit、HTML 或任何畫面元件。

所以無論資料來自網站、手機 App、API 或 AI Agent，都可以呼叫相同的規則函式。

## 五、怎麼確定這個函式真的正確？先寫測試

這裡會碰到兩個重要術語：

- Unit Test（單元測試）：單獨檢查某個函式是否符合預期。
- Test-Driven Development（TDD，測試驅動開發）：先定義測試與預期結果，觀察合理的失敗，再實作功能直到測試通過，最後整理程式。

測試失敗時，先確認失敗來自尚未實作的規則；語法錯誤或未安裝 pytest，不能當作測試已抓到需求的證據。

例如你不能只測試「正常資料能不能過關」，還必須測試「異常資料會不會被拒絕」。

```python
# tests/test_rules.py
import pytest
from rules import validate

VALID = {
    "application_id": "SYN-001",
    "applicant_code": "DEMO-A",
    "document_type": "合成申請表",
}


def test_valid_record():
    assert validate(VALID) == []


@pytest.mark.parametrize("bad_value", ["", "   ", None, 123, "X" * 81])
def test_invalid_document_type(bad_value):
    record = {**VALID, "document_type": bad_value}
    assert validate(record) != []


@pytest.mark.parametrize("missing_key", list(VALID.keys()))
def test_missing_field(missing_key):
    record = VALID.copy()
    del record[missing_key]
    assert validate(record) != []
```

這裡有幾個術語要認識：

| 名詞            | 白話意思               |
| ------------- | ------------------ |
| `pytest`      | Python 常用的自動測試工具   |
| `assert`      | 要求一個條件成立，否則測試失敗    |
| `parametrize` | 用多組不同資料重複執行同一項測試   |
| Positive Test | 確認正確資料可以通過         |
| Negative Test | 確認錯誤資料會被拒絕         |
| Boundary Test | 專門測試 80 與 81 這種邊界值 |

這份精簡測試尚未逐欄涵蓋所有負向值，也沒有明列 80 字元、首尾空白及非 dict 案例；請依第三節矩陣補齊。

要特別注意，上面的部分測試只檢查「有沒有拒絕」，還沒有確認錯誤訊息是否精確、是否方便使用者理解。正式的驗收測試應該進一步檢查訊息內容。

### 為什麼不能只測畫面？

假設醫院的掛號系統限制出生年份只能輸入四個數字。

正常使用者在網頁輸入五個數字時，畫面可能自動阻止。

但另一個醫院系統透過 API 傳入：

```
{
  "birth_year": "abcd"
}
```

如果後端沒有檢查規則，資料仍可能進入系統。

因此，前端檢查主要改善操作體驗；真正接收與處理資料的可信邊界，也必須執行相應的驗證。

任何可能繞過畫面的資料入口，都不能只依賴畫面上的限制。

## 六、資料通過後又被修改，該怎麼辦？

這是本課另一個非常重要的觀念：過期的驗證結果（Stale Validation Result）。

假設一份申請書：

1. 使用者填好三欄，按下「檢查資料」。
2. 系統顯示「完整性檢核通過」。
3. 使用者把其中一欄刪除。
4. 如果畫面仍然顯示「通過」，就會造成誤導。

這背後涉及一個軟體工程概念：State（狀態）與 State Invalidation（狀態失效）。

資料檢核的成功狀態，是針對某一個特定版本的輸入所產生的。

所以：

@figure4

這個原理不只適用於表單。

例如電商平台顯示「付款資料已驗證」，但使用者後來更換信用卡；工廠品質管理系統顯示「批次檢驗通過」，但批次資料又被修改；AI Agent 產生的報告經過審查，但上游輸入文件後來更新。

這些情況都需要思考：原本的驗證結果是否還有效？

本頁示範在輸入事件發生時立即清除舊結果。工作坊 Streamlit 在欄位變更提交並觸發重跑後清除；尚未提交給 Python 的瀏覽器輸入，不代表伺服器已重新檢查。

教材明確要求，修改輸入後應清除先前成功訊息，並重新檢核，而且第二切片尚未提供正式報告匯出。




## 七、不同產業如何運用這種設計？

以下六個合成例子對照「規則檢查什麼」與「仍需另行判定什麼」。

| 產業       | 資料檢核的例子            | 驗證通過不代表什麼    |
| -------- | ------------------ | ------------ |
| 銀行       | 申請編號存在、格式正確、必要欄位完整 | 不代表授信核准      |
| 醫療       | 病歷欄位完整、數值型別正確      | 不代表診斷正確      |
| 製造業      | 批號存在、重量為正數、日期合法    | 不代表產品品質合格    |
| 電商       | 商品數量為正整數、地址必填      | 不代表付款完成      |
| 人力資源     | 履歷必要欄位完整           | 不代表求職者符合錄取條件 |
| AI Agent | 工具呼叫參數符合 Schema    | 不代表工具操作已獲授權  |

這裡要建立一個更深的認識：

資料檢核只是整個可信任系統的一道關卡，而不是全部。

可以區分為四個層次：

1. 結構檢核（Structural Validation）：欄位是否存在、型別是否正確。
2. 業務規則檢核（Business Validation）：數值、長度、日期及其他業務條件是否符合。
3. 授權檢查（Authorization）：執行者有沒有權限處理這筆資料。
4. 真實性與業務判定：資料是否真實、申請是否應批准、文件是否有效。

M07-04 聚焦在前兩者的基礎部分，不應把「三欄通過」誤解為後兩者也通過。

### Agent 工作指令範例

可複製後配合自己的專案調整。

```text
任務：完成 M07-04 資料檢核切片。

1. 閱讀 spec.md 與現有 app.py。
2. 建立獨立的 rules.py，提供 validate(record)。
3. 依 spec 實作三欄必填、字串型別、
   去除首尾空白及最多 80 字元的規則。
4. 先建立正向、負向及邊界測試。
5. 將檢核結果接回既有 UI。
6. 錯誤時保留輸入，顯示可修正的提示。
7. 輸入一旦修改，先前的檢核結果失效。
8. 不增加報告匯出或未經規格要求的功能。

驗收：
- 直接呼叫 validate 可拒絕異常資料。
- pytest 全部通過。
- 瀏覽器可完成錯誤修正與重新檢查。
- 提供 Diff、測試命令及實際執行結果。
- 未執行的測試不可宣稱通過。
```

在教材工作坊目錄中，對應的執行命令是：

```
cd slices/02-validation
python -m pytest -q
python -m streamlit run app.py --server.address 127.0.0.1
```

這兩種驗證有不同目的：`pytest` 檢查程式規則，啟動 Streamlit 後還需要在瀏覽器實際操作，才能確認人機互動、錯誤修正和狀態更新是否正常。

不要只因為 Agent 回報「已完成」，就視為真的通過。應保存程式差異（Diff）、測試結果及實際操作證據。

## 九、最後整理：這一課要真正帶走的五件事

1. 畫面限制不等於資料一定合法。
2. 驗證規則應能脫離 UI 獨立執行。
3. 不只測正確資料，也要測空白、缺鍵、型別錯誤與邊界值。
4. 資料一旦修改，先前的檢核結果就不能直接沿用。
5. 通過完整性檢核，不等於業務核准、資料真實或操作已獲授權。

本課 Python len(str) 計算 Unicode code point。本頁示範也使用相同計數，保留空白規則對照；像部分 emoji 在 JavaScript 的 UTF-16 length 會算成兩個單位，不可直接拿來當 Python 長度。

再補充一個進階實務細節：正式系統還必須明確定義「80 字元」是指 Unicode code point、使用者感知字元（grapheme cluster），還是其他計數方式，避免前後端對中文及組合字元的長度判定不一致。
