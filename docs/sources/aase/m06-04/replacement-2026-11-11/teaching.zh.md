# M06-04｜Browser、HTTP、API 與資料流：白話完整教學

這一章最重要的觀念是：你在網頁上按下一個按鈕，並不代表電腦只做了一件事。背後可能發生資料傳送、程式執行、驗證、資料庫存取，以及結果回傳等一連串動作。

學會這章，你就能開始看懂網站背後的運作方式，也能判斷 AI Coding Agent 畫出來的系統架構是否合理。

## 二、Browser、HTTP、API 到底有什麼不同？

我們用餐廳來比喻。

| 名詞           | 白話理解                       | 餐廳類比       |
| ------------ | -------------------------- | ---------- |
| Browser 瀏覽器  | 讓使用者操作網站、顯示結果的軟體           | 點餐平板       |
| HTTP         | 用戶端與伺服器交換請求與回應的通訊協定        | 傳遞點餐單的通訊規則 |
| API          | 規定軟體可以要求什麼服務，以及如何交換資料的介面契約 | 餐廳接受訂單的規格  |
| Server 伺服器   | 接收請求、執行程式及產生回應             | 廚房與訂單處理系統  |
| Database 資料庫 | 儲存及查詢資料                    | 訂單與庫存紀錄    |

注意兩個容易混淆的地方。

第一，HTTP 與 API 不一樣。HTTP 是通訊協定，API 是介面契約。一個 API 可以透過 HTTP 提供服務，也可以只是 Python 程式裡供其他程式呼叫的函式。

第二，API 不一定是 REST API。REST 是一種 Web API 架構風格，並非所有 API 都採用 REST。

這也符合 MDN 對 HTTP 的定義：HTTP 主要透過用戶端送出 request（請求），伺服器產生 response（回應）來交換資訊。




## 三、HTTP：電腦如何寄出一張「數位訂單」？

一次 HTTP 通訊，通常可以分成 Request 和 Response。

### 1. Request（請求）

假設我們自己設計了一個訂餐 API。

以下網址與內容均為假想教學範例，並非教材中實際存在的端點。

```
POST /api/orders HTTP/1.1
Host: restaurant.example
Content-Type: application/json

{
  "item": "beef_noodles",
  "quantity": 2
}
```

你可以把這份訊息拆成四個部分：

- Method：`POST`，表示這次請求的操作意圖。
- Path：`/api/orders`，要操作的資源或服務位置。
- Headers：例如 `Content-Type`，告訴對方資料的格式。
- Body：真正送出的資料，例如品項和數量。

這些部分共同構成一個 HTTP 請求。

### 2. Response（回應）

伺服器收到請求後，可能回傳：

```
HTTP/1.1 201 Created
Content-Type: application/json

{
  "order_id": "A1024",
  "status": "accepted"
}
```

這代表伺服器依照設計好的 API 契約，回報已建立訂單資源。

但「訂單建立」和「餐點已經煮好」仍然是兩件不同的事。

### 常見 HTTP Method

| Method | 常見用途        | 例子       |
| ------ | ----------- | -------- |
| GET    | 取得資源        | 查詢訂單     |
| POST   | 提交資料、請求處理   | 建立訂單     |
| PUT    | 建立或完整取代指定資源 | 更新整份訂單資料 |
| PATCH  | 部分修改資源      | 修改送餐備註   |
| DELETE | 刪除資源        | 刪除草稿訂單   |

這些是常見語意，不代表伺服器會自動遵守業務規則。真正允許哪些操作，還是由 API 設計及伺服器實作決定。

## 四、為什麼 HTTP 200 不等於任務成功？

這是本章最值得記住的核心觀念。

假設醫院網站允許病患上傳檢驗報告。

系統收到上傳請求後，回傳：

```
HTTP/1.1 200 OK
Content-Type: application/json

{
  "success": false,
  "error": "missing_patient_id"
}
```

HTTP 狀態是 `200 OK`，但內容卻是 `success: false`。

為什麼？

因為這個假想 API 把請求處理成功與業務驗證失敗分開表達。實務上，也可以依 API 契約使用適當的 4xx 狀態碼，例如 `422 Unprocessable Content`。

### 常見 HTTP 狀態碼

| 狀態碼                       | 白話意思         |
| ------------------------- | ------------ |
| 200 OK                    | 這次 HTTP 請求成功 |
| 201 Created               | 成功建立資源       |
| 400 Bad Request           | 請求本身有問題      |
| 401 Unauthorized          | 缺少有效的身分驗證    |
| 403 Forbidden             | 沒有權限存取       |
| 404 Not Found             | 找不到指定資源      |
| 500 Internal Server Error | 伺服器發生內部錯誤    |
| 503 Service Unavailable   | 服務目前無法處理請求   |

來源：[MDN HTTP 回應狀態碼](https://developer.mozilla.org/zh-TW/docs/Web/HTTP/Reference/Status?utm_source=chatgpt.com)。




## 五、不是每個按鈕都會呼叫 REST API：認識 Streamlit

教材特別強調這個觀念。

有些人看到網頁上的「檢查」按鈕，就想當然認為：

「按下這個按鈕，一定會送出 `POST /api/check`。」

這個推論可能完全錯誤。

例如使用 Python 的 Streamlit 製作網頁：

```
import streamlit as st


def validate(name):
    return bool(name.strip())


name = st.text_input("姓名")
if st.button("檢查"):
    if validate(name):
        st.success("資料完整")
    else:
        st.error("請填寫姓名")
```

這段程式並沒有自行定義 `/api/check` 這個 REST API。

Streamlit 由框架管理瀏覽器和 Python 伺服器之間的互動。它使用包含 HTTP 與 WebSocket 在內的通訊機制，WebSocket 提供持續的雙向連線，使伺服器可以把更新推送給瀏覽器。

你需要分清楚「程式內部的函式呼叫」與「跨網路的 API 呼叫」。

## 六、資料在哪裡被檢查，才是系統安全的關鍵

現在換成銀行的徵信報告系統。

使用者在畫面填寫企業統一編號，前端限制必須輸入八個數字。

但如果系統只在瀏覽器檢查，可能存在漏洞。

因為瀏覽器是使用者可以控制的環境。使用者可能透過其他程式或工具繞過前端限制，直接提交不符合規則的資料。

我們需要考慮多個檢查位置：

| 邊界      | 必須檢查什麼               |
| ------- | -------------------- |
| Browser | 提醒使用者格式錯誤，改善操作體驗     |
| Server  | 重新檢查格式、型別、長度、業務條件和權限 |
| 資料庫     | 透過適當限制維持資料一致性        |
| 匯出功能    | 再確認目前資料有效，而且使用者有權匯出  |

尤其要注意舊資料（stale data）。

假設使用者輸入一筆完整資料，按下檢查後獲得成功訊息。接著他又刪除了必填欄位，但原本的「下載報告」按鈕仍然能使用。

如果後端只相信「之前曾經驗證成功」，就可能把不完整的資料匯出。

正確做法是讓修改後的資料使舊驗證結果失效，必要時在匯出入口再次驗證目前資料。

這個設計原則常稱為 Never Trust the Client（不要直接信任用戶端）。

## 七、跨產業應用：相同觀念，不同業務

同一套資料流與結果驗證方法，可以套用到不同產業的工作。

| 產業       | 使用者操作    | 真正需要驗證的業務結果          |
| -------- | -------- | -------------------- |
| 電商       | 按下結帳     | 付款、庫存、訂單狀態是否一致       |
| 醫療       | 上傳報告     | 檔案是否有效、患者是否正確、是否有權存取 |
| 金融       | 匯出徵信報告   | 必填資料是否完整、是否通過權限檢查    |
| 教育       | 繳交作業     | 伺服器是否保存正確版本，是否在期限內   |
| 製造       | 提交設備維修申請 | 工單是否建立，設備編號是否有效      |
| AI Agent | 執行外部工具   | 工具呼叫是否授權、結果是否真實完成    |

AI Agent 也是同樣的道理。

即使工具回傳 `200 OK`，也不能直接推論付款完成、檔案產生成功，或外部操作已達到預期效果。必須檢查工具回應的實際內容，必要時再查詢結果狀態。

在 Network 裡，你要學習觀察四件事：

1. Headers：請求送去哪裡？使用什麼 Method？回傳什麼狀態碼？
2. Payload：如果有請求本文，送出了哪些資料？
3. Response：伺服器回傳什麼結果？
4. WS / Messages：如果使用 WebSocket，有哪些實際可觀察的訊息？

最重要的是不要把「我認為應該如此」當成「我實際觀察到了」。

觀察時請使用合成測試資料，不要公開 Cookie、Token、個人資料或其他敏感內容。

模擬紀錄中的 `101` 示意 HTTP/1.1 WebSocket 協定升級，不表示應用任務成功；不同部署或協定版本的握手呈現也可能不同。

## 九、整章重點：你真正要建立的思考方式

可以用以下五個問題檢查任何 Web 系統：

1. 誰發起操作？ 使用者、瀏覽器，還是背景程式？
2. 資料怎麼走？ HTTP、WebSocket、函式呼叫，還是其他方式？
3. 誰負責處理？ 哪個伺服器、程序或元件？
4. 誰負責驗證？ 哪裡重新檢查資料、權限及目前狀態？
5. 如何證明完成？ 只有 HTTP 成功，還是業務結果與最終產物都已核對？

將這五個問題記錄在 `architecture.md`，就是一份最基本的資料流分析。分開標記文件依據、程式核對與實際觀察，未觀察的細節保留待查。
