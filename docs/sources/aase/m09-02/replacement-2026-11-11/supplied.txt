## 一、先理解最重要的觀念

你把一套軟體做出來，不代表別人就能接手使用。

想像你是一位廚師，研發了一道非常好吃的料理。

你自己知道要放哪些材料、使用什麼器具、烹調多久、什麼時候關火。

但如果你離職，只留下一句：

「把食材放進鍋子，煮熟就可以了。」

下一位廚師能做出同樣的料理嗎？

恐怕很難。

軟體工程也一樣。

你寫了一套程式，在自己的電腦上正常運作，但交給另一個人後，他可能不知道：

- 這套程式究竟要解決什麼問題？
- 需要安裝哪些工具和版本？
- 如何啟動？從哪個資料夾開始？
- 怎樣證明程式真的正常？
- 遇到錯誤怎麼辦？哪些功能還不能使用？
- 使用結束後，資料和服務怎麼處理？

README 就是幫助接手者回答這些問題的入口文件。 這篇教材特別強調：不只要寫操作方法，還要留下可重現的驗收證據、使用限制，以及停止和復原的方法。

## 二、README 是什麼？它在整個專案扮演什麼角色？

README 通常是一個叫做 `README.md` 的文字檔。

你可以把它想成產品隨附的「使用說明書」，但對工程專案而言，它還需要說明如何安裝、驗證和維護。

一個作品從製作者交到接手者的流程

定位：這是什麼？

用途、使用對象、功能範圍、版本

重建：怎麼讓它跑起來？

環境、依賴套件、安裝與啟動命令

驗收：怎麼知道它真的正常？

測試資料、操作步驟、預期結果、實際證據

交接：發生問題或結束使用怎麼辦？

已知限制、錯誤處理、復原、停止、清理

這四個階段可以視為交接文件的基本架構。

## 三、用一個實際案例，把四個階段串起來

假設你替一家餐廳開發了「每日訂單檢查系統」。

店長每天匯入一份 CSV 訂單檔案，系統會檢查是否有缺少訂單編號、金額異常或重複訂單。

### 第一階段：定位——這套系統究竟能做什麼？

不好的說明：

> 這是一個訂單系統，使用 Python 開發。

好的說明：

> 本系統用於檢查每日訂單 CSV 是否存在必要欄位缺漏與重複訂單。適合店長在本機處理測試資料。目前不支援多人登入、即時收銀系統串接與正式金流處理。

兩者差在哪裡？

第一個只告訴別人「這是什麼」，第二個還說清楚「能做什麼、不能做什麼，以及適合在什麼情境使用」。

尤其是「不能做什麼」非常重要。

假設餐廳老闆以為這個工具已經可以直接串接信用卡收費，可能就會做出錯誤的營運決策。

### 第二階段：重建——別人的電腦能不能重新安裝？

你在自己的電腦上可能已經安裝了幾十個 Python 套件。

但新接手的工程師拿到程式時，電腦裡什麼都沒有。

所以 README 至少應說明 Python 版本、需要的依賴套件、檔案位置，以及正確的安裝和啟動方式。

例如，以下是一段示意命令，假設專案確實包含所需檔案：

```
# 建立獨立的 Python 環境
python -m venv .venv

# 在 Linux/macOS 啟用
source .venv/bin/activate

# 安裝專案依賴
python -m pip install -r requirements.txt

# 執行測試
python -m pytest -q

# 啟動程式（假設入口為 app.py）
python app.py
```

這裡要理解兩個重要觀念。

第一，不能只寫「執行 app.py」。 別人還需要知道前置環境、路徑和依賴條件。

第二，最好使用乾淨環境（Clean Environment）驗證。

乾淨環境就像一個新廚房，沒有你平常使用的特殊工具或已經準備好的食材。

如果這套系統只能在你自己的電腦執行，可能表示你遺漏了某些安裝條件。當然，乾淨環境成功不代表所有作業系統都相容，這仍要分別測試。

### 第三階段：驗收——程式跑起來就代表成功嗎？

不一定。

假設你的訂單檢查程式成功開啟，但遇到重複訂單時沒有提出警告，那就沒有達到原本的目的。

因此我們必須定義「成功應該長什麼樣子」。

| 測試情境      | 預期結果        |
| --------- | ----------- |
| 上傳正常訂單    | 顯示檢查通過      |
| 缺少訂單編號    | 顯示欄位缺漏      |
| 兩筆訂單編號相同  | 顯示重複訂單警告    |
| 上傳空白檔案    | 顯示明確錯誤，不應當機 |
| 修正錯誤後重新檢查 | 顯示更新後的結果    |

這張表屬於預期行為，不是已經通過測試的證據。

真正測試時，還需要記下測試日期、程式版本、輸入資料、實際結果，以及成功或失敗。

這就是軟體工程裡非常重要的區別：

「我認為應該成功」不等於「我已經證明它成功」。

### 第四階段：交接——發生問題、停止使用時怎麼辦？

假設餐廳店長在使用軟體時，突然發現某筆訂單金額錯誤。

README 應清楚交代，能否撤銷、是否需要重新匯入、哪些紀錄要保留，以及如何安全停止程式。

另外，如果這只是單機原型，也不能因為現在可以使用，就認為把服務開放給所有分店便能直接正式營運。

多人使用可能涉及身分驗證、存取權限、資料保存、備份和維護等新問題。

交接的目的，不是保證軟體完全沒有問題，而是讓接手者知道問題的邊界，並有能力作出下一步判斷。

## 四、最容易忽略的三種「成功」

原教材特別要求區分三種不同的證據。

[image](https://www.google.com/s2/favicons?domain=https://learn.cs-kairos.com\&sz=32)

CS Kairos Learn



| 證據層級    | 白話意思           | 可以證明什麼       |
| ------- | -------------- | ------------ |
| 作者實測    | 我在自己的環境跑過      | 在這次環境與條件下成功  |
| 作者重新建置  | 我在全新資料夾與環境重新安裝 | 減少了對原環境的依賴   |
| 接手者獨立重現 | 別人只依照文件完成操作    | 文件更有可能真正支援交接 |

想像你是一位老師。

你自己能解開一道數學題，代表你會做。

你重新解了一次，代表你能重現自己的方法。

但如果你寫的解題說明讓另一個學生不需詢問就能理解並解出來，才更能證明你的說明具有可傳遞性。

這也是為什麼 README 不能只是作者自己的筆記。

## 六、什麼才算一份合格的 README？

你可以使用以下清單，快速檢查自己的作品。

交接完成度自我檢查

0 / 8

說明專案用途、使用對象與適用範圍

列出需要的作業系統、軟體版本與依賴

提供正確的安裝、測試與啟動命令

提供測試資料、預期結果與實測紀錄

清楚區分已驗證功能和未驗證事項

記錄已知限制、風險與不能使用的情境

說明錯誤處理、停止服務與資料清理

讓另一個人從乾淨環境獨立重現

重新檢查

這份清單是文件完整度的初步檢查，並不代表勾選後就已證明軟體品質或安全性。

還有一個重要原則：當程式碼、依賴套件、啟動方式或輸出規格改變時，README 與驗收證據也應同步更新。

## 七、最後用一個情境確認是否真正理解

假設你為學校開發了一套 AI 論文摘要系統。

你已經完成程式，並在自己的電腦成功產生 100 篇論文摘要。

你把 GitHub 儲存庫交給一位新加入的研究助理，README 只有：

```
1. 安裝 Python
2. 執行 main.py
3. 開啟瀏覽器使用
```

請回答以下三題，先不用追求標準措辭：

1. 這份 README 至少缺少哪四種重要資訊？
2. 如果研究助理無法執行，但你自己可以，該如何判斷究竟是環境問題、程式問題，還是交接文件問題？
3. 如果研究助理成功產出摘要，是否就能宣稱這套 AI 已經適合醫院或銀行正式使用？為什麼？

本篇最重要的結論：

寫程式，是讓機器能夠執行；寫好 README、驗收證據與交接文件，是讓其他人能夠理解、重建、驗證並負責任地使用這套系統。

真正的工程交付，不只是把作品交出去，而是讓作品不再依賴原作者才能繼續運作。
