# AASE M04-04｜Wireframe：先畫行為，再上色

本課最重要的觀念：設計軟體時，不要急著把畫面做漂亮。應該先確認使用者看得懂、知道怎麼操作，遇到錯誤時也知道如何繼續。

Wireframe（線框稿）就是讓我們在真正開發軟體之前，用很簡單的方框、文字、按鈕和箭頭，先把操作方式排演一遍。

這不是只有 UI/UX 設計師才需要學的技術。產品經理、軟體工程師、AI Agent 開發者，甚至負責規劃醫院、銀行或政府數位服務的人，都可以使用。

本課根據 [AASE M04-04 正式教材](https://learn.cs-kairos.com/courses/aase/v1/m04/concepts/m04-04/?utm_source=chatgpt.com)，核心是學會四件事：

1. 用低成本草圖表達使用者要看到什麼、做什麼。
2. 規劃正常、處理中、失敗與完成等不同狀態。
3. 讓別人實際走讀草圖，找出不合理的地方。
4. 分清楚草圖已經驗證什麼，以及哪些事情仍要透過真正的程式測試。

## 一、為什麼軟體開發要先畫 Wireframe？

想像你要開一家餐廳。

你請設計師幫你規劃店面，他立刻拿出非常漂亮的設計圖：大理石櫃檯、漂亮吊燈、木質桌椅，整間店很有質感。

但是開幕後，你才發現：

- 客人進門不知道要去哪裡點餐。
- 點完餐不知道應該在哪裡等候。
- 點錯餐時不知道怎麼修改。
- 付款失敗，系統卻顯示「訂單完成」。
- 服務人員從廚房到櫃檯的動線互相干擾。

問題不在裝潢不漂亮，而是整個服務流程沒有設計好。

軟體也是一樣。

開發一個網站時，你可以很快利用 React、Figma，甚至 AI Coding Agent 做出看起來專業的畫面。

但畫面漂亮，不代表使用者真的能完成工作。

這就是 Wireframe 的價值：在投入大量開發成本之前，先用便宜、容易修改的方式確認設計方向。

從需求到正式產品的設計流程

需求與使用情境

誰要解決什麼問題？

User Flow（使用者流程）

使用者需要經過哪些步驟？

Wireframe（線框稿）

每個畫面放什麼？按下去會怎樣？

Prototype（可操作原型）

讓使用者試操作，驗證互動方式

實作、測試與交付

完成真正的業務邏輯、安全與品質驗證

這是便於理解的典型順序，不代表每個專案都必須嚴格瀑布式執行。實務上可以在草圖、原型與需求之間反覆修正。

英國政府的 GOV.UK Service Manual 也強調，原型應用來探索與測試不同設計，並依目前要回答的問題，選擇紙筆草圖或可操作的程式原型。

## 二、Wireframe 到底要畫什麼？

先看一個實際例子。

假設我們準備為物流公司開發「出貨資料檢查系統」。

員工輸入三項資料：收件人、收件地址、聯絡電話。系統檢查三個欄位是否填寫，通過後就能預覽並匯出出貨資料草稿。

這裡先假設只檢查三欄是否有值，不驗證地址是否真實、電話是否正確。

我們不需要先決定按鈕要藍色還是綠色，而是先畫出四種情況。

① 輸入中

收件人 \*

王小明

收件地址 \*

請輸入地址

聯絡電話 \*

0912-XXX-XXX

檢查資料

使用者知道要填什麼

② 處理中

出貨資料檢查

正在處理

資料已保留，請勿重複提交

檢查進行中

僅在實際需要等待時出現

③ 資料缺漏

還有 1 項資料需要補填

收件人：王小明

收件地址 \*

請填寫收件地址

聯絡電話：已保留

補填後重新檢查

說清楚哪裡錯，且不清空其他欄位

④ 檢查完成

三欄完整性檢查通過

收件人：王小明

收件地址：已填寫

聯絡電話：0912-XXX-XXX

預覽／匯出資料

修改任一欄後，原檢查結果失效

教學用低保真示意圖，不是真正執行檢查的互動介面。

注意，四種狀態不是要求使用者一定要依序經過四個畫面。

例如：

- 三欄都填好了，而且檢查非常快，可以直接從輸入進入完成。
- 地址沒有填寫，就應該進入缺漏狀態。
- 如果需要向遠端伺服器查詢，才可能出現處理中。
- 如果伺服器故障，這是技術失敗，不應該謊稱使用者忘記填資料。

這裡就出現一個重要的軟體工程概念：State（狀態）與 State Transition（狀態轉換）。

## 三、真正重要的不是四張圖，而是它們之間怎麼連接

一個常見的設計錯誤是，只畫使用者操作成功的情況。

例如：

使用者填完資料 → 按下送出 → 顯示成功。

這條路徑稱為 Happy Path（理想成功路徑）。

但現實世界永遠不只有成功的情況。

我們用三個不同產業的場景理解其重要性。

銀行轉帳： 使用者輸入轉帳資料後，系統確認欄位都已填妥，不代表銀行已經完成轉帳。真正扣款成功需要另行確認。若交易逾時，也不能直接當成交易失敗後重新匯款，因為可能造成重複轉帳。

醫院預約： 病人填寫預約資料後，畫面顯示所有欄位已完成，不代表掛號成功。還必須確認系統真的保留到診次或名額。

AI Agent 工具： 使用者要求 Agent 產出研究報告。Agent 可能處於等待工具回應、資料不足、工具執行失敗、報告已生成但尚待人工確認等狀態。如果只畫「輸入指令」和「報告完成」，就會漏掉最需要治理的中間狀態。

共同原則是：

畫面上的成功訊息，必須對應到真正已經完成的事情，不能把尚未驗證的結果包裝成完成。

## 四、為什麼畫面旁邊還要寫註記？

線框稿本身只能表示畫面大致長什麼樣子，不能充分描述所有行為。

例如，你畫了一個「送出」按鈕。

開發者可能還是不知道：

- 按下去之後要不要鎖住按鈕？
- 網路斷線後要不要保留內容？
- 使用者能不能取消？
- 送出後修改資料，原本的審核是否仍有效？

因此需要 Annotation（行為註記）。

本課要求的 `wireframe-notes.md` 就是用來記錄這些資訊。

例如，對物流系統可以這樣寫：

```
# 出貨資料 Wireframe 行為註記

## 檢查資料
觸發：使用者按下「檢查資料」
條件：檢查三項必填欄位

## 資料缺漏
顯示：指出未填寫的欄位
保留：其他已填資料
允許動作：補填、重新檢查

## 技術失敗
顯示：目前無法完成檢查
允許動作：安全重試或稍後再試
限制：不可宣告檢查成功

## 檢查通過
顯示：三欄完整性檢查通過
允許動作：預覽、匯出
限制：不代表地址或電話已驗證有效

## 完成後修改
觸發：修改任一欄位
結果：舊檢查結果失效
下一步：必須重新檢查
```

這份註記與線框稿互相補充：一份解釋畫面，一份交代規則。

特別要注意「完成後修改」。

假設病歷系統顯示資料已審核，醫師又修改了一項用藥資訊。若系統繼續顯示「已審核」，就可能讓人誤以為新內容也已通過審核。

所以這不只是 UI 問題，也涉及資料一致性、權限、工作流程與安全。

## 五、低保真、中保真與高保真有什麼不同？

Fidelity（保真度）指的是設計稿與實際產品在外觀及互動細節上有多接近。

| 類型                          | 白話解釋            | 適合回答的問題           |
| --------------------------- | --------------- | ----------------- |
| Low-fidelity 低保真            | 像紙上草圖，簡單方框與文字   | 欄位、動作和流程合理嗎？      |
| Mid-fidelity 中保真            | 更精確的灰階版面與真實內容   | 資訊排列、閱讀順序清楚嗎？     |
| High-fidelity 高保真           | 接近正式產品的視覺設計     | 字體、配色、視覺層級與細節合適嗎？ |
| Interactive prototype 可操作原型 | 可以按按鈕、切換畫面、模擬互動 | 使用者操作起來是否順暢？      |

這些類型不是完全互斥的；高保真畫面也可以做成可操作原型。

例如，建築師設計房子，可以先用手繪平面圖討論房間位置，再做精確建築圖，最後用 3D 模型或實體樣品測試體驗。

軟體設計也是同樣道理：不要用昂貴的驗證方式回答廉價草圖就能回答的問題，但也不要拿草圖宣稱已經通過真實互動測試。

## 六、如何確認 Wireframe 真的有用？

本課介紹 Walkthrough（走讀）：請另一個人沿著情境閱讀草圖，判斷他能不能理解接下來要做什麼。

以物流系統為例，可以給測試者兩張任務卡。

任務 A：資料缺漏

你正在準備出貨，但是忘記填寫收件地址。請指出介面上哪裡告訴你這件事，以及你應該如何補救。

任務 B：完成後修改

你已經完成資料檢查，後來發現電話填錯並修改了內容。請說明現在是否可以直接匯出已通過檢查的資料。

走讀時，不要一開始就告訴測試者答案。

我們想觀察的是：草圖本身能不能提供足夠線索，讓人理解。

而且不同的驗證方法，能支持的結論不同：

| 驗證方法    | 可以支持的結論       | 不能直接證明      |
| ------- | ------------- | ----------- |
| 自己走讀    | 發現明顯設計矛盾      | 真正使用者也能理解   |
| 他人走讀    | 此人在指定情境如何理解草圖 | 所有使用者都能完成任務 |
| 可操作原型測試 | 指定設備和情境下的互動表現 | 正式系統的效能與安全  |
| 正式程式測試  | 被測試範圍內的程式行為   | 未涵蓋情境也完全可靠  |

還有一個經常被忽略的面向：Accessibility（無障礙或可近用性）。

即使只是在畫黑白草圖，也要考慮欄位標籤、錯誤訊息與合理閱讀順序。

例如，不能只有一個紅框告訴使用者「這裡有錯」。W3C 的 WCAG 2.2 成功準則 3.3.1 要求，在自動偵測到輸入錯誤時，以文字指出出錯項目並描述錯誤。

[image](https://www.google.com/s2/favicons?domain=https://www.w3.org\&sz=32)

W3C



不過，紙上標示了正確的閱讀順序，不代表實際程式已通過螢幕閱讀器或鍵盤操作測試。

## 七、如何完成這一節的實作？

正式教材要求保留兩項成果：

`wireframe.svg` 是可由瀏覽器顯示的四狀態線框圖。SVG 是 Scalable Vector Graphics（可縮放向量圖形），可以用文字編輯器修改圖中的文字與形狀。

`wireframe-notes.md` 是 Markdown 格式的行為說明，記錄狀態切換、輸入保留、錯誤復原、修改後重新檢查，以及尚未測試的事項。

可以依照這個順序練習：

1. 從教材的工作坊資源下載 `aase-v1-workshop.zip`。
2. 複製 `reference/wireframe.svg`，保留原始參考稿。
3. 將合成情境改成你選擇的產業，例如醫院掛號、物流出貨或銀行表單。
4. 修改 SVG 中的文字，確認瀏覽器能正常顯示、不會裁切。
5. 在 `wireframe-notes.md` 記下觸發條件、可採動作、失敗復原與修改規則。
6. 用缺漏和完成後修改兩個案例走讀，記錄至少一項修正理由。

這一節的實作重點不是做出可執行網站，而是交付一份別人看得懂、可以討論、能追溯設計理由的介面規格草稿。

## 八、從這堂課帶走的工程觀念

Wireframe 可以視為連接需求工程與軟體實作的橋梁。

M03 的需求工程回答「我們要解決什麼問題」；M04-03 的資訊架構回答「資訊應該如何組織」；M04-04 的 Wireframe 則把需求轉成具體畫面、動作和狀態。後面的規格驅動開發與測試，再將這些設計轉成程式可以驗證的規則。

因此，這堂課最值得記住的不是某個繪圖軟體的操作方法，而是：

每當你設計一個畫面，都要追問四件事：使用者現在知道什麼？能做什麼？接下來會發生什麼？出錯時怎麼回復？
