# M09-03｜成果展示與驗收證據：如何證明你做的東西真的符合要求？

這一節屬於 AASE「AI 協作軟體工程」課程的 M09，主題是成果展示與驗收證據（Demo & Acceptance Evidence）。


## 一、先用一句話理解

「做出來」是一回事，「看起來能用」是另一回事，而「有證據證明符合要求」又是第三回事。

想像你請建築公司蓋一棟房子。

建築公司向你展示：

「你看，房子蓋好了，外觀很漂亮！」

但你真正關心的可能是：

- 房子有按照原本的設計圖施工嗎？
- 水電、消防、耐震有符合要求嗎？
- 下雨會不會漏水？
- 如果發現問題，有沒有修好並重新檢查？
- 日後維修時，其他師傅看得懂施工紀錄嗎？

這些問題，不能光靠一張漂亮的完工照片回答。

軟體也是一樣。

AI 可以在很短時間內產生程式、網站和漂亮的操作畫面，但如果缺乏測試紀錄、版本資訊與驗收證據，我們仍然無法確定它是否真的符合要求。

本節的核心就是：

> 每當你宣稱「某項功能已完成」，都應該能指出：要求在哪裡、怎麼實作、使用哪個版本，以及用什麼證據確認它真的完成。

## 二、整體架構：從需求一路追到證據

這條從需求連到驗收的關係，就叫做需求追溯（Requirements Traceability）。

它的重點不是文件越多越好，而是讓其他人能夠沿著證據，檢查你所做的承諾。

例如：

| 階段    | 軟體開發中的常見產物             |
| ----- | ---------------------- |
| 問題    | `problem.md`           |
| 畫面設計  | `wireframe.svg`        |
| 功能規格  | `spec.md`              |
| 系統架構  | `architecture.md`      |
| 程式實作  | `app.py`、`rules.py`    |
| 測試證據  | `tests/`、實際測試紀錄        |
| 版本與交付 | Git Commit、`README.md` |

教材特別強調：最好用同一個案例貫穿所有文件與展示，不要需求文件講 A 案例、程式展示 B 案例、測試又拿 C 案例，導致無法追溯。

## 三、實際怎麼展示？用「保險理賠系統」來理解

假設一家保險公司希望建立 AI 文件檢核系統。

工作人員上傳理賠文件，系統自動檢查資料是否齊全，並產生審查報告。

需求有三個：

「資料不完整，不能產生完整報告。」

「資料齊全，可以產生正確報告。」

「如果使用者修改資料，之前的檢核結果必須失效。」

我們就用同一筆測試案件，展示三種情境。

@figure2

第三種情境尤其重要。

想像銀行系統原本計算出客戶可貸款 500 萬元，後來客戶收入資料改變，系統卻仍沿用原先的核貸結果。

或醫院原本根據某次檢驗數值提供用藥建議，檢驗數據更新後，系統仍繼續顯示舊的分析結果。

這類問題稱為 Stale Result（過期結果）。畫面可能看起來正常，但結果與目前資料已經不一致。

因此，教材才要求同時展示正常、負向與過期結果三種情境。

## 四、什麼叫真正的「驗收證據」？

最重要的是區分「我認為應該會成功」和「我實際觀察到成功」。

| 你拿出的東西     | 它能夠證明什麼？           |
| ---------- | ------------------ |
| 畫面截圖       | 某一時刻畫面長什麼樣子        |
| 規格文件       | 系統原先承諾要做什麼         |
| Git Commit | 某個版本包含哪些程式內容       |
| 自動化測試結果    | 指定版本在指定條件下的測試結果    |
| 真人操作紀錄     | 真實使用者在觀察情境下的操作表現   |
| 另一個人重新部署成功 | 在指定環境與步驟下，別人也能重現成果 |

證據的範圍不能被誇大。

例如，一張「登入成功」截圖，不能證明整套帳號權限系統是安全的；一次測試成功，也不能證明所有輸入、負載和部署環境都會成功。

而且證據要有背景資訊。

假設你在展示系統時說：「我們的 30 項測試全部通過。」

驗收人員至少應該能夠知道這 30 項測試使用哪個程式版本、在什麼環境執行、什麼時間執行，以及留下什麼實際結果。

這也是為什麼 Git 版本與測試紀錄要一起保存。

### 用 Given／When／Then 連接規格與證據

你可以先將保險理賠規則寫成容易核對的情境：

```
Given：案件缺少必要的醫療收據

When：工作人員按下「產生完整報告」

Then：系統拒絕產生完整報告
And：畫面顯示缺少醫療收據
```

然後真正執行測試，檢查程式是否符合這些條件。

Given／When／Then 寫的是預期，測試結果記錄的才是實際觀察。

這種以情境描述行為的方式，也符合 Cucumber Gherkin 的基本方法。這裡的全形冒號是白話說明用的格式；若要執行 .feature 檔，Given／When／Then／And 後不加冒號，並需有 Feature、Scenario 及對應的步驟定義。

## 五、如果展示失敗，怎麼辦？

假設你向公司主管展示 AI 系統，原先測試全部通過，但正式 Demo 時突然跳出錯誤。

你可能很想改放昨天成功的錄影。

錄影可以用來補充說明，但不能因此宣稱今天的展示也成功。

正確方式是保留當次錯誤、指出失敗步驟、記錄使用的版本及環境，並把昨天的成功錄影清楚標示成歷史證據。

這裡要理解兩個概念：

可追溯性（Traceability）：別人可以查到這個問題對應哪項需求、哪次修改和哪份測試。

可重現性（Reproducibility）：別人在相同的必要條件下，能重新執行並檢查結果。

例如，物流系統在你的電腦成功列出配送清單，但換到另一台電腦就無法執行，表示目前還缺少跨環境重現的證據。

失敗紀錄不只是缺點，它也提供排除問題與改善系統的依據。

## 六、驗收通過，不等於可以正式上線

這是本節最值得記住的工程判斷。

假設一套學生專題系統，在個人電腦上通過所有功能測試。是否代表它可以直接讓一家醫院的 100 位員工使用？

不一定。

因為兩種情境的要求完全不同。

| 教學或本機原型驗收 | 正式組織系統驗收       |
| --------- | -------------- |
| 基本功能正確    | 功能與業務流程正確      |
| 本機能順利執行   | 正式部署與維運可行      |
| 測試資料能正確處理 | 真實資料與權限受到保護    |
| 個人操作成功    | 多人同時操作仍可靠      |
| 可以展示成果    | 有監控、備份、復原及安全治理 |

因此，驗收結果必須附帶適用範圍。

例如：

「目前接受此版本作為本機教學原型，已驗證文件缺漏、補齊與結果失效三項行為。尚未驗證多人授權、正式資料保存和部署安全。」

這種說法比直接宣布「系統完成」更有工程價值。

本節教材也明確區分本機原型接受與組織多人使用的正式審查。

## 七、實際工作中可以使用的驗收模板

假設下一次你要交付一個 AI Agent、醫療工具、財務報表程式，甚至一個簡單網站，可以使用下面這份紀錄。

### 成果驗收紀錄

示範用模板，內容應依實際執行結果填寫

```text
功能或需求

缺少必要文件時，不得匯出完整報告

對應規格

spec.md — AC-03

程式版本

Git Commit：填入實際 SHA

驗證情境

缺漏文件、補齊文件、修改已驗證資料

驗證證據

填入測試報告、操作紀錄與實際輸出位置

未驗證項目

多人權限與正式部署安全

驗收範圍

本機教學原型

驗收決定

待驗收

有條件接受

接受指定範圍

不接受，需修正
```

注意：模板中填入某個測試名稱或選擇「接受」，本身並不代表已經完成驗證。仍必須附上實際證據並經適當人員審查。

## 八、最後整理：這一節真正要帶走的觀念

M09-03 不只是教你如何做 Demo，而是教你建立一條可信任的工程證據鏈：

需求說明你承諾什麼，程式表示你實作什麼，測試證明你實際觀察到什麼，驗收則決定目前成果可以被接受到什麼程度。

這套思維不只適用於 AI 或軟體。建築完工檢查、藥廠品質放行、金融稽核、法律證據審查及工廠產品驗收，背後都有類似的邏輯：不能只有聲明，還要有與聲明相符、能被獨立查核的證據。

## 九、理解檢核

假設你開發一個 AI 招募系統，已完成履歷上傳、分析與排序功能。現場展示時，系統成功替 10 份履歷產生排名，主管因此說：「功能已經完成，可以正式讓所有 HR 使用。」

請你回答：

問題一： 現場成功產生排名，究竟證明了什麼？還有哪些重要事項未被證明？

問題二： 如果使用者在排名完成後修改其中一份履歷，系統應該如何處理？你會怎麼設計驗收情境？

問題三： 如果要讓這個系統從個人 Demo 變成正式的企業人資系統，你至少還需要哪三類驗收證據？

請用白話說明判斷依據，再對照參考解析；閱讀答案本身不代表已完成評量。
