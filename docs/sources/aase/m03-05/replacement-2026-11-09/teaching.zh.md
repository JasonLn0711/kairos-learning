# M03-05｜成功指標、假設與需求紀錄：怎麼證明做出來的系統真的有用？

這一課非常重要，因為它決定了你做出來的系統，究竟只是「能夠運作」，還是「真的解決了問題」。

先記住一句話：做出功能不等於達成目標；達成目標必須有證據，而證據必須事先定義怎麼取得。

想像你花了一個月開發 AI 系統，最後向主管報告：

「我們完成了 20 個功能、寫了 10,000 行程式碼，而且 AI 可以自動產生報告！」

主管可能只問一句：

「所以，原本需要半小時的工作，現在到底快了多少？錯誤有沒有減少？」

這就是今天要學的核心。

## 一、先建立完整觀念：從需求到證據

我們先把整個軟體開發流程串起來。

@figure1

其中最需要理解的是：需求說明系統應該做什麼；假設解釋為什麼這樣設計可能有效；指標則定義如何判斷結果。

三者不能混為一談。

## 二、功能指標與任務指標：機器成功，不等於人成功

假設你開發一個「AI 文件收件系統」。

使用者上傳文件後，系統會檢查有沒有缺件，最後產生報告。

現在你想知道它做得好不好。

這時需要兩個不同角度。

@figure2

這兩種指標為什麼一定要分開？

想像系統設計出一個「檢查缺漏」按鈕。

工程師測試後發現，每次按下去都能正確檢查，功能指標達到 100%。

但實際使用者根本不知道這個按鈕在哪裡。

那麼：

- 從工程角度，這項功能可能通過測試。
- 從使用者角度，任務仍然可能失敗。

反過來也一樣。使用者成功產生一份報告，不表示系統已經通過所有安全與例外情境的檢查。

一個好系統，要同時證明「做得對」與「用得成」。

## 三、成功指標怎麼算？分母是關鍵

現在我們來實際計算。

假設總共有六筆合成測試資料，其中四筆缺漏，兩筆完整。

| 測試案例 | 資料狀態   | 系統表現       |
| ---- | ------ | ---------- |
| A    | 缺少姓名   | 阻擋匯出 |
| B    | 缺少電話   | 阻擋匯出 |
| C    | 缺少附件   | 阻擋匯出 |
| D    | 缺少身分資料 | 錯誤放行 |
| E    | 資料完整   | 允許匯出 |
| F    | 資料完整   | 允許匯出 |

我們想衡量的叫「缺漏阻擋率」。

公式：缺漏阻擋率＝成功阻擋的缺漏案例／全部缺漏案例 × 100%。

因此是：3／4 × 100%＝75%。

@figure3

這裡有三個值得記住的地方。

第一，分母必須是你真正想研究的對象。 我們研究的是「缺漏能不能被擋住」，因此只看四筆缺漏資料，而不是全部六筆。

第二，百分比不能取代原始數量。 75% 聽起來好像還可以，但寫成 3/4，就會發現四筆裡有一筆漏擋。對這個特定驗收要求而言，它是失敗的。

第三，沒有測試，不代表成功。 假如這次根本沒有缺漏案例，分母就是零，無法計算阻擋率。應記錄「未測得／不適用」，而不是寫 100%。

還有一個容易忽略的陷阱：系統如果把六筆資料全部擋住，缺漏阻擋率也會是 100%，但正常資料根本不能完成工作。

所以，實務上還需要搭配「完整資料能否正確匯出」等功能測試，避免只把一個指標做到漂亮。

## 四、怎麼證明使用者真的比較快？

假設 AI 系統宣稱：

「使用我們的產品，產製一份報告可以節省五分鐘。」

你第一個應該問的是：

這五分鐘怎麼量出來的？

想像兩種測量方式。

@figure4

看起來節省五分鐘，但兩個流程的計時起點不同。

這個比較就不公平。

比較時，應盡可能做到相同的任務、同等難度的資料、相同起終點，並記錄使用者是否得到額外協助。

例如統一定義：

「從使用者第一次看到指定資料開始，到成功取得與當前資料相符的正確報告為止。」

但即使這樣，也要注意：

假設使用者第一次操作舊系統，第二次操作新系統，他可能只是因為已經熟悉任務，所以做得更快。

這叫做練習效應（Practice Effect）。

因此，一次測量到的時間差，不足以證明改善一定由新系統造成。較嚴謹的比較可以考慮讓不同參與者交換操作順序，或使用難度相當的不同題目。

而且，只計算成功者的完成時間也有問題。如果有一半的人放棄了，就不能只報另一半成功者的平均時間，卻不揭露失敗率。

## 五、假設（Hypothesis）：你相信的事情，不一定是真的

這個觀念在 AI 開發中尤其重要。

例如，你想讓使用者自行修正資料，因此你設計了一個功能：

「當資料缺漏時，畫面顯示缺少的欄位名稱。」

你認為這樣能讓使用者自己補齊資料。

但請注意：

這是設計假設，還不是已經證實的事實。

它可能因為幾種原因而失敗。

使用者可能看不懂欄位的意思；可能知道缺少什麼，卻不知道去哪裡拿；也可能知道資料在哪裡，但沒有權限取得。

你應該把原本的想法轉換成可以驗證的敘述。

| 項目   | 具體例子                |
| ---- | ------------------- |
| 假設   | 明確列出缺漏欄位，能幫助使用者自行修正 |
| 驗證方式 | 讓使用者在不接受提示下完成指定補件任務 |
| 觀察指標 | 無提示完成率、卡住的位置與原因     |
| 反證條件 | 使用者看懂提示，仍反覆無法找到資料來源 |
| 下一步  | 訪談資料取得流程，或改善提示設計    |

最有價值的是「反證條件」。

它在問：

什麼結果出現時，我願意承認原本的想法需要修改？

這也是科學研究和工程驗證的重要共同點。

在研究論文中，你提出 Hypothesis，安排實驗取得 Evidence，最後才形成 Conclusion。

在軟體工程中也是一樣，只是證據可能來自功能測試、使用者任務測試或實際營運資料。

## 六、需求紀錄：為什麼不能隨便改掉原本的要求？

現在進入最後一個關鍵觀念：Traceability（可追溯性）。

想像一個開發情境。

原始需求寫著：

「使用者完成資料檢查後，可以匯出報告。」

工程師已經完成這個功能。

可是測試時發現一個問題。

@figure5

這個問題非常典型。

原本的需求不一定寫錯，但它不夠完整。

因此，不能只是悄悄把原始需求改掉，而是應該記錄：

| 紀錄類型    | 範例                |
| ------- | ----------------- |
| R-01 需求 | 缺件不得完整匯出          |
| H-01 假設 | 明確提示缺漏，有助於使用者自行修正 |
| M-01 指標 | 指定缺漏案例必須全數阻擋      |
| C-01 變更 | 輸入修改後，先前檢查結果失效    |
| 變更理由    | 發現可能使用過期檢查結果匯出    |
| 驗收證據    | 待測試，目前尚未取得        |

這個表格有什麼價值？

三個月後，新工程師可能問：「為什麼每次修改資料，都一定要重新檢查？」

有了紀錄，你可以指出原始需求、發現的風險、決策理由，以及驗證這項規則的測試。

這就是需求可追溯性。它不只是文件管理，更是讓系統長期可維護的重要工程能力。

H、M、R、C 只是教材示範的分類代號，不是強制使用的標準。

## 七、實務上怎麼運用？一張表就能開始

在實際開發 MVP 時，不一定需要導入大型需求管理系統。

可以先用 Markdown 建立 `problem.md`，把最重要的資訊放在一起。

這裡提供一份精簡示範：

```
# AI 文件收件系統

## 問題
使用者常因資料缺漏，產生不完整報告。

## 需求 R-01
缺件時不得完整匯出報告。

## 假設 H-01
顯示缺漏欄位可以協助使用者自行修正。

狀態：尚未驗證

## 功能指標 M-01
名稱：缺漏阻擋率
公式：阻擋成功數 / 指定缺漏案例數
要求：指定案例全數阻擋
結果：未測量

## 任務指標 M-02
名稱：無提示完成率
公式：無提示完成者 / 開始任務者
結果：未測量

## 變更 C-01
修改輸入後，舊檢查結果必須失效。

理由：避免以過期結果匯出。

## 待補證據
- 功能測試結果
- 使用者測試紀錄
- 驗收決策
```

注意這份文件最有價值的地方，不是它有多少欄位。

而是任何人打開，都能知道：

「我們要解決什麼問題？目前相信什麼？怎麼判定成功？實際驗證到什麼程度？為什麼要改？」

這樣的文件才能真正支援開發、驗收與維護。

## 八、把今天學的東西放進更大的工程觀念

你可以把 M03-05 視為連接「需求工程」與「軟體測試」的一座橋。

| 你想回答的問題       | 對應工程概念                        |
| ------------- | ----------------------------- |
| 系統應該做什麼？      | Requirements Engineering      |
| 為什麼這樣設計可能有效？  | Hypothesis                    |
| 怎麼判斷它有沒有做好？   | Metrics / Acceptance Criteria |
| 怎麼取得可靠結果？     | Testing / Evaluation          |
| 怎麼知道每項規則從哪裡來？ | Requirements Traceability     |
| 發現不符合預期時怎麼辦？  | Change Management             |

其中需要特別區分三個常被混淆的詞：

Verification（驗證是否符合規格）：我們有沒有把系統按照要求做對？

Validation（確認是否滿足真實需求）：我們做出來的東西，是否真的適合使用者要完成的工作？

Evaluation（評估）：透過既定指標與方法，衡量系統表現及其限制。

例如，系統能夠正確辨識缺漏，屬於重要的 Verification 證據；使用者能靠它順利完成補件工作，則能提供 Validation 證據。

兩者相互補充，但都不能靠空口宣稱。

## 九、今天的理解測驗

以下是新的合成情境，請先自己作答；本節先保留問題，參考答案可在下方「理解檢核與參考解析」展開。

一家醫院正在測試 AI 文件檢查系統。

工程師準備了五筆缺漏案例，其中四筆被成功阻擋，另一筆卻仍然可以匯出。

另外，四名參與者開始使用系統，其中兩人自行完成、一人需要工作人員提示、一人放棄。

專案經理宣稱：「我們預計讓每位使用者節省八分鐘，所以系統已經具備上線價值。」

請回答：

1. 這次的缺漏阻擋率是多少？如果驗收要求是指定缺漏案例全數阻擋，能否通過？
2. 無提示完成率是多少？需要提示的使用者應不應該算入分母？
3. 「節省八分鐘」目前屬於假設、已測量結果，還是正式結論？要怎麼驗證？
4. 如果發現修改資料後，系統仍使用舊的檢查結果，你會新增什麼需求？要保留哪些變更紀錄？

本課最終重點：成功不是你做了多少事情，而是你能拿出多少可靠、適切的證據，證明真正的問題已經獲得改善。
