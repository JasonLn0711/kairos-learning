# M03-05｜成功指標、假設與需求紀錄：如何證明我們做的系統真的有用？

這堂課最重要的觀念是：做出一個功能，不代表解決了一個問題；而且，即使問題看起來改善了，也不代表一定是你的系統造成的。

我們必須學會三件事情：

1. 定義成功（Success Criteria）：怎樣的結果才算真正成功？
2. 驗證假設（Hypothesis Testing）：我們相信某個設計有用，有沒有證據支持？
3. 保留需求紀錄（Requirements Traceability）：為什麼當初要這樣設計？後來為什麼修改？結果有沒有通過驗證？

這些能力不只適用於軟體工程，也適用於醫療、金融、教育、製造、政府行政、科學研究，甚至企業管理。

本課以跨產業例子說明成功指標、假設與需求紀錄，以及實務上的驗證方法。

## 一、先理解整堂課的核心：我們怎麼知道一件事情真的改善了？

假設有一家醫院，病人從報到到看診，平均需要等待 50 分鐘。

院長希望改善這個問題，於是資訊部門開發了一套 AI 智慧掛號與分流系統。

三個月後，資訊部門向院長報告：

「我們完成了 15 個功能、導入了 AI、自動化了掛號作業，而且系統可以在兩秒內處理一筆資料。」

院長可能會回答：

「很好，但病人現在還是要等 50 分鐘嗎？」

這就是本堂課的起點。

系統處理速度變快，不代表病人等待時間就會縮短。真正的瓶頸也許是醫師人力不足，或檢查室排程不合理。

因此，我們必須區分：

- 產出（Output）：我們做出了什麼？例如完成 AI 掛號功能。
- 結果（Outcome）：使用者的情況有沒有改善？例如平均候診時間縮短。
- 影響（Impact）：長期而言，這項改善帶來什麼價值？例如減少延誤、改善醫療服務品質。

注意：需求是「系統應該做到什麼」；假設是「為什麼這麼做可能有效」；指標是「我們打算怎麼判定效果」。這三者不能混為一談。

## 二、功能成功與使用者成功，是兩件不同的事

我們先認識兩個非常重要的詞。

Functional Metric（功能指標），指的是系統是否按照規定正確運作。

Task Metric（任務指標），指的是使用者是否真的能完成原本要做的事情。

例如，一家銀行導入 AI 文件辨識系統。

工程師說：「我們的文件辨識 API 可以正常回傳資料，而且 99% 的請求都沒有發生系統錯誤。」

這是功能方面的好消息。

但銀行的徵信人員可能說：「我還是需要花很長的時間修正辨識結果，而且現在多了一道檢查步驟。」

也就是說，系統正常運作，卻不一定提高工作效率。

我們再比較幾個不同產業。

| 產業   | 功能指標：系統做得對嗎？  | 任務指標：人真的受益嗎？       |
| ---- | ------------- | ------------------ |
| 醫療   | AI 是否正確讀取病歷欄位 | 醫護能否更快完成正確紀錄       |
| 物流   | 配送演算法是否成功產生路線 | 貨物是否準時送達           |
| 教育   | AI 是否成功產生練習題  | 學生是否真正學會解題         |
| 製造   | 瑕疵檢測是否正確辨識缺陷  | 能否減少不良品流出，又不過度誤擋良品 |
| 政府行政 | 系統是否正確檢查申請文件  | 民眾能否自行完成申請         |

因此，不能只測試程式有沒有出錯，還要看人能不能完成工作。

而且，最好再加入第三種觀察角度：Guardrail Metric（護欄指標）。

它的意思是，改善一件事情時，不可以讓另一件重要的事情變得更糟。

例如：

一家物流公司希望提高配送速度，但不能因此增加交通事故；一家醫院希望減少候診時間，但不能因此提高病歷或分流錯誤。

這三種角度共同回答：系統是否值得採用？

## 三、成功指標要怎麼計算？最重要的是分母

很多人會說：「我們的系統有 90% 的成功率。」

但這句話其實沒有想像中那麼有意義。

我們應該追問：「90% 是從哪些案例計算出來的？什麼叫成功？有沒有排除失敗的案例？」

### 例子：工廠的瑕疵檢測系統

假設工廠正在試驗一套 AI 檢測設備。

我們準備六件測試產品，其中四件確實有瑕疵，另外兩件是良品。

| 產品 | 真實狀態 | AI 決定 |
| -- | ---- | ----- |
| A  | 有瑕疵  | 阻擋    |
| B  | 有瑕疵  | 阻擋    |
| C  | 有瑕疵  | 阻擋    |
| D  | 有瑕疵  | 錯誤放行  |
| E  | 良品   | 放行    |
| F  | 良品   | 放行    |

如果問題是「有瑕疵的產品，有多少比例被成功阻擋？」

那麼公式就是：

瑕疵阻擋率＝成功阻擋的瑕疵品／全部瑕疵品。

這裡是 3／4＝75%。

請注意，分母是四件瑕疵品，不是全部六件產品。

## 分母、錯誤代價與小樣本界線

這個例子其實引出了機器學習當中很重要的觀念：

- False Negative（偽陰性，漏判）：真的有問題，系統卻沒有發現。
- False Positive（偽陽性，誤判）：原本沒有問題，系統卻誤認為有問題。

如果是醫療檢查，漏判可能意味著沒有發現疾病；如果是銀行反詐騙，誤判可能意味著正常交易被阻擋。

不同產業的錯誤代價不同，因此成功指標及驗收標準也不應該完全相同。

另外有兩個容易出錯的地方。

首先，假設根本沒有任何瑕疵測試案例，分母就是零。這時不能把阻擋率寫成 100%，應該寫「未測得」，因為根本沒有驗證到這種情況。

其次，四件瑕疵品都成功阻擋，只能說這四件測試案例全部通過，不能直接推論整個系統的真實準確率必定為 100%。

小樣本通過驗收，與證明整體可靠性，是不同層次的主張。

## 四、為什麼系統變快了，不代表它真的提高效率？

這是本章非常值得深入理解的部分。

假設一家律師事務所想使用 AI 協助整理案件資料。

原本律師需要 30 分鐘整理一份文件，使用 AI 後，系統只需要 5 分鐘就能生成摘要。

於是軟體公司宣稱：「工作效率提高六倍。」

但是我們繼續觀察，發現律師還需要花 20 分鐘確認 AI 摘要是否正確。

實際上：

| 工作流程      | 舊方式    | AI 方式 |
| --------- | ------ | ----- |
| 資料整理及產生摘要 | 30 分鐘  | 5 分鐘  |
| 檢查與修正     | 已含於原流程 | 20 分鐘 |
| 總時間       | 30 分鐘  | 25 分鐘 |

這是示意數字。真正節省的工作時間只有 5 分鐘，約 16.7%，不是六倍的整體效率。

更重要的是，我們還不知道 AI 是否增加了錯誤風險。

### 這時要認識 Baseline（基準值）

Baseline 就是改善之前的狀況。

例如，原本平均要 30 分鐘，這個 30 分鐘就可以作為比較基準。但必須確定兩邊測量的是相同工作。

英國政府的數位服務績效指南也強調，指標要連結服務目的、建立基準值、確認資料來源，並結合使用者研究，而不是只有漂亮的績效數字。

實務上，我們要注意三個問題。

第一，起點與終點必須一致。

舊方式從收到文件開始算，新方式卻從文件已經整理完畢才開始計時，這不是公平比較。

第二，完成品質必須一致。

舊流程做出正確文件，新流程雖然比較快，卻有三處重要錯誤，不能直接當成效率改善。

第三，必須排除其他可能原因。

例如，律師第二次整理相同案件，原本就比較熟悉資料，自然會更快。

這叫做 Practice Effect（練習效應）。

如果要嚴謹比較，可以讓不同參與者交換使用新舊系統的順序，並使用難度相近的任務。這種設計稱為 Counterbalancing（平衡順序設計）。

還要記錄沒有完成工作的人。如果十個人只有五個人成功，就不能只計算這五個成功者的速度，完全不提其餘五人的失敗。

## 五、Hypothesis：假設不是事實，而是等待驗證的想法

很多系統設計錯誤，不是工程師不會寫程式，而是大家一開始相信了一個沒有驗證過的想法。

例如，一所大學發現學生在數學課的成績不佳。

校方提出：「我們應該開發 AI 家教系統，讓學生隨時提問。」

這是一個可能合理的方案，但並不表示 AI 家教一定能改善學習。

學生的問題也許是缺乏先備知識、練習不足，或不理解教材使用的符號。

因此，我們應該寫出可以驗證的假設。

@figure4

這裡最重要的是「反證」。

你不只是問：「有什麼證據支持我的設計？」

你還要問：「出現什麼結果時，我應該承認這個設計可能沒有達到目標？」

這就是 Falsifiability（可反駁性）在工程實務中的精神。

不過，假設沒有獲得支持，不一定代表它已經被徹底推翻。也可能是樣本太少、測量不敏感，或實驗設計存在問題。因此應綜合證據品質、效果大小與不確定性判斷。

## 六、需求紀錄為什麼重要？因為半年後沒有人記得當初為什麼這麼設計

我們換到金融業來看。

假設銀行開發一套 AI 徵信報告系統。

最早的需求是：

「使用者可以上傳資料，經過檢查後，產生報告。」

工程師完成之後，測試人員發現一個問題：

@figure5

因此工程師增加了一條新規則：

「只要會影響檢查結果的資料被修改，先前的通過狀態就必須失效，重新檢查後才能匯出。」

但如果工程師只是直接修改程式，沒有記錄原因，未來接手的人可能會問：

「為什麼每次修改一個欄位，都必須重新檢查？能不能把它移除來提升效能？」

他可能不知道，這條規則其實是為了避免輸出未經驗證的金融資料。

這就需要 Requirements Traceability（需求可追溯性）。

它的本質是：

讓每一個重要決定，都能追查它源自哪個問題、由誰確認、為什麼改變，以及如何證明它已經實現。

例如：

| 編號   | 類型          | 紀錄                    |
| ---- | ----------- | --------------------- |
| R-01 | Requirement | 重要資料修改後必須重新檢查         |
| H-01 | Hypothesis  | 自動使舊狀態失效，可降低未經檢查匯出的風險 |
| M-01 | Metric      | 指定的過期狀態測試案例必須全部阻擋     |
| T-01 | Test        | 修改金額、姓名等影響檢查結果的欄位後測試  |
| C-01 | Change      | 新增檢查結果失效機制            |
| E-01 | Evidence    | 待執行測試，尚未取得結果          |

這些代號只是方便管理的示範，並不是唯一的正式標準。

實際上還應記錄來源、提出者、確認角色、日期、版本、決策理由以及狀態。這能避免把尚未確認的建議，誤當成已核准需求。

## 七、Verification、Validation、Evaluation 有什麼不同？

這三個英文詞在 AI 與軟體工程中很容易混淆。

| 名詞           | 白話文           | 主要問題        |
| ------------ | ------------- | ----------- |
| Verification | 按照規格做對了嗎？     | 系統是否符合要求？   |
| Validation   | 做的是使用者真正需要的嗎？ | 系統能否解決實際問題？ |
| Evaluation   | 效果到底有多好？      | 透過什麼指標衡量表現？ |

例如，一家餐廳開發自助點餐系統。

Verification 是檢查「按下送出訂單，廚房是否收到正確餐點與數量」。

Validation 是檢查「客人能否順利完成點餐，而且這個系統是否真的改善服務問題」。

Evaluation 則是測量「點餐平均花多少時間、訂錯率多少、完成率多少」。

它們不是彼此取代，而是互相補充。

## 八、實務上怎麼開始？用一份 problem.md 就足夠

M03-05 很重要的一個精神，是不要為了管理需求而先導入過度複雜的工具。

小型專案可以先從 Markdown 文件開始。

下面用「物流配送異常通知系統」示範。

```

# 專案：物流配送異常通知

## Problem｜問題
顧客無法及時知道配送異常，
導致反覆查詢客服。

## Requirement｜需求
R-01：配送異常發生後，
系統應發送明確的異常通知。

狀態：需求候選，待業務確認。

## Hypothesis｜假設
H-01：主動通知異常及處理方式，
可以降低顧客重複查詢。

狀態：尚未驗證。

## Metric｜成功指標
M-01：通知成功送達率
公式：成功送達數 / 應通知事件數

M-02：重複查詢率
公式：指定期間內重複查詢的異常訂單數
      / 同期間符合條件的異常訂單數

M-03：異常處理完成時間
起點：異常首次被記錄
終點：異常處理完成且狀態確認

上述指標均需確認適用範圍、
資料來源、測量期間與成功門檻。

## Evidence｜證據
基準值：未測量
新系統結果：未測量
測試紀錄：尚未取得

## Change Log｜變更紀錄
C-01：待確認是否新增通知重試機制
原因：通知可能無法成功送達
決策者：待確認
日期：待確認
狀態：提案中

```

這份文件有兩個關鍵價值。

第一，它把問題、需求、假設、指標與證據接在一起，避免只記錄功能清單。

第二，它明確區分「我們打算做到」與「我們已經證明做到」。

尤其要注意，不能因為 AI 已經產生測試計畫，就把測試結果寫成通過。

AI 可以協助撰寫需求、設計測試案例、整理執行紀錄，但它沒有實際觀察到的結果，就不應宣稱驗收完成。

## 九、將這堂課轉換成真正可執行的工作方法

當你下一次要設計一個 AI 系統，不論是醫療、教育、研究或企業服務，都可以先完成以下五項工作。

| 順序 | 你需要回答的問題     | 應留下的成果           |
| -- | ------------ | ---------------- |
| 1  | 我們究竟要改善什麼？   | 清楚的問題敘述          |
| 2  | 系統必須做到哪些事情？  | 可測試的需求           |
| 3  | 為什麼相信這個設計有用？ | 可被反駁的假設          |
| 4  | 用什麼證據判定成功？   | 指標、分母、基準、門檻、資料來源 |
| 5  | 如何處理測試與變更？   | 測試證據、驗收決策、變更紀錄   |

這份架構也與 英國 GOV.UK 的服務績效指標設計指南（本課下方來源連結） 一致：先理解服務目的，再提出假設、決定如何測量、找到資料來源，最後根據結果持續修正。

在需要進行正式驗收的專案，還應為重要指標預先設定通過條件，並考慮樣本代表性、風險、成本及測量的不確定性。

## 十、理解檢核：你能不能辨識不可靠的成功宣稱？

@figure6

請回答：

1. 指標計算：這套 AI 的瑕疵阻擋率是多少？良品正確放行率是多少？兩個指標分別告訴我們什麼？
2. 證據判斷：10 分鐘變成 7 分鐘，是否足以證明生產效率提高 30%？還缺少哪些資訊？
3. 假設驗證：如果管理層相信「AI 可以降低品質檢查成本」，你會如何把這句話轉換成可驗證的假設？
4. 需求追溯：如果後續發現機器重新校正後，先前的合格判斷可能已經不適用，你會增加什麼需求，又該留下哪些紀錄？
5. 整體決策：假設你是這間工廠的專案負責人，根據現有證據，你會決定直接全面上線、繼續限制範圍試驗，還是停止計畫？為什麼？

請先嘗試回答，再展開參考解析，逐項檢查推理與計算。

最後記住這堂課最重要的一句話：好的工程，不只是把東西做出來，而是能清楚說明為什麼要做、如何判斷成功，以及有什麼證據支持我們的決定。
