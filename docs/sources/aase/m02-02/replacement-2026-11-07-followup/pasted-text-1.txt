# AASE M02-02｜Context Window 與長對話限制：為什麼 AI 明明聽過，卻還是會忘記？

這一課要理解大型語言模型（LLM）非常重要的一個限制：AI 不是能夠隨時翻閱所有過去紀錄的工程師。它每一次回答，主要依靠當次實際取得的資訊。

先記住三句話：

1. 資料有保存，不代表 AI 這一次看得到。
2. AI 看得到，不代表它一定會正確理解與使用。
3. 真正可靠的 AI 工作流程，不是要求 AI 永遠記住，而是確保它每次取得正確資料，並驗證結果。

這正是教材 M02-02 v1.1.0（2026 年 11 月 7 日修訂）的核心。

## 一、把 Context Window 想成工程師的工作桌

想像你聘請了一位非常聰明的工程師，他會寫程式、處理資料、設計網站。

公司有一間很大的資料室，存放著數千份文件。但是工程師工作的時候，只能看見當下擺在桌上的資料。

公司資料室

保存的聊天紀錄、文件、程式碼、資料庫

工程師的工作桌

本次真正取得的規則、需求、相關資料

必須選取資料，不能假設全部都已讀取

Context Window = 工程師這一次能使用的工作桌空間

假設：

- 公司保存了 1,000 份文件。
- 工程師這一次只拿到 10 份。
- 第 237 份文件記載著非常重要的安全規則，但沒有人把它拿到桌上。

即使工程師能力再強，也不能保證他知道第 237 份文件的內容。

AI 也是如此。

所以，當你發現 ChatGPT 或 Coding Agent 沒有遵守之前訂下的規則，第一件事情不是責怪模型，而是確認：

這一次模型實際收到的資料，到底有沒有包含那項規則？

這就是理解 Context Window 的第一個關鍵。

## 二、AI 的工作桌上，到底放了什麼？

一次模型呼叫（Model Invocation），通常不只有你剛剛輸入的問題。

一次 AI 工作可能包含的資料

1

系統規則

AI 必須遵守的工作要求

2

你現在的問題

例如：修改網站的按鈕顏色

3

歷史對話或摘要

之前討論過的設計與決策

4

外部資料及工具回傳

程式碼、文件、Git 內容、測試輸出

5

預留回答空間

留給模型接下來產生的內容

模型根據當次取得的資訊產生回答

以上是概念示意，實際封裝與容量規則依服務而異

這裡需要認識 Token。

Token 是模型處理資訊的基本單位，不保證等於一個中文字或英文單字。Context Window 的容量通常用 Token 數量表示。

因此，當你讓 AI 讀取一份很長的程式碼、十份文件和大量測試日誌時，它們都可能占用這次工作的上下文容量。

而且，模型在訓練中學到的知識、聊天歷史、外部 Memory 和目前 Context，是不同的東西。

例如 Git 裡面已經有 `requirements.md`，不代表 AI 這一次真的讀取了這個檔案。

## 三、實際操作：為什麼 Context Window 會不夠用？

教材設計了一個 10,000 Token 的假想模型。這裡把它做成可以操作的實驗。

Context Window 容量實驗

# 9,500

# 500

0

10,000

額外加入的日誌

500 Token

預設 500試試 1,800最大 3,000

目前在假設容量內

容量裝得下，不代表 AI 一定會正確使用每項資訊。

固定內容包括系統規則 1,000、需求與程式 2,000、測試紀錄 4,500，以及預留回答 1,500，合計 9,000 Token。

當你把額外日誌增加到 1,800 Token，總需求就成為 10,800，超過容量 800。

但是注意一件事：多出來的 1,300 Token 日誌，不代表 AI 更了解你的需求。

假設那些日誌只是在重複列印「服務啟動成功」，那麼它們占用了空間，卻可能沒有帶來有用資訊。

這就是為什麼 AI 工程不只是選擇大模型，也需要 Context Management（上下文管理）。

## 四、Context Window 很大，為什麼 AI 還是可能做錯？

這裡是本課最重要的技術判斷。

想像你在設計一個網站。第一天已經規定採用暖象牙白與陶土紅。四天之後，AI 卻將網站改成紫色。

我們不能直接說「AI 忘記了」。

因為至少有四種不同原因：

| 問題   | 白話解釋             | 應該怎麼處理   |
| ---- | ---------------- | -------- |
| 容量不足 | 桌子放不下全部資料        | 篩選、摘要、分段 |
| 資料選錯 | 桌上根本沒有正確規格       | 正確讀取與檢索  |
| 資料衝突 | 新舊配色規則混在一起       | 明確管理版本   |
| 使用失誤 | 規則就在眼前，但 AI 仍然做錯 | 測試、審查與驗收 |

這四個原因，不能只靠增加 Context Window 一次解決。

還有一個研究概念稱為 Lost in the Middle，意思是長篇資料裡，資訊放在哪個位置，也可能影響模型使用該資訊的表現。

研究在特定多文件問答與資訊檢索任務中觀察到，模型對位於長上下文中間的資訊，有時表現較差。但這不是所有模型都必然遵循的定律。

[image](https://www.google.com/s2/favicons?domain=https://arxiv.org\&sz=32)

因此，容量大小和有效理解能力是兩個不同維度。

## 五、工程實務：不要只靠對話，建立真正的工作交接

假設你和 Coding Agent 花了三天開發一個醫院收件系統，現在發現：

「使用者缺少必填文件，系統竟然仍顯示收件完成。」

你只告訴 Agent：

> 幫我繼續修正，按照之前的規定處理。

這個要求有風險。因為 Agent 可能不知道你說的「之前規定」是哪一個版本。

更可靠的方式，是交給它一份任務工作包（Task Package）。

示範：可交接的 AI 任務

| 工作目標 | 修正收件完成狀態的判斷錯誤             |
| ---- | ------------------------- |
| 有效規格 | `docs/requirements-v3.md` |
| 錯誤證據 | 測試 T-04：缺少必填附件仍顯示完成       |
| 未決問題 | 選填文件是否影響完成狀態              |
| 修改範圍 | 僅修改狀態判斷與相關測試              |
| 停止條件 | 遇到需求衝突先回報                 |
| 完成標準 | T-04 測試通過，並提供實際結果         |

以上檔名、需求及測試都是教材的虛構案例。

這時，即使你換一個新的 AI Agent，它也能按照明確的任務資料繼續工作，而不必依賴三天前的對話紀錄。

這裡再介紹一個重要名詞：Source of Truth（可信的規格正本）。

意思是當多份文件或對話說法不一致時，要明確知道哪份有效規格具有權威性，而不是讓 AI 自己猜。

可靠的 Agent 工作循環

規格正本與版本紀錄

確認現在有效的規則

選取本次需要的 Context

包含正確文件、程式與必要證據

AI Agent 執行工作

讀取、分析、修改、執行工具

測試與審查結果

確認真的符合規格，而非僅相信 AI 宣稱

確認新決策後，更新規格正本供下次使用

這套作法屬於更廣泛的 Context Engineering（上下文工程）：設計模型應該取得什麼資訊、什麼時候取得、如何保留有效狀態，以及如何減少無關資料干擾。

## 六、對話太長，要不要重新開一個？

不必每次都開新對話，也不該只因為對話很長就重新開始。

當目標一致、需求沒有衝突、相關資料仍然清楚，可以繼續原本的對話。

當需求已多次變動、累積大量與任務無關的訊息，或 Agent 持續引用過期規格時，則比較適合先建立交接資料，再開啟新的工作階段。

但開新對話本身不會修復錯誤規格。如果把錯誤摘要交給新 Agent，新 Agent 仍然可能繼續犯錯。

這也連結到下一課 M02-03：Compaction 用來壓縮歷史、RAG 用來檢索資料、Memory 用來保存可供後續使用的資訊。這些方法都能協助管理長任務，但不能替代正確性驗證。

## 七、理解檢核：你能診斷 AI 為什麼犯錯嗎？

假設你讓 Coding Agent 開發醫院內部系統。

昨天你已經明確要求：「只有管理員可以刪除病歷相關紀錄。」

今天 Agent 卻把刪除功能開放給所有登入使用者。

問題 1：你現在能夠判定錯誤原因嗎？

A. 可以，一定是 Context Window 滿了

B. 可以，一定是模型能力不足

C. 還不能，需要檢查實際上下文、版本及執行結果

D. 可以，只要更換更大的模型就能解決

問題 2：你會怎麼查明真正原因？

提交答案，請幫我評分&#x20;

這一課學完之後，最值得保留的能力，是遇到 AI 工作失誤時，能夠區分「沒有取得資料」、「取得了錯誤版本」和「已取得正確資料但仍執行錯誤」，再選擇對應的修正方式。
