# AASE M02-02｜為什麼 AI 明明聽過，卻又忘記？認識 Context Window（上下文視窗）

這堂課最重要的觀念是：

AI 並不是每次回答問題時，都會重新閱讀你們過去講過的所有事情。它主要依靠「這一次實際取得的資訊」來回答。

而 Context Window，就是限制這些資訊一次能放進多少的機制。

## 一、先用生活例子理解：AI 的工作桌

想像你聘請了一位非常聰明的工程師。他會寫程式、會分析文件，也能幫你設計網站。

但這位工程師有一個特殊的工作習慣：

每次工作時，他只能根據桌面上擺出來的資料做判斷。

概念示意：左邊資料即使都存在，也不代表右邊的模型工作視窗已經取得全部內容。

例如：

第一天，你告訴 AI：「我們的網站主要使用暖象牙白，搭配陶土紅。」

第二天，你告訴它：「按鈕要統一圓角，標題要保持一致。」

第三天，你們又討論了 100 個程式錯誤、20 次修改、50 份測試紀錄。

第四天，你說：「幫我繼續做網站。」

結果 AI 突然把網站設計成紫色。

你可能會想：「奇怪！我不是早就跟你講過要用陶土紅了嗎？」

但這裡可能有三種情況：

1. 沒看到：最早的配色規則沒有進入這次的 Context Window。
2. 看錯了：新舊設計紀錄混在一起，它採用了過時版本。
3. 看到了卻沒照做：規則其實在上下文裡，但模型仍然犯錯。

這三種問題的解法不同。

## 二、Context Window 裡面究竟裝了什麼？

Context Window 通常以 Token 作為容量單位。

你上一堂 M02-01 已經學過，Token 是模型處理文字的基本單位，不等於一個中文字或一個英文單字。

當你向 AI 說「請幫我修改這段程式」，它可能不只收到這一句話。

一次 AI 工作可能需要的上下文

系統規則與工具說明

你現在提出的要求

部分歷史對話與摘要

程式碼、文件與查詢結果

模型正在產生的回答

實際組合、資訊選取方式以及容量計算，會依模型與 AI 服務而不同。

這裡有一個非常容易搞錯的地方：

Chat History（聊天歷史）不等於 Context Window（目前上下文）。

你在 ChatGPT 裡面往上滑，可能看到好幾個月前的對話。

但畫面顯示聊天紀錄，只能證明紀錄還能被介面呈現，不代表每次生成答案時模型都收到完整歷史。

這就像公司有十年的公文存檔，卻不代表承辦人每次辦案，都能同時閱讀十年的所有公文。

此外，模型本身的訓練知識、個人化 Memory（記憶）、外部文件檢索，也都不是與 Context Window 完全相同的概念。它們可以協助找資料，但必須透過相應機制，才能讓相關資訊參與這次回答。

## 三、用一個互動實驗，看看為什麼上下文會爆滿

我們假設某個 AI 系統一次可使用 10,000 Token，而且以下練習把輸入與預留輸出放在同一個預算中。

已使用 Token

# 9,500 / 10,000

容量範圍內

系統規則：1,000

需求及程式：2,000

測試紀錄：4,500

預留回答：1,500

額外日誌：500

額外加入的日誌

500 Token

03,000

剩餘 500 Token

目前還在假設的預算內，但這並不保證模型一定能正確使用所有資訊。

試試加入 1,800 Token 日誌此圖僅展示教材中的簡化預算，並非任何特定模型的實際限制。

你可以試著把滑桿往右拉。

注意到一個現象沒有？真正重要的需求、程式碼與測試證據，其實並沒有增加。但是無關日誌增加，依然會擠占整體容量。

所以，工程師不能只想：「我要讓 AI 看到越多資料越好。」

應該想：

我要讓 AI 看到完成這個任務所需要的資料，而且優先保障重要資訊。

這叫做 Context Management（上下文管理）。

## 四、為什麼換成超大 Context Window，也不一定能解決問題？

想像兩位學生：

學生 A 的桌子只能放 10 本書。

學生 B 的桌子能放 100 本書。

你問他們：「根據最新版規範，申請資料應該填寫哪些欄位？」

學生 B 雖然有 100 本書，但如果裡面混了 30 份舊版規範、20 份沒有標註日期的文件，仍然可能找錯。

同樣的道理，AI 的問題不只是容量。

| 問題   | 白話意思      | 改善方向     |
| ---- | --------- | -------- |
| 容量不足 | 桌子擺不下     | 選取、摘要、分段 |
| 資料選錯 | 桌上沒有正確文件  | 檢索與選材    |
| 資料衝突 | 新舊規則互相打架  | 版本管理     |
| 使用失誤 | 資料就在眼前仍看錯 | 測試與驗收    |

這也解釋為什麼大模型有時會出現一種現象：明明給它很多資訊，但它對中間某些細節的利用不穩定。這類問題有時被稱作 Lost in the Middle，但不是所有模型、所有任務都會出現相同程度的情況。

因此：

- Context Window 解決「一次可能放多少」。
- 資訊檢索解決「這次需要拿什麼」。
- 版本管理解決「哪一份才有效」。
- 驗證機制解決「究竟有沒有做對」。

這四個工作不能互相取代。

## 五、真正的工程做法：不要依賴 AI 記憶，而是建立可以交接的工作資料

回到 AASE 課程中的「文件收件與缺漏檢查系統」。

假設你正在用 Coding Agent 開發它。

你們前面花了很長時間討論規格，現在想修正其中一個錯誤：使用者缺少必填文件，系統卻顯示「收件完成」。

不好的指令是：

> 幫我繼續修改剛剛的收件工具。你應該知道規則是什麼。

比較好的指令是：

任務交接範例

&#x20;複製

目標： 修正收件狀態判斷錯誤。

有效規格： 以 `docs/requirements-v3.md` 為準，缺少必填文件不得顯示「收件完成」。

已有證據： 測試 T-04 顯示缺少附件時，系統仍回報完成。

未決問題： 選填文件是否影響狀態，尚未確認。

工作範圍： 只修改狀態判斷邏輯與相關測試，不修改 UI 配色。

停止條件： 遇到需求衝突或需要決定選填文件規則時先回報。

完成條件： T-04 測試通過，提供實際測試結果。

路徑、規格及測試案例均為教學假設，並非已建立或驗證的專案檔案。

這樣做的好處是，即使明天換另一個 AI Agent，對方也能知道：

現在要做什麼、應該遵守什麼規格、哪些東西不能動、怎麼判斷工作完成。

這叫做 Handoff（任務交接）。

更進一步，軟體工程通常會把這些資訊保存在 Git 專案中的規格文件、測試檔與版本紀錄裡，而不是全部依賴聊天對話。

可以把整個流程理解為：

規格正本（Source of Truth）

現在有效的規則與版本

選取相關資料

只拿本次需要的規格、程式與證據

AI Agent 執行任務

使用目前取得的 Context

測試、審查與更新紀錄

有證據後才確認完成，必要時正式更新規格

這裡最值得記住的是：摘要不是正本，AI 的回答也不是驗證結果。

例如，摘要寫著「需求已全部完成」，但 Git 裡的測試仍然失敗，我們就不能因為摘要這樣說而當成完成。

如果修改規格，也要把新決策正式記錄在正本，避免下一次 AI 又拿到舊版本。

## 六、以後實際使用 AI 時，怎麼判斷要不要開新對話？

不是每次開新對話都比較好，也不是越長的對話越好。

如果工作目標沒有改變，相關資料清楚，現有對話通常還可以繼續。

但如果任務已經歷經多次需求變更、累積大量無關日誌，甚至 AI 反覆引用錯誤的舊規格，那就值得整理一份交接資料，再開始一個乾淨的工作階段。

關鍵不是「讓 AI 忘記過去」，而是把過去真正有價值的資訊，重新整理成現在可以使用的正確上下文。

## 七、理解檢核：你能判斷 AI 到底出了什麼問題嗎？

假設你們用 AI Agent 開發一個醫院內部的收件系統。

昨天已經確認：只有管理員可以刪除收件紀錄。

今天 AI 卻把刪除按鈕開放給所有登入使用者。

請試著回答三個問題：

問題 1：可以直接認定 AI 是因為 Context Window 滿了才犯錯嗎？

可以，一定是舊規則被排除。

不能，還需要檢查上下文與執行證據。

不必檢查，一定是模型不夠聰明。

問題 2：如果需求規格已經存在 Git 裡，為什麼 AI 仍然可能不知道這項權限規則？

問題 3：你會如何修改交接方式，避免下一次再發生相同錯誤？

提交答案，請 AI 評估

這堂課可以濃縮為一句話：

優秀的 AI 協作工程，不是要求 AI 永遠記住所有事，而是設計一個工作流程，讓 AI 每次都能取得正確的規格、必要的證據，並且能驗證自己的工作成果。
