# AASE M02-04｜Chatbot、Workflow 與 Agent 白話教學

這一課要理解一件非常重要的事情：AI 可以幫我們做事，但我們究竟要讓 AI 自己決定怎麼做，還是事先替它安排好做事的步驟？

這是設計 AI 系統時最核心的選擇之一。

先記住三句話：

- Chatbot（聊天機器人）：你跟系統說話的方式。
- Workflow（工作流程）：我們事先規定系統要怎麼做。
- Agent（代理系統）：我們給它目標，它根據觀察到的情況，決定下一步要做什麼。

當情況發生變化時，誰負責決定下一個動作？

## 二、從資訊工程角度，三者如何運作？

我們用同一個「讀書計畫系統」來比較。

### Chatbot：對話不等於執行

你問 Chatbot：

「我星期六想念三科，可以嗎？」

它可能回答：「如果你的時間足夠，可以考慮安排三科。」

但這只是文字建議。它可能根本沒有讀取你的正式規則，也沒有修改你的讀書計畫。

重點：回答問題，不代表已經替你執行工作。

### Workflow：規則事先寫好

假設規則是：

- 平日最多兩科。
- 週末最多三科。
- 超過上限不能儲存。

使用者按下「儲存」

程式檢查日期與科目數量

根據預先設定的規則判斷

符合規則

儲存成功

不符合規則

拒絕儲存並提示修改

這裡沒有必要叫 LLM 重新思考「星期六是不是週末」。

因為我們早就能透過程式判斷。

例如：

```
if is_weekend:    max_subjects = 3else:    max_subjects = 2if subject_count > max_subjects:    reject_save()else:    save_plan()
```

這種程式簡單、穩定、容易測試。

而且，即使 Workflow 中某個步驟用了 AI，例如讓 LLM 幫忙把錯誤訊息改寫得更友善，也不代表整個 Workflow 就變成 Agent。

### Agent：先觀察，再決定下一步

現在假設程式出現 Bug：

「星期六明明可以排三科，卻一直被拒絕。」

你把任務交給 Coding Agent。

目標：修好星期六排三科的 Bug

觀察：讀取規格、程式與錯誤紀錄

決策：選擇要檢查哪個檔案

行動：修改程式並執行測試

重新觀察

找出失敗原因，再決定下一步

交付審查

保留差異與測試紀錄

概念示意：真正的 Agent 還需要停止條件、授權限制與資源預算。

這就是 Agent 常見的運作方式：

觀察（Observe）→ 決策（Decide）→ 行動（Act）→ 再觀察。

它和固定流程的不同在於，系統不必事先列出所有可能的檔案搜尋順序與修正方法。

但這不代表 Agent 可以無限制地做任何事情。

## 三、要怎麼選？用這張決策表

| 判斷問題            | 比較適合             |
| --------------- | ---------------- |
| 只需要用對話詢問、獲得建議   | Chatbot          |
| 步驟和規則已經明確       | Workflow         |
| 必須看完新結果，才能決定下一步 | Agent            |
| 同時有固定規則與動態探索需求  | Workflow + Agent |

這不是互斥分類。同一個產品可以同時具備三者。

例如，你在聊天框輸入：「幫我整理今天的工作。」

系統可以先用固定 Workflow 驗證使用者身分，再由 Agent 查找允許存取的任務，最後透過聊天框回報結果。

所以，Chatbot 是互動介面，Workflow 和 Agent 則描述系統背後如何安排工作。

## 四、最容易弄錯的地方：用 Agent 開發，不代表產品要靠 Agent 運作

這個觀念特別重要。

你可以用 Claude Code、Codex 或其他 Coding Agent，協助你開發讀書計畫網站。

開發時：

Coding Agent → 閱讀需求 → 寫程式 → 執行測試 → 交付

但網站正式運作時：

使用者 → 按儲存 → 固定驗證程式 → 資料庫

網站完全可以不需要呼叫 LLM。

為什麼這通常是好事？

因為明確的固定規則，採用普通程式通常更容易做到低延遲、低成本、結果一致，也更容易進行自動測試。

反過來說，當任務需要理解不規則的文件、搜尋不確定位置的資訊、排查複雜錯誤時，Agent 的彈性才可能帶來明顯價值。

因此，我們應該讓 AI 負責真正需要判斷的部分，而不是把所有工作都交給 AI。

## 五、Agent 越自主，為什麼越需要管控？

想像你請 Agent：

「幫我修復網站錯誤。」

這個指令可能引起幾個問題：

1. 它發現錯誤與資料庫相關，是否能自行刪除資料？
2. 它想安裝新套件，是否可以直接安裝？
3. 它修好程式後，是否可以自行部署到正式環境？
4. 它一直測試失敗，究竟要嘗試到什麼時候？

所以，交給 Agent 的不是只有任務目標，還要有一份任務控制卡（Task Contract）。

Agent 任務控制卡

教學範例

目標

修正週末三科無法儲存的問題。

可以做

讀相關程式、修改指定檔案、執行測試。

不能做

刪除正式資料、上傳私人資訊、自行發布。

成功標準

週末三科可以儲存、平日三科依然被拒絕，相關自動測試通過。

停止條件

規格矛盾、需要額外授權、工具無法使用，或達到預算與重試上限。

交付證據

修改過的檔案、差異紀錄、實際測試結果與待確認事項。

這裡還有一個重要的資訊安全觀念：最小權限（Least Privilege）。

如果 Agent 的任務只是修正驗證程式，就不需要給它刪除資料庫或部署正式環境的權限。

而且，不能只在提示詞裡寫「禁止刪除資料」。真正重要的操作限制，還應該由程式、工具權限或執行環境實際強制執行。

## 六、真正成熟的系統，常常是 Workflow 與 Agent 混合

我們不一定要在 Workflow 和 Agent 之間二選一。

例如：

使用者提交修復需求

Workflow

固定檢查權限、需求與操作範圍

Agent

在授權範圍內探索問題、修改程式、執行測試

Workflow

執行固定驗收測試、記錄結果、等待人類審查

這個架構有兩個優點：

一方面保留 Agent 面對未知問題時的彈性，另一方面讓關鍵安全規則、驗收標準與正式發布程序，仍受到固定程式控制。

這往往比「什麼都讓 Agent 自己決定」更合適。

## 七、本課最重要的觀念

以後看到任何 AI 產品，不必只問：「它是不是 Agent？」

更有用的是：

第一個問題：下一步誰決定？

如果是固定程式決定，偏向 Workflow；如果是系統根據目標和新觀察動態選擇，偏向 Agent。

第二個問題：誰負責確認正確？

Agent 宣稱完成，不代表結果已經驗證。仍應有測試、紀錄及必要的人類審查。

第三個問題：誰有權阻止它？

沒有權限邊界、預算上限與停止條件的 Agent，即使能力很強，也可能不適合放進正式系統。

## 八、理解檢核：請你實際判斷

1\. 某個 AI 系統透過聊天框接收指令，但後台完全按照預先設定的步驟執行。它一定是 Agent 嗎？

A. 一定是，因為使用了聊天介面

B. 不一定，可能只是 Chatbot 介面搭配 Workflow

C. 一定不是，因為 Agent 不能有聊天介面

2\. 星期六最多能安排三科，這條規則已經確定。每次儲存時應優先採用什麼？

A. 讓 LLM 每次重新判斷

B. 使用固定驗證程式

C. 直接不檢查

3\. Coding Agent 發現教材沒有定義國定假日是否屬於週末。最合適的做法是什麼？

A. 自行決定國定假日等於週末

B. 忽略規格直接部署

C. 保留未解決問題，請需求負責人確認

提交答案，請老師批改
