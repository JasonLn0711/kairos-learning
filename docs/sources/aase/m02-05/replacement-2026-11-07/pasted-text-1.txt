# AASE M02-05｜Agent Harness 的六個組件：為什麼 AI 很聰明，卻不一定能把事情做好？

這一課最重要的觀念是：

LLM 是負責思考、理解和產生內容的核心，但 Agent Harness 才是讓 AI 能夠取得資料、使用工具、執行工作、遵守限制，以及證明工作成果的整套支援系統。

你可以把 LLM 想成一位非常聰明的工程師，而 Agent Harness 就是公司提供給這位工程師的工作制度、設備、權限與管理機制。

工程師再聰明，如果拿到錯誤需求、沒有工具、電腦環境不正確，或者工作沒有人驗收，仍然可能做錯事情。

## 一、先用一張圖理解 Agent Harness

概念架構圖：六個面向互相配合，不代表六套獨立程式，也不是依序執行的六個階段。

## 二、六個組件，各自究竟在做什麼？

假設我們開發了一個「AI 讀書計畫系統」。

原本週末允許安排三個科目，卻出現 Bug，只要安排第三個科目就被拒絕。

你跟 Coding Agent 說：「請幫我修好。」

接下來看看六個組件如何發揮作用。

1\. Context：工程師手上有沒有正確資料？

想像工程師接到維修任務，主管卻給他三年前的規格書，裡面寫「週末最多兩科」。

工程師照著規格修改，結果反而把錯誤固定下來。

Context 就是讓模型看得到這次需要的需求文件、程式碼、錯誤訊息與測試結果。

關鍵不是資料越多越好，而是資料正確、相關、版本正確。

2\. Tools：工程師有沒有工作工具？

假設工程師已知道程式哪裡出錯，但公司只允許他看程式，不允許修改檔案。

他只能告訴你「應該怎麼修改」，無法真正完成維修。

Tools 就像工作上的工具箱，包括讀檔、寫檔、搜尋程式碼、執行測試等。

能提出修改建議，不等於有能力實際修改。

3\. Orchestration：誰安排工作順序與停止條件？

假設工程師一接到任務，就直接修改十幾個檔案，修改完沒有測試，就說完成。

Orchestration 就像專案經理，負責安排先查規格、再修改、然後測試；如果失敗，決定重試、回復或停止。

如果 AI 自己決定下一步，Orchestration 也可以負責控制 AI 的工具呼叫與可執行範圍。

有工具是一回事，如何正確使用工具是另一回事。

4\. Execution Environment：工程師在哪台電腦工作？

假設工程師使用了正確指令，卻在一份三個月前的專案複本中修改程式。

他在那份舊專案成功執行測試，真正的系統卻沒有改變。

Execution Environment 就是實際工作的電腦、容器、作業系統、目錄、軟體套件和網路環境。

指令正確，不代表執行位置正確。

5\. Security：工程師被允許碰哪些東西？

假設你請工程師修讀書計畫系統，他卻有權限讀取公司的薪資資料庫、刪除其他專案。

即使他沒有惡意，這樣的工作權限仍然太大。

Security 就像辦公室門禁。允許改讀書計畫專案，不代表允許存取其他資料。

最重要的是：口頭要求「不要開那扇門」，不等於門真的上鎖。

6\. Observability：怎麼知道工程師真的做完了？

假設工程師回報：「已修好，測試成功。」

你問：「改了哪個檔案？執行哪個測試？在哪個版本測試？」

他卻答不出來。

Observability 就像工作紀錄與監控系統，讓你檢查實際執行的指令、修改差異、錯誤和測試結果。

AI 宣稱做完，是一項主張；執行紀錄與測試證據，才讓這項主張可以被查核。

## 三、把六個組件串起來：一個完整的 Agent 工作流程

任務：修復週末第三個科目無法新增

1

取得最新版規格

Context：確認週末上限確實是三科

2

讀取專案程式碼

Tools + Execution：確認讀到的是目標專案

3

找出錯誤並修改

LLM 分析，Tools 執行實際修改

4

執行測試

Orchestration：確認完成必要的驗證

5

整理修改證據

Observability：保存變更與測試結果

Security：全程限制檔案、工具及網路存取權限

Observability：全程保留適當紀錄，不只記錄最後一步

這裡要特別理解：上圖是其中一種合理的工作流程，不代表所有 Agent 都必須按照一模一樣的順序執行。

而且，即使測試顯示成功，也還要問：測試案例有沒有真的覆蓋「週末第三科」這個需求？如果測試本身寫錯，綠燈仍可能是假象。

## 四、為什麼這對 AI Agent 系統工程特別重要？

很多人在 AI 做錯事情時，第一個反應是：

「模型是不是太笨？要不要換更大的模型？」

但事實上，有六種完全不同的故障來源。

| 發生的問題           | 優先檢查                  |
| --------------- | --------------------- |
| AI 一直根據舊規格回答    | Context               |
| AI 知道要改什麼，卻不能寫檔 | Tools                 |
| AI 不斷重試、無法停止    | Orchestration         |
| 修改成功，但網站沒有變化    | Execution Environment |
| AI 可以讀取不相關的機密檔案 | Security              |
| AI 說測試成功，卻找不到紀錄 | Observability         |

這張表是一種初步診斷方法，並非每個問題都只有一個原因。

例如「無法修改檔案」，可能是 Tools 不提供寫入能力，也可能是 Security 正確拒絕了未授權的修改。

因此，診斷系統的重點是 找到真正的故障層次，而不是每次都調整 Prompt。

## 五、MCP 與 Agent Harness 的關係是什麼？

這也是很容易混淆的地方。

你可以想像 Agent Harness 是整間工程公司，而 MCP（Model Context Protocol）是一種讓公司能以共同方式接上外部工具或資料服務的介面規範。

例如 Agent 透過 MCP Server 取得某個檔案工具的描述，知道如何提出讀檔請求。

但它不代表：

- 對應的檔案一定存在。
- 工具有足夠且適當的權限。
- 工具回傳的資料一定正確。
- 操作失敗時一定能自動復原。
- 所有敏感操作都已經受到安全控管。

所以，MCP 解決部分系統互通問題，Harness 則要處理 Agent 如何可靠、安全地完成整個工作。

## 七、理解檢核：換你當 Agent 系統工程師

假設有一個 Coding Agent，正在協助你修改網站。

它回報：

「我已成功修改網站，也執行完測試。」

但你發現網站完全沒有變化，而且它曾嘗試讀取一個不相關的資料夾。

請思考三個問題：

1. 網站沒有變化：你會優先檢查哪兩個 Harness 面向？為什麼？
2. 讀取不相關的資料夾：你會透過 Prompt 限制，還是透過作業系統或工具權限限制？兩者有什麼差別？
3. AI 說已完成：你會要求它提供哪三項證據，才能合理判斷工作確實完成？

你可以直接回答 1、2、3，我再逐題評估你的理解與工程判斷。

最後記住一句話：

模型決定 AI 能有多聰明；Agent Harness 則在很大程度上決定這份能力能否轉化成可靠、可控、可驗證的實際工作。
