# AASE M05-04｜SDD：讓規格驅動變更

這一課最重要的觀念：軟體不是「改完程式就好」，而是每次需求改變，都要確保規格、畫面、資料、程式和測試仍然一致。

你提供的網址有一處路徑錯誤，正確教材是 [M05-04｜SDD：讓規格驅動變更](https://learn.cs-kairos.com/courses/aase/v1/m05/concepts/m05-04/?utm_source=chatgpt.com)。

## 一、先從生活理解：為什麼改一個小地方，會影響整個系統？

假設你經營一家連鎖餐廳。

原本有一道雞肉料理，現在因為顧客需求，決定改成不含花生的版本。

你可能覺得：「很簡單，廚師不要加花生就好了。」

但實際上，你還需要考慮：

- 菜單上的過敏原標示是否更新？
- 採購清單是否需要調整？
- 廚師使用的食譜是否改變？
- 外送平台的餐點資訊是否正確？
- 廚房是否可能發生交叉接觸？
- 出餐前要怎麼確認符合新要求？

如果只告訴廚師不加花生，其他環節沒有同步，很可能還是會出問題。

這就是 SDD（Spec-Driven Development，規格驅動開發）要解決的問題。

它不是要求你把文件寫得越多越好，而是建立一套可以追蹤的關係：為什麼修改、應該修改哪些地方、實際修改了什麼，以及如何證明修改正確。這也符合教材對 SDD 的工作定義。

## 二、SDD 的核心工作流程

1\. 需求變更（Change Request）

為什麼要改？誰提出？是否已核准？

2\. 更新規格（Specification）

新的規則是什麼？原有規則哪些不能破壞？

3\. 影響分析與實作（Implementation）

修改哪些畫面、資料、程式與文件？

4\. 測試與驗證（Verification）

新功能正確嗎？舊功能有沒有被破壞？

5\. 審查、決策與留下證據

接受、修正或暫緩；必要時回到前面重新確認

這是反覆迭代的流程，不代表每一步只能執行一次。

### 三個一定要理解的名詞

Specification（規格）：軟體應該遵守的規則。好比餐廳食譜寫明每份餐點必須使用哪些食材。

Diff（差異）：修改前後的差別。就像把新舊食譜放在一起，檢查究竟改動了哪些內容。

Regression Testing（回歸測試）：修改一個功能之後，重新確認原本正常的功能沒有被破壞。例如改了付款功能，還要確認退款與訂單查詢仍然正常。

## 三、實際案例：原本三個必填欄位，現在要增加第四個

這是原教材使用的合成情境。

假設一間公司有收件系統，原本只需要填寫三個必要欄位，現在有人提議增加「收件批次代號」。

直覺作法可能是請 AI Coding Agent：

> 幫我新增一個收件批次代號的輸入框。

AI 可能很快就完成了。

但是，畫面有了輸入框，不代表整個系統已經正確支援這項新需求。

我們應該先做一張變更影響表。

| 影響範圍    | 必須考慮的問題                  |
| ------- | ------------------------ |
| 需求與規格   | 第四欄是否必填？允許哪些值？舊資料怎麼處理？   |
| UI / UX | 欄位放哪裡？沒有填寫要怎麼提示？         |
| 驗證規則    | 少了第四欄是否禁止完成？             |
| 輸出資料    | 匯出的 JSON、CSV 或文件是否加入新欄位？ |
| 程式狀態    | 修改輸入後，舊的驗證結果是否需要失效？      |
| 測試      | 新增哪些案例？原本哪些測試要重新執行？      |

一項需求變更，不一定要修改所有檔案，但必須檢查所有可能受到影響的地方。

這就稱為 Change Impact Analysis（變更影響分析）。

### 把需求寫成可以檢驗的規格

假設負責人確認：「新的收件資料必須填寫第四欄，否則不得完整匯出。」

我們就可以用前一課 M05-03 的 Given / When / Then 格式表示：

```
Scenario: 缺少收件批次代號

Given 使用者已填寫原本三個必要欄位
And 收件批次代號為空白

When 使用者執行資料驗證

Then 系統應顯示缺少收件批次代號
And 系統不得提供完整資料匯出
```

再寫一個容易被忽略的情境：

```
Scenario: 驗證完成後修改輸入資料

Given 四個必要欄位均已通過驗證

When 使用者清空收件批次代號

Then 原本的驗證結果應失效
And 系統不得沿用舊結果完成匯出
```

第一個情境確認新規則，第二個情境防止系統使用過期的結果。

這些情境都是候選規格；實際採用前仍需確認第四欄的有效值、舊資料處理政策及輸出契約。教材本身也沒有宣稱這項變更已經實作完成。

## 四、為什麼 SDD 特別適合 AI 協作軟體工程？

傳統開發常見的問題是工程師只記得改程式，卻忘記同步更新其他地方。

使用 AI Coding Agent 後，這個問題可能更加明顯，因為 AI 可以在短時間內修改大量檔案。

例如你告訴 Agent：

「幫我讓系統支援第四個欄位。」

它可能自行推測新欄位是否必填、資料格式、甚至是否需要修改資料庫。

但這些其實不一定是 AI 有權決定的事情。

所以比較可靠的工作分工是：

| 人類主要負責    | AI Agent 可以協助 |
| --------- | ------------- |
| 決定真正的業務需求 | 盤點可能受影響的檔案    |
| 確認規則與例外   | 起草規格和測試案例     |
| 核准變更範圍    | 修改程式、介面及相關文件  |
| 審查實作差異    | 執行測試、彙整結果     |
| 決定是否接受成果  | 提供可檢查的修改與驗證證據 |

這裡最重要的不是 AI 寫程式有多快，而是人類能不能從需求一路追查到最後的測試結果。

NASA 的軟體工程指引也強調雙向可追溯性（Bidirectional Traceability）：不但要能從需求找到設計與測試，也應能從實作或測試回頭找到對應的需求。

## 六、SDD 最容易犯的三個錯誤

第一，只改程式，不改規格。結果程式已經變了，但下一位工程師或 AI Agent 仍然依照舊文件工作。

第二，為了讓測試通過，反過來修改需求。例如原本明確規定缺少必填資料不得匯出，程式卻仍可匯出。這是實作違反規格，不能直接把規格改成允許缺件，掩蓋原本的錯誤。

第三，把所有測試顯示綠燈當成完成。測試可能漏掉重要情境，也可能因為錯誤地修改預期結果而通過。測試結果必須和真正的業務規格互相核對。

## 七、現在就可以使用的最小 SDD 方法

不需要先導入大型需求管理系統。你可以從一份 Markdown 文件開始，每次變更至少記錄：

```
# CHANGE-001：新增必要欄位

## 目的
為什麼提出這項變更？

## 狀態
候選／已核准／實作中／已驗證

## 待確認事項
哪些規則還不能自行假設？

## 規格
修改後應出現哪些可觀察行為？

## 影響範圍
哪些畫面、資料、程式和測試可能受影響？

## 驗證計畫
如何確認新需求與既有功能？

## 實作證據
修改的檔案、Commit、Diff、測試結果

## 最終決策
接受、退回修正或暫緩
```

它也可以逐步擴展為需求追溯矩陣（Requirements Traceability Matrix），讓每一條需求都能連到實作、測試與驗證證據。

若需要多人協作、較多變更版本或工具化流程，可再評估 OpenSpec；但使用任何工具，都不能取代確認需求與實際驗證的責任。

## 本課理解檢核

請先回答這三題，我再依你的答案分析是否真正掌握 SDD。

問題一｜概念判斷

某位工程師發現系統的必填檢查沒有生效。他為了讓測試通過，直接把規格中的「必填」改成「選填」。

這屬於正常的 SDD 需求變更，還是掩蓋實作錯誤？為什麼？

問題二｜情境分析

一家電商將原本的「訂單滿 1,000 元免運費」，改成「訂單滿 1,500 元免運費」。

除了修改運費計算公式，你認為還有哪些系統或工作流程必須同步檢查？請至少提出四項。

問題三｜AI 協作實務

你交代 AI Agent 增加一項功能，Agent 回覆：「已完成修改，所有測試均通過。」

在接受結果之前，你會要求它提供哪些證據？你又要如何判斷測試是否真的涵蓋需求？

這三題分別檢查你能否區分需求與錯誤、完成變更影響分析，以及審查 AI Agent 的交付成果。
