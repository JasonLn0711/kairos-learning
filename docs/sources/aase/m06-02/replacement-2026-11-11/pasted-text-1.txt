# M06-02｜C4 System Context：先畫清楚系統與外界的關係

這一課最重要的觀念：在設計軟體之前，先搞清楚「我們要建造的是什麼系統、誰會使用它、它需要和哪些外部系統合作」。

這就是 C4 System Context Diagram（系統情境圖）的用途。

它不是用來畫程式碼、API 端點或資料庫結構，而是讓工程師、主管、客戶與其他利害關係人，先對整個系統的範圍形成共同理解。

你提供的網址多了一層 `m04`，實際教材位於 [M06-02 正確課程頁面](https://learn.cs-kairos.com/courses/aase/v1/m06/concepts/m06-02/?utm_source=chatgpt.com)。

這堂課可以用一句話記住：

先畫系統和外界的關係，再深入系統內部的技術設計。

## 一、用白話理解：把軟體當成一家餐廳

想像你要開一家餐廳。

你找來設計師、廚師、會計師與工程師，準備規劃餐廳的營運。

在討論廚房設備、瓦斯管線、收銀機怎麼接線之前，大家應該先知道：

- 餐廳服務哪些人？
- 顧客如何訂餐？
- 餐廳是否需要外送平台？
- 是否需要向外部支付業者收款？
- 哪些工作是餐廳自己負責，哪些交給外部公司？

假設我們正在設計一套「餐廳訂餐系統」。

顧客

選餐點、送出訂單

餐廳訂餐系統

接收訂單、管理訂餐狀態

金流系統

付款／結果

外送平台

配送／狀態

簡化的 System Context 教學示意。假設金流與外送都是實際串接的外部系統；完整正式圖還需要清楚標出每條關係的方向與用途。

這張圖的重點不在精美，而在於我們能立刻辨認三件事：系統主角、外部參與者、互動關係。

而且，如果餐廳根本沒有外送服務，就不應該因為別人的系統都有外送平台，而把外送服務硬畫進來。

這正是本課教材特別強調的原則：架構圖應描述有證據的實際系統，而不是憑想像補齊功能。&#x20;

## 二、C4 是什麼？為什麼分成四個層級？

C4 是一套描述軟體架構的方法，由 Simon Brown 推廣。你可以把它想成 Google Maps：先看整座城市，再逐步放大到街區、建築物與室內配置。

### C1 · Context

系統與外界的關係

### C2 · Container

系統由哪些應用與資料儲存組成

### C3 · Component

應用程式內有哪些功能元件

### C4 · Code

類別、介面等程式碼結構

由外向內逐層放大。C4 並不要求所有專案都畫滿四層，許多團隊用 Context 和 Container 就足以溝通主要架構。

[image](https://www.google.com/s2/favicons?domain=https://c4model.com\&sz=32)

C4 model

例如，設計醫院掛號平台：

| 層級           | 要回答的問題                           |
| ------------ | -------------------------------- |
| C1 Context   | 病患、醫師、醫院既有系統怎麼與掛號平台互動？           |
| C2 Container | 平台內有哪些 Web App、Backend、Database？ |
| C3 Component | Backend 裡有哪些預約、排程、通知模組？          |
| C4 Code      | 預約服務有哪些類別、介面及程式實作？               |

本堂課只需要把 C1：Context 學好。

這裡特別注意，C4 的 Container 是一個架構概念，指應用程式、資料儲存等可執行或儲存單位，不等於 Docker Container。

## 四、實際操作：從零開始畫一張 Context 圖

現在回到原教材的案例：設計一套「收件完整性檢核系統」。

這套程式的工作很單純。使用者輸入一筆合成資料，程式檢查必要欄位有沒有填寫，最後產生檢查報告。

### 收件檢核系統的 Context 示意

此案例沒有其他直接互動的外部運行時軟體系統，因此不額外增加外部服務。

我們可以按照下面五個步驟建立這張圖。

| 步驟       | 要做的事                 | 本案例的答案                |
| -------- | -------------------- | --------------------- |
| 1. 定主角   | 我們正在設計什麼？            | 收件完整性檢核系統             |
| 2. 找角色   | 哪些人直接使用它？            | 收件人員                  |
| 3. 找外部系統 | 運行時依賴哪些其他系統？         | 目前沒有                  |
| 4. 畫關係   | 誰給誰什麼資料、為了什麼目的？      | 輸入資料、回傳檢查結果           |
| 5. 檢查範圍  | 有沒有把內部技術細節或未實作功能畫進來？ | 不畫 Python 函式或不存在的 API |

### 為什麼要把箭頭的意思寫清楚？

比較這兩種寫法：

| 不夠清楚         | 比較正確                    |
| ------------ | ----------------------- |
| 使用者 → 系統：使用  | 使用者 → 系統：輸入資料並要求檢查      |
| 系統 → 使用者：資料  | 系統 → 使用者：回傳缺漏資訊及完整性報告   |
| 系統 → 外部服務：連接 | 系統 → 金流服務：送出付款請求並接收交易結果 |

箭頭的方向表示互動或依賴的方向，不一定代表一個完整的時序。Context 是描述結構關係的圖，不是記錄每一步先後順序的流程圖。

## 五、三個不同產業的應用

下面是假設性案例，目的是練習辨識主系統和外部關係。

| 場景 | 主系統         | 使用角色    | 可能的外部系統                    |
| -- | ----------- | ------- | -------------------------- |
| 教育 | 線上考試平台      | 學生、教師   | 校務身分驗證系統、成績管理系統            |
| 醫療 | AI 影像輔助判讀平台 | 放射科醫師   | PACS 影像儲存傳輸系統、外部推論服務（如有使用） |
| 物流 | 貨物追蹤平台      | 物流人員、客戶 | 地圖服務、承運商追蹤系統               |

以醫療案例來說，PACS（Picture Archiving and Communication System）是管理醫療影像的系統。

如果影像判讀平台需要向既有 PACS 取回 CT 影像，那麼就應該畫出：

PACS → AI 影像判讀平台：提供指定病患的 CT 影像。

但如果整套 AI 都在本機運行，而且根本沒有連接任何外部推論服務，就不應該畫出「雲端 LLM API」。

這正是架構設計最容易犯的錯誤之一：把技術選項、未來計畫和目前已經存在的架構混成一張圖。

## 六、AI Coding Agent 究竟要不要畫進去？

這是本堂課一個很重要的觀念。

假設你用 Claude Code、Codex 或 OpenCode 協助編寫收件檢核系統，但使用者真正操作產品時，程式完全沒有呼叫任何 AI 模型。

那麼 Coding Agent 是開發工具（Development-time Tool），不是產品運行時的依賴。

反過來，假設你設計一套客服平台，顧客每次詢問時，平台都會將訊息傳給外部 LLM API 產生回答。

那麼這個模型服務就成為運行時依賴（Runtime Dependency），應納入 Context。

| 情境                    | 放在產品運行時 Context？         |
| --------------------- | ------------------------ |
| AI 幫你產生程式碼，完成後離開      | 不需要                      |
| AI Agent 在開發時執行測試     | 不需要                      |
| 客服產品每次回答都呼叫外部 LLM API | 需要                       |
| 系統在本機執行內嵌的模型          | 通常描述為主系統內部實作，之後在更細的架構層展開 |
| 產品需要連接獨立的外部 AI 推論服務   | 需要                       |

另外，不在產品運行時 Context 裡面，不代表開發工具沒有安全風險。Coding Agent 可能讀取原始碼、執行指令或連接網路，仍然需要在開發環境的安全設計中管理權限。

## 七、三個容易混淆的重要觀念

### 1. System Context 不等於 User Flow

User Flow 問的是：「使用者先按什麼，再按什麼，接下來發生什麼事？」

System Context 問的是：「這個系統和哪些人、哪些外部系統有關係？」

例如線上購物的「選商品 → 放入購物車 → 結帳」是 User Flow，而「購物系統 ↔ 金流服務」是 System Context 裡的關係。

### 2. 系統邊界不等於安全邊界

假設 Context 圖中畫了一個框，把「醫療影像分析平台」包起來。

這個框表示你目前討論的軟體範圍，不代表它已經有防火牆、TLS 加密、網路隔離或存取控制。

安全上的 Trust Boundary（信任邊界）需要另外分析：資料從哪個信任區域進入哪個區域，是否需要驗證、授權、加密及監控。

### 3. 外部系統不一定是外部公司的系統

「外部」是相對於你選定的主系統而言。

例如公司內部的人事系統與薪資系統都由同一家公司維護，但當你的主角是「請假管理系統」，薪資系統仍可能是它的外部依賴。

所以判定的關鍵是系統責任及設計範圍，而不是機器放在哪裡或由哪家公司擁有。

## 八、你可以實際完成的成果：architecture.md

本課教材要求留下一份能讓別人閱讀的系統範圍與關係紀錄。以下是可以直接參考的最小版本。

```

# System Context — 收件完整性檢核系統

## 1. 系統目的
提供合成資料的必要欄位檢查、缺漏提示及當次報告匯出。

## 2. 系統範圍
主系統：收件完整性檢核系統

## 3. 使用者
收件人員：輸入資料、檢查結果、取得報告。

## 4. 外部運行時系統
無。

## 5. 互動關係
- 收件人員 → 主系統：
  提供合成資料，要求檢查及匯出。
- 主系統 → 收件人員：
  回饋缺漏資訊，提供檢核報告。

## 6. 不在本次範圍內
- Coding Agent（僅用於開發）
- 正式業務受理
- 尚未實作的外部 API

## 7. 邊界備註
- 系統範圍不等於安全信任邊界。
- 尚未確認的整合應另外列為待確認事項。

```

完成後，用以下標準驗收：讓另一位沒有參與開發的人，只閱讀圖與文件，就能正確說出系統的功能、使用者、外部依賴與每條關係的用途，而且不會把尚未實作的功能誤認成已存在。
