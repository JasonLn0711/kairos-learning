# M07-03｜垂直切片一：建立表單（Vertical Slice）

這堂課最重要的觀念：開發軟體時，不必先把整個系統做完。可以先完成一個很小、但使用者真的能從頭操作到尾的功能。

例如，你要開發一套銀行徵信系統，不必先完成帳號、資料庫、審核、報表與權限管理。可以先讓使用者「輸入三項資料 → 按下按鈕 → 看見剛剛輸入的內容」。

這就叫做一個「垂直切片」（Vertical Slice）。

本課程對應的是 [M07-03｜垂直切片一：建立表單](https://learn.cs-kairos.com/courses/aase/v1/m07/concepts/m07-03/?utm_source=chatgpt.com)。你提供的網址將 M07 誤放在 `/m04/` 目錄中，正確章節位於 `/m07/`。

## 一、什麼是垂直切片？

先想像你要開一家餐廳。

你有兩種施工方式。

方式 A：先把所有東西各做一部分。

先裝潢全部座位、買齊所有設備、設計整本菜單、建立所有營運制度。結果過了一個月，仍然沒有辦法服務任何客人。

這就有點像軟體開發先做完所有畫面，再做所有後端，最後才開始整合。

方式 B：先完成一條真正能服務的流程。

先布置一個座位，準備一種餐點，完成點餐、製作、送餐。雖然餐廳還沒全部完成，但已經能讓一位客人走完完整體驗。

這就是垂直切片的精神。

每次完成一項任務所需的層次，儘早取得可操作的結果。

概念示意：並非每個切片都一定需要資料庫，本課的第一切片只需輸入與預覽。

垂直切片不表示「隨便做一小塊」，而是選擇一項有明確起點、終點與可驗證結果的使用者任務。

## 二、用不同產業理解垂直切片

| 產業  | 第一個可以完成的切片     | 暫時不做      |
| --- | -------------- | --------- |
| 醫療  | 輸入病人基本資訊並預覽    | 診斷、健保申報   |
| 電商  | 選擇商品數量並查看訂單草稿  | 金流、物流     |
| 教育  | 輸入作業名稱和內容並預覽   | 自動評分、成績排名 |
| 製造業 | 輸入設備編號與量測數據並預覽 | 異常判定、自動停機 |
| 銀行  | 輸入申請編號等三欄並預覽   | 徵信審核、正式報告 |

共同點是：第一階段只完成「輸入 → 看見結果」，不假裝已經完成後面的判定工作。

## 四、為什麼「必填」標籤不等於真的有檢查？

這是整堂課很容易忽略、卻非常重要的觀念。

想像醫院掛號系統顯示：

「身分證字號（必填）」

但使用者什麼都沒輸入，按下送出，系統竟然顯示：

「掛號成功」。

這裡存在兩個完全不同的東西：

- UI 標示：告訴使用者，這個欄位應該填寫。
- Validation（資料驗證）：程式實際檢查輸入是否符合規則。

前者是溝通，後者才是執行判斷。

在本課 M07-03，你只需要完成表單和未檢核預覽；M07-04 才會加入缺漏、空白、資料型別、長度等驗證規則；M07-05 再進一步處理預覽與匯出。

功能做得多，不一定代表符合本次規格。

## 五、真正寫程式時，要怎麼實作？

教材採用 Python 的 Streamlit，這是一個能快速用 Python 建立網頁互動介面的框架。

以下是可以獨立存成 `app.py` 的簡化範例：

```
import streamlit as stst.title("收件資料預覽")# 初始化預覽狀態if "preview" not in st.session_state:    st.session_state.preview = None# 輸入改變後，清除舊預覽def clear_preview():    st.session_state.preview = Nonest.text_input(    "申請編號（預計必填）",    key="application_id",    on_change=clear_preview,)st.text_input(    "申請人代號（預計必填）",    key="applicant_code",    on_change=clear_preview,)st.text_input(    "文件類型（預計必填）",    key="document_type",    on_change=clear_preview,)if st.button("查看本次輸入（未檢核）"):    st.session_state.preview = {        "application_id": st.session_state.application_id,        "applicant_code": st.session_state.applicant_code,        "document_type": st.session_state.document_type,    }if st.session_state.preview is not None:    st.info("以下資料尚未經過完整性檢核")    st.json(st.session_state.preview)
```

在已安裝 Streamlit 的 Python 環境中執行：

```
python -m streamlit run app.py
```

這段程式有幾個專有名詞值得理解。

| 名詞               | 白話解釋                |
| ---------------- | ------------------- |
| `st.text_input`  | 在網頁放一個文字輸入框         |
| `st.button`      | 放一個可以按的按鈕           |
| `session_state`  | 記住目前這次操作中的資料與畫面狀態   |
| `on_change`      | 使用者修改欄位、變更被提交時觸發的動作 |
| `st.json`        | 把資料用 JSON 格式顯示      |
| `application_id` | 程式使用的穩定欄位識別名稱（Key）  |

你可以把 `session_state` 想成櫃檯人員面前的暫存工作紙。客人改了資料，先前整理好的結果就必須作廢，重新整理後才能展示。

注意：目前這段程式沒有資料庫、沒有持久保存、沒有任何業務檢核。這不是缺點，而是本次切片刻意設定的範圍。

## 六、如何知道第一切片已經完成？

不是 AI Agent 說「完成了」就代表完成。應該由你實際驗收。

| 驗收問題     | 通過條件                |
| -------- | ------------------- |
| 表單能使用嗎？  | 三個欄位能輸入文字           |
| 欄位用途清楚嗎？ | 每個欄位都有持續可見的標籤       |
| 可以操作嗎？   | 能用 Tab 移動焦點，並操作主要按鈕 |
| 結果正確嗎？   | 預覽顯示當次資料，包括空白       |
| 會誤導使用者嗎？ | 沒有「已通過審核」等不實狀態      |
| 舊結果會失效嗎？ | 修改輸入後，不再顯示過期預覽      |
| 可以審查變更嗎？ | 保留 Diff、測試與實際操作紀錄   |

這也呼應 Nielsen Norman Group 的易用性原則：系統需要清楚告知使用者目前狀態，避免使用者誤解操作結果。

[image](https://www.google.com/s2/favicons?domain=https://www.nngroup.com\&sz=32)

NN/G



至於 Diff，就是兩個程式版本間的差異。你可以要求 AI Coding Agent 只修改這個切片需要的檔案，然後用 `git diff` 檢查它究竟改了什麼。

## 七、把這堂課連到整個開發流程

從第一切片逐步擴充

1. M07-03：建立表單

   輸入資料 → 顯示未檢核預覽。
2. M07-04：加入資料檢核

   輸入資料 → 依業務規則檢查 → 顯示通過或錯誤。
3. M07-05：預覽與匯出

   輸入資料 → 檢核 → 預覽有效結果 → 匯出。
4. M07-06、M07-07：審查與修復

   確認 AI 的修改內容、測試證據、錯誤原因，以及是否能安全復原。

這種方式的價值在於：每完成一個階段，就有一個能夠操作、檢查與回歸測試的基礎。不必等到整個系統完成，才發現原本的介面或資料流程存在問題。

但也別把垂直切片誤解成「不用架構設計」。真正需要的安全邊界、資料結構與模組介面，仍應隨風險與需求適度提前規劃。

## 八、理解檢核

假設一家電商公司請 AI Coding Agent 開發退貨系統。

第一切片的需求只有：「讓顧客輸入訂單編號、商品名稱、退貨原因，並查看輸入預覽。」

AI Agent 完成表單後，另外自行加入「退貨審核通過」標記和「退款成功」訊息，但實際上沒有連接訂單系統，也沒有退款功能。

請回答三個問題：

1. 這個 Agent 是否算完成第一切片？為什麼？
2. 如果使用者把訂單編號修改了，畫面還保留舊訂單的預覽，會有什麼風險？
3. 你會如何規劃第二個垂直切片，讓這套系統逐步接近真正可以使用的退貨服務？

先用自己的話回答，我再根據你的答案判斷哪些觀念已經掌握、哪些還需要補強。
