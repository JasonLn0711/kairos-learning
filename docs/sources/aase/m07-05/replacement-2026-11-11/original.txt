# M07-05 白話教學：垂直切片三——預覽與匯出（Preview & Export）

「曾經通過檢查的資料，不代表現在這份資料仍然通過檢查。」

## 一、先用生活例子理解：為什麼檢查成功還不夠？

假設你在銀行辦理貸款，需要填寫：

- 申請編號：A001
- 申請人代號：C123
- 文件類型：收入證明

你按下「檢查」，系統顯示三個欄位都填好了，可以下載申請報告。

C123

目前資料尚未檢查，請按「檢查資料」。

請實際操作：先按檢查，再把「收入證明」改成「戶籍謄本」。

你會發現，雖然新資料也有填寫完整，系統仍然不讓你直接下載。

原因是：原本通過檢查的是「收入證明」那一版，不是後來修改的「戶籍謄本」那一版。

這就是本節的核心：檢查結果必須綁定特定版本的資料。

## 二、理解五個重要觀念

### 1. Snapshot（快照）：把檢查過的資料保存一份

快照就像拍照。

假設你把汽車送去檢驗，檢驗員確認煞車系統正常，發給你一張檢驗證明。

但是檢驗結束後，你把煞車系統換掉了。原本的證明不能直接用來保證新煞車系統安全。

軟體也是一樣。

在使用者按下「檢查」時，程式應該保存當時那份資料的副本：

```
checked_snapshot = record.copy()
```

之後準備預覽或匯出，就要確認目前資料是否仍與快照相同：

```
current_record == checked_snapshot
```

這個方法適合教材中的簡單文字欄位。對於複雜資料庫、多人共同編輯或分散式系統，則通常需要更嚴謹的版本控制機制，例如版本號、交易控制或樂觀鎖定。

### 2. Invalidation（失效）：資料改變，舊結果就不能沿用

這與「快取失效」（Cache Invalidation）的概念很接近。

假設電商網站顯示：

> 你的購物車商品已確認，總價 2,000 元。

接著使用者新增了一件商品，總價變成 3,500 元。

此時系統不能繼續顯示「已確認 2,000 元」，更不能以舊的確認結果進行結帳。

因此我們需要一個規則：

只要會影響檢查結果的資料發生變化，就必須使舊結果失效。

在 Streamlit 中，可以利用 `Session State` 保存檢查快照，以及 `on_change` 在欄位提交變更時清除先前的檢查狀態。`Session State` 是保存工作階段資訊的機制，不是正式的永久資料庫。

### 3. Revalidation（重新驗證）：下載之前，再守一次關

有些人會以為，只要前端把下載按鈕隱藏，就不會產生錯誤報告。

這是不可靠的。

因為下載函式可能還能被其他程式、測試程式或 API 直接呼叫。

所以必須分成兩道檢查：

| 檢查位置                 | 責任                         |
| -------------------- | -------------------------- |
| 畫面端（UI）              | 不要讓使用者看到或使用過期的預覽與下載操作      |
| 匯出端（Export Function） | 即使繞過畫面，也要驗證資料是否合法，並拒絕不合法內容 |

舉例來說，醫院的掛號介面已經把「缺少病歷號」標示為錯誤，但若後端仍能直接產生宣稱資料完整的報告，就代表保護措施不完整。

畫面的限制改善操作體驗；真正的資料規則必須由可信任的處理邏輯執行。

### 4. Allowlist（允許清單）：只輸出明確允許的欄位

假設系統內部有這些資料：

```
{
  "application_id": "A001",
  "applicant_code": "C123",
  "document_type": "收入證明",
  "debug_notes": "內部測試紀錄",
  "internal_token": "SECRET"
}
```

但對外報告只需要前三個欄位。

如果開發者把整個資料物件直接匯出，就可能把內部測試內容或敏感資訊一起送出去。

因此應該先建立允許清單：

```
FIELDS = [    "application_id",    "applicant_code",    "document_type",]export_data = {    key: record[key]    for key in FIELDS}
```

這就是「預設不輸出，除非有明確允許」。

它與資安領域的最小權限原則（Principle of Least Privilege）有相似精神：只提供完成目的所需要的內容。

### 5. Scope（適用範圍）：檢查通過，不等於所有事情都正確

假設軟體檢查三個欄位是否填滿。

系統顯示 `complete`。

那麼 `complete` 到底表示什麼？

它只表示這三個欄位符合目前定義的完整性規則。

不代表申請人身分是真實的，不代表文件內容正確，更不代表銀行已經正式核准貸款。

因此教材特別要求匯出資料附上 `scope`，說明「完成」所代表的範圍。

這是專業軟體設計非常重要的一點：不要讓有限的技術檢查結果，被誤解成更廣泛的業務、法律或安全保證。

## 三、把五個觀念串成完整流程

預覽與匯出的可靠流程

使用者輸入資料

Current Record

按下檢查，執行驗證

Validation

驗證通過，保存快照

Checked Snapshot

資料被修改

舊快照失效，重新檢查

資料沒有變

符合規則，准許預覽

匯出前再驗證 + 允許清單過濾

Revalidation + Allowlist

輸出 JSON 報告

附上適用範圍說明（Scope）

請注意：重新驗證的意思，不只是確認目前輸入的格式合法，還要依業務要求確認目前輸入對應的是已被檢查的版本。

## 四、其他產業如何應用？

這套設計不只適用於表單，更適用於任何「先檢查，再產生結果」的工作流程。

| 產業   | 原本通過檢查的內容   | 之後發生的變化   | 正確做法                 |
| ---- | ----------- | --------- | -------------------- |
| 醫療   | 某份檢驗資料已完成檢查 | 檢驗數值被修正   | 舊報告失效，重新進行必要的檢查及審核   |
| 金融   | 貸款資料已通過欄位檢查 | 申請金額改變    | 重新檢查後才能輸出新版報告        |
| 製造業  | 品質檢查表已完成    | 零件批號變更    | 原檢驗結果不能直接套用新批次       |
| 物流   | 出貨清單已確認     | 出貨地址或件數更改 | 重新核對資料，才產生新出貨單       |
| 科學研究 | 實驗分析結果已驗證   | 資料集或參數改變  | 重新執行必要驗證，確保報告與實驗版本一致 |

這些案例共享同一個原理：結果必須能追溯到產生它的輸入、規則與版本。

## 五、實作時，要怎麼驗收？

這裡可以接上前一章學過的 Given–When–Then：

- Given（前提）：三個欄位填寫完整，而且檢查成功。
- When（事件）：使用者將其中一個欄位清空。
- Then（結果）：舊的成功預覽與下載入口失效，必須重新完成檢查。

還需要檢查另外三種情境：修改後仍是合法資料，也不能沿用舊快照；直接用缺件資料呼叫匯出函式，應被拒絕；匯出資料包含額外內部欄位時，這些欄位不應出現在報告中。

測試工具也有分工。`pytest` 可以驗證資料規則；Streamlit 的 `AppTest` 可以模擬介面操作並檢查元素與狀態；但下載後 JSON 的實際內容、中文編碼及檔案名稱，仍應透過真實瀏覽器或其他適當方式檢查。

## 六、進一步理解：這其實是在管理「結果的可信度」

把本章與整體軟體工程連起來，可以看到三個層次：

| 層次                             | 要回答的問題           |
| ------------------------------ | ---------------- |
| 資料有效性（Validity）                | 目前資料是否符合規則？      |
| 結果一致性（Consistency）             | 預覽或報告是否確實對應目前資料？ |
| 結果授權與範圍（Authorization & Scope） | 誰可以輸出？結果到底保證什麼？  |

本章的本機原型主要處理前兩個層次，以及第三層中的範圍說明。它還沒有實作正式的身分驗證、多人授權或持久儲存，因此不能直接當作完整的企業級安全方案。

更進一步，如果是 AI Agent 自動產生報告，這個觀念同樣重要。Agent 不能只因為先前某次工具呼叫成功，就假設後續修改後的資料仍符合匯出條件；工具邊界應自行檢查資料和授權條件。

## 七、理解檢核

假設你開發一套工廠品質管理系統。

某批產品的檢查表已通過驗證，並產生了「檢查完成」狀態。之後，操作員將產品批號由 `BATCH-100` 改成 `BATCH-101`，其他欄位完全沒有改變，而且新批號格式也合法。

請回答：

1. 系統可不可以直接使用舊的「檢查完成」狀態產生新報告？為什麼？
2. 前端與匯出函式，分別應負責哪些檢查？
3. 如果匯出 JSON 額外包含工廠內部除錯欄位，應如何防止外洩？
4. 即使系統顯示 `complete`，是否就能宣稱這批產品符合所有品質標準？

先用自己的理解回答，之後再逐題分析。

本節最重要的一句話：驗證結果不是一張永久有效的通行證，而是對特定資料、特定規則及特定版本所作的有限保證。
