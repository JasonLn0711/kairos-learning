# M06-05 | Authentication, Authorization and Sessions

Logging in does not grant access to every feature or to other people's data.

Distinguish three responsibilities:

1. Authentication: Who are you, and how do you prove it?
2. Authorization: What may you do, and which data may you access?
3. Session: How does the system recognize continuing interactions, and when does that state become invalid?

When a single-user application becomes a shared system, these responsibilities help prevent users from viewing, changing or exporting data that is not theirs.

## 1. Understand the three concepts through an everyday example

Imagine entering a large hospital to view a patient's medical record.

1. Authentication: establish identity

The hospital asks you to present an employee badge, enter a password or use another verification method to establish that you are a particular doctor.

This answers: “Are you the person you claim to be?”

2. Authorization: decide permission

After identifying you as a doctor, the system must still check whether you may view this patient's record.

This answers: “Knowing who you are, are you allowed to do this?”

3. Session: manage continuing interaction

After logging in, you normally do not re-enter your password for every page. Logging out, remaining idle too long or session invalidation may require authentication again.

This answers: “How can state be maintained safely across multiple actions?”

Compare the responsibilities in a table:

| Concept | Everyday question | Hospital example |
| --- | --- | --- |
| Authentication | Who are you? | Establish that this is Dr. Wang |
| Authorization | What may you do? | Decide whether you may read patient A's record |
| Session | How is this interaction state maintained? | Manage identification information, expiry and logout |

A doctor does not automatically have access to every medical record. Access depends on hospital policy, the care relationship and applicable requirements.

## 2. Authentication: login establishes identity

Imagine conducting business at a bank counter.

The clerk first checks identification to establish who you are. This step does not decide how much you may withdraw.

Website login follows the same distinction.

Common authentication methods include:

- Password: demonstrate knowledge of a secret.
- OTP (one-time password): use a code delivered by text message or generated by an authenticator.
- Passkey: use cryptographic keys, often together with device unlocking.
- MFA (multi-factor authentication): combine different categories of authentication factors to make impersonation harder.

For example, an account and password establish that the user of a company document system is employee A.

The result means:

> The system has established that the current requester is authenticated as A.

It does not establish that:

- A may view every company document.
- A may delete other people's documents.
- A may download the entire customer database.

Authentication and authorization therefore need separate decisions.

## 3. Authorization: check this action even after login

Suppose an insurance company has ten employees, each responsible for different customers' claims.

Employee A handles `CASE-101`; employee B handles `CASE-202`.

Both are logged in and both have the role “claims specialist.” May B view A's case directly?

Not necessarily. Sharing a job title does not imply sharing access to the same records.

Consider this hypothetical policy:

| User | Target record | Action | Result |
| --- | --- | --- | --- |
| A | CASE-101 | Read | Allow |
| A | CASE-101 | Export | Allow |
| B | CASE-101 | Read | Deny |
| B | CASE-101 | Export | Deny |
| B | CASE-202 | Read | Allow |

Actual systems may also have supervisor review, case handover or delegation rules. Do not assume a supervisor automatically has access to everything.

### 2. Three common access-control models

Compare the basis for permission: roles, attributes or relationships between people and resources.

| Model | Everyday meaning | Example |
| --- | --- | --- |
| RBAC (Role-Based Access Control) | Grant permissions by role | Accounting staff may use expense reporting |
| ABAC (Attribute-Based Access Control) | Decide using attributes and conditions | Only employees in a specified department may approve a case in the required state |
| ReBAC (Relationship-Based Access Control) | Decide using relationships between people and resources | The case owner and assigned reviewer may view the case |

These models can be combined. Large systems often need a combination.

For example, RBAC establishes eligibility as a claims specialist, while ReBAC checks the relationship to the particular claim.

OWASP recommends least privilege, deny by default and authorization checks on every access request.

### 3. Why is hiding a button insufficient?

Suppose the system exposes two APIs:

```
GET /api/cases/101
GET /api/cases/101/export
```

The first reads data; the second exports it.

A developer might hide the export button from B because B cannot export A's case.

However, a user can send requests without pressing a button in the interface.

Another HTTP client can request the export directly. If the server does not check permission, the data may still leak.

Enforce authorization where data is actually processed.

This is a conceptual decision flow. Implement checks at each protected entry point and its data-access path.

Two common problems follow from missing checks:

Horizontal privilege escalation: B has the same organizational level as A but can view A's private data.

Vertical privilege escalation: an ordinary employee gains access to a function reserved for administrators.

## 4. Sessions: why can one login support continuing actions?

Start with HTTP's behavior.

HTTP is stateless: individual requests are independent, and the protocol does not automatically remember whether the current request comes from the same person as the preceding request.

Why can you log in to a shopping site, open products, add items to a cart and view orders without entering a password each time?

The site supplies a mechanism to manage state across interactions.

### 1. How does a session work?

Consider a common server-side session:

@figure3

After successful authentication, the server creates a session and the browser retains its identifying information. Later requests carry that information. The server checks session validity and still checks authorization for the requested data.

A cookie is a browser storage and transmission mechanism. A session is a way to manage continuing interaction state. A token is a form of credential that can support identification or authorization. They are related concepts with different responsibilities.

### 2. Sessions need a lifecycle

Suppose you log in to online banking and leave the computer.

If the login remains valid forever, another person using that computer may continue operating your account.

Security design commonly needs these controls:

| Control | Everyday meaning |
| --- | --- |
| Idle timeout | Invalidate the session after a period of inactivity |
| Absolute timeout | Expire or require reauthentication at the maximum lifetime even if activity continues |
| Logout | Invalidate relevant sessions when the user signs out |
| Revocation | Let the system invalidate sessions or credentials |
| Reauthentication | Require authentication again for sensitive actions or risk events |

One timeout value does not suit every system. Bank transfers, shopping sites and healthcare systems need policies based on their risks and use contexts. OWASP also explains that stolen session identification information can enable session hijacking.

Common cookie protections include `Secure`, `HttpOnly` and `SameSite`. They help restrict transport, JavaScript access and cookie sending with cross-site requests. They still need authorization and other security controls alongside them.

Sessions can also exist before login. For example, an anonymous session may retain a language preference or temporary shopping cart.

## 5. Compare the responsibilities across industries

Across industries, identify identity verification, resource permissions and continuing interaction state separately.

| Industry | Authentication | Authorization | Session |
| --- | --- | --- | --- |
| Banking | Establish customer identity | Decide access to an account or a transfer | Maintain and limit online-banking login state |
| University | Establish teacher or student identity | Decide whether a teacher may change grades for a course | Manage the academic-system session |
| E-commerce | Establish member identity | Decide access to an order or refund request | Maintain member interactions and cart state |
| Factory | Establish operator identity | Decide whether an operator may change particular equipment parameters | Limit valid console login state |
| AI agent | Establish user or service identity | Decide tool calls, document access and permitted actions | Manage security state during conversation or tool execution |

Consider an AI agent in particular.

A company builds a document-search agent. Employee B asks: “Summarize all contracts for the customers handled by A.”

Even if the agent correctly identifies B, it cannot infer permission to search all documents.

Authorization must extend to document retrieval, database queries, tool calls and exports. A system-prompt instruction saying “do not read unauthorized data” is insufficient as an access-control boundary.

## 6. Streamlit: session state does not establish secure login

This distinction can be misunderstood.

The course uses a Streamlit prototype. `st.session_state` retains interaction state for a user session, such as the selected file, form fields or results.

Using it does not establish production authentication or authorization for business data.

Streamlit also provides `st.login()`, `st.user` and `st.logout()` for OpenID Connect (OIDC) authentication. These functions still do not automatically implement business-data authorization.

Distinguish the following capabilities:

| Feature | What does it establish? |
| --- | --- |
| `st.session_state` | The application retains interaction state within a session |
| `st.login()` and related login functions | An authentication flow can be established with correct configuration |
| Application permission rules | Decide whether a particular user may operate on a particular resource |
| Session security governance | Requires additional checks of expiry, revocation and reauthentication requirements |

A screen remembering a user code does not demonstrate safe sharing by ten users.

## 7. Turn the lesson into a software specification

Record candidate controls for the shared ten-user version in `architecture.md`, retaining their unimplemented status.

Use this reference template:

```
## Shared-version security design (candidate specification)

Status: not implemented / not verified

### 1. Authentication
- User identity source: undecided
- Login and verification method: undecided

### 2. Authorization
- Each case has an explicit authorization relationship
- Check reads, changes and exports separately
- Enforce authorization server-side
- Deny access unless explicitly allowed
- Denial must return no unauthorized record content

### 3. Session
- Session creation and lifetime: to design
- Idle expiry and logout: to design
- Handling withdrawn permissions: to design
- Reauthentication for sensitive actions: to design

### 4. Negative tests
- B reads A's private case → deny
- B exports A's private case → deny
- Unauthenticated access to a private case → deny
- Access after session invalidation → deny
- Access after permission withdrawal → deny

None of these tests has been executed. Do not mark them as passing.
```

The specification tells the team where checks belong, which conditions must deny access and which security capabilities remain unverified.
