# M08-05｜Task-based Usability Test：任務導向易用性測試

這一課要學的核心是：

軟體功能正常，不代表使用者真的會用。要知道系統是否好用，就讓使用者親自完成真實任務，觀察他在哪裡順利、在哪裡卡住，再根據證據改善設計。

我已找到教材的正確頁面：[M08-05｜Task-based Usability Test](https://learn.cs-kairos.com/courses/aase/v1/m08/concepts/m08-05/?utm_source=chatgpt.com)。你提供的網址多了一層錯誤的 `m04` 路徑。

## 一、什麼是任務導向易用性測試？

先想像你開了一家餐廳，設計了一台自助點餐機。

工程師測試後告訴你：

- 觸控螢幕正常。
- 菜單可以顯示。
- 加入購物車功能正常。
- 信用卡付款正常。
- 訂單確實送進廚房。

工程師認為系統通過測試。

但實際開放客人使用時，卻發生了這些問題：

客人找不到素食餐點、不知道怎麼取消已選品項、付款後不確定有沒有成功，甚至有人因為害怕重複扣款而不敢繼續操作。

這時候你會發現：

工程師證明了系統「可以運作」，卻沒有證明客人「能夠順利完成點餐」。

這就是為什麼需要 Task-based Usability Test。

它不是請使用者隨便看看畫面，也不是只問他「你覺得好不好用？」。

而是給他一個具體目標，例如：

> 你今天要幫三位朋友點餐，其中一位不吃肉。請完成點餐並確認訂單成功送出。

然後觀察他能否自行找到菜單、處理飲食限制、修改數量、付款並確認結果。

這個方法最重要的精神是：

告訴使用者要完成什麼，不要告訴他應該按哪個按鈕。

教材也特別強調，測試中要把實際觀察、可能的原因與後續改善假設分開。

## 二、這種測試和一般軟體測試有什麼不同？

可以把軟體品質分成四個不同的問題來檢查。

| 測試方法                 | 要回答的問題       | 舉例              |
| -------------------- | ------------ | --------------- |
| 單元測試 Unit Test       | 程式邏輯算得對嗎？    | 商品折扣是否正確        |
| 介面自動化測試 UI Test      | 按鈕和畫面運作正常嗎？  | 點擊結帳是否進入付款頁     |
| 易用性測試 Usability Test | 使用者能自行完成工作嗎？ | 客人是否找得到取消訂單功能   |
| 安全測試 Security Test   | 系統能否阻止不當操作？  | A 使用者能否偷看 B 的訂單 |

這些測試互相補充，不能彼此取代。

尤其要理解：系統可以同時通過所有自動化測試，卻在易用性測試中失敗。

### 易用性的三個重要面向

| 英文                | 白話意思     | 怎麼判斷        |
| ----------------- | -------- | ----------- |
| Effectiveness 有效性 | 事情做得成嗎？  | 是否完成預期任務    |
| Efficiency 效率     | 需要花多少力氣？ | 時間、步驟、反覆嘗試  |
| Satisfaction 滿意度  | 使用感受如何？  | 是否清楚、安心、有信心 |

例如兩個人都成功完成網路掛號，但甲只花兩分鐘，乙花十五分鐘，而且一直擔心是否預約成功。

兩人都完成任務，卻不代表體驗品質相同。

## 三、實際要怎麼進行？完整流程

任務導向易用性測試的工作流程

1\. 決定要研究的問題

例如：使用者能不能發現資料缺漏？

2\. 設計有目標的任務

只交代目的、情境和必要資料

3\. 讓使用者自行操作

主持人不提供操作答案

4\. 記錄可觀察的證據

行為、停頓、錯誤、協助、結果

5\. 提出原因假設並改善

先選一個有證據支持的問題

6\. 使用相同目標重新驗證

確認改善是否真的有效

這是一個持續改進的循環，而不是做完一次就結束。英國政府的易用性研究指引也強調，測試任務應該具體、可信、貼近使用者情境，但不能暗示完成方法。

## 四、不同產業應該怎麼設計測試任務？

關鍵是把「操作指令」轉換為「工作目標」。

| 產業 | 不適合的測試說法    | 適合的任務               |
| -- | ----------- | ------------------- |
| 醫療 | 點掛號按鈕，再選內科  | 你想預約下週的內科門診，請完成預約   |
| 金融 | 點報告頁面，再按匯出  | 有一份資料需要交給主管審查，請準備報告 |
| 電商 | 按購物車的刪除圖示   | 你不想買其中一件商品了，請修改訂單   |
| 教育 | 點成績查詢，再點下載  | 請取得本學期的成績紀錄         |
| 物流 | 打開追蹤功能，輸入編號 | 客戶詢問包裹到哪裡了，請找到最新狀態  |

注意：適合的任務不一定比較短，重點是不要把介面設計應該提供的線索，提前由主持人說出來。

否則你測到的就不是介面有多清楚，而是參與者有多會遵從指令。

## 五、最重要的研究能力：區分觀察、推論與假設

這是本課值得特別學習的部分。

假設你正在測試一套銀行報告系統。

使用者修改了資料，但沒有重新產生報告，直接下載舊版檔案。

你可能立刻認為：

「這個人一定不知道資料修改後必須重新檢查。」

但你其實不知道他的想法。

我們應該把事情拆成三層：

| 層次             | 可以怎麼寫                             |
| -------------- | --------------------------------- |
| Observation 觀察 | 使用者修改資料後，未重新執行檢核，直接下載報告           |
| Inference 推論   | 使用者可能以為修改資料會自動更新報告                |
| Hypothesis 假設  | 如果修改後顯示「結果已過期，請重新檢核」，可能減少下載舊報告的情況 |

三者的差別很大。

觀察是實際發生的事；推論是可能的解釋；假設則是準備透過新測試驗證的主張。

例如，使用者也可能知道必須重新檢核，只是當時分心，或者系統的舊報告仍顯示為最新版本。

因此，不能直接把「可能」寫成「事實」。

這種區分不只適用 UX，也適用科學研究、醫療診斷、資安事件調查與企業管理。

## 六、如何記錄一次測試？

下面是一份簡化的紀錄表。

易用性測試觀察表

虛構示例

| 系統版本  | v0.2                |
| ----- | ------------------- |
| 測試者代號 | P01                 |
| 任務    | 修改資料後取得最新報告         |
| 觀察行為  | 修改資料後，未重新檢核即下載      |
| 主持人協助 | 沒有                  |
| 任務結果  | 未取得符合要求的最新報告        |
| 可能原因  | 不清楚報告需要重新產生         |
| 改善假設  | 標記舊結果並引導重新檢核        |
| 再測方式  | 讓其他符合目標族群的參與者完成同類任務 |

這只是教學示例，不代表曾經進行真人測試。

有三種完成情況必須分清楚：獨立完成、協助完成、未完成。

如果主持人提醒參與者應按哪個按鈕，然後他才成功完成工作，不能記成獨立完成。

同樣地，如果要量測完成時間，應先約定何時開始與結束、協助時間如何計算，避免每個人的數據定義不同。

## 七、觀察到問題之後，應該怎麼改善？

延續前面的例子。

假設使用者不知道修改資料後需要重新產生報告。

設計團隊可以嘗試提供更清楚的系統狀態：

改版前

報告管理

資料已修改

下載報告

改版後的設計提案

報告需要重新檢核

資料已經變更，目前的報告不再代表最新資料。完成檢核後才能下載最新報告。

重新檢核並更新報告

示意介面，非實際系統。

這裡運用了兩項重要 UX 設計原則：

Visibility of System Status（系統狀態可見性）：使用者應該清楚知道目前發生什麼事。

Error Prevention（預防錯誤）：比起讓人下載錯誤報告後再補救，最好先降低錯誤操作發生的機會。

這兩項都是 Nielsen Norman Group 整理的十大易用性啟發式原則。

[image](https://www.google.com/s2/favicons?domain=https://www.nngroup.com\&sz=32)

NN/G



不過，提出設計改善，不等於已經證明改善有效。

應該再讓參與者完成同類任務，確認他是否能辨認報告狀態，以及能否取得正確結果。若要比較改版前後的效果，也需要留意參與者熟悉程度與測試條件的差異。

## 八、常見的四種誤區

誤區一：找朋友試用一次，沒問題就代表產品好用。

朋友能幫你發現初步問題，但如果真正使用者是護理師、銀行授信人員或倉儲管理員，仍需要找具有相關工作經驗的人參與。少數人的結果不能直接推廣至全體使用者。

誤區二：測試時不可以給任何協助。

可以協助，但要記錄何時、為什麼、給了什麼提示，並區分獨立完成和協助完成。對真正卡住的人，適度協助有時能讓測試繼續蒐集其他問題的證據。

誤區三：使用者完成任務，就是沒有問題。

有人可能反覆嘗試十幾次才完成。雖然最後成功，但操作過程仍可能暴露設計缺陷。

誤區四：易用性測試可以取代安全和功能驗證。

不行。使用者覺得容易操作，不代表資料權限正確、計算結果準確，或系統符合無障礙要求。這些還需要獨立驗證。

另外，真人測試必須取得適當同意，說明紀錄用途。測試環境應優先使用安全的合成資料；若有錄影或真實個資，必須先處理保存、存取及隱私要求。

## 九、把本課轉換成一項可以執行的工作

你可以直接使用教材中的「收件資料檢核系統」進行一個小型實驗。

準備三個分階段任務：首先給使用者一筆文件類型缺漏的申請資料，請他判斷能不能產生完整報告；接著補充文件類型，請他取得可供同事核對的報告；最後撤回文件類型，請他判斷先前的檢核結果是否仍然有效。

建議讓一位自願同儕先試用，使用合成資料，不透露操作路徑，記錄實際行為、協助情況及完成結果。然後挑出一個最值得改善的問題，提出可以重新測試的設計假設。

這就完成了本課的最小實作。正式產品驗收則應擴大至具代表性的使用者、任務與環境。

## 十、理解檢核

情境題

某醫院開發了一套新的電子病歷系統。工程師已證明所有功能正常，但護士在試用時找不到「取消錯誤醫囑」的操作方式。

研究員認為：「護士一定是不熟悉電腦，所以才找不到。」

下列哪種處理方式最符合任務導向易用性測試的精神？

A. 先請護士參加電腦教育訓練，再結束測試

B. 告訴護士按哪個按鈕，只要成功就記錄通過

C. 記錄護士卡住的操作、詢問當時理解，再提出介面改善假設並重新測試

D. 因為程式測試通過，所以不用修改介面

提交答案並查看解析

本課最重要的結論： 易用性不是開發者自己認為操作簡單，而是目標使用者在特定情境下，能否有效、有效率且有合理信心地完成工作。要改善它，必須依靠真實行為的證據，而不只是直覺。
