# M06-03｜C4 Container 與四層架構圖：白話文完整教學

核心觀念：C4 Model 是一套用不同距離觀察軟體系統的方法，讓我們從「整個系統和外界的關係」，逐步看清楚「有哪些程式」、「程式內部如何分工」，最後才是「程式碼怎麼寫」。

它最大的用途，是讓產品經理、軟體工程師、架構師，以及 AI Coding Agent 對同一個系統建立共同理解。

你提供的網址多了一個 `m04` 路徑；實際教材位於 [M06-03｜C4 Container 與四層導覽](https://learn.cs-kairos.com/courses/aase/v1/m06/concepts/m06-03/?utm_source=chatgpt.com)。

本篇教材特別強調三件事：

1. C4 的四層是四種觀察視角，不是四台電腦、四個服務或四個開發步驟。
2. C4 Container 不等於 Docker Container。
3. 架構圖必須符合實際程式、資料流向與儲存方式，不能憑空畫出不存在的系統。

## 一、先用一個生活比喻理解 C4

想像你要了解一家大型醫院如何運作。

你不會一開始就研究急診室某台儀器的電路板。你會先從整間醫院、各個部門、部門內的人員分工，一路看到具體設備。

C4 就是這個概念。

C1 — System Context

最遠的視角

醫院與病患、健保署、外部檢驗機構的關係

問：誰使用這間醫院？它依賴哪些外部機構？

C2 — Container

掛號系統、病歷系統、檢驗資料庫

問：醫院內有哪些主要系統？各自負責什麼？

C3 — Component

掛號系統內的預約、排程、通知模組

問：一個系統內部如何分工？

C4 — Code

檢查時段的函式、資料模型、程式類別

問：具體如何實作？

由外向內逐步放大。這是概念比喻，實際軟體的四個層級不一定與醫院組織一一對應。

四層的英文分別是：

| 層級 | 名稱             | 最重要的問題            |
| -- | -------------- | ----------------- |
| C1 | System Context | 系統跟誰打交道？          |
| C2 | Container      | 系統由哪些應用程式與資料儲存組成？ |
| C3 | Component      | 每個應用程式內部如何分工？     |
| C4 | Code           | 用什麼程式碼實現？         |

要記住一個重要區別：

C4 並不是把系統拆成四個部分，而是用四種詳細程度描述同一套系統。

## 二、最重要的觀念：C4 Container 到底是什麼？

在軟體工程裡，Container 這個字很容易造成誤會。

因為我們平常聽到 Container，經常想到 Docker。

但是在 C4 Model 中，Container 指的是一個應用程式或資料儲存的執行邊界，不是特定的部署技術。&#x20;

[image](https://www.google.com/s2/favicons?domain=https://c4model.com\&sz=32)

C4 model



以一家餐廳的線上訂餐系統為例：

| 項目               | 是 C4 Container 嗎？ | 原因           |
| ---------------- | ----------------- | ------------ |
| 顧客訂餐網頁 App       | 是                 | 瀏覽器中執行的應用    |
| 訂單處理 API         | 是                 | 負責處理訂單的後端應用  |
| PostgreSQL 訂單資料庫 | 是                 | 獨立的資料儲存      |
| `order.py`       | 通常不是              | 只是應用程式中的程式模組 |
| 「送出訂單」按鈕         | 不是                | 只是使用者介面元素    |
| 一個 Docker 容器     | 不一定               | 是部署與執行技術     |

這裡有個非常重要的例子。

假設餐廳的訂單 API 使用 Docker 部署，因為訂單量增加，工程師開了三個相同的 API 實例處理流量。

C4 Container：訂單 API

一種應用程式角色與責任

實際部署（Deployment）

Docker 1

API 實例

Docker 2

API 實例

Docker 3

API 實例

這是說明性部署範例，並非表示每個 C4 Container 都必須使用 Docker。

雖然實際有三個 Docker 執行實例，但在一般 C4 Container Diagram 中，仍然可以只畫出一個「訂單 API」。

因為 C4 Container 在回答：

「我們的系統包含哪種應用？它負責什麼？」

部署圖（Deployment Diagram）才回答：

「這個應用實際跑在哪裡？執行幾份？如何分配流量？」

這是 C4 創作者 Simon Brown 特別強調的區別。

## 三、用一套訂餐系統，從 C1 一路看到 C4

接著我們使用同一個案例，實際走過四層。

### C1：System Context — 先看系統跟誰有關係

假設你是一名工程師，有人要請你開發餐廳訂餐系統。

第一個問題不是「我們用 Python 還是 JavaScript」。

而是先問：

「誰會使用這個系統？系統需要和誰合作？」

顧客、餐廳店員

線上訂餐系統

我們正在設計的系統

第三方支付平台

這一層沒有必要討論訂單資料表、程式函式或伺服器數量。

因為我們正在定義系統邊界（System Boundary）：哪些東西屬於我們要開發的系統，哪些是外部的人或服務。

### C2：Container — 系統內部有哪些主要應用？

現在把線上訂餐系統打開來看。

顧客

線上訂餐系統 — C4 Container 視角

訂餐前端（Web App）

顯示菜單、購物車與訂單

HTTPS / API

訂單後端（API Application）

檢查訂單、計算金額、處理業務規則

訂單資料庫（PostgreSQL）

保存訂單與商品資料

後端另與外部支付平台通訊

這是一種假設性的訂餐架構。方塊代表主要責任單位，連線表示通訊關係，不代表所有操作都必須依圖中順序進行。

這張圖開始回答重要的技術問題：哪些程式會執行、誰負責業務邏輯、資料存放在哪裡，以及程式之間如何溝通。

但它依然不需要畫出所有函式。

### C3：Component — 再放大訂單後端

假設你的訂單後端使用 Python。

這個後端可能包含以下功能：

訂單後端 API（同一個應用程式）

訂單驗證

檢查品項、數量與輸入格式

價格計算

計算總價、折扣與稅額

支付協調

向支付平台建立交易

資料存取

讀取或保存訂單

這些是 Component 的示例，不表示必須分成四個獨立服務或四個檔案。

此時你是在討論：

「訂單處理程式裡面的工作如何分工？」

而不是討論這些模組是否需要各自一台伺服器。

### C4：Code — 最後才看具體程式碼

現在再放大訂單驗證模組。

假設它包含這個函式：

```
def validate_order(items):    if not items:        return False    for item in items:        if item["quantity"] <= 0:            return False    return True
```

這段程式檢查兩件事情：訂單是否為空，以及購買數量是否大於零。

這就是 Code 層級會關心的內容：函式、類別、介面及它們之間的關係。這只是一段入門示例，正式訂單驗證還需要處理欄位缺漏、資料型別、商品有效性等問題。

現在回頭看：

C1 告訴我們訂餐系統跟誰互動；C2 告訴我們有哪些應用與資料庫；C3 告訴我們訂單後端有哪些模組；C4 則能解釋其中一個函式如何運作。

這就是完整的 C4 思考方式。

## 四、回到教材：為什麼 Streamlit 的 `rules.py` 不是 Container？

原教材使用的不是大型訂餐平台，而是一套「本機收件完整性檢核系統」。

它的實際參考架構是：

收件人員

本機收件完整性檢核系統

瀏覽器中的 Streamlit 前端

顯示介面、接收操作

Streamlit 管理的通訊

Python / Streamlit 程序

處理資料、執行檢核、產生報告

rules.py

程序內部的驗證及匯出邏輯

Session State：暫存工作階段資料

操作者下載資料夾（系統範圍外）

瀏覽器下載 JSON 後，由操作者管理檔案

教材中特別明確指出，這套參考系統沒有持久業務資料庫；前端與 Python 程序的通訊由 Streamlit 框架管理，而不是自行實作的 REST API。

[image](https://www.google.com/s2/favicons?domain=https://learn.cs-kairos.com\&sz=32)

CS Kairos Learn+1



為什麼 `rules.py` 不是另一個 Container？

因為它是被同一個 Python 應用程式載入並執行的模組。即使它包含十幾個驗證函式，也不會因為有很多函式就自動成為獨立應用程式。

相反地，如果未來真的把驗證功能改成獨立執行的服務，例如其他程式必須透過 API 呼叫它，就有理由重新評估是否把該服務畫成一個 C4 Container。

### 另一個容易忽略的問題：Session State 不是資料庫

Streamlit 的 Session State 讓某個瀏覽器工作階段的狀態能在應用程式重新執行時保留，但它本身不是持久儲存機制。關閉或重新整理分頁、伺服器故障等情況可能造成狀態消失。

而使用者下載的 JSON 檔案，已經成為裝置上的持久檔案。這也意味著「系統沒有資料庫」不代表資料完全不會留下。

[image](https://www.google.com/s2/favicons?domain=https://docs.streamlit.io\&sz=32)

Streamlit Docs



還有一點：不同瀏覽器分頁有不同工作階段，不代表系統已完成使用者身分認證（Authentication）與存取授權（Authorization）。這兩種安全機制必須另外設計。

## 五、不同產業可以如何應用 C4？

為了幫助你建立可以轉移的知識，以下比較三個產業。

| 產業  | C1：系統外部關係            | C2：主要 Container   | C3：內部元件        |
| --- | -------------------- | ----------------- | -------------- |
| 醫療  | 醫護人員、醫院系統、外部檢驗機構     | 醫療前端、後端應用、影像儲存    | 影像處理、推論、結果呈現   |
| 金融  | 銀行行員、核心銀行系統、外部徵信資料來源 | 報告前端、報告服務、資料庫     | 文件解析、規則驗證、報告產製 |
| 製造業 | 操作員、生產管理系統、外部供應商     | 監控前端、設備資料服務、時序資料庫 | 異常偵測、告警、品質分析   |

以上均是假設性的架構範例，並非特定機構的實際部署。

注意，這三個產業的系統很不一樣，但 C4 的觀察問題完全相同。

這也是為什麼 C4 值得學習：它提供一種跨領域、跨程式語言、跨框架的架構溝通方法。

## 六、實務上如何畫出一張合格的 Container Diagram？

開始畫圖之前，最好先知道現有系統真正的運作方式。

第一階段：確認系統邊界

確認誰使用系統、哪些外部系統提供服務、哪些程式是你負責開發的。這一步可沿用 C1 的成果。

第二階段：找出主要應用與資料儲存

盤點實際執行的前端、後端、工作程序及必要的資料儲存，不要把每個檔案都當成 Container。

第三階段：標註責任與通訊

每個方塊寫清楚名稱、用途、主要技術。每條連線寫明誰呼叫誰、傳送什麼資料，以及實際使用的通訊方式。

第四階段：檢查真實性與未知事項

確認圖能對應實際執行方式。尚未實作的資料庫、API、認證或遠端部署，必須明確標為未來規劃，而不能畫得像已存在。

以下是一個可寫進 `architecture.md` 的最小範例：

```

# 系統架構 — C4 Container

## 系統名稱
本機收件完整性檢核系統

## 系統邊界內
- Streamlit 瀏覽器前端：接收操作並顯示結果
- Python / Streamlit 程序：檢核資料並產生報告

## 程序內元件
- rules.py：執行欄位驗證及匯出邏輯

## 系統邊界外
- 收件人員：填寫資料、檢查、下載
- 操作者下載資料夾：保存下載報告

## 主要通訊
- 前端 ↔ Python：由 Streamlit 框架管理
- 前端 → 操作者裝置：下載 JSON

## 儲存
- 工作階段資料：Session State
- 持久業務資料庫：無
- 本機下載檔：操作者管理

## 部署
- 目前：本機教學原型
- 未驗證：遠端部署、多人存取、正式授權隔離

```

原教材要求的驗收重點，就是能讓架構圖與這份文字紀錄互相核對，並且能指出每個實際應用、資料位置和通訊關係。

## 七、需要每次都畫滿 C1 到 C4 嗎？

不需要。

根據 C4 Model 官方文件，對多數軟體開發團隊而言，System Context 與 Container Diagram 就已足夠。當內部模組很複雜時，再增加 Component Diagram；只有程式結構確實需要額外解釋，才增加 Code Diagram。

[image](https://www.google.com/s2/favicons?domain=https://c4model.com\&sz=32)

C4 model



你可以用一個簡單的判斷原則：

| 遇到的問題             | 優先查看               |
| ----------------- | ------------------ |
| 不知道系統與外部服務的依賴     | C1                 |
| 不知道資料在哪個程式被處理     | C2                 |
| 不知道程式內部哪個模組負責     | C3                 |
| 不知道某段功能如何實作       | C4                 |
| 不知道服務部署在哪台主機、幾個副本 | Deployment Diagram |

另外要分清楚：C4 主要描述系統的靜態結構。如果要了解「按下按鈕後，哪些操作先後發生」，通常要使用 User Flow、Sequence Diagram 或 C4 Dynamic Diagram 等補充表示法。

這些圖並不是互相取代，而是回答不同問題。

## 八、理解檢核

請先根據剛才學到的觀念，試著回答下面三題。我先不提供答案，等你作答後再逐題分析。

1\. 某銀行有一套 Python 報告產製系統。裡面有 parser.py、validator.py、exporter.py 三個檔案，它們由同一個 Python 程序載入執行。C4 Container Diagram 應該如何表示？

A. 畫成三個獨立 Container

B. 畫成一個 Python 應用，三個功能屬於內部元件

C. 因為是 Python，所以不需要架構圖

2\. 某醫療 AI 推論 API 被部署成五個 Docker 實例，由負載平衡器分配請求。這在 C4 中代表什麼？

A. 一定有五個 C4 Container

B. Docker 數量決定 Component 數量

C. 邏輯上可能是一個 C4 Container，部署上有五個實例

3\. 某 Streamlit 網站可以讓十個人同時開啟，各自有 Session State。是否足以證明十個人之間已有安全的資料授權隔離？

A. 是，不同 Session 就等於正式授權

B. 否，仍需要驗證身分、授權與資料隔離設計

C. 是，只要沒有資料庫就不會有資料外洩
