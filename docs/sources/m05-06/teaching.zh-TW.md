# M05-06｜驗證式與非驗證式掃描：掃完了，真的看得到嗎？

這課回答一個常見問題：**掃描工具顯示「完成」，為什麼仍不能直接說系統已經檢查完整？**

結論先說：**非驗證式掃描看未登入時能取得的資訊；驗證式掃描用事先授權的身分取得更多內部證據。兩者互補，而「有填帳密」「登入成功」「必要檢查完成」是三件不同的事。**

## 一、先用房屋檢查理解

請人檢查房子，可以站在外面看門窗，也可以在屋主同意後拿鑰匙進屋檢查管線。

外面看得到門是否開著，卻不容易知道牆內哪條管線老舊。進屋能看更多，但拿到一樓鑰匙，不代表地下室也能進去；進了屋，也不代表檢查員已把每個指定項目查完。

掃描也是一樣：**檢查位置、身分、權限及實際完成的項目，決定你能支持什麼結論。** 比喻中的「進屋」是合法授權，不是破解取得權限。

## 二、非驗證式掃描：看沒有登入時的可見範圍

Unauthenticated scanning 是非驗證式掃描，指掃描時不使用目標系統的登入身分來做該類檢查。工具可能觀察開放服務、通訊協定回應、憑證或公開介面，依可取得的證據判斷問題。

例如測試用網站的公開回應顯示某個軟體版本。這是線索，仍要考慮版本字串是否可靠、是否有安全修正移植，以及真正受影響的功能是否啟用。外部回應不足時，就不應把猜測寫成已確認。

這裡有兩個容易混淆的地方：

- 非驗證式不等於「一定從網際網路掃描」。掃描器也可以放在公司內網；來源位置不同，可看到的入口就不同。
- 非驗證式不等於「被動式」。工具主動送出探測請求，即使沒有登入，也可能影響服務，仍需要測試授權、時間窗口與停止條件。

因此報告應寫清楚「從哪個位置、未登入、檢查哪些目標」，而不是籠統寫「外部駭客能看到的一切」。

## 三、驗證式掃描：取得內部證據，不是先把系統駭進去

Authenticated scanning 是驗證式掃描；使用登入憑證的做法也常稱 credentialed scanning。Credential 在這裡是身分驗證資料，可能是帳密、金鑰或其他受支援的方式，不是掃描結果合格證明。

掃描器以核准的身分存取目標，可以依工具與權限取得套件、修補與設定資訊，通常比只看公開回應更有助於確認問題。[Rapid7 掃描憑證說明](https://docs.rapid7.com/insightvm/configuring-scan-credentials/)。

這不表示所有驗證式掃描都一樣。作業系統的登入身分、資料庫身分及網站的應用程式身分，各自能看到的範圍不同。登入主機成功，不保證資料庫檢查也成功；登入網站的一般會員帳號，也不能代替主機修補檢查。

## 四、最重要的三道檢查：設定、登入、覆蓋

**第一道：設定有沒有生效？** 帳密雖已存在工具內，可能沒有指派給本次目標，或沒有在這次工作啟用。

**第二道：目標有沒有接受這個身分？** 可能因帳密失效、帳號停用、連線限制或服務不符而失敗。同一批目標也可能部分成功、部分失敗，不能拿一台成功代表全部成功。[Rapid7 實際驗證狀態與診斷流程](https://docs.rapid7.com/insightvm/configuring-site-specific-scan-credentials/)。

**第三道：成功登入後，有沒有取得必要證據？** 帳號可能能登入，卻沒有讀取某些設定、檔案或套件清單的權限。Tenable 的文件也提醒，存取權限不足會造成不完整結果；因此要看檢查輸出及缺漏，不只看登入狀態。[Tenable 權限與檢查完整性](https://docs.tenable.com/nessus/compliance-checks-reference/Content/CredentialedScanningandPrivilegedAccountUse.htm)。

報告可以分別寫：「認證成功」「套件清單取得成功」「設定檢查因權限不足未完成」。這比一句「有用帳密掃」更有用。

沒有漏洞結果可能代表本次沒發現問題，也可能代表必要檢查根本沒跑完。**空白結果不是乾淨的保證。** 下一課會進一步區分誤報、漏報與驗證。

## 五、完整合成案例：同一台主機，三份不同證據

以下是虛構測試機「小樹伺服器」，沒有進行實際掃描。

第一次未登入掃描，看見網頁回應中的舊版本字串。合理結論是：「可能符合某公告的版本線索，修補狀態待確認。」不應直接寫已成功利用。

第二次使用核准帳號，登入成功，但套件清單讀取失敗。報告沒有列出套件漏洞。這時不能把第一次發現關閉，也不能寫「驗證式掃描證明已修補」，因為關鍵證據仍然缺少。

第三次經核准修正檢查設定後，取得完整套件修訂號，並對照發行商公告，確認已安裝包含該項安全修正的版本。這能支持修補判讀，但仍要確認相關執行程序是否已載入更新，以及是否還有其他副本或不同元件受影響。

如果此時某項對外設定問題依然存在，也不會因套件已修補而自動消失。不同檢查回答不同問題，不能互相抵銷。

因此可以寫：「已取得完整套件版本，符合公告修補版本；執行狀態與其他副本仍待確認。原始遠端版本線索保留，並附本次判讀依據。」

## 六、帳號越有權限，不代表越可以隨便用

驗證式掃描需要管理的是兩個風險：掃描對服務的影響，以及掃描憑證本身的權限與外洩風險。

某些工具的完整檢查確實要求管理員或接近 root 的權限；root 是類 Unix 系統中的高權限身分。不能一概承諾「普通唯讀帳號一定能做完整檢查」。但也不能為了方便就把所有設備共用的最高權限帳密貼進任意工具。

實務建議是依目標平台與原廠要求核定必要權限，搭配專用身分、目標限制、核准時段、稽核及憑證保管。權限較低時，明列因此少做哪些檢查，而不是假裝覆蓋相同。Tenable 也列出時段限制、輪替及權限使用監控等補償措施。[原廠特權帳號建議](https://docs.tenable.com/nessus/compliance-checks-reference/Content/CredentialedScanningandPrivilegedAccountUse.htm)。

遇到登入失敗，不要反覆重試到帳號鎖定，也不要自行停用防火牆、MFA 或其他安全機制。先查原因，再由有權人員批准調整。MFA 是多因素驗證；掃描工具是否能配合，必須依實際產品與環境確認。

安全檢查選項也不是零風險保證。先在授權測試環境小規模試跑，設定負載、停止條件與聯絡窗口，再按核准計畫執行。

## 七、有 Agent，是不是就不需要其他掃描？

Agent 是安裝在受管設備上的代理程式，能從本機收集資訊。這是另一種部署方式，不等於「因為沒填遠端帳密，所以它是非驗證式掃描」。它可能已透過本機服務權限取得內部資訊。

但本機資訊不等於從某個網路位置實際能連到哪些入口。Rapid7 的文件將 Agent 與掃描引擎定位為互補，而不是任何一方可以無條件取代另一方。[Rapid7 Agent 與掃描引擎比較](https://docs.rapid7.com/insightvm/using-the-insight-agent-with-insightvm/)。

選擇方式時問：我要確認套件修補，還是確認某個來源位置的曝露？工具支援這種設備嗎？資料何時收集？失敗或離線的資產有沒有被看見？這些答案比單純選「有帳密」或「沒有帳密」更重要。

## 八、操作清單與小檢核

今天只做紙上練習，不建立帳號、不提供密碼、不掃描任何目標。

1. 畫出一台合成主機及兩種掃描視角，寫下各自要取得的證據。
2. 用「小樹伺服器」三次結果，分別填：認證狀態、必要檢查狀態、已知、待確認與下一步。
3. 寫一句結果摘要，不能把「工作完成」寫成「所有檢查完成」，也不能把「沒列出漏洞」直接寫成「沒有漏洞」。

預期成果是一張能看出檢查覆蓋與缺口的表。練習完保留本機筆記即可，沒有實驗環境需復原。

真正執行時，應留下目標與授權範圍、掃描來源、工具與檢查規則版本、執行時間、帳號代號（不記秘密）、認證與權限狀態、完成及失敗項目、證據位置與後續安排。完成後依核准流程撤除臨時存取或輪替憑證，不擅自刪除仍需稽核的紀錄。
