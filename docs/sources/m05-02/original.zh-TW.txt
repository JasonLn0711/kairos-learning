# CEH M05-02｜資產盤點與評估範圍：為什麼不能看到一台電腦，就直接掃描？

這一課是資安工程與滲透測試非常重要的基本功。

先記住三句話：

1. Asset Inventory（資產盤點）： 公司到底有哪些東西需要保護？
2. Assessment Scope（評估範圍）： 這一次我們獲准檢查哪些東西？
3. Rules of Engagement（ROE，執行規則）： 即使可以檢查，哪些操作可以做、哪些不能做？

最重要的觀念是：知道一個系統存在，不代表你有權限測試它；完成一次測試，也不代表整個系統都安全。

## 一、先用醫院健康檢查理解

想像一家醫院要替 100 位員工安排健康檢查。

醫院首先要知道有哪些員工，這叫「盤點」。

接著，這次可能只有 30 位員工報名，這叫「範圍」。

而且這 30 位員工可能只同意量血壓、抽血，不同意做侵入性檢查，這叫「執行規則」。

最後，醫院只能說「30 位員工接受了指定項目檢查」，不能宣稱「100 位員工全部健康」。

資安評估也是完全相同的道理。

公司有 100 項資產（假設案例）

本次授權：30 項

未納入：70 項

即使 30 項全部通過指定檢查，也不能推論其他 70 項沒有弱點。這裡的數量只是示意。

這個比喻說明了資安工作的第一個關鍵：資產總數、授權數量、實際完成數量，是三個不同的數字。

## 二、Asset Inventory：資產盤點到底在盤什麼？

很多初學者會以為資產盤點，就是拿 Nmap 找出公司有哪些 IP 位址。

但這只是可能使用的其中一種技術，並不是完整盤點。

想像你經營一家網路商店。客人下單以後，網站必須接收訂單、查詢庫存、完成付款，才能正常營運。

我們可以把它分成四類資產：

| 資產類型    | 白話文理解      | 例子                 |
| ------- | ---------- | ------------------ |
| 硬體與運算資源 | 提供運算或連線的設備 | 伺服器、筆電、虛擬機器        |
| 軟體與服務   | 執行工作的程式    | 網站、API、資料庫服務       |
| 資料      | 真正需要保護的內容  | 顧客資料、訂單、密碼雜湊       |
| 身分與權限   | 決定誰能使用什麼   | 管理員、服務帳號、API Token |

為什麼要分這麼細？

因為你可能已經盤點到一台伺服器，卻不知道裡面存了十萬筆客戶資料。萬一被入侵，實際損失就可能遠超過這台電腦的價格。

這也是為什麼資產盤點不能只看硬體，還需要了解軟體、資料、帳號與相互依賴關係。

CIS Controls v8.1 中，Control 1 主要處理企業設備資產；Control 2 處理軟體資產，相關資料與帳號管理還涉及其他控制項。

### IP 位址為什麼不是永久身分？

想像公司有一個停車位，編號 15。

星期一是小明停，星期二換成小華。你不能只因為車子停在 15 號位置，就認定兩天是同一台車。

IP 位址也是類似概念。DHCP 可以動態分配位址；同一部電腦可能有不同 IP，同一 IP 也可能在不同時間對應不同裝置。

因此，清冊最好還有穩定的資產編號、主機名稱、擁有者、環境、查核時間等資訊。CIS Safeguard 1.1 也明確要求維護詳盡且更新的資產清冊。

## 三、Assessment Scope：為什麼公司自己的資料庫也不能隨便測？

現在用一個完整案例理解。

你被聘請來評估某公司的網路訂購系統，裡面有三個服務。

A：測試訂購網站

本次授權評估

允許檢查指定安全設定及軟體版本

B：正式資料庫

公司內部

未授權

C：外部金流服務

第三方業者

未授權

示意架構：A 依賴 B、C，但授權範圍只有 A 的特定檢查項目。

你在網站 A 裡面發現一個設定，顯示資料庫 B 的位址。

這時候應該怎麼做？

你可以根據 A 的已授權檢查內容，記錄「網站 A 存在對資料庫 B 的依賴關係」。

但你不能因為發現了 B 的位址，就自行開始掃描 B。

這裡有三個不同的概念：

| 概念                | 意思            |
| ----------------- | ------------- |
| Discovery（發現）     | 我知道 B 的存在     |
| Ownership（歸屬）     | 我知道 B 是誰管理的   |
| Authorization（授權） | 我獲准對 B 進行指定測試 |

這三件事不能混為一談。

即使 B 是公司的資產，也不代表授權 A 的管理者有權批准你測試 B，更不代表原本授權自動擴及 B。

同理，外部金流 C 由第三方管理，通常還要確認第三方同意與服務條款限制。

## 四、ROE：授權測試，不等於什麼操作都可以做

ROE 可以理解為「測試活動的遊戲規則」。

想像老師讓學生進入實驗室做實驗，這不表示學生可以操作所有儀器、使用所有化學藥品。

在資安工作中也是一樣：允許安全設定檢查，不表示允許密碼爆破、弱點利用或修改資料。

下面是一份簡化的合成 ROE。

| 項目   | 本次規則                  |
| ---- | --------------------- |
| 測試目標 | 測試網站 A                |
| 測試環境 | 測試環境，不含正式環境           |
| 允許行為 | 指定設定檢查、版本核對           |
| 禁止行為 | 未授權弱點利用、刪改資料、服務阻斷測試   |
| 測試時段 | 工作日 10:00–12:00       |
| 測試帳號 | 經核准的唯讀帳號              |
| 停止條件 | 發現非授權目標、意外接觸敏感資料、服務異常 |
| 事件處理 | 停止相關操作，依聯絡程序通知負責人     |

其中「停止條件」非常重要。

假設執行指定檢查時，網站突然大量回傳錯誤，甚至服務無法使用。你不能一邊繼續測試，一邊說自己只是想找出問題。

此時應依 ROE 暫停相關操作、保存必要的非敏感證據，並通知約定的負責人。

NIST SP 800-115 的附錄 B 提供 ROE 範本，涵蓋測試目標、範圍、風險、參與人員、時間與設備等內容。這是 2008 年發布的文件，仍可作為流程參考，但實際專案也要符合現行合約、法規及環境要求。

## 五、資安工程師真正的工作流程

1

盤點資產

確認哪些系統、資料與帳號存在

2

確認歸屬

確認管理者與授權權責

3

界定範圍與 ROE

確認能測什麼、如何測、何時停止

4

執行指定評估

只在授權範圍內檢查並保存證據

5

撰寫報告

交代發現、未測項目及結論限制

這個流程還隱含一個很重要的管理問題：如果沒有先確認資產數量與範圍，就很難知道這次究竟測得多完整。

例如這次授權 10 台主機，最後只完成 8 台。

本次授權資產的實際完成覆蓋率

# 80%

8 / 10 台

這裡假設 10 台均有明確且一致的預定檢查項目。8 台完成、2 台未完成。

這個 80% 代表的是資產評估覆蓋率，不是「系統有 80% 的安全性」。

即使完成 100%，也只代表全部指定項目已完成，不代表沒有任何未知弱點。

## 六、CEH 考試常見觀念陷阱

| 題目敘述        | 應該如何判斷       |
| ----------- | ------------ |
| 掃描器發現一台主機   | 不等於該主機已獲授權測試 |
| IP 在公司網段內   | 不等於這次測試必然涵蓋  |
| 某台主機沒有回應    | 不能直接推論它不存在   |
| 資產名稱寫 TEST  | 不代表沒有真實敏感資料  |
| 找不到弱點       | 不代表系統完全安全    |
| 網站連向第三方 API | 不代表可以測試第三方   |

這些題目共同在考一種專業判斷能力：證據可以支持什麼結論，以及授權允許你做到哪一步。

## 七、理解檢核：換你當資安工程師

假設你受託檢查一間醫院的 AI 影像分析測試平台。

醫院授權你檢查測試主機 A 的作業系統版本及安全設定。

在檢查過程中，你發現 A 連接到正式影像資料庫 B，而登入介面也使用外部身分驗證服務 C。

請回答三個問題：

問題一：這次可以直接對資料庫 B 進行弱點掃描嗎？為什麼？

問題二：你會如何把 B、C 記錄在資產清冊與本次評估報告中？

問題三：若你意外看到真實病人的醫療影像，下一步應該怎麼做？

提交答案並取得批改

掌握這一課的核心之後，未來不論使用 Nmap、Nessus、OpenVAS 或其他資安工具，都應該先確認資產、授權與執行邊界，再談如何進行技術檢查。
