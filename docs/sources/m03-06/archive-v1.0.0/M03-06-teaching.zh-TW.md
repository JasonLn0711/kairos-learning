# CEH M03-06｜作業系統指紋：如何從網路回應推測對方的系統？

**一句話結論：作業系統指紋辨識，是把多項網路回應特徵和已知樣本比較，提出有條件的系統推測，再用設備端資料確認。**

上一單元從服務回應辨認軟體。這一課往下一層看：即使對方沒有直接說自己使用哪個系統，網路回應的細節仍可能提供線索。學完後，你要能分清楚「看到的封包特徵」「工具的系統推測」與「管理端確認的版本」。

## 1｜生活例子：從回話習慣辨認窗口

想像你打電話到不同辦公室。大家都遵守接電話的基本禮貌，但有人先報單位、有人先問姓名，有人轉接前會再次確認。把幾種習慣放在一起，你可能推測是哪個窗口；若只有一句「您好」，資訊就太少。

網路上的系統也會留下類似的實作習慣。**Operating System，簡稱 OS（作業系統）**，負責管理電腦資源及提供程式執行環境。**Protocol Stack（協定堆疊）**則是處理不同層次網路通訊的一組實作，例如接收 IP 封包、管理 TCP 連線。

各種系統都需遵循協定，但支援選項、預設值與部分回應細節可能不同。**OS Fingerprinting（作業系統指紋辨識）**就是收集這些特徵，再和已知系統樣本比較。「指紋」在這裡是特徵組合，不是每台電腦唯一、永不改變的身分證。多台設備可能有相似特徵，更新與網路環境也會影響觀察。[Nmap：遠端作業系統辨識](https://nmap.org/book/osdetect.html)

## 2｜主動與被動：你怎麼取得線索？

**Active Fingerprinting（主動指紋辨識）**會向已授權目標送出設計好的探測訊息，再分析回應。像是依約提出幾個固定問題，觀察回答方式。Nmap 的 -O 是這類方法，會產生網路流量。

**Passive Fingerprinting（被動指紋辨識）**則觀察原本就經過、且已獲准分析的流量，不為辨識而另外向目標發送探測。像是在獲准的錄音中分析既有對話。p0f 是此類工具的例子；本課只介紹角色，不要求安裝或擷取任何人的流量。

主動方法能設計問題，被動方法只能利用現場已有的資料。若合法取得的紀錄沒有合適封包，被動方法就缺少辨識材料。能看見哪些流量也受觀察位置影響。兩種方式都需要明確的使用範圍與資料處理權限。[Nmap：被動辨識與其他方法](https://nmap.org/book/osdetect-other-methods.html)

## 3｜工具在看什麼？先認識三種線索

**Packet（封包）**是網路傳送的一份資料；**Header（標頭）**是其中描述如何處理資料的欄位。工具會把多個欄位與多次回應合起來看，而不是只讀一個值。

**A. IP 的 TTL：還能轉送多久**

**IP（Internet Protocol，網際網路協定）**負責封包的位址與跨網路傳遞。IPv4 標頭中的 **TTL（Time to Live，存活時間）**用來限制封包在網路中的壽命，避免一直繞路。實際轉送時，路由器會扣減此值。因此，接收端看到的是沿途處理後的值，未必等於來源一開始設定的值。

例如，合成案例中收到 TTL 61，假設起始值是 64、每站扣 1，才可推算經過 3 次扣減。起始值若未知，這個假設就不能當成已確認路徑，更不能直接推出「一定是某作業系統」。TTL 需要和其他線索一起判讀。[RFC 791：IPv4 標頭與 TTL（1981）](https://www.rfc-editor.org/rfc/rfc791.html#section-3.1)

**B. TCP 接收視窗與選項：如何協商通訊**

**TCP（Transmission Control Protocol，傳輸控制協定）**提供有連線狀態、可靠且有序的位元組傳輸。**Receive Window（接收視窗）**表達接收端願意接收的資料範圍，是流量控制的一部分；它不是整台電腦的記憶體容量，也不是網路頻寬。

TCP 標頭還能帶選項，例如 **MSS（Maximum Segment Size，最大區段大小）**，表達單一 TCP 區段可接收的最大資料量。辨識工具可以觀察初始視窗、選項是否存在及排列方式，將它們納入特徵組合。[RFC 9293：TCP 標頭與選項（2022）](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.1)

**C. 不同探測下的回應方式**

工具也可能比較序號、時間戳記及錯誤回應等特徵。**ICMP（Internet Control Message Protocol，網際網路控制訊息協定）**提供網路狀態或錯誤回報；收到什麼、哪些欄位被保留，都能成為分析材料。Nmap 將多項測試組成指紋，再交給資料庫或分類方法比對。這一課掌握「多個線索共同判讀」即可，不需要背下全部封包欄位。[Nmap：指紋辨識方法](https://nmap.org/book/osdetect-methods.html)

## 4｜為什麼希望同時找到 Open 和 Closed？

**Open（開啟）**表示這次測試看到連接埠有服務接收連線；**Closed（關閉）**表示這次測試得到可判定該入口沒有服務監聽的回應。**Filtered（遭過濾）**則表示受到過濾等因素影響，工具無法按該探測方式判定開或關。

對 Nmap 的 TCP/IP 指紋辨識而言，至少有一個開啟及一個關閉的 TCP 連接埠，通常能提供較完整的比較材料。這好比同時看到窗口「受理案件」與「不受理案件」時的回覆方式。若回應不足，應保留工具警告與辨識限制，不為了取得結果擅自擴大掃描範圍。

辨識參數 **-O 是大寫英文字母 O**。**-sV**偏向服務／版本辨識；兩者的證據來源不同。**-A**還會啟用其他功能，不能把它當作只做 OS 辨識的同義選項。[Nmap：OS 辨識選項](https://nmap.org/book/man-os-detection.html)

本課採紙上判讀，不執行掃描。實作前應另外確認授權的目標、允許探測方式、測試時段及停止條件；營運中的特殊設備應由負責人先評估可承受的測試。

## 5｜相符百分比應該怎麼讀？

假設合成報告寫「系統家族 A：95%」。這表示工具依其比對方法得到很接近的候選結果；記錄時應保留原標籤、分數、工具版本及限制。

以 Nmap 官方說明的 IPv4 比對為例，分數來自各項特徵的加權符合程度。因此，不能直接把 95% 改寫成「這台電腦有 95% 的真實機率是 A」；它不是在所有實際環境都已校準的正確率。不同協定版本的分類方法也可能不同。

若出現「沒有精確匹配」，可能是特徵不足、資料庫缺少合適樣本，或封包受途中設備影響。適當結論是保留候選及待查原因。取得系統名稱，也尚未確認完整修補狀態或可利用弱點。[Nmap：OS 比對演算法](https://nmap.org/book/osdetect-guess.html)

## 6｜你辨認到的是前端，還是後端？

想像你打的是公司的總機，卻把總機的回話習慣當成某位工程師的習慣。網路也有類似情況。

**Reverse Proxy（反向代理）**是代替後方服務接受用戶端連線的前端。**Load Balancer（負載平衡器）**把工作分配到後方服務。**NAT（Network Address Translation，網路位址轉換）**會改寫封包的位址等資訊。這些裝置的行為不同，對觀察的影響也需分開確認。

如果前端終止 TCP 連線，外部 TCP/IP 指紋可能反映前端系統；應用服務回傳的文字則可能來自後端。單純位址轉換不代表所有回應必然都由閘道產生。防火牆可能丟棄、修改或代送部分回應，多個後端也可能讓同一公開入口呈現混合線索。[Nmap：辨識錯誤與網路位置](https://nmap.org/book/osdetect-unidentified.html)

因此，OS 指紋和服務資訊不一致時，先核對網路架構與連線終止位置，再判斷是哪一層的資料。Nmap 本身也把協定堆疊與服務辨識取得的系統線索分開呈現。[Nmap：輸出與代理案例](https://nmap.org/book/osdetect-usage.html)

## 7｜完整合成案例：從「像什麼」走到「確認什麼」

以下是自行編寫的教學情境，不是實際設備掃描結果。

一個已授權的隔離環境，有前端甲及後端乙。外部觀察者取得：

- TCP 443 在這次測試中開啟；TCP 65000 在這次測試中關閉。
- 回應封包 TTL 61，另有 TCP 選項與視窗紀錄。
- 指紋工具提出「系統家族 A」候選。
- 網頁回應含「應用程式 B」自述。
- 架構文件記載：前端甲接受 TCP 連線，再連往後端乙。

一份有用的紀錄可以寫成：

「在指定位置與時間，甲的公開入口回覆了上述 TCP 特徵；工具比對結果接近系統家族 A。架構文件顯示甲終止外部 TCP 連線，因此該指紋優先用來查核甲。應用程式 B 的自述另與乙的執行中服務核對；甲、乙的完整系統版本及修補狀態均待管理端資料確認。」

下一步由授權管理者提供兩台設備的系統版本、執行中的核心與套件、更新紀錄，以及前後端對應關係。資料要能對到同一設備及時間。這樣的紀錄同時保留「已觀察」「合理推測」與「仍待確認」，方便後續盤點與維護。

## 8｜防護與驗收：把識別結果用在維運

辨識的實務價值，是找出需要進一步核對的資產。例如清單上應該只有工作站，卻出現疑似網路設備的特徵，就請管理者核對設備身分與用途。

管理者可依此採取四種工作：

1. **維護資產清單**：核對設備、系統版本、負責人與用途；保留確認日期及來源。
2. **限制不必要的入口**：依需求設計存取規則；驗收時比較核准來源與未核准來源的實際結果。
3. **更新與修補**：用管理端資料核對供應商公告、安裝與重啟狀態；變更指紋或隱藏資訊不等於已完成修補。
4. **觀察異常探測**：將防火牆及設備紀錄依時間、來源、目標對照。沒看到告警時，先確認紀錄範圍與偵測能力，再做判斷。

本章的證據界線仍然相同：連接埠狀態、系統推測、弱點適用性與取得存取權，是不同的判斷。能辨認系統家族，不代表已登入或成功入侵。

## 9｜安全練習與小檢核

使用第 7 節合成資料，以紙本或文字編輯器完成三步，不需連線到任何目標：

1. 列出直接取得的封包、工具輸出與文件，保留各自來源。
2. 寫出甲與乙各自能支持到哪一層結論。
3. 各列一項管理端證據，說明如何確認系統與修補狀態。

預期成果是一份能分清觀察、推論、待確認的短紀錄。練習沒有建立服務或變更設定，無需系統清理；只保存自己的答案即可。

先想四題，下一次也可以只回答你最想確認的一題：

1. 看到 TTL 61，為什麼無法單憑這個數字確認作業系統？
2. 分析已獲授權的既有封包紀錄，與送出 Nmap -O 探測，取得證據的方式有何不同？
3. 指紋推測為家族 A、服務自述為應用程式 B，前方又有 TCP 反向代理。應如何安排查核？
4. 工具沒有精確匹配，或只顯示 95% 候選時，資產清單應如何記錄，還缺什麼資料？

**今天帶走的流程：收集特徵 → 保留比對結果 → 核對網路位置 → 用管理端資料確認。**
