**M05-08｜風險排序、修正與報告：發現弱點之後，怎麼把事情做完？**

上一課處理「工具說的問題是否成立」。這一課接著回答：**確認問題以後，要先處理哪一個、怎麼改善，以及要拿出什麼證據才能結案？**

今天的一句話是：**把已確認的發現，轉成有理由的優先順序、有負責人的行動，以及能被複查的結果。**

**一、用修理房子理解：列出問題，還沒有修好房子**

想像房屋檢查列出三個問題：前門鎖壞了、儲藏室窗框生鏽、浴室水龍頭漏水。報告有照片、有編號，也寫了問題很嚴重，但住戶仍要決定先修什麼、誰來修、修之前怎麼降低風險，以及修好後怎麼確認。

資安也是如此。Risk Prioritization 是「風險優先排序」，把有限人力放在最需要先處理的地方。Remediation 是「修正或補救」，採取措施處理問題。Reporting 是「報告」，把證據、決策、進度與限制交代給需要採取行動的人。

房屋比喻有界線：資安環境會持續改變，今天限制了入口，明天設定變更可能又讓入口開放。因此結案後仍要監控，不能把一次通過當成永久保證。

**二、排序的核心：為什麼這個問題應該先做？**

先以已確認的發現為基礎，再看四件事：

1. **可能造成什麼後果？** 是影響非關鍵測試資料，還是讓重要服務停擺、資料外洩或內容遭竄改？
2. **成立條件在這裡是否存在？** 相關元件有沒有啟用？從哪些位置能到達？需要什麼身分或操作？
3. **目前的威脅情況如何？** 有沒有可靠的實際利用資訊？資訊何時查核？不要把別處發生的利用，直接寫成自己已遭入侵。
4. **現在有哪些防護與限制？** 防護措施是否真的生效？修補是否需要維護時間、相依套件或先做相容性測試？

CVSS 是 Common Vulnerability Scoring System，通用弱點評分系統。它能協助溝通技術嚴重度，但基本分數本身不足以代表組織的全部風險。[FIRST 的 CVSS v4.0 使用指南，文件版本 1.2](https://www.first.org/cvss/v4.0/user-guide)明確區分基本嚴重度與風險。本課不重算分數，也不把分數、資產價值和威脅機率隨意相乘成一個看似精準的答案。

修補困難是需要安排資源的限制，並不會讓原本的技術風險自動變低。高風險又難修的問題，可能更需要先做臨時控制並升級決策。

若已有可信證據顯示正在遭入侵，還要啟動事件應變，不能只排進一般修補佇列。保存證據、控制影響與修正弱點可以互相配合，但不是同一件事。

**三、處置不只一種，狀態也要分開**

**修正根本問題。** 例如安裝適用更新、修正錯誤權限或替換不再支援的元件。Patch 是「修補程式」，通常是供應商提供的軟體修正。不是每個弱點都能靠更新解決，設定與程式邏輯問題可能需要不同處理。

**先降低風險。** Mitigation，緩解，是降低問題造成危害的機會或影響。像暫時關閉受影響功能、限制必要來源、隔離資產。這些措施要驗證效果並記下殘餘風險，也就是措施實施後仍然留下的風險。「入口受限」不能直接改寫成「套件已修補」。

**停止使用造成風險的功能或資產。** 例如經核准退役無法維護的系統。要確認相關服務、相依關係與資料保留需求，不是看到弱點就直接關機。

**接受風險。** 由有權限承擔決策的人，在知道影響、替代方案與限制後決定暫時承擔。應有負責人、適用範圍、理由與重新檢視條件。掃描人員不能因為「不好修」就自行把問題勾成接受。

**分擔風險後果或管理工作。** 例如有契約的保險或委外服務。這不會自動消除弱點，也不代表組織不再需要管理供應商及自身責任。

這些方式可以組合使用，例如先限制入口，再安排永久修正。[NIST SP 800-40 Rev. 4，2022 年 4 月，第 2 節](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-40r4.pdf)將風險回應分成接受、降低、移轉與避免；其中降低風險也包含修補。本課把「永久修正」和「暫時緩解」分開說，是為了讓報告狀態更清楚，不是另創官方分類。

**四、讓修正可執行：變更前、變更中、變更後**

變更前，要確認受影響資產與元件、可信的更新來源、相容性、相依項目和負責人。需要停機時，安排核准的維護時段；準備可用的備份及復原方式，並確定出問題時由誰判斷停止或回復。

Rollback 是「回復到先前狀態」。它能協助處理更新造成的故障，但回復後可能把原本的弱點一起帶回來，所以不能只寫「服務恢復，全部完成」，還要重看資安風險。

變更中，依核准計畫逐步執行並留紀錄。重要系統可能先小範圍驗證，再逐批推進。實際需要的管理權限、重啟或網路設定變更，都要在授權範圍內，不為了趕進度擅自關閉防護。

變更後，至少分開確認兩件事：**原問題是否受到預期處理，以及正常服務是否仍能運作。** 更新安裝成功的訊息只是其中一項證據；若需要重新啟動才能生效，還要確認實際執行中的元件已使用新版本。[NIST SP 800-40 Rev. 4，第 2.3 節](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-40r4.pdf)將部署準備、部署、驗證與後續監控分開，正是為了避免把「有按更新」當成結果。

**五、完整合成案例：三個問題，三條處理線**

以下是虛構的「小樹訂單服務」，不是任何真實客戶或正式弱點編號，也沒有執行掃描。假設本次已確認三項發現。

**A：公開服務的元件有已確認弱點，適用功能已啟用。** 它承接重要訂單，另有可信來源指出同類弱點正遭利用。團隊優先處理 A：先評估並核准可行的臨時入口限制，同時測試更新、安排變更與複驗。這是處理優先，不等於不經測試直接更新。

**B：隔離測試環境有另一項高嚴重度弱點。** 本次已查明沒有真實資料、指定網路控制確實限制可到達性，也沒有已知通往正式環境的相依路徑。在這些假設下，可以排在 A 之後，由測試環境負責人安排修正。若後來發現它能連到正式資料庫，就必須重新排序，不能一直沿用「只是測試機」的標籤。

**C：一份報告缺少必要的認證檢查。** 這不是已證實安全，也不能憑空給出弱點數。把它另列為檢查缺口，指定補查責任與時間。如果它是重要資產，補齊證據本身也可能很急。未知不應自動排到最後。

假設 A 已完成入口限制，但更新還沒有安裝，報告應寫「已緩解、永久修正待辦」。之後完成更新，但複驗登入失敗，狀態應是「已執行更新、驗證未完成」。直到取得適用版本已生效、必要檢查完成及服務正常的證據，才足以支持這個範圍的修正結案。

這個案例沒有通用的幾小時或幾天期限。期限要依實際契約、政策、適用法規、威脅與系統條件決定，不能把教學案例的安排當成所有組織的規定。

**六、報告要讓管理者能決策，也讓工程師能接手**

管理摘要先回答：本次查到什麼重要風險、影響哪些服務、已做什麼、還需要誰決定什麼。不要只貼上紅黃綠數字，也不要把未檢查的資產放進「全部安全」。

技術明細至少保留以下內容：

- 範圍與條件：資產、元件、時間、來源位置、檢查方法及未完成部分。
- 發現與證據：唯一識別碼、具體主張、適用條件、必要且已去識別的證據與來源。
- 優先順序：技術嚴重度、當地情境、排序理由，以及仍不確定的部分。
- 處理計畫：負責人、措施、目標時間、相依條件、核准或例外紀錄。
- 結果與複驗：變更紀錄、複驗時間與方法、實際結果、殘餘風險及下次檢視條件。

可以寫：「截至本次查核，A 已完成指定來源的入口限制；受影響套件仍待更新，永久修正尚未結案。」這句話同時交代完成部分與剩餘責任，不必把進度寫成全有或全無。

報告本身可能暴露系統弱點，因此只交給核准的讀者，保留存取限制；不放密碼、金鑰、工作階段憑證或不必要的個資。對外版本應依授權另行去識別，不直接轉寄原始技術報告。

**七、怎麼判斷進度真的改善？**

數字要先說清楚單位。十台主機各有同一項弱點，可以是「十筆資產上的發現」，也可以是「一種弱點影響十台」，兩種統計回答不同問題，不能混用。同一資產同一問題重複掃到，也不能每次都算全新的問題。

比較前後變化時，要一起看資產範圍、成功檢查比例與例外處理。如果這次少掃了二十台，弱點數下降並不能單獨證明安全改善。

有用的追蹤包括：已確認但尚未處理的高優先項目、超過約定時間的項目、已修正且複驗通過的項目、暫時緩解或接受風險的項目，以及仍未完成檢查的資產。數量之外也要說明主要風險是否下降，避免只追求容易關閉的大量小問題。

「結案」需要清楚的結案原因。修正通過、資產退役、誤報判定、接受風險是不同結果；即使工單系統都標成關閉，報告也要讓讀者辨認。

**八、紙上練習與一個小檢核**

只用紙筆或本機文字檔，不連任何目標，也不實際改設定。

1. 替案例 A、B、C 各寫出下一個具體動作與負責角色。
2. 為 A 補上「完成入口限制」與「永久修正結案」各需要的證據。
3. 寫一段三句話的管理摘要，分別交代已完成、尚待完成與需要的決策。對沒有證據的部分明寫待確認。

預期得到的是可追蹤的合成處理紀錄，並非真實稽核或測試結果。練習後保留或刪除本機草稿即可，沒有設備需要復原。

**小檢核：團隊已限制外部入口，也回報更新安裝成功，但後續掃描因登入失敗而沒有完成必要檢查。這筆發現現在能不能寫「修正完成且驗證通過」？應該如何描述目前狀態，並補哪一類證據？**

今天帶走的完整流程是：**確認發現，說明排序理由，指派處理，驗證實效，留下報告，再持續追蹤。** 報告交出去是溝通完成；風險是否改善，還要看措施與證據。
