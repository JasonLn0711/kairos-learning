# M04-06｜Unix/Linux 使用者與 NFS：為什麼名字一樣，卻讀不到檔案？

這堂課最重要的觀念是：

Linux 不會只因為兩個帳號的名字相同，就認定它們是同一個人；NFS 能看到檔案，也不代表有權限讀取內容。

想像你在兩間公司都認識一個叫「小林」的人。第一間公司的小林，員工編號是 1001；第二間公司的小林，員工編號是 2001。

雖然兩人名字完全一樣，但門禁系統看的是員工編號和授權，不是名字。

Linux 和 NFS 也是類似的道理。

[[figure:workflow]]

掌握這條流程，就能理解 Linux 使用者管理、檔案權限、NFS，以及 CEH 在列舉階段究竟是在蒐集什麼證據。

## 一、Linux 的帳號，是名字重要，還是編號重要？

先認識三個東西：

| 名稱       | 白話意思        | 範例        |
| -------- | ----------- | --------- |
| Username | 使用者名稱，方便人辨識 | `learner` |
| UID      | 使用者編號       | `1001`    |
| GID      | 群組編號        | `3000`    |

Linux 在一般檔案權限判斷中，主要依據的是數字身分，而不是人類看得懂的帳號名稱。程序實際用於檔案存取的身分（Linux 的 filesystem UID／GID，通常與有效 UID／GID 相同）及補充群組也要一併核對。

例如：

[[figure:identity]]

這兩個帳號都叫 `learner`，可是 UID 一個是 1001，一個是 2001。

因此，不能因為名稱相同就說它們具有同樣的檔案身分。

你可以把 Username 想成員工姓名，UID 想成員工證號，GID 則是部門編號。

## 二、`getent`、`id`：查帳號與查現在的身分有什麼不同？

假設你在自己的 Linux 電腦打開 Terminal。

第一個指令：查帳號是否存在於名稱服務中

```
getent passwd learner
```

合成輸出：

```
learner:x:1001:3000:...:/home/learner:/bin/bash
```

這代表系統依照 NSS 設定找到了這筆帳號資料。

`1001` 是 UID，`3000` 是主要 GID。`x` 不是密碼內容，通常表示密碼雜湊不直接放在這個帳號欄位。

特別注意：這筆資料不一定來自本機 `/etc/passwd`，也可能來自 LDAP 等集中式名稱服務。

第二個指令：查指定帳號的身分與群組

```
id learner
```

例如：

```
uid=1001(learner) gid=3000(staff) groups=3000(staff)
```

這是在問：「系統目前查得到的 learner，是哪個 UID？被分配到哪些群組？」

第三個指令：查現在執行指令的身分

```
id
```

這是在問：「目前這個程序帶著什麼使用者與群組身分？」

`id learner` 與 `id` 不能完全互相取代。前者是查指定帳號；後者查目前程序。

為什麼差別重要？

假設管理者剛把你加入 `research` 群組，但你的 Terminal 是很久以前登入的。

帳號資料可能已經更新，既有 Shell 程序卻還帶著原來的群組清單。

因此，即使 `id learner` 看得到新群組，也不能直接推論所有既有程序已取得該群組身分。

更重要的是，能查到帳號，不代表這個帳號能登入、更不代表具有管理員權限。

## 三、NFS 是什麼？為什麼兩部電腦能共用資料？

NFS 是 Network File System，網路檔案系統。

想像研究室有一台 Linux Server，儲存大量研究資料。其他研究生各自有電腦，但不想每個人都複製一份相同資料。

NFS 就能讓大家透過網路使用伺服器上的檔案系統。

[[figure:mount]]

這裡需要認識兩個英文單字。

Export（匯出）：伺服器宣布「這個資料夾可以提供哪些用戶端使用，以及在什麼條件下使用」。

Mount（掛載）：用戶端將遠端檔案系統接到本機目錄，例如 `/mnt/data`。

但有一個重要區別：掛載成功，只表示你已經接上共享檔案系統，不代表每個檔案都可以讀取或修改。

就像公司允許你進入檔案室，不代表你可以打開裡面所有機密文件。

### `sec=sys` 又是什麼？

NFS 使用 RPC（Remote Procedure Call，遠端程序呼叫）來傳遞操作請求。

在常見的 `sec=sys`，也就是 `AUTH_SYS` 模式中，用戶端會提供 UID、GID 等身分資訊給伺服器。

問題在於，這些數字主要由用戶端宣告，本身缺少足以獨立驗證使用者身分的密碼學證明。因此，它依賴對用戶端主機及其管理方式的信任。

這也是為什麼不能只把不同電腦上的帳號都命名為 `learner`，就以為 NFS 身分問題已經解決。

進階補充：NFSv4 的檔案擁有者屬性可能顯示為 `learner@example.com`，但「檔案擁有者如何表示」和「這次網路請求如何驗證身分」仍然是兩個不同問題。

## 四、Linux 權限：為什麼看得到檔案名稱，卻讀不到內容？

這是本課最值得理解的技術核心。

Linux 的基本檔案權限分成三種：

| 符號  | 一般檔案 | 目錄                 |
| --- | ---- | ------------------ |
| `r` | 讀取內容 | 列出目錄項目名稱           |
| `w` | 修改內容 | 配合其他條件新增、刪除或重新命名項目 |
| `x` | 執行檔案 | 通過目錄，查找指定項目        |

目錄的 `x` 不代表執行目錄，而是 Search（搜尋或通過）權限。

假設你有這個路徑：

```
/shared
    └── reports
         └── report.txt
```

你能列出 `reports` 裡有 `report.txt`，可能是因為有目錄的讀取權限。

但想要真正讀取 `report.txt`，你還需要能通過路徑上的目錄，以及對檔案本身具有讀取權限。

### 看懂 `rw-r-----` 與 `rw-------`

一般 Linux 權限字串分成三組：擁有者、群組、其他人。

[[figure:permissions]]

這個練習只展示基本權限，暫時不考慮 ACL、SELinux、特殊特權及 NFS 額外政策。

請特別記住：Linux 不是把三組權限全部加起來給你使用，而是依照你的身分選出適用的那一組。

如果你的 UID 符合擁有者，就看 Owner 那組；否則，如果主要群組或任一補充群組符合，就看 Group；再不符合才看 Others。選到某一組後，不能因該組沒有讀取權就再借用 Others 的權限。

## 五、解讀本課的 `Permission denied` 案例

現在把前面的知識放在一起。

合成案例：讀取 `report.txt`

本例假設路徑可通過、Export 允許該操作、沒有 ACL／額外特權或其他身分映射；以下只判斷表中身分與基本檔案權限。

| 用戶端 UID    | 1001        |
| ---------- | ----------- |
| 用戶端 GID    | 3000        |
| 檔案擁有者 UID  | 2001        |
| 檔案所屬群組 GID | 3000        |
| 檔案權限       | `rw-------` |
| NFS 安全模式   | `sec=sys`   |

伺服器端的基本權限判斷

1. UID 是否符合擁有者？ 不符合，因為 `1001 ≠ 2001`。
2. GID 是否符合？ 符合，因為兩邊都是 `3000`。
3. 群組有讀取權嗎？ 沒有。`rw-------` 的 Group 是 `---`。

Permission denied

依本例已知條件，伺服器拒絕讀取。

那麼，是 `root_squash` 導致的嗎？

不是。本例的請求 UID 是 1001，並不是 root 常見的 UID 0。

`root_squash` 的功能是把來自用戶端的 UID／GID 0 映射成匿名身分；`all_squash` 才是把所有使用者請求映射為匿名身分。

因此，這個案例有充分證據指出：請求者不是檔案擁有者，雖然群組相同，但群組沒有讀取權限。

這是可以根據已知設定作出的結論。

反過來說，如果今天只看到一句 `Permission denied`，卻沒有 UID、GID、路徑權限與安全設定，就不能這麼快下定論。

## 六、CEH 的觀點：列舉到了什麼，不代表取得了什麼

CEH M04 的重要能力，不是記住多少指令，而是能分辨不同工具實際提供了哪一層證據。

例如在經授權的測試環境：

```
rpcinfo -p 192.0.2.10
```

這是在查遠端 RPC 服務登記資訊，不是在讀取檔案。

```
showmount -e 192.0.2.10
```

這是透過 MNT 服務查詢 NFS Export 清單，也不是取得共享內所有資料的讀取權。

你還應該認識兩個常見 Port：

| Port   | 常見用途                |
| ------ | ------------------- |
| `111`  | rpcbind，協助尋找 RPC 服務 |
| `2049` | NFS 服務              |

NFSv3 常涉及 rpcbind、mountd 等服務；NFSv4 可以直接使用 2049，不必依賴同樣的 MNT 查詢機制。

所以，即使 `showmount -e` 查不到結果，也不能證明伺服器沒有 NFS。

### 你需要建立一套「證據階梯」

| 觀察到的結果    | 真正能證明什麼       |
| --------- | ------------- |
| 查到帳號名稱    | 名稱服務有回覆帳號資料   |
| 查到 Export | 服務提供了共享相關資訊   |
| Mount 成功  | 指定共享已掛載       |
| 列出檔案名稱    | 能取得相應目錄清單     |
| 成功讀取檔案    | 對該檔案的讀取操作成功   |
| 成功修改檔案    | 對該檔案的特定修改操作成功 |

每一層都不能自動推論下一層成立。

這也是資安鑑識、滲透測試報告與系統除錯共同需要的觀念：觀察與結論之間，必須有足夠的證據。

## 七、管理者怎麼保護 NFS？遇到拒絕時又該怎麼查？

NFS 安全至少有三層需要一起考慮。

| 安全層次  | 要回答的問題            | 常見控制                    |
| ----- | ----------------- | ----------------------- |
| 主機與共享 | 哪些用戶端可以使用共享？      | Export 允許來源、`ro`／`rw`   |
| 身分與傳輸 | 是誰提出請求？請求有沒有受到保護？ | `sec=sys`、Kerberos      |
| 檔案權限  | 這個身分可以做什麼？        | UID、GID、Permissions、ACL |

### Kerberos 能解決什麼？

前面提到 `sec=sys` 比較依賴對用戶端的信任。

如果需要更強的身分驗證，就可以評估 Kerberos 安全模式。

| 模式          | 提供的主要安全能力        |
| ----------- | ---------------- |
| `sec=sys`   | 傳遞系統身分，缺少密碼學身分驗證 |
| `sec=krb5`  | 使用 Kerberos 驗證身分 |
| `sec=krb5i` | 身分驗證，加上資料完整性保護   |
| `sec=krb5p` | 身分驗證、完整性及傳輸內容加密  |

這些能力需要相應基礎設施和設定才能啟用，並不是 NFSv4 一定自動使用加密。

如果日後在研究室或公司遇到 NFS 讀取失敗，正確的除錯順序應是：確認哪個操作失敗、查實際程序身分、查 NFS 版本與安全模式、查路徑與檔案的有效權限，再由管理者檢查 ACL、Export 設定及相關日誌。

不要一看到 `Permission denied` 就執行 `chmod 777`。這可能讓本來無權讀取的其他使用者取得權限，甚至仍然無法解決真正的拒絕原因。

情境題：判斷拒絕原因

假設另一個測試案例，NFS 伺服器的檔案 `budget.txt` 有以下設定：

檔案擁有者 UID：2001；檔案 GID：3000；權限：`rw-r-----`。用戶端實際請求 UID：1001、GID：4000，補充群組不含 3000。假設路徑可通過，沒有 ACL 或額外特權，使用 `sec=sys` 且未另行映射身分。

請試著用自己的話回答：

A. 用戶端能讀取 `budget.txt` 嗎？為什麼？

B. 如果把用戶端 GID 改成 3000，結果可能有什麼不同？

C. 如果能列出 `budget.txt` 名稱，是否代表能讀取內容？

先自行作答，再展開本頁參考答案核對；本站不提交答案或自動評分。
