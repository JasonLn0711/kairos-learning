# CEH M09-03｜教學參考解答

以下是教學用參考解答，不是學習者已提交的作答，也不代表理解已確認。請先自行推理，再展開相應解答比對。

## 1. 兩分鐘小實驗：哪個查證方式比較可靠？

參考答案是 B：自行開啟先前確認的官方銀行 App，從既有入口查詢。關鍵不是「App 一定比電話安全」，而是這個入口不是這次可疑來電或簡訊臨時指定的。

A 仍然使用可疑來源提供的號碼。即使接電話的人說「確實是我們」，也可能只是同一方安排的另一段話，不能當成獨立證明。

C 要求對方再說一次員工編號，也沒有離開對方控制的資訊來源。對方說得出編號，不等於你已從可信系統查到這個人、工單與要求。

實際處理時，先不提供登入驗證碼，結束可疑通話，再使用自己既有的可信聯絡方式確認身分、要求與授權。即使確認是銀行人員，也不要因此省略敏感操作的正常程序。[加拿大資安中心：語音釣魚的防護](https://www.cyber.gc.ca/en/what-voice-phishing-vishing-itsap00102)

## 2. 課後第 1 題：這起事件可以有哪些分類？

這些概念可以同時成立：簡訊管道對應 Smishing，電話中的欺騙性誘導對應 Vishing，假扮銀行客服則是 Impersonation。它們分別描述管道與手法，不是互斥選項；整體仍屬於 Phishing 的範圍。

從目標角度看，題目明確鎖定公司財務主管，可描述為針對特定目標的 Spear Phishing。如果這位主管具有高階職位、重大付款決策權或其他高價值權限，還可能更精確地稱為 Whaling。不要只因「主管」兩字就補出題目沒有提供的職級或權限。

重點是分清楚「攻擊誰」與「冒充誰」。這裡被鎖定的是財務主管，冒充的是銀行客服；不是因為攻擊者用了某個顯得重要的身分，事件才算鯨釣。實際事件仍應先核對目標、內容與行為，再選擇有證據支持的分類。[加拿大資安中心：社交工程](https://www.cyber.gc.ca/en/guidance/social-engineering-itsap00166)

## 3. 課後第 2 題：真 OTP 為什麼還可能幫助攻擊者？

驗證碼是真的，只能說明它來自真正的平台或符合驗證規則；不能替索取驗證碼的人證明身分。若攻擊者已掌握其他必要條件，又誘導使用者交出仍有效的碼，就可能把它提交給真正的平台，完成那次驗證。

但「取得碼」不等於「一定登入成功」。仍要看碼對應哪項操作、是否過期或已使用，以及裝置限制、額外驗證和其他條件是否成立。成功與否必須用實際紀錄確認，不能只憑這個機制示意推定。

這不代表 MFA 沒有用。不同因素能增加保護，例如只有密碼外洩時，額外因素可能阻止登入；問題在於不同驗證方式的抗釣魚能力不同。需要人手轉填的 OTP 或簡訊帶外驗證輸出，可能被誘騙轉交，不應當成抗釣魚驗證。正確實作的 FIDO2／WebAuthn 則利用密碼學綁定驗證對象。[NIST SP 800-63B-4：抗釣魚能力](https://pages.nist.gov/800-63-4/sp800-63b.html#phishres)

最後還要分開登入與授權：強化登入驗證，不會自動判斷每筆付款、每次資料交付都合理。仍需獨立核准與最小權限等其他控制。

## 4. 課後第 3 題：可以下什麼結論，先做什麼？

依題目前提，員工已把 OTP 說出去，應視為驗證資訊暴露風險；通話紀錄則能支持有相應通話活動。若是在真實調查中，通話紀錄本身不一定證明說話內容，仍要區分使用者陳述、其他佐證與已核實事實。

目前不能直接認定未授權登入已成功、帳號已被完整控制，或教材資料已經外洩。還要查碼對應的操作、有效性、驗證與登入結果、操作者是否獲授權，以及後續存取、下載或傳輸範圍。

第一步不是等到證據全部齊全才處理，而是停止可疑互動，不再提供碼或核准要求，立即從既有正式服務台通報。由有權負責的人員依風險保護帳號、檢查或撤銷可疑工作階段、處理必要憑證，並保留相關訊息、時間與日誌；不要自行清除紀錄或再次測試可疑內容。

之後再交叉核對登入、裝置、權限變更、服務工單與資料活動。找不到異常紀錄不代表絕對安全，也可能是紀錄不完整。白話總結就是：風險可以先處置，成功入侵與外洩則要各自取得證據。[加拿大資安中心：社交工程事件應變](https://www.cyber.gc.ca/en/guidance/social-engineering-itsap00166)
