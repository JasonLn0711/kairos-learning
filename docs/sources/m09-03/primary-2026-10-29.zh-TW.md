# CEH M09-03｜語音釣魚、簡訊釣魚與身分冒充

Module 09：Social Engineering（社交工程）｜初學者教學｜約 12–15 分鐘

本課最重要的觀念：攻擊者不一定需要破解你的電腦，只要讓你誤以為他是可信任的人，就可能誘導你親手完成不安全的操作。

而且，收到兩則看似互相證明的訊息，不代表有兩個獨立的可信來源。

我們會透過一間虛構的 Northstar 教材中心，依序理解：

1. 攻擊者怎麼利用簡訊、電話與假身分？
2. 為什麼真正的登入驗證碼，也可能變成攻擊工具？
3. 為什麼獨立查證比辨識聲音真假更可靠？
4. 資安人員如何結合 CEH 其他單元的觀念，分析、阻擋與調查攻擊？

## 一、先建立全貌：釣魚攻擊其實有四個不同面向

上一課 M09-02 介紹了 Phishing（釣魚）、Spear Phishing（魚叉式／定向釣魚）與 Whaling（鯨釣）。

今天要加入三個新名詞：

- Smishing：簡訊釣魚，使用簡訊誘導被害人。
- Vishing：語音釣魚，透過電話或語音誘導被害人。
- Impersonation：身分冒充，讓被害人誤認攻擊者是其他人或機構。

這些不是互斥的攻擊分類。它們是在回答不同問題。

圖 1｜本課建立的四維攻擊分析框架。

例如，攻擊者可能蒐集小林的背景資料，特別針對他設計簡訊，再以電話假冒公司客服，要求提供驗證碼。

如果確實有證據支持「量身設計」，我們就可以描述為：

定向釣魚（目標）＋簡訊與語音釣魚（管道）＋身分冒充（手法）＋取得驗證碼（目的）。

注意一個考試容易犯的錯誤：攻擊者自稱董事長，並不自動構成 Whaling。鯨釣主要是指鎖定高階或高價值人物，而不是冒充高階人物。

加拿大資安中心也將 Smishing、Vishing 等歸在社交工程及釣魚攻擊的相關類型。[加拿大資安中心：社交工程](https://www.cyber.gc.ca/en/guidance/social-engineering-itsap00166)；[語音釣魚](https://www.cyber.gc.ca/en/what-voice-phishing-vishing-itsap00102)；[簡訊釣魚](https://www.cyber.gc.ca/en/guidance/smishing-protect-yourself-sms-attacks-itsap00103)

## 二、Vishing 與 Smishing：兩個管道，可能只有一個攻擊者

想像你是 Northstar 教材中心的小林。

上午 10 點，你收到簡訊：

> 【Northstar 資訊服務台】偵測到您的教材帳號異常登入，請儘速聯繫客服，以免帳號停權。

兩分鐘後，電話響了。

對方說：「小林您好，我是資訊服務台。你現在負責的教材專案帳號有異常，我們剛才應該有發簡訊給你。」

小林心想：「他竟然知道我的名字、工作內容，還知道我剛收到簡訊。」

然而，真正可能發生的是：

圖 2｜攻擊者可以同時控制簡訊和電話，製造彼此佐證的假象。

這個手法利用了人的一種直覺：當不同地方都出現一致資訊，我們容易認為可信度增加。

但從資安角度，關鍵是證據是否真正獨立。

### 三個需要分清楚的技術觀念

1. Caller ID Spoofing（來電顯示偽冒）

電話顯示的號碼或名稱，可能遭到偽冒。

就像寄信時，信封上寫「某某銀行寄出」，不代表你已經確認寄件者真的是銀行。

FTC 提醒，不能只根據來電顯示判定對方身分。[美國聯邦貿易委員會：來電顯示可以被偽冒](https://consumer.ftc.gov/consumer-alerts/2016/05/scammers-can-fake-caller-id-info)

2. AI Voice Cloning（AI 語音複製）

攻擊者也可能使用 AI 模仿主管、親友或客服人員的聲音。[FTC：AI 語音複製詐騙](https://consumer.ftc.gov/consumer-alerts/2023/03/scammers-use-ai-enhance-their-family-emergency-schemes)

但要注意：

- 聽起來像真人，不代表是真人。
- 聽起來像某個人，不代表真的是那個人。
- 聲音有失真，也不能直接認定使用了 AI。

因此真正的防護策略，不是要求你練出一雙能百分之百辨認 AI 假聲音的耳朵，而是建立不依賴聲音本身的身分驗證程序。

3. Reconnaissance（偵察）與 Footprinting（足跡蒐集）

這裡可以連結 CEH M02 的相關概念。

攻擊者能叫出小林的姓名、部門與專案名稱，可能是因為事前從公司網站、社群貼文、活動名單等地方蒐集資訊。

如果是從系統服務查得具體帳號、群組或共享資訊，還可能連結 M04 的 Enumeration（列舉）。

但要嚴格區分：

知道一個人的背景，不代表攻擊者已經入侵他的帳號；知道內部專案名稱，也不直接證明資料曾經外洩。

## 三、真正的 OTP，怎麼會協助假客服？

這是整堂課最值得理解的技術機制。

OTP（One-Time Password，一次性密碼／驗證碼）原本是一種安全措施。

本課用 OTP 泛指這個案例的一次性登入碼。嚴格依 NIST 分類，平台傳到手機的簡訊碼屬於帶外驗證（Out-of-Band Authentication），與驗證器自行產生的 OTP 是不同類型；兩者若需要人手轉填，仍可能遭到誘騙轉交。[NIST SP 800-63B-4：驗證器與抗釣魚能力](https://pages.nist.gov/800-63-4/sp800-63b.html#phishres)

假設你登入教材系統：

1. 輸入帳號與密碼。
2. 系統要求第二項驗證。
3. 平台傳送一次性驗證碼到你的手機。
4. 你在自己發起的登入流程中輸入驗證碼，平台驗證通過後才可能允許登入。

正常情況下，OTP 是在降低帳號遭盜用的風險。

但攻擊者可以利用社交工程，嘗試讓你把驗證碼交給他。

圖 3｜一次性驗證碼的社交工程攻擊流程。這是合成情境，並非所有網站都採取相同驗證程序。

### 為什麼平台無法單靠 OTP 分辨是不是本人？

用白話來說：

平台檢查的是「這組驗證碼是否正確、有效、符合驗證規則」，不一定能知道輸入驗證碼的人是不是手機真正的持有人。

假設：

- 攻擊者已取得小林的帳號密碼。
- 平台再要求一組簡訊驗證碼。
- 小林把驗證碼念給假客服。
- 攻擊者在有效期限內，把驗證碼提交給真正的平台。

在其他驗證條件也成立時，攻擊者就可能成功登入。

這裡也要修正一個常見誤解：不是所有 OTP 只要被知道，就一定可以登入。 有些系統還有裝置限制、額外驗證、風險判定等條件；不同驗證碼也可能只對應特定操作。

### 接著理解 MFA 與抗釣魚驗證

MFA（Multi-Factor Authentication，多因素驗證）是要求不同類型的驗證因素。

例如：

| 驗證因素               | 生活化例子       |
| ------------------ | ----------- |
| Something you know | 你知道的密碼      |
| Something you have | 你持有的手機或安全金鑰 |
| Something you are  | 你的指紋等生物特徵   |

這裡的核心不是驗證步驟有幾個，而是有沒有使用不同類型的因素。兩組密碼不會因為輸入兩次，就自動變成 MFA。

NIST SP 800-63B-4 明確指出，需要手動輸入驗證輸出的 OTP 與帶外驗證，不屬於抗釣魚驗證（Phishing-resistant Authentication），因為手動輸入不會把驗證輸出綁定到正在驗證的特定工作階段（一段特定的驗證互動），攻擊者可能轉交該輸出。[NIST SP 800-63B-4：抗釣魚能力](https://pages.nist.gov/800-63-4/sp800-63b.html#phishres)

進一步比較：

傳統 OTP

本例的簡訊驗證碼有期限、只能使用一次，仍可能被即時轉交給攻擊者。

抗釣魚驗證

例如正確實作的 FIDO2／WebAuthn 驗證，透過密碼學機制綁定驗證對象。

圖 4｜抗釣魚能力不等於只是增加一個驗證步驟。

Passkey（通行密鑰）是基於 FIDO 標準的密碼學登入憑證，常透過 WebAuthn 使用；但完整服務的保護仍要看具體實作、帳號復原及使用情境。抗釣魚驗證主要防止登入憑證被假網站利用，不會自動阻擋所有詐騙付款或不當資料授權。[FIDO Alliance：Passkeys](https://fidoalliance.org/passkeys/)

### 再連到 Authentication 與 Authorization

這裡要建立資安工程最基本的區分：

- Authentication（身分驗證）：你是誰？你能否證明自己控制這個帳號？
- Authorization（授權）：你通過身分驗證後，可以做什麼？

就像進辦公室要先刷員工證，但進去之後，也不是每間主管辦公室、每個資料櫃都可以打開。

因此，登入成功不代表所有操作都有授權；攻擊者取得驗證碼，也不代表他已讀取全部資料。

## 四、Independent Verification：真正的查證，是離開對方控制的資訊來源

現在回到小林的案例。

假客服說：「如果你不相信我，可以回撥剛剛簡訊裡的客服電話。」

小林照做，接電話的人說：「對，剛才確實有一張異常登入工單。」

你覺得這樣完成查證了嗎？

沒有。因為客服號碼和工單資訊，可能全部都是攻擊者提供的。

圖 5｜獨立查證最重要的是信任來源，不是更換通訊工具。

假設你收到有人冒充銀行客服的電話，正確做法是結束可疑通話，再自己開啟銀行原本就已安裝的官方 App，或使用之前已核實的官方聯絡方式查證。

在台灣，民眾也可以自行撥打 165 反詐騙諮詢專線，協助辨識可疑詐騙情境。這是刑事警察局提供的正式諮詢管道。[刑事警察局：165 反詐騙諮詢專線](https://www.cib.npa.gov.tw/ch/app/faq/view?id=18233&module=faq&serno=8306e5f3-6b7a-45e9-9d21-af24d4fac9af)

但要進一步記住：即使確認來電者真的在公司工作，也不代表他的每一項要求都有授權。

例如真正的資訊人員要求你寄出全公司員工資料，也需要檢查工作目的、權限與正式核准流程。

所以我們要分成三件事：身分是真的嗎？要求是真的嗎？操作有獲得授權嗎？

## 五、資安事件判讀：交出驗證碼，不等於已經完成入侵

這裡直接連結先前 M01-07 的 Incident Response（資安事件應變）。

假設小林向資安人員報告：「我接到假客服電話，好像把驗證碼唸給他了。」

資安工程師不能直接寫：

「攻擊者已經入侵公司，所有教材資料全部外洩。」

因為目前的證據只能支持更有限的結論。

圖 6｜事件發展與證據層次。實務上各階段可能重疊、跳過或尚無法確認。

現在用實際的證據思考：

| 已經掌握的資料     | 能合理下什麼結論？             |
| ----------- | --------------------- |
| 簡訊截圖與通話紀錄   | 確實有訊息與通話的跡象，還不能確認來源身分 |
| 小林表示已唸出 OTP | 有驗證資訊暴露風險，需要立即處理      |
| 平台顯示成功登入    | 有登入成功事件，仍要確認是否為未授權登入  |
| 異常裝置存取、下載紀錄 | 有值得調查的存取行為，需確認操作者及目的  |
| 經核實的資料傳輸證據  | 才能進一步支持資料外流判斷，並評估範圍   |

風險處置可以先於完整調查，但最終結論不能超越證據。

如果小林真的把驗證碼交給陌生人，應立即透過正式服務台通報。視系統情況，由授權人員檢查登入紀錄、終止可疑工作階段、更新必要憑證，並保全日誌。

如果沒有看到登入紀錄，也不能保證絕對安全，因為紀錄可能不完整或尚未查到正確來源。

這其實就是 M01-07 教過的原則：先限制可能的損害，再調查、復原與改善。

現在最重要的不是再背更多縮寫，而是理解相關概念怎麼一起運作。

圖 7｜將 M09-03 放回整體 CEH 的知識架構，而不是單獨背誦三個新名詞。

### 再深入兩個最重要的連結

第一個：M01-05 MITRE ATT&CK。

M01-05 說明了：MITRE ATT&CK 不只是把攻擊分階段，而是用 Tactics（戰術目的）與 Techniques（技術行為）描述攻擊。

針對目標使用語音誘導他提供存取權限，能與 ATT&CK 的 [T1566.004 — Spearphishing Voice](https://attack.mitre.org/techniques/T1566/004/) 對應。這項技術位於 Initial Access（初始存取）的戰術範疇。

但不能因為看到一通假客服電話，就認定攻擊者已成功取得初始存取權限。ATT&CK 的技術分類是在描述行為，事件成功程度仍要用證據確認。

第二個：M01-06 Defense in Depth（縱深防禦）。

假設 Northstar 要防止這類事件，不能只靠教育員工「不要相信陌生電話」。

應同時安排不同層次的措施：

| 防禦層次  | 對應措施                           |
| ----- | ------------------------------ |
| 人員與流程 | 既有查證管道、可疑要求通報、敏感操作複核           |
| 帳號與驗證 | 適當採用抗釣魚 MFA、異常登入監控             |
| 權限管理  | 最小權限（Least Privilege）、重大變更另行核准 |
| 裝置保護  | 遠端協助工具須經正式授權                   |
| 偵測與應變 | 日誌、異常告警、工作階段撤銷與事件調查            |

這就是縱深防禦的價值：即使小林一時做出錯誤判斷，還有其他控制措施降低攻擊成功與損害擴大的可能性。

從 M01-01 的 CIA Triad 來看，未授權讀取教材資料可能危害機密性（Confidentiality）；擅自修改課程成績可能危害完整性（Integrity）；帳號遭鎖定使工作中斷，則可能危害可用性（Availability）。

## 七、兩分鐘小實驗：親自判斷可信來源

不用安裝 Kali Linux、不需要執行指令，也不需要真的傳簡訊。

假設有人自稱銀行客服，要求你提供手機收到的登入驗證碼。你要如何查證？

A. 回撥對方簡訊提供的客服號碼

B. 自行開啟先前確認的官方銀行 App，從既有入口查詢

C. 請來電者再說一次自己的員工編號

請先選擇並說出理由，再展開參考解答。這是桌上練習，不會送出答案，也不代表已完成理解驗收。

## 八、課後理解檢核

下面三題涵蓋本課的攻擊分類、驗證機制與事件應變。先用自己的話思考，不需要寫很長。

第 1 題｜攻擊分類

攻擊者針對一名公司財務主管，先傳送釣魚簡訊，再打電話假冒銀行客服。這個事件可能同時涉及哪些釣魚概念？為什麼？

第 2 題｜技術原理

為什麼真正的平台產生的 OTP，仍可能協助攻擊者完成登入？為什麼這不代表 MFA 完全沒有用？

第 3 題｜事件處置

員工確實說出 OTP，但目前只有通話紀錄，尚無登入與存取日誌。你可以確認哪些事？不能確認哪些事？第一步應如何處理？

請先用自己的話回答三題，再逐題對照參考解答。參考解答是教學資料，不是學習者已提交的答案或已確認的理解紀錄。

最後把 M09-03 收斂成一個完整思考模式：

先確認對方透過什麼管道接觸你、聲稱具有什麼身分、要求取得什麼權限；接著離開可疑來源獨立查證；如果已經發生危險操作，就先控制風險，再以證據判定實際影響。

這套方法不只適用於假客服電話，也適用於假檢警、冒充主管、帳號復原詐騙，以及未來遇到的 AI 語音冒充攻擊。
