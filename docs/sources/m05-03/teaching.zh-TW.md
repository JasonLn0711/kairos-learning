**CEH M05-03｜弱點分類與評估類型**

同樣是「系統不安全」，原因不同，檢查和修正方法也不同。上一課決定可以檢查誰；這課回答：**要檢查哪種問題，從什麼角度才看得到？**

**一、先用餐廳理解分類**

餐廳食材變質，可能是冰箱故障、溫度設定錯誤，或員工忘了把食材放進冰箱。結果相似，原因卻不同。換冰箱不能解決工作流程；重新訓練員工也不能修好壞掉的壓縮機。

資訊系統也是一樣：看到弱點後，還要了解原因，才能找到適合的修正方法。

**二、弱點從哪裡來？**

Vulnerability（弱點）是可能被利用、使安全目標受損的缺陷。以下是方便理解的分類，不是全世界唯一的分類法：

- **設計缺陷**：一開始的規則漏了重要事項。例如訂單系統沒規劃每筆訂單的存取權限。修正方向是補足設計和權限規則。
- **實作缺陷**：規則合理，但程式沒有正確完成。例如某個介面漏掉訂單擁有者檢查。需要修程式並補測試。
- **設定錯誤**：功能具備，設定卻不符合需求。例如原本限內部讀取的儲存空間被設為公開。需要修正權限和設定。
- **已知缺陷尚未修補**：廠商提供修正，系統仍符合受影響條件。應核對適用性後更新、驗證。
- **管理與流程缺口**：維護、覆核或責任安排不足，例如人員離職後帳號未撤銷。需要改善流程、明確責任和稽核。

分類可能重疊。未修補既可能是軟體缺陷，也可能反映修補流程失效。分類是為了找到原因與負責人，不必硬塞進唯一格子。[OWASP 的弱點說明](https://community.owasp.org/vulnerabilities/)也顯示弱點不只是舊版本。

**三、在哪裡檢查，是另一種分類**

Assessment type（評估類型）描述檢查對象或方法，回答的問題與弱點成因不同。

- **Host-based，主機層級**：檢查單台系統的套件、更新、設定與權限。
- **Network-based，網路層級**：從網路連線角度檢查可見服務與暴露情形。
- **Application assessment，應用程式評估**：檢查登入、授權、資料處理和業務規則。
- **Database assessment，資料庫評估**：關心設定、帳號權限與資料存取。
- 無線與雲端環境也有各自的設定及責任邊界，不能只做主機檢查就當成全都完成。

例如「儲存空間權限設錯」是問題類型；「雲端設定評估」是可能找到它的方法。

**四、內部與外部：你站在哪裡看？**

External assessment（外部評估）從組織外部可到達的位置觀察；Internal assessment（內部評估）從獲准的內部位置觀察。兩個角度看到的暴露面可能不同。

像站在人行道可以看大樓門口，進到辦公室後才能觀察內部房間的隔離。外部沒看到資料庫連接埠，只能說這次外部視角沒觀察到，不能直接說資料庫不存在或內部權限正確。內部可連線，也不自動代表可以讀取資料。

內外指觀察位置，不是測試人員受雇於哪家公司。獲授權的外包顧問也可以做內部評估。[NIST SP 800-115](https://csrc.nist.gov/pubs/sp/800/115/final)

**五、主動與被動：怎麼取得證據？**

Active（主動式）會發送測試或探測請求、觀察回應；Passive（被動式）觀察已有訊息或流量，不靠主動探測取得回應。

主動式可能更直接回答問題，也可能增加目標負載；被動式受觀察位置和時間限制，沒出現的流量可能看不到。**被動不代表不需要授權，也不代表沒有隱私風險。**

另外兩組標籤：
- **Authenticated／Unauthenticated，具身分驗證／未具身分驗證**：是否使用獲准帳號取得檢查資訊。這不是內部／外部的同義詞。
- **Automated／Manual，自動化／人工**：由工具執行重複檢查，或由人分析與驗證。實務通常搭配使用。

同一場評估可以同時是「內部、具身分驗證、自動化的主機檢查」。這些是不同維度，不互相排斥。

**六、案例：為什麼一份工具報告不夠？**

以下都是合成情境：

- **發現 A**：工具從回應推測套件版本偏舊。這只是可能受影響的線索，還要核對實際套件、修補和成立條件，不能立刻寫「已可入侵」。
- **發現 B**：管理員提供設定證據，顯示測試資料夾允許匿名讀取。這支持該設定存在，但仍需確認預期政策與內容敏感程度，才能判斷影響。
- **發現 C**：在隔離環境用兩個獲准的合成帳號測試，發現 A 帳號能取得 B 的假訂單。若政策不允許跨帳號存取，就有具體授權檢查缺口的證據。

A 需要套件與公告核對，B 需要設定和政策比對，C 需要應用程式邏輯檢查。只做版本掃描，可能回答不了 B 和 C。

**七、分類不等於已排好優先順序**

Severity（嚴重程度）描述問題可能有多嚴重；Priority（處理優先順序）還要考慮實際暴露、資料價值、現有防護與修正條件。「設定錯誤」不一定小；「軟體漏洞」也不一定是最急的一項。

修正證據要對得上問題：更新後核對版本；改權限後檢查政策和存取結果；修邏輯後補上應允許與應拒絕的測試。不要把「掃描有發現」寫成「已遭入侵」。

**五分鐘紙上練習**

把案例 A、B、C 各寫一列，分別填上「已觀察什麼」「可能是哪類問題」「還缺什麼證據」，再選一種適合的評估方式並說明原因。不必安裝工具或掃描系統。

**小檢核**

工具沒有找到已知版本漏洞，但測試帳號仍能看到另一個測試帳號的訂單。這比較需要補哪種評估？為什麼不能因「版本掃描沒發現」就宣布安全？

這課的核心是分開說清楚：**問題是什麼、從哪個角度檢查、目前證據能證明什麼。**
