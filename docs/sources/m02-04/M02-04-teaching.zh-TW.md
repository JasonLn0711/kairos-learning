# M02-04｜DNS、WHOIS / RDAP Footprinting：查得到地址，不等於知道屋主

## 1｜結論先行：把「服務怎麼找到」與「網域怎麼登記」分開

今天只學一個完整概念：用 DNS 與網域註冊資料建立可查證的外部輪廓，而不是看到一個 IP 就認定找到公司的主機或擁有人。

DNS（Domain Name System，網域名稱系統）像電話簿加分層問路系統，回答「這個名稱有哪些服務紀錄」。WHOIS（傳統註冊資料查詢協定）與 RDAP（Registration Data Access Protocol，註冊資料存取協定）則比較像查登記資料，回答「這個網域在註冊體系中留下哪些資料」。Footprinting（足跡蒐集）是把這些線索整理成範圍清楚、附時間與來源的輪廓。

生活上，一間咖啡店的外送聯絡電話、代收郵件地址、店面租約登記人可能各不相同。網域也一樣：網站、信箱、DNS 託管商、註冊商和實際營運者可以是不同角色。真正要學會的是「每個欄位回答哪個問題，以及不能回答什麼」。

## 2｜DNS 查詢的旅程：誰幫你問，誰有權回答？

假設你要開啟合成案例的 www.coffee.example。你的裝置通常先問遞迴解析器（Recursive Resolver）：一個替你找答案、也可能保存先前答案的服務。若快取已有可使用的答案，它就回覆，不必每次從頭找。

若需要查找，解析器可沿 DNS 階層取得指引：根名稱伺服器知道頂層網域的委派資訊；頂層網域（Top-Level Domain，TLD）伺服器再指向相關網域的權威名稱伺服器（Authoritative Name Server）。權威伺服器提供它負責區域的紀錄。這是角色示意，不代表每次查詢都會走完整條路。

「遞迴」是幫你完成查找；「權威」是對自己管理的區域提供正式資料。DNS 區域（Zone）是一段由特定權威伺服器管理的名稱空間，與口語中的整個網域不一定完全重合，子網域可以另外委派。以上角色與委派結構可參考 [RFC 1034](https://www.rfc-editor.org/rfc/rfc1034)。

快取（Cache）像抄下來暫時使用的電話簿。TTL（Time to Live，存活時間）告訴快取一筆紀錄可以保留多久；它不是「修改後全世界一定在這個時間內更新」的保證。觀察到的 TTL 也可能是剩餘時間。不同解析器、查詢時間或網路位置，可能看到不同結果。

## 3｜讀懂紀錄：每種欄位都只回答自己的問題

資源紀錄（Resource Record）是 DNS 中的資料單位。不要把所有紀錄都解讀成「這是公司的伺服器」。

| 類型 | 白話用途 | 合理線索與限制 |
| --- | --- | --- |
| A | 名稱對應 IPv4 位址 | 可能是共用主機或代理服務，不一定是原始主機 |
| AAAA | 名稱對應 IPv6 位址 | 與 A 分開查；沒有 A 不代表沒有服務 |
| CNAME | 這個名稱是另一個名稱的別名 | 可看出服務依賴，但不能直接斷言最終主機歸屬 |
| MX | 郵件應送往哪些郵件交換主機 | 是收信路由線索，不代表每封信的寄件來源 |
| NS | 這個區域由哪些名稱伺服器服務 | 常反映 DNS 託管，不等於網域擁有人 |
| SOA | 區域管理的起始資訊與計時參數 | 序號協助區域版本管理，不保證是日期格式 |
| TXT | 文字資料，可供驗證或政策使用 | 要依內容與相應規格解讀，不是看到文字就當秘密 |
| PTR | 常用於反向查詢，由位址找名稱 | 不是法律上的所有權證明，也不保證與正向查詢一一對應 |

MX 的偏好值較小者優先嘗試，不是較大者更重要。TXT 可能放 SPF（Sender Policy Framework，寄信來源政策）、網域驗證字串等；這些用途不同，不能混為「所有 TXT 都是郵件設定」。DNS 的基本紀錄格式及多數上述類型見 [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035)；IPv6 的 AAAA 紀錄見 [RFC 3596](https://www.rfc-editor.org/rfc/rfc3596)。

## 4｜WHOIS 與 RDAP：註冊商不是註冊人

註冊人（Registrant）是網域註冊關係中的持有人角色；註冊商（Registrar）提供網域註冊服務；註冊管理機構（Registry）管理某個頂層網域的登錄資料。這三者不是同一件事。即使某平台同時提供多種服務，仍要按欄位角色判讀。

傳統 WHOIS 使用 TCP（Transmission Control Protocol，傳輸控制協定）的 43 埠；埠可想成服務的收件窗口。回覆常是文字，格式及可取得的欄位會因服務而異；協定本身沒有內建強固的存取控制或資料保密機制。[RFC 3912](https://www.rfc-editor.org/rfc/rfc3912)

RDAP 的安全規範要求支援 HTTPS，也就是以加密連線傳送 HTTP（Hypertext Transfer Protocol，超文字傳輸協定，網頁傳輸常用規則）資料；但連線安全仍不代表每個登記欄位都能證實網站實際營運者。[RFC 7481](https://www.rfc-editor.org/rfc/rfc7481)

RDAP 使用標準化查詢與結構化回應，讓人和程式較容易辨識欄位；JSON（JavaScript Object Notation，資料交換格式）就是把欄位名稱和值組織起來的方式，不是網頁畫面本身。RDAP 回應可包含名稱、狀態、事件、實體及其角色、名稱伺服器、說明與連結，應連同角色和事件類型一起讀。[RFC 9083](https://www.rfc-editor.org/rfc/rfc9083)

例如「某日期」要先看它是註冊、更新還是到期事件；更新日期不等於網站改版日，註冊日期不等於公司成立日。顯示某註冊商，也不等於網站由該註冊商營運。資料因隱私保護而遮蔽或缺省時，結論是「公開資料不足」，不是「沒有持有人」或「一定可疑」。

截至本課查核，ICANN 說明 RDAP 已成為註冊資料的主要替代協定；自 2025 年 1 月 28 日起，一般頂層網域的註冊管理機構與註冊商通常不再被要求提供 WHOIS，但頁面列有 .com、.name、.post 例外。這不是所有 WHOIS 已消失，也不能直接套用到所有國家或地區頂層網域。[ICANN RDAP 說明](https://www.icann.org/rdap)

## 5｜把線索串起來：一間合成咖啡店的外部輪廓

以下全是教材自編資料，不是實際查詢結果；.example 與文件用 IP 只為說明，不用來測試第三方。

| 自編觀察 | 可以記錄的事實 | 還不能下的結論 |
| --- | --- | --- |
| www.coffee.example 的 CNAME 指向 edge.vendor.example | 這個網站名稱使用了另一名稱作為別名 | 網站原始主機就在該服務商，或整個服務商都在測試授權內 |
| 別名後續的 A 回覆為 192.0.2.10 | 此次解析取得這個 IPv4 位址 | 該 IP 專屬咖啡店、就是內網或存在漏洞 |
| coffee.example 的 MX 為 10 mail.vendor.example | 收信路由指向這個郵件主機 | 郵件帳號清單、寄信者身分或密碼已被掌握 |
| RDAP 的 registrar 角色為範例註冊商 | 登記資料標示此註冊商角色 | 範例註冊商就是店主 |
| 另一時間查詢得到不同 IP | 兩次結果不同，需保留各自時間與查詢條件 | 一定遭到入侵 |

內容傳遞網路（Content Delivery Network，CDN）或反向代理（Reverse Proxy，替後端接收請求的前端服務）可能讓你只看見對外入口，而看不見原始主機。多個網站共用一個入口 IP 很常見；共用 IP 不代表同一家公司。這裡的安全做法是把關係寫成「觀察到依賴或對應」，而非「已證實資產歸屬」。

## 6｜查不到、查不同，以及被動／主動的界線

NXDOMAIN 表示回覆中指出所問名稱不存在；沒有某一種紀錄，不一定是名稱不存在。逾時則是沒有及時收到答案，可能與網路、伺服器、限制或設定有關，不能寫成「不存在」。務必保留回應狀態、查詢名稱和類型，而不是只抄一個空白結果。DNS 負面回覆也可能被快取。[RFC 2308](https://www.rfc-editor.org/rfc/rfc2308)

結果不同，可能是快取、變更時點、地理或負載導向、不同 DNS 視圖。Split DNS（分割視圖 DNS）讓內外部網路看到不同答案，因此外部沒看到某主機，不能推論內部沒有。也不能憑兩次結果不同就宣告 DNS 被竄改。

查第三方已保存的歷史 DNS 資料，和直接向解析器或權威伺服器查詢，不是同一種互動。一般 DNS 查詢仍會產生網路流量；你問遞迴解析器，也可能間接觸發它去問權威伺服器。是否列為被動蒐集，要按課程定義與書面測試規則判斷，不能拿「DNS 是公開的」當作不限量或不限對象的授權。

本單元重點是少量、範圍明確的紀錄判讀。先前 M04 的 DNS Enumeration（DNS 列舉）內容可用來快速複習：蒐集單筆線索，不等於已列出所有名稱；大量猜名稱、測試區域傳送或進一步探測，都要另外確認授權與規則，不在本課執行。

## 7｜防護與證據：看得見，不等於可任意存取

DNS 本來就需要對外公布部分服務線索。防護目標不是把一切藏起來，而是讓公開資料恰當、管理權安全、服務本身有存取控制。

可落實的作法包括定期盤點公開紀錄，移除不再使用的紀錄與服務依賴，避免把內部命名或敏感資料放入公開區域，保護註冊商與 DNS 管理帳號，啟用適當的多因素驗證與異動監控。若 CNAME 指向已停用的外部服務，先核實服務實際狀態與可接管條件，再處理紀錄，不能僅靠名稱就宣布可接管。

DNSSEC（Domain Name System Security Extensions，DNS 安全擴充）讓驗證端檢查 DNS 資料來源真實性及完整性。它不會把 DNS 內容加密，也不保證網站內容安全、服務不中斷或網域營運者可信；這幾種安全問題必須分開處理。[RFC 4033](https://www.rfc-editor.org/rfc/rfc4033)

| 證據欄位 | 要留下什麼 |
| --- | --- |
| 範圍與來源 | 被授權的名稱、查詢服務或資料庫、直接查詢或歷史資料 |
| 時間與條件 | 日期、時區、解析器、網路視角、查詢名稱與紀錄類型 |
| 原始結果 | 回應狀態、紀錄值、TTL；只保留必要資料 |
| 判讀 | 觀察到的事實、可能解釋、尚未證實的歸屬 |
| 防護核驗 | 經授權的變更前後比較、管理紀錄及仍待確認之處 |

例如「已移除舊 CNAME」要以設定變更與適當查核支持；剛改完後某個快取仍看到舊值，先檢查時間、TTL 與查詢來源，不直接判定變更失敗。

## 8｜小檢核：一個情境，四個判讀

在授權的合成練習中，你看到：www.coffee.example 指向某 CDN 名稱；A 回覆 192.0.2.10；RDAP 只有註冊商資料，持有人欄位未公開；另一位同事的 DNS 查詢逾時。

請試著用自己的話回答：① 可以把 192.0.2.10 當成咖啡店專屬原始主機嗎？② 註冊商能直接當成網站擁有人嗎？③ 逾時能當成名稱不存在嗎？④ 若想讓報告可重查，你最少要補哪些查詢條件？

這是理解檢核，不需要實際操作第三方目標。未作答只代表尚未取得理解證據，不會因此標記已學會。

## 9｜今天帶走的觀念與來源

一句話收束：DNS 告訴你「名稱如何連到服務」，WHOIS／RDAP 告訴你「註冊資料如何描述角色」；兩者都需要來源、時間與限制，才能變成可靠的資產線索。
