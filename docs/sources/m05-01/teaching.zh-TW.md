# CEH M05-01｜弱點評估與滲透測試：發現問題後，還要證明什麼？

今天進入 M05「弱點分析」。先抓住一句話：弱點評估幫你整理哪些地方可能有安全問題、應該怎麼處理；滲透測試在明確授權範圍內，進一步驗證攻擊路徑與實際影響。兩者互補，不能只用「有沒有跑工具」區分。

## 一、先從住家檢查理解

想像你請專業人員檢查住家安全。對方逐項查看門窗、鎖具、出入口與警報設備，記錄哪裡有缺失、證據是什麼、建議先修哪裡。這很像弱點評估。

如果你再明確授權他，只在指定時間和方法下試著證明某扇門能否被繞過，且不能破壞物品或碰私人物品，這比較接近滲透測試。

兩者都需要許可。發現窗戶有問題，不代表獲准翻進去；即使獲准驗證，也要遵守停止條件。

## 二、六個名詞，串成一個故事

- Asset（資產）：想保護、有價值的東西，例如訂單資料、帳號、網站服務，以及服務不中斷的能力。
- Vulnerability（弱點或漏洞）：可能被利用而影響安全的缺陷，例如權限設定錯誤，讓一般會員能讀到其他人的訂單。弱點可能來自程式、設定或作業流程。
- Threat（威脅）：可能造成傷害的來源或情境，例如外部攻擊者嘗試取得訂單資料。
- Exploit（漏洞利用方法或程式）：把特定弱點轉成實際效果的方法。找到利用程式，還要核對是否適用於目前環境。
- Attack（攻擊）：實際嘗試破壞、繞過或濫用安全機制的行為。弱點存在不代表已遭攻擊；有人攻擊也不代表成功。
- Risk（風險）：在目前環境中，威脅造成損害的可能性與影響。相同缺陷出現在公開訂單系統或隔離練習機，處理急迫性可能不同。

串起來看：訂單是資產；越權讀取是弱點；有人企圖偷看資料是威脅情境；利用缺陷的做法是 exploit；實際嘗試是攻擊；發生可能性和損害則是風險判斷的重點。

## 三、弱點評估在做什麼？

Vulnerability Assessment（弱點評估，簡稱 VA）是有系統地檢查安全缺失、整理證據，並協助決定改善方向。可以包含工具掃描、人工檢查、設定與文件檢閱，以及授權範圍內的結果驗證。

Vulnerability Scanning（弱點掃描）只是取得線索的一種方法。掃描器可能根據版本、設定或回應產生警告；評估者還要核對它是否適用、證據夠不夠、對業務有何影響。

例如掃描器指出某服務版本疑似有弱點，接著要問：產品辨識正確嗎？版本資訊可靠嗎？必要功能是否啟用？是否已修補？在什麼網路與權限條件下能接觸？

可用的評估結果應交代問題、證據、範圍、優先順序及下一步，不只是給管理者一大包紅色警告。[NIST 弱點評估定義](https://csrc.nist.gov/glossary/term/vulnerability_assessment)也涵蓋檢查安全措施和改善後的確認。

## 四、滲透測試在做什麼？

Penetration Testing（滲透測試，簡稱 PT）是在指定限制下模擬攻擊者做法，驗證安全機制能否被繞過，以及可能造成什麼影響。

它常關注「條件串起來，能做到什麼」。例如公開入口洩漏資訊，加上權限缺陷，是否讓測試帳號接觸不屬於它的測試資料？[NIST 的定義](https://csrc.nist.gov/glossary/term/penetration_testing)也說明受限測試、模擬攻擊及組合弱點的觀點。

成功不等於拿走所有真實資料或破壞系統。可事先約定用一筆合成資料或指定標記取得最小必要證據，足夠後就停止。

Rules of Engagement（交戰規則，簡稱 ROE）是事先講清楚哪些系統、帳號、時段和方法可以測，哪些不能碰，何時停止、通知誰，以及測試資料如何清除。網站公開可見，不等於授權測試。

## 五、怎麼區分與選擇？

- 主要目的：VA 偏向系統性找出與評估缺失；PT 偏向驗證可利用路徑與影響。
- 常見產出：VA 提供缺失、適用性證據及改善排序；PT 提供測試條件、驗證過程、達成效果、限制和改善建議。
- 如何選擇：想了解一批資產的問題分布，可安排 VA；想驗證某個攻擊情境、防護機制或關鍵系統的抵抗能力，可安排範圍明確的 PT。

這是目的上的比較，不是硬性二分。VA 也可能人工驗證，PT 也會使用掃描器；實際工作以委託目的與授權範圍為準。

## 六、案例：版本警告如何變成可信結論？

以下是匿名合成案例，不是真實系統測試結果。某公司的隔離練習網站回傳「服務版本 2.4」，工具因而列出高嚴重度警告。

1. 分開觀察與推論：觀察是「回應顯示版本字串 2.4」；推論是「可能符合弱點條件」。目前還不能說已可成功利用，更不能寫成已外洩資料。
2. 核對適用條件：查實際套件、廠商公告、修補狀態、功能設定與存取限制。版本字串未必反映全部修補狀態。
3. 決定工作範圍：若要整理待修清單，就記錄已確認及待確認條件；若需要證明特定路徑影響，須依明確 PT 授權，在隔離環境使用合成資料驗證。
4. 寫清楚證據邊界：測試帳號若成功讀到一筆不該讀的合成訂單，只能支持本次條件下這條路徑發生越權，不能直接推論所有訂單均可取得，也不能證明過去遭入侵。
5. 改善後複測：修改權限或程式，以相同角色和條件再檢查。確認不該讀取的請求被拒，同時合法使用者仍能正常使用。

學習時可以記成：發現線索 → 核對條件 → 授權內驗證 → 說明影響與限制 → 改善後複測。這是本課整理的流程，不是宣稱官方固定五階段。

## 七、防護端要保留什麼證據？

至少記錄測試資產、時間、角色及條件、實際觀察、尚未確認事項和建議。修正後補上變更紀錄、複測條件、預期與實際結果。敏感資料應最小化或遮蔽，不為報告保留不必要的密碼、金鑰或完整個資。

兩個限制要記住：

- 沒掃到不代表不存在。範圍、權限、工具規則與可達性都會影響結果。
- 測試沒成功不代表永遠安全。結論只涵蓋這次的時間、方法及條件；未測不等於通過。

[NIST SP 800-115](https://csrc.nist.gov/pubs/sp/800/115/final) 是 2008 年發布的技術測試與評估指南；這裡採用規劃、證據、限制及改善的基本觀點，不把它當成最新工具操作說明。

## 小檢核

掃描報告因版本字串列出高嚴重度弱點。你還沒核對修補狀態，也沒有進一步測試授權。下一步哪個最合理？

- A. 直接在正式網站執行利用程式，確認影響。
- B. 把報告寫成「已遭入侵」。
- C. 核對產品、修補與必要條件，區分已觀察與待確認；需要進一步驗證時先確認授權範圍。
- D. 因為沒看到資料外洩，所以刪除警告。
