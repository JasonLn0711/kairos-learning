## **二、L01–L04：先弄清楚加密、金鑰與雜湊**

### **L01｜機密性、完整性、可用性：CIA Triad**

這三個概念是資訊安全的基本分類。

**機密性（Confidentiality）**：不讓未經授權的人讀懂資訊。

例如晶片設計檔被駭客複製，但檔案經過適當加密，駭客沒有金鑰，便難以還原原始內容。

**完整性（Integrity）**：確保資料未遭未授權修改，或能偵測修改。

例如設計圖中的電路參數被偷偷改掉。如果系統能透過可信的雜湊值或數位簽章發現異動，就能辨識資料可能遭到竄改。

**可用性（Availability）**：合法使用者需要資料或系統時，能取得並使用。

例如硬碟經 AES-256 加密，但硬碟損毀且沒有備份。資料可能依然保密，卻已經無法使用。

博士班需要再理解一個層次：

**密碼學的安全性質，不等於整個資訊系統的安全性質。**

加密演算法沒有被破解，不代表攻擊者無法透過已登入的使用者帳號取得明文。保護靜態資料，也不等於保護正在執行的應用程式。

這是「演算法安全」與「系統安全」的第一個重要區別。

### **L02｜明文、密文、演算法、金鑰：各自扮演什麼角色？**

用一個簡單的數學式表示：

\\[ C=\operatorname{Enc}(K,M) \\]

\\[ M=\operatorname{Dec}(K,C) \\]

其中：

- \\(M\\)：Message，明文。
- \\(K\\)：Key，金鑰。
- \\(C\\)：Ciphertext，密文。
- Enc：加密運算；Dec：解密運算。

假設某公司的設計文件是明文 \\(M\\)，系統利用 AES 和金鑰 \\(K\\) 產生密文 \\(C\\)。

不知道 \\(K\\) 的人，即使知道系統採用 AES，也不應因此就能有效解密。

這裡還有一個重要原則：**安全性不應建立在攻擊者不知道演算法的假設上。**

這和 Kerckhoffs's Principle（柯克霍夫原則）一致。演算法可以公開接受安全分析，真正必須安全管理的是秘密資訊，特別是金鑰。

但是，即使金鑰沒有被直接偷走，攻擊者仍可能透過受控程式、記憶體、使用者工作階段等途徑取得明文。

因此，系統設計者不能只問「使用什麼加密演算法」，還要問「金鑰在哪裡、誰能使用、資料在哪個階段會解密」。

### **L03｜對稱式與非對稱式加密：差別在金鑰**

這是本份 CEH 題目中最重要的分類觀念之一。

**對稱式加密**

Symmetric Encryption

加密與解密使用相同的秘密金鑰，或容易互相推導的秘密金鑰。

代表：AES、Blowfish、Twofish、DES

**非對稱式加密**

Asymmetric Encryption

使用具有特定數學關係的公鑰與私鑰，不同方案指定不同金鑰角色。

代表：RSA

示意圖：非對稱式圖解以公開金鑰加密、私密金鑰解密為例；數位簽章則採另一套運算流程。

#### **為什麼需要非對稱式密碼學？**

假設臺灣公司與美國合作廠商需要共享一把 AES 金鑰。

使用對稱式加密的前提，是雙方已經有共同秘密。問題是：**雙方一開始要怎麼安全取得這把共同金鑰？**

如果直接透過不安全的通訊管道傳送，攻擊者就可能攔截。

公開金鑰密碼學可以支援金鑰建立與分配：

1. 一方擁有公鑰及私鑰。
2. 對方取得並確認公鑰。
3. 雙方利用適當的公開金鑰機制建立共享金鑰材料。
4. 再利用對稱式加密保護大量資料。

不一定是直接把一把 AES 金鑰用 RSA 加密送出去；Diffie–Hellman 類機制可以透過金鑰協議建立共享秘密。

這種將不同密碼學技術搭配使用的概念，是理解現代安全通訊的基礎。

\*\*關鍵限制：\*\*如果取得的是攻擊者假冒的公鑰，即使數學運算完全正確，仍可能把秘密交給錯誤的人。因此公鑰認證是必要的一環。

### **L04｜Hash、Encoding、Encryption：三種技術不可以混用**

想像你收到一份重要檔案：

\*\*Encoding（編碼）\*\*就像把中文翻譯成摩斯密碼，目的是方便表示或傳輸。知道規則便能解碼，例如 Base64。

\*\*Encryption（加密）\*\*就像把文件放進需要正確鑰匙才能開啟的保險箱。設計目的是只有具備必要秘密資訊的人能還原。

\*\*Hashing（雜湊）\*\*比較像計算文件的數位指紋。你可以利用指紋比對文件是否改變，但不會從指紋還原完整文件。

數學上可以寫成：

\\[ h=H(M) \\]

其中 \\(H\\) 是雜湊函數，\\(M\\) 是輸入資料，\\(h\\) 是摘要。

一份 1 KB 的文件與一份 1 GB 的文件，如果使用 SHA-256，輸出摘要長度都是 256 bits。

這裡要特別區分：

- **Preimage Resistance**：給你摘要，難以找出對應原始輸入。
- **Second-preimage Resistance**：給你一份原始資料，難以找出另一份具有相同摘要的資料。
- **Collision Resistance**：難以找到任意兩份不同資料，卻具有相同摘要。

這三個性質不同，不是單純說「Hash 無法逆轉」就能完整描述。

#### **Hash 可以確保資料完整性嗎？**

要看情況。

假設工程師下載韌體，同時取得檔案與 SHA-256：

- 攻擊者只能修改韌體，無法修改可信摘要：比對有助於發現竄改。
- 攻擊者能同時替換韌體與網站上的摘要：兩者仍可能相符。

因此，**單純 Hash 能支援變更偵測，但不會自動提供可信的來源認證。**

需要認證時，可以進一步使用 HMAC 或數位簽章等機制。

這也是 NIST FIPS 180-4 對雜湊摘要用途的基本定位。

## **三、L05–L08：區塊密碼、演算法辨識與磁碟加密**

### **L05｜Block Size 與 Key Size：區塊長度和金鑰長度完全不同**

CEH 很喜歡考這個差異。

想像你有一台機器，要把大量文件處理成加密資料。

\*\*Block Size（區塊長度）\*\*是機器每次處理的固定大小資料單位。

\*\*Key Size（金鑰長度）\*\*則是控制加密轉換的秘密金鑰大小。

兩者不是同一個概念。

AES-256 的兩個重要參數

Block Size

# **128 bits**

每個基本資料區塊

Key Size

# **256 bits**

秘密金鑰長度

AES-128、AES-192、AES-256 的區塊長度都相同，差別在金鑰長度與加密輪數。

依 NIST FIPS 197，AES 的區塊固定為 128 bits，支援 128、192、256-bit 金鑰。2023 年更新並未改變 AES 的核心演算法。

[image](https://www.google.com/s2/favicons?domain=https://csrc.nist.gov\&sz=32)

NIST Computer Security Resource Center+1



#### **為什麼不只看金鑰長度？**

假設兩套系統都使用 256-bit 金鑰，是否一定同樣安全？

不一定。

因為實際安全還取決於演算法、區塊長度、運作模式、金鑰產生與管理，以及程式實作。

尤其是具有較短區塊長度的舊式演算法，處理大量資料時，還需要注意區塊重複與相關安全界限。

這是為什麼不能看見某個演算法支援很長的金鑰，就直接認定它比 AES 更安全。

### **L06｜Blowfish、Twofish、AES、RC4：怎麼快速辨識？**

這組是本份最適合用表格記憶的內容。

| 演算法      | 類型   | 區塊長度      | 金鑰長度             | 考題辨識          |
| -------- | ---- | --------- | ---------------- | ------------- |
| Blowfish | 對稱區塊 | 64 bits   | 32–448 bits      | 64、448        |
| Twofish  | 對稱區塊 | 128 bits  | 最高 256 bits      | AES 決選者       |
| AES      | 對稱區塊 | 128 bits  | 128／192／256 bits | Rijndael      |
| RC4      | 對稱串流 | 不適用固定區塊長度 | 可變               | Stream Cipher |

來源：Blowfish、Twofish 設計者文件及 NIST FIPS 197。

[image](https://www.google.com/s2/favicons?domain=https://www.schneier.com\&sz=32)

Schneier on Security+2



記憶方式：

**Blowfish 與 Twofish 是兩個不同的演算法，不是同一演算法的兩個版本。**

Blowfish 最容易辨認的數字是 64-bit 區塊與最高 448-bit 金鑰。

Twofish 則具有 128-bit 區塊、最高 256-bit 金鑰，而且參加過 AES 決選。

RC4 特別注意：它是串流密碼，不是固定區塊密碼。歷史考題會考，但不代表現代系統應採用 RC4。

### **L07｜AES 與 Twofish：為什麼這是博士班需要注意的題幹歧義？**

本份的 EC-Q493 與 P1-Q114 有一個重要問題。

兩題都提及：

但是，這些資訊並不能完全唯一識別演算法。

為什麼？

因為 NIST 的 AES 遴選有五個決選者：

這段歷史由 NIST 的 AES Development 紀錄明確支持。

## **四、L09–L12：數位簽章、非對稱演算法與 PKI**

這四個觀念是本份較需要深入理解的部分。

### **L09｜數位簽章到底在證明什麼？**

數位簽章（Digital Signature）不是把文件加密，目的是讓驗證者判斷：

「這份資料是否由持有指定私鑰的一方簽署，而且資料是否在簽署之後遭到修改？」

基本流程如下：

簽署端

原始資料 M

Hash(M)

使用私鑰簽署

簽章 Signature

驗證端

收到資料 M

驗證原始資料

使用公鑰驗證

有效／無效

概念示意。實際簽章運算依 RSA-PSS、DSA 等不同方案而異，不等於單純以私鑰加密雜湊值。

數位簽章通常支持三種安全目標：

**Integrity（完整性）**：偵測已簽署資料的變動。

**Authentication（來源認證）**：驗證簽章與特定簽署金鑰的關聯。

**Non-repudiation（不可否認性）**：提供可供第三方判斷簽署來源的證據。

但是，不可否認性不是數學演算法能無條件保證的法律事實。

例如公司董事的私鑰遭到竊取，駭客利用私鑰簽署交易，技術上簽章可能有效，但不能直接推出董事本人親手核准了交易。

NIST FIPS 186-5 對數位簽章的安全用途有明確說明。

### **L10｜RSA、DSA、Diffie–Hellman、ElGamal：如何分辨？**

這幾個名詞都是公開金鑰密碼學中常見的機制，但用途不完全相同。

| 演算法／機制         | 加密    | 數位簽章  | 金鑰建立  |
| -------------- | ----- | ----- | ----- |
| RSA            | 有對應方案 | 有對應方案 | 有特定方案 |
| DSA            | 不支援   | 支援    | 非其用途  |
| Diffie–Hellman | 不直接提供 | 不提供   | 主要用途  |
| ElGamal 家族     | 有加密方案 | 有簽章方案 | 依具體構造 |

最簡單的記憶法：

RSA 是可以支援多種用途的公開金鑰演算法家族；DSA 主要處理簽章；Diffie–Hellman 主要處理金鑰協議。

#### **RSA 為什麼不能只記「公鑰加密、私鑰解密」？**

因為 RSA 有不同的實際方案。

例如：

- RSAES-OAEP：用於公開金鑰加密。
- RSASSA-PSS：用於數位簽章。

兩者使用 RSA 的數學基礎，但具有不同目的與編碼規則，不能任意互換。技術規格可參考 RFC 8017 §7–9。

RFC Editor



另外，Diffie–Hellman 建立共享秘密的能力，不等於它會自動驗證通信對象的身分。

這個差異正是中間人攻擊（Man-in-the-Middle, MITM）可能利用的信任缺口。

### **L11｜DSA 每次簽章的秘密值：為什麼隨機數可能害私鑰外洩？**

這是本份最值得稍微理解數學原理的主題。

傳統 DSA 簽章會用到一個每次簽署專用的秘密值 \\(k\\)。

你可以把它理解為：除了長期私鑰，簽章時還使用一個暫時性的秘密參數。

若這個秘密值遭到重複、不當預測或外洩，就可能危及長期私鑰。

為什麼？

DSA 的一部分簽章計算可以簡化表示為：

\\[ s=k^{-1}(H(m)+xr)\pmod q \\]

其中 \\(x\\) 是長期私鑰，\\(k\\) 是每次簽署所使用的秘密值，\\(r,s\\) 是簽章的兩個組成值。

如果攻擊者取得 \\(k\\)，便可能藉由重新排列等式推得私鑰 \\(x\\)：

\\[ x=(sk-H(m))r^{-1}\pmod q \\]

以上是理解風險所用的簡化數學表示；實際 DSA 另有雜湊值處理與參數限制。

因此，簽章系統的隨機數品質並不是無關緊要的小細節。

不過，還要區分「每次秘密值必須安全」和「每次都必須向外部隨機數產生器取得新的值」。

RFC 6979 允許使用決定性方式，從私鑰及訊息產生符合要求的簽章秘密值。

### **L12｜PKI 與 CA：公鑰為什麼需要身分認證？**

前面已經學到非對稱密碼學需要公鑰。

但現在有一個問題：

你收到一把公鑰，怎麼知道它真的是合作廠商的公鑰，而不是攻擊者給你的？

這就是 PKI（Public Key Infrastructure，公開金鑰基礎建設）要處理的核心問題之一。

CA（Certificate Authority，憑證機構）負責依照其程序簽發數位憑證，建立身分資訊與公鑰的可驗證連結。

**Root CA（信任錨）**

驗證系統預先信任的根

**Intermediate CA**

由上一層 CA 授權簽發

**Server Certificate**

將伺服器身分與公鑰連結

典型 X.509 憑證鏈示意，不代表所有 PKI 必須使用完全相同的階層。

當瀏覽器或其他驗證程式接收到伺服器憑證時，會根據憑證鏈與信任設定，檢查簽章、身分名稱、有效期間、憑證用途及相關限制；撤銷狀態也需要依情境處理。

這些原則可對應 RFC 5280 §6 的憑證路徑驗證。

[image](https://www.google.com/s2/favicons?domain=https://www.rfc-editor.org\&sz=32)

RFC Editor



關鍵觀念是：

**「公鑰可以驗證簽章」與「這把公鑰屬於你真正想要聯繫的人」是兩個不同問題。**

密碼學負責前者，可信身分與金鑰管理機制則協助處理後者。

## **五、博士班整合案例：把所有觀念組成一個真正的系統**

假設臺灣一家半導體公司正在開發跨國晶片設計協作平台。

平台需要傳送機密設計檔，保護資料不被修改，並讓合作方確認資料來源。

一個簡化的安全架構可以這樣設計：

**1. 確認合作方身分**

檢查 PKI 憑證、信任鏈及相關授權

**2. 建立加密金鑰**

利用經認證的金鑰建立協定協商共享秘密

**3. 保護傳輸資料**

使用合適的對稱加密與認證機制，例如 AES-GCM

**4. 驗證重要文件**

必要時另外使用數位簽章，確認文件簽署來源

**5. 安全儲存與復原**

加密靜態資料、管理金鑰、備份與權限

其中 AES-GCM 是認證加密（Authenticated Encryption）機制，可以在正確使用下同時支援資料機密性與完整性驗證，但必須遵守 nonce／IV 使用限制並驗證認證標籤。詳見 NIST SP 800-38D。

[image](https://www.google.com/s2/favicons?domain=https://csrc.nist.gov\&sz=32)

NIST Computer Security Resource Center



這個案例最重要的結論是：

**密碼學提供安全元件，安全工程負責把這些元件在正確的條件下組合成系統。**

即使所有演算法都正確，若金鑰被偷走、私鑰使用權限錯誤、公鑰身分沒有驗證，或主機本身遭到控制，系統仍可能失去安全性。
