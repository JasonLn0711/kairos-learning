# CEH M04-01｜掃描找到入口，列舉問出資訊
## Enumeration vs. Scanning｜逐章白話文完整教學

**課程：** CEH 2026 · Module 04 — Enumeration（列舉）  
**教材：** [CS Kairos Learn — M04-01](https://learn.cs-kairos.com/courses/ceh/v13/m04/concepts/ceh26-m04-c01/?utm_source=chatgpt.com)  
**範圍：** 原網站第 1～10 節，以及概念 Q&A。

## 一、先掌握這堂課最重要的觀念

這堂課要教你的，其實就是一件事情：

> **發現電腦有開放某項網路服務，不代表你已經知道服務裡面有什麼，更不代表你有權限使用裡面的資源。**

我們可以把 M03、M04、M05 想像成調查一棟辦公大樓。

| 學習階段 | 白話文 | 技術上在做什麼 |
|---|---|---|
| M02 偵察 | 這棟大樓在哪裡？屬於哪家公司？ | Reconnaissance |
| M03 掃描 | 大樓有哪些入口？哪些門有人應答？ | Scanning |
| **M04 列舉** | 裡面有哪些部門、房間和資源？ | **Enumeration** |
| M05 弱點分析 | 有沒有不該開放的資訊或權限？ | Vulnerability Analysis |
| M06 系統入侵 | 在授權測試中，是否能實際證明弱點造成的影響？ | System Hacking |

這是一張概念地圖，不代表每次測試都必須依照這個順序執行。

例如，你在 M03 學會了使用 Nmap，發現：

```text
192.168.56.10

PORT      STATE    SERVICE
445/tcp   open     microsoft-ds
```

你知道 TCP 445 開放了。

但是，接下來你可能還想知道：

1. 這個入口是不是真的提供 SMB 檔案共用？
2. 這台伺服器有哪些共用資料夾？
3. 我能不能看到這些資料夾的名稱？
4. 我能不能讀取裡面的檔案？
5. 我能不能修改裡面的檔案？

這些問題的答案可能完全不同。

**M04 最重要的能力，就是學會向服務查詢資訊，並且正確理解查詢結果能夠證明什麼。**

# 第 1 節｜先想像：看見文件櫃，不等於能打開抽屜

## 1.1 用公司文件室來理解

假設你是公司的資安工程師。

公司委託你檢查一台檔案伺服器（File Server）。

伺服器就像一間文件室，裡面有好幾個文件櫃：

```text
                   公司檔案伺服器
                 192.168.56.10
                        │
              ┌─────────┴─────────┐
              │    SMB 檔案服務    │
              │     TCP 445       │
              └─────────┬─────────┘
                        │
          ┌─────────────┼─────────────┐
          │             │             │
     ┌────▼────┐   ┌────▼────┐   ┌────▼────┐
     │ Public  │   │ Finance │   │ Archive │
     │ 公開共用 │   │ 財務資料 │   │ 歷史資料 │
     └─────────┘   └─────────┘   └─────────┘
```

你可能會經歷以下情況。

**第一種：知道文件室在哪裡。**

你知道伺服器的 IP 是 `192.168.56.10`。

但你還不知道它提供什麼服務。

**第二種：發現文件室有一個入口。**

透過 Nmap，你發現 TCP 445 是開放的。

這表示有程式接受這個連接埠上的 TCP 連線。

但你還沒有證明裡面有任何資料夾。

**第三種：知道這個入口提供檔案共用服務。**

你透過協定辨識，確認它提供 SMB 服務。

這就像確認這棟建築物確實有文件室。

**第四種：知道文件櫃有哪些名稱。**

你查詢後得到：

```text
Public
Finance
Archive
```

這就是列舉（Enumeration）。

但注意！

你只是知道有三個共用資源的名稱。

你還不知道自己能不能讀取它們。

**第五種：實際讀取某個檔案。**

你使用公司提供的測試帳號，成功讀取：

```text
Public/demo.txt
```

這才證明你在當時的身分與測試條件下，可以讀取這份指定檔案。

它仍然不代表你可以讀取其他檔案，也不代表你可以修改任何資料。

### 1.2 這節真正要理解的觀念

請分清楚四種不同的能力：

| 能力 | 代表意義 | 是否證明下一項能力？ |
|---|---|---|
| 發現服務 | 知道入口有回應 | 否 |
| 列出資源名稱 | 知道有哪些共用資源 | 否 |
| 讀取指定檔案 | 已成功取得該檔案內容 | 否 |
| 修改指定檔案 | 已證明能對該檔案執行修改 | 不代表能修改其他檔案 |

你可以把這套觀念用在很多系統。

例如，你在 NAS 管理頁面上看見一個資料夾名稱，不代表你能進入。

你能進入資料夾，也不代表你能刪除檔案。

**資安測試必須區分「看得見」、「進得去」、「讀得到」和「改得動」。**

# 第 2 節｜掃描與列舉，問的是不同問題

## 2.1 先複習三個基礎概念

這一節會與 M03 的內容直接連接。

### IP Address：你要找哪台設備？

IP 位址就像設備在網路上的地址。

例如：

```text
192.168.56.10
```

我們透過 IP 定位要溝通的設備。

但知道 IP，不代表知道該設備提供什麼服務。

### Port：你要連哪個服務入口？

一台電腦可能同時提供多種網路服務。

例如：

| Port | 常見用途 |
|---|---|
| TCP 22 | SSH 遠端管理 |
| TCP 80 | HTTP 網站 |
| TCP 443 | HTTPS 網站 |
| TCP 445 | SMB 檔案共用 |
| TCP 3389 | RDP 遠端桌面 |

這些是常見的對應關係，不保證實際服務一定如此。

尤其要記住：

**Port 是傳輸層用來區分通訊端點的編號，而不是某項服務的身分證。**

例如，TCP 443 常見於 HTTPS，但不是說任何開放 TCP 443 的程式都一定是 HTTPS 伺服器。

### Protocol：雙方使用什麼規則溝通？

Protocol 就是通訊規則。

例如：

你走進銀行，不能直接對著櫃台說一串沒有意義的數字，就期待銀行完成轉帳。

你必須按照銀行規定的方式提出請求。

網路服務也是一樣。

如果你要向 SMB 伺服器查詢資源，就必須使用符合 SMB 協定的請求。

這也是為什麼：

- Nmap 可以協助確認服務入口的狀態。
- `smbclient` 可以向 SMB 伺服器提出具體查詢。

兩者並不是做同一件事。

## 2.2 Scanning 與 Enumeration 的差別

想像你是一位受公司授權的稽核人員。

### Scanning：確認服務入口

你詢問：

「這個門口有人嗎？」

伺服器回應：

「有。」

你得到的資訊是：

```text
TCP 445: open
```

### Enumeration：查詢服務提供的資訊

接著，你向服務詢問：

「目前有哪些共用資料夾？」

服務回應：

```text
Public
Finance
Archive
```

現在你不只知道入口開著，還取得了服務提供的具體資訊。

這就是列舉。

### 2.3 一個容易混淆的地方

是不是使用 Nmap 就叫 Scanning，使用其他工具才叫 Enumeration？

**不是。**

分類的重點在於：

> 你向目標提出什麼問題，以及取得了什麼證據。

例如，Nmap 除了掃描連接埠，也能使用服務偵測及腳本功能取得更詳細的資訊。

當工具開始向服務詢問具體資源或屬性時，這部分工作就具有列舉的性質。

因此，CEH 的章節是在幫助你理解資安工作的概念，不是規定每個工具只能用在哪個階段。

Nmap 官方文件也強調，掃描結果描述的是測試者當下觀察到的狀態，而不是對所有網路位置都永遠成立的結論。[nmap.org](https://nmap.org/book/man-port-scanning-basics.html?utm_source=chatgpt.com)

# 第 3 節｜第一個容易誤判的地方：445 open 到底證明什麼？

這節非常重要，因為它牽涉到資安人員如何正確解讀證據。

## 3.1 先看指令

在已授權的隔離練習環境中：

```bash
nmap -p 445 192.168.56.10
```

逐個拆解：

| 指令 | 意義 |
|---|---|
| `nmap` | 執行網路掃描工具 |
| `-p` | 指定要掃描的 Port |
| `445` | 這次檢查 TCP 445 |
| `192.168.56.10` | 目標設備的 IP |

假設結果如下：

```text
PORT      STATE    SERVICE
445/tcp   open     microsoft-ds
```

現在我們逐項解讀。

### 445/tcp

代表這次掃描的是：

```text
傳輸協定：TCP
Port：445
```

### open

代表 Nmap 根據此次探測得到的回應，判斷這個連接埠有程式在接受連線。

但不代表：

- 可以登入。
- 可以讀取檔案。
- 存在可利用漏洞。

### microsoft-ds

這是最容易讓初學者誤判的地方。

你可能會想：

「Nmap 已經告訴我 microsoft-ds，所以我已經確認這台電腦提供 SMB 服務了。」

其實沒有這麼簡單。

在這個沒有啟用服務版本偵測的基本掃描案例中，`microsoft-ds` 通常只是 Nmap 根據 Port 445 所顯示的常見服務名稱。

就像你看到一棟大樓的門牌寫著「圖書館」。

這是線索，但你還沒有實際確認裡面是否正在提供圖書館服務。

## 3.2 如何進一步確認？

Nmap 有一個參數：

```bash
-sV
```

它代表 Service Version Detection（服務與版本偵測）。

例如：

```bash
nmap -sV -p 445 192.168.56.10
```

它會嘗試向目標服務發送探測資料，並分析回應，以推測實際提供的服務及可能的版本。

但即使成功辨識 SMB，也不代表你有檔案讀取權限。[nmap.org](https://nmap.org/book/man-version-detection.html?utm_source=chatgpt.com)

## 3.3 SMB 是什麼？

SMB 的完整名稱是：

**Server Message Block**

它是一種網路資源共用協定。

最常見的用途是：

讓使用者透過網路，存取另一台電腦上的共用資料夾或檔案。

例如：

```text
你的 Windows 電腦
       │
       │ 使用 SMB 協定
       ▼
公司檔案伺服器
       │
       └── \\fileserver\Public
```

你在 Windows 檔案總管輸入：

```text
\\fileserver\Public
```

就可能透過 SMB 存取遠端共用資料夾。

Linux 也能使用 SMB，並非只有 Windows 可以。

另外，SMB 不一定只能透過 TCP 445 運作；現代 Windows 也支援其他 SMB 傳輸方式。[Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/storage/file-server/file-server-smb-overview?utm_source=chatgpt.com)

## 3.4 請看 SMB 的基本運作方式



最基本的模型是：

```text
┌───────────────────┐
│  SMB Client       │
│  你的電腦          │
└─────────┬─────────┘
          │
          │ SMB Request
          │ 請求列出共用資源
          ▼
┌───────────────────┐
│  SMB Server       │
│  公司檔案伺服器     │
│                   │
│  檢查相關身分      │
│  與存取權限        │
└─────────┬─────────┘
          │
          │ SMB Response
          │ 回傳允許揭露的資訊
          ▼
┌───────────────────┐
│  SMB Client       │
│                   │
│  Public           │
│  Finance          │
│  Archive          │
└───────────────────┘
```

要注意，這是教學用的簡化圖。實際 SMB 可能涉及協定協商、身分驗證、工作階段建立，以及不同資源的權限檢查。

**第 3 節的核心：Port 開放只是網路層面的觀察；要確認服務的具體功能，需要進一步取得協定層面的證據。**

# 第 4 節｜真正進入列舉：問服務「你有哪些共用資源？」

這一節開始接觸真正的 Enumeration。

## 4.1 認識 smbclient

`smbclient` 是 Samba 專案提供的 SMB 用戶端工具。

你可以想像它是一個能用終端機和 SMB 伺服器溝通的程式。

例如：

你平常在 Windows 裡使用檔案總管查看網路共用資料夾。

在 Linux 上，我們可以使用 `smbclient` 與 SMB 伺服器溝通。

它可以執行的工作包括：

- 查詢伺服器提供的共用資源。
- 連接指定的共用資料夾。
- 在有權限時，查詢資料夾內容。
- 在有權限時，進行檔案傳輸。

這些功能及參數都有 Samba 官方文件支援。[Samba](https://www.samba.org/samba/docs/current/man-html/smbclient.1.html?utm_source=chatgpt.com)

## 4.2 逐項拆解指令

假設公司提供測試帳號：

```text
labuser
```

你已獲得查詢共用資源的授權。

執行：

```bash
smbclient -L 192.168.56.10 -p 445 -U labuser
```

| 參數 | 白話解釋 |
|---|---|
| `smbclient` | 使用 SMB 用戶端程式 |
| `-L` | 請伺服器列出可查詢的共用資源 |
| `192.168.56.10` | 要詢問的伺服器 |
| `-p 445` | 指定 TCP 445 |
| `-U labuser` | 以 labuser 的身分提出請求 |

若需要密碼，讓程式在互動提示時要求輸入。

不要把密碼直接接在指令後面，以免意外暴露在 Shell 歷史紀錄或程序資訊中。

### 4.3 伺服器可能回傳什麼？

假設得到：

```text
Sharename       Type
---------       ----
Public          Disk
Finance         Disk
Archive         Disk
```

逐個理解。

**Sharename**

表示共用資源的名稱。

這不是實際檔案清單，而是伺服器對外提供的資源名稱。

例如：

```text
Finance
```

可能是一個部門共用資料夾的名稱。

**Type**

表示資源種類。

這裡的：

```text
Disk
```

表示檔案儲存類型的共用資源。

但不表示整個磁碟都能被存取。

### 4.4 看見 Finance，代表什麼？

假設你得到：

```text
Finance    Disk
```

你可以合理說：

「在這次查詢條件下，伺服器回傳了一個名稱為 Finance 的共用資源。」

但不能直接說：

「我已經取得 Finance 內部的財務報表。」

為什麼？

因為你目前取得的是：

```text
共用名稱
```

不是：

```text
檔案內容
```

更不是：

```text
修改權限
```

實際上，服務甚至可能依照你的帳號身分，決定哪些資訊可以回傳。

因此，另一個帳號可能得到不同結果。

### 4.5 從系統設計角度理解

為什麼伺服器願意告訴使用者有哪些共用資料夾？

因為列出資源本身就是很多系統的正常功能。

例如，一家公司的共用伺服器可能希望員工知道：

```text
Public
HR
Finance
Engineering
```

但不代表每個人都能進入所有部門的資料夾。

所以，伺服器可以允許你查詢資源名稱，同時拒絕你讀取某個資源。

這並不矛盾。

Microsoft 的 `NetShareEnum` 也是用來查詢共用資源資訊的介面，且不同查詢層級可能需要不同權限。[Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/lmshare/nf-lmshare-netshareenum?utm_source=chatgpt.com)

**第 4 節的核心：Enumeration 的目標是取得服務提供的具體資訊，但資訊可見性與資源存取權限是兩個不同問題。**

# 第 5 節｜身分驗證、存取權限、測試許可，要分開

這節是 M04 非常重要的資安觀念。

我們要認識三個不同的概念：

1. Authentication：身分驗證。
2. Authorization：存取授權。
3. Testing Authorization：測試許可。

它們看起來相似，但解決的是完全不同的問題。

## 5.1 Authentication：身分驗證

Authentication 問的是：

**「你是誰？」**

假設你在公司上班。

每天進入辦公室時，需要刷員工識別證。

門禁系統會確認：

「你是不是這家公司已登記的員工？」

通過確認，就是身分驗證成功。

在電腦系統裡也是一樣。

例如：

```text
Username: labuser
Password: ********
```

伺服器可能驗證這組登入資訊。

成功後，系統便能以特定身分處理後續請求。

但注意：

**成功登入不代表擁有所有權限。**

你可以成功登入公司的 NAS，但可能無法讀取主管的私人資料夾。

## 5.2 Authorization：存取授權

Authorization 問的是：

**「你能做什麼？」**

延續剛才的公司例子。

假設你已經刷卡進入公司。

公司裡面有：

```text
公司辦公室
    │
    ├── 一般辦公區
    ├── 會議室
    ├── 財務室
    └── 機房
```

你雖然是公司員工，但不代表能進入所有區域。

例如：

| 資源 | 一般員工 | 財務人員 | 系統管理員 |
|---|---|---|---|
| 公開文件 | 可讀取 | 可讀取 | 可讀取 |
| 財務文件 | 不可讀取 | 可讀寫 | 依工作需求設定 |
| 系統設定 | 不可修改 | 不可修改 | 可管理 |

這是一個假設性的權限設計，不是所有公司的標準。

身分驗證讓系統知道你是誰。

存取授權則決定你對特定資源可以執行哪些操作。

這兩者的差異在 Microsoft 官方身分管理文件中也有明確區分。[Microsoft Learn](https://learn.microsoft.com/en-us/entra/identity-platform/authentication-vs-authorization?utm_source=chatgpt.com)

## 5.3 Testing Authorization：測試許可

這是資安人員還必須考慮的第三個問題：

**「你是否獲得委託者允許執行這項測試？」**

假設你是資安工程師。

公司要求你測試一台 NAS。

你的任務範圍是：

```text
測試目標：
192.168.56.10

允許：
✓ 掃描指定連接埠
✓ 查詢 SMB 共用名稱
✓ 使用 labuser 登入
✓ 讀取指定測試檔案

不允許：
✗ 猜測其他員工密碼
✗ 下載非測試資料
✗ 修改正式檔案
✗ 刪除資料
```

即使系統本身允許你讀取某個敏感檔案，也不代表你的測試委託允許這樣做。

這就是技術權限與測試許可的差別。

### 5.4 三種權限要如何一起思考？

```text
                  你提出一個存取請求
                          │
                          ▼
               ┌──────────────────┐
               │ Authentication   │
               │ 你是誰？          │
               └────────┬─────────┘
                        │
                        ▼
               ┌──────────────────┐
               │ Authorization    │
               │ 系統允許做什麼？   │
               └────────┬─────────┘
                        │
                        ▼
               ┌──────────────────┐
               │ Test Permission  │
               │ 測試範圍允許嗎？   │
               └──────────────────┘
```

注意，前兩者通常是資訊系統執行的安全機制。

第三者是執行資安測試前必須確認的合法性與作業範圍，並不是 SMB 協定裡的第三道自動驗證程序。

### 5.5 常見考試觀念

題目可能問：

某個使用者已經成功登入 SMB 伺服器，但無法讀取 Finance 資料夾。

請問問題發生在哪個階段？

如果身分驗證已經成功，而系統基於權限設定拒絕讀取，這就是 Authorization 的問題。

但實務上仍必須查核錯誤原因，不能僅憑畫面上的 Access Denied 就斷言特定權限設定有問題。

**本節重點：Authentication 是確認身分；Authorization 是檢查操作權限；測試許可則決定資安人員被允許做哪些事情。**

# 第 6 節｜同一個案例，四種結果要分開記

這一節在訓練你建立正確的證據判讀能力。

## 6.1 假設我們取得以下結果

公司提供一個測試帳號：

```text
labuser
```

我們在已核准的環境中查詢 NAS。

得到：

```text
Public
Finance
Archive
```

接著，依照授權執行指定的讀取測試。

結果如下：

| 資源 | 是否列出名稱 | 指定檔案讀取 | 寫入測試 |
|---|---|---|---|
| Public | 成功 | 成功 | 未測試 |
| Finance | 成功 | 遭拒 | 未測試 |
| Archive | 成功 | 未測試 | 未測試 |

接下來，我們逐一理解。

## 6.2 Public：讀取成功

假設你成功讀取：

```text
Public/demo.txt
```

能證明什麼？

能證明：

在目前的網路、身分與測試條件下，`labuser` 成功讀取了這份檔案。

但不能證明：

- Public 裡的每一份檔案都能讀取。
- 其他帳號也能讀取。
- Public 裡的檔案都能修改。
- 可以建立或刪除檔案。

因為檔案可能有不同權限。

這裡要記住：

**一次成功的操作，只能支持它實際測試到的範圍。**

## 6.3 Finance：讀取遭拒

假設你嘗試讀取指定的測試路徑，得到：

```text
NT_STATUS_ACCESS_DENIED
```

這代表什麼？

它表示這次請求被拒絕。

但背後可能有不同原因。

例如：

**情況 A：共用資源權限不足。**

NAS 可能規定：

```text
Finance

允許：
FinanceGroup

拒絕：
一般員工
```

所以一般員工無法存取。

**情況 B：檔案系統權限不足。**

在 Windows 檔案伺服器上，除了共用權限（Share Permissions），還可能受到 NTFS 權限影響。

例如：

```text
SMB 共用層
    │
    │ 允許連接
    ▼
NTFS 檔案系統層
    │
    │ 不允許讀取
    ▼
Access Denied
```

即使共用層允許存取，底層檔案系統仍可能拒絕讀取。

Microsoft 官方疑難排解文件也特別提醒，遇到 SMB Access Denied 時，需要確認實際身分、相關安全設定及權限，而不是直接關閉防護機制。[Microsoft Learn](https://learn.microsoft.com/en-us/troubleshoot/windows-client/networking/access-denied-access-smb-file-share?utm_source=chatgpt.com)

**情況 C：遭拒不一定證明檔案存在。**

假設你嘗試：

```text
Finance/salary.xlsx
```

結果被拒絕。

是否代表一定存在 `salary.xlsx`？

不一定。

如果系統在你進入共用資源時就已拒絕請求，這次測試根本沒有確認那份檔案是否存在。

因此，報告應記錄實際遭拒的操作與位置，而不是自行推測內部檔案。

## 6.4 Archive：沒有測試

這個例子很有價值。

假設你知道 Archive 這個名稱存在，但沒有進一步測試。

那麼你知道什麼？

```text
名稱可見：是
讀取權限：未知
寫入權限：未知
```

不能因為 Public 可以讀取，就推測 Archive 也能讀取。

更不能因為 Finance 遭拒，就認為 Archive 一定也遭拒。

這就是資安研究很重要的原則：

> **沒有測試，不等於測試失敗，也不等於測試成功。**

## 6.5 為什麼要這樣記錄？

因為資安評估是一種證據推論。

如果你把不同操作混在一起，就容易高估實際風險。

例如：

```text
觀察：
Finance 這個名稱可見。

錯誤結論：
已取得財務資料。

合理結論：
目前確認該共用名稱可被查詢；
尚未證實內容可讀取。
```

這種證據思維不只適用於 SMB。

未來你學習 Web API、LDAP、DNS、雲端儲存與身分管理系統時，都會遇到相同問題。

**本節重點：每一項操作都應獨立記錄成功、失敗或未測試，不能把局部結果擴大成整個系統的結論。**

# 第 7 節｜查到資訊，是不是就找到漏洞？

答案是：

**不一定。資訊可被查詢，可能是正常功能，也可能形成資訊揭露風險。**

關鍵在於資訊內容、接收者及業務需求。

## 7.1 舉一個生活中的例子

你到醫院掛號。

醫院大廳有一張樓層配置圖：

```text
1F：掛號櫃台
2F：門診
3F：檢驗科
4F：行政辦公室
```

任何民眾都能看見。

這是不是漏洞？

通常不是。

因為醫院原本就希望民眾知道這些位置。

但假設醫院的公共資訊看板還顯示：

```text
內部管理系統帳號
員工個人資料
機密伺服器登入資訊
```

這就可能構成不適當的資訊揭露。

差別在哪裡？

不是「有沒有顯示資訊」，而是：

**什麼資訊被提供給了什麼人，以及這是否符合組織的安全要求。**

## 7.2 我們建立一個簡單的風險判斷框架

```text
                發現資訊可以被查詢
                         │
                         ▼
               ┌─────────────────┐
               │ ① 資訊是什麼？    │
               │ 名稱？個資？機密？ │
               └────────┬────────┘
                        │
                        ▼
               ┌─────────────────┐
               │ ② 誰可以取得？    │
               │ 員工？訪客？外部？ │
               └────────┬────────┘
                        │
                        ▼
               ┌─────────────────┐
               │ ③ 是否符合需求？  │
               │ 業務與政策允許嗎？ │
               └────────┬────────┘
                        │
                        ▼
                  判斷是否有風險
```

### 第一個問題：資訊是什麼？

例如：

```text
Public
```

和：

```text
Confidential_Merger_Project
```

揭露的資訊性質不同。

但不能光看名稱就確認裡面的內容或資料敏感度。

### 第二個問題：誰可以取得？

假設 Finance 部門員工可以看到財務資料夾名稱。

這可能完全合理。

但假設一個不相關的訪客帳號，也可以查詢大量敏感內部系統資訊。

就需要進一步評估風險。

### 第三個問題：是否符合業務需求？

有些資訊必須公開才能提供服務。

例如：

醫院的門診科別，應讓病患知道。

但病患沒有必要知道醫院內部資料庫帳號或機密文件路徑。

因此，判斷資訊揭露是否不當，必須考慮實際使用情境。

## 7.3 從 Enumeration 到 Vulnerability Analysis

你可以這樣理解：

```text
Enumeration
    │
    │ 發現：
    │ 一般使用者能查詢 Finance 共用名稱
    ▼
Vulnerability Analysis
    │
    │ 調查：
    │ 這個可見性是否符合組織政策？
    │ 該帳號是否有不應取得的權限？
    ▼
Risk Assessment
    │
    │ 評估：
    │ 可能影響哪些資產？
    │ 有什麼業務後果？
    ▼
Remediation
    │
    └── 修正有問題的設定並驗證
```

請注意：M04 與 M05 的工作實際上可能互相重疊。

M04 幫助我們發現具體資訊。

M05 則會更深入分析其中是否存在弱點，以及弱點可能造成的影響。

**本節重點：發現資訊不等於發現漏洞；必須結合資產敏感度、存取身分及預期安全政策才能判斷。**

# 第 8 節｜防護要保護資訊與操作，不只是把名稱藏起來

這節開始從防禦者角度思考。

假設你是公司的資安工程師。

發現一般員工能夠看到：

```text
Finance
```

你可能想到：

「是不是把 Finance 這個名稱隱藏起來就安全了？」

答案是：

**隱藏名稱可以降低資訊曝光，但真正的安全仍然依賴存取控制。**

## 8.1 第一層：Network Access Control

先確認哪些設備可以連接 SMB。

例如：

```text
                 公司網路
                     │
       ┌─────────────┴─────────────┐
       │                           │
  員工工作電腦                   外部網路
       │                           │
       ▼                           ▼
   防火牆檢查                  防火牆檢查
       │                           │
    符合規則                      不允許
       │                           │
       ▼                           X
   NAS TCP 445
```

這樣的設計，是避免不需要的設備直接連接檔案服務。

實際政策應依照使用者、設備、業務需求及網路架構設定。

一般企業內部的 SMB 服務，不應任意直接暴露 TCP 445 到公網。

Microsoft 也有專門的 SMB 網路安全強化指引。[Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-secure-traffic?utm_source=chatgpt.com)

## 8.2 第二層：Resource Access Control

假設一個員工通過防火牆，已經能夠連線 NAS。

接下來是不是就可以讀取全部資料？

當然不是。

還需要對資源設定權限。

例如：

```text
NAS
 │
 ├── Public
 │    └── 一般員工可讀取
 │
 ├── Finance
 │    └── 僅授權財務人員可存取
 │
 └── Admin
      └── 僅授權管理員可存取
```

這裡會用到最小權限原則：

**Least Privilege**

意思是：

使用者只應取得完成工作所需的權限。

例如：

一般員工只需要閱讀某份公告時，就不必同時取得修改或刪除權限。

這樣即使帳號遭到冒用，攻擊者能利用的權限也可能受到限制。

但不能因此認為單靠最小權限就能防止所有攻擊。

## 8.3 第三層：Logging and Auditing

第三層是紀錄與稽核。

假設某個帳號在短時間內多次查詢 SMB 資源，或持續對未獲授權的檔案提出存取請求。

資安人員可能希望知道：

```text
哪個帳號？
什麼時間？
從哪台設備？
存取什麼資源？
操作成功還是失敗？
```

這就需要適當的日誌紀錄與稽核設定。

但是請注意：

沒有日誌，不代表事情沒有發生。

也可能只是系統沒有啟用相關事件的紀錄功能。

## 8.4 真正完整的防護架構

```text
                  使用者／設備
                       │
                       ▼
             ┌──────────────────┐
             │ 第一層：網路控制  │
             │ 允許哪些來源連線？│
             └─────────┬────────┘
                       │
                       ▼
             ┌──────────────────┐
             │ 第二層：身分驗證  │
             │ 確認使用者身分    │
             └─────────┬────────┘
                       │
                       ▼
             ┌──────────────────┐
             │ 第三層：存取授權  │
             │ 可讀？可寫？可刪？│
             └─────────┬────────┘
                       │
                       ▼
             ┌──────────────────┐
             │ 第四層：日誌稽核  │
             │ 紀錄相關操作與結果│
             └──────────────────┘
```

這是一個用來理解防護控制的簡化架構。實際系統的日誌可能分散在各層，權限檢查也可能多次發生。

另外，現代 SMB 還有 SMB Signing（訊息簽章）及 SMB Encryption（加密）等安全機制，可以協助保護通訊內容的完整性或機密性。

但這些傳輸保護功能不能取代檔案存取權限。

### 8.5 一個值得記住的反例

假設你把 Finance 的名稱隱藏了。

但某個不應具備權限的帳號，仍然能直接透過已知路徑讀取財務文件。

這樣安全嗎？

不安全。

因為你只是讓它比較不容易被發現。

卻沒有真正限制存取。

這就像把一間房間的門牌拿掉，卻仍然讓所有人都能打開房門。

**本節重點：隱藏資源名稱是資訊曝光控制，不是完整的存取控制。真正的防護必須限制不應被允許的操作。**

# 第 9 節｜把結果寫成別人看得懂、能核對的一句話

這一節非常實用。

因為資安工程師不只要會操作工具，也要有能力把技術結果轉換成可以被查核的報告。

## 9.1 不好的報告寫法

假設你執行：

```bash
smbclient -L 192.168.56.10 -p 445 -U labuser
```

得到：

```text
Public
Finance
Archive
```

你向主管報告：

「我們已經攻破公司的 Finance 資料夾！」

這個說法有什麼問題？

它把：

```text
成功列出名稱
```

誇大成：

```text
成功攻破系統
```

兩者完全不同。

## 9.2 比較好的報告寫法

你可以說：

「在本次授權測試中，使用測試帳號 labuser，從指定測試網路對 192.168.56.10 執行 SMB 共用資源查詢，成功取得 Public、Finance、Archive 三個共用名稱。後續測試確認 Public 中指定測試檔案可讀取，Finance 指定路徑的讀取要求遭拒；Archive 與所有寫入操作均未測試。」

這樣的描述有什麼優點？

它明確交代：

- 使用哪個身分。
- 測試哪個目標。
- 執行哪些操作。
- 得到哪些結果。
- 哪些事情尚未確認。

最重要的是：

**不會讓主管誤以為你已經證明了實際上沒有測試過的風險。**

## 9.3 一個可以重複使用的報告框架

以後你在 M04、M05，甚至正式滲透測試時，都可以採用以下邏輯：

| 報告元素 | 需要回答的問題 | 範例 |
|---|---|---|
| Scope | 測試範圍是什麼？ | 192.168.56.10 |
| Identity | 使用什麼身分？ | labuser |
| Action | 執行什麼操作？ | SMB 共用資源查詢 |
| Observation | 觀察到什麼？ | 回傳三個共用名稱 |
| Evidence | 有什麼證據？ | 指令與原始輸出 |
| Limitation | 哪些沒有確認？ | 未測試寫入 |
| Assessment | 這代表什麼風險？ | 需結合權限政策評估 |

這裡有一個值得特別強調的區別：

**Observation（觀察結果）不等於 Assessment（風險評估）。**

例如：

觀察結果：

```text
labuser 可以列出 Finance 共用名稱。
```

風險評估：

```text
需確認 Finance 共用名稱是否預期對 labuser 可見。
```

不能在沒有更多證據時，直接把觀察結果解釋成重大資料外洩。

## 9.4 更進一步的專業做法

正式資安報告通常還應保留：

測試日期與時間、來源位置、工具版本、原始指令、相關輸出、測試範圍限制，以及風險判斷依據。

若發現值得修正的問題，應提出對應的修補與驗證方式。

例如：

```text
發現：
非預期的帳號可讀取指定敏感測試檔案。

可能原因：
共用或檔案系統權限設定不符合政策。

改善方向：
檢查相關群組及資源權限。

驗證方法：
使用原帳號重新測試指定讀取操作，
同時確認合法使用者仍能正常工作。
```

不要因為修正後查不到資料夾名稱，就認為問題已經解決。

應重新確認原本不應被允許的操作是否確實受到限制。

**本節重點：好的資安報告必須讓其他人能夠理解、驗證並重現你的觀察，同時清楚區分已證實與未確認的事項。**

# 第 10 節｜今天只做一個小檢核

這一節的目標不是考指令。

而是檢查你是否真正掌握了本課的核心觀念。

我們先把整堂課整理成一個證據模型。

## 10.1 請建立這張概念地圖

```text
                      目標主機
                         │
                         ▼
                ┌─────────────────┐
                │ ① 發現服務入口   │
                │ TCP 445 open    │
                └────────┬────────┘
                         │
                         ▼
                ┌─────────────────┐
                │ ② 辨識協定       │
                │ 確認 SMB 服務    │
                └────────┬────────┘
                         │
                         ▼
                ┌─────────────────┐
                │ ③ 查詢資源資訊   │
                │ Public/Finance  │
                └────────┬────────┘
                         │
                         ▼
                ┌─────────────────┐
                │ ④ 測試指定操作   │
                │ 讀取／修改等     │
                └────────┬────────┘
                         │
                         ▼
                ┌─────────────────┐
                │ ⑤ 分析測試證據   │
                │ 是否符合政策？   │
                └─────────────────┘
```

這張圖是一條方便學習的推理路徑，不是固定的實際通訊順序。

尤其要記住：

每一個階段得到的資訊，都必須對應它實際支持的結論。

例如：

```text
觀察 A：
445 open

只能證明：
有服務入口接受這次探測。

觀察 B：
取得 Finance 共用名稱

只能證明：
在本次條件下可以查詢到該名稱。

觀察 C：
指定測試檔案讀取成功

能進一步證明：
當時使用的身分可以讀取該檔案。
```

但是，你還沒有測試的其他行為，仍然是未知。

## 10.2 最後的核心觀念

請特別記住三句話：

**第一句：服務存在，不等於可以使用所有資源。**

**第二句：資源名稱可見，不等於可以讀取內容。**

**第三句：成功讀取指定檔案，不等於具備整個資料夾的完整讀寫權限。**

這三句話就是本堂課的精華。

# 補充｜概念 Q&A

目前原教材的 Q&A 區域尚未加入具體問題。以下是依照本課內容，補充的常見問題。

### Q1：Enumeration 跟 Scanning 到底有什麼不同？

Scanning 主要是辨識主機、連接埠與服務狀態。

Enumeration 則進一步向服務查詢具體資訊，例如共用資源、使用者、群組或目錄物件。

兩者不是完全互斥，因為同一個工具可能同時執行掃描與列舉。

### Q2：看到 TCP 445 open，是否代表存在資安漏洞？

不代表。

TCP 445 開放，通常只表示你從目前的位置可以連接到該服務入口。

是否存在漏洞，還需要評估實際服務、版本、設定、權限及網路暴露情況。

### Q3：列舉是不是一定要先登入？

不一定。

有些服務提供不需要登入的查詢功能。

有些服務必須完成身分驗證，才能取得特定資訊。

即使不需要登入，也不一定代表存在漏洞。

### Q4：`smbclient -L` 和 Nmap 有什麼差別？

假設：

```bash
nmap -p 445 192.168.56.10
```

主要是檢查 TCP 445 的狀態。

而：

```bash
smbclient -L 192.168.56.10 -p 445 -U labuser
```

則是嘗試以指定身分，向 SMB 伺服器查詢共用資源清單。

前者偏向服務入口觀察，後者偏向應用協定層面的資訊查詢。

### Q5：SMB 和 NAS 是不是同一個東西？

不是。

NAS（Network Attached Storage）是一種透過網路提供儲存服務的設備或系統。

SMB 則是實現網路檔案共用的一種協定。

例如：

```text
NAS
 │
 ├── SMB
 │    └── 提供網路檔案共用
 │
 ├── NFS
 │    └── 提供另一種網路檔案存取方式
 │
 └── HTTPS
      └── 提供網頁管理介面
```

因此，SMB 是 NAS 可能提供的服務之一。

NAS 不一定只能使用 SMB，SMB 也不只能用在 NAS 上。

### Q6：M04 為什麼只先教 SMB？

因為這一課最重要的是先建立 Enumeration 的共通原理。

之後學習 DNS、LDAP、SNMP 等不同服務時，仍然會反覆遇到：

「查詢什麼資訊、使用什麼身分、取得什麼結果，以及結果能證明什麼？」

只要這個框架建立起來，後面的列舉技術就比較容易理解。

# 本堂課總整理：你應該掌握的知識架構

| 主題 | 最重要的知識 | 實務意義 |
|---|---|---|
| Reconnaissance | 蒐集目標背景 | 建立調查線索 |
| Scanning | 確認服務入口與狀態 | 了解可觀察的服務 |
| Enumeration | 查詢具體資源與屬性 | 理解系統暴露的資訊 |
| SMB | 網路檔案共用協定 | 認識常見的檔案共用服務 |
| Authentication | 確認身分 | 知道誰提出請求 |
| Authorization | 控制可執行的操作 | 保護資源 |
| Information Disclosure | 評估資訊是否不當揭露 | 辨識潛在風險 |
| Access Control | 限制不應允許的操作 | 降低未授權存取 |
| Evidence | 保留可核對的觀察結果 | 避免錯誤結論 |
| Reporting | 明確描述操作與限制 | 支持修補與決策 |
