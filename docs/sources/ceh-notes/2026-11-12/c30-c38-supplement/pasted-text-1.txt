# CEH M01｜C30–C38：SOC、營運持續與安全治理文件

CEH v13 · M01-07 · 9 個核心觀念 · NIST × ISO × MITRE ATT&CK × 臺美產業規範

## 核心結論：企業資安不只要防止攻擊，更要有能力發現事件、指揮應變、維持營運，並透過文件建立明確的責任

假設一家臺灣半導體製造商，在凌晨兩點發現製造系統出現異常。

同一時間，美國矽谷的雲端供應商發出安全告警，而與該公司合作的臺灣銀行，也發現異常的系統登入紀錄。

這時，企業必須回答四個問題：

1. Detection： 誰負責發現並初步判斷異常？
2. Response： 誰負責深入調查、決策與指揮事件應變？
3. Continuity： 如果系統無法正常使用，如何維持最重要的業務？
4. Governance： 企業與供應商各自承諾了什麼？哪些行為被允許？哪些資訊必須保密？

這四個問題，正好涵蓋你的 C30–C38。

## 二、C30｜Security Operations Center：SOC 是什麼？

### 1. 白話理解：SOC 就是資安系統的監控與應變協調中樞

想像一家大型半導體工廠。

生產設備有溫度、壓力、電流與設備狀態監控。

當某個數值異常，系統會通知工程師確認是否存在故障。

SOC 也是類似概念，只是監控對象變成資訊安全。

它可能接收：

- 伺服器與作業系統日誌。
- 防火牆與網路流量紀錄。
- EDR（Endpoint Detection and Response）端點告警。
- 雲端與身分管理系統日誌。
- 應用程式安全事件。
- Threat Intelligence（威脅情報）。

SOC 將這些訊號轉化成有意義的安全判斷。

### 2. SOC 不等於一套 SIEM 軟體

這是第一個容易混淆的觀念。

| 名詞                  | 主要功能                        |
| ------------------- | --------------------------- |
| SOC                 | 負責監控、分析、分流、協調與改善安全事件處理的組織能力 |
| SIEM                | 集中收集、搜尋、關聯分析日誌及安全事件         |
| EDR                 | 偵測、調查並回應端點的可疑活動             |
| SOAR                | 整合安全工具與工作流程，自動化部分應變動作       |
| Threat Intelligence | 提供攻擊者、技術、指標與威脅背景資訊          |

所以，企業購買一套 SIEM，並不代表已經建立有效的 SOC。

真正的 SOC 還需要明確的職責、值班制度、事件標準、升級規則、處置授權及績效評估。

### 3. 一個 SOC 告警如何變成安全事件？

假設銀行系統發出一則告警：

「某管理員帳號在異常時間登入。」

這個訊號可能有多種解釋。

管理員可能正在合法執行夜間維護；也可能是帳號遭到入侵。

因此，SOC 的工作不是看到異常就直接判定企業遭受攻擊，而是建立證據。

Telemetry / Logs

收到登入時間、來源、帳號及端點資訊

Alert

規則或分析系統標示可疑活動

Triage

比對授權變更、帳號行為及其他日誌

Incident Determination

依事先定義的條件確認是否宣告資安事件

Escalation / Response

依事件等級通知適當人員並採取行動

NIST CSF 2.0 對此有非常直接的對應：

- DE.AE-02： 分析潛在不利事件。
- DE.AE-03： 關聯多個資訊來源。
- DE.AE-07： 整合威脅情報與其他背景資訊。
- DE.AE-08： 當符合事件判定條件時，宣告資安事件。
- RS.MA-03： 對已識別事件分類並排定優先順序。
- RS.MA-04： 必要時進行事件升級。

上述內容可以直接從 NIST CSF 2.0 官方繁體中文版核對。

### 4. 如何利用 MITRE ATT&CK？

假設 SOC 發現：

某個原本只在正常上班時間使用的外部維修帳號，凌晨透過 VPN 登入半導體公司的維護系統。

MITRE ATT&CK 的 T1078 — Valid Accounts 描述攻擊者如何利用有效帳號進行初始存取、持續存取、權限提升或規避防禦。

[image](https://www.google.com/s2/favicons?domain=https://attack.mitre.org\&sz=32)

MITRE ATT&CK®



SOC 可以利用 ATT&CK 建立調查假說：

「這是否為合法維修，或是被竊取的有效帳號遭到濫用？」

接著關聯登入紀錄、MFA、工單、設備維護時段，以及是否出現非預期的後續行為。

但必須記住：某個行為符合 ATT&CK 技術描述，不代表已經證明攻擊發生。 ATT&CK 是攻擊行為知識庫，不能單獨代替證據驗證。

C30 核心：SOC 的真正功能，是把分散的安全訊號轉化為可採取行動的事件判斷與處置流程。

## 三、C31｜Tier 1 Analyst：第一線分析人員為什麼重要？

### 1. Tier 1 就像急診的檢傷分流

醫院急診收到病人後，不是所有病人都立即進入手術室。

首先需要確認症狀、危急程度，以及應交由哪個專業團隊處理。

SOC 的 Tier 1 Analyst 也有類似職責。

Tier 1 的主要工作是初步監控、驗證、分流及升級安全告警。

它不代表只能按下「確認」按鈕，而是要在有限時間內做出有根據的第一線判斷。

### 2. 一則告警應如何處理？

假設臺灣銀行的 SIEM 偵測到某位管理員帳號：

凌晨 02:00 從未見過的來源登入雲端管理平台。

Tier 1 應先查核幾個重要事實：

1. 這個帳號的正常登入模式是什麼？
2. 是否有已核准的夜間維護工單？
3. MFA 與身分驗證紀錄是否正常？
4. 是否存在異常的後續存取或大量資料下載？
5. 是否符合預先定義的事件升級條件？

得到證據後，才能適當分類。

| 判斷狀態                      | 意義                  | 合理行動        |
| ------------------------- | ------------------- | ----------- |
| False Positive            | 告警條件觸發，但證據不支持所警示的問題 | 記錄原因、調整偵測規則 |
| Suspicious / Inconclusive | 存在異常，但尚不足以確定        | 補充證據、必要時升級  |
| Confirmed Incident        | 已符合組織定義的資安事件條件      | 啟動相應事件應變程序  |

初步分流不只是確認真假，也要評估潛在影響與急迫性。

例如，企業網站上的單次失敗登入，與晶圓廠製造設備的管理員帳號遭異常使用，即使告警種類相似，處理優先順序也可能截然不同。

### 3. Tier 1 的技術能力

Tier 1 應具備基本的網路、作業系統、身分驗證、日誌分析及安全事件概念。

同時，必須知道自己的處置權限。

例如，Tier 1 可以依據預先核准的 Playbook（應變操作手冊）執行特定操作，但不代表每位 Tier 1 都有權停止銀行正式交易系統。

對照標準： NIST CSF 2.0 的 DE.AE-06、DE.AE-08，以及 RS.MA-02–04，分別涉及事件資訊傳遞、事件判定、事件報告驗證、優先排序與升級。

[image](https://www.google.com/s2/favicons?domain=https://tsapps.nist.gov\&sz=32)

NIST



C31 核心：第一線分析人員的價值，是及時把大量原始告警轉換成可靠的判斷，而不是把所有告警一律升級。

## 四、C32｜Tier 3 Analyst / Threat Hunter：為什麼不能只等系統告警？

### 1. 偵測不到，不代表沒有攻擊

假設半導體公司的防毒、EDR 和防火牆都沒有產生告警。

這是否意味著企業沒有遭到入侵？

不能這樣推論。

原因包括：

- 攻擊者可能利用正常帳號登入。
- 攻擊行為可能沒有觸發現有偵測規則。
- 某些資料來源可能沒有被收集。
- 安全工具可能被規避或失效。
- 攻擊者可能已長期存在於環境中。

因此，需要主動威脅獵捕（Threat Hunting）。

### 2. Tier 3 與 Threat Hunting 是同一件事嗎？

不完全是。

許多 SOC 會將 Tier 3 設計成進階分析人員，負責複雜事件調查、進階威脅分析及改善偵測能力。

Threat Hunter 則是專門主動尋找尚未被既有告警系統發現的威脅。

在部分企業，Threat Hunter 是 Tier 3 的工作之一；在其他企業，威脅獵捕可能由獨立團隊執行。

Tier 1、Tier 2、Tier 3 是常見的 SOC 組織分層，並不是 NIST 強制規定的全產業職稱。

NIST SP 800-181 Rev. 1 的 NICE Framework 比較重視實際工作任務、知識與技能，並將 Defensive Cybersecurity、Incident Response、Threat Analysis 等能力加以區分。

### 3. 威脅獵捕與一般告警處理的差異

|       | 一般告警處理          | Threat Hunting                  |
| ----- | --------------- | ------------------------------- |
| 起點    | 安全工具產生告警        | 研究人員提出威脅假說                      |
| 工作方式  | 驗證已被標記的異常       | 主動搜尋潛在攻擊證據                      |
| 主要產出  | 事件判斷、處置或升級      | 威脅發現、偵測改善、涵蓋缺口                  |
| 典型參與者 | Tier 1 / Tier 2 | 進階分析師、Hunter、Detection Engineer |

### 4. 使用 MITRE ATT&CK 建立獵捕假說

假設我們懷疑半導體公司的外部設備供應商帳號遭到濫用。

可以從 MITRE ATT&CK T1078（Valid Accounts）建立假說：

> 攻擊者可能利用合法帳號登入，但其登入時間、來源設備及後續操作不同於正常維護模式。

接著驗證：

- 維護帳號是否在未核准時段登入？
- 是否來自非預期的 VPN 或網路來源？
- 是否存取正常職務範圍以外的系統？
- 是否出現非預期的權限提升？
- 是否可以與其他端點及系統日誌交叉驗證？

ATT&CK T1078 的現行技術頁也提供異常登入、服務帳號濫用及雲端身分行為等偵測分析範例。

[image](https://www.google.com/s2/favicons?domain=https://attack.mitre.org\&sz=32)

MITRE ATT&CK®



但要注意一個研究方法上的問題：

假設獵捕沒有發現異常，不代表可以證明攻擊者不存在。

因為可能仍存在 Telemetry Coverage Gap（遙測涵蓋缺口）。

所以好的 Threat Hunting 報告，除了說明找到什麼，也應記錄搜尋範圍、資料來源、假設條件、觀察期間及未知區域。

C32 核心：Tier 3 處理更複雜的安全分析；Threat Hunting 的重要特色，是在尚未收到明確告警時，主動尋找隱藏的攻擊證據。

## 五、C33｜SOC Manager：管理 SOC，不等於指揮每一場資安事故

### 1. SOC Manager 是資安監控能力的管理者

假設一家矽谷科技公司有 12 名 SOC 分析師，輪班監控多個雲端產品。

SOC Manager 必須考慮的不只是技術問題，還包括人員、流程、預算與交付品質。

典型工作包括管理排班、教育訓練、事件分流流程、工具品質、服務承諾、案件積壓與持續改善。

例如：

如果同一條 SIEM 規則每天產生 2,000 則沒有調查價值的告警，分析師可能疲於處理雜訊，反而忽略真正重要的事件。

這不是單一 Tier 1 可以完全解決的問題。

SOC Manager 應要求改善偵測規則，合理配置資源，並檢查流程是否仍能達到安全目標。

### 2. 如何量測 SOC 的運作品質？

| 指標                  | 英文                               | 衡量問題                   |
| ------------------- | -------------------------------- | ---------------------- |
| MTTD                | Mean Time to Detect              | 從定義的事件起點到偵測，平均需要多久？    |
| MTTA                | Mean Time to Acknowledge         | 告警出現後，多久有人確認接手？        |
| MTTR                | Mean Time to Respond / Recover 等 | 依明確定義衡量回應、修復或恢復時間      |
| False Positive Rate | 誤報率                              | 偵測結果中有多少不正確的告警？        |
| Escalation Quality  | 升級品質                             | 被升級的案件是否具有足夠證據與正確優先順序？ |

這些是常見營運量測指標，不是所有 SOC 都必須使用相同名稱及公式。

尤其 MTTR 在不同組織可能分別指 Mean Time to Respond、Repair、Resolve 或 Recover，正式使用時必須明確定義起訖點。

### 3. 為什麼不能只追求快速結案？

假設主管設定：

「所有告警必須在五分鐘內結案。」

分析師為了達成 KPI，可能把缺乏證據的事件直接標成誤報。

結果報表非常漂亮，但 SOC 的偵測品質下降。

這是一個典型的代理指標問題（Proxy Metric Problem）。

真正的目標不是縮短工單存在時間，而是在合理成本下，提高偵測、分析與應變的正確性及時效性。

因此，SOC Manager 應將處理時效和案例抽樣覆核、漏報檢查、偵測涵蓋率及應變結果一起評估。

C33 核心：SOC Manager 對 SOC 的持續運作與管理品質負責，不必然是每一場重大事件的現場指揮官。

## 六、C34｜Incident Response Commander：重大事件發生後，誰有權決定下一步？

### 1. 一場重大資安事件，需要跨部門決策

假設某半導體工廠的設備維護管理系統疑似遭入侵。

資安團隊提議立即隔離相關伺服器。

但是製造部門指出：

「現在直接斷線，可能造成設備失去必要的管理功能，進而影響生產與實體安全。」

法務部門也提醒，部分日誌需要保存，以供後續調查。

這時候，如果所有部門各自採取行動，可能產生更大的問題。

Incident Response Commander（事件應變指揮者）的核心職責，就是在預先賦予的權限內，統一協調事件應變。

### 2. 指揮者不一定是技術最強的人

Incident Commander 不必親自分析所有封包、記憶體映像或惡意程式。

他必須能整合各專業團隊的判斷，處理優先順序、權限及衝突。

Incident Commander

事件目標、決策、升級、協調及溝通

Security / SOC

調查攻擊、保存證據

IT / Cloud

隔離、修復、基礎設施復原

OT / Operations

設備安全、製程連續性

Legal / Compliance

法遵、通報、證據要求

Business Continuity

替代流程與持續營運

Communications

內外部訊息與利害關係人

這是重大事件的組織設計範例。實際權限與角色配置由企業事先建立的應變計畫決定。

### 3. 事件應變的關鍵決策

Incident Commander 可能需要主持以下判斷：

| 決策問題         | 需要的證據            |
| ------------ | ---------------- |
| 是否宣告重大資安事件？  | 技術證據、業務影響、事件判定準則 |
| 是否隔離系統？      | 持續攻擊風險、隔離後果、替代方案 |
| 是否啟動 BCP？    | 服務受損程度、關鍵業務可持續能力 |
| 是否通知客戶或主管機關？ | 事件事實、契約與適用通報義務   |
| 何時恢復服務？      | 系統可信狀態、修復驗證及業務核准 |

關鍵不是所有事情都由指揮者自行決定，而是依據事先建立的權限與決策規則，讓有權責的人及時作出可追溯的決策。

NIST SP 800-61 Rev. 3 將事件應變視為持續的風險管理能力。NIST CSF 2.0 的 RS.MA-01–05 則涵蓋應變計畫執行、事件驗證、排序、升級及啟動復原準則。

[image](https://www.google.com/s2/favicons?domain=https://csrc.nist.gov\&sz=32)

NIST Computer Security Resource Center+1



### 4. SOC Manager 與 Incident Commander 的本質差異

|       | SOC Manager | Incident Commander |
| ----- | ----------- | ------------------ |
| 管理對象  | SOC 的長期營運能力 | 特定事件的應變過程          |
| 工作時間軸 | 持續性         | 事件啟動到結案            |
| 主要重點  | 人員、流程、品質、績效 | 情勢判斷、應變決策、協調       |
| 主要交付  | SOC 績效及管理改善 | 事件控制、復原與結案結果       |

在規模較小的企業，同一個人可能兼任兩者；但角色的權責仍應分開定義。

C34 核心：事件指揮者負責把跨部門的資訊轉變成一致、及時、可追溯的應變行動。

## 七、C35｜Business Continuity Plan（BCP）：災難發生時，企業如何繼續營運？

### 1. BCP 不是「如何把伺服器重新開機」

假設一家銀行的網路銀行系統遭受勒索軟體攻擊。

IT 團隊可能需要數小時才能恢復相關伺服器。

但是銀行不能只回答：

「我們正在修電腦。」

銀行還要思考：

- 哪些重要金融業務必須持續？
- 是否有替代交易或服務管道？
- 哪些業務可以暫時延後？
- 客戶如何得知服務狀態？
- 其他銀行系統是否受到影響？
- 什麼時候能恢復到可接受的服務能力？

這就是 BCP 的目的。

Business Continuity Plan（營運持續計畫）描述組織在重大中斷發生期間及之後，如何持續維持必要的業務功能。

NIST SP 800-34 Rev. 1 將 BCP 定義為一組預先建立的程序，用來確保重要業務流程在重大中斷期間及之後持續運作。

[image](https://www.google.com/s2/favicons?domain=https://csrc.nist.gov\&sz=32)

CSRC



BCP 所處理的範圍不只包含資安事故，也可能包括地震、停電、供應鏈中斷、設備故障或其他重大事件。

### 2. BCP、DRP 與 Incident Response Plan 的差異

這三份文件極容易混淆。

| 計畫  | 全名                       | 核心問題                    |
| --- | ------------------------ | ----------------------- |
| IRP | Incident Response Plan   | 發生資安事件時，如何調查、控制及處置？     |
| DRP | Disaster Recovery Plan   | 發生重大災難後，如何恢復受影響系統與基礎設施？ |
| BCP | Business Continuity Plan | 正常系統無法使用期間，如何維持關鍵業務？    |

假設一家半導體公司的 MES（Manufacturing Execution System，製造執行系統）發生重大異常。

IRP 關心是否遭到惡意入侵，以及如何隔離、調查與控制事件。

DRP 關心如何使用備援資源與可信備份，恢復 MES 的技術功能。

BCP 則進一步關心 MES 無法正常運作時，哪些製造活動必須暫停、哪些可依核准的替代程序執行，以及如何確保人員與設備安全。

這三種計畫可以彼此配合，但不能互相替代。

### 3. Business Impact Analysis（BIA）：企業為什麼需要先決定什麼最重要？

BCP 的基礎之一是 BIA（業務衝擊分析）。

BIA 不只是列出所有系統，而是要回答：

> 如果某項業務中斷 10 分鐘、1 小時、1 天，分別會造成什麼後果？

例如：

| 業務        | 中斷可能造成的影響    | 需要調查的相依關係    |
| --------- | ------------ | ------------ |
| 晶圓廠製造管理   | 製程排程或生產控制受影響 | MES、設備、電力、人員 |
| 銀行支付服務    | 客戶交易無法正常處理   | 核心系統、支付通道、網路 |
| SaaS 文件分析 | 客戶無法使用平台功能   | 雲端、資料庫、身分服務  |

ISO 22301:2019 是營運持續管理系統（BCMS）的國際要求標準，ISO/TS 22317:2021 則專門提供 BIA 的實施指引。

[image](https://www.google.com/s2/favicons?domain=https://www.iso.org\&sz=32)

Business continuity management systems+1



### 4. RTO 與 RPO：兩個數字不能搞混

RTO（Recovery Time Objective）：復原時間目標。

描述系統或服務應在多長的目標時間內恢復到所要求的狀態。

RPO（Recovery Point Objective）：復原點目標。

描述系統復原後，資料至少需要恢復到事故前的哪個時間點；在常見時間差表示法中，可以理解為容忍多少時間範圍內的資料損失。

銀行交易系統示例

假設銀行設定 RTO = 2 小時、RPO = 15 分鐘。以下數字僅供教學。

RPO 關心資料損失的時間範圍；RTO 關心恢復服務所需的時間。兩者必須分別經過備份、復原與演練驗證。

NIST SP 800-34 Rev. 1 的術語定義也明確區分 Recovery Time Objective 與 Recovery Point Objective。

[image](https://www.google.com/s2/favicons?domain=https://csrc.nist.gov\&sz=32)

CSRC+1



這裡還有一個重要的邏輯：

即使企業每 15 分鐘備份一次，也不代表一定能達成 RPO 15 分鐘，更不代表能在兩小時內完成復原。

還需要考慮備份是否成功、是否有一致性、備份有沒有受到破壞，以及實際復原速度。

### 5. 臺灣金融監理對營運持續的要求

金管會《金融控股公司及銀行業內部控制及稽核制度實施辦法》第 12 條，明確將營運持續管理機制列為內部控制應涵蓋的政策與作業程序。

同條也要求涵蓋重大偶發事件處理及客戶資料保密。

[image](https://www.google.com/s2/favicons?domain=https://law.banking.gov.tw\&sz=32)

Banking Law Search System



金融機構需要把這些要求落實到實際業務與系統，而不是只有一份文件。

銀行公會的《金融機構資通安全防護基準》及《金融機構辦理電子銀行業務安全控管作業基準》則是查核相關安全實務時應參考的自律規範。

[image](https://www.google.com/s2/favicons?domain=https://ba.org.tw\&sz=32)

「金融機構資通安全防護基準」+1



### 6. ISO 22301 的定位

ISO 22301 是 BCMS 的要求標準，而 BCP 是營運持續管理體系中的一項重要計畫與交付物。

截至 2026 年 11 月，ISO 22301:2019 仍是正式發布的主要版本，另有 Amd 1:2024 修訂；後續修訂尚處於開發階段。

[image](https://www.google.com/s2/favicons?domain=https://www.iso.org\&sz=32)

Business continuity management systems+1



C35 核心：BCP 要維持的是重要業務，不只是讓 IT 系統重新上線。

## 八、C36｜Service Level Agreement（SLA）：服務承諾如何轉換成可驗證的責任？

### 1. SLA 就是對服務品質與責任的具體約定

假設一家矽谷雲端公司向臺灣銀行提供 AI API。

供應商說：

「我們的系統非常穩定，而且有專業客服。」

這句話沒有具體衡量標準。

銀行無法清楚知道何時算服務失敗、供應商多久必須回應，或服務不符合承諾時應如何處理。

因此需要 SLA。

NIST 對 Service Level Agreement 的定義，涵蓋服務提供者的責任、客戶期待、可靠性、服務水準、回應時間，以及通報、解決與終止等約定。

[image](https://www.google.com/s2/favicons?domain=https://csrc.nist.gov\&sz=32)

CSRC



### 2. 一份完整的 SLA 可以約定什麼？

| 面向                       | 示例內容           |
| ------------------------ | -------------- |
| Availability             | 每月服務可用率目標      |
| Response Time            | 嚴重事件通報後的首次回應時間 |
| Resolution / Restoration | 修復或恢復的目標與責任    |
| Measurement              | 使用什麼監控資料計算服務水準 |
| Reporting                | 提供服務報告的頻率及方式   |
| Exclusions               | 哪些情況不計入特定指標    |
| Remedies                 | 未達服務承諾時的補救方式   |

以上是設計 SLA 時可以採用的項目，具體條件必須由當事方約定。

### 3. 99.9% 的可用率代表什麼？

假設某份 SLA 承諾，按照其定義，每月服務可用率達到 99.9%。

若以 30 天、24 小時的完整月份計算，而且沒有額外排除項目：

\\[ 30\times24\times60\times(1-0.999) =43.2\text{ 分鐘} \\]

也就是整個月份容許約 43.2 分鐘的不符合可用性條件時間。

但是，真正的 SLA 必須先定義什麼算「不可用」，以及如何計算。

例如，登入頁面正常，但主要交易 API 全部失敗，究竟算不算服務可用？

如果 SLA 只用不適當的健康檢查端點衡量，可能出現監控顯示服務正常、客戶實際無法使用的情況。

所以 SLA 不只是數字，而是可以驗證的服務定義。

### 4. SLA、RTO、RPO 的重要差別

|              | SLA          | RTO           | RPO           |
| ------------ | ------------ | ------------- | ------------- |
| 目的           | 定義服務承諾       | 定義復原時間目標      | 定義資料復原點目標     |
| 核心問題         | 供應商提供什麼服務品質？ | 多久恢復所需能力？     | 可容忍多少資料損失？    |
| 所在制度         | 服務合約與供應商治理   | BCP／DRP       | BCP／DRP       |
| 是否一定具有相同約束力？ | 依契約條件        | 視企業目標及契約／法規要求 | 視企業目標及契約／法規要求 |

一家供應商可以同時承諾可用率及 RTO，但兩者不能互相推論。

而且 SLA 不一定涵蓋所有系統故障情境，必須查看實際約定。

C36 核心：SLA 是服務水準與責任的約定，不是營運持續計畫，也不是保密契約。

## 九、C37｜Non-Disclosure Agreement（NDA）：保密協議在保護什麼？

### 1. NDA 的目的，不是讓資訊永遠不能使用

假設臺灣半導體公司委託美國資安顧問，檢查製程資料交換平台。

顧問可能需要接觸：

- 系統架構圖。
- 資料庫結構。
- 尚未公開的技術資訊。
- 測試過程取得的漏洞資訊。
- 客戶或供應商的機密資料。

這些資訊是為了完成特定工作而提供，不代表顧問可以任意複製、利用或公開。

所以雙方需要明確約定保密責任。

NDA（Non-Disclosure Agreement）是一種以契約方式約束特定資訊使用、保存與揭露的協議。

它可以是雙方相互承擔保密義務的 Mutual NDA，也可以是單方承擔保密義務的 Unilateral NDA。

### 2. 完整的 NDA 應回答哪些問題？

| 核心條款                     | 必須解決的問題          |
| ------------------------ | ---------------- |
| Confidential Information | 哪些資訊受到保護？        |
| Permitted Purpose        | 資訊可以用於什麼目的？      |
| Permitted Recipients     | 哪些人可以取得資訊？       |
| Protection Obligations   | 接收方應採取哪些保密措施？    |
| Exceptions               | 哪些資訊不受保密條款限制？    |
| Duration                 | 保密義務持續多久？        |
| Return / Destruction     | 合作結束後如何返還或清理資訊？  |
| Required Disclosure      | 遇到適用法律要求揭露時如何處理？ |

特別重要的是，NDA 不應被設計成妨礙依法向主管機關通報或其他受法律保護的揭露活動。

### 3. 臺灣半導體：NDA 與《營業秘密法》的關係

臺灣《營業秘密法》第 2 條規定，受保護資訊需要符合秘密性、因秘密性具有經濟價值，以及所有人已採取合理保密措施等要件。

第 10 條則將特定以不正當方法取得、使用或洩漏營業秘密的行為納入侵害範圍，其中包括違反保密義務等不正當方法。

[image](https://www.google.com/s2/favicons?domain=https://law.moj.gov.tw\&sz=32)

Law\.gov.tw



因此，NDA 可以成為企業合理保密措施的重要組成部分。

但不能反向推論：

「只要文件上寫了 Confidential，或者雙方簽署 NDA，所有資訊就必然構成法律上的營業秘密。」

仍須檢視法定要件及實際保護措施。

### 4. 美國矽谷：《Defend Trade Secrets Act》

美國聯邦法律 18 U.S.C. §1839(3) 也要求營業秘密所有人採取合理保密措施，且資訊因不為一般人所知而具有獨立經濟價值。

[image](https://www.google.com/s2/favicons?domain=https://uscode.house.gov\&sz=32)

uscode.house.gov



另外，18 U.S.C. §1833(b) 對特定為通報或調查疑似違法行為，而向政府官員或律師保密揭露營業秘密的情形，設有法定免責規定。

[image](https://www.google.com/s2/favicons?domain=https://uscode.house.gov\&sz=32)

uscode.house.gov



這說明 NDA 的保密義務需要與適用法律共同理解。

### 5. NDA 與 C15 弱點揭露的連結

假設資安顧問發現半導體平台有重大漏洞。

顧問應依照授權與約定的回報管道，提供經過適當保護的測試證據。

但 NDA 不會自動取代：

- 測試授權書。
- Scope 與 ROE。
- 弱點回報流程。
- 資安事件通報程序。
- 資料刪除及清理要求。

這些文件規範不同的問題，需要相互協調。

C37 核心：NDA 處理的是特定資訊的保密、使用與揭露義務，不是服務可用率，也不是系統操作許可。

## 十、C38｜Acceptable Use Policy（AUP）：企業為什麼需要可接受使用政策？

### 1. 有系統使用權，不代表可以任意使用

假設某位銀行工程師擁有公司核發的筆記型電腦。

這台電腦由他日常使用，但他是否可以：

- 將客戶資料上傳到個人雲端硬碟？
- 使用私人 AI 服務分析銀行內部文件？
- 安裝未經核准的遠端控制軟體？
- 將公司設備借給其他人使用？
- 把正式環境資料複製到自己的測試電腦？

這些問題不是靠防火牆就能全部解決。

企業必須對資訊資產的合理用途與禁止行為建立明確規則。

這就是 AUP。

### 2. AUP 與 Access Control 有何不同？

Access Control 是技術上能否進行特定操作。

Acceptable Use Policy 是組織制度上是否允許該行為。

例如，某員工可能技術上能夠安裝一套軟體，但企業政策規定正式環境不得安裝未核准工具。

所以：

\\[ \text{技術上可以執行} \not\Rightarrow \text{組織政策允許執行} \\]

這正是 Governance（治理）與 Technical Controls（技術控制）之間的重要區別。

### 3. NIST SP 800-53 的正式對應

NIST SP 800-53 Rev. 5 的 PL-4 — Rules of Behavior，要求組織向需要存取系統的人員提供資訊及系統使用相關的責任與行為規則，取得必要的知悉與遵守確認，並定期檢討規則。

其補充指引也將 Acceptable Use Agreements 和 Non-Disclosure Agreements 列為相關的存取協議類型。

[image](https://www.google.com/s2/favicons?domain=https://csf.tools\&sz=32)

CSF Tools



因此，AUP 不應只是入職時簽署一次、之後再也不檢討的文件。

### 4. 三種產業的 AUP 如何設計？

| 產業    | 重要使用情境             | 可建立的 AUP 管理規則               |
| ----- | ------------------ | --------------------------- |
| 臺灣半導體 | 設備維護電腦、USB、製程資料    | 限制未核准軟體、外接媒體及資料外傳           |
| 美國矽谷  | SaaS 開發環境、雲端憑證、程式碼 | 定義個人雲端、外部 AI 工具、正式環境憑證的使用規則 |
| 臺灣金融  | 客戶資料、交易系統、行員設備     | 限制客戶資料查詢、個人裝置使用與未核准服務       |

這些是可依風險採用的企業政策設計，不代表每一家企業都有完全相同的法律條文要求。

對臺灣銀行業而言，金管會《金融控股公司及銀行業內部控制及稽核制度實施辦法》第 12 條要求內部控制涵蓋資訊管理及客戶資料保密，第 25 條則規範資訊安全制度、風險控管及事件通報應變。AUP 可以成為落實制度的一項組織控制措施。

[image](https://www.google.com/s2/favicons?domain=https://law.banking.gov.tw\&sz=32)

Banking Law Search System+1



### 5. AUP 如何變成可驗證的控制？

真正有效的 AUP 應與技術控制相互配合。

例如：

| AUP 規則           | 對應技術控制                   | 驗證證據      |
| ---------------- | ------------------------ | --------- |
| 禁止使用未授權軟體        | Application Allowlisting | 程式執行及阻擋紀錄 |
| 禁止將機密資料傳至私人雲端    | DLP、雲端存取控制               | 上傳事件及政策紀錄 |
| 管理員不得共用帳號        | IAM、PAM、MFA              | 帳號與存取稽核紀錄 |
| 禁止未授權使用 USB 儲存設備 | Endpoint Device Control  | 裝置存取紀錄    |

這些技術控制不一定能阻止所有違規行為，但可以協助企業預防、偵測並驗證政策執行情況。

C38 核心：AUP 定義資訊資產被允許如何使用；它是治理規則，不是服務水準或保密協議。

## 十一、四份治理文件的決策矩陣

這是整個單元最值得記住的比較表。

| 比較     | BCP                      | SLA                   | NDA             | AUP                 |
| ------ | ------------------------ | --------------------- | --------------- | ------------------- |
| 核心目的   | 維持關鍵業務                   | 約定服務品質                | 保護機密資訊          | 規範資產使用              |
| 主要對象   | 企業及應變團隊                  | 服務提供者與客戶              | 資訊揭露方與接收方       | 員工、承包商、使用者          |
| 何時最重要  | 重大業務中斷                   | 服務提供與履約期間             | 交換敏感資訊前後        | 使用資訊系統期間            |
| 典型內容   | 關鍵流程、替代措施、復原             | 可用率、回應、補救             | 保密範圍、期間、例外      | 允許及禁止行為             |
| 重要參考依據 | ISO 22301、NIST SP 800-34 | NIST SP 800-47 Rev. 1 | 臺灣營業秘密法、美國 DTSA | NIST SP 800-53 PL-4 |

一個實用記憶方法：

BCP 管營運不中斷；SLA 管服務承諾；NDA 管資訊保密；AUP 管資產使用。

再加上 C30–C34 的角色分工，就形成：

「由 SOC 發現問題、由事件應變組織協調處置、透過 BCP 維持營運，並以 SLA、NDA、AUP 明確化責任。」

## 十二、三大產業的整合治理實務

### 1. 臺灣半導體科技產業

假設設備供應商的遠端維修帳號遭到濫用。

SOC： 偵測異常登入與後續操作，建立事件證據。

Incident Response： 與設備工程、IT、OT 及業務管理人員協調，避免不適當的隔離措施危及製程安全。

BCP： 確保工廠可以按照已核准的替代程序，維持必要製造活動或安全停機。

SLA： 與設備或雲端供應商約定回應及服務恢復責任。

NDA／AUP： 規範供應商對製程資料的保密義務、遠端工具與帳號的允許用途。

可以參照 NIST SP 800-82 Rev. 3、SEMI E187，以及臺灣《營業秘密法》第 2、10 條。

其中 NIST、SEMI 為技術及產業標準，《營業秘密法》則具有法律效力。

### 2. 美國矽谷科技產業

假設一家 SaaS 公司的管理員帳號遭到入侵，攻擊者可能接觸客戶資料。

SOC 負責偵測與分析；Incident Commander 協調工程、法務、客戶服務及管理階層；BCP 確保重要產品功能持續運作。

在治理上，SLA 約束服務承諾，NDA 管理供應商取得的機密資訊，AUP 則規範內部管理員及開發人員的系統使用。

技術上可以引用 NIST SP 800-61 Rev. 3、NIST SP 800-53、OWASP Logging Cheat Sheet 及 MITRE ATT&CK T1078。

## 十三、如果真正建立一套 SOC × BCP 系統，需要哪些交付物？

學到這裡，已經可以把 CEH 觀念轉換成一個小型專案。

| 交付物                       | 最小必要內容            | 驗收重點          |
| ------------------------- | ----------------- | ------------- |
| SOC Alert Triage Playbook | 告警來源、查核方式、分流及升級條件 | 能正確處理典型告警     |
| Incident Response RACI    | 決策、執行、諮詢與知會責任     | 重大事件不會出現指揮權混亂 |
| Threat Hunting Plan       | 假說、資料來源、分析及限制     | 可重複執行並留下證據    |
| BCP / DRP                 | 關鍵業務、替代措施、RTO、RPO | 完成演練並驗證目標     |
| SLA                       | 服務範圍、指標、計算、責任及補救  | 能客觀判定是否達標     |
| NDA                       | 機密資訊、用途、接受方、期限及例外 | 資訊處理責任明確      |
| AUP                       | 允許用途、禁止行為及接受確認    | 政策可執行、可驗證     |

工程上，這些文件應形成一個相互連結的控制系統。

例如，SOC 發現供應商管理帳號遭濫用，就應能從事件應變計畫找到升級程序，從 SLA 找到供應商的配合責任，從 BCP 找到替代服務方案，從 NDA 確認資料處理限制，並從 AUP 確認是否存在使用政策違規。

這樣才能把資訊安全從孤立工具整合成企業的實際運作能力。

## 十五、理解檢查：整合 C30–C38 的實務案例

這次不只測試名詞，而是讓你扮演跨國資安事件應變協調者。

### 情境：半導體製造商與金融服務供應鏈遭受攻擊

臺灣一家半導體設備製造商使用美國矽谷公司的 SaaS 平台管理設備維修紀錄，同時使用臺灣某銀行的金融服務。

凌晨 02:00，發生以下事件：

事件 A： SOC 偵測到供應商維護帳號在異常地點登入，並出現非預期的資料存取。

事件 B： Tier 1 無法確認帳號是否遭入侵。進階分析人員進一步發現帳號曾從未核准的設備登入。

事件 C： 資安團隊建議立即隔離設備管理伺服器，但製造部門擔心隔離造成生產中斷。

事件 D： 美國 SaaS 平台隨後停止提供服務，造成臺灣半導體公司無法取得必要維修資訊。

事件 E： 供應商主張其 SLA 只保證每月 99.9% 可用率，並未承諾任何特定復原時間。

事件 F： 調查發現某位員工曾將機密設備紀錄複製至未經核准的私人雲端帳號。

請回答：

1\. SOC 與事件判定： 事件 A、B 應由 Tier 1 和 Tier 3 分別進行哪些工作？需要哪些證據才能決定是否宣告資安事件？

2\. 事件指揮與權限： 事件 C 應由誰協調決策？SOC Manager、Incident Commander、製造主管與法遵人員各自負責什麼？

3\. 營運持續： 針對事件 D，如何建立 BIA、RTO、RPO 及替代業務程序？哪些控制必須透過實際演練驗證？

4\. 契約治理： 事件 E 中，SLA 的月可用率與 RTO 為什麼不能直接畫上等號？若你是採購方，會要求補強哪些服務承諾？

5\. 保密與可接受使用： 事件 F 主要涉及 NDA、AUP 中的哪些不同義務？又可能與臺灣《營業秘密法》的哪些要件有關？

6\. 監理與供應鏈： 如果這套系統也影響臺灣銀行的重要業務，銀行應如何運用金管會的內控制度規定，以及銀行公會的資訊安全與供應鏈規範，建立事件通報、供應商監督與營運持續程序？

這六題能檢查你是否把 SOC 分工、事件指揮、營運持續、服務承諾、資訊保密及使用政策整合成完整的安全治理能力。

本單元最重要的結論：資安事件的成熟處理方式，是由可靠的偵測開始，經過明確的責任與決策流程，維持必要業務，最後透過證據、制度與契約完成改善。
