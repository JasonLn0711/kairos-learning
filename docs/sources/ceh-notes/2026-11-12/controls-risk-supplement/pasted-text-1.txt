# CEH M01｜C17–C24：安全控制與資料清理

CEH v13 · M01-06 安全控制與縱深防禦 · 8 個核心觀念

## 核心結論：資訊安全不是裝了多少防護工具，而是能否有效控制風險，並在資料生命週期結束時確實消除暴露風險

這一單元有兩個核心問題：

第一，如何保護仍在使用的系統與資料？ 我們需要理解 Security Controls（安全控制），包括實體控制、技術控制、防火牆、防毒軟體與加密。

第二，當資料不再需要時，如何確保資料不會被還原？ 這涉及 Media Sanitization（媒體資料清理）、Purge、一般檔案刪除、儲存媒體回收及資料保存政策。

這兩個問題其實是同一件事的不同階段：

資料正在使用

防止未授權存取、竄改與服務中斷

資料進入儲存、備份與封存階段

控制誰可以存取、如何保存、保存多久

資料或設備到達生命週期終點

選擇 Clear、Purge、Destroy 等適當處置

驗證清理結果並保存證據

確保後續再利用、報廢或委外回收符合風險要求

特別重要的是，NIST 已於 2025 年 9 月 26 日正式發布 SP 800-88 Revision 2，取代 2014 年的 Revision 1。新版更重視企業整體媒體清理制度、清理方法的可信度及驗證，而不是只教你操作某種刪除工具。

[image](https://www.google.com/s2/favicons?domain=https://csrc.nist.gov\&sz=32)

因此，本次教學將保留 CEH 題目中的術語，同時使用現行 NIST 標準解釋它們的真正技術意義。

## 二、C17｜Security Controls：安全控制到底是什麼？

### 1. 白話理解：控制風險，而不是消滅所有風險

假設你負責一座先進晶圓廠的資安管理。

公司擔心三件事：

- 外部攻擊者從網路入侵製造管理系統。
- 未授權人員進入設備機房。
- 報廢硬碟中的製程資料被第三方還原。

你會怎麼辦？

對第一件事，可以設置防火牆、網路區隔及存取控制；第二件事需要門禁與保全；第三件事則需要資料清理及報廢管理。

這些都是 Security Controls（安全控制）。

它們不一定是軟體，也可能是人員、政策、設備、工作流程或技術機制。

NIST SP 800-53 Rev. 5 的安全控制目錄包括 Access Control（AC）、Physical and Environmental Protection（PE）、System and Communications Protection（SC）、Media Protection（MP）等控制家族。其維護版本已更新至 Release 5.2.0。

[image](https://www.google.com/s2/favicons?domain=https://csrc.nist.gov\&sz=32)

csrc.nist.gov



### 2. 安全控制必須同時理解三個分類維度

這是本章第一個核心觀念。

維度 A：控制如何實施？

Administrative

政策、制度、人員與程序

Technical

軟體、系統、網路與密碼學

Physical

門禁、保全、機房與實體設備

維度 B：控制發揮什麼作用？

Preventive

預防：降低事件發生機會

Detective

偵測：發現事件或異常

Corrective

矯正：修正已發現的問題

Recovery

復原：恢復必要能力

Deterrent

嚇阻：降低行為動機

Compensating

補償：替代或補足其他控制

維度 C：控制要保護什麼？

Confidentiality（機密性）、Integrity（完整性）、Availability（可用性），以及適用情境下的身分、可追溯性和隱私等要求。

注意：這些維度可以交叉組合，並不是三套互相排斥的分類。一個控制也可能同時具有預防、偵測和其他作用。

### 3. 一個控制可以擁有多種功能

| 控制措施               | 實施形式                       | 主要作用                 |
| ------------------ | -------------------------- | -------------------- |
| Security Guard     | Physical                   | 預防、嚇阻、觀察異常           |
| Firewall           | Technical                  | 預防、監控流量              |
| Antivirus / EDR    | Technical                  | 預防、偵測、隔離             |
| Encryption         | Technical                  | 保護資料機密性；搭配適當模式可驗證完整性 |
| Security Policy    | Administrative             | 建立安全規則與責任            |
| Backup             | Technical + Administrative | 支援復原                 |
| Media Sanitization | 依清理技術而定                    | 防止殘留資料外洩             |

最後一列很重要。安全控制要依據實際機制分類。

使用加密清除金鑰，是邏輯／技術操作；將儲存晶片實體粉碎，則屬實體處置。兩者都可能用於媒體資料清理，但不代表使用相同的控制形式。

### 4. Defense in Depth：為什麼需要多層控制？

假設半導體公司只部署了防火牆。

如果內部員工直接將機密資料複製到隨身碟，防火牆可能根本看不到這個行為。

再假設公司只有機房保全。

如果攻擊者透過合法開放的 HTTPS 服務利用 API 弱點，保全也無法直接阻止。

所以，我們需要縱深防禦（Defense in Depth）。

實體環境與資產控制

網路區隔與流量控制

端點與身分保護

關鍵資料與系統

加密、授權、備份、完整性保護

概念示意：多層防禦旨在避免單一控制失效就造成不可接受的後果；各控制仍須分別驗證有效性。

C17 核心： 分類安全控制時，先問它如何實施，再問它如何發揮作用，最後問它保護哪一項安全目標。

## 三、C18｜Physical Controls：為什麼保全人員是資訊安全控制？

### 1. 網路再安全，實體資產仍可能遭到接觸

假設一家銀行擁有非常安全的資料庫。

系統有防火牆、加密及多因素驗證。

但機房門沒有上鎖，外部訪客可以直接進入，拿走備份媒體或接觸伺服器。

這時問題不是缺少加密演算法，而是缺少 Physical Controls。

實體安全控制就是透過人員、設施與實體機制，防止未經授權的人接觸重要資產。

### 2. 為什麼 Security Guard 屬於 Physical Control？

保全人員透過現場身分確認、巡邏、監控與進出管制，限制實體空間的存取。

NIST SP 800-53 Rev. 5 的 PE-3（Physical Access Control）明確將 guards 納入設施進出控制的實施方式；PE-6（Monitoring Physical Access）則規範實體存取監控與事件回應。

[image](https://www.google.com/s2/favicons?domain=https://csf.tools\&sz=32)

CSF Tools+1



注意：保全人員當然也是「人員」，但在此分類中，他執行的主要控制是實體安全，而不是 Administrative Control。

這是 CEH 非常容易考的概念。

### 3. 臺灣半導體實務：機房與製造設備區域

假設某晶圓廠有三種空間：

| 區域      | 主要資產          | 適合的實體控制                |
| ------- | ------------- | ---------------------- |
| 行政辦公區   | 一般企業資訊        | 基本門禁、訪客登記              |
| 研發資料中心  | 晶片設計、研發伺服器    | 限制授權人員、機櫃上鎖、存取紀錄       |
| 製造設備控制區 | 製造控制設備、設備維修介面 | 維修人員授權、設備實體存取管制、現場安全程序 |

這是依據資產風險所設計的示例。

NIST SP 800-82 Rev. 3 強調，OT 系統的安全控制必須考慮實體製程、安全性與可用性之間的關係。

[image](https://www.google.com/s2/favicons?domain=https://csrc.nist.gov\&sz=32)

csrc.nist.gov



因此，在製造設備環境，門禁與緊急疏散設計也必須協調，不能讓資安控制阻礙人員安全。

### 4. 與臺灣金融監理的關係

《金融控股公司及銀行業內部控制及稽核制度實施辦法》第 12 條要求內部控制涵蓋資訊管理及客戶資料保密，第 25 條要求資訊安全制度維持機密性、完整性與可用性。

[image](https://www.google.com/s2/favicons?domain=https://law.fsc.gov.tw\&sz=32)

law\.fsc.gov.tw



實體門禁、訪客管理與機房保護可以作為金融機構實現這些目標的控制措施，但不能將上述條文解讀成「每一家銀行依法必須採用同一種保全人員配置」。

C18 核心： Security Guard、門禁、圍籬與機櫃鎖，主要屬於 Physical Security Controls；防火牆與加密則屬於 Technical Controls。

## 四、C19｜Firewall：防火牆在保護什麼？

### 1. 防火牆就是網路交通的管制站

假設一座晶圓廠有兩個網路：

- IT Network：企業辦公與一般資訊系統。
- OT Network：製造設備與工廠控制系統。

公司不希望辦公電腦可以任意連線到製造設備。

因此，在兩個網路之間建立防火牆。

IT Network

辦公端點

Firewall

流量規則

OT Network

製造設備

經核准的管理服務連線

Allow

未授權的直接設備連線

Deny

防火牆會依照規則與流量特徵，判斷哪些網路連線允許通過。

常見的判斷資訊包括來源／目的 IP、通訊協定、連接埠及連線狀態。較進階產品還會檢查應用層流量。

NIST SP 800-53 的 SC-7（Boundary Protection）屬於系統邊界防護的重要控制；在 OT 環境可結合 NIST SP 800-82 Rev. 3 進行網路區隔設計。

[image](https://www.google.com/s2/favicons?domain=https://csrc.nist.gov\&sz=32)

csrc.nist.gov+1



### 2. 防火牆不是萬能的

想像美國矽谷一家 SaaS 公司，已經允許使用者透過 HTTPS 存取 API。

攻擊者使用正常網路連線，卻透過 API 的權限驗證缺陷讀取其他使用者的資料。

防火牆可能允許 HTTPS 通過，因為連線本身符合網路政策。

真正的問題在於應用程式的授權邏輯。

因此還需要：

- Network Firewall：保護網路與連線邊界。
- WAF（Web Application Firewall）：檢查 HTTP 請求中的可疑模式。
- Application Authorization：由後端程式檢查使用者對特定資料或功能的權限。

OWASP WSTG 指出，WAF 可以協助阻擋 SQL Injection 或 XSS 等常見攻擊，但對存取控制與業務邏輯問題的保護能力有限。

[image](https://www.google.com/s2/favicons?domain=https://owasp.github.io\&sz=32)

OWASP Foundation



### 3. 工程上如何驗證防火牆？

不能只問：「有沒有裝防火牆？」

應該問：

1. 哪些連線應該被允許？哪些應該被拒絕？
2. 實際規則是否符合最小必要存取？
3. 是否存在可繞過預期網路路徑的連線？
4. 規則是否定期檢查，變更是否留下紀錄？
5. 發現異常連線時，是否有監控與處置機制？

C19 核心：Firewall 是 Technical Control，主要提供網路流量的預防性管制，也可以提供監控與紀錄；它不能取代應用程式內部授權。

## 五、C20｜Antivirus：防毒軟體究竟如何知道程式有問題？

### 1. 防毒不是只有比對病毒名稱

假設半導體設備維修人員將一個 USB 裝置接到維修電腦。

USB 裡有一個看似正常的工具程式，但實際上包含惡意程式。

防毒軟體可能透過數種方式發現問題。

| 技術                   | 白話解釋           | 局限             |
| -------------------- | -------------- | -------------- |
| Signature-based      | 比對已知惡意程式特徵     | 未知變種可能沒有相符特徵   |
| Heuristic            | 分析可疑程式結構或行為特徵  | 可能發生誤判         |
| Behavioral Detection | 觀察執行時的可疑行為     | 惡意行為可能已部分發生    |
| EDR                  | 蒐集端點活動、調查並回應事件 | 需要正確部署、權限與持續監控 |

這些機制可能共存於同一產品。

NIST SP 800-53 的 SI-3（Malicious Code Protection）是惡意程式防護的對應控制。

[image](https://www.google.com/s2/favicons?domain=https://csrc.nist.gov\&sz=32)

csrc.nist.gov



### 2. 半導體產業的特殊需求：安全更新可能影響設備

一般員工電腦可能採用較頻繁的安全更新。

但如果一台製造設備使用經過高度驗證的控制軟體，更新端點防護元件可能影響設備驅動程式、效能或可用性。

因此，不能把一般辦公電腦的更新方法，毫無調整地套用在所有製造設備上。

SEMI 產業標準：

SEMI E187《Specification for Cybersecurity of Fab Equipment》建立半導體製造設備的基礎資安要求，包含作業系統、網路安全、端點防護與日誌等面向。

SEMI E188《Specification for Malware Free Equipment Integration》則專注於設備交付與支援過程中，降低惡意程式進入製造環境或傳播的風險。

[image](https://www.google.com/s2/favicons?domain=https://www.semi.org\&sz=32)

SEMI+1



兩者的定位不同：E187 側重設備資安基線，E188 側重設備整合與支援過程的惡意程式傳播防範。

值得注意的是，SEMI 於 2026 年公布了 E187 分級安全架構的重大修訂方向；該修訂計畫不能直接視為所有現有設備都已適用的新規定。

[image](https://www.google.com/s2/favicons?domain=https://www.semi.org\&sz=32)

SEMI



### 3. 防毒不是資料清理工具

這一點要和 C22–C24 連起來理解。

假設銀行有一台準備報廢的伺服器，已安裝最新版本防毒軟體，也沒有檢出病毒。

這並不代表伺服器中的客戶資料已經安全清除。

因為：

Antivirus 管理惡意程式風險；Media Sanitization 管理殘留資料的機密性風險。

前者不能取代後者。

C20 核心：防毒軟體屬 Technical Control，可能具有預防、偵測及部分回應功能；即使沒有檢出惡意程式，也不代表系統不存在其他安全風險。

## 六、C21｜Encryption：加密能解決什麼？又不能解決什麼？

### 1. 加密的目的，是讓未持有必要金鑰者難以理解資料

假設一家矽谷科技公司在雲端儲存客戶的重要商業資料。

資料若以明文儲存，儲存設備遭到未授權存取時，內容可能直接暴露。

若使用適當的加密設計，未持有解密金鑰者即使取得密文，也難以還原內容。

最基本的加密模型：

\\[ C = E_K(P) \\]

\\[ P = D_K(C) \\]

其中：

- \\(P\\)：Plaintext（明文）。
- \\(C\\)：Ciphertext（密文）。
- \\(K\\)：加密與解密所需的金鑰（對稱加密）。
- \\(E\\)、\\(D\\)：加密及解密演算法。

### 2. 加密主要保護機密性，但可以結合完整性保護

這是另一個容易誤解的地方。

如果只使用不提供驗證能力的加密模式，加密本身不一定能防止攻擊者不被察覺地修改密文。

現代系統常採用 Authenticated Encryption with Associated Data（AEAD），例如 AES-GCM。

AEAD 可以同時提供機密性與資料完整性驗證；但它不會自動解決業務授權、金鑰遭竊或使用者身分歸屬等問題。

OWASP《Cryptographic Storage Cheat Sheet》建議使用成熟的密碼學函式庫、適當演算法及安全的金鑰管理方法，而不是自行發明加密機制。

[image](https://www.google.com/s2/favicons?domain=https://cheatsheetseries.owasp.org\&sz=32)

OWASP Cheat Sheet Series



### 3. 三種資料狀態，需要不同的保護設計

| 資料狀態 | 英文              | 常見保護方式                |
| ---- | --------------- | --------------------- |
| 傳輸中  | Data in Transit | TLS                   |
| 儲存中  | Data at Rest    | 磁碟、資料庫或物件層級加密         |
| 使用中  | Data in Use     | 記憶體與執行環境保護；特定情況使用機密運算 |

### 4. 為什麼金鑰管理比想像中重要？

假設半導體公司把客戶設計檔案全部加密，卻把解密金鑰寫在同一台伺服器的公開設定檔中。

攻擊者取得檔案時，也取得金鑰。

結果就是：雖然有加密，卻未必達到預期保護效果。

OWASP 建議依系統設計妥善管理金鑰產生、儲存、輪替、停用與銷毀，並在適合的架構中將資料加密金鑰（DEK）與金鑰加密金鑰（KEK）分層管理。

[image](https://www.google.com/s2/favicons?domain=https://cheatsheetseries.owasp.org\&sz=32)

更深一層的問題是：

如果資料已經加密，那麼刪掉解密金鑰，是不是就等同於清除資料？

這正是下一個 C22 的核心。答案取決於金鑰、加密實作、資料副本及媒體清理條件，不能只根據「有加密」就作出判斷。

## 七、C22｜Purge：真正的資料清理是什麼？

這是整個 C17–C24 中，技術細節最值得深入理解的部分。

### 1. 白話理解：看不到資料，不代表資料不存在

假設臺灣半導體公司準備將一台使用五年的伺服器轉交設備回收商。

IT 人員說：

「我已經把硬碟格式化，所有檔案都不見了。」

這是否代表硬碟已經安全？

不一定。

因為檔案是否出現在作業系統中，以及儲存媒體是否還留有可還原的資料，是兩件不同的事。

我們真正要考慮的是：

> 假設下一位持有這個儲存媒體的人具有專業鑑識設備、時間與技術能力，他是否仍能還原原本的機密資料？

這是 Media Sanitization 要處理的問題。

### 2. NIST SP 800-88 Rev. 2：Clear、Purge、Destroy 三種方法

NIST SP 800-88 Rev. 2 第 3.1 節正式定義三種資料清理方法。

[image](https://www.google.com/s2/favicons?domain=https://nvlpubs.nist.gov\&sz=32)

NIST Publications



Clear（一般清除）

§3.1.1

目標：抵抗簡單、非侵入式的資料復原

針對使用者可存取的儲存區域，採用適當的邏輯清理技術。

例：對適合的媒體，透過標準讀寫介面覆寫使用者可定址的資料區域

Purge（進階清除）

§3.1.2

目標：使先進實驗室復原技術也無法可行地還原目標資料

使用適合媒體的邏輯或實體技術，並保留媒體可能再次使用的能力。

例：符合條件的裝置清理指令、Cryptographic Erase

Destroy（銷毀）

§3.1.3

目標：使資料無法以先進實驗室技術可行地復原，並讓媒體失去儲存功能

使用符合媒體特性的實體破壞程序。

例：適當規格的媒體粉碎、解體或其他核准的銷毀技術

| 比較       | Clear     | Purge       | Destroy    |
| -------- | --------- | ----------- | ---------- |
| 主要防護目標   | 一般非侵入式復原  | 先進實驗室復原     | 先進實驗室復原    |
| 媒體可否再利用  | 通常可以      | 可能可以        | 不可以        |
| 是否只能使用軟體 | 主要為邏輯清理   | 可採邏輯或實體技術   | 實體銷毀       |
| 適用前提     | 儲存媒體及風險適合 | 技術能達到較高保護程度 | 清理結果符合銷毀要求 |

這裡的差別是威脅模型與可達成的清理保證，不是簡單地比較「覆寫一次、三次或七次」。

新版 NIST 特別要求清理技術與實際媒體特性相符，並參照 IEEE 2883、相關 NSA 規格或組織核准的標準。

NIST



### 3. 為什麼 Purge 不能理解成數學上的「永遠不可能復原」？

你的 CEH 附件特別標示了這個疑義。

原始題目使用 impossible even with laboratory-grade tools 這類過於絕對的語句，但標準中的概念是：在指定的技術與資源條件下，使復原資料不可行。

CEH-Day01-A-2026-11-12(1).md



這裡應區分：

- Logical impossibility： 邏輯上根本不可能。
- Computational infeasibility： 在實際可用的時間、資源與技術能力下，無法可行地完成。
- Operational assurance： 依照可信程序執行，並具有足夠證據支持清理結果。

NIST 採用的是風險與能力導向的判準，不是宣稱任何媒體都能取得不受未來技術影響的絕對保證。

### 4. 為什麼傳統覆寫方法不適合直接套用在所有 SSD？

先了解 HDD 與 SSD 的差異。

傳統 HDD 主要透過磁性方式儲存資料。

SSD 則使用快閃記憶體，並透過控制器管理實際資料位置、磨耗平均化（Wear Leveling）及備用儲存區域（Overprovisioning）。

因此，當作業系統要求寫入某個邏輯位址時，SSD 控制器可能把資料寫到另一個實體位置，而不是直接覆蓋原本的儲存單元。

SSD 邏輯位址與實體儲存位置

邏輯位址映射至實體快閃記憶體

Page A

舊資料可能尚未被實體抹除

概念示意：實際行為取決於 SSD 控制器、韌體和儲存技術；不代表每次覆寫都會產生完全相同的結果。

NIST SP 800-88 Rev. 2 §3.1.1 明確指出，SSD 的備用儲存單元與 Wear Leveling，可能使一般覆寫方式無法觸及所有曾儲存敏感資訊的實體區域。

[image](https://www.google.com/s2/favicons?domain=https://nvlpubs.nist.gov\&sz=32)

NIST Publications



所以，在真正的資料清理決策中，不能只依照磁碟容量或覆寫次數選擇方法，而必須考慮儲存媒體的控制器、支援指令、韌體及實際清理保證。

### 5. Cryptographic Erase：只要讓金鑰失效，就可以安全清理嗎？

這是一個非常重要的概念。

假設你有一台使用可信全碟加密的 SSD。

所有敏感資料都在寫入媒體前加密，對應金鑰受到適當保護。

當需要清理資料時，可以在符合條件的情況下，透過安全清除必要金鑰的方式，使媒體上的密文無法再被解密。

這就是 Cryptographic Erase（CE，加密清除）。

但它至少必須滿足以下條件：

1. 目標敏感資料沒有先前以未加密形式殘留於該媒體。
2. 加密演算法、金鑰產生與實作具有足夠的可信度。
3. 相關金鑰的所有可用副本均受到適當處置。
4. 不存在可重新取得相同解密能力的金鑰備份或託管途徑。
5. 清理程序經過驗證，且其結果足以支持風險判斷。

NIST SP 800-88 Rev. 2 §3.2.2–3.2.4 直接討論上述先決條件，並參照 ISO/IEC 27040 的儲存安全與金鑰管理要求。

[image](https://www.google.com/s2/favicons?domain=https://nvlpubs.nist.gov\&sz=32)

NIST Publications



要特別理解：

Cryptographic Erase 不代表把硬碟中的所有位元都變成零。

它的保護依據是：原有密文仍可能存在，但組織已確實消除取得必要解密能力的可行途徑。

如果原始資料曾經以明文存放，或金鑰在其他地方仍能取得，就不能只根據一個「刪除金鑰成功」訊息，斷言資料清理已經完成。

## 八、C23｜File Deletion：為什麼刪除檔案不等於清理資料？

### 1. 檔案系統不是單純把資料放在資料夾裡

想像一家圖書館。

一本書放在第 5 排第 20 格，而圖書館的目錄記錄了這本書的位置。

如果管理員將目錄紀錄刪除：

「系統現在查不到這本書。」

但實體書籍是否仍然放在架上？

可能仍然存在。

很多傳統檔案系統的刪除行為與此相似。

作業系統可能解除檔名與儲存資料之間的參照關係，並將相應空間標記為可重新使用，卻不一定立即覆寫實際資料內容。

MITRE ATT&CK 的 T1485（Data Destruction）也指出，常見的 `rm`、`del` 等檔案刪除指令，往往只是移除檔案參照，而不會確保所有原始資料內容都遭到抹除。

[image](https://www.google.com/s2/favicons?domain=https://attack.mitre.org\&sz=32)

MITRE ATT&CK®



### 2. 必須區分四種不同操作

| 操作                    | 發生什麼事                              | 是否足以證明安全清理                   |
| --------------------- | ---------------------------------- | ---------------------------- |
| Delete File           | 移除檔案系統中的檔案參照或使檔案不可見                | 否                            |
| Quick Format          | 重新初始化部分檔案系統結構                      | 否                            |
| Overwrite             | 嘗試以新資料取代既有儲存內容                     | 需依媒體、介面及清理目標判斷               |
| Approved Sanitization | 使用經核准且適用的 Clear、Purge 或 Destroy 方法 | 尚需 Verification 與 Validation |

這裡還有一個進階細節：現代 SSD 可能透過 TRIM 與背景回收程序，讓被刪除資料在某些情況下難以透過一般介面還原。

但這不是所有 SSD 的固定行為，也不能因此將「刪除檔案」直接等同於經驗證的媒體清理程序。

### 3. 美國矽谷：雲端資料刪除比本機硬碟更複雜

假設一家矽谷 SaaS 公司讓客戶透過網站刪除專案。

客戶按下 Delete 後，資料可能從網站消失。

但它先前可能分散在：

- 主要資料庫。
- Read Replica（讀取複本）。
- Object Storage（物件儲存）。
- Backup（備份）。
- Snapshot（快照）。
- Log（系統日誌）。
- Cache（快取）。

這些是不同的資料實體或副本，不一定同步消失。

因此，雲端資料清理應回答：

「我們究竟刪掉了哪一份資料？是否存在其他副本？各副本何時依法或依政策到期？如何驗證後續處置？」

NIST SP 800-88 Rev. 2 的 Executive Summary 特別指出，現代資料會經過多個組織、系統與儲存媒體，資料清理責任必須涵蓋分散式與雲端環境。

## 九、C24｜Hardware Recycling、Archiving 與 Sanitization：為什麼三者不能混為一談？

這是把 C22、C23 延伸到企業資產管理的最後一個觀念。

### 1. 三個操作的目的根本不同

Recycling（回收） 的主要目的，是將不再使用的設備或材料重新利用。

Archiving（封存／歸檔） 的目的，是在特定期間內保留紀錄，供稽核、業務、法律或研究需要。

Sanitization（資料清理） 的目的，是防止目標資料在媒體處置或再利用過程中遭到不當還原或揭露。

| 項目                 | 核心目的       | 資料是否應繼續保留       |
| ------------------ | ---------- | --------------- |
| Hardware Recycling | 設備或材料再利用   | 不應因回收而不當殘留敏感資料  |
| Data Archiving     | 合法且必要的紀錄保存 | 是，依適用保存期限與政策    |
| Media Sanitization | 消除殘留資料暴露風險 | 清理目標資料不應仍可被不當還原 |

特別注意：封存不是刪除，回收也不是清理。

### 2. 真正的金融監理案例：設備報廢與資產清冊缺失

金管會檢查局公開的《113 年度上半年票券金融公司主要檢查缺失》第 8 頁記載了實際資安缺失類型：

檢查發現部分資訊儲存設備報廢時，沒有實施適當的資料清理或實體破壞；另有從報廢主機拆下的硬碟，安裝到其他主機繼續使用，卻未納入財產清冊。

金管會檢查局要求依內部規範進行適當的清理或銷毀，並對再利用設備妥善保管及列入資產清冊。

[image](https://www.google.com/s2/favicons?domain=https://www.feb.gov.tw\&sz=32)

feb.gov.tw



這裡有兩個不同的控制失效：

- 資料保護失效： 報廢媒體仍可能保存敏感資訊。
- 資產治理失效： 組織無法完整追蹤硬碟的去向與再利用狀態。

這份文件針對的是票券金融公司，屬於金管會公開的檢查缺失與改善指引，不應直接視為所有銀行共通的逐字作業條文；但對金融機構的資訊資產治理極具參考價值。

### 3. 臺灣半導體：舊設備轉售前應做什麼？

假設一家半導體公司準備處分老舊製造設備，設備內包含：

- 設備維護電腦的 SSD。
- 製程參數與操作日誌。
- 控制器的非揮發性記憶體。
- 維修人員儲存的設定與診斷資料。

即使主要 SSD 已清理，也不能直接推定所有設備元件都不再保存敏感資訊。

NIST SP 800-88 Rev. 2 第 4 章特別要求組織識別儲存媒體、資料保護等級、媒體再利用方式及清理需求。附錄 B 亦列出評估儲存設備特性時應注意的問題。

[image](https://www.google.com/s2/favicons?domain=https://nvlpubs.nist.gov\&sz=32)

NIST Publications



而《營業秘密法》第 2 條把合理保密措施列為營業秘密成立的必要要件之一。因此，對可能含有先進製程、配方或設計資訊的媒體，清理和資產管控不只是 IT 例行工作，也有助於維持營業秘密保護制度。

[image](https://www.google.com/s2/favicons?domain=https://law.moj.gov.tw\&sz=32)

Law\.gov.tw



### 4. 最重要的取捨：資料是否應該先保留？

不能因為 Purge 很安全，就對所有舊資料立即執行 Purge。

假設某銀行有一份交易資料，依適用法律或監理規定仍有保存義務。

即使業務部門認為該資料「不再常用」，也不代表可以直接銷毀。

實務上應先確認：

1. 法律與合約是否要求繼續保存？
2. 是否存在稽核、爭議處理或其他合法保存需求？
3. 資料是否已超過適用的保存期限？
4. 是否還有其他複本或備份？
5. 決定清理後，如何留下不包含原始敏感內容的必要證據？

這是資料治理的核心矛盾：

保存太久，會增加資料暴露風險；過早銷毀，則可能違反保存義務，並損害稽核、調查與營運需求。

因此資料生命週期應由資料擁有者、法遵、資安及資產管理職責共同協調，而非由執行刪除指令的人單獨決定。

## 十、實務深化：如何建立可稽核的資料清理程序？

理解 C22–C24 後，我們應該進一步把知識轉換成企業能實際執行的程序。

### 1. 六個階段的資料清理治理模型

階段 1：Identify — 識別資產與資料

確認媒體序號、擁有者、資料類別、敏感度及所有已知資料副本。

階段 2：Authorize — 確認處置權限

確認資料保存期限、法律義務、Legal Hold（法律保留）及核准人員。

階段 3：Select — 選擇清理方法

根據媒體技術、敏感程度、復原威脅及再利用需求，決定 Clear、Purge 或 Destroy。

階段 4：Execute — 執行清理

使用核准工具與程序，記錄操作人員、設備識別資訊及執行結果。

階段 5：Verify / Validate — 驗證結果

先確認操作是否成功完成，再判斷該結果是否符合資料機密性所需的保護程度。

階段 6：Document — 紀錄與結案

保存清理證明、覆核與核准紀錄，決定媒體可否釋出、再使用或報廢。

這個六階段流程是根據 NIST SP 800-88 Rev. 2 第 4 章的 Media Sanitization Program 整理出的實務模型。

[image](https://www.google.com/s2/favicons?domain=https://nvlpubs.nist.gov\&sz=32)

NIST Publications



### 2. Verification 與 Validation 的區別

這是本章進一步深化時最值得掌握的細節。

假設你對一台 SSD 執行資料清理指令。

工具回報：

`Sanitization completed successfully`

這代表什麼？

它只能支持「執行結果已完成」這一層面的判斷，不足以單獨證明清理方法對目標資料已達到所需的保護程度。

NIST SP 800-88 Rev. 2 §4.5 明確區分：

|      | Verification    | Validation          |
| ---- | --------------- | ------------------- |
| 中文   | 操作結果驗證          | 清理有效性確認             |
| 核心問題 | 程序是否成功執行？       | 資料是否達到所需的清理保證？      |
| 主要檢查 | 執行狀態、錯誤、異常、設備狀況 | 結果是否符合資料敏感度、媒體與風險要求 |
| 失敗後  | 調查、重新執行或更換方法    | 拒絕接受結果，補強或提升清理方法    |

例如，拿消磁設備對 SSD 執行操作，設備可能回報操作正常完成，但 SSD 並不依賴磁性儲存資料，因此該操作無法達到預期的清理目標。

這正是 NIST 在 §4.5.2 提出的錯誤清理方法案例。

[image](https://www.google.com/s2/favicons?domain=https://nvlpubs.nist.gov\&sz=32)

NIST Publications



所以，系統顯示 Success，與安全目標真正達成，不是同一個命題。

這也和 C17 的安全控制概念一致：部署控制、執行控制、驗證控制有效性，是三個不同的工程活動。

## 十二、研究深化：安全清理與惡意資料破壞有什麼差別？

這裡可以利用 MITRE ATT&CK 建立另一個重要連結。

MITRE ATT&CK T1485（Data Destruction）描述攻擊者破壞資料，影響系統與服務可用性的技術行為。

T1490（Inhibit System Recovery）則描述攻擊者透過破壞或移除備份、復原機制，阻礙系統恢復運作。

[image](https://www.google.com/s2/favicons?domain=https://attack.mitre.org\&sz=32)

MITRE ATT&CK®+1



兩者與 Media Sanitization 看起來都可能涉及資料刪除，但目的相反：

|      | 合法資料清理        | 惡意資料破壞         |
| ---- | ------------- | -------------- |
| 目標   | 防止不再需要的敏感資料外洩 | 破壞資料或系統可用性     |
| 授權   | 經適當權責核准       | 通常沒有有效授權       |
| 範圍   | 明確指定資料與媒體     | 攻擊者選擇的破壞目標     |
| 證據   | 清理及覆核紀錄       | 需透過事件調查建立      |
| 系統結果 | 達成預期的資料生命週期處置 | 可能導致非預期資料損失與中斷 |

這說明：不能僅從指令或工具名稱判斷一項操作的安全性質，還必須分析其授權、目的、執行脈絡與造成的結果。

## 十三、這八個觀念應該如何記憶？

建議用以下八個核心問題，取代死背名詞。

| 觀念                        | 一句話記憶                 |
| ------------------------- | --------------------- |
| C17 Security Controls     | 控制如何實施、發揮什麼功能、保護什麼目標？ |
| C18 Physical Controls     | 如何防止未授權者實體接觸資產？       |
| C19 Firewall              | 哪些網路連線應該允許或拒絕？        |
| C20 Antivirus             | 如何預防、偵測與處理惡意程式？       |
| C21 Encryption            | 如何使未持有必要金鑰者難以理解資料？    |
| C22 Purge                 | 如何使先進資料復原方法不可行？       |
| C23 File Deletion         | 刪除檔案參照是否真的移除了資料？      |
| C24 Recycling / Archiving | 資料應保留、清理，還是設備應報廢回收？   |

這八項又可以濃縮成兩個思考軸線：

控制正在使用的資產：C17–C21。控制資料生命週期終點：C22–C24。

## 十四、理解檢查：整合型實務案例

以下先不公布答案。請試著用本章概念及規範依據獨立推理。

### 案例：半導體企業的設備退役與銀行資料安全

一家臺灣半導體設備供應商，準備淘汰一批工廠伺服器，並將其中可用的 SSD 交給外部設備商回收。

同時，該企業使用一家美國矽谷公司的 SaaS 平台保存維修紀錄，並向臺灣銀行申請設備融資。

企業資安主管發現下列情況：

A. 工廠機房已經配置防火牆與防毒軟體，但是沒有進出管制，任何員工都可以接觸伺服器。

B. 某伺服器 SSD 已經快速格式化，IT 人員認為裡面的客戶機密資料已經完全消失。

C. 另一台 SSD 使用全碟加密，但企業無法確認解密金鑰是否還有備份。

D. SaaS 供應商已從正式資料庫刪除企業的維修資料，但仍可能存在備份及快照。

E. 外部回收商提供一份清理完成報告，內容只有「清除成功」，沒有設備序號、清理方法、執行結果或覆核紀錄。

請回答：

1\. 安全控制分類： A 缺少哪一類控制？應該怎麼補強？為什麼防火牆與防毒無法替代？

2\. 資料清理方法： B 的快速格式化與 NIST 的 Clear、Purge 有什麼差別？若要再利用 SSD，應如何選擇清理方法？

3\. 加密清除： 對 C 而言，使用 Cryptographic Erase 前必須先驗證哪些條件？為什麼金鑰備份會改變結論？

4\. 資料生命週期： 對 D 而言，如何同時處理資料清理要求、必要保存期限與分散式備份？

5\. 稽核與證據： 對 E 而言，應補齊哪些證據才能支持 Verification 與 Validation？應援引 NIST SP 800-88 Rev. 2 哪些章節？

6\. 產業規範： 如果你要向臺灣半導體客戶、美國 SaaS 業者及金管會監理下的銀行說明這套制度，應分別援引哪些法律、標準或監理依據？它們哪些具有法律約束力，哪些屬於技術標準或企業政策？

完成這六題後，便能檢查自己是否真正掌握 C17–C24 的分類、控制機制、儲存技術、治理程序與產業適用性，而不是僅能辨認 CEH 選項中的名詞。
