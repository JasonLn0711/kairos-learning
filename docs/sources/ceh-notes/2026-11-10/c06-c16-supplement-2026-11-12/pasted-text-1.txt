# CEH M01｜C06–C16：倫理駭客、授權與交戰規則（ROE）

CEH v13 · M01-03 · 11 個核心觀念 · 法律、標準、攻擊技術與實務治理

## 核心結論：駭客與倫理駭客的區別，不在使用什麼工具，而在是否取得有效授權、遵守測試邊界，以及如何處理測試結果

同一個人使用同一套工具、執行相同的漏洞驗證方法，在不同的授權條件、行為目的與執行方式下，可能構成正當安全測試，也可能構成違反規範甚至觸法的行為。

我們要理解的並非單純的「白帽好、黑帽壞」，而是一套能讓安全測試具有可授權性、可控制性、可驗證性與可問責性的治理架構。

先把五個重要原則記住：

1. Authorization（授權）： 誰有權允許測試？允許誰測試？
2. Scope（範圍）： 允許測試哪些資產、系統與資料？
3. ROE（Rules of Engagement）： 可以採取哪些行為、何時測試、何時必須停止？
4. Evidence（證據）： 如何證明漏洞確實存在，且測試過程受到控制？
5. Remediation（改善）： 如何將發現轉化為安全修補、風險降低和再次驗證？

這套思路以 NIST SP 800-115《Technical Guide to Information Security Testing and Assessment》的規劃、測試、評估與報告要求為基礎，並結合 OWASP、MITRE ATT&CK 及臺美產業規範。

## 二、C06｜Ethical Hacking：為什麼需要倫理駭客？

### 1. 從攻擊者的角度，驗證防禦系統是否有效

想像你負責半導體公司的資訊安全。

公司已經購買防火牆、端點防護系統、身分驗證服務，也建立了數十項安全政策。

管理階層問你：

「我們到底安全嗎？」

你可能回答：

「我們有防火牆，有多因素驗證，也符合資訊安全政策。」

但是，這並不能充分證明系統能抵抗真實攻擊。

原因是：

控制措施存在，不等於控制措施有效。

例如，系統雖然要求登入，但工程師可能仍能透過 API 取得其他客戶的機密設計檔案。

這就是倫理駭客要解決的問題。

Ethical Hacking 是在經過適當授權與控制的條件下，使用攻擊者可能採取的技術，尋找並驗證安全弱點，以改善組織的防禦能力。

### 2. 三種不同的安全工作

| 工作類型                           | 核心問題              | 典型方法           |
| ------------------------------ | ----------------- | -------------- |
| Security Audit（安全稽核）           | 是否遵守指定政策與要求？      | 文件、控制與執行證據檢查   |
| Vulnerability Assessment（弱點評估） | 哪些地方可能有弱點？        | 設定檢查、弱點掃描與分析   |
| Penetration Testing（滲透測試）      | 弱點能否被實際利用，造成什麼影響？ | 受控的漏洞利用驗證與風險分析 |

三者有重疊，但不能互相取代。

NIST SP 800-115 第 5 章區分弱點識別與滲透測試，指出滲透測試可進一步驗證弱點的可利用性。

### 3. 如何使用 OWASP 與 MITRE ATT&CK？

假設半導體平台有一個 API：

`GET /api/designs/1234`

研究人員懷疑，使用者修改檔案 ID 後，可能存取其他客戶的設計資料。

我們可以分別使用兩種知識體系。

OWASP：告訴我們應驗證什麼安全控制。

OWASP API Security Top 10 2023 的 API1：Broken Object Level Authorization（BOLA），就是典型的物件層級授權失效。

其核心要求是：當 API 使用物件識別碼存取資料時，必須驗證當前使用者是否有權對該物件執行指定操作。

[image](https://www.google.com/s2/favicons?domain=https://api-security.owasp.org\&sz=32)

OWASP API Security Top 10



MITRE ATT&CK：幫助我們理解真實攻擊者如何行動。

例如，T1190「Exploit Public-Facing Application」描述攻擊者利用對外服務弱點取得初始存取的技術。

[image](https://www.google.com/s2/favicons?domain=https://attack.mitre.org\&sz=32)

MITRE ATT&CK®



兩者關注點不同：

OWASP

從應用程式弱點與安全控制出發

要測什麼？如何驗證與改善？

MITRE ATT&CK

從已知攻擊者行為出發

攻擊者如何行動？防禦能否偵測？

NIST SP 800-115 則補上測試活動的規劃、執行、證據與報告方法。

C06 的重點：倫理駭客的成果不是「成功入侵了多少系統」，而是為組織建立多少可信、可採取行動的安全證據。

## 三、C07｜Authorization：授權到底是什麼？

### 1. 有公司委託，不代表可以測試公司所有系統

回到半導體案例。

假設委託書只寫：

「請協助進行資訊安全滲透測試。」

這句話可以證明雙方有合作意願，但對實際測試而言，資訊仍然不足。

例如，研究人員可能不知道：

- 是否可以測試正式生產環境？
- 是否包括雲端服務商管理的基礎設施？
- 是否允許觸碰其他客戶的資料？
- 是否能嘗試修改製程設備參數？
- 是否允許執行可能中斷服務的測試？

因此，專業測試不只需要取得授權，還需要把授權轉化為明確的操作權限。

NIST 對 ROE 的定義指出，交戰規則應在測試開始前建立，並授權測試團隊執行其中明定的活動。

[image](https://www.google.com/s2/favicons?domain=https://csrc.nist.gov\&sz=32)

CSRC



### 2. Authorization 有兩種不同的意思

這是進階學習時必須區分的地方。

| 概念   | 英文                    | 解釋                         |
| ---- | --------------------- | -------------------------- |
| 測試授權 | Authorization to Test | 資產擁有者或適當權責人，允許研究人員執行特定安全測試 |
| 存取授權 | Access Authorization  | 系統允許使用者存取哪些資料與功能           |

例如，研究人員得到半導體公司授權，測試客戶資料平台是否存在存取控制問題。

他的測試授權是有效的，但測試目的正是驗證系統內的存取授權是否能被繞過。

OWASP WSTG-ATHZ-02 專門處理存取授權繞過測試，包括同權限使用者之間的水平越權，以及不同權限角色之間的垂直越權。

[image](https://www.google.com/s2/favicons?domain=https://wstg.owasp.org\&sz=32)

OWASP Web Security Testing Guide



### 3. 臺灣與美國法律如何看待未經授權的存取？

中華民國：《刑法》第 358–360 條

第 358 條處理無故以帳密、破解保護措施或利用系統漏洞入侵他人電腦的行為。第 359 條涉及無故取得、刪除或變更他人電磁紀錄而致生損害；第 360 條涉及以電腦程式或其他電磁方式干擾他人電腦而致生損害。

不同條文具有不同構成要件，實際行為須分別判斷。

[image](https://www.google.com/s2/favicons?domain=https://law.moj.gov.tw\&sz=32)

Law\.gov.tw



美國：Computer Fraud and Abuse Act（CFAA），18 U.S.C. §1030

CFAA 第 (a)(2) 項涵蓋特定未經授權或超越授權的電腦存取並取得資訊的行為；第 (a)(5) 項則涉及特定未經授權造成電腦損害的行為。

[image](https://www.google.com/s2/favicons?domain=https://uscode.house.gov\&sz=32)

U.S. Code



美國司法部 2022 年修訂的 CFAA 起訴政策，對符合定義的善意安全研究設有不起訴方向，但它是聯邦檢察機關的起訴政策，並非授予研究者無限制測試權。

### 4. 為什麼要書面授權？

書面文件可以確定授權者、測試者、目標、期限、允許活動及責任分工。

常見文件包括授權書（Authorization Letter）、工作說明書（Statement of Work, SOW）、交戰規則（ROE）及保密協議（NDA）。

這些文件功能不同：NDA 處理保密義務，SOW 處理交付範圍，ROE 處理測試操作，而適當的書面授權則建立明確的測試許可。

C07 最重要的一句話：有權委託測試的人，必須對被測資產具有相應的授權權限；有權測試一項資產，不代表有權測試與它連接的所有資產。

## 四、C08｜Scope 與 Rules of Engagement：把授權落實成可執行規則

### 1. Scope 是「測試邊界」，ROE 是「執行規則」

假設某銀行只授權測試網路銀行的測試環境。

這就是 Scope。

但研究人員還需要知道：

「可以在幾點測？每秒最多多少請求？能不能進行權限提升驗證？如果系統異常，誰有權要求停止？」

這些屬於 ROE。

在 NIST SP 800-115 的架構中，ROE 可以同時包含範圍與操作規則；這裡把 Scope 單獨區分，是為了讓學習與管理更清楚。

### 2. 一份專業 ROE 的六大控制面向

依據 NIST SP 800-115 Appendix B，原始範本涵蓋目的、範圍、風險、測試人員、時間、通訊、目標系統、允許／禁止行為、資料處理、報告及簽署等項目。以下將其整理成六大實務控制面向。

[image](https://www.google.com/s2/favicons?domain=https://nvlpubs.nist.gov\&sz=32)

NIST Publications



| 控制面向       | 需要明確約定的內容                  |
| ---------- | -------------------------- |
| 1. 授權與責任   | 授權者、測試團隊、權責主管、簽署與有效期限      |
| 2. 資產與範圍   | 允許及排除的網域、IP、API、雲端帳號、資料與設備 |
| 3. 測試行為    | 可用工具、攻擊驗證方式、禁止操作與操作限制      |
| 4. 時間與安全限制 | 測試時段、負載限制、停止條件、恢復程序        |
| 5. 通報與應變   | SOC、系統負責人、緊急聯絡及事件升級程序      |
| 6. 證據與交付   | 日誌、敏感資料處理、漏洞報告、修補及複測       |

### 3. 半導體產業：為什麼不能照一般 IT 方式測試所有設備？

這是非常值得深入研究的案例。

NIST SP 800-82 Rev. 3《Guide to Operational Technology (OT) Security》附錄 C.3.4 記載，一次工業控制系統的 ping sweep（主機探測）曾導致晶片製造系統停止運作，造成約 50,000 美元的晶圓損失。同一節也記錄了工業網路探測造成機械手臂非預期動作的案例。

[image](https://www.google.com/s2/favicons?domain=https://nvlpubs.nist.gov\&sz=32)

NIST Publications



這說明一般 IT 網路中常被視為相對低風險的探測，到了 OT（Operational Technology，營運技術）環境，可能具有完全不同的後果。

同樣是安全測試，風險並不相同

企業 IT 系統

辦公網路、網站、一般應用程式

主要考量：服務可用性、資料安全、系統復原

晶圓廠 OT 系統

製造設備、控制系統、製程網路

額外考量：設備安全、製程穩定、實體損失

產業安全要求取決於實際資產與風險，不代表所有 IT 或 OT 系統都具有相同測試限制。

在臺灣半導體設備安全領域，SEMI E187《Specification for Cybersecurity of Fab Equipment》針對半導體生產設備提出作業系統支援、網路安全、端點防護及安全監控等基本要求。其公開適用範圍主要涉及搭載 Windows 或 Linux 的設備運算裝置，並未涵蓋所有 PLC、SCADA 及相關感測／致動控制裝置。

[image](https://www.google.com/s2/favicons?domain=https://store-dev2.semi.org\&sz=32)

Specification for Cybersecurity of Fab Equipment



臺灣亦已建立以 SEMI E187 為基礎的半導體設備資安查核與驗證制度。

[image](https://www.google.com/s2/favicons?domain=https://www.acw.org.tw\&sz=32)

資安產業跨域聯防推動計畫網站 ACW



將 NIST 800-82 的 OT 風險觀念與 SEMI E187 的設備安全要求結合，專業團隊可以將 ROE 設計為：

生產設備先進行安全影響評估；優先選擇被動監控、離線分析或經驗證的測試環境；正式設備上的主動測試須經額外核准，且具有停止與復原措施。

這是根據上述標準所做的風險導向設計，而不是宣稱 SEMI E187 逐字要求所有設備採用相同測試程序。

C08 的關鍵：ROE 不是行政文件，而是一套控制安全測試行為的操作規則。

## 五、C09–C13｜駭客類型：從名稱分類，進一步理解行為、目的與能力

這五個概念最適合一起學習，因為它們其實在描述不同的分類維度。

### C09｜White Hat：白帽駭客

白帽駭客是經過適當授權，以改善系統安全為目的，並遵守約定測試規則的安全研究或測試人員。

假設一家矽谷科技公司聘請研究人員評估產品的 API 安全。

研究人員取得書面授權，使用公司提供的測試帳號，確認是否存在權限繞過問題，最後提交弱點報告並協助複測。

這是典型的 White Hat Hacking。

判斷重點不在於研究人員有多厲害，而在於其行為是否符合授權、範圍與目的。

實務依據： NIST SP 800-115 第 6–8 章，關注測試規劃、執行、報告及修補活動。

[image](https://www.google.com/s2/favicons?domain=https://www.nist.gov\&sz=32)

NIST



### C10｜Grey Hat：灰帽駭客

灰帽駭客通常指沒有明確惡意目的，卻在未取得授權或未完全遵守測試規則的情況下進行安全探索的人。

例如，某研究人員發現銀行網站可能有弱點。

他沒有取得銀行授權，就進一步存取其他客戶的資料，隨後私下通知銀行：「我幫你們找到漏洞了。」

即使他最初的目的是改善安全，也不會因此自動取得測試權限。

這裡應區分三個命題：

| 命題                  | 是否成立 |
| ------------------- | ---- |
| 想幫助企業改善安全           | 可能成立 |
| 因此已取得該企業的測試授權       | 不成立  |
| 行為是否違法，需要依適用法律與事實判斷 | 成立   |

前面提及的美國 DOJ 2022 年 CFAA 善意研究起訴政策，正好說明「研究動機」、「執行方式」、「起訴政策」與「法律授權」是不同層次。

[image](https://www.google.com/s2/favicons?domain=https://www.justice.gov\&sz=32)

United States Department of Justice



### C11｜Black Hat：黑帽駭客

黑帽駭客通常以未經授權方式入侵系統，並具有竊取、勒索、破壞或其他惡意目的。

例如，攻擊者利用半導體供應鏈入口取得資料，將機密技術文件轉售給第三方。

其核心問題包括未授權存取與不當取得資訊。

在臺灣法律體系中，應依實際行為分別檢視《刑法》第 358–360 條，以及資料符合營業秘密要件時的《營業秘密法》相關規定。

[image](https://www.google.com/s2/favicons?domain=https://law.moj.gov.tw\&sz=32)

Law\.gov.tw+1



### C12｜Blue Hat：藍帽駭客

這個詞需要特別注意，因為在不同資料中並沒有完全一致的定義。

有些資安教材將 Blue Hat 指為受邀協助產品上市前安全測試的外部專家；另一些資料則把它用於具有報復動機的攻擊者。

例如，ESET 的術語資料使用前一種定義，其他產業資料則記錄兩種用法。

[image](https://www.google.com/s2/favicons?domain=https://help.eset.com\&sz=32)

ESET Online Help+1



Microsoft 也有名為 BlueHat 的安全研究交流活動，但不能因此把 BlueHat 會議的參加者，直接等同於某一類具有固定法律或技術身分的駭客。

[image](https://www.google.com/s2/favicons?domain=https://msrc.microsoft.com\&sz=32)

Microsoft



CEH 遇到 Blue Hat 選項時，應結合題幹和指定教材理解，不應單靠顏色做出判斷。

### C13｜Script Kiddie：依賴現成工具的低經驗攻擊者

Script Kiddie 通常指技術理解較有限、主要依賴他人開發工具或程式進行操作的人。

重要的是，技術能力與授權狀態不是同一件事。

一位初學者在經過授權的實驗環境使用 Nmap，可以是在正常學習安全測試；一位資深工程師未經授權入侵系統，仍可能屬於不當行為。

所以 Script Kiddie 主要描述技術能力或使用方式，而不是直接判定是否合法。

### 更精確的分類模型

與其記住帽子的顏色，更重要的是用三個互相獨立的維度理解一個行為：

|              | 有效授權且遵守範圍                      | 未取得有效授權或超出範圍    |
| ------------ | ------------------------------ | --------------- |
| 以改善安全為主要目的   | 典型 White Hat 行為                | 常見 Grey Hat 情境  |
| 以竊取、破壞或勒索為目的 | 若利用測試權限從事未被允許的惡意行為，該行為已不受原授權涵蓋 | 典型 Black Hat 行為 |

技術能力可以再獨立加入分析，不應與這個矩陣混為一談。

這也是為什麼 CEH 要學白帽、灰帽、黑帽，但真正進入企業安全治理時，應用行為、權限、目的與證據描述事實，而不能只用顏色標籤替代分析。

## 六、C14｜Penetration Testing：滲透測試究竟在驗證什麼？

滲透測試不等於單純「試著駭進去」。

它是一個在事先設定的安全條件下，建立可重複的測試過程，驗證系統弱點、分析可能影響、提供改善證據的技術活動。

### 1. 弱點掃描與滲透測試的科學差異

假設弱點掃描工具發現一台網站伺服器使用了有已知漏洞的元件版本。

這是重要線索，但尚不能直接推論攻擊一定成功。

可能的原因包括：系統已套用修補但未更新版本字串、弱點僅存在於特定設定，或攻擊所需的前提條件並不存在。

因此我們需要驗證。

觀察到潛在弱點

掃描、設定分析、原始碼審查

建立可驗證假說

在指定條件下，這個弱點是否可被利用？

受控驗證

使用授權資產與測試資料，採取足以確認弱點的操作

記錄觀察與限制

證據、影響、測試條件、未測試範圍

修補與再次驗證

確認弱點關閉，且正常業務沒有受到破壞

這與科學研究的邏輯非常接近：觀察、假說、實驗、證據、結論，以及可重現性。

但滲透測試還多一項特殊要求：測試本身必須受到風險限制。

### 2. NIST SP 800-115：滲透測試的階段

NIST SP 800-115 第 5.2 節把滲透測試的主要技術工作分成 Planning、Discovery、Attack 與 Reporting；報告工作並非只在最後才開始，而是可以貫穿整個過程。

[image](https://www.google.com/s2/favicons?domain=https://nvlpubs.nist.gov\&sz=32)

NIST Publications



| 階段        | 工作內容           | 主要產出      |
| --------- | -------------- | --------- |
| Planning  | 明定目標、授權、ROE、風險 | 測試計畫與核准   |
| Discovery | 了解系統、服務及可能弱點   | 資產與弱點清單   |
| Attack    | 在核准範圍內驗證可利用性   | 可驗證的影響證據  |
| Reporting | 分析影響、修補優先順序與限制 | 技術報告、改善計畫 |

### 3. 進階案例：驗證半導體設計資料平台的 BOLA

假設我們有兩個由測試團隊控制的帳號：

帳號 A 屬於測試客戶 A；帳號 B 屬於測試客戶 B。

兩者各自擁有一份人工建立、沒有真實營業秘密的設計文件。

我們要驗證：

> 帳號 A 是否可能在未獲授權的情況下，讀取帳號 B 的測試文件？

這是一個明確、可驗證的安全假說。

OWASP WSTG-ATHZ-02 指出，水平越權測試會檢查同一權限層級但不同使用者的資源是否能被彼此存取。

[image](https://www.google.com/s2/favicons?domain=https://wstg.owasp.org\&sz=32)

OWASP Web Security Testing Guide



如果帳號 A 能讀取 B 的測試資料，就能建立弱點證據；不需要再下載所有真實客戶的文件。

還可以提出更深入的驗證問題：伺服器是否在每次存取資料時檢查權限，或只在使用者登入時檢查一次？

這會影響修補方法。

真正的問題可能不在前端頁面，而在後端 API 缺少物件層級授權檢查。

### 4. 如何衡量滲透測試的品質？

對研究與企業交付而言，可以使用下列模型：

\\[ \text{測試價值} \approx \frac{\text{可驗證且可採取行動的安全證據}} {\text{測試成本與造成的附加風險}} \\]

這是協助思考的概念模型，並非 NIST 的官方計算公式。

有價值的報告，應讓工程團隊知道弱點發生的必要條件、實際影響、證據、修補方向與修補後如何複測。

C14 的關鍵：成功的滲透測試不以破壞程度衡量，而以可驗證的風險發現及改善成效衡量。

## 七、C15｜弱點揭露、資訊保密與研究責任

### 1. 找到弱點，不代表可以任意公開

假設研究人員在臺灣半導體公司的系統發現一項重大漏洞。

該漏洞可能讓其他客戶讀取未公開的晶片設計檔案。

研究人員擁有技術發現，不代表擁有客戶文件的處分權或公開權。

因此，漏洞研究必須同時管理兩種資訊：漏洞本身的技術細節，以及測試過程接觸到的敏感資料。

### 2. Coordinated Vulnerability Disclosure（CVD）

CVD 是協調式弱點揭露。

它的基本思路是研究人員向適當的安全窗口回報弱點，讓供應商、研究人員及相關利害關係人協調驗證、修補、通知及公開時機。

OWASP《Vulnerability Disclosure Cheat Sheet》建議研究人員確認測試合法且已授權，尊重他人隱私，提供足夠的驗證與重現資訊，並避免在既有獎勵制度以外要求付款作為揭露條件。

[image](https://www.google.com/s2/favicons?domain=https://cheatsheetseries.owasp.org\&sz=32)

OWASP Cheat Sheet Series



一份實用的弱點報告可以長這樣：

| 欄位         | 半導體平台案例                           |
| ---------- | --------------------------------- |
| Finding ID | SEC-2026-001                      |
| 弱點類型       | Broken Object Level Authorization |
| 受影響資產      | 已授權的設計資料測試 API                    |
| 重現條件       | 測試帳號 A、B 與指定資料                    |
| 影響         | 可能違反不同客戶之間的資料隔離                   |
| 證據         | 遮罩後的請求、回應與存取日誌                    |
| 修補方向       | 在後端建立物件層級授權檢查                     |
| 驗收條件       | A 無法取得 B 的資料，且合法存取仍正常             |

其中 OWASP 的 API1:2023 明確指出，物件層級授權應在涉及用戶端提供之物件 ID 的資料存取操作中進行驗證。

[image](https://www.google.com/s2/favicons?domain=https://api-security.owasp.org\&sz=32)

OWASP API Security Top 10



### 3. 臺灣半導體的法律關聯

《營業秘密法》第 2 條將秘密性、因秘密性而具有的經濟價值，以及合理保密措施列為營業秘密的核心要件。

[image](https://www.google.com/s2/favicons?domain=https://law.moj.gov.tw\&sz=32)

Law\.gov.tw



因此，企業在進行外部安全測試時，應透過資料分級、最小必要存取、保密約定、證據保存及交付控制，降低敏感技術資料的暴露風險。

### 4. 美國矽谷公司的弱點回報制度

矽谷科技公司常透過 Vulnerability Disclosure Policy（VDP）或 Bug Bounty 計畫定義研究者可測試的資產與行為。

OWASP 指出，這類計畫應明確交代 Scope、測試規則、回報方式及適用的 safe harbor 條件；並可透過符合 RFC 9116 的 `security.txt` 協助研究者找到安全回報窗口。

[image](https://www.google.com/s2/favicons?domain=https://cheatsheetseries.owasp.org\&sz=32)

OWASP Cheat Sheet Series



需要注意，Bug Bounty 是特定條件下的測試邀請，不是對企業所有系統開放無限制測試。

### 5. 金融業的資訊保護與監督責任

《金融控股公司及銀行業內部控制及稽核制度實施辦法》第 24 條要求適用機構設置資訊安全專責單位，第 25 條則規範資安制度規劃、風險控管及安全事件通報應變等職責。

[image](https://www.google.com/s2/favicons?domain=https://law.fsc.gov.tw\&sz=32)

FinSupReg System



金融機構在委託外部滲透測試時，可以將這些法規要求轉化為承包商測試流程、敏感客戶資料保護、資安事件通報與改善追蹤的管理要求。

銀行公會另於 2026 年 3 月 5 日公布《金融機構資通系統與服務供應鏈風險管理規範》，是研究金融機構供應鏈安全治理時應一併查核的自律規範。

ba.org.tw



C15 的關鍵：弱點發現不是工作的終點。如何處理證據、通報風險、完成修補，才決定研究成果是否真正改善安全。

## 八、C16｜攻擊目的與測試目的：同樣的技術，為什麼可能具有不同性質？

CEH 有時會把 Ethical Hacking 與 DoS、資料竊取及散布惡意軟體放在同一道選擇題。

這些題目通常不是在問技術是否強大，而是在問其主要目的。

### 1. 用 MITRE ATT&CK 理解攻擊行為

| 攻擊行為         | MITRE ATT&CK 對應                           | 典型影響        |
| ------------ | ----------------------------------------- | ----------- |
| 利用對外服務弱點     | T1190 — Exploit Public-Facing Application | 未授權初始存取     |
| 濫用有效帳號       | T1078 — Valid Accounts                    | 未授權存取、權限提升等 |
| 網路阻斷服務       | T1498 — Network Denial of Service         | 服務可用性降低     |
| 端點阻斷服務       | T1499 — Endpoint Denial of Service        | 系統資源耗盡或服務中斷 |
| 透過 C2 通道外洩資料 | T1041 — Exfiltration Over C2 Channel      | 機密資料外洩      |

以上對應均以 MITRE ATT&CK Enterprise 技術頁面為依據。

[image](https://www.google.com/s2/favicons?domain=https://attack.mitre.org\&sz=32)

MITRE ATT&CK®+4



這裡要注意一個非常重要的觀念：

MITRE ATT&CK 描述的是攻擊者行為與技術，不負責決定某次安全測試是否已獲授權。

研究團隊可以在受控條件下模擬部分 ATT&CK 技術，以評估防禦控制，但是否能執行，仍由測試授權與 ROE 決定。

### 2. 以金融業 DDoS 情境說明

假設銀行想知道自己的網路銀行，是否能承受大量惡意請求。

這個目的本身可以是正當的安全驗證。

但如果團隊直接對正式網路銀行發動大量流量攻擊，導致客戶無法進行正常交易，就可能產生嚴重營運風險，也可能超出授權。

更合理的測試設計，是先確認需要驗證的是哪一項防護能力。

例如：流量清洗服務的偵測能力、限流規則、應變程序，或系統在特定流量情境下的承載能力。

再依風險與適用的 ROE，選擇模擬環境、受控負載或經核准的服務提供者測試機制。

金管會《金融控股公司及銀行業內部控制及稽核制度實施辦法》第 25 條要求資安專責單位督導資訊機密性、完整性與可用性，並建立資安事件通報應變機制，與上述風險控制目標相符。

[image](https://www.google.com/s2/favicons?domain=https://law.fsc.gov.tw\&sz=32)

FinSupReg System



### 3. 判斷是否屬於正當安全測試的決策模型

提出測試行為

具有有效授權嗎？

授權人、期間、測試者與資產

否

不得作為已授權測試執行

是

繼續審查行為與風險

符合 Scope、ROE 與風險限制嗎？

否：停止並申請變更授權

是：執行受控驗證與證據保存

回報、改善、複測與結案

此流程是根據 NIST SP 800-115 與 OWASP 弱點揭露原則整理的實務決策模型，不是法律構成要件判定流程。

## 九、整合實務：三大產業如何設計安全測試治理？

| 治理面向     | 臺灣半導體科技業                         | 美國矽谷科技業                         | 臺灣金融機構                |

| 主要目標     | 保護製程、設備、研發資料與生產持續性               | 保護產品、雲端服務、軟體供應鏈與使用者資料           | 保護交易、客戶資料及金融服務可用性     |

### 進階理解：為什麼安全測試是一種 Governance 問題？

傳統上，我們可能認為滲透測試主要是技術問題。

但一旦測試涉及多個部門、雲端服務商、外部顧問、金融資料或半導體製造設備，就必須處理誰能授權、誰承擔風險、誰決定停止，以及誰負責修補。

因此，專業測試系統必須同時具備三個層次：

| 層次          | 要解決的問題         | 對應工具與制度            |
| ----------- | -------------- | ------------------ |
| Technical   | 弱點存在嗎？如何驗證？    | OWASP WSTG、掃描、受控測試 |
| Operational | 測試會不會影響服務？     | ROE、停止條件、SOC、事件應變  |
| Governance  | 誰有權核准、監督與承擔責任？ | 授權、風險管理、稽核、法令遵循    |

這三層的共同核心，是把具有潛在破壞能力的技術行為，限制在可授權、可稽核、可控制的執行範圍內。

## 十一、理解檢查：半導體供應鏈安全測試專案

請先獨立思考，不必急著查資料。這組題目要求你同時運用 C06–C16。

案例：

臺灣一家半導體設備公司委託美國資安公司測試供應鏈管理平台，測試團隊取得書面授權，可測試指定的測試環境。

測試期間發生以下情況：

A. 工程師使用 OWASP 方法，發現測試帳號可能讀取另一個帳號的測試文件。

B. 工程師發現正式環境也可能存在相同問題，於是直接登入正式系統驗證，但正式系統不在授權範圍內。

C. 工程師發現設備管理網路與企業辦公網路相連，決定使用主動掃描工具探測設備控制器，但 ROE 並未允許測試 OT 網路。

D. 測試團隊只使用人工測試資料，完整記錄弱點證據，向企業安全負責人回報並提出修補建議。

E. 另一位研究人員發現銀行的電子交易平台存在疑似安全問題，未取得授權即嘗試存取其他客戶的交易資料，之後表示自己的目的只是幫助銀行。

請回答：

1\. 分類判斷： A–E 哪些行為符合有效授權與測試邊界？哪些需要重新取得核准？哪些最接近 White Hat 或 Grey Hat 的典型情境？

2\. 標準應用： 針對 C 的 OT 測試風險，應如何運用 NIST SP 800-82 與 SEMI E187 的不同角色，重新設計測試程序？

3\. 安全工程： 針對 A 的弱點，你會使用 OWASP 的哪一項測試概念？可能如何對應 MITRE ATT&CK？為什麼兩者不能互相替代？

4\. 法令與治理： 如果 B 的正式系統包含美國公司的客戶資料，而 E 的銀行位於臺灣，你會分別先檢視哪些法律、授權文件與自律規範？

5\. 研究方法： 如何設計最小充分驗證（Minimum Sufficient Validation），證明弱點存在，同時限制資訊暴露、設備異常及對第三方的影響？

本章最應掌握的核心能力，是能把「安全測試技術」轉換成「經授權、受風險限制、產生可信證據且可以改善系統的工程流程」。 這也是 C06–C16 從 CEH 基礎概念延伸到資安工程研究與實務治理的主要連結。
