# **CSRF 完整教學：從瀏覽器、HTTP、Session、Cookie 到跨網站攻擊**

## **一、先回答你最核心的五個疑問**

**你對瀏覽器沙盒（Sandbox）的理解有一個重要部分是正確的：不同網站通常不能任意讀取彼此的資料。**

但是，這不代表不同網站不能要求瀏覽器向其他網站發送 HTTP Request。

這兩件事是理解 CSRF（Cross-Site Request Forgery，跨網站請求偽造）的關鍵。

| 你的疑問                       | 核心答案                                                                  |
| -------------------------- | --------------------------------------------------------------------- |
| 不同網頁不是獨立沙盒嗎？               | 是，但主要隔離的是不同 Origin 的資料與程式存取權限，不是禁止所有跨網站網路請求。                          |
| 惡意網站怎麼取得銀行的 Session Token？ | **一般 CSRF 不需要取得 Token**。瀏覽器可能自行把銀行的 Session Cookie 附在發往銀行的 Request 上。 |
| 為什麼瀏覽器願意替惡意網站送出 Request？   | 因為跨網站連結、表單提交、載入圖片等，本來就是 Web 設計允許的正常功能。                                |
| 惡意網站怎麼知道 Alice 已經登入銀行？     | 通常不需要知道。攻擊者可以預先指定目標網站，只有符合條件的使用者才可能受影響。                               |
| 攻擊者怎麼知道銀行的網址與 API？         | 可以透過公開網頁、前端 JavaScript、API 文件、測試觀察或目標情報蒐集取得；但不保證能找到可利用的端點。            |

這裡有一個非常重要的區別：

**CSRF 通常不是攻擊者偷走 Alice 的身分證明，而是攻擊者誘使 Alice 的瀏覽器，利用原本已經存在的身分證明，向銀行發出 Alice 沒有授權的操作。**

而且，現代瀏覽器已經透過 `SameSite` 等機制限制這種行為。因此，**能跨網站發出 Request，不代表一定會帶上 Cookie，更不代表 CSRF 一定成功。**&#x20;

## **二、理解 CSRF 之前，先建立正確的 Web 架構**

請把 Web 想成四個不同的部分：

**Alice 的電腦：同一個瀏覽器**

銀行網頁

bank.example

自己的 DOM、JavaScript

惡意網頁

evil.example

自己的 DOM、JavaScript

**Browser 的 Cookie 儲存與網路管理機制**

儲存不同網站的 Cookie，依照目標網址、Cookie 屬性和請求情境決定是否附帶。

HTTPS Request / Response

HTTPS Request / Response

**銀行 Server**

驗證 Alice 身分、維護 Session、處理交易

**惡意網站 Server**

提供惡意頁面，但無權直接取得銀行的 Cookie

這張架構圖要記住三件事。

第一，**網頁（Page）和瀏覽器（Browser）不是同一個東西**。網頁內的 JavaScript 受到安全限制；瀏覽器本身則負責處理網路連線、Cookie 和導航。

第二，Cookie 通常不是分別保存在每個分頁裡，而是由瀏覽器的 Cookie 儲存機制管理。在一般瀏覽器設定檔中，兩個分頁可以共用相同網站的登入 Session，但不同設定檔、無痕模式及 Cookie 分區機制可能隔離這些狀態。

第三，銀行 Server 通常只看到「收到什麼 HTTP Request」，不會自然知道 Alice 是親自按下轉帳按鈕，還是其他網頁觸發了這個操作。Server 必須使用額外的安全機制判斷請求是否可信。

### **HTTP 為什麼需要 Session？**

HTTP 基本上是 Stateless（無狀態）的協定。

假設 Alice 今天向銀行 Server 發出三個 Request：

```
GET /login
GET /accounts
GET /transactions
```

單看這三個 Request，銀行無法確定它們一定來自同一個已驗證身分的使用者。

就像你每次走到銀行櫃檯，櫃員都需要某種方式確認：「你是誰？你是否已經完成身分驗證？」

這正是 Session Management（工作階段管理）要解決的問題。它讓 Server 可以把多次獨立 HTTP Request 關聯到已登入的使用者。

## **三、Alice 從登入銀行到完成操作：HTTP 與 Session 的完整生命週期**

我們先完全不考慮攻擊者，只研究正常情況。

以下是簡化的教學案例，使用虛構網域與 Session 值，不代表任何真實銀行的實作。

### **階段 A：第一次開啟銀行網站**

Alice 在瀏覽器輸入：

`https://bank.example/login`

發生的事情大致如下：

1. 瀏覽器解析網址，透過 DNS 取得 Server 的 IP 位址（如果沒有可用快取）。
2. 建立網路連線，例如 TCP 與 TLS，或 HTTP/3 使用的 QUIC。
3. HTTPS 連線建立後，瀏覽器發出 HTTP Request。
4. 銀行 Server 回傳登入頁面的 HTML。
5. 瀏覽器解析 HTML，可能繼續請求 CSS、JavaScript、圖片，再顯示登入頁面。

例如，HTTP Request 可以簡化為：

```
GET /login HTTP/1.1
Host: bank.example
```

銀行可能回傳：

```
HTTP/1.1 200 OK
Content-Type: text/html

<html>...</html>
```

此時 Alice 還沒登入，因此不一定存在已驗證身分的 Session Cookie。

但有些網站會在登入前建立匿名 Session，作為 CSRF 防護或登入流程管理之用。

### **階段 B：Alice 輸入帳號密碼並登入**

Alice 輸入：

- Username：alice
- Password：她自己的密碼

點擊「登入」。

瀏覽器發出類似：

```
POST /login HTTP/1.1
Host: bank.example
Content-Type: application/x-www-form-urlencoded

username=alice&password=...
```

此 HTTP Body 經過 HTTPS 傳送時受到 TLS 加密保護。

Server 收到後，可能執行：

```
1. 檢查帳號是否存在
2. 驗證密碼
3. 執行必要的 MFA
4. 建立已登入的 Session
5. 產生安全、不可預測的 Session ID
```

這裡要理解兩個不同概念：

**Authentication（身分驗證）**：確認使用者是 Alice。

**Session Management（工作階段管理）**：讓後續的 Request 不必每次重新輸入密碼，也能識別已驗證的 Alice。

### **階段 C：銀行建立 Session ID，並透過 Cookie 交給瀏覽器**

假設銀行產生一個隨機 Session ID：

```
s_9cf72a...（示意值）
```

Server 內部保存：

```
Session Store（可能是 Redis / Database）

s_9cf72a...
    user_id: 42
    username: alice
    authenticated: true
    expires_at: ...
```

Server 再透過 Response Header 通知 Browser：

```
HTTP/1.1 303 See Other
Location: /accounts
Set-Cookie: __Host-sid=s_9cf72a...; Path=/; Secure; HttpOnly; SameSite=Lax
```

注意最重要的地方：

`Set-Cookie`**&#x20;是 Server 對 Browser 發出的指示，而不是 Server 直接去修改某個網頁的 JavaScript 變數。**

瀏覽器收到後，會依照自己的 Cookie 規則儲存它。

另外，Session ID 通常只是個隨機識別值，不必包含 Alice 的姓名或密碼。Server 透過它查詢 Session Store。

這是一種常見的 Server-side Session 設計。其他架構也可能使用經過簽署的 Token，例如 JWT，不一定每個請求都查詢 Session Store。

### **階段 D：Cookie 內的安全屬性是什麼？**

剛才的 Cookie：

```
Set-Cookie: __Host-sid=s_9cf72a...;
            Path=/;
            Secure;
            HttpOnly;
            SameSite=Lax
```

可以拆解為：

| 屬性             | 功能                                         |
| -------------- | ------------------------------------------ |
| `__Host-sid`   | Cookie 名稱；`__Host-` 前綴要求更嚴格的主機範圍設定         |
| `s_9cf72a...`  | Session ID，作為身分驗證狀態的識別依據                   |
| `Path=/`       | 允許該 Host 下符合路徑規則的 Request 附帶               |
| `Secure`       | 原則上只透過 HTTPS 傳送                            |
| `HttpOnly`     | 不允許網頁 JavaScript 直接透過 `document.cookie` 讀取 |
| `SameSite=Lax` | 限制跨網站 Request 何時能附帶這個 Cookie               |

Cookie 若未設定 `Domain`，通常是 Host-only Cookie，也就是只針對設定它的主機，而非任意其他網域。

銀行也可以設定 Cookie 的有效期限。即使瀏覽器還保存 Cookie，Server 仍必須自行判斷 Session 是否過期、撤銷或已登出。

### **階段 E：Alice 再次查詢銀行帳戶**

Alice 已登入，現在點擊「我的帳戶」。

瀏覽器準備向銀行發 Request：

```
GET /accounts HTTP/1.1
Host: bank.example
Cookie: __Host-sid=s_9cf72a...
```

這次 Request 多了：

`Cookie: __Host-sid=s_9cf72a...`

請特別注意：**Alice 並沒有再次輸入 Session ID，網頁的 JavaScript 也不必先讀出它。**

是瀏覽器發送 Request 時，依據 Cookie 規則附帶它。

Server 接收到後：

```
收到 Cookie
     ↓
取得 Session ID
     ↓
查詢並驗證 Session
     ↓
辨認 user_id = 42
     ↓
檢查 Alice 是否有權查看該帳戶
     ↓
回傳帳戶資料
```

這個過程同時涉及三個不同的安全判斷：

- Authentication：這是哪個已驗證的使用者？
- Authorization：這位使用者有沒有權限執行這項操作？
- Request legitimacy：這個請求是否符合應用程式的安全要求，包括必要的 CSRF 防護？

**Session Cookie 通常主要解決前兩者需要的身分關聯問題，並不能單獨證明 Alice 有意發出這次 Request。**

這就是 CSRF 問題的根源。

### **階段 F：登出銀行**

Alice 點擊登出時，銀行應使 Server 端的 Session 失效，並指示瀏覽器刪除或過期對應 Cookie。

假設 Server 已撤銷 `s_9cf72a...`，那麼即使 Browser 之後再次送出舊 Cookie，銀行也應拒絕它。

因此必須區分：

**Cookie 還存在 ≠ Session 還有效 ≠ 使用者仍具有執行某操作的權限。**

## **四、為什麼有沙盒，卻仍然允許跨網站 Request？**

現在進入你提出的最重要的架構問題。

你認為：

> 銀行網頁與惡意網頁不是應該處於不同的沙盒嗎？為什麼惡意網頁還可以要求 Browser 對銀行送 Request？

要回答這個問題，我們必須區分三種行為。

| 行為                              | 不同 Origin 間的基本規則 | 例子           |
| ------------------------------- | ---------------- | ------------ |
| Cross-origin read               | 通常受到限制           | 惡意網頁讀取銀行帳戶內容 |
| Cross-origin write / navigation | 許多基本操作允許         | 跨網站表單提交、點擊連結 |
| Cross-origin embedding          | 許多資源類型允許，但有個別限制  | 引用其他網站的圖片、影片 |

這是 MDN 對 Same-Origin Policy（SOP，同源政策）的核心分類。

[image](https://www.google.com/s2/favicons?domain=https://developer.mozilla.org\&sz=32)

MDN+1



### **1. 什麼是 Origin？**

Origin 由三個要素構成：

`Scheme（協定） + Host（主機） + Port（連接埠）`

例如，以 `https://bank.example` 為基準：

| 網址                              | 是否 Same-Origin |
| ------------------------------- | -------------- |
| `https://bank.example/accounts` | 是              |
| `https://bank.example/transfer` | 是              |
| `https://api.bank.example`      | 否，Host 不同      |
| `http://bank.example`           | 否，Scheme 不同    |
| `https://bank.example:8443`     | 否，Port 不同      |
| `https://evil.example`          | 否，Host 不同      |

所以你所說的沙盒概念，主要是不同 Origin 之間的資料存取與程式互動限制，而不是「每個分頁完全不能影響其他網路資源」。

### **2. 同源政策不是網路防火牆**

假設 Alice 正在閱讀：

`https://blog.example`

網站上寫著：

「推薦閱讀：MDN Web Docs」

```
<a href="https://developer.mozilla.org">
  閱讀 MDN
</a>
```

Alice 點擊後，Browser 就會向另一個 Origin 發出 HTTP Request。

如果 SOP 完全禁止跨網站 Request，那麼這個連結就不能正常運作。

同樣道理，網頁中的圖片、外部表單、登入導向、付款頁面，也經常需要向另一個 Origin 發出 Request。

因此瀏覽器需要在兩個目標之間取得平衡：

**允許跨網站互動，才能讓 Web 正常運作；限制跨網站讀取，才能保護各網站的資料。**

### **3. 所謂的 Sandbox，到底保護什麼？**

假設 Alice 同時開著：

銀行：`https://bank.example`

惡意網站：`https://evil.example`

惡意網站內的 JavaScript 一般不能直接執行：

```
// 示意：不能任意取得另一個 Origin 的私人 DOM
const secret = bankWindow.document.body.innerText;
```

也不能直接讀取銀行的 HttpOnly Session Cookie。

但是，它可以在自己管理的頁面建立連結或表單，指定目標 URL 為銀行。

這兩者完全不同：

- **讀取別人的資料**：涉及跨 Origin 的資料存取權。
- **要求瀏覽器對別人發出 Request**：涉及跨 Origin 的網路操作能力。

更精確地說，瀏覽器不是把整個控制權交給惡意網頁；它只是允許網頁使用受限制的瀏覽器功能，並在實際執行時套用 Cookie、SameSite、CORS 等政策。

## **五、Web 為什麼需要跨網站連結、表單、圖片和重新導向？**

以下用五個日常情境說明。

**情境 A：新聞網站提供外部連結**

Alice 從新聞網站點擊政府公告連結，Browser 向政府網站發送 GET Request。新聞網站不需要有權讀取政府網站的私人資料。

**情境 B：從 CDN 載入圖片**

商品網站使用另一個網域提供產品圖片。

```
<img src="https://cdn.example/product.jpg">
```

瀏覽器向 CDN 發送 Request，取得圖片並顯示。這不代表商品網站的 JavaScript 可以讀取 CDN 的任意私人資料。

**情境 C：購物網站前往第三方付款服務**

商家網站把顧客導向付款服務商，也可能透過表單提交必要資料。跨網站表單提交本來就是 Web 支援的能力，實際付款仍須通過付款服務商的安全驗證。

**情境 D：使用 Google 或 Microsoft 登入**

應用程式導向身分提供者；驗證完成後，再重新導向原本的應用程式。這類跨網站導航是 OAuth 2.0／OpenID Connect 等流程的重要組成部分。

**情境 E：嵌入另一個網站的影片**

教學網站透過 iframe 嵌入影片播放器。Browser 可以載入它，但不同 Origin 的 Frame 仍受 SOP 與各種嵌入政策限制。

所以，跨網站發 Request 並不是 CSRF 發明的新能力，而是 Web 原本就有的功能。

**CSRF 是攻擊者利用這些正常功能，加上目標 Server 錯誤的請求信任判斷，造成未經使用者意願授權的操作。**

我們研究兩個不同對象：

- Alice：銀行的合法使用者，Browser 已有銀行 Session Cookie。
- Mallory：攻擊者，控制 `https://evil.example`，但不知道 Alice 的密碼，也不知道她的 Session ID。

### **第一步：攻擊者建立帶有表單的網頁**

例如：

```
<form
  id="attack"
  action="https://bank.example/transfer"
  method="POST"
>
  <input
    type="hidden"
    name="recipient"
    value="attacker"
  >
  <input
    type="hidden"
    name="amount"
    value="1000"
  >
</form>

<script>
  document.getElementById("attack").submit();
</script>
```

這個表單的意思是：

「請 Browser 將收款對象 `attacker`、金額 `1000`，以 POST Request 送到銀行的 `/transfer`。」

注意：惡意網頁不需要也沒有包含 Alice 的 Session ID。

而且，這段程式只有在銀行端存在相容的操作端點、接受這些欄位，並缺乏適當防護時，才可能造成預期操作。

### **第二步：Alice 開啟惡意網站**

Browser 取得惡意網頁的 HTML，解析後執行表單提交。

這時發出 Request 的過程是：

惡意網頁

指定銀行 URL 與參數

瀏覽器

決定 Cookie 是否附帶

銀行 Server

驗證並處理 Request

Session Cookie 若被允許附帶，是直接送到銀行，不是送給惡意網站。

### **第三步：Browser 檢查銀行的 Cookie**

這裡才是重點。

假設銀行使用的是：

```
Set-Cookie: __Host-sid=s_9cf72a...;
            Path=/;
            Secure;
            HttpOnly;
            SameSite=None
```

這表示 Cookie 可以用於符合條件的跨網站 Request，仍須遵循瀏覽器其他 Cookie 與隱私限制。

如果該請求允許附帶 Cookie，銀行可能收到：

```
POST /transfer HTTP/1.1
Host: bank.example
Origin: https://evil.example
Sec-Fetch-Site: cross-site
Cookie: __Host-sid=s_9cf72a...
Content-Type: application/x-www-form-urlencoded

recipient=attacker&amount=1000
```

觀察這裡的三個重要欄位：

`Cookie` 是 Alice 的登入憑證，由 Browser 附帶。

`Origin` 表示 Request 來自哪個 Origin，銀行可以用它協助判斷請求來源。

`Sec-Fetch-Site` 告訴銀行 Request 的跨站關係。現代瀏覽器可提供這類 Fetch Metadata 資訊。

這個 Request 確實可能攜帶有效的 Alice Session，但來源是惡意網頁。

### **第四步：銀行 Server 決定是否執行**

如果銀行只檢查：

```
session = find_session(request.cookies["__Host-sid"])if session.is_authenticated:    transfer_money(        recipient=request.form["recipient"],        amount=request.form["amount"]    )
```

那麼邏輯就不完整。

因為銀行只確認「這是 Alice 的有效 Session」，沒有確認「這是不是一個符合安全政策、可被接受的操作請求」。

假設銀行缺乏 CSRF 防護，也沒有額外交易確認，攻擊可能成功。

反之，銀行若驗證 CSRF Token、來源資訊、權限及必要的交易確認，就能在對應的驗證階段拒絕它。

這也是 OWASP 與 MDN 所描述的典型 CSRF 風險。

### **你應該注意的反直覺現象**

攻擊者的 JavaScript 無法讀取銀行的 Session Cookie。

但如果 Browser 的 Cookie 規則允許，**Browser 自己可以把這個 Cookie 送給銀行**。

因此：

`HttpOnly` 能防止 JavaScript 直接讀取 Session Cookie，但它本身不是 CSRF 防護。

SOP 能限制跨 Origin 的資料讀取，但不代表所有跨 Origin 的 Request 都會被阻止。

CORS 即使阻止惡意 JavaScript 讀取回應，也不代表此前的跨網站表單提交一定沒有送達銀行。

這三件事必須分開理解。

## **七、那為什麼現在的瀏覽器不會全部遭受 CSRF？SameSite 是關鍵**

剛才我們使用 `SameSite=None`，是為了說明攻擊能成立的情境。

現在改成較常見的安全設定：

```
Set-Cookie: __Host-sid=s_9cf72a...;
            Path=/;
            Secure;
            HttpOnly;
            SameSite=Lax
```

再讓惡意網頁提交前面那個跨網站 POST 表單。

在正常的明確設定 `SameSite=Lax` 情境下，Browser **不會附帶銀行的 Session Cookie**。

銀行可以收到 POST，但通常無法將它識別為已登入的 Alice。

因此剛才那個攻擊通常失敗。

### **三種 SameSite 設定的差異**

| 請求情境                  | `Strict` | `Lax` | `None` |
| --------------------- | -------- | ----- | ------ |
| 銀行自己的頁面向銀行發 Request   | 可附帶      | 可附帶   | 可附帶    |
| 從惡意網站點連結，頂層導航 GET 到銀行 | 不附帶      | 可附帶   | 可附帶    |
| 惡意網站發起跨站頂層 POST 表單    | 不附帶      | 不附帶   | 可附帶    |
| 惡意網站嵌入銀行圖片，發跨站 GET    | 不附帶      | 不附帶   | 可附帶    |

表格假設 Cookie 的 Domain、Path、Secure、有效期等條件均符合，且未受其他隱私機制阻擋。「可附帶」不等於一定附帶，也不代表 Server 會接受請求。

還有一個實作細節：部分瀏覽器在 Cookie **沒有明確設定&#x20;**`SameSite`、而是採用預設 Lax 行為時，可能對剛建立不久（約兩分鐘內）的 Cookie 放寬跨站 POST 限制。因此不能單純依賴瀏覽器預設值。

### **SameSite=Lax 仍然存在什麼風險？**

假設某個設計不良的網站竟然使用：

```
GET /delete-account
```

來刪除帳戶，而且只檢查 Session Cookie。

惡意網頁可以讓 Browser 進行跨站頂層導航：

```
<a href="https://bank.example/delete-account">
  查看重要通知
</a>
```

在 `SameSite=Lax` 下，這種頂層 GET 導航仍可能帶上銀行 Cookie。

如果 Server 把 GET 當成更改資料的操作，又沒有其他防護，就存在 CSRF 風險。

這也是為什麼安全設計要求 **GET、HEAD 等 Safe Methods 不應執行具有業務狀態變更意義的操作**。

### **另一個重要概念：Same-Origin 不等於 Same-Site**

例如：

`https://app.company.example`

以及：

`https://hr.company.example`

兩者不同 Origin，但通常屬於同一個 Site。

原因是 `SameSite` 主要考慮 Scheme 與可註冊網域，而不是完整的 Scheme、Host、Port 三元素。

因此，若攻擊者控制了同一個 Site 底下的不可信子網域，單靠 SameSite 未必能防禦所有攻擊。

這也是 OWASP 特別提醒必須評估 sibling subdomains 與 subdomain takeover 風險的原因。

## **八、惡意網站究竟怎麼知道 Alice 有沒有登入銀行？**

直接回答：

**大部分傳統 CSRF 攻擊，不需要預先知道 Alice 是否已登入。**

我們從攻擊者的角度想一次。

Mallory 經營一個惡意網站，目標是一個會員系統。

Mallory 完全不知道哪一位訪客登入過會員系統，但他可以把觸發跨站 Request 的表單放在惡意網頁裡。

假設有很多人瀏覽這個網站。

其中有人沒有會員帳號，有人有帳號但沒登入，也有人剛好保持登入狀態。

攻擊者未必能辨認每個人的狀態，但也不一定需要知道。

一次廣泛的 CSRF 嘗試可能產生的結果

**Bob：沒有登入銀行**

沒有有效 Session，通常無法以已登入使用者身分執行操作

**Carol：登入已過期**

Server 應拒絕失效 Session

**David：已登入，但網站有 CSRF 防護**

即使 Session 有效，Server 仍可阻擋未通過檢查的 Request

**Alice：已登入，且目標操作缺乏防護**

若 Cookie 被附帶、參數符合要求、權限足夠，攻擊可能成功

這是網路攻擊裡很常見的一種邏輯：

**攻擊者可以先發起嘗試，由目標的實際狀態決定結果。**

不用每次都先知道結果一定會成功。

### **那麼，攻擊者完全不可能知道 Alice 的登入狀態嗎？**

也不能如此絕對。

一般的 SOP 會阻止惡意頁面直接讀取其他 Origin 的私人資料，但仍可能存在某些間接推測技術，例如 XS-Leaks（Cross-Site Leaks）。

這些技術利用網頁載入、瀏覽器行為或其他可觀察差異，嘗試推測跨網站狀態。

不過，這類攻擊具有特定成立條件，並不是攻擊者可以隨意讀取 Alice 的銀行登入資訊。

對理解一般 CSRF 而言，你暫時不需要把它與 XS-Leaks 混在一起。

## **九、如果攻擊者不知道 Alice 常用什麼網站，他又怎麼決定攻擊哪個網站？**

這個問題已經從 Web 安全機制，進入了攻擊者的 **Target Selection（目標選擇）與 Reconnaissance（情報蒐集）**。

這兩個階段與 CSRF 的漏洞原理有關，但不是同一件事。

### **攻擊者不一定是先選 Alice，也可能先選有漏洞的網站**

例如，Mallory 發現某個會員網站存在可被跨網站請求觸發的個人資料修改功能。

他可以先研究那個會員網站的功能，再設法讓該網站的使用者瀏覽惡意頁面。

這是一種「先有漏洞目標，再尋找符合條件的受害者」的思路。

相反地，如果 Mallory 明確想針對一家企業的員工，則可能先研究企業使用的 HR、ERP、SSO 或管理系統，再尋找可能存在的 CSRF 攻擊面。

這是一種「先有受害者群體，再研究目標系統」的思路。

### **攻擊者怎麼知道 URL 與 API？**

這些資訊不一定是秘密。

例如，公開網站可能存在：

```
<form action="/profile/update" method="POST">
```

或者前端 JavaScript 出現：

```
fetch("/api/profile/update", {
  method: "POST",
  body: ...
});
```

只要攻擊者能合法取得這些公開資源，或用自己的測試帳號觀察功能，就可能了解網站使用的部分路徑、HTTP Method 與參數格式。

其他來源可能包括公開的 API 文件、開發者文件、公開程式碼、應用程式流量觀察，以及對已知功能的測試。

但要強調：

**知道 Endpoint，不等於可以成功執行它；知道 Endpoint，也不等於知道 Alice 的 Session Token。**

目標 Server 仍然可以要求 CSRF Token、授權檢查、MFA、交易確認、不可預測的操作識別資訊等。

### **社交工程是否必要？**

不一定。

假設惡意網頁本身有流量，攻擊者可以利用該流量嘗試影響符合條件的訪客。

如果攻擊者希望特定 Alice 進入惡意網頁，才可能透過釣魚郵件、通訊訊息、社群貼文或其他社交工程方式誘導 Alice 開啟。

因此，社交工程在這裡的角色通常是 **Delivery（攻擊投遞）**，而非 CSRF 的必要技術條件。

## **十、CSRF、CORS、SOP、Session Token、CSRF Token 到底有什麼差異？**

這是建議你特別整理的一組概念，因為它們經常在同一個 HTTP Request 中出現，卻各自負責不同工作。

| 名詞            | 核心問題                                                  | 主要由誰處理                |
| ------------- | ----------------------------------------------------- | --------------------- |
| Session ID    | 這個 Request 對應哪個登入 Session？                            | Server 與 Session 管理系統 |
| Cookie        | 要怎麼儲存及傳送相關資料？                                         | Browser 與 Server      |
| SOP           | 這個 Origin 能讀取另一個 Origin 的資料嗎？                         | Browser               |
| CORS          | Server 是否允許另一個 Origin 的 JavaScript 讀取回應，或通過特定跨來源請求檢查？ | Browser 與 Server      |
| SameSite      | 跨網站 Request 是否可以附帶這個 Cookie？                          | Browser               |
| CSRF Token    | 這個受保護的 Request 是否攜帶 Server 要求的不可預測證明？                 | Server 驗證，Client 附帶   |
| Authorization | 這個使用者有權執行操作嗎？                                         | Server                |

### **為什麼已經有 Session Token，還需要 CSRF Token？**

因為兩者回答不同的問題。

Session ID 主要告訴銀行：

「這個 Request 搭配的登入狀態是 Alice。」

CSRF Token 則讓銀行增加一項檢查：

「這個 Request 是否持有合法應用程式流程提供的防偽造值？」

例如銀行原本產生：

```
<form action="/transfer" method="POST">
  <input name="recipient">
  <input name="amount">

  <input
    type="hidden"
    name="csrf_token"
    value="RANDOM_UNPREDICTABLE_TOKEN"
  >
</form>
```

當 Alice 正常提交表單時，CSRF Token 會一起送給 Server。

Server 再比對這個 Token 是否屬於相應的 Session、是否有效。

而在一般跨 Origin 攻擊中，惡意網站通常無法讀取銀行網頁裡的這個值，也無法可靠猜出它。

這就能阻止單純依靠 Cookie 和可預測參數的偽造請求。

不過，CSRF Token 並不是對 Alice 真實意願的絕對證明。如果銀行自己的頁面存在 XSS，或合法應用程式 JavaScript 被攻擊者操縱，威脅模型就不同了。

OWASP 建議使用成熟框架內建的 CSRF 防護，並對狀態變更請求執行 Server-side 驗證。

### **那麼，Authorization: Bearer Token 又如何？**

這也是你最初問題值得補充的部分。

如果應用程式不是用 Cookie，而是由 JavaScript 明確加入：

```
Authorization: Bearer eyJ...
```

那麼其他 Origin 的網頁通常無法像使用 Cookie 一樣，要求 Browser 自動附帶該應用程式持有的 Bearer Token。

所以，是否容易受到傳統 CSRF 攻擊，取決於**身分憑證如何被儲存、取得及附帶**，而不只是它的名稱是否叫 Session Token 或 JWT。

例如，JWT 如果存在 Cookie 中，而且會自動附帶，仍可能面臨 CSRF 風險。

反過來說，也不應因為想避免 CSRF，就一律把 Token 改放 `localStorage`，因為這又牽涉到 XSS 與 Token 竊取風險。

## **十一、現代 Web 應該如何防禦 CSRF？**

對有登入 Session 的 Web 系統，我建議使用分層防護，而不是只依賴單一瀏覽器設定。

| 防禦層               | 做法                                                  | 目的                   |
| ----------------- | --------------------------------------------------- | -------------------- |
| 1. Cookie 安全設定    | `Secure`、`HttpOnly`、`SameSite=Lax/Strict`、`__Host-` | 限制憑證傳送、存取與 Cookie 範圍 |
| 2. CSRF Token     | 使用 Server 驗證的 Token，或妥善設計的簽章 Double-submit Cookie   | 防止請求僅靠自動附帶憑證就被接受     |
| 3. Request 來源檢查   | 驗證 `Origin`，必要時使用 `Referer` 作備援                     | 識別非預期跨 Origin 操作     |
| 4. Fetch Metadata | 檢查 `Sec-Fetch-Site` 等 Header                        | 區分同源、同站與跨站請求         |
| 5. HTTP API 設計    | GET 不執行狀態變更；必要時要求非 Simple Request                   | 減少可利用的跨來源請求方式        |
| 6. 高風險操作確認        | 重新驗證、交易簽核、OTP 或其他交易綁定證明                             | 限制金流、帳號權限與高風險操作      |

對於 JSON API，要求適當的 `Content-Type` 或自訂 Header，可利用 CORS Preflight 限制不被允許的跨 Origin 非 Simple Request，但不能把 CORS 當成萬能的 CSRF 防火牆。傳統 HTML 表單仍可能直接送出 Simple Request。

這些機制可以採取不同組合，並不表示每個 Endpoint 都必須毫無區分地同時使用所有六層。

參考依據包括：

- [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html?utm_source=chatgpt.com)
- [MDN Cross-site Request Forgery](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/CSRF?utm_source=chatgpt.com)
- [NIST SP 800-63B — Session Management](https://pages.nist.gov/800-63-4/sp800-63b/session/?utm_source=chatgpt.com)

NIST SP 800-63B 的 Session Management 指引也建議使用 HTTPS、HttpOnly、限縮 Cookie 範圍，以及 `SameSite=Lax` 或 `Strict`。

### **最核心的缺口：沒有把整套系統拆成三個獨立決策**

你可以把這次學習凝結成一個簡單的模型：

決策 1：網頁能不能發起這個操作？

Browser 檢查 Web Platform、Sandbox、SOP、Fetch 等規則。

決策 2：Browser 實際送出哪些憑證？

依 Cookie Domain、Path、Secure、SameSite、Credentials Mode 等規則決定。

決策 3：Server 應不應該接受並執行？

驗證 Session、Authorization、CSRF、來源、操作參數與必要的額外確認。

這三個決策是互相獨立、但依序互動的。

而你最初的困惑，是把「決策 1 的隔離」當成也會保證「決策 2 不送 Cookie」以及「決策 3 不執行操作」。

實際上，沒有這樣的自動保證。

一旦理解這個模型，你會比較容易看懂 XSS、Clickjacking、CORS Misconfiguration、Session Hijacking，甚至與 OAuth 授權流程有關的攻擊問題。

## **十三、你可以怎麼實際驗證這些概念？**

建議使用 Chrome 或 Firefox 的 Developer Tools，在你自己控制的測試網站觀察：

1. 開啟 Network，觀察登入 Request 與 Response。
2. 找到 Response 裡的 `Set-Cookie`，以及後續 Request 裡的 `Cookie`。
3. 在 Application／Storage 的 Cookies 區域查看 `HttpOnly`、`Secure`、`SameSite`。
4. 使用另一個測試 Origin 發出表單 Request，觀察 `Origin`、`Sec-Fetch-Site` 與是否附帶 Cookie。
5. 將測試 Cookie 分別設定為 `SameSite=Strict`、`Lax`、`None`，驗證不同跨站請求的結果。

一個有趣的進階陷阱：`http://localhost:3000` 和 `http://localhost:8000` 雖然是 Cross-Origin，通常仍屬於 Same-Site，單靠改變 Port 不足以測試真正的 Cross-Site Cookie 行為。這是很適合用實驗釐清的差異。

測試時請使用自建應用與虛構 Session，不要貼出真實 Session Cookie 或銀行憑證。

## **十四、理解檢查：三個情境**

先不提供答案。請依照你現在建立的 Browser → Cookie → Server 模型判斷。

情境 1：Alice 已登入銀行。銀行 Session Cookie 明確設為 SameSite=Lax。惡意網站自動提交跨站 POST 表單到銀行。

A. Browser 一定附帶 Cookie，因為 Alice 已登入

B. Browser 通常不會附帶 Cookie，因為這是跨站 POST

C. 因為 SOP，Browser 連 POST 都不會發送

情境 2：銀行把刪除帳號錯誤設計成 GET /delete-account。Session Cookie 是 SameSite=Lax。惡意網站讓 Alice 點擊該銀行網址並進行頂層導航。

A. 仍可能存在 CSRF 風險

B. SameSite=Lax 一定會阻擋 Cookie

C. GET 一定不能造成 Server 狀態改變

情境 3：銀行的 Session Cookie 設定 HttpOnly、Secure、SameSite=None。惡意網站無法讀取銀行 Cookie，卻嘗試跨站表單 POST。

A. 只要 HttpOnly 存在，CSRF 就不可能成功

B. 惡意網站必須先取得 Session ID 才能提交表單

C. 若 Browser 附帶 Cookie，且 Server 缺乏 CSRF 防護，攻擊仍可能成功
