# **CEH Day02-A｜白話文博士班教學**

CEH v13｜2026 年 11 月 14 日｜M01、M02、M03、M04、M20

## **一、先理解：今天到底在學什麼？**

這份教材有 **23 題（20 題首讀、3 題複習）、13 個知識點（K01–K13）**，核心是三個問題：

1. **我怎麼知道一個組織有哪些資訊系統？**——Footprinting、OSINT、DNS。
2. **我怎麼知道這些系統是否存在、是否提供網路服務？**——Host Discovery、TCP、UDP、Nmap。
3. **我看到的資訊能證明什麼？又不能證明什麼？**——證據可信度、授權範圍、安全控制與推論限制。

後面還有兩個密碼學複習單元：磁碟加密及金鑰分發。

這一課最重要的觀念是：

**「找到線索」不等於「確認事實」；「發現服務」不等於「發現弱點」；「發現弱點」更不等於「可以合法利用」。**

這既是 CEH 考題的解題基礎，也是資安研究中區分 observation（觀察）、inference（推論）與 validation（驗證）的基礎。

## **三、K01–K03：Footprinting 與 OSINT——先蒐集資訊，不急著碰系統**

### **1. Footprinting 到底是什麼？**

假設你是一位獲得授權的資安工程師，要評估一間醫院的對外 AI 服務。

你不能一開始就入侵伺服器，而是要先搞清楚：

- 這間醫院有哪些網域及網站？
- 有哪些對外的 API、郵件服務與系統？
- 可能使用 AWS、Kubernetes 或地端機房嗎？
- 哪些資訊可能被一般網路使用者看到？

蒐集並整理這些線索的過程，叫作 **Footprinting（足跡蒐集）**。

它就像刑事偵查中的前期情報蒐集：先建立對目標的輪廓，再決定後續哪些事情值得查證。

Footprinting 不是直接拿到管理員權限，也不是攻擊系統。

### **2. Passive 與 Active Reconnaissance 有什麼不同？**

這是本份教材最常重複考的觀念。

[How to Find a Person on Social Media: an Osint Guide for | DFC](https://images.openai.com/static-rsc-4/NmWTWiQSOy3ZicpINFykvCUmNiDsw6vLJ_pRtjI0tM7F_5mYFMa-gXKkSLuFre8PUUvG_geEyRMnecEfE7WpFWye3-b2m8ctaUK6GFBJ_QfyauF4QHLTWCjZLiiB3-ecaeE01kW2uM6DhVB8wCn6wyjL2MLv8Il4TTvdFJv9ipc?purpose=inline)

**Passive Reconnaissance**

被動偵察：先從第三方既有資訊了解目標，避免直接探測目標系統。

[Cybersecurity Analyst Carefully Monitors Laptop](https://images.openai.com/static-rsc-4/Bzz3C_Ja3Y1Sxyqdq6sOfAi_ShpS3gWvbmZrKuPQJisbMixPldfhR5LUg0B3CqHvARiJ2WhLSD-k7Vn8GDIbAdblOIE1Lamv-NUCx7ai_v0E25WBMdyAE6FdZWO-6wi-8vJloxcqcBxaFT11LDjBBo54ta76TQYn1P9aeXgf01qtS9FmNO0XDP70tU2UkCqX?purpose=inline)

**Active Reconnaissance**

主動偵察：向目標送出查詢、封包或其他互動，以觀察其回應。

例如：

| 行為             | 依本課分類      |
| -------------- | ---------- |
| 閱讀公司的公開徵才廣告    | 被動         |
| 查詢第三方保存的歷史網站   | 被動         |
| 查看公開的網域註冊資料    | 通常視為被動情報蒐集 |
| 直接掃描公司伺服器的連接埠  | 主動         |
| 嘗試大量 DNS 子網域猜測 | 主動         |
| 打電話向員工套問系統細節   | 主動互動／社交工程  |

這裡要掌握一個微妙區別：

**被動／主動是依照資訊取得的實際方式，不是單憑工具名稱決定。**

例如 DNS 查詢，若只是向第三方查詢過去保存的紀錄，可以是被動資訊蒐集；若直接向目標的權威 DNS 伺服器發送查詢，則已產生直接互動。

同樣地，使用 Tor 或 VPN 可能改變流量的來源與路徑，但不會讓直接探測自動變成被動。

### **3. OSINT：公開資訊為什麼能變成情報？**

OSINT（Open-Source Intelligence，公開來源情報）並不是單純使用 Google 搜尋。

完整流程是：

蒐集資料

確認來源與時間

交叉比對

形成情報判斷

**舉例：徵才廣告真的能暴露技術架構嗎？**

假設某醫療 AI 公司發布職缺：

> 招募 DevOps Engineer，需熟悉 Kubernetes、PostgreSQL、NVIDIA GPU 與 AWS。

你可以推論：該公司可能使用這些技術，或準備導入這些技術。

但是，你不能直接宣稱：

「該公司正式環境一定是 Kubernetes，而且資料庫一定部署於 AWS。」

為什麼？

因為徵才廣告可能描述未來計畫、研發環境、技術遷移，甚至已經棄用的架構。

博士班程度的思考，不是記住「Job Posting 可以用於 OSINT」，而是知道：

- **Observation：** 徵才廣告提到 Kubernetes。
- **Hypothesis：** 該公司可能部署 Kubernetes。
- **Evidence gap：** 尚未確認是否使用於正式環境。
- **Validation：** 需要其他獨立且合法的證據支持。

這個推理方式可以直接移植到數位鑑識、威脅情報與 AI Agent 的證據治理系統。

### **4. Wayback Machine 和外洩資料的差異**

Wayback Machine（歷史網頁）

它能幫你看到網站過去的樣子。

例如 2023 年網站出現 `/old-api/`，但 2026 年網站已經沒有這個連結。

這能支持「過去曾經公開過該路徑」，但不能證明目前服務仍然存在。

Leaked documents（外洩文件）

題庫將已存在的外洩資料視為可能的情報來源，但這裡要分清楚：

公開可見，不代表有權取得、使用或散布。尤其是病歷、帳密與個資，即使被放在公開網站上，也不代表可以任意處理。

真實評估必須依授權範圍與資料處理規範進行，而不是因為資料已外洩就假設可以使用。

**本段對應考題：** P3-Q055、EC-Q112、EC-Q278、EC-Q332、EC-Q519、EC-Q248，以及部分 EC-Q434。

## **四、K01：什麼叫合法的倫理駭客？**

Ethical Hacking（倫理駭客）的關鍵，不是你使用了哪一套工具，而是**有沒有授權，以及有沒有遵守授權範圍**。

假設某公司聘請你進行滲透測試，授權你測試：

- `api.example.com`
- 每日上午 9 點至下午 6 點
- 可以進行連接埠掃描
- 不得進行阻斷服務攻擊（DoS）

即使你有測試合約，也不能因此掃描這間公司所有伺服器。

這叫作 Rules of Engagement（ROE，交戰規則）。

考試中要辨識以下角色：

| 類型        | 白話解釋                  |
| --------- | --------------------- |
| White Hat | 經授權、以改善安全為目的          |
| Black Hat | 惡意入侵或破壞               |
| Grey Hat  | 可能出於善意，但未必有事前授權       |
| Blue Hat  | 定義因教材與情境而異，不能單憑顏色判定授權 |

在正式資安評估中，授權至少要釐清目標、方法、時間、聯絡人、停止條件及意外事件處置。

這也是 [NIST SP 800-115](https://csrc.nist.gov/pubs/sp/800/115/final?utm_source=chatgpt.com) 所強調的技術安全測試規劃精神。

## **五、K04：WHOIS、RDAP 與 DNS——三者到底有什麼不同？**

這裡是非常容易混淆的地方。

假設某企業經營 `example.com`。

你想問三個問題：

1. 這個網域的註冊資訊是什麼？
2. 這個網域對應哪個 IP 位址？
3. 這個網域使用哪些郵件伺服器？

這三個問題，不能全部靠同一種資料回答。

### **1. WHOIS／RDAP：查網域的註冊資料**

你可以把它想成查詢「網域的登記資料」。

可能取得註冊商、註冊日期、到期日期，以及依政策允許公開的註冊人資訊。

要分清三個角色：

- **Registrant（註冊人）：** 登記網域的人或組織。
- **Registrar（註冊商）：** 提供網域註冊服務的業者。
- **Registry（註冊局）：** 維護某類頂級網域註冊資料的機構。

註冊商不是網站伺服器營運商，註冊人也不必然是目前網站內容的實際經營者。

另外，CEH 題庫常寫 WHOIS，但你要知道實務上的更新：

**自 2025 年 1 月 28 日起，RDAP 已成為 ICANN 管轄的通用頂級網域（gTLD）註冊資料正式查詢來源。** RDAP 提供更標準化的資料格式、國際化與差異化存取能力。

[image](https://www.google.com/s2/favicons?domain=https://www.icann.org\&sz=32)

ICANN



查詢入口：[ICANN Lookup](https://lookup.icann.org/en?utm_source=chatgpt.com)

考試看到 WHOIS，不要因此誤認為它是 DNS 紀錄類型；兩者處理的問題完全不同。

### **2. DNS：網際網路的名稱與服務資料系統**

DNS（Domain Name System）可以先想成網際網路的通訊錄。

你輸入：

`www.example.com`

電腦必須知道它應該連線到哪個 IP 位址。

而 DNS 不只是把網域名稱轉成 IP，也提供郵件路由、名稱伺服器與其他服務相關資料。

我們接著深入理解。

## **六、K07–K08：DNS——本份最需要精讀的技術核心**

### **1. DNS 八種常見紀錄**

不必先記縮寫，先理解每種紀錄在回答什麼問題。

| 紀錄    | 白話文功能      | 問題                   |
| ----- | ---------- | -------------------- |
| A     | 對應 IPv4 位址 | 這個名稱的 IPv4 是什麼？      |
| AAAA  | 對應 IPv6 位址 | IPv6 是什麼？            |
| MX    | 郵件交換伺服器    | 寄到這個網域的信應交給誰？        |
| NS    | 權威名稱伺服器    | 誰負責提供這個區域的權威 DNS 資訊？ |
| SOA   | DNS 區域管理資訊 | 區域版本、主要伺服器與計時設定是什麼？  |
| TXT   | 文字型資料      | 有哪些文字設定？例如 SPF 等     |
| CNAME | 別名         | 這個名稱別名指向哪個名稱？        |
| PTR   | 反向名稱查詢     | 某 IP 位址對應什麼名稱？       |

這些主要定義可對照 [RFC 1035 §3.3–3.4](https://www.rfc-editor.org/rfc/rfc1035?utm_source=chatgpt.com)。

[image](https://www.google.com/s2/favicons?domain=https://www.rfc-editor.org\&sz=32)

implementation and specification



### **2. 為什麼 MX 特別重要？**

假設你經營一間公司，電子郵件地址是：

`research@example.com`

別人寄信進來時，寄件方的郵件系統需要找出負責接收 `example.com` 郵件的伺服器。

DNS 可能提供以下假設資料：

```
example.com.       MX 10 mail.example.com.
mail.example.com.  A 192.0.2.25
```

**寄件端郵件伺服器**

要寄信到 research\@example.com

**DNS：查詢 MX**

回傳 mail.example.com

**DNS：查詢 A／AAAA**

取得郵件主機的 IP 位址

**嘗試連線郵件伺服器**

DNS 查詢成功，不保證 SMTP 服務實際可用

請特別注意：

**MX 紀錄通常提供郵件伺服器的主機名稱，不是直接提供該伺服器的 IP 位址。**

想知道 IP，還需要解析那個主機名稱。

### **3. SOA 和 NS 到底有什麼不同？**

這兩個容易混淆。

**NS（Name Server）** 是在說：「哪些名稱伺服器對這個 DNS 區域具有權威？」

**SOA（Start of Authority）** 則像是 DNS 區域的管理表頭，包含主要名稱伺服器、管理聯絡資訊表示方式、區域序號及相關計時參數。

例如 SOA 裡的：

- Serial：區域資料版本序號。
- Refresh：次要伺服器在傳統區域同步機制下的更新檢查間隔。
- Retry：更新失敗後重試的間隔。

因此，如果題目問「區域序號與 Refresh Interval」，應聯想到 SOA。

如果問「所有權威名稱伺服器」，就要想到 NS。

如果問「郵件伺服器」，則是 MX。

這三種紀錄不能互相取代。

你的附件 P2-Q006 同時要求郵件主機、權威名稱伺服器與區域管理資訊，因此原題存在複合需求造成的歧義。**SOA 可以回答其中的管理資訊問題，但不能取代完整的 MX 與 NS 查詢。**

### **4. DNS 能不能查出員工帳號密碼？**

一般而言，不能把 DNS 當成公司的帳號密碼目錄。

但這裡有兩個重要細節：

第一，DNS 可以顯示一些公開子網域、服務名稱與 IP 位址，不代表能取得內部完整架構。

第二，DNS TXT 等資料也可能因錯誤配置而意外洩漏敏感字串，所以不應把「DNS 絕對不可能出現密碼」當成技術定律。

同理，DNS 可以提供 IP 位址，但是伺服器實際地理位置通常需要其他資料來源推估。

因此附件 EC-Q513 與 EC-Q198 的選項存在判斷問題：**帳密不是 DNS 的正常資料用途，但地理位置也不是 DNS 直接保證提供的資訊。**

### **5. DNS Enumeration：列舉到名稱，不等於確認服務存在**

假設第三方資料顯示：

`legacy-api.example.com`

你最多可以先形成假設：

「過去或目前可能有一個名叫 legacy-api 的對外名稱。」

你還不能直接認定：

- 這個服務目前仍在運作。
- 它一定部署於公司內網。
- 它有可利用的弱點。
- 你有權對它進行測試。

這也是 DNS Enumeration（DNS 列舉）的核心限制。

本份 EC-Q140 涉及 Netcraft、DNSdumpster 等工具。題庫的方向是利用第三方資訊尋找子網域，但工具是否真正被動，仍取決於實際操作模式，不能只靠工具品牌判斷。

## **七、K05–K06：Google Dorking、Alerts 與 robots.txt**

### **1. Google Dorking 是什麼？**

一般搜尋引擎使用者可能輸入：

`Python 教學`

但研究者會使用搜尋運算子，讓搜尋範圍更精確。

例如：

```
site:example.com filetype:pdf
```

意思是尋找搜尋引擎已索引、符合條件的 PDF 頁面。

另外：

`intitle:` 是將搜尋條件限制到網頁標題。

Google Dorking 的核心是**利用搜尋引擎已建立的索引尋找資訊**。

它不是直接入侵網站，也不是 SQL Injection 或 Vulnerability Scanning。

Google Alerts 則偏向內容變化通知；它不能保證監測網站所有更新，也不能取代完整的網站監控系統。

### **2. robots.txt 為什麼是資安常考題？**

想像一間圖書館在門口貼了一張告示：

「請自動整理書籍的機器人，不要進入地下室。」

這張告示不是門鎖。

robots.txt 也是如此。

例如：

```
User-agent: *
Disallow: /admin/
Disallow: /backup/
```

這是在告訴遵守規則的爬蟲不要抓取這些路徑。

但是，如果伺服器沒有做好存取控制，這些路徑仍可能被直接存取。

**robots.txt**

爬蟲行為規則，不提供身分驗證

**Authentication + Authorization**

確認你是誰，以及是否有權讀取資源

這不是單純的考試技巧，而是 Security by Obscurity（依靠隱藏資訊維持安全）的典型問題。

RFC 9309 §3 明確說明，robots.txt 並不能取代真正的內容安全措施。

[image](https://www.google.com/s2/favicons?domain=https://www.rfc-editor.org\&sz=32)

RFC Editor



而且要區分三個不同攻擊概念：

- **Directory Traversal：** 利用路徑處理問題，存取原本不允許的位置。
- **SQL Injection：** 利用未妥善處理的輸入，干預資料庫查詢。
- **CSRF：** 誘使已登入的使用者瀏覽器發出非預期請求。

這三者都不是「單純從 robots.txt 看到了某個路徑」的同義詞。

## **八、K09–K11：TCP、UDP 與 Nmap——開始接觸網路協定**

前面我們主要是在找資訊。

現在我們進入第二個問題：

**假設知道一個 IP 位址，該如何理解它是否回應，以及哪些網路服務可能在運作？**

### **1. TCP Three-way Handshake**

TCP（Transmission Control Protocol）是傳輸層協定，提供可靠、有序的位元組串流。

建立一般 TCP 連線需要三向交握。

TCP 一般連線建立流程示意圖

白話來說：

1. Client 發送 SYN：「我想建立連線。」
2. Server 回傳 SYN-ACK：「收到，我也準備好了。」
3. Client 回傳 ACK：「確認收到。」

接著雙方才進入已建立連線的狀態。

但請注意：**TCP 連線成功不等於 TLS 加密成功，也不等於通過登入驗證。**

### **2. UDP 跟 TCP 哪裡不同？**

UDP（User Datagram Protocol）不使用 TCP 的三向交握，也不提供 TCP 那種內建的可靠有序傳輸。

你可以先把它理解成：

- TCP：在傳輸層維持連線狀態與可靠資料傳輸。
- UDP：以資料報傳送，較少傳輸層機制；可靠性等能力可以由上層協定另外提供。

DNS 經常使用 UDP，但也可以使用 TCP。

另外幾個需要記住的協定：

| 協定   | 功能               |
| ---- | ---------------- |
| ICMP | 網路錯誤、診斷與 Echo 訊息 |
| IGMP | IPv4 多播群組管理      |
| SNMP | 網路設備監測與管理        |

### **3. Ping Sweep：主機有沒有回應？**

假設你管理一個測試網段：

`192.0.2.0/28`

你想了解其中哪些位址有主機回應。

傳統 Ping Sweep 會對一批 IP 發出 ICMP Echo Request。

如果收到 Echo Reply，就有證據支持該次探測的目標路徑存在可回應節點。

但是，如果沒有收到回應，是否代表電腦關機？

不一定。

可能是：

- 防火牆封鎖 ICMP。
- 回應被限速。
- 封包遺失。
- 主機根本不支援或不回應該類探測。

這是網路探測非常重要的推論限制。

事實上，Nmap 的主機探索也支援 TCP、UDP 及區域網路探索等方法，不只使用 ICMP。

### **4. SYN Scan 為什麼稱作 Half-Open Scan？**

這是 CEH 很常考的技巧。

在前面的 TCP 三向交握裡，正常流程會完成三個步驟。

但 SYN Scan 的想法是：

「我先送出 SYN，觀察對方怎麼回答，就可能知道連接埠狀態，不必完成一般三向交握。」

以可連線的埠為例，對方可能回傳 SYN-ACK。

掃描端因此可以推論該連接埠處於開放狀態，再送出 RST 結束這次嘗試，而不完成一般 TCP 連線建立。

這就是 Half-Open 的基本概念。

要知道另一種重要回應：如果目標回傳 RST，通常表示該埠關閉；若受到封包過濾，則可能出現無回應或特定 ICMP 錯誤。

### **5. Nmap 四個旗標一定要記住**

| 指令選項  | 名稱               | 重點            |
| ----- | ---------------- | ------------- |
| `-sT` | TCP Connect Scan | 使用完整 TCP 連線建立 |
| `-sS` | SYN Scan         | 不完成一般三向交握     |
| `-sU` | UDP Scan         | 探測 UDP 連接埠    |
| `-sA` | ACK Scan         | 主要判斷封包過濾狀態    |

最容易混淆的是 `-sS` 和 `-sA`。

SYN Scan 可用來判斷 TCP 連接埠是否開放；ACK Scan 主要分析是否有封包過濾，通常不是用來確定連接埠是否開放。

而「Stealth」不是隱形的意思。IDS、IPS、Firewall 或其他監控設備仍可能記錄 SYN 探測。

這些差異可在 [Nmap 官方掃描技術文件](https://nmap.org/book/man-port-scanning-techniques.html?utm_source=chatgpt.com) 核對。

### **6. 博士班要更進一步分清五個證據層級**

| 層級 | 你知道了什麼？        | 還不能證明什麼？      |
| -- | -------------- | ------------- |
| 1  | 某 IP 回應探索封包    | 不代表所有服務可用     |
| 2  | 某 TCP 埠呈現 open | 不代表服務類型已確認    |
| 3  | 服務類型與版本有證據支持   | 不代表一定存在漏洞     |
| 4  | 發現某個具體弱點       | 不代表已可成功利用     |
| 5  | 在授權範圍驗證可利用性    | 不代表所有環境都具相同風險 |

這張表非常重要。

資安工具顯示「open」或「vulnerable」，都需要放回具體的測試方法、觀測視角與證據限制來理解。

## **九、K12–K13：密碼學複習——加密磁碟與安全分發金鑰**

這兩個單元來自本份的三題複習題，其中 K12 與 K13 是密碼學主題。

### **1. 磁碟加密究竟保護什麼？**

Disk Encryption（磁碟加密）的主要目的，是保護儲存資料，尤其是在設備遺失、磁碟被取走等情境下的資料機密性。

例如 AES-256，指的是使用 256-bit 金鑰的 AES 演算法，不是一套磁碟加密產品。

常見產品包括 BitLocker、FileVault 與 VeraCrypt。

附件的 EC-Q024 特別描述：

- Encrypted Container（加密容器）
- Hidden Volume（隱藏卷）
- AES-256

其中 VeraCrypt 有明確的 Hidden Volume 功能文件。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



但是題目的情境有更大的問題：

**如果伺服器已經遭到攻擊者控制，而且加密卷目前仍處於掛載狀態，新增磁碟加密未必能阻止攻擊者繼續讀取明文。**

因為合法程式能讀取的資料，取得足夠權限的惡意程式也可能讀取。

VeraCrypt 官方甚至明確提醒，在受惡意程式控制的電腦上，可能無法保障資料安全。

[image](https://www.google.com/s2/favicons?domain=https://veracrypt.io\&sz=32)

veracrypt.io



這就是為什麼要區分：

- Encryption at Rest：保護靜態儲存資料。
- Runtime Access Control：控制系統運作時誰可以讀取資料。
- Incident Response：遭入侵後的隔離、調查及處置。

三者不能互相取代。

### **2. 非對稱加密為什麼能協助建立共享金鑰？**

對稱式加密使用雙方共享的秘密金鑰。

例如 Alice 和 Bob 想用 AES 傳送機密訊息。

問題是：他們怎麼安全取得同一把金鑰？

這就是 Key Establishment（金鑰建立）要解決的問題。

非對稱式密碼技術利用公鑰和私鑰之間的數學關係，可以實作安全的金鑰傳遞或金鑰協議。

要特別分清兩種機制：

- **Key Transport：** 一方產生秘密金鑰材料，再透過受保護的方法交給另一方。
- **Key Agreement：** 雙方交換必要資訊，合作導出共享秘密，例如 ECDH。

實務上的安全通訊通常是混合式設計：利用公開金鑰密碼技術建立或驗證共享秘密，再使用對稱式加密處理大量資料。

Hash Function（雜湊函數）則是另一種工具，不能把它當成可以逆向解密、把秘密金鑰送到對方手中的機制。

NIST SP 800-57 Part 1 Rev. 5 對金鑰建立、分配與管理有更完整的區分。

## **十、博士班程度的提升：從 CEH 知識轉成可靠的安全研究方法**

這一節是超出考題字母選擇、但與今天所有觀念直接相關的研究思維。

我們可以把整份教材抽象成以下模型：

證據到決策模型（Evidence-to-Decision）

1\. Evidence

取得了什麼原始證據？

2\. Provenance

證據來自哪裡、什麼時間？

3\. Interpretation

證據可以支持哪些解釋？

4\. Uncertainty

還有哪些其他合理解釋？

5\. Validation

什麼測試可以區分這些解釋？

6\. Authorization

這個測試有沒有獲得授權？

以剛才的醫院 AI 服務為例：

| 證據               | 可支持的判斷               | 不可直接推論        |
| ---------------- | -------------------- | ------------- |
| 徵才提到 Kubernetes  | 公司可能有相關技術需求          | 正式環境一定在 K8s   |
| DNS 有 mail 主機名稱  | DNS 宣告了郵件路由目標        | SMTP 一定可用     |
| ICMP 沒有回應        | 本次探測沒收到回覆            | 主機一定離線        |
| SYN Scan 顯示 open | 該埠在測試視角下可接受 TCP 起始交握 | 服務一定有漏洞       |
| 磁碟已加密            | 資料在某些靜態儲存情境受到保護      | 已入侵主機上的明文必然安全 |

從研究方法來看，這些都是「觀察資料不足以唯一決定系統真實狀態」的例子。

如果你未來研究 AI Agent Security，可以把這套方法做成機器可檢查的主張：

```
Claim:
  mail.example.com 的 SMTP 服務正在運作

Evidence:
  DNS MX -> mail.example.com

Assessment:
  證據不足

Reason:
  MX 只顯示郵件路由設定，
  未證明目前的 SMTP 服務可連線。

Next Validation:
  依授權範圍進行服務可用性測試。
```

這就是將 OSINT 與掃描結果提升為 **Evidence-Grounded Security Reasoning（證據導向安全推理）**。

真正有研究價值的問題不只是「AI Agent 會不會使用 Nmap」，而是：

「AI Agent 能不能辨識不同證據的適用範圍、限制過度推論，並在每次行動前檢查授權條件？」

這個研究問題同時連結了 Agent Governance、工具調用安全，以及可稽核的決策系統。
