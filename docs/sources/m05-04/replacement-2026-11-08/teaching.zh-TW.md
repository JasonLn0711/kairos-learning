# M05-04｜CVE、CWE、CPE 與弱點資料庫

這一課將幫助你在辨認資安名詞後，進一步理解當弱點掃描工具告訴你「系統有漏洞」時，你要如何判斷這個警告是不是真的。

先記住一個觀念：

掃描器說你的系統「可能有漏洞」，不代表系統真的存在該漏洞；即使確認有漏洞，也不代表駭客已經入侵。

## 一、用汽車召回事件，一次搞懂三個名詞

假設你買了一台 Toyota 汽車。

某天新聞報導：「某款 Toyota 汽車的煞車系統存在安全缺陷，車廠宣布召回。」

這時候你會想知道：

1. 這次是哪一件召回事件？
2. 煞車究竟是哪一類問題？
3. 我的車型和年份是否也有問題？

資訊安全領域剛好有三套對應的標準。

| 名詞  | 汽車的比喻        | 在資安領域代表            |
| --- | ------------ | ------------------ |
| CVE | 召回事件的案件編號    | 某一個公開漏洞的編號         |
| CWE | 煞車設計或製造錯誤的類型 | 漏洞背後的缺陷類型          |
| CPE | 車廠、車型、年份及規格  | 軟體、硬體或作業系統的標準化產品名稱 |

{{figure:roles}}

注意：CVE、CWE、CPE 都不是駭客使用的攻擊工具，它們是讓研究人員、軟體廠商、資安工程師與弱點掃描器能交換資訊的共同語言。

## 二、CVE：每個公開漏洞的「案件編號」

CVE 全名是 Common Vulnerabilities and Exposures，中文常稱「通用漏洞與曝險」。

你可以把它想成警察辦案時使用的案件識別編號。

假設某間軟體公司發現，自己的產品存在一個漏洞：

「未登入的使用者，在特定條件下可能讀取不應公開的文件。」

如果沒有共同編號，可能會出現：

- A 廠商稱它為「文件外洩問題」。
- B 掃描器稱它為「未授權讀取漏洞」。
- C 研究員稱它為「權限驗證缺陷」。

三個人可能在討論同一件事，但使用不同名稱。

CVE 就是用來降低這種混亂的。

### CVE 編號怎麼看？

{{figure:identifier}}

CVE 不會直接告訴你：

- 你的電腦是否安裝了有問題的軟體。
- 你的軟體是否已經修補。
- 駭客是否已經利用這個漏洞。
- 漏洞的嚴重程度是多少。

它的首要作用，是讓大家知道正在討論的是哪個漏洞。

### CVE 也有不同狀態

| 狀態        | 白話說明                 |
| --------- | -------------------- |
| Reserved  | 編號先保留下來，細節可能還沒公布     |
| Published | 漏洞紀錄正式公開             |
| Rejected  | 這個編號已被判定不應繼續作為有效漏洞紀錄 |

有些編號遭 Rejected，是因為重複登錄、紀錄有誤或其他原因。應查看原始說明及是否有替代編號。

還有一個專業名詞叫 CNA（CVE Numbering Authority），就是在指定範圍內負責分配及發布 CVE 紀錄的組織。你現在只需要知道：CVE 不是任何人隨意取一個數字就算成立。

[CVE 狀態與 CNA 說明](https://www.cve.org/Resources/Media/Archives/OldWebsite/about/faqs.html)

## 三、CWE：漏洞背後「犯了哪一類錯誤」

CWE 全名是 Common Weakness Enumeration，中文是「通用弱點列舉」。

假設你是修車師傅。

今天有三輛不同品牌的車，都出現煞車失靈。

三件召回事件各有自己的案件編號，但仔細調查之後，你發現三個問題都源於相似的設計缺陷。

這時候，三個不同的 CVE 就可能對應同一類 CWE。

### 以 CWE-79 為例：XSS 跨網站指令碼

想像你經營一個留言網站。

正常情況下，訪客留言：

> 今天的天氣很好。

網站就應該把它當成普通文字，顯示在畫面上。

但是某個網站沒有正確處理使用者輸入的內容，導致有人輸入的網頁程式碼，被其他訪客的瀏覽器當成指令執行。

這就可能形成 XSS（Cross-Site Scripting）。

問題的根源，不是留言功能本身，而是程式沒有妥善區分「使用者提供的資料」和「可以執行的網頁程式碼」。

MITRE 將這類缺陷整理為 CWE-79。

理解這個差異很有用：

CVE 主要幫你找到某次具體的漏洞及修補資訊；CWE 則能幫工程師思考如何從程式設計、輸出編碼、框架選擇及安全測試等層面，降低同類問題反覆發生的機率。

而且，不是每個 CWE 都一定對應某個 CVE。你自己開發的系統即使沒有公開 CVE，也可能存在 CWE 所描述的缺陷。

[MITRE CWE-79](https://cwe.mitre.org/data/definitions/79.html)

## 四、CPE：辨認「到底是哪個產品、哪個版本」

CPE 全名是 Common Platform Enumeration，中文是「通用平台列舉」。

我們再回到汽車的例子。

如果車廠宣布：

「2023 年生產的某款車型存在煞車問題。」

你總不能因為自己也是同一個品牌，就認為自己的車一定需要召回。

軟體也是如此。

假設某間公司使用三套不同版本的文件伺服器：

| 設備    | 安裝版本 | 公告影響 2.4～2.6 |
| ----- | ---- | ------------ |
| A 伺服器 | 2.3  | 初步不符合        |
| B 伺服器 | 2.5  | 初步符合         |
| C 伺服器 | 2.7  | 初步不符合        |

為了讓掃描器和資料庫能使用一致的方式描述產品，就需要 CPE。

### CPE 長什麼樣子？

假設有一個虛構產品，叫做 Orange Document Server 2.4。

我們可以用教學用的 CPE 2.3 字串表示：

```
cpe:2.3:a:orange:document_server:2.4:*:*:*:*:*:*:*
```

你先認識最重要的部分：

- `cpe:2.3`：CPE 命名格式版本。
- `a`：Application，應用程式（`o` 是作業系統，`h` 是硬體）。
- `orange`：廠商。
- `document_server`：產品。
- `2.4`：版本。

後面的欄位還能描述更新、版本類型、語言及其他條件。完整格式不需要現在背下來。

有兩件事情要特別注意：

第一，CPE 不是設備身分證。 公司有十台電腦安裝相同版本的軟體，它們可能符合相同的 CPE，但仍然是十台不同設備。

第二，CPE 比對成功，不代表漏洞一定存在。 因為真正是否受影響，還可能取決於功能是否啟用、套件是否修補，以及其他軟體或平台條件。

[NIST CPE 2.3 命名規格](https://csrc.nist.gov/pubs/ir/7695/final)

## 五、NVD：整合公開漏洞資訊的資料庫

前面認識了三種識別方式，但你可能會想：

「這麼多 CVE，我要到哪裡查？」

答案之一，就是 NVD。

NVD 全名是 National Vulnerability Database，美國國家漏洞資料庫，由 NIST 維護。

你可以把它想成一個資安資料整理中心。

{{figure:lookup}}

上圖是建議的查證順序，不代表 NVD 必然完整，也不代表廠商公告一定比其他來源更新。

例如在真實的 [CVE-2021-44228 的 NVD 頁面](https://nvd.nist.gov/vuln/detail/CVE-2021-44228)，就能查到 Log4Shell 的描述、嚴重度、產品適用條件及相關公告。Apache 自己的安全公告還進一步說明，受影響的是 `log4j-core` 元件，不能把所有名稱中有 Log4j 的元件都當成同樣受影響。

### 為什麼不能只相信 NVD？

因為資料庫也需要時間整理資料。

NIST 在 2026 年 4 月 15 日宣布，NVD 改以風險為導向，優先補充已知遭利用漏洞、聯邦政府使用的軟體等紀錄。其他 CVE 仍會列入，但可能不會立即補上全部分析資訊。

所以，NVD 沒有顯示完整 CPE 或嚴重度資料，不等於漏洞不存在，也不代表風險是零。

[NIST 2026-04-15 NVD 政策](https://www.nist.gov/news-events/news/2026/04/nist-updates-nvd-operations-address-record-cve-growth)

[Apache 安全公告](https://logging.apache.org/security.html)

## 六、完整模擬案例：掃描器告訴你「有漏洞」，你該怎麼做？

現在假設你是某公司的資安工程師。

公司有一台對外提供服務的文件伺服器。

弱點掃描器回報：

{{figure:finding}}

乍看之下，2.4 在受影響範圍內，你可能想直接在報告寫「已確認存在漏洞」。

但這樣太快了。

### 第一步：確認版本是不是真的

掃描器可能只是看到網站回應：

`Server: Orange Document Server 2.4`

這個文字不一定等於目前實際執行的完整軟體版本。它可能是舊資訊、被設定成固定值，或忽略了套件修訂號。

因此需要確認實際安裝的產品與套件版本，而不是只相信網站提供的字串。

### 第二步：確認漏洞成立的條件

公告指出：只有啟用「文件預覽」功能時才會受影響。

那就需要檢查設定。

如果功能沒有啟用，這條攻擊路徑可能不成立；但你還不能因此斷言整個產品絕對安全。

### 第三步：確認修補狀態

這裡要認識一個重要觀念：Backport，中文常稱「安全修補回移」。

假設某套軟體版本是 2.4，原廠後來將 2.7 的某個安全修補移植回 2.4 維護分支。

結果可能出現：

- 版本看起來仍然是 2.4。
- 但套件已包含修正漏洞的程式碼。

這不是理論上的例外。Linux 發行商確實會採取 Backport 策略，因此單看上游版本號可能造成掃描器誤報。

反過來說，系統管理員口頭表示「我們有更新」，也不是足夠證據。還需要確認實際安裝的完整套件版本、更新紀錄，必要時確認執行中的服務是否已載入更新。

### 第四步：依照證據下結論

現在把情況分成三種。

| 查證結果                 | 合理結論               |
| -------------------- | ------------------ |
| 只知道掃描器偵測到 2.4        | 疑似受影響，待確認          |
| 確認未修補、預覽功能也已開啟       | 符合已知漏洞成立條件，可判定受影響  |
| 確認已有對應修補，而且正在執行修補後版本 | 可認定該公告漏洞已修復，仍需記錄證據 |

這三種結果的差異，就是資安工程師和單純操作掃描器的人最重要的能力差距。

[Red Hat 安全修補回移](https://access.redhat.com/security/updates/backporting)

## 七、寫資安報告時，怎麼區分證據的強度？

這裡有一個非常實用的觀念：發現弱點、確認弱點、證明可利用、確認已遭入侵，是四個不同層次。

{{figure:evidence}}

這是一個方便教學的證據層次模型，不代表所有弱點都必須執行利用測試才能成立，也不表示單靠成功利用就能推論以前已有駭客入侵。

### 一份比較專業的弱點紀錄

沿用前面的虛構案例：

| 欄位   | 記錄內容                   |
| ---- | ---------------------- |
| 資產   | 文件伺服器 A                |
| 疑似弱點 | 文件預覽功能的權限控制缺陷          |
| CVE  | 教學公告，未使用真實編號           |
| 版本證據 | 掃描器偵測為 2.4，尚待主機端確認     |
| 已知條件 | 公告指出 2.4～2.6 且啟用預覽時受影響 |
| 未知條件 | 預覽功能、修補與執行狀態           |
| 目前結論 | 疑似受影響，尚未確認             |
| 建議   | 先完成版本與設定查核，再依結果修補或排除   |

你在正式滲透測試報告裡，可以這樣寫：

> 經初步偵測，目標系統回應資訊與公開安全公告所列的受影響產品版本相符。然而，目前尚未完成實際套件版本、功能設定及修補狀態查核，亦未進行漏洞利用驗證。因此，本項列為疑似弱點，建議由系統維護單位進一步確認並提供相關證據。

這種寫法同時做到三件事：揭露安全疑慮、不誇大已取得的證據，以及清楚指定接下來要查什麼。

## 八、這一課的知識整理

| 遇到的問題           | 應該想到          |
| --------------- | ------------- |
| 這是哪個公開漏洞？       | CVE           |
| 這屬於哪類程式設計或系統缺陷？ | CWE           |
| 可能影響哪些產品與版本？    | CPE           |
| 哪裡可以查詢公開漏洞資訊？   | CVE 官方、NVD    |
| 應該如何修正？         | 廠商安全公告及修補說明   |
| 我的設備是否真的受影響？    | 資產、版本、設定及修補證據 |
| 是否已被駭客利用？       | 事件紀錄、鑑識與入侵調查  |

官方學習資源可由 [CVE 官方網站](https://www.cve.org/)、[MITRE CWE](https://cwe.mitre.org/)、[NVD 弱點資料庫](https://nvd.nist.gov/) 開始查閱。

## 九、理解檢核

假設你幫一間公司做弱點掃描，發現：

某台 Ubuntu 伺服器的 Nginx 被辨識為較舊版本。掃描器據此列出一個 CVE，評為高風險。

但系統管理員說：「我們已經透過 Ubuntu 的安全更新修補過了，只是 Nginx 主要版本號沒有變。」

請回答兩個問題：

1. 你應該直接相信掃描器，還是直接相信系統管理員？為什麼？
2. 你會向系統管理員索取哪兩項關鍵證據，判斷這個漏洞是否真的已經修補？

請先寫下你的判斷與所需證據，再於後續討論核對推理；本頁不提供自動送出或批改功能。

這一課最重要的一句話是：

CVE 告訴你要調查哪個漏洞，CWE 告訴你要理解哪類缺陷，CPE 幫你找出可能受影響的產品；但只有現場證據，才能讓你對這台設備做出可靠的判斷。
