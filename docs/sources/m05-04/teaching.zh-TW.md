# M05-04｜CVE、CWE、CPE 與弱點資料庫

從資產盤點及弱點分類接著回答：**看到安全公告的編號，怎麼判斷它和自己的系統有沒有關係？**

先記住：**CVE 辨認「哪個已公開漏洞」，CWE 說明「哪一類缺陷」，CPE 描述「哪種產品與版本」。三者幫助對照，不能單靠其中一項就宣布你的系統已遭入侵。**

## 一、先用汽車召回理解

想像車廠發布召回：某款車的煞車零件可能有問題。你會問三件不同的事：是哪一件召回事件？問題屬於哪種設計或製造缺陷？我的車型、年份與零件版本是否符合條件？

軟體也需要共同語言。同一漏洞可能被廠商、研究人員及掃描工具用不同標題描述；沒有共同識別碼，很容易重複計算或把不同問題混在一起。這個比喻只用來分辨角色，CVE 不是法律上的召回命令，CPE 也不是某一台設備的車身號碼。

## 二、CVE：讓大家知道在談同一個漏洞

CVE 是 Common Vulnerabilities and Exposures，通常稱為「通用漏洞與曝險」。CVE ID 是公開漏洞的共同識別碼，格式像 `CVE-年份-流水號`，流水號至少四位。它不是嚴重度分數，也不代表被攻擊次數；年份不能直接當成漏洞首次被發現或你的系統開始受影響的日期。

CNA 是 CVE Numbering Authority，指在指定範圍內負責分配 CVE 編號及發布紀錄的組織。公開紀錄提供漏洞描述與參考資料，讓不同工具和團隊對得上同一個問題。

查閱時也要看狀態：Reserved 表示編號已保留，不等於完整細節已公開；Published 是紀錄已公開；Rejected 表示該編號不應再作為有效漏洞紀錄使用，需要看原因及替代參照。[CVE 官方識別碼說明](https://www.cve.org/Resources/Media/Archives/OldWebsite/cve/identifiers/index.html)與[官方詞彙表](https://www.cve.org/ResourcesSupport/Glossary?activeTerm=glossaryRBP)。

有 CVE 不表示你一定受影響；沒有 CVE 也不表示沒有弱點。例如自製程式的權限缺陷可能尚無公開編號，仍然需要處理。

## 三、CWE：看懂是哪一類錯誤

CWE 是 Common Weakness Enumeration，通常稱為「通用弱點列舉」。它整理常見的軟體與硬體缺陷類型，幫助理解成因及改善方向，不是單一產品的漏洞個案清單。[MITRE CWE 說明](https://cwe.mitre.org/about/index.html)。

例如 CWE-79 涉及產生網頁時，沒有正確處理使用者可控制的內容，可能造成 Cross-Site Scripting，也就是 XSS「跨網站指令碼」。白話說，原本應顯示為資料的內容，卻可能被瀏覽器當成有作用的網頁程式碼。這裡先認識類型，實際機制留到 Web 安全章節。[CWE-79](https://cwe.mitre.org/data/definitions/79.html)。

不同產品的許多 CVE 可以對應同一 CWE，就像不同車廠可能犯相似的設計錯誤。一個漏洞也可能涉及多種缺陷，對應結果可能更新。所以不能把 CWE 當特定事件，更不能因兩份報告的 CWE 相同就合併。

團隊如果反覆出現同一類問題，可以回頭改善設計、框架與測試方式，而不只是每次修一個畫面。

## 四、CPE：把產品名稱寫成工具能比對的格式

CPE 是 Common Platform Enumeration，通常稱為「通用平台列舉」，提供作業系統、硬體與應用程式的標準化命名。常見資訊包括廠商、產品、版本及其他平台條件。本課採用 [NIST CPE 定義](https://csrc.nist.gov/glossary/term/common_platform_enumeration)及 [CPE 2.3 命名規範](https://csrc.nist.gov/pubs/ir/7695/final)的基本觀點。

先不必背整串格式，把它想成「讓不同系統對得上商品型號的標籤」。但 CPE 不是主機的 IP、MAC 位址或唯一資產編號，也不是漏洞編號。兩台相同產品與版本的設備可以對應相同 CPE，仍是兩個不同資產。

工具可能辨識錯誤或資訊不完整。產品名稱吻合之後，還要檢查版本範圍、分支、功能設定、平台及修補狀態。受影響條件也可能是多個條件的組合，不一定是「產品字串相同就中」。

## 五、資料庫和廠商公告，各自提供什麼？

1. CVE Record（CVE 紀錄）：確認漏洞個案、紀錄狀態及引用來源。
2. NVD（National Vulnerability Database，美國國家漏洞資料庫）：以 CVE 資料為基礎，提供可用的分析與結構化資訊，例如產品適用性及嚴重度資料。它與 CVE 計畫不是同一項服務。
3. 廠商安全公告：確認受影響版本、修補版、設定條件及處理建議。套件由作業系統發行商維護時，也要讀該發行商的說明。
4. 自己的資產與變更紀錄：確認真正安裝、執行的是什麼，以及更新是否已套用。公開公告不會自動知道這台主機的現況。

資料庫欄位不一定即時完整。NIST 在 2026 年 4 月調整 NVD 補充分析方式，不是每個紀錄都會立即補齊，也不再例行為已有 CNA 評分的項目重複提供另一份分數。欄位空白或尚未排入立即補充，不能推論你的系統沒有風險。[NIST 2026 年 4 月公告](https://www.nist.gov/news-events/news/2026/04/nist-updates-nvd-operations-address-record-cve-growth)。

來源不一致時，記下更新日期、產品分支和原文差異，確認是不是在比較不同條件，再保留待釐清事項。不要挑自己喜歡的答案。下一課才進一步討論嚴重度與處理優先順序。

## 六、完整案例：收到警告，怎麼查才不會誤判？

以下產品、版本和公告都是合成情境，沒有對應真實 CVE，也沒有執行掃描。

某測試服務使用「橙子文件伺服器 2.4」。掃描器回報可能符合某公告。教學公告寫：「2.4 至 2.6 在啟用預覽功能時受影響，2.7 已修正。」

第一步，確認觀察內容。工具看到的是回應字串 2.4，還是管理端提供的完整套件版本？回應字串可能只是線索，不能直接寫已成功入侵。

第二步，讀漏洞個案。對照 CVE 紀錄及原廠公告，確認同一產品和版本分支，查看是否有撤回或更新說明。

第三步，核對條件。即使確定是該分支 2.4，還要查預覽功能、修補狀態及入口存取條件。關閉功能可能降低這條路徑的風險，但不能證明整個產品沒有其他問題。

第四步，留意 backport。Backport 是把安全修正移植回較舊的維護版本；主要版本可能沒變，完整套件修訂號與安全公告卻已表明修補。因此「看起來舊」不一定等於「未修補」。反過來，也不能只聽說有 backport 就認定這台已裝上更新，仍需安裝與執行狀態的證據。

第五步，寫有界線的結論。如果版本已確認，但功能與修補狀態不明，可以寫：「產品版本符合公告初步比對條件；功能啟用與修補狀態待確認，尚未進行利用驗證。」不能寫成已遭入侵，也不能直接刪掉警告。

若需驗證實際可利用性，仍遵守授權範圍與停止條件。查到公開利用程式，不代表獲准在正式環境執行。

## 七、防護端要留下的證據

一筆可複核紀錄可包含：資產編號、實際產品與完整版本、CVE 與紀錄狀態、CWE 類型（有資料才填）、產品匹配依據、成立條件、公告連結與查核日期、已確認／待確認事項、處理建議及修補後證據。

三者不是一對一：同一產品可能有多個漏洞；同一漏洞可能影響多個產品版本；同一類缺陷可能反覆出現。不要用 CVE 數量直接當作受影響設備數，也不要用 CWE 數量當漏洞個案數。

## 八、紙上練習與小檢核

拿合成公告畫三欄：「已知」「待確認」「下一步」。把版本、功能設定、修補狀態放入適當欄位，再寫一句不超出證據的結論。預期成果是一張能說明缺什麼資料的紀錄，不需安裝或執行工具，也沒有要清理的測試環境。

小檢核：掃描器把某資產對應到 CPE，並列出一個 CVE，但尚未確認功能與修補狀態。能否直接寫成「已確認可入侵」？請用一句話說明理由，以及你要補查的兩項資料。
