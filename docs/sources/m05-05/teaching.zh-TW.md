# M05-05｜CVSS、KEV、EPSS：漏洞到底該先修哪一個？

## 一、先理解：最嚴重的漏洞，不一定最需要先修

這堂課最重要的觀念是：

漏洞有多嚴重、駭客有沒有利用、你的系統有多危險，是三個不同的問題。

假設你是公司的資安工程師，今天掃描出 100 個漏洞，但是只有時間修補其中 10 個。

你會怎麼選？

可能有人說：「從 CVSS 分數最高的開始修就好了！」

問題是，有些 9.8 分的漏洞可能只存在於完全隔離的實驗室；某個 8.1 分的漏洞卻可能存在於公司對外服務的伺服器，而且駭客已經在利用這個漏洞攻擊其他企業。

這時候，後者反而更值得優先處理。

我們需要三種工具協助判斷：

CVSS — 漏洞有多嚴重？

好比門鎖的設計缺陷有多嚴重，以及被突破後可能有什麼後果。

KEV — 駭客真的利用過嗎？

好比已經有可靠消息確認，竊賊正在利用這種門鎖缺陷作案。

EPSS — 接下來被利用的可能性有多高？

好比根據過去案例與目前跡象，預測未來 30 天這類缺陷被用來作案的可能性。

{{figure:signals}}

但這三個工具都不知道你的完整公司環境。因此還需要第四個問題：

這個漏洞真的影響我的哪一台設備？這台設備有多重要、是否容易被攻擊？

這才是 Vulnerability Prioritization（漏洞處理優先順序）的核心。

## 二、CVSS：告訴你漏洞有多嚴重

CVSS 全名是 Common Vulnerability Scoring System，中文是「通用漏洞評分系統」。

你可以把它當成漏洞的技術危險程度評量表。

| CVSS 分數  | 嚴重程度         |
| -------- | ------------ |
| 0.0      | 無            |
| 0.1–3.9  | 低（Low）       |
| 4.0–6.9  | 中（Medium）    |
| 7.0–8.9  | 高（High）      |
| 9.0–10.0 | 嚴重（Critical） |

這是 CVSS 的標準嚴重度分級。 [FIRST CVSS v4.0 規範](https://www.first.org/cvss/v4.0/specification-document)

例如，假設某個漏洞是 CVSS 9.8 分。

它的意思不是「有 98% 的機率被駭」。

它是在說，根據這個版本、評分類型與向量所描述的技術條件，這是一個非常嚴重的漏洞。

### CVSS 主要評估什麼？

想像駭客要利用一台伺服器的漏洞：

- Attack Vector（攻擊途徑）： 能不能從網路上攻擊？還是必須接觸設備？
- Attack Complexity（攻擊複雜度）： 攻擊成功需要克服多少技術障礙？
- Privileges Required（所需權限）： 是否需要先取得帳號或管理權限？
- User Interaction（使用者互動）： 是否需要有人點擊、開啟檔案或進行其他操作？
- Impact（影響）： 成功後能否偷資料、竄改資料或使系統停止運作？

CVSS v4.0 的 Base 指標還包含 Attack Requirements（攻擊必要條件），並區分受漏洞影響的系統與後續受影響系統。 [FIRST CVSS v4.0 規範](https://www.first.org/cvss/v4.0/specification-document)

### CVSS v4.0 的四個層次

Base（基本）

漏洞本身具備什麼技術特性？可能造成什麼後果？

Threat（威脅）

是否已出現可用的利用技術，或實際利用活動？

Environmental（環境）

放到我的公司後，系統的重要性、防護與實際條件有什麼差別？

Supplemental（補充）

還有什麼額外資訊值得參考，例如復原困難程度？這組指標不改變 CVSS 分數。

{{figure:groups}}

這代表 CVSS 不只是公告上常看到的 Base Score。它還能結合威脅與環境資訊，讓技術嚴重度評估更符合實際部署情境，但仍不能取代完整的業務風險分析。 [FIRST CVSS v4.0 規範](https://www.first.org/cvss/v4.0/specification-document)

這一節最重要的結論：CVSS 很高，代表值得重視；但不能只憑 CVSS 決定修補先後。

## 三、KEV：這個漏洞真的被駭客利用過嗎？

KEV 是 Known Exploited Vulnerabilities，也就是「已知遭利用漏洞目錄」，由美國 CISA 維護。

假設你看到兩則公告：

- 漏洞 A：研究人員發現，可以利用某個錯誤取得管理員權限。
- 漏洞 B：研究人員發現同樣的問題，而且已經有可靠證據顯示攻擊者在真實環境中利用它。

兩個漏洞都嚴重，但 B 多了一項重要的威脅證據。

這就是 KEV 的價值。

要注意，研究人員公開 PoC（概念驗證程式），不等於漏洞已在真實攻擊中被利用。 CISA 的 KEV 收錄標準要求有實際利用證據，單純掃描或安全研究並不足以成立。 [CISA 官方 KEV 公告與收錄條件](https://content.govdelivery.com/accounts/USDHSCISA/bulletins/42a9f71)

### 如果漏洞列入 KEV，我該怎麼做？

先區分三個判斷：

| 問題         | 說明               |
| ---------- | ---------------- |
| 有列入 KEV？   | 已有外部實際利用證據       |
| 我的設備有這個漏洞？ | 需要核對版本、設定與影響條件   |
| 我的設備已被駭？   | 需要日誌、系統跡證或其他調查證據 |

這三件事不能畫上等號。

例如，公司使用的防火牆存在 KEV 漏洞，代表應該提高處理優先順序，必要時調查是否存在入侵跡證，但不能直接向主管宣布「公司已經被駭」。

同樣地，沒有列入 KEV，也不能保證攻擊者沒有利用這個漏洞。

## 四、EPSS：預測未來 30 天被利用的可能性

EPSS 是 Exploit Prediction Scoring System，由 FIRST 提供。

它運用機器學習與漏洞相關的威脅訊號，估計特定 CVE 在未來 30 天被觀察到真實利用活動的機率，而且每天更新。 [FIRST EPSS](https://www.first.org/epss/)

例如，你看到：

假設某漏洞的 EPSS

0.20

＝ 20%

代表模型預測，這個 CVE 在接下來 30 天於其觀測範圍內出現利用活動的機率約為 20%。

這是全球漏洞層級的預測，不是你的單一伺服器有 20% 的機率遭到入侵。

{{figure:probability}}

### EPSS 的兩個欄位最容易搞混

| 欄位          | 假設數值 | 意思                 |
| ----------- | ---- | ------------------ |
| Probability | 0.20 | 未來 30 天利用機率預測為 20% |
| Percentile  | 0.95 | 分數高於約 95% 的受評漏洞    |

這兩個數值只是說明用途的假設範例，並非同一筆實際評分。

Probability 是預測機率；Percentile 則是相對排名。不能把第 95 百分位解讀成 95% 被利用機率。 [FIRST Probability 與 Percentile 說明](https://www.first.org/epss/articles/prob_percentile_bins)

更重要的是，EPSS 不知道你公司的系統是否連上網際網路、是否有防火牆保護，或者裡面存放什麼資料。

另外，EPSS 為 1% 也不代表風險等於零。若已經有 KEV 等可靠實際利用證據，應優先考慮這些證據，而不是因為 EPSS 低就忽略。 [FIRST EPSS 實務指南](https://www.first.org/epss/using-epss)

## 五、真正的排序方法：四個問題依序回答

這裡給你一套可以用於真實資安工作的決策流程。

第一關：漏洞是否真的影響我的資產？

確認產品、版本、設定、受影響功能

第二關：漏洞與外部威脅訊號告訴我什麼？

CVSS、KEV、EPSS 及其他威脅情資

此處 CVSS 提供技術嚴重度背景，分數本身不是外部實際利用的證據；KEV 與 EPSS 分別回答不同的威脅問題。

第三關：攻擊者能接近嗎？影響多大？

網路曝露、權限、防護、資料與業務重要性

第四關：決定處理優先順序與措施

立即緩解、安排修補、驗證、持續追蹤

{{figure:workflow}}

這是一種定性的風險決策流程，不是官方提供的自動計分公式。

實際執行時，我建議特別注意三個因素：

Presence（存在性）： 你的系統是否真的受影響？

Reachability（可達性）： 攻擊者是否具備接觸與利用漏洞的必要條件？

Consequence（後果）： 如果成功利用，會造成多嚴重的業務或安全影響？

FIRST 的 EPSS 實務指南也強調，應將這三種本地情境與漏洞利用預測結合。 [FIRST EPSS 實務指南](https://www.first.org/epss/using-epss)

## 六、實際案例：CVSS 9.8 與 8.1，你會先修誰？

以下都是虛構的教學數據。

| 條件        | 漏洞甲   | 漏洞乙   |
| --------- | ----- | ----- |
| CVSS Base | 9.8   | 8.1   |
| KEV       | 未列入   | 已列入   |
| EPSS      | 1%    | 60%   |
| 設備        | 隔離測試機 | 對外伺服器 |
| 業務影響      | 低     | 高     |
| 漏洞適用性     | 已確認   | 已確認   |

單看 CVSS，你可能選甲。

但如果你同時考慮外部威脅與實際環境，應該優先處理乙。

原因不是 8.1 比 9.8 嚴重，而是乙同時符合幾個條件：已有實際利用證據、可從外部接觸、設備具備重要業務功能，而且漏洞尚未修復。

相對而言，甲雖然技術嚴重度較高，但目前有經過驗證的隔離措施，且業務影響較低，因此可以在可接受的風險與政策期限內安排後續修補。

但是，如果後來發現甲的隔離設定失效，或乙已有經過確認且有效的緩解措施，優先順序就必須重新評估。

### 排序之後還要做什麼？

決定乙優先，不代表立即在正式環境安裝更新、強制重新開機。

你仍然需要判斷：

1. 能否先以限制網路入口、停用受影響功能或原廠建議措施降低曝露？
2. 更新會不會造成服務中斷？是否需要測試與回復方案？
3. 修補後要用什麼證據確認漏洞已解除、系統仍正常運作？
4. 如果已知存在攻擊活動，是否需要額外檢查本機入侵跡證？

要特別分清楚：已完成緩解，不一定代表已修復；已安裝更新，也不一定代表已驗證安全。

## 八、學完這堂課，你應該帶走什麼？

CVSS、KEV、EPSS 最容易記憶的方式是：

CVSS 衡量技術嚴重度；KEV 提供已知實際利用證據；EPSS 預測未來 30 天的利用活動機率。

真正的修補優先順序則要看：

漏洞是否適用 + 攻擊者是否容易接近 + 外部威脅證據 + 成功利用的後果 + 現有防護。

因此，不要只按照 CVSS 由高到低排序，也不要把 CVSS、KEV、EPSS 隨意加權，誤以為得到一個官方認證的風險分數。

## 九、理解檢核

假設你是資安工程師，同事告訴你：

> 這個漏洞 CVSS 9.8，但 EPSS 只有 1%，而且沒有列入 KEV。所以我們完全不需要處理它。

請回答兩個問題：

1. 這位同事的結論缺少哪兩類最重要的本地環境證據？
2. 假設漏洞存在於公司內部的關鍵資料庫，而不是對外網站，你會直接降低它的修補優先順序嗎？為什麼？

請用白話文回答，核對推理是否連結漏洞適用性、可達性與後果，不只背誦定義。
