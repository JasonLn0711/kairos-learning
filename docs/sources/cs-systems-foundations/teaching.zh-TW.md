# 資工底層原理通識課：從一個位元組到完整軟體系統

Computer Science & Systems Engineering｜通用概念、第一原理、運作機制與實務判斷

這份教學將電腦系統與軟體工程涉及的技術，整理成可以適用於 Linux、macOS、Windows、網站、AI 系統與雲端服務的通用知識體系。

整套課程最重要的概念是：電腦系統由許多不同層次組成，每一層都在管理特定的資源、身分、狀態與操作。

理解各層的責任與它們如何連接，就能從「會使用工具」進一步成為「知道系統為什麼這樣運作，也能自行判斷問題原因」的人。

## 二、電腦的第一原理：程式到底是怎麼跑起來的？

### 1. CPU、RAM、SSD 各自負責什麼？

想像一間餐廳：

- CPU 是廚師，負責按照指令做事。
- RAM 是料理工作檯，存放目前正在使用的材料。
- SSD 是倉庫，保存需要長期留下的資料。
- 作業系統是餐廳管理系統，負責分派工作、管理設備及存取權限。

這個比喻可以讓我們先建立基本模型，但還有幾個重要細節。

CPU

執行指令、運算與控制

RAM

暫存程序正在使用的資料

SSD

持久保存檔案與程式

GPU

大量平行計算，常用於圖形與 AI

最重要的區別是：

資料存在 SSD，不代表 CPU 已把它載入記憶體；資料存在 RAM，也不代表 GPU 已經取得它。

假設你要執行一個 AI 語音辨識程式。

模型權重可能保存於 SSD。當程式啟動時，系統需要讀取模型檔案，建立程序所需的記憶體狀態；若使用獨立 GPU，還可能需要將相關權重或資料傳到 GPU 可存取的記憶體。

所以，兩個專案即使透過 hard link 共用同一份磁碟模型檔案，也不代表它們的 GPU 程序就會自動共用同一份顯示記憶體。

這是儲存層共享與執行期記憶體共享的差別。

### 2. Kernel（核心）是什麼？

Kernel 是作業系統的核心部分，負責管理硬體資源及提供受控的系統服務。

你的 Python 程式不能隨意直接控制所有磁碟硬體。它通常會透過作業系統提供的介面來讀寫檔案。

例如：

```
with open("data.txt", "r") as f:
    content = f.read()
```

從程式設計師的角度，只是開啟檔案、讀取內容。

但在底層，概念上會經過這條路徑：

```
Python 程式
    ↓
Python Runtime / 函式庫
    ↓
System Call（系統呼叫）
    ↓
Kernel（核心）
    ↓
檔案系統與儲存裝置
    ↓
回傳資料給程式
```

System Call 可以理解成應用程式向作業系統提出服務請求的正式入口。

這也是作業系統保護資源的重要機制之一。

### 3. Process（程序）與 Program（程式）不一樣

Program 通常指保存起來的程式內容。

Process 是程式正在執行時，由作業系統管理的執行實體。

你可以把 Program 想成一份食譜，Process 則是正在按照食譜做菜的廚師與工作狀態。

同一個程式可以同時啟動多個程序，而每個程序可能具有自己的記憶體空間、開啟檔案、執行環境與權限。

例如：

```
python server.py
```

它不是單純「打開一個 Python 檔案」。

Shell 需要找到 Python 直譯器，作業系統建立程序，直譯器讀取程式並載入必要模組，再依程式內容執行操作。

要真正理解程式執行，必須區分磁碟上的程式檔、執行中的程序，以及程序使用的記憶體與外部資源。

## 三、檔案系統的第一原理：路徑不是資料本體

### 1. 檔名、inode、資料區塊是不同東西

我們平常會認為：

```
/home/user/report.txt
```

就是一個檔案。

但典型 Linux 檔案系統可以分成三個概念。

```
Path（路徑）
    ↓
Directory Entry（目錄項目）
    ↓
inode（檔案物件的中繼資料）
    ↓
Data Blocks / Extents（實際內容）
```

inode 是檔案系統管理檔案的資料結構，包含權限、擁有者、連結數量、大小、時間戳及資料配置資訊等。

一個很重要的觀念是：inode 編號只保證在所屬檔案系統內具有識別意義，所以比較檔案身分時，通常需要將 device 與 inode 一起考慮。

### 2. Hard Link、Symbolic Link、Reflink、Copy 的本質

{{figure:links}}

Hard Link（硬連結）

兩個路徑指向同一 inode。刪掉其中一個名稱，不會自動刪除另一個名稱所指的內容；但透過其中一個名稱原地修改檔案，另一個名稱也會看到變更。

另外三種技術可用下表區分：

| 技術            | 共用的實體    | 修改時的行為             |
| ------------- | -------- | ------------------ |
| Symlink       | 目標路徑     | 預設沿路徑找到目標；目標消失可能斷鏈 |
| Hard link     | 同一 inode | 原地寫入影響所有別名         |
| Reflink / CoW | 底層資料區塊   | 寫入時將需要改變的區塊分離      |
| Copy          | 通常是獨立資料  | 修改一份不影響另一份         |

CoW 是 Copy-on-Write，意即「寫入時複製」。

它的核心思想是：如果兩份資料目前一樣，先共用內容；等其中一份真的要改時，才為修改的部分分配獨立儲存。

這個想法會反覆出現在檔案系統、虛擬記憶體、容器及快照等技術中。

### 3. 為什麼硬連結可能有風險？

假設兩個應用程式都需要 `config.json`。

今天兩份內容完全相同，所以你把它們做成 hard link。

明天應用程式 A 修改設定檔，應用程式 B 可能也同時看到新的內容。

不只是內容，hard link 所共享的 inode 中繼資料也包含權限與時間戳等資訊。

因此，要共享可寫檔案，就必須理解程式的更新方式。

例如，程式直接開啟檔案原地覆寫，與先建立新檔、再使用 `rename` 取代舊路徑，是不同的行為。

後者可能使該路徑改指向新的 inode，不再與其他硬連結共享原本的檔案物件。

### 4. 為什麼刪掉大檔案，磁碟空間卻沒有立即增加？

可能的原因包括：還有其他硬連結指向同一 inode，或者程序仍然持有已刪除檔案的開啟參照。

也可能涉及快照、CoW 共享、其他程序同時寫入，以及檔案系統的配置方式。

因此，必須區分三個量：

Logical Size（邏輯大小）是檔案對外呈現的位元組長度；Allocated Size（配置大小）是儲存系統實際配置的容量；Free Space（可用空間）則是整個檔案系統目前可用的空間。

這解釋了為什麼 `du`、`df` 與某些應用程式的快取統計結果可能不同。

另外，GB 與 GiB 也不同：GB 通常使用 10⁹ bytes，GiB 使用 2³⁰ bytes。

### 5. 如何觀察？

以下以 Linux／GNU 工具為例，指令只讀取資訊，不會修改檔案。請把 `example.txt` 換成存在的檔案；macOS 的 `stat` 欄位格式與 `readlink` 選項依版本不同，先以 `man stat`、`man readlink` 核對。

```
# 檔案系統的容量
df -h

# 目錄的使用量估計
du -sh .

# 查看某檔案的 inode、連結數與權限
stat example.txt

# 看符號連結的解析結果
readlink -f example.txt
```

看到兩個檔案大小相同，還不能斷定是同一份檔案。你需要進一步確認內容與身分。

這就帶我們進入下一個重要主題：Hash。

## 四、Hash、內容定址與資料去重複：如何知道兩份資料是否相同？

### 1. Hash 是替內容計算一個指紋

假設你有兩份檔案，名稱分別叫：

```
report-final.pdf
report-final-copy.pdf
```

光看名字不知道內容是否相同。

Hash Function（雜湊函數）會將輸入資料轉換成固定長度的摘要。

例如 SHA-256 不論處理多大的檔案，產生的摘要長度都是 256 bits。

```
檔案內容 A ── SHA-256 ──> 雜湊 X
檔案內容 B ── SHA-256 ──> 雜湊 X
```

如果兩個檔案的完整 SHA-256 相同，工程上通常可以極高信心認為內容相同。這是基於密碼學上的抗碰撞性，並非數學上絕對不可能碰撞。

### 2. Content-Addressable Storage 是什麼？

一般儲存方式用檔名找資料：

`文件名稱 → 檔案內容`

內容定址儲存（Content-Addressable Storage，CAS）則使用內容雜湊作為識別資訊：

`檔案內容 → Hash → 儲存位置`

Content：檔案位元組

SHA-256：計算摘要

Blob Store：依摘要保存內容

版本 A

參照 Hash X

版本 B

參照 Hash X

不同版本可以參照相同的內容物件，避免為一模一樣的位元組保存重複副本。

Blob 可以理解為「一塊由系統當作整體管理的資料」。

Snapshot 則是某個時間點的狀態描述。它可以記錄「當時有哪些路徑、各自對應哪些內容」，不必替每次快照重新保存全部相同的位元組。

這套概念可以應用在 Git 物件、套件 store、模型快取、備份與歷史版本管理。

### 3. 相同的 Hash，不代表資料可信

這是資訊安全上的關鍵區分。

Integrity（完整性）關心資料有沒有被改變；Authenticity（真實性／來源可信性）則關心資料是否來自你信任的來源。

攻擊者也能產生一份惡意檔案，再替它計算 SHA-256。

所以，檢查下載檔案時，不能只確認「某個雜湊值與同一個不可信網站提供的值相符」，就推論軟體安全。

還需要考慮可信發布來源、數位簽章、封裝來源與供應鏈安全。

這裡的核心原理是：

Hash 可以建立內容身分，但不能單獨建立來源信任。

## 五、程序、命令與權限：為什麼同一條指令在不同地方可能有不同結果？

### 1. Terminal、Shell、Runtime 是三個不同角色

你在終端機輸入：

```
python app.py
```

這裡有不同的元件參與。

Terminal 是文字互動介面。Shell 是解析命令、管理環境與啟動其他程式的工具。Python Runtime 則負責執行 Python 程式。

Shell 遇到 `python` 時，通常會依照 PATH 環境變數尋找對應的可執行檔。

PATH 就像一份「可以去哪裡找工具」的目錄清單。

假設你安裝了兩個 Python：

```
/usr/bin/python3
/home/user/project/.venv/bin/python
```

在不同 Shell、不同 PATH 或不同虛擬環境下，輸入 `python` 可能選到不同的直譯器。

因此，命令名稱相同，不保證執行的是相同程式。

### 2. Shebang、PATH 與子程序

在 Unix 類系統中，腳本開頭可能有：

```
#!/usr/bin/env python3
```

這叫 Shebang，用來指定腳本直接執行時的直譯器選擇方式。

此處透過 `env` 尋找 `python3`，結果會受到執行環境影響。若工具使用固定的直譯器路徑，則會受到該路徑是否仍有效的影響。

這也是為什麼搬動 Python CLI 工具環境後，入口腳本可能失效。

另外，一個程序可以啟動另一個程序。

例如 Node.js：

```
import { spawnSync } from "node:child_process";

const result = spawnSync("python3", ["worker.py"], {
  encoding: "utf8"
});
```

這裡的 Node.js 是父程序，Python 是子程序。

子程序有自己的程序身分，但通常會繼承父程序傳入的部分環境，例如環境變數與工作目錄。

因此，外層工具執行成功，不代表內層一定取得正確的 PATH 或 Python 環境。

### 3. Exit Code（結束碼）代表什麼？

Unix 類程序通常使用結束狀態向呼叫者報告結果。

慣例上：

`0` 表示程序自行宣告成功；非零表示某種失敗或異常狀態。

例如：

```
python validate.py && python build.py
```

`&&` 的意思是：前一個命令成功，才執行下一個命令。

但如果 `validate.py` 明明發現錯誤，卻仍回傳 0，後面的 `build.py` 就可能繼續執行。

所以，系統顯示成功，只代表它收到成功訊號；還要確認這個訊號是否真正反映驗收結果。

### 4. 權限與最小權限原則

Linux 程序通常以某個使用者身分執行，能否讀取檔案、修改設定或管理服務，取決於相應的權限機制。

這與以下概念密切相關：

Least Privilege（最小權限）：一個程序只應取得完成工作所需的能力，不應因為操作方便，就一律取得最高權限。

例如，單純讀取 Docker 容器清單，不應直接推論需要授予某個工具不受限制的主機管理能力。Docker socket 的權限尤其需要謹慎。

這也解釋了為什麼 venv 的套件隔離，不等於程式受到安全沙箱保護。

## 六、套件管理的第一原理：Dependency 是圖論問題，安裝是資源配置問題

### 1. Dependency Graph 是什麼？

假設你的程式依賴 A、B，而 A 又依賴 C。

```
應用程式
  ├── A
  │   └── C
  └── B
      └── D
```

這是一張圖（Graph）：套件是節點，依賴關係是邊。

Direct Dependency（直接依賴）是應用程式明確宣告需要的套件；Transitive Dependency（間接依賴）則是由其他套件帶進來的需求。

還有一個經常造成問題的概念：Peer Dependency（對等依賴）。

例如，一個 UI 元件套件可能要求由主專案提供相容的 React 版本。這種關係不能簡單理解成「每個套件自己下載一份 React 就好」。

因此，套件管理器要解決的不只是下載，而是相依約束與版本選擇問題。

### 2. Manifest、Lockfile、已安裝環境有什麼差別？

Manifest

允許哪些依賴

Lockfile

選定哪些版本

Installed Environment（已安裝環境）

磁碟上真正存在的程式、模組、入口與連結

Manifest 是需求規格，lockfile 是某次依賴解析的結果，已安裝環境則是實際建立出來的檔案與連結。

這三者可能不一致。

假設專案容許某函式庫的 2.x 版本，lockfile 選定 2.5.1，但開發者本機還有 2.4.0 的舊環境。

那麼，本機能執行並不保證正在使用與 CI 相同的依賴。

因此，lockfile 要搭配受控的安裝方式與驗證。

### 3. npm、pnpm 的底層差異

npm 和 pnpm 都能解析並安裝 JavaScript 套件，但它們建立依賴目錄與重用檔案的方式可能不同。

pnpm 的典型安裝結構會透過共用 store、`node_modules/.pnpm` 與符號連結表達依賴關係，並依平台及設定採用不同的套件內容匯入方式。

這反映兩個要分開的問題：

依賴解析：程式要求套件 A 時，應該找到哪個版本？

儲存配置：同一份套件內容，是否有必要在每個專案保存獨立副本？

pnpm 將兩個問題分開處理，因此能在維持各專案依賴關係的同時重用套件內容。

### 4. Python 的 venv、pip、uv、pipx 各自負責什麼？

| 技術             | 主要角色                          |
| -------------- | ----------------------------- |
| Python Runtime | 執行 Python 程式                  |
| venv           | 建立隔離的套件安裝與搜尋環境                |
| pip            | 安裝 Python 套件                  |
| uv             | 管理 Python 專案、相依解析、環境、工具與快取等工作 |
| pipx           | 以隔離環境安裝並執行 Python CLI 工具      |
| Wheel          | Python 可安裝的發行封裝格式             |

venv 讓不同專案能使用不同的套件安裝位置，而不必全部共用同一個全域 Python 環境。

uv 則提供不同的套件匯入策略，包括 copy、hardlink、symlink 與 clone（CoW）。它們對共享程度、修改副作用及清理快取的安全性有不同影響。

這裡必須理解：

套件版本一致，不等於二進位環境相容。

### 5. ABI、CPU Architecture、Toolchain 是什麼？

想像你買了一個電器插頭。

產品名稱與型號都正確，但如果插頭規格與插座不相容，仍不能直接使用。

原生軟體也有相似情況。

CPU Architecture，例如 x86-64 與 ARM64，描述處理器所支援的指令集架構等條件。

ABI（Application Binary Interface）則描述已編譯程式之間如何在二進位層面互動，例如函式呼叫約定、資料結構安排及特定二進位相容要求。

Toolchain（工具鏈）是編譯、連結及其他建置工具的組合。

因此：

可執行性 ≠ 只有套件版本正確

還需要考慮作業系統、CPU 指令集、ABI、原生函式庫、直譯器與必要的驅動等條件。

這也解釋了為什麼某些 Python Wheel 或 GPU 專用編譯產物，不能因為名稱或大小一樣，就在不同架構間互換。

Rust 又有 Host 與 Target 的區分：Host 是編譯器執行的平台，Target 是編譯結果要執行的平台。

### 6. APT、Snap、Rustup 與專案套件管理器

還需要分清楚「誰負責管理這項軟體」。

APT 常用於 Debian／Ubuntu 的系統套件管理。

Snap 管理自身封裝與 revision；某些舊 revision 可能是回復點。

Rustup 管理 Rust 的工具鏈與相關代理入口。

pnpm 和 uv 則偏向程式語言或專案層級的依賴與工具管理。

這些工具可能在同一台電腦共存，而且各自保管不同層次的資產。

例如更新 rustup，並不等於所有 Rust compiler toolchain 都已更新；刪除一個 Python CLI 環境，也不代表整個 pipx 或 uv 都不再需要。

所以，整理電腦之前，應先回答：「這個檔案由誰建立、誰使用、由誰更新，以及如何恢復？」

## 七、Cache、Garbage Collection 與 Docker：資源生命週期的共通原理

### 1. Cache 為什麼能加速？

Cache 的核心概念是：

把一部分空間成本，換成未來較低的存取或計算成本。

例如第一次下載一個套件需要網路傳輸，第二次若能從快取取得，就可能減少下載。

但 Cache 不只一種。

CPU Cache 保存處理器近期可能使用的資料；作業系統的 Page Cache 可以緩存檔案資料；套件管理器 Cache 保存下載或建置結果；瀏覽器 Cache 則能保存部分網頁資源。

它們都使用「重用」的思想，但內容、管理者、失效條件與安全契約不相同。

### 2. Garbage Collection（垃圾回收）如何判斷可以刪除什麼？

一種常見方法是從 Root Set（根集合）出發，找出仍可被引用到的物件。

```
Root（仍在使用的入口）
   ├── 物件 A
   │    └── 物件 C
   └── 物件 B

物件 D：沒有可達的有效引用
```

在這個簡化模型中，D 可能是回收候選。

但是，如果系統沒有正確登錄所有引用者，就可能誤判。

例如某個程式還需要特定版本的瀏覽器執行檔，但快取管理器不知道這個需求，清理程序便可能將它移除。

所以，垃圾回收是否安全，取決於其引用模型與生命週期資訊是否足夠完整。

對於 uv 這類工具，應優先透過它提供的快取管理功能操作，而不是直接刪除內部管理的檔案。官方文件也明確提醒不要直接修改其快取內容。

### 3. Docker Image 與 Container 是什麼？

Docker Image 可以想成已經準備好的軟體執行模板，包含應用程式及所需的檔案層。

Container 是根據映像建立、具有隔離設定與可寫狀態的執行實例。

在一般 Linux 容器架構中，容器與主機共享核心，透過 namespaces、cgroups 等機制實現不同程度的隔離與資源控制；它不是完整模擬一台獨立電腦的虛擬機。

## Docker 的典型分層儲存概念

Container Writable Layer

容器執行時新增或修改的狀態

Application Layer

應用程式及相關檔案

Dependency Layers

執行環境與套件

Base Image Layers

基底檔案系統內容

Volume / Bind Mount

獨立於容器可寫層管理的持久資料

示意結構。多個映像可共用相同層，因此映像列表顯示的大小不能直接加總為實際唯一磁碟占用。

Volume 尤其重要。

假設資料庫執行在容器裡，資料卻保存在獨立 volume。

重新建立容器，不一定會刪掉 volume；相反地，如果你誤刪 volume，可能損失真正需要保留的資料。

Docker 官方也將容器與資料持久化分開教學，強調需要長期保留的資料應有獨立的管理方式。

### 4. 為什麼清理快取不能只追求 SSD 空間最小？

我們可以把資源最佳化寫成一個概念性問題：

最小化（儲存成本＋重建成本＋操作風險）

但三種成本必須根據情境衡量，不能未經定義便直接當作同一單位加總。

一份 5 GB 的快取若十分容易重新下載，可能適合清理。

但一份 500 MB 的本機編譯結果，如果重建需要特殊環境、已下架的上游資源或大量人工工作，保留反而可能更有價值。

所以真正成熟的資源管理，不是「刪除最多」，而是在可恢復、可驗證的前提下，降低整體維護成本。

## 八、Git 的第一原理：版本控制其實是在管理有向無環圖

### 1. Git 到底保存什麼？

很多人把 Git 當成「程式碼備份工具」。

這個理解不算錯，但不夠完整。

Git 是一套分散式版本控制系統，核心能力是保存內容、版本快照，以及版本之間的關係。

理解 Git，先認識三種物件：

Blob 保存檔案內容；Tree 描述某個目錄層級的檔案與子目錄；Commit 記錄某個版本對應的 Tree、父提交及其他中繼資料。

這些結構讓 Git 能保存一連串版本歷史。

## Git 的三個主要工作區域

Working Tree

正在修改的檔案

Index

準備提交的內容

Repository

已提交的版本物件

Working Tree

git add

git commit

工作樹、暫存區與已提交的版本資料是不同狀態。`git add` 和 `git commit` 並不是同一件事。

官方 Git 文件也把這三個區域作為基本工作模型。

### 2. 為什麼 Git 使用 DAG？

DAG 是 Directed Acyclic Graph，中文為「有向無環圖」。

簡單理解，就是一張有方向、且不會沿著方向繞回原點的關係圖。

Git commit 指向父提交，因此可以表示版本歷史。

概念示意：從 B 分出兩條開發歷史，最終由 G 作為合併提交記錄雙方的父關係。Git 內部的提交指標方向實際上是由新提交指向父提交。

這種結構非常重要，因為多位開發者不可能永遠按照同一條線修改程式。

Branch（分支）本質上是指向某個 commit 的參照。

這讓每位開發者可以在自己的歷史上工作，再選擇如何整合。

### 3. Fast-forward、Merge、Rebase 有什麼不同？

Fast-forward 是單純把分支指標往較新的後代提交移動，不必額外製造合併提交。

Merge 是整合分岔的歷史，必要時建立具有多個父提交的新 commit。

Rebase 則是將某條開發線的變更重新套用到另一個基礎上，會產生新的提交身分。

對已經與他人共享的歷史，不應在沒有協作約定的情況下任意重寫。

這也是為什麼 force push 需要特別謹慎：它可能改變遠端分支的可達歷史。

### 4. Stash 和 Worktree 解決什麼問題？

Stash 用來暫時保存工作樹與索引中的修改。常見的 `git stash push -u` 也會納入未追蹤檔案，但預設不包括 ignored 檔案。

Worktree 則允許同一個 Git repository 擁有額外的工作目錄與索引。

例如，你正在修改某個功能，卻需要從最新 main 建立一份乾淨環境來測試正式發布。

使用獨立 worktree，可以降低兩項工作在相同目錄互相覆蓋的風險。

這裡反映的是一個通用工程原理：

不同工作應該適當隔離，但可以共享其真正需要的底層資源與版本歷史。

### 5. 為什麼 Commit、Push、Deploy 不是同一件事？

Commit 是將版本保存到本地 Git 物件資料庫。

Push 是嘗試更新遠端 Git repository 的參照。

Deploy 是將某個可執行或可提供服務的成品交付到目標環境。

三者可能使用不同的時間點、提交與產物。

因此：

Commit 成功 ⇏ Deploy 成功

甚至 Deploy 成功，也不代表應用程式符合需求。

這就需要下一層：建置、交付與驗收。

## 九、CI/CD 的第一原理：如何把人工流程變成可重複的工程程序？

### 1. CI 和 CD 是什麼？

CI（Continuous Integration，持續整合）是頻繁整合程式變更，並透過自動化檢查降低問題累積的做法。

CD 可以是 Continuous Delivery（持續交付）或 Continuous Deployment（持續部署）。

持續交付強調系統維持可交付狀態；持續部署則進一步自動將符合條件的變更部署到目標環境。

以一般網站為例：

```
工程師提交原始碼
        ↓
CI 建立執行環境
        ↓
安裝指定依賴
        ↓
執行內容、型別、單元與安全檢查
        ↓
Build（建置）
        ↓
產生 Artifact
        ↓
部署
        ↓
對正式服務執行驗收
```

其中 Build 指把來源經過編譯、轉換或封裝，產生可使用的成果。

例如 TypeScript 需要轉換成瀏覽器可執行的 JavaScript，網站也可能經過打包、壓縮、預先渲染等步驟。

### 2. Source、Cache、Artifact 為什麼必須分開？

| 類別       | 本質        | 常見例子            |
| -------- | --------- | --------------- |
| Source   | 定義應該建立什麼  | 程式碼、需求、設定、內容模型  |
| Cache    | 加速重複工作    | 已下載套件、編譯中間資料    |
| Artifact | 一次執行產生的成品 | 建置好的網站、執行檔、測試報告 |

Cache 應在缺少時仍能重建必要內容；Artifact 則可能是需要正式保存、傳遞或部署的結果。

GitHub 官方文件也明確區分 workflow artifact 與 dependency cache 的使用目的。

這個區分在 AI 系統也適用。

例如，模型原始訓練資料、訓練過程產生的暫時快取、最終交付的模型權重與評估報告，不應全部採用相同的保管策略。

### 3. 為什麼 CI 要固定環境？

假設開發者本機使用 Python A 版本，CI 則使用 Python B 版本。

即使原始碼相同，可能仍有語法、套件、ABI 或行為差異。

因此可把建置結果理解成：

B = f(S, D, T, P, E)

其中 B 是建置結果，S 是來源，D 是依賴，T 是工具鏈，P 是平台，E 是環境條件。

這個式子不是特定軟體的執行公式，而是用來表達：建置結果可能受多個條件共同影響。

要追求 Reproducible Build（可重現建置），就必須控制足夠的輸入。

Lockfile 只能處理其中一部分。

### 4. 為什麼 CI 也需要安全治理？

CI 通常能下載程式、執行命令、讀取部分機密設定，甚至部署正式系統。

因此 CI 本身就是值得保護的攻擊面。

例如 GitHub Actions 可能使用不同權限的 Token 或 OIDC 憑證。

這牽涉最小權限原則、供應鏈安全、工作流程觸發條件與不可信輸入處理。

此外，CI 快取不應被視為永遠可信。低信任來源若能影響快取內容，可能造成 Cache Poisoning（快取污染）風險。

### 5. Eventual Consistency（最終一致性）是什麼？

假設一個服務已上傳 Artifact，但另一個服務稍後才能在清單中查到它。

這不一定代表上傳失敗，可能只是不同元件對狀態的可見時間不同。

這種現象可以用分散式系統的一致性模型理解。

常見處理方法是有限重試（Bounded Retry），但必須注意兩件事。

首先，重試應有明確停止條件。其次，執行可能產生副作用的操作時，要考慮 Idempotency（冪等性）。

冪等性指重複執行某項操作，不會讓預期的最終狀態因重複而繼續改變。

例如，單純查詢 Artifact 清單通常可以安全重試；付款、刪除資料或部署新版本則需要更謹慎的重試設計。

### 6. Concurrency（併發）為什麼會造成問題？

Concurrency 是多個工作在時間上重疊進行。

假設兩個建置程序同時讀寫同一份輸出目錄。

其中一個程序可能讀到另一個程序尚未完成的中間檔案，導致結果依執行順序不同而改變。

這叫 Race Condition（競爭條件）。

因此，應辨認哪些工作可平行執行，哪些工作必須串行，哪些需要使用獨立工作區或鎖定機制。

CI 的 concurrency group 也不是自然等於一條完整的 FIFO（先進先出）佇列。實際保留多少等待工作、是否取消執行中工作、如何排序，要看平台與具體設定。

## 十、網站系統的底層：從資料模型到瀏覽器畫面

### 1. HTML、CSS、JavaScript 分別做什麼？

想像你要建造一棟房子。

HTML 決定房子的結構；CSS 決定外觀與配置；JavaScript 則可以提供互動行為。

更精確地說：

HTML 描述文件的內容與語意結構。

CSS 控制畫面呈現與排版。

JavaScript 在瀏覽器中執行程式邏輯，操作頁面、處理互動或與服務交換資料。

三者彼此合作，但責任不同。

例如，一個按鈕即使外觀很漂亮，如果語意結構錯誤，可能使鍵盤操作或輔助科技難以辨認。

因此，前端設計不能只看視覺效果。

### 2. 瀏覽器如何取得網站？

理解網站部署，需要先認識瀏覽器取得資源的網路流程。

一般 HTTPS 網站請求大致涉及：

```
輸入網址
    ↓
DNS：查詢主機名稱對應的位置資訊
    ↓
建立網路連線與 TLS 安全通道
    ↓
HTTP：請求網頁資源
    ↓
伺服器或 CDN 回應 HTML / CSS / JS
    ↓
瀏覽器解析並呈現畫面
```

DNS、TLS 和 HTTP 是不同層次的機制。

DNS 協助找出要連往哪裡；TLS 負責通訊安全相關功能；HTTP 定義請求與回應的語意。

當 GitHub Pages 已完成部署，但你看到的網站仍不正確時，問題可能位於部署產物、網頁資產、瀏覽器行為或快取，而不一定是 Git 原始碼。

### 3. 靜態網站與動態網站的差別

靜態網站通常在建置階段就產生可以直接提供的 HTML、CSS、JavaScript 等檔案。

動態網站則可能在每次請求時，讓伺服器程式查詢資料庫、計算內容，再產生回應。

例如：

```
靜態：
來源 → 建置 HTML → 伺服器提供 HTML

動態：
請求 → 應用程式 → 資料庫／業務邏輯 → 回應
```

兩種方式沒有絕對的優劣，應依網站功能、更新頻率、互動需求及部署成本選擇。

很多現代網站也會結合兩種模式。

### 4. Schema 與 TypeScript 在保護什麼？

假設你的教材資料長這樣：

```
{
  "lessonId": "lesson-01",
  "title": "Introduction",
  "published": true
}
```

Schema（資料結構契約）可以規定這份資料應有哪些欄位、型別與有效條件。

TypeScript 可以在開發與建置階段檢查程式碼中的型別關係。

但是，TypeScript 檢查通過，不能直接證明外部 JSON 一定符合預期。

因為程式執行時，仍可能從檔案、API 或資料庫讀入不合法資料。

因此需要 Runtime Validation（執行期驗證）。

同樣地，資料格式合法，也不保證內容在事實上正確。

這是三種不同的判斷：

結構是否合法、程式能否處理、資料內容是否正確。

### 5. 為什麼 Responsive Design 不只是把圖片縮小？

響應式設計（Responsive Design）要讓內容能根據可用空間、裝置條件及使用情境保持可理解、可操作。

如果一張 1200px 的流程圖直接縮小成 300px，圖形雖然完整顯示，但文字可能只剩原來的四分之一大小。

更好的方法可能是讓 HTML 文字重新換行，利用 CSS Grid、Flexbox 或 Container Query 重新排列內容。

但還要注意：排版改變，不應改變資訊原本的邏輯關係。

例如分類樹的兩個平行分支，不應因為手機版改成直向排列，就看起來像前後相依的步驟。

這是語意與視覺呈現必須共同考慮的原因。

另外，Accessibility（無障礙）不只是文字能否看清楚，還涉及鍵盤操作、閱讀順序、語意標記、輔助科技及互動狀態等。

### 6. 為什麼隱藏草稿不等於保護草稿？

假設系統不顯示某篇文章的導覽連結，但內容仍然被打包到搜尋索引或 JavaScript 檔案。

使用者仍可能取得它。

所以，不顯示某項資料，與不將該資料交付給使用者，是兩件不同的事。

這也是資訊安全常見的誤解。

前端畫面上的隱藏條件，不應取代真正的資料發布或存取控制規則。

在靜態網站中，應檢查整個正式輸出，而不只確認某個頁面不存在。

## 十一、測試工程的第一原理：證據必須與主張相符

這是整套教程最重要的跨領域能力之一。

### 1. 為什麼「測試通過」不是完整的結論？

假設你執行 100 個測試，全部成功。

你究竟證明了什麼？

答案取決於測試內容、測試環境及測試斷言。

如果只測加法函式，就不能拿結果證明整個網站安全。

如果只測本機瀏覽器，就不能宣稱正式服務一定正常。

因此，每個測試都需要明確的證據範圍。

| 測試種類             | 核心用途          | 主要限制        |
| ---------------- | ------------- | ----------- |
| Unit Test        | 驗證小範圍程式邏輯     | 不代表整體系統正確   |
| Integration Test | 驗證元件之間的互動     | 不一定涵蓋真實部署   |
| End-to-End Test  | 驗證指定完整使用流程    | 只涵蓋設計過的情境   |
| Regression Test  | 防止既有功能退化      | 未測到的問題仍可能存在 |
| Negative Test    | 驗證不應允許的情況會被拒絕 | 需要有效的負向案例   |
| Security Test    | 檢查指定威脅或安全條件   | 不能概括為完全安全   |

### 2. 為什麼要分別測試正向與負向行為？

假設你正在開發一個檔案上傳系統。

正向測試會確認合法使用者能正常上傳符合條件的檔案。

負向測試則會確認未授權使用者、不合法檔案或超出限制的操作受到正確處理。

兩者缺一不可。

尤其在資安領域，「正常流程可以成功」和「不被允許的流程確實被阻擋」是兩個不同的安全需求。

### 3. 為什麼測試資料本身也需要有效？

假設你要驗證「未發布文章不能上線」。

你建立了一篇草稿，但它的基本 JSON 結構本身就是錯的。

結果建置程序在內容解析階段就失敗。

這時，你不能直接宣稱發布控制有效，因為系統根本沒有走到發布控制的判斷。

正確的測試設計應盡可能讓其他條件合法，只改變你真正想測的條件。

這反映了實驗設計裡的控制變因思想。

### 4. SHA-256、Playwright、人工審查各自能證明什麼？

假設一份 SVG 圖檔經過 SHA-256 比對，確認與可信的來源檔案一致。

這只能證明位元組相符。

它無法告訴你圖中的箭頭是否畫錯、文字是否容易閱讀、讀者是否正確理解。

Playwright 可以在指定瀏覽器環境中檢查畫面與互動，但也不會自動理解所有教學內容的事實正確性。

人工審查則可以評估語意、脈絡與專業內容，但也有遺漏與主觀判斷的可能。

因此，成熟驗收需要將不同證據結合，而不是找一個測試工具取代所有判斷。

## 十二、可靠系統的進階底層：原子性、競爭條件、恢復與治理

前面學過的檔案、Git、Docker、CI/CD 與資料治理，其實還共享一些更深層的系統原理。

### 1. Atomicity（原子性）是什麼？

原子性的核心想法是：某項操作對外應呈現為不可分割的狀態轉換。

例如，程式要更新一份重要檔案。

如果直接原地覆寫，其他程序可能讀到只完成一半的內容。

一種常見做法是先寫入暫存檔，再以適當的原子更名操作取代目標。

這能降低其他程序觀察到中間狀態的可能性。

但請注意：

操作對外可見的原子性，不等於斷電後一定完成持久保存。

檔案同步、目錄中繼資料、檔案系統日誌與儲存裝置保證，都可能影響持久性（Durability）。

### 2. TOCTOU 是什麼？

TOCTOU 是 Time-of-Check to Time-of-Use。

意思是：系統檢查某項條件時，它是正確的；但真正執行操作時，狀態可能已經改變。

例如：

```
檢查檔案未被修改
       ↓
另一個程序更新該檔案
       ↓
原程序仍依舊檢查結果進行操作
```

這可能造成錯誤或安全問題。

所以，「操作前檢查一次」不一定足以保證操作時的條件仍然成立。

需要依情況採用鎖、版本檢查、原子操作、隔離或其他併發控制機制。

### 3. 為什麼跨多個 Repository 的提交不是一個交易？

假設一項發布工作需要同時更新網站 Repository 與 Planning Repository。

網站已成功推送，但 Planning 推送失敗。

Git 並沒有自動替這兩個獨立 repository 提供全有或全無的交易保證。

因此可能出現短暫的狀態不一致。

這時需要有明確的恢復與對帳流程，例如保留已完成的提交識別資訊，再補上另一個 repository 的更新。

大型分散式系統同樣常常面對這個問題。

它們不能只依賴單一資料庫的交易觀念，還可能需要補償操作、冪等設計與狀態對帳。

### 4. Single Source of Truth 與 Data Provenance

Single Source of Truth（單一可信正本）是一種資料責任設計原則。

不是說全系統只能有一個資料庫，而是每一項資訊應有清楚的權威來源。

例如產品規格由規格文件負責，建置結果由 CI 紀錄負責，部署版本由部署系統負責，使用者學習結果則由實際學習證據負責。

Data Provenance（資料來源追溯）則關心資料從哪裡來、經過哪些處理、由誰或什麼系統修改，以及能否追查。

兩者相互配合：

單一正本減少衝突，來源追溯讓變更可以被理解與驗證。

### 5. Control Plane 與 Data Plane 是什麼？

這兩個概念常見於網路、雲端及分散式系統。

Data Plane（資料平面）是處理實際資料或執行主要工作的部分。

Control Plane（控制平面）則負責設定、協調與管理系統應如何運作。

例如在一個網站系統中，提供正式網頁的伺服器屬於實際服務路徑；記錄部署目標、發布狀態與工作流程的管理系統，則可借用控制平面的概念理解。

不過，這是架構類比。不是所有專案管理文件都真的實作了一套正式的分散式控制平面。

### 6. 為什麼應該保留 Unknown？

工程系統經常需要記錄狀態。

假設網站已部署，但是否完成無障礙人工驗收仍未確認。

如果只有一個 `done = true`，就可能把不同工作混在一起。

較精確的資料模型可能是：

```
build        = passed
deployment   = succeeded
browser_test = passed
a11y_review  = pending
user_impact  = unknown
```

這種做法能避免把「尚未測得」誤寫成「已通過」。

尤其是工時、績效、可靠性與安全指標，不應根據推測補造數字。

Unknown 是一種有意義的資訊狀態，不一定是資料管理的失敗。

## 十三、把所有知識變成實際排錯能力

假設你接到這些不同的系統問題，應該如何選擇第一個檢查方向？

| 觀察到的現象             | 優先檢查的底層機制                       |
| ------------------ | ------------------------------- |
| 兩個資料夾看起來各占 10 GB   | inode、hard link、CoW、配置大小        |
| 刪掉大型檔案，`df` 沒變     | 其他連結、開啟參照、快照、同期寫入               |
| 本機程式能跑，另一台電腦不能     | Runtime、套件版本、ABI、CPU 架構         |
| 同一個命令在不同終端結果不同     | PATH、Shebang、環境變數、工作目錄          |
| 清快取後工具壞掉           | 引用關係、連結模式、版本耦合                  |
| Git push 成功，網站沒有更新 | CI、Build、Artifact、Deploy        |
| CI 顯示成功，但網站內容錯誤    | 測試斷言、發布邊界、正式環境                  |
| 網頁桌面正常，手機無法閱讀      | CSS 重排、語意結構、Responsive Design   |
| 多個工作互相覆蓋檔案         | Race Condition、隔離、鎖與交易          |
| 版本已發布，但完成紀錄矛盾      | Source of Truth、Provenance、狀態模型 |

請注意這個診斷方式：

我們不是直接猜「哪個工具壞了」，而是先辨認問題發生在哪一個抽象層，再找對應的觀察方法。

這就是理解底層知識之後，最直接的實務價值。

## 十四、實際練習：用安全的小實驗觀察 inode 和硬連結

可以在 Linux 或 macOS 終端機使用一個全新的暫存資料夾練習，不必碰正式專案。

```
# 建立一個獨立的暫存目錄
lab=$(mktemp -d)

# 建立檔案
printf 'Hello Computer Science\n' > "$lab/a.txt"

# 建立硬連結
ln "$lab/a.txt" "$lab/hard.txt"

# 建立符號連結
ln -s a.txt "$lab/soft.txt"

# 觀察檔案身分與連結數
stat "$lab/a.txt"
stat "$lab/hard.txt"

# 比較內容：Linux 使用 sha256sum，macOS 使用 shasum
if command -v sha256sum >/dev/null 2>&1; then
  sha256sum "$lab/a.txt" "$lab/hard.txt"
else
  shasum -a 256 "$lab/a.txt" "$lab/hard.txt"
fi
```

重點是觀察：原始檔案與硬連結的 inode 是否相同？Hard link count 是否改變？兩個內容雜湊是否相同？

這個練習可以把前面抽象的檔案系統概念，轉變成實際看得見的證據。預期 `a.txt` 與 `hard.txt` 在同一裝置上有相同 inode，連結數為 2，SHA-256 摘要相同；`soft.txt` 自己是另一個符號連結物件。實際 inode 數字由檔案系統決定。

觀察完成後，在同一個 Shell 僅刪除本練習建立的三個名稱，再移除空目錄；`rmdir` 若發現額外內容會停止。

```
rm -- "$lab/soft.txt" "$lab/hard.txt" "$lab/a.txt"
rmdir -- "$lab"
unset lab
```

## 十五、綜合理解檢核

下面是一個完整案例，涵蓋本次教材的主要領域。先不提供答案。

情境：某研究團隊同時維護一個 Python AI 推論服務、一個 JavaScript 教學網站和一個 Docker 資料庫服務。團隊發現 SSD 空間不足、不同工程師的環境不一致、CI 偶爾失敗，而且某次網站更新後正式頁面顯示了不該公開的草稿內容。

可使用自己的語言回答，重點是說明判斷步驟與需要的證據。

A｜硬體與檔案系統
兩個 AI 專案各有一份大小相同的模型權重。你如何判斷它們是否真的重複占用磁碟？若共用硬連結，還需要確認什麼？磁碟共用是否代表 GPU 記憶體也共享？

B｜依賴與執行環境
Python 和 JavaScript 專案在不同工程師電腦上執行結果不同。你會如何區分 PATH、依賴解析、lockfile、ABI 和平台架構造成的問題？

C｜快取與容器
主管要求一次清除所有大型快取、Docker 映像與 volume。你會如何分類哪些可以重建、哪些可能是唯一重要資料、哪些刪除後可能破壞其他環境？

D｜Git、CI/CD 與分散式系統
Git push 已成功，CI 建置也通過，但正式網站沒有更新。你會沿著哪些階段追查？如果兩個建置工作同時修改同一個輸出目錄，可能發生什麼問題？

E｜網站與安全
為什麼草稿沒有公開頁面，仍可能從搜尋索引被取得？你會設計哪些正向、負向與正式網站測試？

F｜測試、恢復與治理
系統恢復後，如何區分「檔案完整」「服務可用」「版本正確」「安全限制有效」與「使用者需求已滿足」？你會保存哪些證據，如何避免將未知狀態宣稱為成功？

完成 A–F 後，可將回答交給授課者或帶入後續討論逐題檢視；本頁不提供線上送出或自動批改功能。

## 最後，把這門課濃縮成五個能長期使用的觀念

一、名稱不等於物件。 檔名不等於 inode，套件名稱不等於具體安裝版本，命令名稱不等於實際執行檔。

二、內容相同不等於可以安全共用。 共用之前，還要確認寫入行為、責任與恢復需求。

三、環境一致不只靠版本號。 工具鏈、作業系統、CPU 架構、ABI 與執行條件都可能影響結果。

四、完成一個階段不等於完成整個系統。 Commit、Build、Deploy、Test 與使用者驗收，各有不同的完成條件。

五、工程結論必須有對應的證據。 能證明檔案位元組相同的證據，不能直接證明程式安全；能證明服務啟動的證據，也不能直接證明使用者已成功完成工作。

接下來最有效的學習方式，是將這套知識分別應用於一個真實的 Python 專案、一個 JavaScript 網站及一個 Docker 服務，逐步觀察它們的資源、依賴、版本、執行與驗收證據。這會比單純背誦工具指令更能建立可遷移的資工能力。
