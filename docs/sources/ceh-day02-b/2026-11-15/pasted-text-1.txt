# **CEH Day 02-B｜網路掃描、TCP／UDP、服務列舉與安全判讀完整教學**

**本次教材：23 題，涵蓋 12 個知識點（K01–K12）。**

這份教材最重要的，不是背誦 Nmap 指令或連接埠號碼，而是學會：

**當一個封包從電腦送出去，經過網路，到達另一台主機，再收到某種回應時，我們究竟能從這些證據推論出什麼？又有哪些事情不能推論？**

只要這個問題想通，Host Discovery、Port Scanning、TCP SYN Scan、UDP Scan、Enumeration，以及防火牆與 IDS 的判讀，就能組合成一套連貫的知識系統。

## **一、先看全貌：網路安全測試究竟在做什麼？**

想像你是銀行的資安工程師。銀行有數百台伺服器，其中一些是十年前建置的系統，甚至連資訊部門都不確定它們目前提供哪些服務。

你的工作不是立刻找漏洞，而是先回答以下問題。

1. **授權（Authorization）**

   我可以測哪些系統？允許什麼方式？什麼時候必須停止？
2. **主機探索（Host Discovery）**

   這個 IP 位址是否有主機正在使用？
3. **連接埠掃描（Port Scanning）**

   主機上哪些 TCP／UDP 入口可以到達？
4. **服務辨識（Service Identification）**

   這些入口後面，究竟是哪個軟體或服務？
5. **服務列舉（Enumeration）**

   服務會暴露哪些帳號、分享資源或設定資訊？
6. **風險判斷（Risk Assessment）**

   已取得的證據是否足以支持弱點、暴露面或設定錯誤的結論？

這六個階段有一個非常重要的邏輯：

**每完成一個階段，只能回答該階段能回答的問題，不能直接跳到下一個階段的結論。**

例如：

- 主機回應 Ping，不代表上面有網站。
- TCP 443 開放，不代表一定正在執行 HTTPS。
- HTTPS 正常運作，不代表網站沒有漏洞。
- 找到使用者帳號名稱，不代表能登入該帳號。
- 某個掃描沒有觸發 IDS，不代表它無法被偵測。

這是整份教材最重要的推理原則。

## **二、K02–K03｜先理解網路通訊：IP、Port、Protocol 與服務**

### **2.1 為什麼電腦需要 IP 和 Port？**

想像銀行總部是一棟大樓。

- **IP Address**：這棟大樓的地址。
- **Port**：大樓裡不同部門的服務櫃台。
- **Protocol**：櫃台與客戶遵守的通訊規則。
- **Service**：真正負責處理工作的服務或程式。

例如，一台銀行伺服器位於：

`192.168.1.10`

它可能同時提供：

| 目的地                     | 可能的服務                |
| ----------------------- | -------------------- |
| `192.168.1.10:22/tcp`   | SSH 遠端管理             |
| `192.168.1.10:443/tcp`  | HTTPS 網站             |
| `192.168.1.10:445/tcp`  | SMB 檔案分享             |
| `192.168.1.10:1433/tcp` | Microsoft SQL Server |

但請注意，**埠號只是服務的慣例，不是服務身分的保證**。

SSH 也可以設定在 TCP 2222；TCP 443 後面也可能是一個非 HTTPS 的自訂程式。

IANA 的官方登錄說明也明確指出，埠號被登錄給某項服務，不代表實際流量必然屬於該服務。

### **2.2 封包如何從瀏覽器走到伺服器？**

假設 Alice 在瀏覽器開啟 `https://bank.example`。

簡化流程：以 TCP 型 HTTPS 為例。HTTP/3 通常改走 QUIC／UDP 443，不使用 TCP 三向交握。

標準的 TCP 型 HTTPS 連線，大致經過四個步驟：

1. **DNS**：瀏覽器先查詢網域名稱對應的 IP。
2. **TCP**：向銀行的 TCP 443 建立連線。
3. **TLS**：協商加密與驗證伺服器身分。
4. **HTTP**：在受保護的連線上送出網頁請求並取得回應。

這裡還有一個經常被忽略的問題：為什麼 Alice 的電腦也是 `:53000`？

因為網路連線通常有兩端的 Port。

Alice 的作業系統會選擇一個臨時來源埠（Ephemeral Port），用來接收這條連線的回應。

伺服器以目的埠 443 接受服務，而 Alice 用臨時來源埠區分不同連線。

因此，辨識一條 TCP／UDP 通訊時，常會用到五個資訊：

`來源 IP、來源 Port、目的 IP、目的 Port、傳輸協定`

這稱為 **5-tuple（五元組）**，也是許多防火牆、流量紀錄與連線追蹤的重要基礎。

### **2.3 TCP 與 UDP 的真正差別**

TCP 和 UDP 都能讓應用程式透過網路交換資料，但它們的設計取捨不同。

| 特性     | TCP              | UDP               |
| ------ | ---------------- | ----------------- |
| 開始傳輸前  | 建立連線             | 不需建立 TCP 式連線      |
| 可靠傳送   | 提供序號、確認與重傳       | 不由 UDP 本身保證       |
| 資料順序   | 提供依序的位元組串流       | 不保證到達順序           |
| 常見情境   | SSH、傳統 HTTPS、SMB | DNS、DHCP、QUIC     |
| 掃描主要線索 | SYN/ACK、RST 等    | UDP 回應、ICMP 錯誤或靜默 |

這些差異將直接決定為什麼 TCP 埠可以相對明確地判斷 Open／Closed，而 UDP 埠經常會得到 `open|filtered`。

### **2.4 必須掌握的標準連接埠**

| Port       | 常見協定／服務       | 主要用途         |
| ---------- | ------------- | ------------ |
| TCP 21     | FTP           | 檔案傳輸控制連線     |
| TCP 22     | SSH           | 加密遠端操作       |
| TCP 23     | Telnet        | 傳統明文遠端終端     |
| TCP 25     | SMTP          | 郵件傳送         |
| TCP 80     | HTTP          | 網頁通訊         |
| TCP 110    | POP3          | 郵件收取         |
| TCP／UDP 53 | DNS           | 網域名稱解析       |
| UDP 67     | DHCP Server   | 配發網路設定       |
| TCP 443    | HTTPS         | 加密網頁通訊       |
| TCP 445    | SMB           | 檔案與資源分享      |
| TCP 1433   | MS SQL Server | 常見資料庫連線      |
| TCP 3389   | RDP           | Windows 遠端桌面 |

這張表是基本慣例，不是所有實際部署都必須遵守的設定。

**特別重要：TCP 1433 與 TCP／UDP 1434**

原題 EC-Q038 與 EC-Q149 故意使用相近的服務名稱。

IANA 登錄：

- TCP 1433：`ms-sql-s`
- TCP 1434：`ms-sql-m`
- UDP 1434：`ms-sql-m`

但 Microsoft SQL Server 的常見實際用途是：

- TCP 1433：資料庫引擎連線。
- UDP 1434：SQL Server Browser。
- TCP 1434：在特定設定下可能涉及 Dedicated Administrator Connection（DAC）。

所以看到 TCP 1434 時，應先分清楚兩件事：**標準登錄名稱是什麼，以及實際執行的程式是什麼**。後者需要進一步核對。

### **2.5 Netcat：監聽和主動連線的區別**

教材中的指令：

```
nc -l -p 4444
```

想像你在辦公室開設一個臨時服務櫃台：

- `nc`：啟動網路通訊工具。
- `-l`：在本機監聽（listen）。
- `-p 4444`：傳統 Netcat 實作中指定監聽埠。

它的意思是：**在本機 TCP 4444 等待其他端點連進來**。

這不表示正在掃描 1 到 4444，也不表示主動去連線別人的伺服器，更不表示檔案已被傳送。

不同 Netcat 版本的參數可能不同。例如 OpenBSD `nc` 常使用 `nc -l 4444`。考題要理解的是監聽方向，而不是把某一版本的語法當成所有版本的共同規格。

## **三、K04｜Host Discovery：如何判斷一台電腦是否存在？**

這個部分看似簡單，卻最容易產生錯誤推論。

### **3.1 Ping 到底做了什麼？**

一般的 `ping` 通常使用 ICMP Echo 訊息。

可以想像 Alice 在銀行機房門口喊：

「192.168.1.10，你在嗎？」

正常情況下：

```
Alice                       Server
  |                           |
  |------ ICMP Echo Request -->|
  |                           |
  |<------ ICMP Echo Reply ----|
  |                           |
```

Alice 收到 Echo Reply，可以合理認為：有某個符合探測條件的網路端點回應了她。

但如果沒有回覆：

```
Alice                       Server
  |                           |
  |------ ICMP Echo Request -->|
  |                           |
  |         沒有回覆           |
  |                           |
```

你能證明伺服器不存在嗎？

**不能。**

因為中間可能發生：

- 防火牆丟棄 ICMP Echo Request。
- 伺服器本身設定不回覆 Echo。
- 網路封包遺失。
- 回應遭到過濾或限速。
- 探測路徑與其他服務的路徑或控制條件不同。

因此，假設銀行網站 HTTPS 一直正常，但 Ping 沒有回應，你應優先考慮探測方式受到限制，而不是認定銀行主機已關機。

這對應 EC-Q047、EC-Q540。

### **3.2 ICMP Echo 與 ICMP Timestamp 有什麼不同？**

ICMP 不是只有 Ping 一種訊息。

| 類型                           | 想問什麼？                |
| ---------------------------- | -------------------- |
| ICMP Echo                    | 你有收到我的訊息嗎？           |
| ICMP Timestamp               | 你能提供時間戳記資訊嗎？         |
| ICMP Destination Unreachable | 某個目的地、協定或入口無法到達      |
| ICMP Time Exceeded           | 封包在允許的時間／跳數限制內未能完成傳送 |

教材 P2-Q107 所說的「請求目標主機的內部時鐘資訊」，對應的是 **ICMP Timestamp**，而不是一般 Echo。

要注意，Timestamp 訊息是歷史上定義的 ICMPv4 功能，不是每個現代系統都會回應，也不能把回傳時間當作完全可信的主機時鐘。

### **3.3 fping 和 Nmap 的 Host Discovery 指令**

**指令 A：**

```
fping -a -g 192.168.1.0/24
```

拆成三部分：

- `fping`：支援多目標探測的工具。
- `-g`：根據網段產生目標位址。
- `-a`：列出有回應的主機。

`/24` 是 CIDR 網段表示法，代表前 24 個位元用於識別網路。在典型 IPv4 子網中，這個範圍共有 256 個位址。

所以它的目標是找出該範圍內有哪些主機回應，而不是找每台主機開啟哪些埠。

**指令 B：**

```
nmap -sn -PE 10.0.0.0/24
```

- `-sn`：執行主機探索，不進行一般埠掃描。
- `-PE`：指定 ICMP Echo 探測類型。
- `10.0.0.0/24`：指定目標網段。

但有一個進階細節：如果掃描者和目標位於同一本地 Ethernet，Nmap 通常會優先使用 ARP 進行 IPv4 主機探索，即使指定了 ICMP 探測選項。

因為在本地網路中，ARP 本來就負責把 IPv4 位址解析為鏈路層的 MAC 位址。Nmap 會利用這個機制判斷本地目標是否存在。

## **四、K05–K08｜TCP 掃描：為什麼 SYN/ACK 可以支持埠開放？**

這是整份教材的技術核心。

### **4.1 先理解 TCP 三向交握**

假設 Alice 要跟銀行伺服器建立 TCP 連線。

逐步解釋：

**第一步：SYN**

Alice 告訴 Server：「我想建立一條 TCP 連線。」

SYN 是 Synchronize，涉及初始序號同步。

**第二步：SYN/ACK**

Server 回覆：「我收到了你的請求，也願意建立這條連線。」

SYN/ACK 同時包含同步與確認的意義。

**第三步：ACK**

Alice 再次回覆：「我確認收到你的回應。」

雙方完成連線建立，接著就能交換應用資料。

### **4.2 TCP Connect Scan 與 SYN Scan 到底差在哪？**

**TCP Connect Scan**

Nmap `-sT`

```
Client      Server
  SYN  ----->
       <----- SYN/ACK
  ACK  ----->

  連線成立
```

由作業系統執行一般連線建立，完成 TCP 交握。

**TCP SYN Scan**

Nmap `-sS`

```
Client      Server
  SYN  ----->
       <----- SYN/ACK
  RST  ----->

  未完成交握
```

透過觀察 SYN 的回應辨識埠狀態，通常以 RST 結束探測。

SYN Scan 又稱 Half-open Scan（半開掃描）。

它的關鍵是：**根本不需要完成 TCP 連線，就能透過對方是否回覆 SYN/ACK，取得判斷埠狀態的重要證據。**

但 Half-open 並不代表無法偵測。網路上的防火牆、IDS 或封包擷取系統仍可能看見 SYN 與 RST。

Nmap 官方文件也指出，SYN Scan 不完成正常 TCP 連線，因此可能比完整 Connect Scan 減少部分應用程式層的紀錄，但這不構成隱形保證。

### **4.3 Open、Closed、Filtered 到底是什麼？**

假設我們只討論標準 TCP SYN Scan。

| 觀察到的回應         | 可能判斷       | 原因            |
| -------------- | ---------- | ------------- |
| SYN/ACK        | `open`     | 目標願意建立 TCP 連線 |
| RST            | `closed`   | 目標拒絕該連線       |
| 無回覆／特定 ICMP 錯誤 | `filtered` | 可能有過濾阻止判斷     |

用生活比喻：

- **Open**：櫃台有人回答「可以辦理」。
- **Closed**：櫃台回應「這裡沒有提供這項服務」。
- **Filtered**：你的詢問可能被門口的警衛擋下，無法知道櫃台裡面是否有人。

而且掃描狀態是有條件的觀測結果。

例如同一台銀行伺服器：

- 在銀行內網掃描 TCP 445：`open`
- 從外部網際網路掃描 TCP 445：`filtered`

這完全可能同時成立。

因為防火牆可以允許內網存取 SMB，卻拒絕外網存取。

所以一份嚴謹的掃描報告，至少應保留掃描來源、目的地、傳輸協定、掃描方法、時間和回應證據，不能只寫「Port 445 是 Open」就當作永久且普遍的事實。

### **4.4 為什麼「大量 SYN、沒有 ACK」可能代表掃描？**

假設 SOC（安全營運中心）看到這樣的封包模式：

```
192.168.1.30 → 10.0.0.5:21   SYN
192.168.1.30 → 10.0.0.5:22   SYN
192.168.1.30 → 10.0.0.5:23   SYN
192.168.1.30 → 10.0.0.5:80   SYN
192.168.1.30 → 10.0.0.5:443  SYN
```

卻幾乎沒有觀察到完成連線的 ACK。

這與 SYN 半開掃描的行為相符，因為掃描器並不需要完成每條 TCP 連線。

但是，**相符不等於證明**。

如果封包擷取只有一個方向、部分封包遺失，或系統正遭遇 SYN Flood，也可能看到類似現象。

實務上還要結合目標埠分布、封包方向、掃描頻率、RST、應用日誌和網路設備紀錄。

這對應 EC-Q317、EC-Q415、P3-Q023、EC-Q446、EC-Q388。

## **五、K07｜UDP 掃描：為什麼沒有回應，比 TCP 更難判斷？**

這是另一個重要觀念。

### **5.1 UDP 沒有 TCP 的三向交握**

想像 Alice 寄一封信給銀行某個部門。

TCP 比較像先打電話，確認對方接聽，再開始談事情。

UDP 則比較像直接寄出資料，傳輸層本身不要求對方先建立連線，也不保證一定回覆。

因此，掃描器想知道某個 UDP Port 是否開放，不能使用 SYN/ACK 這種 TCP 特有的證據。

### **5.2 UDP 掃描可能得到的四種結果**

假設掃描器向一台主機的 UDP 53 發送探測資料。

UDP 探測結果判斷

**送出 UDP 探測封包**

觀察目標或網路設備是否回應

UDP 服務回覆

## **open**

確實收到對應服務的回應

ICMP Type 3 Code 3

## **closed**

Port Unreachable：目的埠不可達

其他特定 ICMP 不可達錯誤

## **filtered**

存在網路存取限制的證據

完全沒有回覆

## **open|filtered**

無法確定開放或受到過濾

這是 Nmap UDP Scan 的典型判讀規則。

### **5.3 為什麼 UDP 不回應，不代表 Port 關閉？**

假設我們向 DNS Server 發送一個毫無意義的 UDP 封包。

DNS Server 可能收到它，但發現資料不符合預期格式，因此直接忽略。

這代表：

- 主機存在。
- UDP 53 可能正在提供服務。
- 但這次探測沒有得到有效回覆。

另一方面，防火牆也可能直接丟棄 UDP 封包。

這兩種不同情況，都可能呈現相同的觀察結果：**靜默（Silence）**。

所以，`open|filtered` 的意思不是「確定同時開放又被過濾」，而是目前的證據還不能區分這兩種假設。

這是很重要的證據推理問題。

多做一次掃描能解決嗎？

不一定。

如果第一次沒收到回覆是因為封包遺失，重新探測可能有幫助。

但如果伺服器永遠不回覆無效格式的 UDP 封包，即使再試一百次，也未必取得新資訊。

更有效的方法，可能是使用符合應用協定格式的有效探測、比對防火牆紀錄，或直接檢查有權限存取的伺服器設定。

### **5.4 必須區分「負面觀察」與「否定證據」**

這是 TCP、UDP 與 ICMP 三種探測共同的重要思維。

| 觀察                      | 可以合理推論      | 不能直接推論      |
| ----------------------- | ----------- | ----------- |
| 收到 ICMP Echo Reply      | 有端點回應探測     | 所有服務都正常     |
| 沒有 ICMP Echo Reply      | 本次未取得回應     | 主機一定不存在     |
| SYN Scan 收到 SYN/ACK     | TCP 埠支持開放判定 | 後端應用沒有漏洞    |
| UDP 收到 Port Unreachable | UDP 埠支持關閉判定 | 其他 UDP 埠都關閉 |
| UDP 完全靜默                | 開放或過濾尚未釐清   | 一定被 IDS 阻擋  |

如果能把這個表格理解透徹，掃描結果就不再只是幾個固定答案，而是一種有明確限制的證據。

## **六、K08｜Stealth Scan：為什麼「半開」不等於「隱形」？**

教材多次使用 *Stealth* 這個詞。

它常被翻譯為「隱匿」，但應該小心解讀。

### **6.1 系統有很多不同的觀察位置**

想像銀行從三個地方觀察網路活動：

**掃描者發送 SYN**

**第一層：防火牆／網路 IDS**

看得到封包、TCP Flags、來源、目的地與流量模式。

**第二層：作業系統／TCP Stack**

可以觀察連線嘗試、狀態變化及部分事件。

**第三層：應用程式日誌**

是否留下紀錄，取決於應用程式何時開始記錄及其設定。

SYN Scan 因為沒有完成 TCP 交握，某些應用程式可能不會記錄到一筆完整連線。

但防火牆和 IDS 可以直接在較低層觀察 SYN 封包。

因此：

**「應用程式沒有留下完整連線紀錄」與「網路設備偵測不到」是完全不同的命題。**

這也說明為什麼不能單靠 `nmap -sS`，就保證不觸發告警。

### **6.2 其他掃描類型應該怎麼比較？**

| 掃描方法              | 主要機制             | 核心用途或限制             |
| ----------------- | ---------------- | ------------------- |
| TCP Connect `-sT` | 完成 TCP 連線        | 一般連線式探測             |
| SYN `-sS`         | 不完成 TCP 交握       | 辨識 TCP 埠狀態          |
| UDP `-sU`         | 發送 UDP 探測        | 辨識 UDP 服務狀態         |
| ACK `-sA`         | 發送 ACK 探測        | 主要研究過濾規則，不直接辨識開放服務  |
| FIN `-sF`         | 發送 FIN           | 依賴特定 TCP 行為，結果可能有歧義 |
| Xmas `-sX`        | 組合 FIN、PSH、URG   | 依 TCP 實作而異          |
| Idle `-sI`        | 利用中介主機的 IP ID 行為 | 間接推測，條件較特殊          |

如果題目問：

「哪一種掃描技術不完成完整 TCP 連線？」

應該從 TCP 交握機制判斷，而不是把所有帶有 *Stealth* 名稱的技術當成有絕對優勢。

如果題目問：

「哪一種掃描一定不會被 IDS 偵測？」

那就是另一個問題。沒有充分的 IDS 規則、網路拓樸、封包證據與測試條件，不能做這種保證。

## **七、K09–K10｜Enumeration：找到服務後，還能知道什麼？**

前面學的是：

「這個服務入口是否可達？」

現在進一步研究：

「這個服務會對外透露什麼資訊？」

這叫 Enumeration（列舉）。

### **7.1 SMTP：怎麼可能還沒登入，就知道某個帳號存在？**

SMTP 是電子郵件傳送協定。

假設一家公司有以下員工信箱：

- `alice@example.com`
- `bob@example.com`

郵件伺服器需要處理郵件投遞，因此必須理解收件人位址。

某些 SMTP 伺服器會對不同的收件人給予不同回覆。

例如概念上的情境：

```
詢問 alice@example.com
伺服器：接受此收件人

詢問 unknown@example.com
伺服器：無此收件人
```

即使詢問者沒有登入，仍可能藉由回覆差異推測哪些帳號存在。

這就形成了 User Enumeration（使用者列舉）。

### **7.2 三種需要分清楚的 SMTP 指令**

| 指令        | 功能            | 可能的資訊暴露       |
| --------- | ------------- | ------------- |
| `VRFY`    | 詢問使用者或信箱是否可辨識 | 使用者存在與否       |
| `EXPN`    | 請求展開郵件名單      | 清單成員資訊        |
| `RCPT TO` | 在郵件交易中指定收件人   | 依回覆差異推測信箱是否有效 |

但請注意：**知道 Alice 的信箱存在，不表示可以登入 Alice 的信箱。**

這裡至少有三個不同的安全問題：

1. **Enumeration**：外部能否辨識有效帳號？
2. **Authentication**：外部能否通過身分驗證？
3. **Authorization**：登入後能否存取原本不應存取的資源？

不能因為第一個問題有風險，就直接宣稱第二、第三個問題也已被突破。

### **7.3 STARTTLS 能防止帳號列舉嗎？**

不必然。

STARTTLS 主要處理傳輸通道的加密。

假設 Alice 與 SMTP Server 之間的訊息已經受到 TLS 保護，但伺服器仍向 Alice 回答：

「這個收件人存在。」

那麼訊息雖然經過加密，Alice 自己仍然可以知道伺服器的回答。

**傳輸加密保護通訊內容不被未授權的中途觀察者讀取，不代表伺服器不會對詢問者透露資訊。**

這是教材 EC-Q310、EC-Q523 的核心。

補充一個原題細節：附件中的 `smtp-enum-users` 命令參數是題庫原文，不能直接當成現行版本的正確用法。Nmap 官方文件使用 `smtp-enum-users.methods` 指定 EXPN、VRFY 或 RCPT 等方法。

### **7.4 SMB：Port 445 開放，能知道多少資訊？**

SMB（Server Message Block）常見於 Windows 網路檔案與印表機分享。

假設公司某台伺服器開放 TCP 445。

它可能提供：

- 部門共享資料夾。
- 印表機分享。
- 其他 SMB／RPC 相關服務。

但這裡有三個不同層次：

| 層次    | 問題                |
| ----- | ----------------- |
| 網路可達性 | TCP 445 是否能建立連線？  |
| 資訊可見性 | 能否列出共享名稱、帳號或網域資訊？ |
| 存取權限  | 能否讀取、修改或刪除分享中的檔案？ |

例如：

外部可能知道某台伺服器提供名為 `Finance` 的分享。

但這不代表能打開 `Finance` 中的薪資資料。

真正的存取能力仍取決於身分驗證、分享權限、檔案系統權限及伺服器設定。

而且 SMB 並不是只要開啟 TCP 445，就必然允許匿名帳號列舉。

## **八、K11｜DNSSEC：為什麼它不是 DNS 加密？**

這個部分很適合用密碼學的觀念理解。

### **8.1 DNS 可能面對什麼問題？**

假設 Alice 詢問 DNS Resolver：

「`bank.example` 的 IP 是什麼？」

DNS Resolver 回答：

`203.0.113.10`

但 Alice 要如何知道這個回答沒有被不當修改？

DNSSEC 的設計目標之一，就是讓驗證端能利用密碼學證據，檢查 DNS 資料來源的真實性（Authenticity）與完整性（Integrity）。

### **8.2 DNSSEC 如何建立信任？**

DNSSEC 採用數位簽章及信任鏈（Chain of Trust）。

可以用下列簡化流程理解：

1. 權威 DNS 區域持有相應的簽章金鑰。
2. 區域資料附有數位簽章（例如 `RRSIG`）。
3. 驗證端利用對應的公開金鑰（`DNSKEY`）驗證簽章。
4. 再透過上層區域的 `DS` 等紀錄，以及已信任的根金鑰，建立信任鏈。

如果驗證成功，表示相關 DNS 資料符合該信任鏈下的驗證要求。

但 DNSSEC 不會因此保證網站本身沒有惡意程式，也不保證查詢過程具有保密性。

### **8.3 DNSSEC、DoH、DoT、HTTPS 的功能不同**

| 技術                  | 主要保護目標                          |
| ------------------- | ------------------------------- |
| DNSSEC              | DNS 資料來源真實性與完整性                 |
| DNS over HTTPS（DoH） | DNS 查詢在特定傳輸鏈路上的機密性與完整性          |
| DNS over TLS（DoT）   | 使用 TLS 保護 DNS 傳輸鏈路              |
| HTTPS               | 保護瀏覽器與網站之間的 HTTP 通訊，並驗證相應的伺服器身分 |

DNSSEC 與 DoH／DoT 可以互補，並不是二選一。

RFC 4033 明確說明 DNSSEC 所提供的服務及其限制。

## **九、K12｜非對稱密碼學：為什麼公開金鑰能協助安全建立共享金鑰？**

這個知識點與前面 TLS 的連線建立機制有直接關係。

### **9.1 對稱式加密的核心問題**

假設 Alice 與 Bob 想秘密交換資料。

如果使用 AES 這類對稱式加密，雙方需要持有適當的共享秘密金鑰。

問題來了：

**如果雙方原本沒有共享金鑰，該如何安全建立或傳送這把金鑰？**

如果 Alice 直接透過未受保護的網路把金鑰傳給 Bob，旁觀者可能也取得金鑰。

這就是初始金鑰建立問題。

### **9.2 非對稱式密碼學如何幫忙？**

非對稱式密碼學涉及公開金鑰與私人金鑰，可以支援適當的金鑰建立、加密或數位簽章機制。

以一種採用公開金鑰加密的金鑰傳送情境來看：

1. Bob 產生公鑰與私鑰。
2. Bob 向 Alice 提供公鑰。
3. Alice 驗證公鑰確實屬於 Bob。
4. Alice 利用適當的機制保護要傳給 Bob 的金鑰材料。
5. Bob 使用自己的私鑰完成相應操作。
6. 雙方取得可用於後續對稱加密的秘密金鑰。

現代協定也常使用 ECDHE 等金鑰協議機制，讓雙方共同建立共享秘密，而不是直接加密傳送一把預先選好的對稱金鑰。

因此，必須區分：

- **Key Transport**：安全傳送金鑰材料。
- **Key Agreement**：雙方透過協定共同建立共享秘密。
- **Symmetric Encryption**：利用已建立的金鑰有效率地保護資料。

這些方法都需要適當的身分認證，否則可能受到中間人攻擊。

### **9.3 為什麼 Hash 與 Disk Encryption 不是相同問題的答案？**

| 機制              | 解決的主要問題       |
| --------------- | ------------- |
| 非對稱金鑰建立機制       | 如何安全建立或傳送共享秘密 |
| 對稱式加密           | 如何有效率地加密資料    |
| Hash            | 如何產生資料摘要      |
| Disk Encryption | 如何保護儲存中的資料    |

單獨的 Hash 並不能把秘密安全傳給對方。

磁碟加密能保護儲存設備上的資料，卻不會自動解決兩個遠端通訊者如何建立共享金鑰的問題。

這是 EC-Q053 的考點；附件所引用的主要技術依據為 NIST SP 800-56 系列。

## **十、K01｜最根本的問題：為什麼資安測試需要事先授權？**

這是整份教材的治理基礎。

假設某個資安工程師發現某家銀行的伺服器似乎存在弱點。

他認為自己正在做好事，所以直接對銀行進行完整掃描與弱點驗證。

即使他的目的是幫忙，也不能因此認定行為獲得授權。

有效的安全測試至少需要確定：

- 誰有權批准測試。
- 哪些系統與網段屬於範圍。
- 允許哪些技術和操作。
- 何時可以測試。
- 發生異常時如何停止與通報。

這些通常透過測試計畫、授權文件與 Rules of Engagement（ROE，交戰規則）進行約束。

教材中的 White Hat、Grey Hat、Black Hat，重點不應只放在名稱，而應落到**授權、行為、目的與責任**。

其中 White Hat 通常強調事先取得有效許可，並在約定範圍內進行安全測試。

這與 NIST SP 800-115《Technical Guide to Information Security Testing and Assessment》的測試規劃精神一致。

### **11.1 EC-Q255：為什麼某個 Ping Sweep 沒觸發 IDS？**

題目把「使用 ICMP Echo，不做埠掃描」與「未被 IDS 偵測」連在一起。

但這裡缺少一個重要環節：**IDS 實際上偵測什麼？**

如果 IDS 只針對高頻率的 TCP 埠掃描建立規則，那麼 ICMP 探測可能不會命中該規則。

可是，假如 IDS 對 ICMP 探測頻率、來源分布或異常模式設有規則，同一種探測也可能被偵測。

因此，工具使用的探測方式是已知事實，而沒有告警的真正原因仍需要更多證據。

### **11.2 EC-Q388：哪一種掃描最能避開 IDS？**

題庫傾向選擇 SYN Scan。

但這個問題缺少 IDS 類型、部署位置、規則和測試流量條件。

不同工具在不同網路環境中，可能呈現不同可見性。

所以可以說 SYN Scan 不完成完整 TCP 交握，不能直接說它一定能規避 IDS。

### **11.3 EC-Q522：UDP 沒有回應，一定是 open|filtered 嗎？**

依照 Nmap 一般的 UDP 掃描判讀規則，沒有回覆通常歸類為 `open|filtered`。

但題目又宣稱沒有防火牆或 IDS 干擾。

這時就必須考慮服務不回應無效資料、封包遺失、限速等其他原因。

問題不是 Nmap 的分類錯誤，而是題目是否已充分給出判定真實狀態的條件。

### **如何處理這類題目？**

我建議養成三層判讀習慣：

| 層次   | 應該回答的問題              |
| ---- | -------------------- |
| 題庫意圖 | 出題者最可能希望選擇哪個選項？      |
| 技術機制 | 這個選項在哪些條件下成立？        |
| 證據限制 | 目前還缺少什麼，才能形成可靠的實際判斷？ |

這種方法比單純背誦答案更有價值，也能避免將證照題目的簡化假設誤用到真正的系統安全分析。

## **最後整理：真正要建立的五個觀念**

1. **IP、Port、Service 是不同層次。** 找到開放埠，不等於證明特定軟體存在，更不等於證明存在漏洞。
2. **TCP 與 UDP 的掃描證據不同。** TCP SYN/ACK 是較明確的狀態線索；UDP 靜默往往留下較多不確定性。
3. **Host Discovery、Port Scanning、Enumeration 是不同任務。** 每一步取得的證據，都有自己的推論邊界。
4. **安全控制必須對準真正的安全目標。** TLS 保護傳輸，DNSSEC 驗證 DNS 資料，身分驗證與授權控制資源存取，IDS 則負責依觀測與規則偵測活動。
5. **沒有觀察到，不等於沒有發生。** 沒回覆、沒日誌、沒告警，都必須結合觀測位置、探測條件與替代解釋判讀。
