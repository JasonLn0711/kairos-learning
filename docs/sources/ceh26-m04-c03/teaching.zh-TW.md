# CEH M04-03｜FTP／SMTP 列舉：讀懂回覆，分清資訊與權限

FTP / SMTP Enumeration · 新版第三課

這一課把檔案服務與郵件服務放在一起，練習同一個判斷：**對方願意回答什麼、目前讓你做了什麼，以及還缺哪些證據。** 我們先用生活例子建立概念，再讀兩份合成紀錄，最後只做一個小檢核。

## 一、服務像櫃檯，回答問題和允許辦事是不同層次

想像你走進辦公大樓。櫃檯會告訴你這裡有哪些部門，也可能提供公開的資料目錄。知道某份資料的名稱，不表示你能翻閱內容；有訪客證，也不表示能修改所有文件。

電腦服務也有這些區別：

- **服務辨識**：這個入口是否回應？它宣告提供哪種服務？
- **資訊列舉（Enumeration）**：進一步整理它提供的名稱、功能、目錄或帳號線索。
- **身分驗證（Authentication）**：服務如何確認你用哪個身分連線。
- **存取授權（Authorization）**：這個身分可對哪些資源執行哪些操作。

另外還有一層「測試授權」：管理者同意你測試的範圍。服務技術上接受某個要求，不會自動擴大你被允許測試的範圍。

本課使用原創、虛構的文字紀錄；沒有連線、登入、下載檔案或寄送郵件。名稱與帳號只表示教學角色，請不要拿它們去測試真實服務。

## 二、FTP 做什麼？先分開指令與資料

**FTP（File Transfer Protocol，檔案傳輸協定）**讓用戶端和伺服器交換檔案。用戶端是發出要求的軟體，伺服器則處理這些要求。

FTP 通常有兩類連線：

- **控制連線**：傳送要求與回應，常用 TCP 21。例如告知帳號、詢問功能、要求列出目錄。
- **資料連線**：傳送檔案內容或目錄清單，與控制連線分開。

這就像你先打電話向倉庫訂資料，再由另一條運送路線拿到資料。電話接通，運送路線仍可能不通。因此，「已登入，但列目錄失敗」值得先查資料連線與政策，不宜立刻認定帳號錯誤。[FTP 基本連線與命令](https://www.rfc-editor.org/rfc/rfc959.html)

資料連線又有兩種常見安排：

- **主動模式（Active Mode）**：用戶端告知接收位置，伺服器發起資料連線。
- **被動模式（Passive Mode）**：伺服器提供資料連線的接收位置，用戶端再連過去。

EPSV 是被動模式的延伸命令，回覆資料連接埠，資料連線使用控制連線所連的伺服器位址。防火牆或網路位址轉換（NAT，讓不同位址範圍之間轉換連線位址的機制）會影響這些連線。因此不要把所有 FTP 資料傳輸都背成「一定走 TCP 20」。[FTP 的 IPv6 與 NAT 延伸](https://www.rfc-editor.org/rfc/rfc2428.html)

## 三、FTP 能列舉哪些資訊？每個要求都有範圍

**Banner（服務招呼文字）**是連線後看到的歡迎或識別訊息。它可能提供產品名稱，但文字可被設定、隱藏或由前置服務提供，應記成「端點宣告的資訊」，不能只靠它判定完整版本或漏洞適用性。

**FEAT** 詢問伺服器支援哪些延伸功能。看到某個功能名稱，只能證明該次對話宣告它；登入狀態、設定與政策仍會影響能否使用。[FTP 功能協商](https://www.rfc-editor.org/rfc/rfc2389.html)

檔案清單也有不同表示法：**MLSD** 可列出目錄項目與標準化欄位，例如檔案類型、大小、修改時間；**MLST** 用於提供單一項目的資訊。這些是檔案的描述資料，稱為 **Metadata（中繼資料）**。讀到名稱或大小，與讀到檔案內容是兩件事。[FTP 機器可讀目錄延伸](https://www.rfc-editor.org/rfc/rfc3659.html)

傳統 **LIST** 常提供人類閱讀的目錄清單，**RETR** 要求取得檔案，**STOR** 要求儲存上傳資料。它們代表不同操作。檢查時應分別記錄「列目錄、讀取、寫入」的結果，不能因為其中一項成功，就替其他項目填上成功。[FTP 操作定義](https://www.rfc-editor.org/rfc/rfc959.html)

## 四、匿名登入代表使用共同身分，權限仍要另外確認

**Anonymous FTP（匿名 FTP）**通常提供不具個人專屬帳號的存取方式。管理者可能刻意用它公開下載資料，因此「匿名登入可用」本身不是漏洞結論。

風險要對照原定用途：

- 只供下載的區域是否意外允許上傳或刪除？
- 不該公開的備份、設定或其他資料是否出現在可見範圍？
- 匿名使用者能看到的目錄與可讀檔案是否超過政策？

匿名帳號取得的權限應受到限制；若業務不需要匿名服務，就應關閉。傳統 FTP 的明文密碼與資料傳輸也需要納入風險評估。[FTP 安全考量](https://www.rfc-editor.org/rfc/rfc2577.html)

安全的報告會把「觀察」和「政策」放在一起。例如：「指定測試身分可列出公開目錄；依政策，此目錄允許列出。財務目錄未測，不能列為已通過檢查。」這樣比直接寫「FTP 安全」更有用。

## 五、讀一份 FTP 合成紀錄

以下只模擬已獲准實驗室中的幾個步驟，省略連線建立、登入與資料通道協商細節。每行旁的「用戶端／伺服器／資料」說明資料來源，不是要貼到終端機執行的指令稿。

伺服器：230 Session established
用戶端：MLSD
伺服器：150 Data transfer starting
資料：type=file;size=640; notice.txt
資料：type=file;size=8192; draft.txt
伺服器：226 Transfer complete
用戶端：RETR draft.txt
伺服器：550 Access denied

逐步讀取：

1. 230 表示伺服器回報目前已登入。這裡沒有提供登入過程，因此不能自行補寫成「匿名登入成功」。
2. MLSD 的兩筆資料讓我們知道該次清單列出 notice.txt 與 draft.txt，以及伺服器回報的大小。
3. 226 對應前面的清單傳輸完成，不代表後面的檔案下載也完成。
4. RETR draft.txt 後收到拒絕；這份紀錄沒有取得 draft.txt 的內容，也沒有測試寫入。

這個例子的重點是：**名稱可見、內容可讀、檔案可寫，必須分別留下證據。** 若看到 425 資料連線無法建立，調查方向又與這裡明示的 Access denied 不同。[FTP 回應與狀態順序](https://www.rfc-editor.org/rfc/rfc959.html)、[MLSD 清單欄位](https://www.rfc-editor.org/rfc/rfc3659.html)

## 六、FTP、FTPS、SFTP，名稱相近但不能混用

**TLS（Transport Layer Security，傳輸層安全協定）**用來保護連線上的資料。**FTPS**是在 FTP 上加入 TLS；控制連線與資料連線的保護需要分別確認。控制連線完成 TLS，不代表資料連線就已加密。PROT P 表示要求以 TLS 保護資料連線；仍要核對實際協商與設定。[FTP 使用 TLS](https://www.rfc-editor.org/rfc/rfc4217.html)

**SFTP（SSH File Transfer Protocol）**則是透過 SSH 安全連線提供檔案操作的另一種協定。SSH 是安全遠端連線協定；OpenSSH 的 sftp 用戶端使用它傳輸資料。SFTP 不是「把 FTP 換成另一個連接埠」，也不是 FTPS 的另一個拼法。[OpenSSH sftp 手冊](https://man.openbsd.org/sftp.1)

選用加密傳輸後，仍要驗證對端身分與檔案權限。加密保護傳輸，並不決定某個帳號應該能讀哪些檔案。

## 七、SMTP 是郵件收送櫃檯，先區分投遞與寄件提交

**SMTP（Simple Mail Transfer Protocol，簡易郵件傳輸協定）**處理郵件傳送；它不是拿來瀏覽收件匣的協定。

先分清兩個角色：

- 郵件伺服器之間轉送郵件，通常使用 TCP 25。
- 使用者把要寄的信交給寄件服務，稱為 **Message Submission（郵件提交）**，常用 TCP 587，依服務政策驗證使用者身分。

這兩種角色的存取政策不同。外部郵件伺服器投遞給本網域收件人，與替任意來源轉寄給任意外部網域，不應混為一談。[郵件提交與轉送分工](https://www.rfc-editor.org/rfc/rfc6409.html)

TCP 465 也用於一開始就建立 TLS 的郵件提交。587 常搭配 STARTTLS，將既有 SMTP 連線升級為 TLS；實際保護要看協商與驗證，不靠埠號猜測。[加密郵件提交的建議](https://www.rfc-editor.org/rfc/rfc8314.html)

## 八、SMTP 回覆能透露功能，但帳號線索要審慎判讀

**EHLO** 是用戶端自我介紹並取得延伸功能清單的要求。伺服器可能宣告 STARTTLS 或 AUTH 等功能。

**AUTH** 是 SMTP 身分驗證延伸。看到 AUTH，代表伺服器在當時宣告相關機制，不表示你已登入；未看到它，也要先確認是否需完成 TLS 才會提供。不要把支援某種登入機制寫成登入成功。[SMTP 身分驗證延伸](https://www.rfc-editor.org/rfc/rfc4954.html)

**VRFY** 用於查詢使用者或郵件地址資訊，**EXPN** 用於展開郵件名單。伺服器可能基於資訊揭露風險限制它們。判讀時保留完整命令、回應碼與文字：

- 252：伺服器未確認所問使用者，不能當成帳號存在或不存在的證明。
- 550：要求未被接受，可能涉及信箱不存在、權限或政策；要連同當時要求與文字判讀。
- 250：某個要求成功，意義取決於它回應的是哪一步。

例如接受一個收件者，不等於信件已完成傳送；伺服器也可能延後驗證收件人。更不能因此推論有人已讀信，或某個郵件地址一定對應可互動登入的作業系統帳號。[SMTP 驗證命令與回應](https://www.rfc-editor.org/rfc/rfc5321.html)

有些回覆還會帶 5.1.1、5.7.1 這種 **Enhanced Status Code（增強狀態碼）**，提供更細的分類，例如地址或政策問題。保存它們能協助查核，但仍需對照伺服器實作與日誌。[郵件增強狀態碼](https://www.rfc-editor.org/rfc/rfc3463.html)

## 九、讀一份 SMTP 合成紀錄：功能清單不是測試結果

這是另一份紙上範例，沒有發信：

伺服器：220 mail.training.example ESMTP
用戶端：EHLO client.training.example
伺服器：250-mail.training.example
伺服器：250-STARTTLS
伺服器：250 SIZE 10485760
用戶端：VRFY learner
伺服器：252 Cannot verify this user

我們能記下：端點有 SMTP 回覆，宣告 STARTTLS 及 SIZE，對這次 VRFY 沒有確認使用者。250 後的連字號表示同一份多行回覆尚未結束，最後一行使用空格。這裡沒有 TLS 交握、登入或郵件提交紀錄。

STARTTLS 出現在清單中，只表示它被宣告。成功升級 TLS 後，先前取得的 SMTP 功能資訊必須重新建立；用戶端應再次 EHLO，因為加密前後的清單可能不同。TLS 還只保護這一段連線，並不自動證明整封信從寄件者到收件者都受到端對端加密。[SMTP STARTTLS 的狀態重設](https://www.rfc-editor.org/rfc/rfc3207.html)

若要調查 **Open Relay（開放式郵件轉送）**，問題應是「未獲准的來源能否透過這台服務，把信轉送到政策不允許的目的地」。只看到 220、250 或 VRFY 的回覆，無法完成這個判斷。本課不安排真實轉寄測試；需要另有測試帳號、收件端與操作範圍的授權。

## 十、防護與驗證：讓業務正常，讓多餘權限消失

對 FTP，先確認是否仍需要服務、哪些身分可用、目錄與讀寫權限如何分配；選擇合適的安全傳輸，限制不必要的匿名存取。對 SMTP，分開管理提交與轉送政策，限制不必要的帳號查詢資訊，要求適當驗證與傳輸保護。

兩者都適用一個做法：用指定測試身分，對照「應允許」與「應拒絕」的操作，再以日誌和設定佐證。驗證範圍要寫到資源與動作，不能只寫「有登入，所以通過」。

例如預定政策是「訪客可以看到公開說明檔，但不能讀取草稿」。驗收應分開確認公開說明檔是否可正常讀取，以及草稿是否受限制。若草稿名稱也應保密，目錄清單能看到它就是另一個需要處理的資訊揭露問題；即使內容讀取被拒絕，名稱曝光仍值得核對。

日誌建議保留：時間與時區、測試來源、身分、協定及加密狀態、要求的資源／操作、完整回應、預定政策、可支持的結論及待查項目。分享時遮蔽真實密碼、驗證資料與不必要的個資。

### 安全紙上練習

環境只需本課文字與一張紙，或離線筆記；不安裝軟體、不發出網路要求。

1. 在兩份紀錄旁標出每個結果回應的是哪個要求，避免把前一步成功套到下一步。
2. 分成「已取得的資訊」「已完成的操作」「尚未確認」三欄整理。
3. 寫出下一步需要哪種證據，例如檔案權限設定、TLS 協商紀錄或伺服器日誌；先不執行測試。

預期產物是一張有界線的證據表，不是一份已通過的系統稽核報告。練習沒有改動系統，不需還原環境；保留筆記即可。

## 十一、最後只做一個小確認

同事讀到「FTP 已登入，MLSD 列出 draft.txt，但 RETR 回覆拒絕」和「SMTP 的 VRFY 回覆 252」，便寫下：

「我們已取得草稿內容，而且已確認 learner 帳號不存在。」

**你會怎麼用一兩句話修正這兩個結論？**
