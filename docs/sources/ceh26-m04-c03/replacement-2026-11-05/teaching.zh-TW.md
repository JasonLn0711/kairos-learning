# M04-03｜FTP／SMTP 列舉：從零開始的白話文教學

**這一課最重要的觀念：知道一個系統有什麼資訊，不代表你有權限使用那些資訊；系統願意回答問題，也不代表它允許你執行操作。**

我們會學習兩種常見的網路服務：

- **FTP（File Transfer Protocol）**：負責傳輸檔案，就像公司的檔案倉庫。
- **SMTP（Simple Mail Transfer Protocol）**：負責傳送電子郵件，就像公司的郵件收發室。

駭客可能透過這些服務蒐集系統資訊，而資安人員則需要判斷哪些資訊不應公開，以及服務是否存在權限設定問題。

本課依 [CS Kairos M04-03 原始教材](https://learn.cs-kairos.com/courses/ceh/v13/m04/concepts/m04-03/) 的 11 個章節進行教學。

## 一、服務像櫃檯：回答問題和允許辦事是兩回事

想像你走進一間公司。

你向櫃檯詢問：

「請問你們公司有哪些部門？」

櫃檯可能回答：

「我們有資訊部、財務部、人資部。」

這代表你知道公司有哪些部門。

但如果你接著詢問：

「那我可以進去財務部看薪資資料嗎？」

櫃檯可能會拒絕。

這就是資安中非常重要的四個概念：

| 概念 | 英文 | 白話文 |
|---|---|---|
| 服務辨識 | Service Identification | 知道這間公司有沒有開門 |
| 資訊列舉 | Enumeration | 知道公司有哪些部門、員工、資源 |
| 身分驗證 | Authentication | 確認你是誰 |
| 存取授權 | Authorization | 決定你能做什麼 |

例如，你知道 FTP 伺服器裡有一個 `salary.xlsx` 檔案。

但這不代表你能夠下載它。

即使你成功登入 FTP，也不代表你具有讀取該檔案的權限。

### 與前面 CEH 課程的關係

在 M03 網路掃描，我們可能透過 Nmap 發現：

```text
21/tcp   open   ftp
25/tcp   open   smtp
```

這代表掃描結果指出目標主機可能有 FTP 與 SMTP 服務。

到了 M04 列舉，我們進一步了解服務提供什麼功能、透露哪些資訊，以及測試身分具有什麼權限。

但是，**發現服務、列出資訊、取得權限、完成操作，是四件不同的事情。**

此外，即使技術上能夠執行操作，也必須確認是否在管理者授權的測試範圍內。

## 二、FTP 是什麼？為什麼會有兩條連線？

FTP 是一種讓電腦之間傳輸檔案的協定。

例如，公司有一台檔案伺服器，員工需要從自己的電腦下載報表。

我們可以把 FTP 想像成物流公司。

你要取得一個包裹，通常有兩件事：

第一件事是向客服提出要求。

第二件事是物流系統實際把包裹送到你手上。

FTP 也有類似的設計。







[[figure:protocols]]

### 1. 控制連線（Control Connection）

通常使用 TCP Port 21。

這條連線負責溝通命令，例如：

「我要登入。」

「請告訴我有哪些檔案。」

「我要下載 report.pdf。」

可以把它想成客服電話。

### 2. 資料連線（Data Connection）

這條連線負責真正傳送檔案內容，或傳送目錄清單。

可以把它想成物流配送。

因此，會出現一種情況：

你成功登入 FTP，也成功要求伺服器列出目錄，但資料連線卻無法建立。

原因可能是防火牆或網路設定阻擋了資料連線。

這時候並不是帳號密碼一定有問題。

### 3. Active Mode 與 Passive Mode

FTP 傳送資料時，有兩種常見方式。

**主動模式（Active Mode）**

用戶端告訴伺服器：「我在這裡等你連過來。」

然後伺服器主動建立資料連線。

**被動模式（Passive Mode）**

伺服器告訴用戶端：「我已經準備好這個接收位置，你連過來。」

然後由用戶端建立資料連線。

現在很多環境都有 NAT 和防火牆，因此被動模式相當常見。

這裡需要特別注意：

FTP 的控制連線通常使用 TCP 21，但資料連線不一定使用 TCP 20。實際連接埠要看模式及協商結果。[RFC Editor](https://www.rfc-editor.org/rfc/rfc959.html)

## 三、FTP 列舉：可以從伺服器問出哪些資訊？

假設你連上公司的 FTP 伺服器。

你可以把 FTP 列舉想像成向檔案管理員詢問問題。

不同命令代表不同問題。

| FTP 命令 | 白話文 | 用途 |
|---|---|---|
| `FEAT` | 你支援哪些功能？ | 查詢伺服器宣告的功能 |
| `LIST` | 這個資料夾有什麼？ | 列出目錄 |
| `MLSD` | 給我標準格式的目錄清單 | 取得目錄項目及其屬性 |
| `MLST` | 告訴我這個項目的資訊 | 查詢單一項目的中繼資料 |
| `RETR` | 我要下載這個檔案 | 要求讀取檔案內容 |
| `STOR` | 我要上傳一個檔案 | 要求寫入檔案 |

### 範例：LIST 與 RETR 有什麼不同？

假設你進入公司 FTP 伺服器，看見：

```text
public/
reports/
finance/
```

這代表你知道有三個目錄。

接著你嘗試進入 `finance`，但伺服器拒絕。

這代表什麼？

代表目錄名稱可能對目前的使用者可見，但不代表該使用者具有進入目錄或讀取裡面檔案的權限。

### Metadata 是什麼？

Metadata 翻譯成「中繼資料」。

簡單來說，就是描述資料的資料。

例如：

```text
filename: report.pdf
size: 102400
modified: 2026-11-04
```

你知道這份檔案的名稱、大小及修改時間。

但你不一定看過這份 PDF 的內容。

這種差異在資安分析非常重要。

即使不能下載檔案，檔案名稱本身仍可能透露敏感資訊，例如客戶名稱、專案代號或備份日期。

## 四、Anonymous FTP：匿名登入是不是漏洞？

不一定。

Anonymous FTP 的概念，是允許使用者使用共同的匿名身分存取服務，而不必擁有個人專屬帳號。

假設某間大學提供公開研究資料。

任何人都可以下載：

```text
public/
├── dataset.csv
├── documentation.pdf
└── license.txt
```

這是大學刻意提供的公開服務。

因此，匿名登入本身不一定是安全漏洞。

真正需要關注的是：

**匿名使用者是否取得了超過預期的權限？**

例如，原本政策只允許下載公開資料，但系統意外允許匿名使用者上傳、覆寫或刪除檔案。

這就產生安全風險。

還有另一種情況：

匿名使用者無法修改檔案，但能看見未公開的資料：

```text
backup/
├── customer_database.sql
└── internal_config.txt
```

即使下載受到限制，檔案名稱的曝光也可能涉及資訊揭露。

另外，傳統未加密 FTP 可能以明文傳輸帳號密碼及資料。因此，即使權限設定正確，傳輸安全仍需另外檢查。[learn.cs-kairos.com](https://learn.cs-kairos.com/courses/ceh/v13/m04/concepts/m04-03/)

## 五、如何看懂 FTP 的操作紀錄？

這是本課非常重要的部分。

假設我們看到教材中的合成紀錄。

首先：

```text
230 Session established
```

這表示伺服器回報目前工作階段已登入。

但我們不知道使用的是哪個帳號，因此不能自行推論是匿名登入。

接著：

```text
MLSD
```

代表用戶端要求取得目錄清單。

伺服器回覆：

```text
150
```

表示準備開始資料傳輸。

資料連線提供了兩個項目的資訊：

`notice.txt` 和 `draft.txt`。

之後伺服器回覆：

```text
226
```

表示前面的目錄清單傳輸已完成。

到目前為止，我們證明了什麼？

**這次測試成功取得了目錄清單。**

但是，還沒有證明可以下載檔案內容。

接著，用戶端要求：

```text
RETR draft.txt
```

意思是：

「我要下載 draft.txt。」

伺服器回覆：

```text
550 Access denied
```

代表這次要求遭到拒絕。

所以，這份紀錄真正支持的結論是：

「使用者看得見 draft.txt 的名稱，但這次下載要求被拒絕。」

而不是「使用者成功取得 draft.txt」。

### FTP 常見回應碼

| 回應碼 | 白話文 |
|---|---|
| `150` | 準備開始資料傳輸 |
| `226` | 目前對應的資料傳輸操作完成 |
| `230` | 伺服器回報已登入 |
| `425` | 無法建立資料連線 |
| `530` | 尚未登入或需要登入 |
| `550` | 要求無法執行，原因需看上下文 |

要特別區分 `425` 和 `550`。

`425` 通常讓我們優先調查資料連線是否建立成功。

`550` 則表示要求未被執行，可能涉及檔案不可用、權限或其他條件，需要看完整回覆。

**不能只看數字就直接推論安全漏洞的原因。**

## 六、FTP、FTPS、SFTP 有什麼不同？

這三個名稱看起來很像，但實際上存在重要差異。

我們可以用寄送文件來理解。

### FTP：一般郵寄

傳統 FTP 不提供內建的傳輸加密保護。

如果沒有其他安全機制，資料及驗證資訊可能被網路路徑上的第三方看見。

### FTPS：加上加密保護的 FTP

FTPS 是 FTP 加上 TLS 保護。

TLS 就是我們在 HTTPS 等服務中經常接觸到的傳輸加密技術。

但是 FTP 有控制連線與資料連線，因此 FTPS 必須分別確認保護狀態。

**控制連線加密成功，不代表資料連線必然已加密。**

例如 `PROT P` 是 FTPS 用來要求保護資料連線的命令，還需要搭配實際的協商及設定驗證。[RFC Editor](https://www.rfc-editor.org/rfc/rfc4217.html)

### SFTP：使用 SSH 的另一種檔案傳輸協定

SFTP 並不是 FTP 加上 TLS。

它是透過 SSH 運作的檔案傳輸協定。

常見使用 TCP Port 22。

可以把它理解成另一套具有安全連線機制的檔案傳輸系統。

### 三者比較

| 比較 | FTP | FTPS | SFTP |
|---|---|---|---|
| 基礎技術 | FTP | FTP + TLS | SSH |
| 常見連接埠 | 21 | 21、990 | 22 |
| 傳輸加密 | 本身沒有 | 支援 | 透過 SSH |
| 是否為相同協定 | FTP | FTP 的安全延伸 | 不同協定 |

注意，這些只是常見連接埠，不能只根據埠號認定協定或加密狀態。

另外，加密與授權是兩回事。

**即使使用 SFTP，也不能保證使用者的檔案權限設定正確。**

# 第二部分：SMTP 列舉

## 七、SMTP 是什麼？

SMTP 是負責傳送電子郵件的網路協定。

你可以把它想成郵局。

當你使用 Gmail 或公司的郵件系統寄信時，背後會有郵件傳送機制負責把郵件送到目的地。

不過，我們需要區分兩件事。

### 第一件事：使用者把信交給寄件伺服器

例如：

你在郵件程式寫好信件，按下「寄送」。

郵件程式將信件交給寄件伺服器處理。

這個步驟稱為：

**Message Submission（郵件提交）**

常見連接埠是：

TCP 587 或 TCP 465。

### 第二件事：郵件伺服器之間傳遞郵件

例如：

公司 A 的郵件伺服器，需要把信送到公司 B 的郵件伺服器。

這通常使用 TCP Port 25。

可以理解成：

```text
你的郵件程式
      │
      │ TCP 587 / 465
      ▼
公司的寄件伺服器
      │
      │ TCP 25
      ▼
對方的郵件伺服器
      │
      ▼
收件者的信箱
```

這兩種工作雖然都使用 SMTP，但安全政策不一樣。

一般使用者提交郵件，通常需要適當的身分驗證。

郵件伺服器之間的正常投遞，則不能簡單地要求所有外部寄件伺服器都使用本公司的使用者帳號登入。

### SMTP 與 IMAP、POP3 的區別

SMTP 主要負責送信。

IMAP 和 POP3 則主要用於讓使用者存取信箱中的郵件。

所以，SMTP 不是用來直接瀏覽收件匣的協定。

---

## 八、SMTP 列舉：EHLO、AUTH、VRFY、EXPN

假設你連上郵件伺服器。

你可以向它提出不同問題。

### 1. EHLO：詢問伺服器支援哪些功能

EHLO 可以想成：

「你好，我是郵件用戶端，請問你支援哪些功能？」

例如，伺服器可能宣告：

```text
250-STARTTLS
250-AUTH PLAIN LOGIN
250 SIZE 10485760
```

這些資訊的意思是：

`STARTTLS`：伺服器宣告支援透過這個機制升級傳輸加密。

`AUTH`：伺服器宣告支援所列的 SMTP 驗證機制。

`SIZE`：伺服器宣告郵件大小限制。

這裡的重點是：

**伺服器說它支援某功能，不代表你已經成功使用該功能。**

例如，看到 `AUTH`，不代表你已經登入。

看到 `STARTTLS`，也不代表目前連線已經加密。

而且，有些 SMTP 伺服器會在完成 TLS 升級後才宣告部分驗證功能，因此不能單憑加密前的清單判斷最終支援狀態。[RFC Editor](https://www.rfc-editor.org/rfc/rfc4954.html)

### 2. VRFY：詢問使用者資訊

VRFY 可以理解成：

「請問你能不能確認這個使用者？」

假設你詢問：

```text
VRFY learner
```

伺服器回覆：

```text
252 Cannot verify this user
```

這代表什麼？

代表伺服器沒有確認該使用者。

但不能直接判斷：

「這個帳號不存在。」

因為伺服器可能刻意限制帳號查詢，以免外部人員蒐集使用者資訊。

### 3. EXPN：查詢郵件群組的成員

假設某個公司有一個郵件群組：

```text
engineering@example.com
```

這個群組可能對應多位員工。

EXPN 原本可以用來請伺服器展開郵件名單。

但如果對外提供過多資訊，可能造成員工信箱或組織資訊外洩。

因此，管理者可能基於安全政策限制 EXPN。

### 4. SMTP 回應碼

| 回應碼 | 白話文 |
|---|---|
| `220` | 郵件服務已準備好 |
| `250` | 目前這個要求已被接受或完成 |
| `252` | 無法確認所查詢使用者 |
| `550` | 要求未被接受，原因需對照命令與回覆文字 |

這裡最容易犯的錯誤是：

「SMTP 回覆 250，所以信件一定已送達。」

這個推論不正確。

因為 `250` 只是對某個特定 SMTP 步驟的成功回覆。

例如，伺服器接受收件者地址，不代表完整郵件已經完成投遞。

而且，**SMTP 帳號不一定等於作業系統帳號。**

知道某個電子郵件地址，也不能直接認定它可以登入 Windows 或 Linux。

## 九、看懂 SMTP 的操作紀錄

教材提供了一份合成紀錄。

我們逐步解釋。

### 第一個步驟：連上郵件伺服器

```text
220 mail.training.example ESMTP
```

代表伺服器回報郵件服務已準備好。

但目前沒有登入。

### 第二個步驟：詢問伺服器功能

```text
EHLO client.training.example
```

伺服器提供功能清單。

其中宣告支援 STARTTLS。

這裡需要注意 SMTP 的多行回覆格式。

例如：

```text
250-mail.training.example
250-STARTTLS
250 SIZE 10485760
```

`250-` 後面的連字號代表這一組多行回覆尚未結束。

最後一行使用 `250` 加上空格。

因此，這是同一個 EHLO 要求所對應的多行回覆。

### 第三個步驟：詢問使用者

```text
VRFY learner
```

伺服器回覆：

```text
252 Cannot verify this user
```

這不能證明使用者不存在。

### 第四個步驟：我們能做出什麼結論？

目前已經知道：

這台服務有 SMTP 回應，並且宣告了部分延伸功能。

同時，伺服器沒有確認指定使用者。

但目前沒有證據顯示：

TLS 已成功建立、使用者已成功登入、郵件已經提交，或郵件已經送達。

### STARTTLS 還有一個重要細節

完成 STARTTLS 升級後，SMTP 用戶端應重新發送 EHLO。

因為加密前後的伺服器功能清單可能不同。

而且，SMTP 連線上的 TLS 只保護對應傳輸區段，並不自動提供寄件者到收件者的端對端加密。[RFC Editor](https://www.rfc-editor.org/rfc/rfc3207.html)

### 什麼是 Open Relay？

Open Relay 稱為「開放式郵件轉送」。

想像某間郵局原本只應該處理符合政策的郵件。

但現在任何陌生人都可以利用它，把郵件轉寄到任意外部地址。

這就可能成為垃圾郵件濫發的管道。

不過：

**看到 SMTP 服務有開放 Port 25，不能證明它是 Open Relay。**

看到 EHLO 成功，也不能證明。

必須在有授權的測試環境中，依來源與目的地的政策確認轉送行為，才能支持相關結論。

## 十、防護與驗證：我們應該怎麼保護 FTP 和 SMTP？

這一章的重點，是從資安人員的角度判斷系統安全。

假設你負責一間公司的資安管理。

你不應該只確認：

「FTP 有沒有登入成功？」

而應該確認：

「這個帳號究竟可以存取哪些檔案？」

同樣地，你不應該只確認：

「SMTP 有沒有正常回覆？」

而應該確認：

「郵件服務是否允許符合政策的傳送行為，同時拒絕不該允許的轉送？」

|---|---|---|
| 服務存在 | FTP 有回應 | SMTP 有回應 |
| 功能資訊 | FEAT 宣告功能 | EHLO 宣告功能 |
| 身分驗證 | 指定帳號完成登入 | 指定帳號完成驗證 |
| 存取授權 | 允許讀取指定檔案 | 允許符合政策的郵件提交或轉送 |
| 操作結果 | 檔案確實讀取成功 | 指定郵件處理步驟成功 |
| 安全驗證 | 非授權檔案受到限制 | 非授權轉送受到限制 |

在正式資安稽核中，還需要保存測試時間、測試身分、命令、回覆、加密狀態及相關設定或日誌。

因為我們最終要回答的不是：

「系統看起來有沒有問題？」

而是：

**「根據政策要求與實際測試證據，我們能證明哪些操作被允許，又能證明哪些操作受到限制？」**

這種思考方式，也適用於前面學過的 DNS 列舉，以及接下來的 SMB 列舉。

## 十一、最後確認：為什麼這兩種推論都是錯的？

教材最後提出兩個情境。

第一個是：

FTP 已登入，而且 MLSD 列出了 `draft.txt`，但下載要求遭到拒絕。

第二個是：

SMTP 使用 VRFY 查詢指定帳號，得到 `252`。

如果有人因此寫下：

「已取得草稿內容，而且已確認帳號不存在。」

這兩個結論都超出現有證據。

FTP 的紀錄只能說明檔案名稱可見，但下載要求沒有成功。

SMTP 的紀錄則只能說明這次查詢沒有確認該使用者，不能直接證明帳號不存在。

這是整個 M04-03 最希望建立的判斷能力。

# 本課重點整理

如果要把這一課濃縮成三句話：

**第一句：FTP 管檔案，SMTP 管郵件。**

FTP 用來交換檔案，SMTP 用來傳送郵件。兩者都是網路上的服務，也都可能在回覆中提供資訊。

**第二句：列舉資訊，不等於取得權限。**

看到檔案名稱不等於能下載；看到郵件伺服器支援驗證，也不等於已經登入。

**第三句：每一項資安結論，都必須有對應證據。**

不能因為某個步驟成功，就推論其他步驟也成功。

這是從 CEH M03 網路掃描、M04 資訊列舉，進入 M05 弱點分析時非常重要的觀念。

## 理解檢核

以下有兩個情境，請嘗試判斷。

**問題一：FTP**

你正在檢查公司內部 FTP 伺服器，使用經授權的測試帳號成功登入，並且可以列出以下檔案：

```text
public.txt
employee_salary.xlsx
backup.sql
```

但你尚未下載任何檔案。

請問：

A. 你能不能認定這些檔案都已經外洩？

B. 如果政策規定薪資檔名也不得對一般員工公開，這份紀錄有沒有值得調查的問題？

**問題二：SMTP**

你在已授權的測試環境中，向郵件伺服器發送 EHLO，伺服器宣告支援 STARTTLS 與 AUTH。

請問：

A. 這代表目前連線已經加密了嗎？

B. 這代表你已經成功登入了嗎？

C. 如果想確認郵件伺服器會不會被濫用為 Open Relay，還需要取得哪一類證據？

請先回答各題的 A、B、C，再比對參考解答，檢查你的判斷及推理。
