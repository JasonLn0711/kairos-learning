**M04-08｜LDAP／Active Directory 列舉：查到一些帳號，怎麼判斷有沒有查完整？**

**先說結論：LDAP 查詢得到的是「這個身分，在這次查詢條件與限制下看見的資料」。要把它當成完整盤點，還得確認查詢範圍、權限、回傳欄位，以及結果是否收完。**

這一課接續 LDAP 的基礎，回顧目錄位置、搜尋範圍及登入，並用一個新的合成案例，把它們串成「如何判讀結果」的完整流程。只討論合法授權的隔離環境，不對第三方目標操作。

**1. 把目錄想成公司的通訊錄**

通訊錄可能記錄同仁姓名、帳號、所屬部門與群組。你問櫃檯「研發部有哪些人」，櫃檯給了兩個名字，並不代表全公司只有兩個人：你問的範圍、可看的資料和是否還有下一頁，都會影響答案。

LDAP，全名 Lightweight Directory Access Protocol，中文是「輕量型目錄存取協定」，就是程式向目錄查詢資料的一套溝通規則。Active Directory Domain Services，簡稱 AD DS，中文是「Active Directory 網域服務」，是微軟管理帳號、電腦與相關目錄資訊的服務。LDAP 是溝通方式，AD DS 是提供目錄服務的系統，兩者不是同義詞。

列舉，英文 Enumeration，在這裡是依條件整理可取得的目錄項目與屬性。防守方可用它盤點帳號及檢查資訊暴露；未經授權的人若讀到過多資料，也可能藉此了解組織結構。**所以要控制誰能看什麼，不能只想著把協定一律關掉。**

**2. 先弄清楚你到底問了什麼**

目錄中的一筆資料叫 Entry，中文可理解為「項目」；項目內的姓名、郵件等欄位叫 Attribute，也就是「屬性」。DN 是 Distinguished Name，「識別名稱」，用來描述項目在目錄階層中的位置。

例如合成資料 CN=Lin,OU=People,DC=example,DC=test，可讀成：example.test 目錄內 People 組織單位中的 Lin 項目。這裡 CN 是通用名稱，OU 是組織單位，DC 是網域名稱的組成部分。另一種常見用語 Domain Controller 也縮寫 DC，意思是「網域控制站」，不要與 DN 裡的 DC= 欄位混淆。

一次搜尋至少要看清四件事：

- Base：從哪個項目開始找。
- Scope：搜尋多深。base 只看起點本身；one-level 只看下一層，不含起點；subtree 看起點與底下各層。
- Filter：只挑符合什麼條件的項目，例如特定類型或名稱。
- Requested attributes：要求回傳哪些欄位。

這像向櫃檯說：「以研發部為起點，只查直接隸屬的人，只要符合某條件者，給我姓名即可。」你沒查子部門，也沒要求郵件欄位，就不能拿結果宣稱「子部門沒人、這些人都沒有郵件」。

**3. AD 裡，查詢入口也有差別**

AD 的網域是組織目錄的一個管理範圍；樹系是由一個或多個網域構成的整體架構。這裡先記住：**一個網域不必然等於整個樹系。**

RootDSE 是 LDAP 伺服器用來提供自身資訊的特殊項目，可以把它想成櫃檯的「服務說明牌」。它能告訴你伺服器有哪些目錄分割區、支援哪些能力。在 AD 中，defaultNamingContext 可幫你找到該伺服器的預設網域目錄起點。讀到說明牌，不代表已經拿到所有帳號，也不代表匿名身分可讀整份通訊錄。

Global Catalog，簡稱 GC，中文是「通用類別目錄」，則像跨網域的索引。它能協助跨網域找物件，但對其他網域持有的是部分屬性的副本，不是每個物件所有欄位都在裡面。

因此，某欄位沒出現在 GC 查詢結果中，可能與它未包含在該部分屬性集合有關。應再核對查詢欄位、資料所在目錄及讀取權限，不能直接說原始資料不存在。

**4. 帳號登入、讀取權限、傳輸保護是三件事**

LDAP 的 Bind 是建立或變更連線驗證狀態的操作。你要記錄實際採用的驗證方式及身分，不能只看到「Bind 成功」四個字，就認定自己以某個帳號登入、而且什麼都能看。

想成公司櫃檯就很好理解：

- 驗證：你是誰，或目前是不是匿名身分。
- 授權：這個身分可讀哪些項目與欄位。
- 傳輸保護：查詢與資料在路上會不會被偷看或竄改。

TLS，中文是「傳輸層安全協定」，可保護傳輸。LDAPS 通常在 TCP 636 連線開始時使用 TLS；StartTLS 則可在 TCP 389 的 LDAP 連線上啟動 TLS。不要只靠埠號判斷安全，要確認實際保護有成功建立，且伺服器憑證驗證正確。

另有 LDAP signing，也就是「LDAP 簽章」，主要用於驗證訊息完整性與來源。**簽章不等於加密：內容未被竄改，和旁人看不到內容，是不同保證。** 實際防護要核對作業系統版本、驗證方式與生效設定，不套用「所有 AD 預設都一樣」的說法。

**5. 新案例：畫面有資料，不等於搜尋做完了**

以下完全是教學用的合成紀錄，沒有連線、沒有實測，也不代表任何真實公司的資料。

你獲准盤點隔離實驗網域中 People 組織單位底下的帳號。工具顯示：

- 查詢起點：OU=People,DC=example,DC=test。
- 搜尋範圍：subtree。
- 篩選條件：本次帳號盤點指定的條件。
- 回傳欄位：只有 cn，也就是通用名稱。
- 本次搜尋的筆數限制：2。
- 顯示兩筆名稱：Lin、Chen。
- 最後狀態：sizeLimitExceeded，結果代碼 4。

**觀察：**你收到兩筆符合本次條件、且本次身分可見的項目；搜尋因筆數限制沒有正常收完。

**可以下的結論：**目前取得兩筆結果，但完整數量尚未確認。

**不能下的結論：**People 底下總共只有兩個帳號；整個網域只有兩個帳號；這兩人沒有郵件；他們能登入任何特定應用程式。

你應先保留原始查詢條件、身分、結果及結束狀態。後續若仍在授權範圍內，可使用工具支援的分頁搜尋，逐頁取回資料，而不是為了讓數字變多就直接改動正式伺服器的限制。

Paging 是「分頁」：資料分批回來，工具用伺服器提供的續查資訊取得下一批。頁面大小是每批上限，不是帳號總數。**只看第一頁，或沒有確認工具把後續頁面取完，都不能當作完整結果。** 分頁也不會自動擴大你的讀取權限或搜尋範圍。

即使最後顯示 success，也只表示這次操作成功；它不是「整個組織所有資料都盤點完畢」的保證。盤點是否完整，還要回頭對照你原先要回答的問題。

**6. 防守方應留下什麼證據？**

以下是這個案例的驗證做法，不是聲稱已完成的設定：

- **查詢可重現：**記錄時間、伺服器、使用身分、起點、範圍、篩選條件與欄位；不記錄密碼或秘密。
- **結果有收完：**保留最後結果代碼、分頁是否完成及工具錯誤，將「收到幾筆」與「是否完整」分開。
- **可見範圍合理：**用管理者事先建立的合成測試資料核對低權限帳號可見內容；讀不到的原因保留待確認，不自行提高權限。
- **連線確實受保護：**核對實際 TLS 連線及憑證驗證，而非只看連線位址寫了 636；若查簽章，另確認適用的驗證方式與有效設定。
- **異常判讀有上下文：**大量目錄查詢值得調查，但盤點工具也會合法查詢。把來源、身分、時間及既有作業排程一起看，不能只憑「有 LDAP 查詢」判定入侵。

**這課要帶走的一句話：先問「我用誰的身分、從哪裡、按什麼條件查，結果收完了嗎」，再解釋查到的數字。**

**小檢核，一題就好**

同事用已驗證的低權限帳號，經過有效 TLS 連線，對 People 組織單位做 one-level 搜尋，只要求姓名。工具顯示兩筆結果及 success，他說：「People 底下連同所有子部門只有兩個人，而且都沒有郵件。」

這個結論有哪兩處超出證據？你會先核對哪兩個查詢設定？
