# M02-05 參考解答

## answer-check｜郵件角色與驗證

退信交由 platform.example 處理，畫面作者使用 shop.example。可信收件端顯示 DKIM 驗證通過，而且簽署網域 d=shop.example 與 From 的 shop.example 相同；這條路徑符合 DMARC 的驗證與對齊條件。

SPF pass 描述 platform.example 這個信封網域的寄送來源檢查。各自記下檢查對象，就容易看懂平台代寄的分工。

遇到更改付款帳戶的要求，可透過原先保存的官方電話、已知客服入口或原有負責人聯絡方式確認。以獨立取得的管道核實新收款資訊，完成技術與業務兩層查核。

## answer-choice｜Received 與可信紀錄

選 B：先查看自家可信節點產生的 Received。它記錄該節點接收郵件的連線對象與時間，適合對照自家日誌。接著逐段確認上游紀錄的產生者，再整理時間順序。

## answer-extension-1｜兩種驗證通過後，還要對照哪個網域？

答案是 A。SPF 通過的信封網域是 mailer.example，DKIM 通過的簽署網域也是 mailer.example；畫面 From 則是 bank.example。兩條通過的路徑都與 bank.example 未對齊，因此這份可信結果記為 DMARC fail。

可以在紙上畫三欄：From → bank.example；SPF → mailer.example；DKIM → mailer.example。先找出每個驗證結果所屬的身分，再與 From 比較。DMARC 的通過條件是至少一條「通過而且對齊」的路徑。SPF 的來源 IP 檢查與 DKIM 的簽章檢查，各自有不同工作；合法代寄可以透過對齊的信封網域或 DKIM 簽署網域配合此規則。

## answer-extension-2｜從哪裡開始驗證 Received？

答案是 B。先讀公司可信收件節點自己產生的 Received，對照實際連線來源與郵件日誌，再逐段往前核對。最下面那行可以先列為「較早的來源主張」，確認其寫入系統後，再給予相應的證據權重。

記憶方式是：「時間線由下往上整理；可信度從自己的收件系統往前查。」若先前節點的日誌尚未取得，就把那段列為待查證，保留原始標頭與已核實部分。若需確認實際操作人員，另依權限取得帳號與登入等紀錄。

## answer-extension-3｜哪兩項證據能支持下一步判斷？

第一項可以是己方郵件閘道或 MTA 日誌，搭配它產生的 Received 與 Authentication-Results。核對接收時間、連線 IP、內部郵件識別與驗證服務，確認這份結果確實屬於本封郵件，並確認外部系統把信送到哪個己方節點。

第二項可以是銀行既有官方聯絡管道及相關業務或交易紀錄。使用先前已保存、由獨立來源確認的客服或承辦窗口，核對本次要求、通知編號與交易背景；涉及付款變更時，沿用公司的覆核流程。這樣同時建立技術來源和實際業務需求的證據。

其他合理材料包括授權取得的代寄服務日誌、DKIM 簽章與當時驗證紀錄、帳號異常登入紀錄。判斷重點是寫清楚每份材料回答哪一個問題，並把技術驗證與業務確認接起來。
