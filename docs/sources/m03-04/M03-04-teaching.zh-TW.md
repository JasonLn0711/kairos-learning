# CEH M03-04｜Open、Closed、Filtered：從回應讀懂連接埠狀態

連接埠掃描（Port Scanning）透過探測與回應，判讀一個通訊入口在當時呈現的狀態。先記住：open 有接受通訊的證據；closed 有明確的關閉回應；filtered 表示這種探測無法確認入口是否開放。實際分類還要看掃描方法。

M03-01 認識 IP、TCP、UDP 與 Port；M03-02 探索主機並解讀 ICMP、ARP；M03-03 比較 Connect、SYN、UDP 掃描。這一課把結果串成「方法 → 回應 → 狀態 → 查核 → 安全判斷」。讀完後，請用最後四個情境題練習寫出證據與下一步。

## 1｜從辦公大樓的分機開始理解

把電腦想成辦公大樓：IP 位址像總機號碼，Port（連接埠）像分機，服務程式像接聽人員，防火牆像限制來電的門禁。比喻幫助我們分工；實際入口必須用 IP、傳輸協定與 Port 一起描述。

| 常見入口 | 常見用途 | 判讀限制 |
| --- | --- | --- |
| TCP 22 | SSH 遠端管理 | 編號不能證明實際服務 |
| TCP 80 | HTTP | 仍需應用層查核 |
| TCP 443 | HTTPS | TCP 成功不保證 TLS／網站正常 |
| TCP 3306 | MySQL | 服務可能使用其他編號 |

例如 192.0.2.10:443/TCP 與 192.0.2.10:443/UDP 是兩個入口。TCP 443 可能提供 HTTPS；UDP 443 可能提供 HTTP/3（使用 QUIC）。TCP 443 open 不代表 UDP 443 也 open，反過來亦然。

192.0.2.10 與本課其他 192.0.2.x 位址是文件範例，不表示有真實服務。完整的查核問題是：「從哪裡、何時、用什麼協定與方法，探測哪個入口，收到什麼？」實作限定自己的本機或另行核准的設備。

## 2｜先把三個核心狀態分清楚

Nmap 是網路探索與安全稽核工具，會根據探測方法與回應分類。想像打分機：有人接受通話、有人明確回覆不受理，或來電受限制而無法確認是否有人接聽。三種情況得到的證據不同。

| 狀態 | TCP SYN 的典型證據 | 能說明什麼、還缺什麼？ |
| --- | --- | --- |
| open（開放） | 目標回 SYN/ACK | 該入口接受起始連線請求；服務功能與安全性另查 |
| closed（關閉） | 對 SYN 回 RST | 工具判為關閉；核對服務監聽及回覆是否來自中間設備 |
| filtered（受到過濾） | 重試後無回覆或特定 ICMP 錯誤 | 此方法無法確認開放或關閉；核對政策、路徑與日誌 |

open 不等於有漏洞，也不保證應用程式正常。TCP 443 接受請求後，仍可能遇到 TLS 憑證、HTTP 錯誤、登入或權限問題。確認服務與版本可接到 M03-05，弱點分析則需要另外的證據。

closed 通常正是因為收到明確回應才成立，不能解讀成整台電腦關機或網路完全不通。例如 TCP 8443 closed，可能是服務未啟動、未監聽該埠、只綁定其他介面，也可能是防火牆或中間設備產生 RST。工具分類不等於已證明目標主機內部狀態。

filtered 的現象是缺少可確認開放／關閉的回應，或收到符合規則的錯誤。防火牆、路由器規則、主機防火牆是常見原因；封包遺失、設備或路徑異常也會影響探測。不能單憑 filtered 指認某台防火牆。

同一 Port 從不同位置可呈現不同狀態。把結果寫成「從管理網段測得 TCP 443 open」，會比「443 開著」更容易重現。[Nmap：六種狀態](https://nmap.org/book/man-port-scanning-basics.html)

## 3｜TCP SYN 掃描：用回應讀懂三種狀態

TCP 一般新連線的三向交握是：用戶端送 SYN，伺服器回 SYN/ACK，用戶端回 ACK。SYN（Synchronize）同步初始序號；ACK（Acknowledgment）確認收到資訊；RST（Reset）重設連線或連線嘗試。這些是 TCP 標頭中的控制旗標。

```text
一般 TCP 連線：掃描端 → SYN → 目標
              掃描端 ← SYN/ACK ← 目標
              掃描端 → ACK → 目標
SYN 掃描開放情境：收到 SYN/ACK 後，由掃描端以 RST 結束嘗試
```

Connect 掃描請作業系統完成連線。SYN 掃描收到 SYN/ACK 就有接受起始請求的證據，不必再送最後 ACK。Half-open（半開式）描述未完成一般交握，並非 Port 開了一半；也不表示掃描無法被偵測。

| 送出 | 收到 | Nmap 常見分類 |
| --- | --- | --- |
| SYN | SYN/ACK | open |
| SYN | RST | closed |
| SYN | 重試後仍無回應 | filtered |
| SYN | IPv4 ICMP Type 3，Code 1、2、3、9、10、13 | filtered |

對 SYN 回 RST，與掃描端收到 SYN/ACK 後主動送 RST，方向及用途不同。前者是 closed 的典型依據，後者是在 open 探測情境結束嘗試。記錄時要保留來源、目的及前後封包。

ICMP（網際網路控制訊息協定）用來傳遞網路錯誤等資訊。只有符合這種方法規則的 Type／Code 才對應 filtered；不能把所有 ICMP 都當成過濾。上表數字是 IPv4，不套用到 ICMPv6。[Nmap：SYN 判讀](https://nmap.org/book/synscan.html)

例如：「收到 TCP RST」放在觀察欄；「Nmap 分類為 closed」放在判讀欄；「查服務監聽與防火牆日誌」放在下一步。封包回應與工具分類分開，其他人才能核對推論。

## 4｜UDP 的沉默，要保留兩個可能方向

UDP 直接傳送資料報，沒有 TCP 三向交握。可以把它想成寄送申請單：對方可能收到，卻因格式不符而不回覆；也可能是申請單或回信在路上被擋住、遺失。

因此，UDP 沒回應時不能直接判為 closed。open|filtered 的「|」表示「或」：目前無法區分開放但沉默與受到過濾，不是半開放，也不是已證明兩種狀態同時存在。

| UDP 探測後的觀察 | 分類 | 下一步 |
| --- | --- | --- |
| 對應的 UDP 回覆 | open | 核對回覆內容及服務設定 |
| IPv4 ICMP Type 3 / Code 3（Port Unreachable） | closed | 核對接收端點與錯誤來源 |
| IPv4 ICMP Type 3 / Code 1、2、9、10、13 | filtered | 核對路徑與政策 |
| 重試後仍無回覆 | open\|filtered | 補服務格式查詢、監聽設定與日誌 |

ICMP Port Unreachable 表示連接埠無法到達。分析時核對回報來源及其中引用的原始探測，避免把不相關錯誤算入結果。主機也可能對 ICMP 錯誤限速，讓掃描端需要等待與重試。

假設有以下示意輸出：

```text
PORT    STATE          SERVICE
53/udp  open|filtered  domain
```

53/udp 是 UDP 53；open|filtered 保留不確定性；未做服務辨識時，domain 通常只是常見 Port 名稱，不能單靠這一欄證明 DNS 正在執行。

若設備由你管理或已核准測試，可用有效的 DNS 查詢增加證據：

```bash
dig @192.0.2.53 example.com A
```

192.0.2.53 是文件位址，操作時換成已核准的 DNS 伺服器。收到有效 DNS 回應可支持服務有回應該次查詢；dig 在部分情況會改用 TCP，因此要確認輸出或封包確實使用 UDP，才將它算作 UDP 證據。

也可在核准範圍使用服務版本探測。以下是指令格式，尖括號是待替換的目標，不能直接貼入 shell：

```text
sudo nmap -sU -sV -p 53 --reason <authorized-host>
```

-sU 選 UDP，-sV 嘗試辨識服務，-p 53 限定埠，--reason 顯示判定理由。服務探測可能取得回應而縮小不確定性，但不保證消除所有 open|filtered。[Nmap：UDP](https://nmap.org/book/scan-methods-udp-scan.html)

## 5｜另外兩個標籤：知道它在回答哪個問題

ACK Scan（-sA）送出帶 ACK 旗標的探測，主要觀察這類封包的過濾行為。SYN Scan 問入口是否接受新的連線，兩者的判讀規則不同。

```text
掃描端 → 目標／路徑：ACK
掃描端 ← 目標／路徑：RST
ACK Scan 分類：unfiltered
```

unfiltered 表示該 ACK 探測可取得回應，仍未分清 open 或 closed。未受該探測所見過濾的系統，開放與關閉的 Port 都可能對 ACK 回 RST。若重試後無回覆或收到特定 ICMP 錯誤，ACK Scan 會分類 filtered。要確認是否接受新連線，再用核准的 SYN 或 Connect 掃描。[Nmap：ACK Scan](https://nmap.org/book/scan-methods-ack-scan.html)

closed|filtered 則是 IP ID Idle Scan（閒置掃描）使用的候選分類，表示該方法無法區分關閉與過濾。本課先理解標籤，不延伸到閒置掃描操作。

| 狀態 | 可以怎麼讀？ | 還不能斷言什麼？ |
| --- | --- | --- |
| open | 有接受相應通訊的證據 | 所有功能正常或存在漏洞 |
| closed | 得到明確關閉特徵 | 整台主機離線，或已查清所有拒絕原因 |
| filtered | 此方法無法確認入口開放 | 一定由某台防火牆造成 |
| unfiltered | ACK 探測可得到回應 | 服務一定接受新的 TCP 連線 |
| open\|filtered | 開放或過濾尚未區分 | 已確定其中一種 |
| closed\|filtered | 關閉或過濾尚未區分 | 已確定其中一種 |

例如同樣收到 RST：SYN 掃描通常讀成 closed，ACK 掃描讀成 unfiltered。先問工具送了什麼，再讀它收到什麼。[Nmap：狀態定義](https://nmap.org/book/man-port-scanning-basics.html)

## 6｜讀一次完整的合成案例

假設驗收伺服器 192.0.2.10：TCP 443 是管理介面，只允許管理網段；TCP 8443 是目前不應啟用的備用入口；UDP 53 預計提供 DNS。核准從管理網段與一般網段觀察。以下都是合成紀錄，不是實測結果。

| 來源／方法 | 入口 | 回應／分類 | 管理者的下一步 |
| --- | --- | --- | --- |
| 管理網段／SYN | TCP 443 | SYN/ACK → open | 符合接受起始請求的初步預期；續查 TLS、登入與權限 |
| 一般網段／SYN | TCP 443 | 重試無回覆 → filtered | 核對限制規則與同時段日誌，排除非預期路徑故障 |
| 管理網段／SYN | TCP 8443 | RST → closed | 對照目前不應啟用的部署計畫 |
| 管理網段／UDP | UDP 53 | 重試無回覆 → open\|filtered | 用有效 DNS 查詢、監聽設定及日誌補證據 |

443 的兩個結果可以同時正確，因為來源、路徑與存取條件不同。SYN/ACK 只證明起始請求得到接受回應；案例沒有完成三向交握，不能直接寫成已建立完整 TCP 連線。

若 8443 原本應該提供服務，closed 就需要調查：程式是否啟動、埠號是否正確、綁定在哪個位址、是否有中間設備回 RST。Ubuntu 可查看 TCP 監聽端點：

```bash
ss -lnt
sudo ss -lntp
```

第一行可查看監聽狀態；第二行在具備權限時加入程序資訊。127.0.0.1:8443 表示只監聽本機 Loopback（迴環）位址，其他電腦通常不能經伺服器外部 IP 直接連到它。0.0.0.0:8443 表示監聽所有本機 IPv4 位址，但遠端是否可達仍取決於路由、防火牆等條件；它也不自動代表 IPv6。

UDP 53 的下一步是確認 DNS 是否啟動、是否有 UDP 監聽、查詢是否到達服務，以及去回程是否遭到阻擋。程式有監聽與遠端能存取，是兩個要分別驗證的問題。

## 7｜把掃描報告寫成別人能重現的紀錄

| 層次 | 範例 |
| --- | --- |
| 觀察 | 收到 TCP SYN/ACK |
| 工具分類 | Nmap 依 SYN 掃描規則記為 open |
| 下一步 | 核對服務用途、TLS、權限與允許來源 |

在自己的 Ubuntu 上，可先確認工具版本，再只檢查本機三個 TCP 埠：

```bash
nmap --version
nmap -sT -p 22,80,443 --reason 127.0.0.1
```

-sT 是 TCP Connect，-p 22,80,443 限定範圍，--reason 顯示理由，127.0.0.1 連回自己的電腦。未啟動服務的埠可能 closed；實際結果取決於本機設定。這不經過外部網路，不能用來驗收外部防火牆；本機防火牆仍可能影響回應。

若有原始封包權限，可比較 SYN 掃描：

```bash
sudo nmap -sS -p 22,80,443 --reason 127.0.0.1
```

先記下方法與結果，再用核准的 Wireshark 或 tcpdump 擷取確認交握差異。需要停止時按 Ctrl+C。本練習不啟動服務、不改防火牆；結束擷取並妥善保管或移除自行產生的紀錄即可，不需關閉原有服務。

以下是 SYN 掃描的簡化示例，非實測輸出：

```text
PORT      STATE   SERVICE    REASON
443/tcp   open    https      syn-ack
8443/tcp  closed  https-alt  reset
```

可讀成「TCP 443 因收到 SYN/ACK，被分類為 open」。Connect 的理由文字可能是 conn-accepted 或 conn-refused，會依方法及版本而異；不能把 SYN 範例當作 -sT 固定輸出。--reason 提供工具理由，精確封包序列仍要由擷取紀錄核對。[Nmap：輸出選項](https://nmap.org/book/man-output.html)

| 紀錄類別 | 應保留的資訊 |
| --- | --- |
| 範圍 | 目標 IP、協定、Port、授權用途 |
| 條件 | 來源網段、時間與時區、工具版本、選項、等待與重試 |
| 原始觀察 | 封包、系統錯誤、無回應或原始輸出 |
| 判讀 | 狀態與理由，連回所用方法 |
| 後續處理 | 預期差異、設定與日誌、負責人、複測安排 |

例如時間記成 2026-11-03 10:30 UTC+08:00（示例），讓管理者能定位同時段日誌。紀錄可寫：「從管理網段，以 SYN 探測 TCP 443，收到 SYN/ACK，記為 open；依變更單核對服務及來源政策。」

## 8｜防護怎麼做，驗收就怎麼看

open 本身無法回答安全或不安全。公開 HTTPS 與內部資料庫本來就有不同的可存取需求。防護目標是讓入口與業務用途、信任範圍一致。

| 層次 | 要問的問題 | 行動與驗收 |
| --- | --- | --- |
| 服務層 | 這個入口為什麼存在？ | 確認用途、維護人與更新安排；依核准變更停用不必要服務 |
| 存取層 | 誰需要使用？ | 設定必要來源與用途，結合身分驗證、加密及應用權限 |
| 驗收層 | 設定有達到目的嗎？ | 從允許及限制位置分別測試，對照設定與日誌 |

以一台合成的 AI 推論伺服器為例：HTTPS 443 提供給核准使用者，SSH 22 限管理網段，PostgreSQL 5432 只供指定應用主機，Prometheus 9090 限監控網段。這是政策範例，不是對真實設備的設定建議；Port 與來源 IP 不能取代身分驗證及權限控制。

防火牆、安全群組與網路 ACL（存取控制清單）可限制流量。管理網段看到 SSH open、一般網段看到 filtered，是政策可能生效的線索；仍要對照規則、實際連線與日誌，排除路由故障等其他原因。這也銜接 M12 的網路防護觀念。

## 9｜小檢核：把狀態翻成下一步

知識路線是「選方法 → 收集 TCP／UDP／ICMP 或等待結果 → 分類 → 記錄 → 查設定 → 對照政策」。六種狀態是依方法產生的不同結果，不是一定要依序經過的階段。

常見誤解有三個：filtered 不足以指認防火牆；open 不足以證明漏洞；closed 與 filtered 不能互換。狀態幫助選下一步，安全判斷需要用途與政策。

問題一：SYN 掃描 TCP 443 收到 RST。A. 通常是什麼狀態？B. 能據此認定伺服器關機嗎？C. 若預期有 HTTPS，接著查什麼？

問題二：DNS Server 的 UDP 53 顯示 open|filtered。A. DNS 一定啟動嗎？B. 防火牆一定阻擋嗎？C. 如何補證據？

問題三：SSH 22 從管理網段看 open，一般網段看 filtered。A. 是否矛盾？B. 若政策只允許管理網段，是否符合初步預期？C. 完整驗收還缺什麼？

問題四：ACK Scan 顯示 unfiltered。A. 能直接判成 open 嗎？B. 這種方法主要檢查什麼？C. 要確認接受新 TCP 連線，改用什麼方法？

另保留原有紀錄練習：若報告只有「UDP 53 open|filtered」，請補至少四項資訊，讓下一位工程師能接續查核。參考答案在文末收合區；它們不代表讀者已完成測驗。

## 10｜概念問答：把容易混淆的地方接起來

### 10.1｜open 就能直接使用服務嗎？

open 提供相應通訊入口的證據，還可能遇到 TLS、應用錯誤、登入或權限限制。TCP 443 的探測成功與 HTTPS 正常運作分開驗證。

### 10.2｜同一個 Port，為什麼不同人看到不同結果？

來源網段、路徑、NAT／代理、存取政策、時間及方法都可能不同。先確認實際測到同一入口，再比較管理者與一般使用者的結果；若符合設計，兩者可以同時正確。

### 10.3｜UDP 沉默為什麼不能直接算 closed？

服務可能只回覆特定格式，也可能收到但不需要回覆；路徑丟棄也會造成沉默。缺少可區分的證據時，保留 open|filtered，再補有效查詢與設備紀錄。

### 10.4｜unfiltered 與 open 差在哪裡？

ACK Scan 的 unfiltered 只說這類探測取得回應，未確定服務接受新連線。open 則是另一種方法取得接受相應通訊的特徵。同樣收到 RST，SYN 與 ACK 掃描也必須按原本送出的探測分別解讀。

### 10.5｜看到 filtered，調查從哪裡開始？

先對照預期來源政策，再查來源位置、路由、防火牆規則、同時段日誌與服務監聽。必要時從另一個核准位置複測。目標是釐清原因、驗證設計，並非把所有結果都改成 open。
