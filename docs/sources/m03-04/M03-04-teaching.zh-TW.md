# CEH M03-04｜Open、Closed、Filtered：從零開始看懂連接埠掃描結果

**本單元的核心觀念：Port Scan（連接埠掃描）不是單純檢查某個 Port 有沒有開啟，而是透過網路封包的回應，判斷某個服務入口目前呈現什麼狀態。**

你可以先記住三句話：

- **Open（開放）**：有人接聽，這個入口可以接受對應的通訊。
- **Closed（關閉）**：有人明確回覆，但這個入口沒有服務在接聽。
- **Filtered（受到過濾）**：探測受到阻擋或限制，還無法確認入口是否開放。

不過，這三句只是初步理解。真正重要的是：**你怎麼知道它是 Open、Closed 或 Filtered？**

我們要從封包（Packet）如何傳送、對方如何回覆，以及掃描工具如何解讀回覆開始學習。

本課依序說明第 1～10 節，搭配 Nmap 官方技術文件、合成案例，以及前面 CEH M03-01～M03-03 的觀念。最後四個情境題附有參考答案；概念 Q&A 是教材解說，不是學習者提交紀錄。

## 一、先建立完整概念：掃描工具到底在做什麼？

在前面三個單元，我們已經學過：

| 單元 | 學習內容 | 這次如何運用 |
|---|---|---|
| M03-01 | IP、TCP、UDP、Port | 知道封包要送給誰、哪個程式入口 |
| M03-02 | ICMP、ARP、網路探索 | 知道如何探索目標，以及如何解讀網路錯誤回報 |
| M03-03 | TCP Connect、SYN、UDP 掃描 | 知道可以用哪些方法探測 Port |
| **M03-04** | **Open、Closed、Filtered** | **學會根據封包回應判斷 Port 狀態** |

把這四個單元連在一起，其實就是一個很簡單的流程：

```text
                  你想檢查一台伺服器
                          │
                          ▼
               ① 確定伺服器的 IP
                          │
                          ▼
               ② 決定要檢查哪個 Port
                          │
                          ▼
               ③ 選擇 TCP 或 UDP
                          │
                          ▼
               ④ 使用 Nmap 發送探測
                          │
                          ▼
                ⑤ 觀察對方的反應
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
           有接受       明確拒絕     沒有回應
           的回應       的回應       或過濾訊息
              │           │           │
              ▼           ▼           ▼
             Open       Closed      Filtered
                                     │
                          UDP 等方法還可能是
                             Open|Filtered
```

這張圖是概念上的簡化；實際判定必須考慮探測方法。例如，TCP SYN 掃描沒有回應通常會被分類為 `filtered`，但 UDP 掃描沒有回應通常會被分類為 `open|filtered`。

**請特別記住：相同的「沒有回應」，不一定代表相同的 Port 狀態。** [Nmap](https://nmap.org/book/synscan.html)

# 1｜從辦公大樓的分機開始理解

### 1.1 把電腦想像成一棟辦公大樓

假設今天你想打電話給某間公司的資訊部門。

你需要知道兩件事：

第一，這間公司的總機電話是多少？

第二，資訊部門的分機號碼是多少？

電腦的網路通訊也有類似概念。

| 辦公大樓 | 電腦網路 |
|---|---|
| 公司地址 | IP Address |
| 分機號碼 | Port |
| 分機後面的接聽人員 | 接收通訊的服務程式 |
| 打電話 | 發送網路封包 |
| 有人接起電話 | 收到接受通訊的回應 |
| 總機或門禁限制來電 | 防火牆等存取控制 |

例如：

```text
伺服器 IP：192.0.2.10

              ┌──────────────────────┐
              │       伺服器         │
              │     192.0.2.10       │
              │                      │
              │  Port 22   → SSH     │
              │  Port 80   → HTTP    │
              │  Port 443  → HTTPS   │
              │  Port 3306 → MySQL   │
              │                      │
              └──────────────────────┘
```

上面是常見的服務與 Port 對應關係，不代表這台假設的伺服器真的有啟動所有服務。

你可以理解成：

- IP：我要找到哪一台電腦？
- Port：我要找這台電腦裡面的哪個服務？
- TCP／UDP：我要用哪一種通訊協定？

所以，當我們說：

`192.0.2.10:443`

通常表示我們正在討論這台伺服器的 443 Port，但完整描述還需要加上傳輸協定，例如 `192.0.2.10:443/TCP`。

### 1.2 為什麼 TCP 443 和 UDP 443 不一樣？

這是一個初學者很容易忽略的地方。

想像同一間辦公室有兩種聯絡方式：

- 第一種是一般電話。
- 第二種是無線電。

雖然聯絡的是同一間辦公室，但兩種通訊方式的運作機制不同。

TCP 與 UDP 也是這樣。

例如：

```text
192.0.2.10
    │
    ├── TCP 443
    │      └── 可能提供 HTTPS 網頁服務
    │
    └── UDP 443
           └── 可能提供 HTTP/3（QUIC）服務
```

兩者使用相同的數字 443，但因為傳輸協定不同，必須分別檢查。

因此：

**TCP 443 是 Open，不代表 UDP 443 也是 Open。**

反過來也一樣。

### 1.3 本節最重要的觀念

我們不是只在問：

「443 Port 有沒有開？」

更完整的問題應該是：

「我從哪個網路位置，使用哪種協定與掃描方法，檢查哪台伺服器的 443 Port，最後得到了什麼回應？」

這個問題會貫穿整個 M03-04。

# 2｜先把三個核心狀態分清楚

這是本單元最重要的一節。

我們分別理解 Open、Closed 與 Filtered。

## 2.1 Open：入口有人接聽

假設你打電話到公司：

你：「您好，請幫我轉接 101 分機。」

總機：「好的，101 分機可以接聽。」

這就很接近 Open 的意思。

在電腦世界，如果我們使用 TCP SYN 掃描，發現目標 Port 回覆了 `SYN/ACK`，Nmap 就能判定該 Port 為 Open。

例如：

```text
掃描端                         伺服器
   │                              │
   │──── SYN：有人嗎？ ──────────►│
   │                              │
   │◄─── SYN/ACK：可以連線 ───────│
   │                              │
   ▼
判斷：OPEN
```

這代表目標對該 TCP 連線請求作出了接受連線的回應。

但要注意：

**Open 不等於有漏洞，也不等於服務可以正常完成所有工作。**

例如，你的 HTTPS 服務可以接受 TCP 連線，但可能因為 TLS 憑證錯誤、應用程式故障或身分驗證失敗，導致使用者無法正常操作。

因此 Open 只回答了部分問題。

接下來才需要確認：

服務是什麼？版本是多少？有沒有正常運作？誰可以連線？是否存在弱點？

這些會逐漸連到 M03-05 的服務版本探測，以及 M05 的弱點分析。

## 2.2 Closed：有明確回應，但沒有服務接聽

再回到辦公大樓。

你：「您好，請幫我轉接 888 分機。」

總機：「這個分機目前沒有提供服務。」

這就接近 Closed 的概念。

使用 TCP SYN 掃描時，如果對方回覆 `RST`，Nmap 通常會把它分類為 Closed。

RST 是 Reset，意思是重設或拒絕繼續這次 TCP 連線嘗試。

```text
掃描端                         伺服器
   │                              │
   │──── SYN：有人嗎？ ──────────►│
   │                              │
   │◄─── RST：不接受連線 ─────────│
   │                              │
   ▼
判斷：CLOSED
```

這裡有個非常重要的細節：

**Closed 不等於網路完全不通。**

相反地，掃描端通常正是因為收到明確回應，才能判定 Closed。

例如，某台伺服器的 TCP 8443 顯示 Closed。

可能原因包括：

- Web 服務沒有啟動。
- 程式沒有監聽 8443。
- 程式只監聽其他網路介面。
- 防火牆或其他中間設備回覆了 TCP RST。

所以，看到 Closed，還要根據實際架構調查原因。

## 2.3 Filtered：可能有人接聽，但探測沒有得到足以確認的回應

現在假設你打電話給某間公司。

你：「您好，請幫我轉接資訊部門。」

但這次，總機依照公司規定，直接阻擋外部來電。

結果你完全不知道資訊部門究竟有沒有人上班。

這就是 Filtered 最值得理解的地方。

```text
掃描端             防火牆              伺服器
   │                  │                   │
   │── SYN ──────────►│                   │
   │                  │                   │
   │                DROP                  │
   │                  X                   │
   │                                      │
   │          等待後仍沒有回覆            │
   ▼                                      │
判斷：FILTERED
```

防火牆可能直接丟棄封包（Drop），也可能回傳特定 ICMP 錯誤訊息。

從掃描端的角度，我們沒有取得足以判定 Port 開放或關閉的證據。

因此 Nmap 將其分類為 Filtered。

不過，這裡要區分兩個層次：

**觀察到的現象：** 沒有收到預期回覆，或者收到特定網路錯誤。

**可能的原因：** 防火牆、路由器規則、主機防火牆、封包遺失或其他網路因素。

不能單憑 Filtered 就斷言一定存在某台防火牆。

## 2.4 三個狀態放在一起比較

| 狀態 | 白話文 | TCP SYN 常見回應 | 能否確定服務有接聽？ |
|---|---|---|---|
| Open | 有人接聽 | SYN/ACK | 可以確認該連線請求得到接受回應 |
| Closed | 明確回覆這次連線不受理 | RST | 工具判為關閉；仍須核對監聽與 RST 是否來自中間設備 |
| Filtered | 探測受到限制或無法確認 | 無回應、特定 ICMP | 無法確認 |

這三個狀態不是伺服器永遠不變的屬性，而是根據當次探測方法與觀察位置得到的分類。

Nmap 官方文件也特別說明：同一個 Port 從不同網路位置掃描，可能出現不同的狀態。[Nmap](https://nmap.org/book/man-port-scanning-basics.html)

**本節記憶法：**

Open：有接受回應。

Closed：有明確拒絕。

Filtered：目前證據無法確認入口是否開放。

# 3｜TCP SYN 掃描：用回應讀懂三種狀態

上一節我們知道了三種狀態。

這一節要往下深入一層：

**Nmap 怎麼從 TCP 封包判斷這些狀態？**

## 3.1 先複習 TCP 三向交握

TCP 在建立連線時，通常會經過三個步驟。

假設你的電腦要連線到一台 Web Server。

```text
你的電腦                              Web Server
   │                                      │
   │                                      │
   │──────────── SYN ────────────────────►│
   │         我想建立連線                │
   │                                      │
   │◄────────── SYN/ACK ─────────────────│
   │         好的，我收到請求            │
   │                                      │
   │──────────── ACK ────────────────────►│
   │         好，我確認收到              │
   │                                      │
   │          TCP 連線建立完成           │
   │                                      │
```

這就是 TCP Three-Way Handshake（三向交握）。

三個重要旗標：

| 旗標 | 英文 | 白話文 |
|---|---|---|
| SYN | Synchronize | 我想開始建立連線 |
| ACK | Acknowledgment | 我確認收到 |
| RST | Reset | 重設這次連線 |

這裡的「我想建立連線」是方便理解的比喻。實際上，SYN、ACK、RST 都是 TCP Header 中的控制旗標。

## 3.2 為什麼 SYN Scan 不需要完成三向交握？

還記得 M03-03 教過的兩種 TCP 掃描嗎？

TCP Connect Scan 通常由作業系統完成 TCP 連線建立程序。

TCP SYN Scan 則是只利用交握的前段回應，就判斷 Port 的狀態。

為什麼？

因為當伺服器回覆 SYN/ACK 時，我們其實就已經取得重要資訊：

**伺服器願意接受這個 TCP 連線請求。**

Nmap 不需要再完成第三步 ACK。

對於 Open 的 Port，SYN 掃描通常會透過 RST 結束尚未完成的連線嘗試。

因此 SYN Scan 也被稱為 Half-Open Scan（半開放式掃描）。

但不要誤會：Half-Open 不代表對方的 Port 是半開放，而是指掃描過程沒有完成一般的 TCP 三向交握。[Nmap](https://nmap.org/book/synscan.html)

## 3.3 SYN Scan 的三種結果

### 情況 A：收到 SYN/ACK

```text
你  ────── SYN ──────► 伺服器
你  ◄──── SYN/ACK ──── 伺服器

Nmap：OPEN
```

因為目標回覆了接受建立 TCP 連線的訊號。

### 情況 B：收到 RST

```text
你  ────── SYN ──────► 伺服器
你  ◄───── RST ─────── 伺服器

Nmap：CLOSED
```

代表這次探測收到重設連線的回應。

### 情況 C：沒有收到回應

```text
你  ────── SYN ──────► 防火牆
                            │
                          DROP
                            │
                            X

你等待……
重新探測……
仍然沒有回應……

Nmap：FILTERED
```

另外，若收到符合判定條件的 ICMP 無法到達錯誤，也可能分類為 Filtered。

這個地方連到了我們在 M03-02 學過的 ICMP。

ICMP 可以協助我們理解網路上的錯誤或限制，但不同的 ICMP Type 和 Code 代表不同意思，不能把所有 ICMP 回應都當成 Filtered。

## 3.4 SYN Scan 怎麼把封包變成結果？

你可以把 Nmap 想成一位觀察員。

它先發送探測，接著收集證據，最後根據判定規則分類。

```text
                   發送 TCP SYN
                         │
                         ▼
                   收到什麼？
                         │
             ┌───────────┼────────────┐
             │           │            │
             ▼           ▼            ▼
          SYN/ACK       RST      無回應或特定
                                     ICMP
             │           │            │
             ▼           ▼            ▼
            OPEN       CLOSED      FILTERED
```

這裡的核心是：

**封包回應是證據；Open、Closed、Filtered 是 Nmap 根據證據給出的分類。**

這兩件事要分開理解。

如果掃描工具顯示 `closed`，你不應該只記錄「關閉」，最好還要記錄「因收到 TCP RST 而分類為 closed」。

這就是從操作工具進入真正技術分析的第一步。

官方參考：[Nmap TCP SYN Scan 技術文件](https://nmap.org/book/synscan.html)。

# 4｜UDP 的沉默，要保留兩個可能方向

這一節非常重要，因為 **UDP 與 TCP 判讀掃描結果的方式不同**。

前面我們已經學過：

TCP 建立連線時，有三向交握。

但 UDP 沒有這個機制。

因此，當你使用 UDP 掃描時，不能直接沿用 TCP 的判斷方式。

## 4.1 為什麼 UDP 比 TCP 更難判斷？

想像你今天要聯絡一間公司。

TCP 就像打電話：

你撥電話，對方可能接聽，也可能明確拒絕。

UDP 則比較像寄送一張紙條：

你把紙條交給對方，但對方不一定會回覆。

更重要的是：

**對方沒有回覆，不代表對方沒有收到。**

例如：

你把一張紙條交給某個部門：

「請問你們有人在嗎？」

但這個部門有規定，只處理符合特定格式的申請文件。

因此，即使裡面有人，也可能直接忽略你的紙條。

在電腦世界中，UDP 服務也可能只處理符合協定格式的資料。

所以：

```text
                    UDP 掃描
                        │
                        ▼
                  發送 UDP 封包
                        │
                        ▼
                    沒有回應
                        │
             ┌──────────┴──────────┐
             │                     │
             ▼                     ▼
       情況 A：服務開放       情況 B：封包被過濾
             │                     │
       服務收到資料            防火牆直接丟棄
       但選擇不回覆                  │
             │                     │
             └──────────┬──────────┘
                        │
                        ▼
                  掃描結果相同
                     沒回應
                        │
                        ▼
                  OPEN|FILTERED
```

Nmap 沒有足夠證據區分這兩種情況，因此保留兩種可能性。

這就是 `open|filtered`。

中間的 `|` 可以理解成「或者」（OR）。

也就是：

「可能是 Open，也可能是 Filtered。」

它不是另一種特殊的半開放狀態。

## 4.2 UDP 掃描的四種結果

當我們使用 UDP Scan 時，Nmap 主要會根據以下四類觀察結果進行判斷。

| 觀察結果 | Nmap 狀態 | 白話文 |
|---|---|---|
| 收到目標 Port 的 UDP 回應 | Open | 對方有回覆 |
| 收到 ICMP Port Unreachable | Closed | 對方回報這個 Port 無法到達 |
| 收到特定其他 ICMP 不可達訊息 | Filtered | 網路回報了符合過濾判定的錯誤 |
| 多次探測後沒有回應 | Open\|Filtered | 可能開著但不回覆，也可能被阻擋 |

這是 Nmap UDP 掃描的基本判讀方式。[Nmap](https://nmap.org/book/scan-methods-udp-scan.html)

### 情況 A：收到 UDP 回應

```text
你的電腦                     DNS Server
   │                             │
   │────── DNS Query ───────────►│
   │                             │
   │◄───── DNS Response ─────────│
   │                             │
   ▼
OPEN
```

例如，你對自己的 DNS 伺服器送出正確格式的 DNS 查詢。

對方回覆查詢結果。

這時候，我們就有證據支持：

UDP 53 目前可以提供相應服務。

### 情況 B：收到 ICMP Port Unreachable

```text
你的電腦                       伺服器
   │                              │
   │────── UDP 探測 ─────────────►│
   │                              │
   │◄───── ICMP Port Unreachable ─│
   │                              │
   ▼
CLOSED
```

這裡要接回 M03-02 學過的 ICMP。

ICMP 不只是 Ping 使用的協定。

它也可以用來回報網路錯誤。

例如在 IPv4 中：

`ICMP Type 3 / Code 3`（此處是 IPv4，不能套用到 ICMPv6）

意思是：

Destination Unreachable — Port Unreachable。

白話文：

「目的地的這個 Port 無法到達。」

對於一般 UDP 掃描，Nmap 收到這種回應，通常會將該 Port 分類為 Closed。

### 情況 C：收到特定 ICMP 過濾訊息

假設你送出 UDP 封包。

中間的網路設備回報：

「根據管理政策，這項通訊不被允許。」

Nmap 便可能據此判斷為 Filtered。

不是所有 ICMP 都代表 Filtered，必須看 Type 和 Code。Nmap UDP 掃描在 IPv4 收到 Type 3、Code 1、2、9、10、13 時分類為 filtered；Type 3、Code 3 則是 closed。

### 情況 D：完全沒有回應

這就是最需要小心的情況。

如果沒有收到 UDP 回應，也沒有收到足以判定 Closed 或 Filtered 的 ICMP 訊息：

Nmap 通常只能判斷：

`open|filtered`

不能直接寫成：

「服務一定有開。」

更不能寫成：

「防火牆一定有擋住。」

## 4.3 實際案例：UDP 53 的 DNS 服務

假設你正在檢查一台實驗室 DNS Server。

Nmap 顯示：

```text
PORT     STATE          SERVICE
53/udp   open|filtered  domain
```

你應該怎麼理解？

第一，這裡的 `53/udp` 指的是 UDP Port 53。

第二，`open|filtered` 表示 Nmap 目前無法確認它是開放還是受到過濾。

第三，`domain` 是 Nmap 根據常見 Port 對應關係顯示的服務名稱，單靠這個欄位並不能證明該設備正在執行 DNS。

那麼，下一步怎麼做？

如果這台伺服器是你管理的設備，可以使用符合 DNS 協定格式的查詢進一步確認。

例如：

```bash
dig @192.0.2.53 example.com A
```

其中 `192.0.2.53` 是文件保留的示範 IP，實作時請換成自己管理或獲准測試的 DNS 伺服器。

如果確認使用 UDP 並收到有效的 DNS 回應，就有更強的證據支持 UDP 53 能回應查詢。dig 在某些情況（例如回應被截斷）會改用 TCP，因此也要核對實際傳輸協定，不能把 TCP 成功當成 UDP 證據。

也可以使用：

```text
sudo nmap -sU -sV -p 53 --reason <authorized-host>
```

上方是命令模板：先把 `<authorized-host>` 換成自己管理或獲准測試的主機，不要將角括號原樣貼到 shell。這會搭配服務版本探測，嘗試取得更多資訊，但不保證一定能判別所有 `open|filtered` 的情況。Nmap 官方文件也介紹了使用服務探測來進一步區分 UDP 狀態的方法。[Nmap](https://nmap.org/book/scan-methods-udp-scan.html)

**本節記憶重點：**

TCP SYN 掃描沒有回應，通常是 Filtered。

UDP 掃描沒有回應，通常是 Open|Filtered。

原因就在於 TCP 和 UDP 的通訊機制不同。

# 5｜另外兩個標籤：知道它在回答哪個問題

到目前為止，我們已經認識四種狀態：

Open、Closed、Filtered、Open|Filtered。

但 Nmap 實際上有六種 Port 狀態。

剩下兩種是：

- Unfiltered
- Closed|Filtered

這裡最重要的不是背英文，而是理解：

**不同掃描方法，想回答的問題不一定相同。**

## 5.1 Unfiltered：探測可達，但不知道有沒有服務

先想像一個問題。

你今天想知道某間公司是否有人在辦公室。

但你不是打電話詢問是否有人接聽，而是向警衛確認：

「我送過去的東西，會不會被門禁擋下？」

警衛回答：

「這類東西沒有被目前的規則擋住。」

這不代表辦公室裡面一定有人。

只是代表：

「你所測試的這種通訊，沒有呈現被過濾的結果。」

這就接近 Unfiltered 的意思。

### ACK Scan 是什麼？

在前一單元，我們學過 SYN Scan。

SYN Scan 使用 SYN 封包，觀察目標是否接受建立連線的請求。

ACK Scan 則是發送帶有 ACK 旗標的 TCP 封包，用來觀察防火牆或其他設備對這類封包的處理情況。

例如：

```text
掃描端                  防火牆／目標
   │                          │
   │────── TCP ACK ──────────►│
   │                          │
   │◄───── TCP RST ───────────│
   │                          │
   ▼
UNFILTERED
```

在一般 ACK Scan 中，收到 RST 可能表示該 ACK 探測並未被過濾。

但是，這不足以證明 Port 正在提供服務。

**Unfiltered 不等於 Open。**

這是 CEH 很值得理解的觀念。

因為 SYN Scan 和 ACK Scan 所檢查的問題不同：

| 掃描方法 | 主要想知道什麼？ |
|---|---|
| SYN Scan | 目標是否接受建立 TCP 連線？ |
| ACK Scan | 這類 ACK 探測是否受到過濾？ |

ACK Scan 的觀察可能幫助你理解網路過濾規則，但不能單靠 Unfiltered 判定服務開放。

要確認服務是否開放，仍需要在授權範圍內使用 SYN Scan、TCP Connect Scan，或其他適當方法。

這也是 Nmap 官方對 Unfiltered 的定義。[Nmap](https://nmap.org/book/man-port-scanning-basics.html)

## 5.2 Closed|Filtered：關閉或受到過濾

這個狀態比較少見。

通常出現在特定的 IP ID Idle Scan（閒置掃描）。

你可以先把它理解成：

「這次的掃描方式無法確定目標是 Closed 還是 Filtered。」

它的邏輯和 Open|Filtered 類似。

| 狀態 | 還無法區分哪兩種可能？ |
|---|---|
| Open\|Filtered | Open 或 Filtered |
| Closed\|Filtered | Closed 或 Filtered |

現在不需要急著深入 Idle Scan 的所有機制。

先把六種狀態完整建立起來比較重要。

## 5.3 六種 Port 狀態的完整地圖

| Nmap 狀態 | 白話文 | 最重要的判讀 |
|---|---|---|
| Open | 有服務接受相應通訊 | 入口可接受該探測所對應的通訊 |
| Closed | 入口可達，但沒有服務接聽 | 收到明確的關閉回應 |
| Filtered | 探測呈現過濾情況 | 無法確定服務是否開放 |
| Unfiltered | 探測可達 | 不能單靠此結果確認 Open 或 Closed |
| Open\|Filtered | 開放或受到過濾 | 兩種可能尚未區分 |
| Closed\|Filtered | 關閉或受到過濾 | 兩種可能尚未區分 |

這六種狀態是 Nmap 官方定義的分類。[Nmap](https://nmap.org/book/man-port-scanning-basics.html)

本節需要建立的觀念是：

**掃描結果必須搭配掃描方法解讀，不能只看狀態名稱。**

# 6｜讀一次完整的合成案例

接下來把前面所有知識整合起來。

我們設計一個實驗室網路情境。

## 6.1 假設你要驗收實驗室伺服器

你管理一台伺服器：

`192.0.2.10`

它預計提供三種服務：

| Port | 預期用途 |
|---|---|
| TCP 443 | 管理介面 |
| TCP 8443 | 備用管理服務，目前不應啟用 |
| UDP 53 | DNS 服務 |

實驗室有兩個網路區域：

**管理網段：** 只有經過授權的管理人員能使用。

**一般網段：** 一般測試用電腦所在的網路。

安全政策規定：

「TCP 443 管理介面只能從管理網段存取。」

現在你要驗收這個政策是否正確。

## 6.2 第一個結果：管理網段看到 Open

你從管理網段檢查 TCP 443。

```text
管理者電腦                 伺服器
     │                        │
     │──── SYN ──────────────►│
     │                        │
     │◄─── SYN/ACK ───────────│
     │                        │
     ▼
    OPEN
```

這個結果符合預期嗎？

如果政策允許管理網段連線，那麼結果就符合初步預期。

但還不能因此認定整個安全設定完全正確。

因為我們只證明：

管理網段的 SYN 得到 SYN/ACK，表示該入口接受起始連線請求；這段探測尚未證明三向交握已完成。

還需要確認身分驗證、應用程式權限、TLS 設定等控制措施。

## 6.3 第二個結果：一般網段看到 Filtered

接下來，從一般測試網段檢查相同的 TCP 443。

```text
一般網段電腦            防火牆           伺服器
     │                     │                │
     │──── SYN ───────────►│                │
     │                     │                │
     │                   DROP               │
     │                     X                │
     │                                      │
     ▼                                      │
  FILTERED                                  │
```

這個結果也可能符合預期。

因為安全政策本來就希望：

一般網段不能直接連線到管理介面。

注意這個現象：

**同一台伺服器、同一個 Port，卻可以同時得到 Open 與 Filtered 兩種結果。**

這不是矛盾。

因為觀察來源不同。

換句話說，Port 狀態不是一個脫離網路環境的固定標籤。

它是從特定觀察位置、使用特定方法，在特定時間得到的結果。

## 6.4 第三個結果：TCP 8443 顯示 Closed

假設你從管理網段探測 TCP 8443。

Nmap 顯示：

```text
8443/tcp closed
```

這代表什麼？

目前這次探測獲得了 Closed 的判定。

那這是好事還是壞事？

**答案取決於原本的設計。**

如果 TCP 8443 原本就不應該提供服務：

Closed 可能符合預期。

如果 TCP 8443 原本應該提供服務：

Closed 就代表需要調查。

例如：

- 服務是否啟動？
- 有沒有監聽 8443？
- 是否只綁定 `127.0.0.1`？
- 是否有設備主動回傳 RST？

這裡可以連結到 Linux 的實際操作。

使用：

```bash
sudo ss -lntp
```

可以查看目前系統有哪些 TCP Listening Socket（監聽中的通訊端）。沒有 sudo 權限時可先使用 `ss -lnt`，但程序資訊可能無法完整顯示。

例如：

```text
127.0.0.1:8443
```

表示程式監聽在本機 Loopback 位址。

一般情況下，其他電腦無法直接透過伺服器的外部 IP 連接這個 Listener。

而：

```text
0.0.0.0:8443
```

表示程式監聽所有 IPv4 本機介面。

但即使程式監聽所有介面，實際遠端存取仍可能受到防火牆或路由規則限制。

這也說明了：

**程式有沒有監聽 Port，與遠端能不能存取 Port，是兩個不同層次的問題。**

## 6.5 第四個結果：UDP 53 顯示 Open|Filtered

現在檢查 UDP 53。

結果：

```text
53/udp open|filtered
```

這代表：

Nmap 目前沒有足夠的回應證據，無法區分開放或受到過濾。

如果它原本應該提供 DNS 服務，就需要使用符合 DNS 格式的查詢進一步驗證。

同時檢查：

- DNS 服務是否啟動。
- 是否監聽 UDP 53。
- DNS 查詢是否有進入服務日誌。
- 防火牆是否阻擋了查詢或回應。

## 6.6 整個案例的結論

| 來源 | 目標 | 結果 | 管理者應採取的下一步 |
|---|---|---|---|
| 管理網段 | TCP 443 | Open | 確認符合允許政策，驗證應用層控制 |
| 一般網段 | TCP 443 | Filtered | 核對防火牆規則與日誌 |
| 管理網段 | TCP 8443 | Closed | 確認這是否符合服務部署計畫 |
| 管理網段 | UDP 53 | Open\|Filtered | 用有效 DNS 查詢取得更多證據 |

這個案例希望你學會的是：

**我們不是為了得到 Open、Closed 或 Filtered 而掃描，而是為了確認系統是否符合預期的安全設計。**

# 7｜把掃描報告寫成別人能重現的紀錄

這一節開始進入實際資安工作。

假設你今天受託進行滲透測試或資安驗收。

你完成 Nmap 掃描後，告訴管理員：

「443 是 Open。」

這樣的資訊其實不夠完整。

為什麼？

因為管理員可能想知道：

你從哪裡掃描？

什麼時間掃描？

使用 TCP 還是 UDP？

使用什麼掃描方式？

有沒有證據支持這個分類？

這些資訊會直接影響其他人能不能重現你的結果。

## 7.1 先把「事實」和「推論」分開

假設今天你使用 Nmap 檢查 TCP 443。

收到：

`SYN/ACK`

Nmap 顯示：

`open`

你應該把資訊拆成三個層次。

| 層次 | 內容 |
|---|---|
| 觀察事實 | 收到 TCP SYN/ACK |
| 工具分類 | Nmap 判定 Open |
| 後續推論 | 該入口接受 TCP 連線，需要進一步確認服務及安全設定 |

為什麼要拆開？

因為「收到 SYN/ACK」是網路回應證據。

「Open」是工具根據規則給出的狀態。

「服務是否安全」則是尚待其他證據回答的問題。

這三個層次不能混為一談。

## 7.2 在自己的 Ubuntu 上實際操作

如果你希望先熟悉 Nmap，可以從自己的電腦開始。

例如：

```bash
nmap --version
```

先確認 Nmap 是否已安裝。

接著執行：

```bash
nmap -sT -p 22,80,443 --reason 127.0.0.1
```

這個指令的意思是：

| 參數 | 作用 |
|---|---|
| `nmap` | 執行 Nmap |
| `-sT` | 使用 TCP Connect Scan |
| `-p 22,80,443` | 只檢查指定的三個 TCP Port |
| `--reason` | 顯示 Port 狀態的判定理由 |
| `127.0.0.1` | 檢查自己的電腦 |

`127.0.0.1` 是 Loopback Address（迴環位址）。

也就是讓你的電腦連回自己。

如果你的電腦沒有在 80 或 443 提供服務，這些 Port 就可能顯示 Closed。

實際結果取決於你目前的系統設定。

本機 Loopback 流量不會經過外部防火牆；主機自身的過濾規則仍可能影響結果。

### 想觀察 SYN Scan，可以使用：

```bash
sudo nmap -sS -p 22,80,443 --reason 127.0.0.1
```

`-sS` 表示 TCP SYN Scan。

它通常需要能夠發送 Raw Packet 的權限，因此在 Linux 上常透過 `sudo` 執行。

你可以比較：

`-sT` 與 `-sS`

在本機相同 Port 上得到的結果有何異同。

如果使用 Wireshark 或 tcpdump 觀察封包，還可以看到兩種掃描的交握行為差異。

這能把 M03-03 與 M03-04 真正連起來。

## 7.3 使用 --reason 的價值

假設某次掃描結果顯示：

```text
PORT      STATE    SERVICE  REASON
443/tcp   open     https    syn-ack
8443/tcp  closed   https-alt reset
```

以上是 TCP SYN 掃描的簡化示意輸出，並非實際執行結果。不同方法、平台與 Nmap 版本的理由字串可能不同；例如 Connect 掃描可能出現 conn-refused，應保存實際輸出。

它想表達的是：

Nmap 不只能告訴你狀態，還能說明分類依據。

例如：

`443/tcp open syn-ack`

你可以讀成：

「TCP 443 被判斷為 Open，因為掃描時收到 SYN/ACK 回應。」

這就比只記錄「443 Open」更有分析價值。

`--reason` 是 Nmap 官方支援的輸出選項。[Nmap](https://nmap.org/book/man-output.html)

## 7.4 如何撰寫一份合格的掃描紀錄？

建議至少保留五類資訊。

| 項目 | 應記錄內容 |
|---|---|
| 測試範圍 | 目標 IP、Port、協定、授權範圍 |
| 測試條件 | 時間、時區、來源網段、Nmap 版本、掃描參數 |
| 原始觀察 | 收到 SYN/ACK、RST、ICMP，或無回應 |
| 判讀結果 | Open、Closed、Filtered 等狀態及理由 |
| 後續處理 | 是否符合設計、需要哪些證據、誰負責查核 |

其中，時間最好包含時區。

例如：

`2026-11-03 10:30 UTC+08:00`

這樣管理者才能查找對應時間的防火牆日誌。

本節最重要的能力不是背指令，而是：

**讓另一位工程師能根據你的紀錄，理解你做了什麼、看到了什麼，以及為什麼得到這個結論。**

# 8｜防護怎麼做，驗收就怎麼看

這一節要把掃描技術與實際資安防護連起來。

我們先思考一個問題：

**如果 Nmap 掃描結果是 Open，代表安全還是不安全？**

答案是：無法單憑 Open 判定。

為什麼？

因為有些服務本來就應該對外開放。

例如公開網站的 HTTPS 服務。

但有些服務不應該直接暴露在不受信任的網路上。

例如內部資料庫管理介面。

所以，資安工作的目標不是讓所有 Port 都變成 Closed。

真正要做的是：

**讓服務的可存取範圍符合業務需求與安全政策。**

## 8.1 第一層：服務層

先問：

「這個 Port 為什麼需要開啟？」

假設你管理一台醫療 AI 推論伺服器。

它可能有：

- HTTPS API。
- SSH 管理服務。
- 資料庫。
- 監控服務。

但並不是每個服務都需要開放給所有使用者。

例如，資料庫可能只需要讓後端 API 存取。

SSH 可能只需要讓管理者透過特定管理網段連線。

因此第一層的工作是：

確認哪些服務確實需要存在，並關閉不必要的服務。

這也是 Attack Surface Reduction（攻擊面縮減）的基本做法。

## 8.2 第二層：存取控制層

接著問：

「誰可以使用這個 Port？」

例如：

| 服務 | 預期允許來源 |
|---|---|
| HTTPS 443 | 核准的網站使用者 |
| SSH 22 | 管理網段 |
| PostgreSQL 5432 | 指定應用程式主機 |
| Prometheus 9090 | 監控網段 |

這裡的「允許來源」仍須配合身分驗證、加密與應用程式權限，不能只依賴 Port 或來源 IP。

我們可以使用防火牆、安全群組、網路 ACL 等方式控制網路存取。

這裡也可以連到後面的 CEH M12：IDS、防火牆與蜜罐。

## 8.3 第三層：驗收層

最後問：

「我們設定的政策真的有生效嗎？」

假設安全政策是：

管理網段可以存取 SSH。

一般網段不可以存取 SSH。

那麼你應該分別從兩個網段測試。

```text
                  管理網段
                     │
                     │ 允許
                     ▼
               ┌────────────┐
               │            │
               │  SSH: 22   │
               │            │
               └────────────┘
                     ▲
                     X 阻擋
                     │
                  一般網段
```

如果管理網段測得 Open，而一般網段測得 Filtered，這可以作為政策初步生效的線索。

但完整驗收仍需要：

對照防火牆規則、設備紀錄，以及實際應用層連線結果。

因為 Filtered 也可能來自其他非預期的網路問題。

## 8.4 用三層架構理解資安驗收

```text
                 資安防護目標
                       │
                       ▼
              ① 服務是否必要？
                       │
                       ▼
                移除不必要服務
                       │
                       ▼
              ② 誰可以存取？
                       │
                       ▼
                 設定存取政策
                       │
                       ▼
              ③ 政策是否生效？
                       │
                       ▼

                       │

```

從「我會掃 Port」，進步到「我能驗證系統是否符合安全設計」。

這也是從 CEH 的網路掃描知識，延伸到實際資安工程的重要一步。

## 9.2 三個最常見的觀念錯誤

### 錯誤一：Filtered 代表一定有防火牆

不一定。

Filtered 是根據封包回應與掃描方法得到的分類。

防火牆是常見原因，但不是唯一可能。

如果網路封包遺失、設備離線，或路由存在問題，也可能影響結果。

因此應結合其他觀察與設備端證據確認。

### 錯誤二：Open 代表有安全漏洞

不一定。

公開網站的 HTTPS Port 本來就可能需要 Open。

Open 代表有可以接受相應通訊的入口。

是否存在弱點，還需要檢查服務版本、組態及程式行為。

### 錯誤三：Closed 代表封包被防火牆阻擋

不一定。

以一般 TCP SYN Scan 來說：

Closed 通常來自明確的 RST 回應。

相較之下，Filtered 才是工具根據無回應或特定錯誤訊息，判斷探測受到過濾的分類。

因此：

**Closed 與 Filtered 是兩種不同的觀察結果，不能直接畫上等號。**

# 10｜概念 Q&A：補充初學者最容易困惑的問題

以下五個概念問題補充本單元的判讀界線，請搭配前面的封包與案例閱讀。

### Q1：Port 顯示 Open，代表可以直接使用服務嗎？

不代表。

Open 通常表示該入口接受相應的網路通訊。

但你還可能遇到：

身分驗證失敗、應用程式錯誤、TLS 設定問題或權限限制。

例如：

TCP 443 Open，只代表你取得了 TCP 層的連線證據。

它不保證 HTTPS 一定能正常運作。

### Q2：為什麼同一個 Port，不同人掃描會得到不同結果？

因為來源網段、網路路徑、存取政策、時間以及掃描方法都可能不同。

例如：

```text
管理者 → SSH 22 → Open

一般使用者 → SSH 22 → Filtered
```

如果這符合原本設計，兩個結果都可能正確。

### Q3：UDP 沒有回應，為什麼不直接判斷 Closed？

因為 UDP 沒有 TCP 的連線建立機制。

而且某些 UDP 服務只會回覆符合特定格式的請求。

因此，沒有回應仍可能代表服務存在。

在一般 UDP 掃描中，Nmap 通常會保留 Open|Filtered 的可能性。

### Q4：Unfiltered 和 Open 最大差別是什麼？

Open 表示有相應的服務接受通訊。

Unfiltered 在 ACK Scan 的語境中，主要表示這類探測可獲得回應，沒有呈現被過濾的結果。

所以：

Unfiltered 不等於服務正在接受新連線。

### Q5：如果看到 Filtered，接下來應該怎麼調查？

應先確認這次結果是否符合預期存取政策。

接著可以在授權範圍內：

檢查來源位置、路由、防火牆規則、同時段日誌，以及目標設備的服務監聽設定。

必要時，再從不同的核准網段重新測試。

目標不是強行把 Filtered 變成 Open，而是釐清原因並確認安全設計是否生效。

## 理解測驗：四個情境題

請先試著回答，之後可以依據你的答案逐題檢查觀念。

**問題一：TCP SYN Scan**

你使用 Nmap 掃描某台伺服器的 TCP 443。

目標回覆了 RST。

請問：

A. Nmap 通常會分類成什麼狀態？

B. 可以據此認定這台伺服器已經關機嗎？

C. 如果你原本預期這個 Port 應該提供 HTTPS，接下來會檢查什麼？

**問題二：UDP Scan**

你對某台 DNS Server 的 UDP 53 進行掃描。

Nmap 顯示：

`open|filtered`

請問：

A. 這代表 DNS 一定有啟動嗎？

B. 這代表防火牆一定有擋住嗎？

C. 可以使用什麼方法取得更多證據？

**問題三：不同網段的掃描結果**

同一台伺服器的 SSH 22：

管理網段掃描結果為 Open。

一般網段掃描結果為 Filtered。

請問：

A. 這兩個結果互相矛盾嗎？

B. 如果安全政策要求只有管理網段能使用 SSH，這是否符合初步預期？

C. 還需要核對哪些證據才能完成驗收？

**問題四：ACK Scan**

某台伺服器在 ACK Scan 中顯示：

`unfiltered`

請問：

A. 能否直接判定這個 Port 是 Open？

B. ACK Scan 主要是在檢查什麼？

C. 如果你想確認該 Port 是否接受新的 TCP 連線，下一步應該使用什麼掃描方法？

這四題涵蓋了 M03-04 最重要的 TCP、UDP、Port 狀態、網路觀察位置與安全驗收觀念。
