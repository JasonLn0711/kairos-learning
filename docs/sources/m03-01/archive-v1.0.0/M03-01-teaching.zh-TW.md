# CEH M03-01｜IP、TCP、UDP、連接埠與服務：一個網路請求怎麼找到對方？

## 1｜先記住這個結論

**IP 位址協助把資料送往網路上的目的地；TCP 或 UDP 提供傳輸方式；連接埠協助把資料交給對應程式；服務則實際處理你的需求。**

想像你到一棟辦公大樓洽公。地址幫你找到大樓，櫃檯分機幫你找承辦窗口，窗口使用的辦事流程決定如何收件與回覆，真正提供服務的是裡面的工作人員。

對照到網路：IP 像地址；連接埠像窗口號碼；TCP、UDP 像兩種收送方式；網頁、郵件與名稱查詢程式是不同服務。比喻幫助理解分工，實際運作還要看通訊協定、程式設定與路徑。

本課回答一個主要問題：「我按下開啟網頁之後，資料如何找到正確的主機與程式？」讀完後，你可以看懂一筆來源、目的、協定與連接埠紀錄，這也是後續主機探索和掃描結果判讀的基礎。全部例子使用文件示例位址，紙上演練即可。

## 2｜IP：先找到網路上的位置

IP（Internet Protocol，網際網路協定）處理跨網路的定址與封包傳送。Packet（封包）可理解為有標頭與內容的一份傳輸資料；Header（標頭）攜帶處理它所需的資訊，Payload（負載）則是這一層承載的內容。

IP 標頭包含來源與目的位址。Router（路由器）依目的位址與路由表，決定封包的下一站。Routing（路由）就是選擇及使用這些轉送路徑。

IPv4 位址長 32 位元，常寫成 `192.0.2.10` 這種四段十進位數字；IPv6 位址長 128 位元，常寫成 `2001:db8::10` 這種冒號分隔的十六進位形式。IPv6 的定址與標頭由 RFC 8200 定義。[RFC 8200：IPv6](https://www.rfc-editor.org/rfc/rfc8200)

Subnet（子網路）將位址分成共同前綴的範圍。例如 `192.0.2.0/24` 的 `/24` 表示前 24 個位元是網路前綴。主機依位址設定及路由決定直接送到同一網段的鄰居，或交給 Gateway（閘道）往其他網路傳送。

一台設備可以有多個網路介面與位址；同一個公開位址也可能代表代理、負載平衡器或多個共用出口的裝置。分析時把「觀察到的位址」「觀察時間」「網路位置」記在一起，再結合資產清單理解是哪個服務入口。

DNS（Domain Name System，網域名稱系統）協助把名稱查成位址等紀錄。例如瀏覽器先取得 `shop.example` 的位址，再依連線需求使用。名稱解析與後續資料傳輸是兩個可以分別查核的步驟，這接回 M02-04 的網域足跡。

## 3｜TCP：有連線狀態的有序位元組串流

TCP（Transmission Control Protocol，傳輸控制協定）提供可靠、有序的位元組串流。Stream（串流）是連續的位元組序列；應用程式自行決定哪幾個位元組構成一則訊息。

一般建立 TCP 連線時，會看到 Three-way Handshake（三向交握）：

1. 用戶端送 SYN，提出建立連線並提供起始序號。
2. 伺服器回 SYN-ACK，提供自己的起始序號並確認對方。
3. 用戶端回 ACK，確認伺服器的序號，完成這個基本交握流程。

SYN 表示同步序號；ACK 表示確認。Sequence Number（序號）追蹤位元組的位置；Acknowledgment Number（確認號碼）表示接收端下一個期待的序號。收到序號 1201 開始、連續 128 個資料位元組時，下一個期待值是 1329；本例假設沒有缺口且只計資料。

TCP 透過確認、遺失資料重傳、流量控制及壅塞控制協調傳輸。應用程式收到連線或寫入成功的結果後，若要確認交易完成，仍由自己的請求／回應流程回報，例如訂單系統回傳訂單編號。TCP 的正式規格見 RFC 9293。[RFC 9293：TCP](https://www.rfc-editor.org/rfc/rfc9293.html)

可以把交握理解為雙方建立「這段資料往來的傳輸狀態」。網站登入則是應用程式確認帳號身分；兩個階段各有自己的目的。這也讓今天課堂提到的工作階段更容易理解：網路連線、登入驗證與應用程式登入狀態，可以分層觀察。

## 4｜UDP：以資料報為單位傳送

UDP（User Datagram Protocol，使用者資料報協定）以 Datagram（資料報，一則有邊界的訊息）為單位傳送。它的標頭包含來源埠、目的埠、長度與檢查碼。基本 UDP 傳輸直接交送資料報；需要確認、重試、排序或重複抑制時，由上層協定依用途設計。[RFC 768：UDP](https://www.rfc-editor.org/rfc/rfc768)

例如即時語音重視目前聲音的時間性：應用程式會依延遲、遺失率與播放時點決定如何處理。名稱查詢也常使用 UDP，由查詢端處理逾時與必要重試。DNS 同時支援 TCP，實際採用哪一種要看查詢情境及協定需求。[RFC 1035：DNS 傳輸](https://www.rfc-editor.org/rfc/rfc1035)

這裡用兩個問題比較：TCP 提供的基本介面是有序位元組串流；UDP 提供的基本介面是獨立資料報。最後呈現的可靠性、延遲與安全性，來自整套協定及實作。

現代網頁就是好例子：QUIC 是建立在 UDP 上的安全多路傳輸協定，提供串流與可靠傳輸等機制；HTTP/3 把網頁請求及回應放在 QUIC 上運作。因此觀察 UDP 流量時，也可能看到現代網頁服務。[RFC 9000：QUIC](https://www.rfc-editor.org/rfc/rfc9000)、[RFC 9114：HTTP/3](https://www.rfc-editor.org/rfc/rfc9114)

## 5｜Port：把資料交給對應的程式入口

Port（連接埠）是 TCP、UDP 等傳輸協定使用的數字欄位，協助作業系統區分程式的通訊端點。TCP 與 UDP 的埠號各自構成命名空間，所以 `TCP/53` 和 `UDP/53` 是兩個需要分別處理的端點。

埠號欄位有 16 位元，數字範圍是 0–65535。IANA（Internet Assigned Numbers Authority，網際網路號碼分配機構）登錄表將其分為：系統埠 0–1023、使用者埠 1024–49151、動態／私用埠 49152–65535；其中 0 為保留埠。[IANA 服務名稱與連接埠登錄表](https://www.iana.org/assignments/service-names-port-numbers/)

用戶端發出請求時，通常由作業系統選一個暫用的來源埠；伺服器在設定的目的埠提供服務。Ephemeral Port（暫用連接埠）的實際選取範圍依作業系統設定；IANA 的動態範圍是登錄分類，閱讀實際紀錄時以主機設定為準。

例如：`192.0.2.10:53000 → 198.51.100.20:443，TCP`。

這表示來源位址 192.0.2.10 的 53000 埠，正與目的位址 198.51.100.20 的 443 埠進行 TCP 通訊。回程資料則對應目的端的來源埠，讓作業系統找到發出請求的程式。

Five-tuple（五元組）通常是「來源 IP、來源埠、目的 IP、目的埠、傳輸協定」。它常用來描述一條網路流；記錄時加上時間與觀察位置，就更容易區分不同階段的往來。

## 6｜Service：真正處理請求的程式與規則

Service（服務）是提供某種功能的程式或程序，例如網頁、名稱解析、郵件或遠端管理。Listener（監聽端點）表示程式已在指定位置準備接收通訊。Socket（通訊端）是程式與網路互動的介面概念，常以位址、埠及協定描述其綁定或連線資訊。

同一台伺服器可以同時提供多個服務；一個服務也可以分散到多台機器。程式 Bind（綁定）到哪個位址，會影響它在哪些介面接收資料。例如只綁定 Loopback（回送）位址的開發服務，供本機程式使用；綁定對外介面時，再由主機及網路規則決定可達範圍。

常見對照可先記：SSH（Secure Shell，安全遠端管理）常用 TCP/22；DNS 常用 UDP/53 與 TCP/53；HTTP（Hypertext Transfer Protocol，超文字傳輸協定）常用 TCP/80；HTTPS（以安全通道承載 HTTP）常見 TCP/443，HTTP/3 則使用 QUIC，常見 UDP/443。

讀埠號時，可以先用登錄慣例形成服務假設，再以服務設定、實際協定回應與管理紀錄確認。某程式也能使用自訂埠，例如測試網頁用 8443。辨識服務時，描述「哪個協定、哪個埠、得到什麼回應」，資訊最完整。

公開網頁可能由 Reverse Proxy（反向代理）接收請求，再轉給內部程式；同一 IP 上也可能承載多個網站。網站名稱、TLS 設定與 HTTP 請求共同決定最終服務。這延伸了前面「位址、埠、服務」各自分工的概念。

第一步，瀏覽器依名稱解析結果取得 `shop.example` 的服務位址 198.51.100.20。實際系統也可能使用快取中的結果。

第二步，用戶端 192.0.2.10 選來源埠 53000，連到目的 TCP/443。中間路由器依路由轉送，防火牆按設定處理這條通訊。

第三步，TCP 完成基本交握。接著 TLS（Transport Layer Security，傳輸層安全性協定）建立安全通道，瀏覽器核對服務憑證與網站名稱等條件。

第四步，瀏覽器傳送 HTTP 請求，網頁服務處理並回應內容。若頁面需要登入，應用程式再處理帳號驗證與授權；若使用者送出訂單，服務再回覆該筆交易結果。

這個例子能分成四張查核卡：

- 位址卡：名稱解析到了哪個位址？觀察時間及來源是什麼？
- 傳輸卡：TCP 還是 UDP？來源及目的埠是什麼？
- 安全通道卡：TLS 的連線與憑證檢查結果如何？
- 應用卡：收到什麼 HTTP 回應、登入或交易結果？

用這種分層方式排查，可以清楚表達「名稱已解析，TCP 已建立，正在查 TLS 設定」或「網頁已回應，正在查應用程式權限」。每一步都有自己的觀察資料。

## 8｜如何轉成防護與可查核的紀錄？

管理服務時，先建立「業務用途 → 程式 → 綁定位址 → 協定／埠 → 允許來源 → 負責人」的對照。只開放業務需要的入口，管理用途安排核定的網路及身分條件；服務退役時一起關閉端點並更新清單。

Firewall（防火牆）依規則處理流量。L3（第三層）條件常包含 IP；L4（第四層）條件包含 TCP／UDP 與連接埠。實際規則依部署產品及架構設計；應用程式身分驗證與授權繼續在相應層次執行。

在已授權的環境，驗證時可比較三種證據：主機上的監聽設定、網路規則與日誌、正常使用者的服務回應。例子是「程式綁定內部位址的 TCP/8443；規則只允許管理網段；管理網段正常連線，其他測試來源按規則受限」。

若觀察位置跨越 NAT（Network Address Translation，網路位址轉換）或代理，保存位置與對應紀錄，因為不同位置看到的位址或埠可能不同。這接回 M02-06 的網路足跡，以及 M02-08 的來源、時間、觀察與推論分欄。

本課只練習讀資料。後續實作會在明確授權的隔離環境，逐步學習主機探索、掃描方法與服務辨識，並記下工具、參數、目標範圍與回應。
