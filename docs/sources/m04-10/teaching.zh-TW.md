# M04-10｜列舉防護：怎麼證明「該看的看得到，不該看的拿不到」？

前面幾課，我們練習從 DNS、SMB、SNMP、LDAP 等服務回應判讀資訊。這次把方向反過來，整合複習列舉防護：站在管理者的位置，決定服務應向誰提供哪些資訊，以及如何驗證設定真的生效。

本課的核心是：**先寫清楚允許的行為，再把防護措施和驗收證據一一對上。** 服務正常運作、資訊適當揭露、權限受到限制，三件事要一起確認。

## 一、列舉防護在保護什麼？

Enumeration 是「列舉」：透過服務回應整理帳號、共用名稱、設備、目錄物件或其他資源資訊。Countermeasures 是「防護措施」，用來降低不必要的資訊揭露與後續濫用風險。

很多查詢本來就是服務用途。例如 DNS 必須回答公開網站的名稱，監控系統需要取得設備狀態，員工也需要查詢工作所需的目錄。

因此，先問三件事：這份資訊是什麼？誰需要它？取得後可以做哪些操作？

例如公司允許員工知道有 Finance 共用資料夾，但只准財務人員讀取裡面的檔案。「名稱可見」是否需要改善，要看公司的揭露政策；「一般員工讀到財務內容」則是另一個需要獨立查證的問題。不能把兩者混成同一種風險。

防護目標可寫成：「一般員工可以讀公開公告；只有財務群組能讀財務檔；訪客不能連到檔案服務。」比起「不要被列舉」，這樣更容易設定與驗收。

## 二、先分清楚四個關卡

把服務想成大樓櫃檯，但每項規則都必須落實到系統：

1. **網路可達性：從這裡能不能聯絡服務？** 例如訪客網路是否能連到管理介面。
2. **身分驗證（Authentication）：服務把你辨識成誰？** 可能是已登入帳號，也可能是匿名身分。
3. **存取授權（Authorization）：這個身分能對哪個資源做什麼？** 查名稱、讀內容、修改設定，是不同操作。
4. **傳輸保護：這段通訊如何防止旁觀者讀取或竄改？** 例如加密與完整性保護。

能連線只是走到櫃檯；登入成功也不會自動拿到全部文件。加密像保護運送過程，但若櫃檯把不該交出的文件交給已登入的人，加密仍然無法修正錯誤的權限。

這些是不同的檢查面向，不是所有協定都必須依序完成的四步。公開 DNS 查詢就可能不要求使用者登入。

## 三、先減少不需要的入口，再限制來源

先盤點每個服務的用途、負責人、需要連線的設備與相依系統。不再使用的功能可以安排停用；仍有業務用途的功能則設定適當邊界。這是「最少功能」的思路：只保留完成任務需要的能力。[NIST SP 800-171 Rev. 3：最少功能，03.04.06](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/800-171r3/NIST.SP.800-171r3.html)

Network Segmentation 是「網路分段」，把訪客、一般工作與管理等用途分開，再管理彼此可以通過的連線。Firewall（防火牆）或網路 ACL（Access Control List，存取控制清單）可依部署限制來源、目的地、協定與連接埠。服務層的存取規則則進一步決定資料與操作權限；兩個層次要分開核對。

例如本課假想的公司，只讓指定監控主機接觸設備管理服務。驗收時要同時看「監控主機仍可取得必要資料」及「訪客來源受到限制」。只看到設定畫面有規則，還沒證明它套在正確介面、方向與實際路徑上。

企業 SMB 檔案服務也應依需要限制邊界流量，而不是讓不需要的網路任意連入。實際規則要配合現行架構與例外需求。[Microsoft：保護 SMB 流量](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-secure-traffic)

變更前先確認授權、相依服務、維護時段及還原方式。把所有埠或流量全部擋掉，雖然可能讓查詢失敗，也可能讓正常工作一起中斷。**查不到資料，並不自動代表防護做對了。**

維護也包含安排安全更新，確認修補是否實際套用，再檢查服務功能。隱藏版本字串或更換埠號可以減少部分線索，但不會修掉軟體缺陷，也不能取代權限控制。修補管理要包含識別、評估、安裝與驗證，而不只記錄「已下載更新」。[NIST SP 800-40 Rev. 4：修補管理](https://csrc.nist.gov/pubs/sp/800/40/r4/final)

## 四、用最小權限限制資料與操作

Least Privilege 是「最小權限」：只給完成工作所需的權限。它同時關係到誰可以用、可以看哪些資料，以及可以執行哪些操作。[NIST：最小權限定義](https://csrc.nist.gov/glossary/term/least_privilege)

例如監控帳號只需讀取設備名稱與介面狀態，就不應為了設定方便給它任意修改設備的權限。普通目錄查詢帳號只需要工作聯絡資訊，也不應因此讀到所有受限制欄位。

設定時要看有效權限，包括群組、繼承、資源規則與產品的判定方式。不能只看帳號名稱叫 reader，就相信它真的只能讀。[Microsoft：存取控制](https://learn.microsoft.com/en-us/windows/security/identity-protection/access-control/access-control)

匿名存取也要按資料用途處理。公開資訊可以有明確的匿名讀取政策；不需要匿名取得的內部資訊，則應限制。停用匿名查詢之後，仍要檢查一般登入帳號的權限。**「必須登入」和「登入後只拿到需要的資料」是兩個驗收項目。**

## 五、加密、簽章與權限各自解決什麼？

Encryption 是「加密」，主要保護內容的機密性；Integrity Protection 是「完整性保護」，用來偵測受保護內容被竄改。某些協定以簽章或訊息驗證碼提供完整性與來源認證，實際能力要依協定與設定確認。

以 SMB 為例，Signing（簽章）與 Encryption（加密）有不同用途。不能因為「已啟用簽章」就說內容已加密，也不能因為 SMB 傳輸已加密，就說磁碟中的檔案也受到相同保護。[Microsoft：SMB 安全功能](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-security)

LDAP 的 Simple Bind 若使用名稱與密碼，應有適當的機密性保護。若採 TLS（Transport Layer Security，傳輸層安全協定），還要確認實際建立的保護及伺服器身分驗證，不能只看設定頁寫了 TLS。[RFC 4513：LDAP 身分驗證與安全機制](https://www.rfc-editor.org/rfc/rfc4513.html#section-5.1.3)

把這些機制分開，才知道缺口在哪裡。未加密傳輸的問題，要查通訊保護；一般帳號能讀到敏感欄位的問題，要查存取規則。兩者可能同時存在，需要分別改善。

## 六、把防護對回前面學過的服務

### DNS：公開查詢與區域傳送分開管。

DNS（Domain Name System，網域名稱系統）的 AXFR 是整個 DNS 區域資料的傳送機制，常用於授權名稱伺服器之間同步。若政策只允許指定對象取得，就核對其授權設定；同時確認正常名稱查詢與必要同步仍可用。拒絕 AXFR 不會讓原本公開的個別名稱記錄自動變成秘密。[RFC 5936，第 5 節：AXFR 授權](https://www.rfc-editor.org/rfc/rfc5936.html#section-5)

### FTP／SMTP：檔案權限與帳號線索分開管。

FTP 是 File Transfer Protocol「檔案傳輸協定」。檢查哪些身分能登入、列出目錄、讀取與寫入，尤其要確認匿名帳號是否真的有業務需要。列目錄、下載和上傳是不同操作，應分別核對權限；目錄清單受到限制，仍不能代替檔案本身的存取控制。[RFC 959：FTP 操作](https://www.rfc-editor.org/rfc/rfc959.html#section-4.1.3)

SMTP 是 Simple Mail Transfer Protocol「簡易郵件傳輸協定」。VRFY／EXPN 等功能可能提供信箱或清單線索；可依產品與政策限制不必要的資訊揭露，但其他郵件流程仍可能透露線索。功能限制與正常郵件收送要一起驗證，不能把停用一個命令寫成「帳號資訊完全無法推知」。[RFC 5321，第 7.3 節](https://www.rfc-editor.org/rfc/rfc5321.html#section-7.3)

### SMB／NFS、NetBIOS／RPC：入口、名稱與實際資源權限分開管。

SMB 是 Server Message Block，常用於檔案共用；NFS 是 Network File System「網路檔案系統」。兩者都要確認核准來源、使用身分與實際檔案操作。隱藏共用名稱或減少清單曝光，可以降低線索，但不能代替檔案授權。NFS 的細節應按版本核對，例如 NFSv4.1 另有檔案存取控制屬性的規範。[RFC 8881，第 6 節：NFSv4.1 存取控制](https://www.rfc-editor.org/rfc/rfc8881.html#section-6)

NetBIOS 是傳統的網路基本輸入輸出介面相關機制；RPC 是 Remote Procedure Call「遠端程序呼叫」。判斷是否停用或限制時，要先查服務相依關係。取得名稱或端點清單，與獲准呼叫某項功能，仍是不同能力。本課不直接修改這些設定。[Microsoft：SMB 流量限制](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-secure-traffic)｜[存取權限](https://learn.microsoft.com/en-us/windows/security/identity-protection/access-control/access-control)

### SNMP：安全層級與可讀範圍一起管。

SNMP 是 Simple Network Management Protocol「簡易網路管理協定」。在常見 SNMPv3 USM（User-based Security Model，以使用者為基礎的安全模型）中，authPriv 提供訊息認證與內容加密；它不決定使用者能讀寫哪些管理物件。[RFC 3414：USM 安全服務](https://www.rfc-editor.org/rfc/rfc3414.html#section-1.3)

可讀與可寫範圍由存取控制另外決定，例如 VACM（View-based Access Control Model，以檢視範圍為基礎的存取控制模型）的 read view／write view。驗收要核對實際安全層級、必要物件可讀、受限制物件未揭露；不因為「已改 v3」就勾選全部完成。[RFC 3415，第 2.5 節](https://www.rfc-editor.org/rfc/rfc3415.html#section-2.5)

### LDAP／Active Directory：針對物件、欄位與身分確認。

LDAP 是 Lightweight Directory Access Protocol「輕量型目錄存取協定」；Active Directory 是 Microsoft 的目錄服務。檢查帳號可以搜尋哪個範圍、讀取哪些屬性，以及傳輸保護。不同實作的規則與預設值要分別核對。

例如 OpenLDAP 可以針對項目、屬性與要求者設定存取規則，規則順序也影響結果。因此「沒有特別加規則」不能直接當成「預設一定拒絕所有讀取」；更不能把 OpenLDAP 的預設值套到 Active Directory。[OpenLDAP 2.6：存取控制](https://www.openldap.org/doc/admin26/access-control.html)

### 其他服務：保留必要功能，限制多餘資訊。

以 NTP（Network Time Protocol，網路時間協定）為例，可以保留核准用戶端校時，同時限制外部的管理查詢。驗收要分別測量這兩件事。這是「服務功能」和「管理資訊」分開保護的具體例子。[RFC 8633，第 3.4 節](https://www.rfc-editor.org/rfc/rfc8633.html#section-3.4)

上一課的 VPN、語音、IPv6 與路由服務，也沿用同樣的問題：必要功能是什麼、准許誰使用、資訊向誰揭露、怎麼驗證。不要把某項查詢沒有回應，寫成整個服務都已安全。

## 七、日誌與告警：要能看見，也要有人處理

Log 是「日誌」，記錄事件；Alert 是「告警」，把符合條件的事件提出來讓人注意。兩者都不等同於自動阻擋。

針對實際風險，選擇需要保留的事件與欄位，例如時間、來源、使用身分、目標、操作及結果，再確認收集、保存和查閱方式。[NIST SP 800-171 Rev. 3：稽核紀錄，03.03.02–03.03.03](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/800-171r3/NIST.SP.800-171r3.html)

例如短時間查詢許多不同帳號，可能值得查看，也可能是正常同步程式。要和核准用途、平常的活動量及來源一起判讀；警示是調查線索，不是已證明入侵。

驗收監控時，可以事先約定一個低風險測試事件，核對它是否出現在預期位置、告警是否送達負責人。若沒有紀錄，要查事件是否真的發生、產品是否記錄此類操作，以及收集與篩選是否正常。**日誌空白本身，還不能證明沒有人查詢。**

紀錄只保存必要資料。密碼、金鑰及不需要的個人資訊，不應為了「證據完整」而寫進報告。

## 八、驗收方法：同時檢查允許、拒絕與正常功能

本課採用一個簡單的驗收寫法：

- **政策預期：**誰從哪裡，應能對什麼資源做什麼？
- **實際觀察：**在相同條件下，收到什麼回應？
- **交叉證據：**有效設定、服務紀錄或其他核准觀察是否支持原因？
- **結論與缺口：**哪項符合、哪項不符、哪項還沒測？

「允許案例」確認工作所需的功能仍能使用；「拒絕案例」確認不該取得的資訊或操作受到限制。兩者都需要，不要只選容易成功的一側。

如果工具只回報 timeout（逾時），先記「未收到回應」。它可能和網路、服務、設定或測試條件有關。若要說「已被指定防火牆規則阻擋」，還需要對應的規則與流量證據。

測試權限也要分清楚：獲准讀取不包含試寫、重設帳號或停用服務。寫入防護可以先列為設定核對項目；是否進行實際寫入測試，要由明確授權的範圍決定。

## 九、一份完整的合成案例

以下是紙上推演，沒有對任何主機連線，也沒有修改設定。

假設實驗室要改善一台目錄伺服器。管理者訂出三項政策：

1. 訪客網路不能連入這台目錄服務。
2. 工作網路的 lookup-demo 帳號，可以讀測試人員的姓名與工作信箱。
3. lookup-demo 不能讀取限制欄位 privateNote；通訊須使用核准的 TLS 保護。

管理者提供以下合成證據：

- 訪客測試連線沒有成功；同一時間的防火牆紀錄顯示對應流量命中拒絕規則。
- 工作網路的 lookup-demo 已建立核對過伺服器身分的 TLS 連線，成功讀到指定姓名及工作信箱。
- 同一帳號、同一連線，也讀到了 privateNote＝training-only。
- 稽核紀錄可查到這次測試查詢。

判讀時逐項對政策：訪客網路限制在本次測試條件下符合預期；必要的目錄查詢和這段 TLS 連線已有證據；限制欄位卻被不應取得的帳號讀到，顯示該案例的資料權限不符政策。日誌有記下來，對追查有幫助，但沒有修正已發生的超額讀取。

下一步由管理者檢查該欄位的有效存取規則、群組與繼承，按核准變更流程修正，再用同一組允許與拒絕案例重測。若只把 privateNote 從畫面藏起來，卻沒有驗證服務端的讀取權限，還不足以關閉這項缺口。

適合的報告是：「指定來源限制、正常欄位查詢及 TLS 測試符合預期；lookup-demo 仍可讀取政策禁止的 privateNote，權限修正與重測待完成。」這比「已啟用 TLS，全部安全」更能指引下一步。

## 十、這次只做一個小檢核

另一個合成案例中，管理者只提供兩項結果：訪客查詢得到逾時，核准監控主機卻也無法讀取原本應可讀的設備狀態。沒有防火牆或服務紀錄。

同事說：「大家都查不到，代表列舉防護已經成功，可以結案。」

**你會怎麼修正這個結論，並指出下一步最需要補哪類證據？**

練習環境是紙上推演，不需要安裝工具或操作真實設備。步驟一：圈出政策預期。步驟二：分開寫實際觀察與可能原因。步驟三：回答上面這一題，指出下一步需要補的證據。預期產物是一段有證據界線的判讀；沒有改動環境，因此沒有環境清理操作。
