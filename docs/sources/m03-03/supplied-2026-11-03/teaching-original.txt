# 2｜先分清楚：連線、服務與掃描結果

## 2.1 先從一個生活場景開始

假設你要拜訪一棟辦公大樓。

你知道大樓地址，也知道裡面有不同的服務窗口：

- 80 號窗口：提供一般網站服務。
- 443 號窗口：通常用來提供 HTTPS 網站服務。
- 22 號窗口：通常提供 SSH 遠端登入服務。
- 53 號窗口：常見於 DNS 網域名稱查詢服務。

這些數字可以幫助我們理解 **Port（連接埠）**。

不過，請先記住：

**Port 是通訊入口的編號，不是服務本身。**

例如：

```text
IP：192.0.2.20
│
├── TCP 22   → 可能是 SSH
│
├── TCP 80   → 可能是 HTTP
│
├── TCP 443  → 可能是 HTTPS
│
└── UDP 53   → 可能是 DNS
```

其中 `192.0.2.20` 是保留給文件與教學的範例位址。

需要特別注意：

第一，這些 Port 只是常見慣例。TCP 443 不一定提供 HTTPS，服務也能使用其他 Port。

第二，TCP 53 與 UDP 53 是**兩個不同的通訊入口**。即使數字相同，也不能視為同一個連接埠。

## 2.2 什麼是連線（Connection）？

假設你走到大樓的 443 號窗口，對方接受了你的報到。

這代表：

「你與這個窗口之間，已經建立了基本的通訊關係。」

在 TCP 網路中，就是成功建立 TCP Connection。

但要注意：

**TCP 連線成功，不代表後面的網站一定可以正常使用。**

例如：

```text
你的電腦
   │
   │ ① TCP 連線
   ▼
TCP 443
   │
   │ ② TLS 加密協商
   ▼
HTTPS
   │
   │ ③ HTTP 請求
   ▼
網站應用程式
   │
   │ ④ 應用程式處理
   ▼
資料庫或其他後端服務
```

可能出現什麼狀況？

- TCP 連線成功，但 TLS 協商失敗。
- TLS 協商成功，但 HTTP 回傳 `500 Internal Server Error`。
- 網站可以開啟，但登入功能故障。
- 網站功能正常，但某個使用者沒有操作權限。

所以，**連線成功，只證明某個通訊階段成功，不代表整個服務正常。**

這也是為什麼資安檢測不能只看 Port 是否開放。

## 2.3 什麼是服務（Service）？

服務是實際負責處理通訊的軟體。

例如你在 Ubuntu 上啟動 Nginx：

```text
Ubuntu Linux
    │
    └── Nginx（服務程式）
           │
           └── 監聽 TCP 443
                   │
                   └── 等待用戶端連線
```

這裡有兩個概念：

**Listener（監聽端點）**

代表作業系統中的程式，已經準備在特定的 IP、協定及 Port 上接受通訊。

**Service（服務）**

代表後面真正處理請求的程式或系統。

例如 Nginx、OpenSSH、PostgreSQL 等。

監聽端點與服務通常有關聯，但不是完全相同的概念。也可能由反向代理、負載平衡器或防火牆代理接收連線，再轉交後端。

因此，掃描看到 TCP 443 開放，還不能直接確定是 Nginx，也不能確定後端網站的健康狀態。

## 2.4 什麼是掃描結果（Scan Result）？

假設你使用 Nmap：

```bash
nmap -sT -p 443 127.0.0.1
```

其中：

- `nmap`：網路掃描工具。
- `-sT`：使用 TCP Connect 掃描。
- `-p 443`：指定連接埠 443。
- `127.0.0.1`：自己的電腦（Loopback）。

假設輸出顯示：

```text
PORT      STATE    SERVICE
443/tcp   open     https
```

要如何理解？

| 欄位 | 白話解釋 |
|---|---|
| `443/tcp` | 這次檢查的是 TCP 443 |
| `open` | Nmap 根據探測結果，判斷這個入口開放 |
| `https` | Nmap 根據連接埠名稱資料庫顯示的常見服務名稱 |

**特別注意：`SERVICE` 顯示 `https`，不代表 Nmap 已經確認該處真的在提供 HTTPS。**

只有進一步做服務辨識，例如使用 Nmap 的 `-sV`，才是在嘗試確認實際服務。即使如此，結果仍可能需要人工驗證。

### 三個層次一定要分開

| 層次 | 要回答的問題 | 可以取得的證據 |
|---|---|---|
| ① 原始觀察 | 我送出什麼？收到什麼？ | SYN、SYN/ACK、RST、ICMP 等封包 |
| ② 掃描判讀 | 工具認為這個 Port 是什麼狀態？ | open、closed、filtered |
| ③ 服務查核 | 裡面到底提供什麼服務？是否正常？ | TLS、HTTP、服務指紋、應用程式回應 |

以 CEH 的角度來說：

掃描結果是根據觀察所做的判斷，不是對整個系統狀態的完整證明。

這個觀念會貫穿後面的 TCP Connect、SYN 與 UDP 掃描。

# 3｜TCP Connect：請作業系統完成連線

## 3.1 TCP Connect 就像真的走進辦公室報到

假設你要確認某棟大樓的 443 號窗口是否有人服務。

你走到窗口：

你：「你好，我想進來。」

窗口：「可以，我接受你的報到。」

你：「收到，那我們開始。」

這三句話，就很接近 TCP 的三向交握（Three-way Handshake）。

TCP Connect Scan 的特色是：

**真的把 TCP 連線建立起來，再依據連線成功或失敗，判斷這個 Port 的狀態。**

## 3.2 三向交握到底在做什麼？

首先認識三個 TCP 控制旗標（TCP Flags）。

| 旗標 | 英文 | 白話意思 |
|---|---|---|
| SYN | Synchronize | 我想建立連線，並同步初始序號 |
| ACK | Acknowledgment | 我確認收到你的訊息 |
| RST | Reset | 重設這個連線或連線嘗試 |

假設你的電腦是 A，伺服器是 B。

**第一步：A 傳送 SYN**

```text
電腦 A                          伺服器 B
   │                               │
   │ ─────── SYN ────────────────> │
   │                               │
   │     我想建立 TCP 連線          │
```

SYN 就是在提出建立連線的請求。

而且，TCP 不只是在打招呼，雙方還需要建立序號等通訊狀態。

**第二步：B 回傳 SYN + ACK**

```text
電腦 A                          伺服器 B
   │                               │
   │ <───── SYN + ACK ──────────── │
   │                               │
   │     我收到你的請求了，          │
   │     我也願意建立連線。          │
```

這裡同時做了兩件事：

- ACK：確認對方的 SYN。
- SYN：提供自己建立連線所需的同步資訊。

**第三步：A 回傳 ACK**

```text
電腦 A                          伺服器 B
   │                               │
   │ ─────── ACK ────────────────> │
   │                               │
   │      我也收到你的確認了         │
   │                               │
   ▼                               ▼
            TCP 連線建立
```

三向交握完成後，雙方就能透過這條 TCP 連線傳送資料。

這時的狀態通常稱為 `ESTABLISHED`。

有了 TCP 連線，應用程式才可能接著交換資料。

例如 HTTPS 網站會繼續進行 TLS 協商。

## 3.3 TCP Connect Scan 實際上怎麼做？

假設我們想測試：

```text
目標 IP：192.0.2.20
協定：TCP
Port：443
```

Nmap 使用：

```bash
nmap -sT -p 443 192.0.2.20
```

這裡的 `-sT` 就代表 TCP Connect Scan。

但有個重要問題：

**Nmap 自己需要手動處理三向交握嗎？**

通常不用。

它可以呼叫作業系統提供的 `connect()`，由作業系統的 TCP/IP 網路堆疊處理連線建立。

你可以想像：

```text
Nmap
 │
 │ 我要連線到 192.0.2.20:443
 ▼
作業系統（Linux）
 │
 │ 負責 TCP 交握
 ▼
網路
 │
 ▼
192.0.2.20:443
```

作業系統再把結果告訴 Nmap。

例如：

**情境 A：連線成功**

```text
connect() → 成功

Nmap → open
```

代表從目前測試位置，可以建立 TCP 連線。

**情境 B：目標明確拒絕連線**

```text
connect() → Connection refused

Nmap → closed
```

典型的底層封包特徵是目標回傳 TCP RST。

這通常代表測試的入口沒有接受這條連線。

**情境 C：一直沒有成功建立連線**

```text
connect() → 等待、重試或相關錯誤

Nmap → 可能判讀 filtered
```

例如防火牆丟棄封包，可能造成這類結果。

但要注意：不是所有連線錯誤都等於 `filtered`。Nmap 還要根據具體錯誤與探測結果判斷。

## 3.4 TCP Connect 的優點與限制

最大的優點是：

**它直接利用一般應用程式建立 TCP 連線的方式進行測試。**

例如瀏覽器、SSH Client 等程式，本來就會透過作業系統提供的通訊介面建立連線。

因此，TCP Connect Scan 通常不需要直接收送原始封包的特殊權限。

但也有代價。

因為真的完成了 TCP 連線：

- 伺服器可能產生連線紀錄。
- 應用程式可能感知到有人建立連線又立即斷開。
- 大量連線可能增加系統負擔。
- 它仍然不能證明應用程式功能正常。

Nmap 官方也指出，Connect Scan 相較 SYN Scan，通常會對開放的連接埠完成更多連線處理，而且比較可能產生服務端紀錄。[Nmap](https://nmap.org/book/scan-methods-connect-scan.html?utm_source=chatgpt.com)

### 本節最重要的一句話

**TCP Connect Scan 是請作業系統真正建立連線，再根據成功或失敗來觀察 Port。**

# 4｜SYN 掃描：從交握起始判讀

這一節有趣的地方在於：

**如果我們只是想知道一個 Port 是否願意接受 TCP 連線，有沒有必要真的完成三向交握？**

答案是：不一定。

這就是 SYN Scan 的核心想法。

## 4.1 SYN Scan 就像只問窗口願不願意受理

還是使用辦公大樓的例子。

你走到窗口：

你：「你好，我想進來。」

窗口：「可以，請進。」

你：「謝謝，我只是確認這個窗口有受理服務。」

接著就結束這次詢問。

你沒有真的走完整個報到流程。

對應到 TCP：

```text
電腦 A                          伺服器 B
   │                               │
   │ ───────── SYN ──────────────> │
   │                               │
   │ <────── SYN + ACK ──────────  │
   │                               │
   │ ───────── RST ──────────────> │
   │                               │
   X                               X
       不完成一般 TCP 三向交握
```

為什麼這樣就能掃描？

因為當目標回覆 SYN + ACK 時，就已經提供了重要訊息：

「這個 TCP 入口願意接受建立連線的請求。」

因此，工具可以根據 SYN + ACK 判斷它為 `open`。

此時不必再完成最後的 ACK。

RST 則用來重設這次連線嘗試，避免目標持續等待。

這種方法稱為：

**TCP SYN Scan，也常稱為 Half-open Scan（半開式掃描）。**

它的「半開式」是指沒有完成正常 TCP 三向交握，不是在說 Port 只有開啟一半。

## 4.2 SYN Scan 如何判斷 Port 狀態？

我們把情況拆成三種。

### 情況一：收到 SYN + ACK

```text
Scanner                         Target
   │                               │
   │ ───────── SYN ──────────────> │
   │                               │
   │ <────── SYN + ACK ──────────  │
   │                               │
   ▼                               ▼
             判讀：open
```

白話文：

「我問你願不願意建立連線，你回答願意。」

所以判斷 `open`。

掃描端接著通常會以 RST 結束這次嘗試。

### 情況二：收到 RST

```text
Scanner                         Target
   │                               │
   │ ───────── SYN ──────────────> │
   │                               │
   │ <──────── RST ──────────────  │
   │                               │
   ▼                               ▼
            判讀：closed
```

白話文：

「我想建立連線，但對方直接拒絕。」

典型的 SYN Scan 會判斷為 `closed`。

這裡要特別區分兩種 RST：

| RST 的方向 | 意義 |
|---|---|
| **目標 → 掃描端** | 目標拒絕連線，典型判讀為 closed |
| **掃描端 → 目標** | 掃描端收到 SYN + ACK 後，主動結束連線嘗試 |

兩者都是 RST，但在封包流程中扮演完全不同的角色。

**讀封包時，不只看封包類型，還要看是誰傳給誰。**

這是使用 Wireshark 分析 TCP 流量時非常重要的能力。

### 情況三：沒有收到回覆

```text
Scanner                         Target
   │                               │
   │ ───────── SYN ──────────────> │
   │                               │
   │         沒有收到回覆           │
   │                               │
   │ ─────── 重試 SYN ───────────> │
   │                               │
   │         仍沒有回覆             │
   │                               │
   ▼                               ▼
          可能判讀：filtered
```

為什麼會這樣？

可能是：

1. 防火牆把 SYN 丟掉。
2. 防火牆阻擋回傳流量。
3. 網路封包遺失。
4. 目標或中間設備發生異常。

所以 SYN Scan 的 `filtered` 不等於已經證實有防火牆。

它代表的是：**根據目前的探測證據，無法確定這個 TCP 入口是否開放。**

另外，收到特定 ICMP 無法到達訊息，也可能被 Nmap 判讀為 `filtered`。[Nmap](https://nmap.org/book/synscan.html?utm_source=chatgpt.com)

## 4.3 SYN Scan 為什麼需要比較高的系統權限？

這是 TCP Connect 和 SYN Scan 的重要差別。

TCP Connect：

```text
Nmap
  │
  └── 請作業系統 connect()
             │
             └── 作業系統處理 TCP 交握
```

SYN Scan：

```text
Nmap
  │
  └── 直接建立與收送探測封包
             │
             └── 自行分析 SYN、RST 等回應
```

這裡的「直接」是概念上的簡化，實際上仍會透過作業系統提供的封包介面與網路驅動。

Nmap 進行 SYN Scan 通常需要原始封包（Raw Packet）操作權限。

例如 Linux 上常見：

```bash
sudo nmap -sS -p 443 192.0.2.20
```

但並不是 SYN Scan 必然需要完整的 root 權限；實際取決於作業系統、Capabilities 與執行環境。

## 4.4 SYN Scan 真的是隱蔽掃描嗎？

你可能在 CEH 教材中看到：

**SYN Scan = Stealth Scan**

Stealth 的意思是隱蔽。

早期之所以這樣稱呼，是因為 SYN 掃描沒有完成一般 TCP 連線，因此某些只記錄完整連線的應用程式，可能不會留下相同的日誌。

但這不代表它不會被發現。

例如：

```text
掃描者
   │
   │ SYN
   ▼
防火牆 / IDS / IPS
   │
   │ 觀察：
   │
   ├── 同一來源連續嘗試多個 Port
   ├── 大量 SYN 封包
   ├── 短時間出現異常連線模式
   └── 多次建立與重設嘗試
```

IDS（入侵偵測系統）可能從流量本身識別掃描行為。

IPS（入侵防禦系統）也可能依據政策採取阻擋動作。

因此：

**SYN Scan 不等於無法被偵測，只是它沒有完成一般 TCP 連線。**

### TCP Connect 與 SYN Scan 比較

| 比較項目 | TCP Connect | SYN Scan |
|---|---|---|
| Nmap 選項 | `-sT` | `-sS` |
| 是否完成正常三向交握 | 是 | 否 |
| 典型 open 證據 | 作業系統連線成功 | 收到 SYN + ACK |
| 典型 closed 證據 | 連線被明確拒絕 | 目標回傳 RST |
| 特殊封包權限 | 通常不需要 | 通常需要 |
| 是否可能被 IDS 偵測 | 是 | 是 |
| 能否確認網站正常運作 | 不能 | 不能 |

從兩種掃描的差異，我們也能理解一個網路安全上的重要觀念：

**網路協定可以利用不同階段的回應，取得不同程度的資訊。**

# 5｜UDP 掃描：以資料報與錯誤回報判讀

## 5.1 UDP 沒有三向交握，怎麼知道 Port 是否開放？

前面學到，TCP 的特色是：

建立連線之前，雙方會先進行三向交握。

但 UDP 完全不同。

**UDP 沒有建立連線的三向交握。它直接把資料報送出去，不要求對方先確認願意建立連線。**

我們用生活中的例子比較。

### TCP 像打電話

你打電話給朋友。

```text
你：喂，你在嗎？
朋友：我在。
你：好，那我們開始說話。

接著開始溝通。
```

這就像 TCP 需要先建立連線。

### UDP 像寄信

假設你要寄一封信。

```text
你
 │
 │ 寄送信件
 ▼
郵局
 │
 │ 負責運送
 ▼
收件人
```

你不一定會先跟收件人確認：

「你現在願意收信嗎？」

你就是把信送出去。

但問題來了：

**你寄出一封信，卻沒有收到回信，代表什麼？**

可能有很多原因：

1. 對方收到信，但不需要回覆。
2. 對方收到信，但看不懂內容。
3. 對方根本沒有收到信。
4. 信件被中途攔截。
5. 對方已經回信，但回信途中遺失。

UDP 掃描最大的困難，就是這種不確定性。

## 5.2 UDP 掃描究竟送出什麼？

以 DNS 為例。

假設我們要檢查：

```text
192.0.2.20:53/udp
```

我們知道 DNS 通常使用 Port 53。

UDP Scan 可以向這個連接埠送出 UDP 資料報（Datagram）。

但這裡有一個重要問題：

**這封 UDP 資料報裡面放了什麼內容？**

假設 DNS Server 正常運作。

情境 A：

```text
掃描端
  │
  │ UDP 53
  │
  │ 內容：格式正確的 DNS 查詢
  ▼
DNS Server
  │
  │ DNS 回覆
  ▼
掃描端
```

因為 DNS Server 認得這個查詢，所以可能正常回覆。

但是情境 B：

```text
掃描端
  │
  │ UDP 53
  │
  │ 內容：空白或無效資料
  ▼
DNS Server
  │
  │ 不回覆
  X
```

即使 DNS Server 正在正常運作，也可能沒有提供回覆。

因此，UDP 掃描除了要知道 Port，還必須理解：

**Payload（酬載）會影響探測結果。**

Payload 就是資料報裡面實際攜帶的內容。

不同的 UDP 服務，例如 DNS、NTP、SNMP，對資料內容有不同的要求。

Nmap 對部分常見 UDP Port 會使用協定專屬的探測內容，以提高取得有效回覆的機會；但並不是每個 Port 都會收到有效的應用層請求。[Nmap](https://nmap.org/book/scan-methods-udp-scan.html?utm_source=chatgpt.com)

## 5.3 UDP 掃描有哪四種結果？

接下來是這一節最重要的內容。

假設掃描端送出：

```text
Scanner → Target:9999/udp
```

我們要觀察對方的回應。

### 情況一：收到 UDP 回覆 → open

```text
Scanner                         Target
   │                               │
   │ ─────── UDP 資料報 ─────────> │
   │                               │
   │ <────── UDP 回覆 ───────────  │
   │                               │
   ▼                               ▼
              open
```

這種情況比較容易判斷。

因為掃描端收到與探測對應的 UDP 回覆，代表確實有端點對這次 UDP 通訊做出回應。

所以 Nmap 可以判斷為：

`open`

但是，這不代表應用程式所有功能都正常。

### 情況二：收到 ICMP Port Unreachable → closed

這時就要呼應上一課 M03-02 的 ICMP。

還記得我們學到：

**ICMP 是 IP 網路用來傳達錯誤與狀態的控制訊息。**

例如：

- Echo Reply：回應 Echo Request。
- Destination Unreachable：目的地無法到達。
- Time Exceeded：封包傳輸時間或跳數限制耗盡。

現在假設：

```text
Scanner                         Target
   │                               │
   │ ─────── UDP 資料報 ─────────> │
   │                               │
   │ <───── ICMP 錯誤 ───────────  │
   │                               │
   │       Port Unreachable        │
   ▼                               ▼
             closed
```

為什麼 UDP Scan 會收到 ICMP？

因為 UDP 本身沒有 TCP RST 這種連線重設機制。

當 IPv4 主機收到送往某個 UDP Port 的資料報，而沒有相應的接收端點時，典型情況下可能發出 ICMP 錯誤。

其中：

```text
ICMP Type 3
ICMP Code 3
```

代表：

```text
Type 3：Destination Unreachable
        目的地無法到達

Code 3：Port Unreachable
        連接埠無法到達
```

因此：

**收到符合探測的 IPv4 ICMP Type 3 / Code 3，Nmap 通常會將該 UDP Port 判讀為 closed。**

但這裡講的是 IPv4 ICMP，不應直接把相同的 Type／Code 數字套用到 ICMPv6。

另外，實務分析還應核對錯誤訊息來源，以及它所指向的原始資料報。

### 情況三：收到特定其他 ICMP 錯誤 → filtered

假設資料報沒有抵達最終服務。

中間的路由器或防火牆可能送回：

```text
Destination Unreachable
```

但不是前面的 Port Unreachable。

例如某些 ICMP 回報可能與管理政策禁止通訊有關。

Nmap 可能根據具體的 ICMP Type、Code 判讀：

```text
filtered
```

白話文：

「這次探測似乎受到網路政策或傳輸路徑的限制。」

所以不能直接判斷目標服務是否開放。

### 情況四：完全沒有回覆 → open|filtered

這是最容易產生誤解的一種。

假設：

```text
Scanner                         Target
   │                               │
   │ ─────── UDP 資料報 ─────────> │
   │                               │
   │         沒有回覆              │
   │                               │
   │ ─────── UDP 重試 ───────────> │
   │                               │
   │         仍然沒有回覆           │
   │                               │
   ▼                               ▼
          open|filtered
```

你可能會想：

「既然沒有回覆，為什麼不直接判斷 closed？」

因為目標可能真的正在監聽 UDP Port，只是沒有回覆。

例如：

```text
UDP Port 9999
    │
    ├── 程式正在監聽
    │
    ├── 收到資料
    │
    └── 程式設計成不需要回覆
```

也可能是：

```text
UDP Port 9999
    │
    └── 防火牆擋住探測
```

因此，掃描工具無法確定是哪一種情況。

Nmap 就使用：

`open|filtered`

這裡的 `|` 可以理解成「或」。

也就是：

「可能是 open，也可能是 filtered。」

**不是同時證明 open 與 filtered，更不能把它當成確定開放。**

Nmap 官方文件也將沒有回覆的 UDP 探測歸類為 `open|filtered`，並指出可利用適當的服務辨識探測來縮小不確定性。[Nmap](https://nmap.org/book/man-port-scanning-techniques.html?utm_source=chatgpt.com)

### 四種 UDP 判讀整理

| 收到的回應 | Nmap 狀態 | 白話文 |
|---|---|---|
| 對應的 UDP 回覆 | `open` | 有端點願意回覆 |
| IPv4 ICMP Type 3 / Code 3 | `closed` | 連接埠無法到達 |
| 特定其他 ICMP 無法到達錯誤 | `filtered` | 可能受到網路政策或路徑限制 |
| 重試後仍無回覆 | `open\|filtered` | 無法區分開放與被過濾 |

這也是為什麼 TCP 與 UDP 掃描不能套用完全相同的判讀規則。

# 6｜為什麼等待時間、速率與位置很重要？

這一節要建立一個重要觀念：

**掃描結果不只由目標主機決定，也會受到掃描的位置、時間、速率及網路環境影響。**

我們分成三個部分理解。

## 6.1 等待時間：為什麼太早下結論會有問題？

假設你打電話給朋友。

第一次：

```text
你：喂？

等待 1 秒。

對方沒有回答。
```

你能因此認定他不在家嗎？

當然不能。

可能是對方還沒接起電話。

網路也有類似的情況。

例如：

```text
Scanner
   │
   │ UDP 探測
   ▼
網際網路
   │
   ▼
Target
   │
   │ 處理請求
   ▼
回傳封包
```

整個過程需要時間。

如果掃描工具設定：

```text
等待 100 ms
```

但實際上回覆需要：

```text
300 ms
```

就可能發生：

```text
100 ms：掃描工具判定逾時

300 ms：回應才抵達
```

所以等待時間太短，可能增加誤判。

這裡有兩個名詞。

**Timeout（逾時）**

在設定的時間內沒有取得預期回應。

**Retry（重試）**

沒有得到回應時，重新送出探測。

但是重試也有代價。

重試越多：

- 掃描可能耗費更多時間。
- 網路傳送更多封包。
- 目標系統承受更多探測。

所以不是重試越多越好，而是要依環境設定合理的等待與重試條件。

## 6.2 掃描速率：為什麼不是越快越好？

假設你要測試一台伺服器的 1,000 個 Port。

有兩種方式。

方法 A：

```text
每秒探測 10 個 Port
```

方法 B：

```text
每秒探測 1,000 個 Port
```

直覺上，B 比較快。

但是對方可能有防護機制。

例如：

```text
Scanner
   │
   │ 大量探測封包
   ▼
Firewall / IDS / IPS
   │
   ├── 偵測異常頻率
   │
   ├── 限制流量
   │
   └── 丟棄部分封包
```

當封包被丟棄，掃描工具可能得到更多逾時結果。

這會影響掃描的完整性與判讀。

### UDP 還有一個特殊問題：ICMP Rate Limiting

Rate Limiting 就是速率限制。

假設一台主機每秒最多產生少量特定 ICMP 錯誤。

你一次送出大量 UDP 探測。

```text
Scanner
   │
   ├── UDP Port 1000
   ├── UDP Port 1001
   ├── UDP Port 1002
   ├── UDP Port 1003
   └── UDP Port 1004
             │
             ▼
          Target
             │
             └── ICMP 錯誤回覆受到限速
```

即使多個目標 Port 都沒有監聽服務，主機也不一定會針對每一個探測立即回報 ICMP Port Unreachable。

如果有些 ICMP 錯誤因限速而沒有送出，掃描端就得等待或重試。

這也是 UDP 掃描可能比較慢的重要原因之一。

Nmap 官方特別指出，部分作業系統對 ICMP Port Unreachable 具有速率限制，可能顯著增加 UDP 掃描所需時間。[Nmap](https://nmap.org/book/scan-methods-udp-scan.html?utm_source=chatgpt.com)

### 那應該怎麼設定速率？

在取得授權的測試環境中，可以先從少量 Port 開始。

例如：

```bash
sudo nmap -sU -p 53,123,161 --max-rate 10 192.0.2.20
```

這裡的：

```text
--max-rate 10
```

代表設定 Nmap 的探測封包傳送速率上限為每秒 10 個。

但這不是所有環境都適用的最佳值。

實際測試仍應根據設備承載能力、掃描範圍及維護窗口調整。

過快可能遺失資訊，過慢則增加時間成本。

關鍵是找到符合測試目標與環境限制的設定。

## 6.3 掃描位置：為什麼同一台主機可能有不同結果？

這個概念可以直接連結到防火牆與網路分段。

假設實驗室有一台伺服器：

```text
Server
192.168.10.20

TCP 443：HTTPS
TCP 22 ：SSH
```

管理員希望：

- 實驗室內網可以連線 SSH。
- 外部網路不能連線 SSH。
- HTTPS 可以對外提供服務。

網路架構可能如下：

```text
                 伺服器
              192.168.10.20
                   │
              ┌────┴────┐
              │ Firewall│
              └────┬────┘
                   │
         ┌─────────┴─────────┐
         │                   │
     實驗室內網           外部網路
         │                   │
         ▼                   ▼
    測試電腦 A           測試電腦 B
```

假設我們掃描 TCP 22。

**從實驗室內部掃描**

```text
A → Server:22

結果：open
```

因為防火牆政策允許內部管理人員使用 SSH。

**從外部網路掃描**

```text
B → Server:22

結果：filtered
```

因為防火牆可能直接丟棄從外部進來的 TCP 22 探測。

請注意：

同一台伺服器、同一個 Port，卻得到不同結果。

到底哪個是正確的？

**兩個結果都可能正確，因為它們是在不同觀察位置、不同網路路徑下得到的結果。**

但這裡還需要一個前提：測試確實抵達了相同的服務入口，沒有因 NAT、代理或負載平衡器而指向不同設備。

這也是為什麼資安工程師需要保留測試來源、路徑與目的地資訊。

## 6.4 什麼是 NAT？為什麼也會影響掃描？

假設你在家裡使用：

```text
電腦：192.168.1.100
```

這是私有 IP 位址。

但外部網路上的使用者，不一定可以直接連到這個位址。

一般家用路由器可能透過 NAT（Network Address Translation，網路位址轉換）處理內外網通訊。

例如：

```text
外部使用者
    │
    │ 連到路由器的公開 IP
    ▼
家用路由器
    │
    │ NAT / Port Forwarding
    ▼
192.168.1.100
```

如果沒有設定對應的連接埠轉送規則，從外部發起的連線可能無法抵達內部主機。

因此：

```text
內網掃描 → open

外網掃描 → filtered
```

這種差異並不必然代表伺服器的服務狀態改變。

也可能只是因為網路入口和轉送政策不同。

# 7｜把三種掃描方法整合起來

現在我們已經知道：

TCP Connect、SYN 與 UDP Scan 的差異，不只是使用的 Nmap 參數不同。

而是它們**取得證據的方式不同**。

| 比較項目 | TCP Connect | SYN Scan | UDP Scan |
|---|---|---|---|
| Nmap 參數 | `-sT` | `-sS` | `-sU` |
| 通訊協定 | TCP | TCP | UDP |
| 是否完成 TCP 交握 | 是 | 否 | 不適用 |
| 主要判讀依據 | 連線成功或錯誤 | SYN 的回覆 | UDP、ICMP、逾時 |
| 開放的典型證據 | 連線建立成功 | SYN + ACK | 收到對應 UDP 回覆 |
| 關閉的典型證據 | 明確拒絕連線 | 目標回傳 RST | IPv4 ICMP Type 3 / Code 3 |
| 無回覆時常見判讀 | filtered 等，依具體情況 | filtered | open\|filtered |
| 主要限制 | 無法確認應用程式正常 | 不會完成一般 TCP 連線 | 缺乏回覆不代表關閉 |

**最容易考錯的地方：TCP SYN Scan 與 UDP Scan 在無回覆時的判讀不一定相同。**

TCP SYN 掃描在重試後仍無回覆，典型情況會判讀 `filtered`。

UDP 掃描在重試後仍無回覆，則通常保留 `open|filtered`。

原因就是 UDP 並沒有 TCP 那種建立連線時的確認流程。

# 8｜實際操作：在自己的 Ubuntu 上建立安全實驗

以下實驗只針對自己的 `127.0.0.1`，不需要掃描其他設備。

我們先用一個簡單的 HTTP Server 觀察 TCP，再利用 UDP Server 展示「Port 開放卻不回覆」的情況。

## 實驗一：TCP Connect 與 SYN Scan

### 步驟一：啟動測試服務

開啟 Ubuntu Terminal A：

```bash
python3 -m http.server 8000 --bind 127.0.0.1
```

這會在自己的電腦上建立簡單的 HTTP Server。

監聽：

```text
127.0.0.1:8000/tcp
```

保持這個 Terminal 開啟。

### 步驟二：執行 TCP Connect Scan

開啟 Terminal B：

```bash
nmap -sT -p 8000,8001 127.0.0.1
```

如果你的系統沒有安裝 Nmap，可以先使用：

```bash
sudo apt update
sudo apt install nmap
```

預期會看到類似結果：

```text
PORT      STATE    SERVICE
8000/tcp  open     http-alt
8001/tcp  closed   vcom-tunnel
```

這只是可能的示例輸出。`SERVICE` 欄位的顯示取決於 Nmap 服務名稱資料庫；重點是 `STATE`。

為什麼？

因為：

- TCP 8000 有 Python HTTP Server 正在監聽。
- TCP 8001 假設沒有程式監聽，因此通常會回覆連線拒絕。

### 步驟三：執行 SYN Scan

接著執行：

```bash
sudo nmap -sS -p 8000,8001 127.0.0.1
```

預期同樣可能得到：

```text
8000/tcp  open
8001/tcp  closed
```

但你要注意：

**即使最後的掃描狀態相同，兩種方法所使用的封包流程並不相同。**

### 步驟四：觀察實際封包

如果安裝了 tcpdump，可以在另一個 Terminal 執行：

```bash
sudo tcpdump -i lo -nn 'tcp port 8000 or tcp port 8001'
```

再重新執行兩種掃描。

觀察：

- 哪一方先送 SYN？
- 哪一方回 SYN + ACK？
- Connect Scan 是否完成最後 ACK？
- SYN Scan 是否在收到 SYN + ACK 後以 RST 結束嘗試？
- 對沒有監聽的 Port，是否收到 RST？

需要注意，實際看到的 RST、ACK 組合和連線結束細節，可能因作業系統及 Nmap 實作而異。

這個練習的重點不是死背封包數量，而是理解**封包的方向與意義**。

實驗完成後，按 `Ctrl+C` 停止 HTTP Server。

---

## 實驗二：證明 UDP Port 開放也可能沒有回覆

這個實驗直接驗證：

**UDP 沒有回覆，不代表沒有程式正在監聽。**

### 步驟一：建立一個不回覆的 UDP Server

在 Terminal A 執行：

```python
import socket

sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sock.bind(("127.0.0.1", 9999))

print("UDP 9999 正在監聽，但不會回覆資料報")

while True:
    data, addr = sock.recvfrom(4096)
    print(f"收到來自 {addr} 的 {len(data)} bytes")
```

可以將程式儲存為：

```text
udp_server.py
```

然後執行：

```bash
python3 udp_server.py
```

現在有一個 UDP 程式正在監聽 Port 9999。

但我們故意沒有寫：

```python
sock.sendto(...)
```

也就是它收到訊息後，不會主動回覆。

### 步驟二：使用 Nmap 掃描

在 Terminal B 執行：

```bash
sudo nmap -sU -p 9999 127.0.0.1
```

你可能會看到：

```text
PORT      STATE          SERVICE
9999/udp  open|filtered  distinct
```

這裡最重要的是：

```text
open|filtered
```

Nmap 不知道：

- UDP Port 真的開放但不回覆。
- 還是探測遭到過濾。

但是我們自己知道：

**UDP 9999 確實有程式正在監聽。**

因此，這就是理解 `open|filtered` 很好的實驗。

### 步驟三：讓 UDP Server 主動回覆

現在修改原本的程式。

在 `print(...)` 後面加上：

```python
sock.sendto(b"OK", addr)
```

重新啟動 UDP Server，再掃描一次。

如果 Nmap 收到這筆對應的 UDP 回覆，就能把該 Port 判讀為：

```text
open
```

這個實驗可以幫助你理解：

```text
同一個 UDP Port
      │
      ├── 有回覆   → open
      │
      └── 無回覆   → open|filtered
```

即使 Port 的實際監聽狀態沒有改變，掃描工具得到的結果也可能不同。

這正是本課最值得掌握的技術觀念之一。

# 9｜資安實務：掃描結果可以怎麼使用？

假設你正在替一個實驗室進行已授權的資安檢查。

實驗室有以下設備：

```text
實驗室網路
    │
    ├── NAS
    │    ├── TCP 5001
    │    ├── TCP 22
    │    └── TCP 445
    │
    ├── Web Server
    │    ├── TCP 443
    │    └── TCP 80
    │
    └── DNS Server
         ├── UDP 53
         └── TCP 53
```

你可以用掃描協助確認：

第一，哪些通訊入口在指定測試位置可以連通？

第二，哪些入口符合預期的網路存取政策？

第三，哪些入口可能不應該開放？

第四，同一個服務從內部網路與外部網路觀察，是否存在不同的暴露情況？

第五，防火牆、IDS、IPS 是否能按照預期觀察或處理這些流量？

這也呼應 CEH 後面的課程：

**M03 網路掃描 → M04 列舉 → M05 弱點分析 → M12 IDS、防火牆與蜜罐。**

它們的關係可以理解為：

```text
M03｜網路掃描
 │
 │ 發現有哪些 Port 可能開放
 ▼
M04｜列舉
 │
 │ 進一步確認服務、版本或可取得的資訊
 ▼
M05｜弱點分析
 │
 │ 評估服務設定與已知弱點
 ▼
M12｜網路防護
 │
 │ 驗證防火牆政策與偵測能力
 ▼
持續監控與改善
```

需要特別強調：**Port 開放不等於存在漏洞。**

Port 可能是業務正常運作所需的入口。

資安工作的重點，是確認它的用途、暴露範圍、防護措施與風險是否符合預期，而不只是追求關閉所有 Port。

# 10｜本課重點總結

如果今天只能記住五件事，我建議記住：

**第一，TCP Connect 是完整建立連線。**

它讓作業系統完成 TCP 交握，再根據連線結果判斷 Port。

**第二，SYN Scan 不需要完成三向交握。**

它可以從 SYN + ACK 等起始回應，判斷 TCP 入口的狀態。

**第三，UDP 沒有三向交握。**

UDP Scan 主要根據 UDP 回覆、ICMP 錯誤及等待結果判讀。

**第四，沒有回覆不等於 Port 關閉。**

尤其 UDP 的 `open|filtered`，代表目前無法區分開放與過濾。

**第五，掃描結果一定要保留情境。**

同一個 IP、Port，因為來源位置、網路政策、掃描方法、時間及設定不同，可能得到不同的結果。

把這五個觀念理解透徹，後面學習 Open、Closed、Filtered 等狀態，以及進行 Wireshark 封包分析時，就比較不容易混淆。

## 理解檢核：三個情境題

**問題一｜TCP 封包分析**

你使用 SYN Scan 檢查 TCP 443。

觀察到：

```text
Scanner → Target：SYN

Target → Scanner：SYN + ACK

Scanner → Target：RST
```

請問：

1. 這個 Port 應該判斷為什麼狀態？
2. 最後一個 RST 是誰發出的？
3. TCP 三向交握有完成嗎？

**問題二｜UDP 的不確定性**

你使用：

```bash
sudo nmap -sU -p 53 192.0.2.20
```

掃描結果：

```text
53/udp open|filtered
```

請問：

1. 能不能直接判斷 DNS Server 沒有啟動？
2. 請提出三種造成這個結果的可能原因。
3. 如果想進一步確認服務，應該補充哪一種證據？

**問題三｜從資安工程師角度思考**

你從實驗室內網掃描 NAS 的 TCP 22：

```text
open
```

但從外部網路掃描同一台 NAS：

```text
filtered
```

請問：

1. 這兩個結果一定互相矛盾嗎？
2. 哪些網路設備或政策可能造成差異？
3. 如果你的目標是驗證 NAS 沒有對外暴露 SSH，你會如何進一步查核？

這三題涵蓋了本課最重要的三種能力：**理解封包流程、正確解讀掃描結果，以及根據網路環境做出合理的資安判斷。**
