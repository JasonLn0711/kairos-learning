# CEH M01-03｜道德駭客、合法授權與 ROE
**Module 01：Introduction to Ethical Hacking（道德駭客入門）**

難度：★☆☆☆☆（初學者）  
建議學習時間：8～10 分鐘  
核心觀念：Authorization、Scope、Rules of Engagement（ROE）

## 一、先理解：為什麼駭客需要授權？

**今天最重要的一句話：你有能力進入某個系統，不代表你有權利進入；你被允許檢查某個系統，也不代表你可以任意操作。**

我們先把前面三堂課串起來：

| 單元 | 核心問題 | 白話說明 |
|---|---|---|
| M01-01 CIA Triad | 要保護什麼？ | 保護資料不外洩、不被亂改，並且能正常使用 |
| M01-02 資產、威脅、弱點、風險 | 要優先處理什麼？ | 找出重要資產及可能受到的傷害 |
| **M01-03 道德駭客與 ROE** | **誰可以測？怎麼測？** | 確認授權、測試範圍，以及必須遵守的規則 |

### 1. 用生活中的例子理解

假設你住在公寓，最近擔心家中的門鎖不安全。

於是，你找來一位鎖匠。

你告訴他：

「我想知道家裡的大門會不會被人輕易打開，麻煩你幫我檢查。」

鎖匠接受委託，開始檢查。

這時候有三個問題：

**問題 A：鎖匠可以檢查你的大門嗎？**

可以，因為你已經授權他檢查。

**問題 B：鎖匠可以順便檢查隔壁鄰居家的門嗎？**

不可以。

即使隔壁的門鎖跟你家一模一樣，他仍然沒有得到鄰居的允許。

**問題 C：鎖匠可以直接把你的門破壞掉嗎？**

不一定。

你授權的是「檢查門鎖安全性」，不是「破壞大門」。

除非你事先同意使用可能破壞門鎖的測試方式，否則他不能擅自這麼做。

這就是道德駭客最重要的觀念：

**善意只是動機，合法授權與遵守約定才是執行測試的基本條件。**

## 二、什麼是 Ethical Hacking（道德駭客）？

Ethical Hacking 可以翻成「道德駭客」或「倫理駭客」。

它指的是：

在取得適當授權的前提下，使用資安技術檢查系統的弱點，協助組織改善資訊安全。

### 1. 道德駭客和惡意駭客有什麼不同？

假設有一間學校提供線上成績查詢系統。

正常情況下，學生只能查看自己的成績。

某天，有人發現修改網址中的學生編號，可能就能看到其他人的成績。

這時候可能出現三種情況：

| 類型 | 行為 | 主要差別 |
|---|---|---|
| White Hat（白帽駭客） | 取得授權後，在約定範圍內驗證弱點並回報 | 符合授權與規則 |
| Black Hat（黑帽駭客） | 未經授權入侵系統，竊取成績並販售 | 具有惡意目的與行為 |
| Gray Hat（灰帽駭客） | 未經授權自行測試，發現問題後通知學校 | 即使自稱善意，也可能涉及未授權行為 |

注意：這是資安教育常見的簡化分類，不是法律上的正式身分認定。

**駭客是不是「好人」，不能只看他聲稱想做什麼，還要看他的授權與實際行為。**

### 2. 臺灣法律怎麼看？

以臺灣《刑法》第 358 條為例，條文涉及無故輸入他人帳號密碼、破解保護措施，或利用系統漏洞入侵他人電腦等行為。

另外，第 359 條涉及無故取得、刪除或變更電磁紀錄並致生損害；第 360 條則涉及無故干擾電腦系統並致生損害。

這些條文提醒我們：資安測試不是只要自認動機良善就沒有法律風險。實際上是否構成犯罪，仍須依具體行為、法律要件及個案情況判斷。[Mojlaw](https://mojlaw.moj.gov.tw/LawContent.aspx?LSID=FL001424\&TypeSort=2\&lawNumber=358)

因此，實務上應該：

在開始測試前，取得有權者的明確授權，並保存可核對的書面紀錄。

# 三、最重要的三個概念：Authorization、Scope、ROE

這是今天最值得記住的部分。

我們可以把三個概念想像成你參加一場正式考試。

| 概念 | 中文 | 考試比喻 | 資安測試 |
|---|---|---|---|
| Authorization | 授權 | 你有沒有考試資格？ | 你有沒有被允許測試？ |
| Scope | 範圍 | 這次考試考哪些章節？ | 可以測試哪些系統？ |
| ROE | 測試行動規則 | 考試可以使用什麼工具？何時交卷？ | 可以用什麼方法？何時停止？ |

我們逐一理解。

## 3.1 Authorization（授權）

**Authorization 要回答的是：誰有權允許你做這件事？**

例如，你在公司擔任工程師。

公司提供一個內部系統：

`https://internal.example.test`

你擁有自己的員工帳號，也可以正常登入。

這是否表示你可以使用 Nmap 掃描伺服器，或自行嘗試破解其他人的密碼？

答案是：**不代表可以。**

因為這涉及兩種不同的權限。

**第一種：使用權限（Access Permission）**

你被允許使用公司的某項服務。

例如登入請假系統、上傳文件、下載自己有權存取的報表。

**第二種：安全測試授權（Security Testing Authorization）**

你被允許針對特定系統執行安全性檢查。

例如掃描特定測試伺服器的開放連接埠，或檢查指定功能是否存在存取控制弱點。

這兩種權限不能混為一談。

而且，授權者必須有相應的權限。

例如，公司資訊部門主管未必能授權你測試外部雲端供應商的整個基礎設施。

### CEH 必記

Authorization = 是否得到適當授權。

但是，**得到授權不等於取得無限制的操作權限。**

---

## 3.2 Scope（測試範圍）

**Scope 要回答的是：你可以測試哪些東西？**

假設 Northstar 公司有三個系統：

| 系統 | 用途 | 是否允許測試 |
|---|---|---|
| `training.example.test` | 教學測試網站 | ✅ 允許 |
| `production.example.test` | 正式營運網站 | ❌ 不允許 |
| 第三方登入平台 | 提供 Google 等帳號登入 | ❌ 不允許 |

即使這三個系統彼此連線，也不代表測試權限可以跟著擴張。

### 生活中的比喻

假設你是一名消防安全檢查員。

今天受委託檢查 A 棟大樓。

當你走到二樓時，發現有一條通道連接 B 棟大樓。

你可以直接進去檢查 B 棟嗎？

不可以。

因為：

**系統之間存在連線，不代表你取得了另一個系統的測試授權。**

Scope 除了列出允許測試的目標，也應該列出明確排除的目標。

在實務上，可以具體到 IP 位址、網域、服務、功能、測試帳號，以及環境類型。

---

## 3.3 Rules of Engagement（ROE）

ROE 通常翻成「交戰規則」。

但為了便於理解，我建議你先把它想成：

**資安測試的行動規則。**

假設公司已經同意你測試教學網站。

但還有很多問題沒有解決。

例如：

你可以測試到幾點？

可以用自動化工具嗎？

可以進行密碼暴力破解嗎？

可以執行會造成伺服器當機的壓力測試嗎？

如果意外發現真實使用者的個資，應該怎麼處理？

這些問題，就是 ROE 要解決的事情。

### ROE 一定要事先確認的六件事

1. **測試人員與負責窗口：**誰執行測試？誰有權批准、變更或停止測試？
2. **測試目標：**哪些 IP、網域、功能與帳號可以測試？哪些明確排除？
3. **測試時間：**哪一天、幾點開始、幾點結束？使用哪個時區？
4. **允許的方法：**可以使用什麼工具與技術？哪些高風險測試被禁止？
5. **停止條件：**發現個資、服務異常或超出範圍時，應停止哪些活動？如何通報與恢復？
6. **資料與報告處理：**證據如何保存？誰能查看？如何交付報告與處理測試資料？

這並不是我自行發明的原則。

美國國家標準暨技術研究院（NIST）的 SP 800-115 指引，在第 6 章說明安全評估計畫的制定，第 7 章討論測試執行與協調，附錄 B 則提供 ROE 的參考架構。[NIST](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=152164)

它是一份測試管理指引，不是法律授權書。

# 四、實際案例：Northstar 學生成績系統

現在我們把前面的概念整合起來。

假設 Northstar 是一間提供線上教學服務的公司。

系統裡面有兩名測試學生：

Alice（學生 A）

Bob（學生 B）

原則上：

Alice 只能查看自己的作答資料。

Bob 只能查看自己的作答資料。

公司擔心系統可能存在權限控管問題，因此委託你進行安全測試。

## 步驟一：測試前建立 ROE

下面是一份教學用的簡化 ROE。

| 項目 | 約定內容 |
|---|---|
| 測試目的 | 確認學生只能查看自己的作答 |
| 授權者 | 有權管理測試環境的負責人 |
| 測試人員 | 指定的資安測試人員 |
| 測試網站 | `training.example.test` |
| 測試時間 | 10 月 27 日 14:00～15:00（臺灣時間） |
| 測試帳號 | Alice、Bob |
| 測試資料 | 虛構的學生作答 |
| 允許操作 | 檢查約定功能的讀取權限 |
| 禁止操作 | 猜測密碼、壓力測試、測試第三方網站 |
| 停止條件 | 發現真實個資、服務異常或超出範圍 |
| 證據處理 | 只保存足以證明問題的最小必要資料 |
| 通報方式 | 透過指定窗口回報測試結果 |

假設這份文件已經由具有適當權限的人員正式核准。

那麼你就知道哪些事情可以做，哪些不行。

## 步驟二：開始測試

14:00，開始測試。

你使用 Alice 的帳號登入測試網站。

接著查看 Alice 自己的作答。

系統正常顯示：

`學生：Alice`

`作答：A、B、C`

目前沒有發現異常。

接著，你依照 ROE 許可的方法，使用 Alice 的身分檢查能否讀取事先準備的 Bob 測試資料。

結果：

系統居然回傳 Bob 的作答內容！

這代表什麼？

### 技術上的意義

正常的權限控管應該是：

Alice 的帳號 → Alice 的資料：允許。

Alice 的帳號 → Bob 的私人資料：拒絕。

但是實際結果卻是：

Alice 的帳號 → Bob 的私人資料：允許。

這就可能是 **Broken Access Control（存取控制失效）**。

如果問題是系統沒有針對所指定的資料物件正確檢查存取權限，後續還可能涉及 IDOR 或 BOLA 等概念。

不需要在今天深入這些漏洞分類；先理解「系統沒有正確限制使用者能讀取哪些資料」就好。

### 回到 M01-01 的 CIA

這個問題主要影響哪項安全目標？

答案是 Confidentiality（機密性）。

因為不應該被 Alice 看見的資訊，卻被 Alice 讀取了。

這也說明 M01-01、M01-02 和 M01-03 並不是獨立的知識。

它們可以串成一個完整的安全管理流程。

---

## 步驟三：發現弱點後，應該怎麼做？

這時你很興奮。

因為你真的找到一個安全問題。

你可能會想：

「既然可以讀取 Bob 的資料，那我是不是應該再試試看其他 100 個學生的資料？」

**不應該自行擴大測試。**

因為你的授權是驗證指定測試帳號之間的讀取權限。

不是把所有學生資料都下載下來。

正確做法是依照 ROE，保存足以證明問題的最小必要證據。

例如：

| 證據項目 | 紀錄 |
|---|---|
| 測試時間 | 14:20 |
| 測試環境 | training.example.test |
| 執行身分 | Alice |
| 目標資料 | Bob 的虛構作答 |
| 預期結果 | Alice 應該無法讀取 |
| 實際結果 | 系統允許 Alice 讀取 |
| 初步判斷 | 疑似存取控制失效 |

之後依照約定方式通知負責人。

這種做法也符合許多正式漏洞揭露政策採用的原則：僅在必要程度內確認漏洞，避免不必要的資料取得與系統干擾。[U.S. Consumer Product Safety Commission](https://www.cpsc.gov/vulnerability-disclosure-policy?utm_source=chatgpt.com)

# 五、三種容易越界的情況

我們繼續使用 Northstar 的案例。

### 情況一：網站連到另一個伺服器

14:40，你發現測試網站連到：

`payment.example.test`

你懷疑這個網站也有同樣的問題。

可以順便檢查嗎？

不能直接測試。

因為這個網站不在原本的 Scope 裡。

你可以記錄發現的線索，向負責人確認是否需要另外授權。

**重點：發現新目標，不代表取得新授權。**

### 情況二：已經超過測試時間

14:59，你正要進行最後一項檢查。

但還沒完成，時間就已經來到 15:00。

可以說「我只差一分鐘」就繼續嗎？

不應自行繼續。

測試時間本身也是 ROE 的一部分。

應停止尚未完成的測試，確認是否取得有效的延長授權。

### 情況三：AI 建議使用新工具

假設你詢問 ChatGPT：

「我要怎麼找出這個網站的安全漏洞？」

AI 建議你執行某個資安工具。

你可以直接照做嗎？

不能因為是 AI 建議就直接執行。

你仍然需要確認工具的目標、參數、可能影響，以及 ROE 是否允許這項行為。

例如，Nmap 雖然是常見的網路掃描工具，但工具本身並不會替使用者判斷測試是否合法。

**工具的功能，與你擁有的權限，是兩回事。**

# 六、實務補充：公開網站是不是任何人都可以測？

這是一個很容易產生誤會的問題。

例如，你在網路上發現一間公司的網站。

網站可以公開瀏覽，也沒有要求你先註冊。

是否代表你可以進行漏洞掃描？

**公開提供服務，不等於公開授權資安測試。**

不過，有些企業會設立：

Vulnerability Disclosure Policy（VDP，漏洞揭露政策）

或 Bug Bounty Program（漏洞懸賞計畫）。

這些政策可能明確說明哪些系統開放安全研究、允許哪些方法、禁止哪些行為，以及如何通報。

但即使企業有公布 VDP，也不能認為該企業的所有資產都可以測試。

例如，美國商務部的漏洞揭露政策，就明確排除不在範圍內的系統、第三方服務，以及若干高風險測試方法。[U.S. Department of Commerce](https://www.commerce.gov/vulnerability-disclosure-policy?utm_source=chatgpt.com)

另外，NDA（Non-Disclosure Agreement，保密協議）與測試授權不同。

NDA 主要約定資訊保密義務；它本身不代表你已經取得安全測試許可。

# 七、把今天的知識整理成一套決策流程

這是你日後進行任何資安測試前，都可以使用的判斷架構。

### 安全測試決策流程

```text
想對某個系統進行資安測試
           │
           ▼
    是否取得適當授權？
           │
      ┌────┴────┐
      │         │
     沒有      有
      │         │
      ▼         ▼
   不得測試   是否在 Scope 內？
                │
           ┌────┴────┐
           │         │
          否        是
           │         │
           ▼         ▼
       停止確認   方法及時間符合 ROE？
                     │
                ┌────┴────┐
                │         │
               否        是
                │         │
                ▼         ▼
             停止確認   執行測試
                          │
                          ▼
                出現停止條件了嗎？
                          │
                     ┌────┴────┐
                     │         │
                    是        否
                     │         │
                     ▼         ▼
                  停止通報   依規則繼續
                     │
                     ▼
               等待適當核准
```

這個流程有兩個值得注意的地方。

第一，授權不是只在開始測試時確認一次。當測試目標、時間或方法改變時，就必須重新確認原有授權是否仍然涵蓋這些活動。

第二，停止相關測試不一定代表整個專案永久取消。是否可以繼續其他測試、何時可以恢復，應依事先約定的應變與核准程序辦理。

# 八、CEH 考試與實務必記重點

這堂課不需要背誦大量工具或指令。

最重要的是能夠區分以下概念。

| 英文術語 | 中文 | 一句話記憶 |
|---|---|---|
| Ethical Hacking | 道德駭客 | 在適當授權下進行安全測試 |
| Authorization | 授權 | 誰批准你測試？ |
| Scope | 測試範圍 | 可以測試哪些目標？ |
| ROE | 測試行動規則 | 可以怎麼測？什麼時候停止？ |
| Written Authorization | 書面授權 | 留下可查核的批准紀錄 |
| NDA | 保密協議 | 規範資訊保密，不等於測試授權 |
| VDP | 漏洞揭露政策 | 規定漏洞研究與通報條件 |
| Out of Scope | 超出測試範圍 | 不得擅自擴大測試 |
| Evidence | 證據 | 保存足以支持發現的必要資訊 |

特別注意：
