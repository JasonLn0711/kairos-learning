# CEH v13｜M03-05：服務版本與橫幅蒐集（Service Version & Banner Grabbing）
## 完整白話文教學：從 Port 掃描到服務辨識，再到漏洞判斷

**本章最重要的觀念：發現一個 Port 開著，不代表你知道它提供什麼服務；知道服務名稱，不代表你知道真正的軟體版本；知道版本，也不代表它一定有漏洞。**

這個章節承接前面學過的 M03-01 至 M03-04，開始進入真正的資安實務：**我們要如何從網路上的回應，一步步確認伺服器正在提供什麼服務，以及是否存在資安風險？**

本次教學依照 [CS Kairos M03-05 原始教材](https://learn.cs-kairos.com/courses/ceh/v13/m03/concepts/m03-05/?utm_source=chatgpt.com) 的章節順序，逐節說明，並補充實際 Ubuntu 操作、Nmap 指令與資安判斷方法。

# 一、先建立完整的觀念地圖

你之前學過：

| 章節 | 學習重點 | 我們在回答什麼問題？ |
|---|---|---|
| M03-01 | IP、TCP、UDP、Port | 網路上的電腦如何溝通？ |
| M03-02 | ICMP、ARP、主機探索 | 要找的電腦在哪裡？能否取得回應？ |
| M03-03 | TCP、SYN、UDP 掃描 | 哪些 Port 可能開著？ |
| M03-04 | Open、Closed、Filtered | 如何解讀 Port 掃描結果？ |
| **M03-05** | **Service Version、Banner Grabbing** | **開著的 Port 裡面，究竟是什麼服務？** |
| M03-06 | OS Fingerprinting | 這台電腦可能使用什麼作業系統？ |

例如，你正在檢查一台自己管理的 Ubuntu 伺服器。

先使用 Nmap 掃描，得到：

```text
PORT      STATE    SERVICE
22/tcp    open     ssh
80/tcp    open     http
443/tcp   open     https
3306/tcp  filtered mysql
```

初學者可能會說：

「這台電腦有 SSH、HTTP、HTTPS、MySQL 四個服務。」

但這個說法需要修正。

因為你目前能確定的事情是：

- TCP 22、80、443 在這次掃描中呈現 `open`。
- TCP 3306 呈現 `filtered`，無法直接判定它是否有服務正在接聽。
- `SERVICE` 欄位可能只是 Nmap 根據 Port 編號提供的常見服務名稱。
- 你還沒有確認這些 Port 背後實際執行的軟體。

**M03-05，就是教你如何從「Port 的觀察結果」，進一步取得「服務身分的證據」。**

整體流程可以想成：

```text
                一台 Ubuntu 伺服器
                        │
                        ▼
              ① 主機探索（M03-02）

                        │
                        ▼
              ② Port 掃描（M03-03）
                 443/tcp open
                        │
                        ▼
              ③ 服務辨識（M03-05）
                 真的是 HTTPS 嗎？
                        │
                        ▼
              ④ 版本辨識（M03-05）
                 是哪一種伺服器軟體？
                 能否辨識其版本？
                        │
                        ▼
              ⑤ 內部核對
                 實際套件版本？
                 是否經過 Proxy？
                 修補是否已套用？
                        │
                        ▼
              ⑥ 弱點分析（M05）
                 是否存在適用的漏洞？
                 是否真的受到影響？
```

注意：這是一條調查與驗證流程，不代表每個階段都一定能取得明確答案。

# 1｜先用店面招牌理解

## 1.1 為什麼 Port 不等於 Service？

想像你走在一條商店街上。

每一間店都有門牌號碼。

例如：

```text
                    一條商店街

     ┌─────────────┐     ┌─────────────┐
     │   22 號     │     │   80 號     │
     │             │     │             │
     │  遠端管理   │     │  網頁服務   │
     └─────────────┘     └─────────────┘

     ┌─────────────┐     ┌─────────────┐
     │   443 號    │     │  8080 號    │
     │             │     │             │
     │  安全網頁   │     │  開發測試   │
     └─────────────┘     └─────────────┘
```

這些門牌號碼，就是我們之前學過的 Port。

一般情況下：

- TCP 22：常見 SSH。
- TCP 80：常見 HTTP。
- TCP 443：常見 HTTPS。
- TCP 8080：常見替代 HTTP 服務或代理服務。

但是，**門牌號碼不會強制決定店家必須經營什麼業務。**

例如：

你在 443 號店面，預期找到一間提供 HTTPS 的商店。

但是實際上，店家可能把這個入口拿來提供其他 TCP 服務。

換成網路世界：

```text
IP: 192.168.1.100

Port: 443

你預期：
    HTTPS

但實際可能：
    HTTPS
    自訂 TCP 應用程式
    其他使用 TCP 的服務
```

因此：

**Port 是入口編號；Service 才是入口背後真正提供的功能。**

### 1.2 那 Version 又是什麼？

繼續使用商店的例子。

你知道 443 號是一間書店。

這只能告訴你它提供什麼服務，還不知道它使用什麼管理系統。

假設你進一步知道：

```text
門牌：443
    │
    ▼
服務：HTTPS
    │
    ▼
產品：Nginx
    │
    ▼
版本：1.x.x
```

其中：

`443` 是 Port。

`HTTPS` 是通訊服務或協定。

`Nginx` 是提供網頁服務的軟體產品。

`1.x.x` 是軟體版本的示意寫法，還不是已經確認的完整版本。

我們把四者分開，就能避免很多常見的資安誤判。

### 1.3 為什麼這件事重要？

假設你負責管理一家醫院的伺服器。

資安掃描工具告訴你：

```text
443/tcp open
```

如果你立刻認定：

「這台醫院伺服器正在執行某個版本的 Nginx。」

這就是沒有足夠證據的推論。

因為它也可能使用 Apache、Caddy、其他 HTTP 伺服器，或透過負載平衡器及反向代理提供服務。

正確的資安流程，是持續蒐集證據，而不是直接猜測。

**本節重點：Port 告訴你入口在哪裡，但不能單靠 Port 確認服務、產品與版本。**

# 2｜Banner 是什麼？取得它有什麼用？

## 2.1 Banner 就像店家的自我介紹

繼續想像剛才的商店。

你走到 22 號店門口。

店員主動說：

「您好！我們提供遠端管理服務。」

這句自我介紹，就是 Banner 的概念。

在網路世界裡，當你與某些服務建立連線，伺服器可能會傳送一段資訊，告訴你：

「我是誰、支援什麼協定，或者使用哪種軟體。」

這種能夠用來辨識服務身分的資訊，統稱為 **Banner（服務識別資訊）**。

取得這些資訊的過程，就是：

**Banner Grabbing（服務識別資訊擷取）**。

它不是某一個特定的網路協定，而是資安人員取得服務識別線索的一類技術。

## 2.2 範例一：SSH 的 Banner

假設你連上自己管理的 SSH 伺服器。

伺服器可能回傳：

```text
SSH-2.0-OpenSSH_9.6p1 Ubuntu-3ubuntu13
```

這是一個格式示例，不是實際掃描結果。

我們把它拆開：

| 資訊 | 白話文解釋 |
|---|---|
| `SSH` | 這是 SSH 協定相關的識別字串 |
| `2.0` | 宣告的 SSH 協定版本 |
| `OpenSSH` | 宣告使用 OpenSSH 軟體 |
| `9.6p1` | 宣告的 OpenSSH 軟體版本 |
| `Ubuntu-3ubuntu13` | Ubuntu 發行版的套件修訂字串 |

這裡有一個很容易混淆的地方。

`SSH-2.0` 和 `OpenSSH_9.6p1` 並不是同一種版本資訊。

前者描述 SSH 通訊協定。

後者描述 OpenSSH 軟體版本。

這就像：

「我們使用 HTTP/1.1」與「我們使用 Nginx 1.24」是兩個不同層次的資訊。

而且，這一行是服務對外宣告的識別資訊，不是已經查核過的內部套件清單。

## 2.3 範例二：HTTP 的 Banner

假設你使用瀏覽器開啟一個網站。

瀏覽器向伺服器發出：

```http
GET / HTTP/1.1
Host: example.test
```

這可以理解成：

「我要讀取 example.test 網站的首頁。」

伺服器可能回傳：

```http
HTTP/1.1 200 OK
Server: nginx/1.24.0
Content-Type: text/html
Content-Length: 1250
```

逐行解釋：

`HTTP/1.1 200 OK`：這次 HTTP 請求成功處理。

`Server: nginx/1.24.0`：回應中宣告了伺服器產品及版本識別。

`Content-Type: text/html`：回傳內容是 HTML。

`Content-Length: 1250`：回應本文的大小為 1250 bytes。

最值得注意的是：

```http
Server: nginx/1.24.0
```

這就是可能被 Banner Grabbing 蒐集到的資訊。

不過，HTTP 的 `Server` 標頭不是強制提供的資訊。它可能不存在，也可能被修改，或由反向代理產生。RFC 9110 也建議避免在此欄位揭露不必要的實作細節。[RFC Editor](https://www.rfc-editor.org/rfc/rfc9110.html?utm_source=chatgpt.com)

## 2.4 範例三：郵件伺服器的 Banner

假設你連線到一個 SMTP 郵件伺服器。

它可能先回傳：

```text
220 mail.example.test ESMTP
```

其中：

`220` 是 SMTP 回應碼，代表服務已準備好接受進一步的 SMTP 指令。

`mail.example.test` 是伺服器宣告的主機名稱。

`ESMTP` 表示它宣告支援 Extended SMTP。

你不需要登入，就可能看見這段開場回應。

這也說明為什麼服務識別資訊值得關注。

即使攻擊者沒有登入帳號，某些網路服務仍可能對外提供識別線索。

## 2.5 為什麼資安人員要蒐集 Banner？

想像你是公司資安管理員，負責盤點 100 台伺服器。

你可能原本只知道：

```text
伺服器 A：22、80、443 開啟
伺服器 B：22、443 開啟
伺服器 C：21、22、8080 開啟
```

經過服務辨識後，你可能獲得更多線索：

```text
伺服器 A
    22   → 可能是 OpenSSH
    80   → 可能是 Nginx
    443  → 可能是 Nginx

伺服器 B
    22   → 可能是 OpenSSH
    443  → 可能是 Apache httpd

伺服器 C
    21   → 可能是 FTP 服務
    22   → 可能是 OpenSSH
    8080 → 可能是 HTTP 應用程式
```

這可以協助你找出：

哪些服務原本就應該存在。

哪些服務可能是管理者忘記關閉的。

哪些服務需要確認版本與修補狀況。

哪些入口不應該對一般網路使用者開放。

但還有一個重要限制。

**Banner 代表某個端點「對外宣告」了什麼，不代表我們已經確認其真實身分。**

例如，管理者可能把某個服務的 Banner 改成其他文字。

因此不能只靠 Banner 就認定版本一定正確。

# 3｜「等服務先說話」與「送出探測」有何不同？

這一節要理解兩種取得資訊的方式。

它們的差別在於：

**你建立連線之後，是等待對方主動介紹自己，還是主動送出問題讓對方回答？**

## 3.1 第一種：等服務主動說話

假設你走進一家商店。

你沒有主動提問，店員就說：

「您好！歡迎光臨。」

在網路世界中，也有類似的行為。

例如某些 SSH、FTP、SMTP 伺服器，在 TCP 連線建立後，會先傳送識別資訊。

```text
       客戶端                        伺服器
          │                            │
          │ ─────── SYN ─────────────→ │
          │                            │
          │ ←────── SYN/ACK ────────── │
          │                            │
          │ ─────── ACK ─────────────→ │
          │                            │
          │      TCP 連線建立完成      │
          │                            │
          │ ←─────── Banner ────────── │
          │                            │
          │    SSH-2.0-OpenSSH_...     │
          │                            │
```

這裡要連結 M03-01 和 M03-03 的 TCP 三向交握。

你之前學過：

```text
SYN → SYN/ACK → ACK
```

這三個步驟是在建立 TCP 連線。

TCP 連線建立後，應用程式才開始透過這條連線交換資料。

因此，SSH Banner 並不是 SYN/ACK 封包本身包含的資訊，而是建立連線後，服務透過 TCP 傳送的應用層資料。

這個區別非常重要。

**Port 掃描著重觀察網路連線狀態；Banner 擷取則進一步觀察應用程式的回應內容。**

## 3.2 第二種：主動送出探測訊息（Probe）

有些服務不像 SSH 一樣會主動自我介紹。

例如一般 HTTP 伺服器，通常要等客戶端發出 HTTP 請求，才會回傳 HTTP 回應。

```text
       客戶端                        HTTP 伺服器
          │                              │
          │ ───── 建立 TCP 連線 ───────→ │
          │                              │
          │      等待對方說話            │
          │                              │
          │       沒有回應               │
          │                              │
          │ ───── GET / HTTP/1.1 ──────→ │
          │                              │
          │ ←──── HTTP/1.1 200 OK ────── │
          │       Server: nginx/...     │
          │                              │
```

客戶端送出的：

```http
GET / HTTP/1.1
Host: example.test
```

就可以視為一種符合 HTTP 協定的探測請求。

伺服器收到後回傳資料，我們再根據回應判斷它的服務特性。

這就是主動探測的基本原理。

### 3.3 什麼是 Nmap 的 NULL Probe？

NULL Probe 容易讓初學者誤會。

因為看到 NULL，有人會以為：

「是不是完全沒有傳送封包？」

不是。

在 Nmap 的 TCP 服務辨識流程中，NULL Probe 指的是：

**先建立 TCP 連線，但不立即送出應用層的探測內容，而是等待伺服器自行回傳資訊。**

例如：

```text
Nmap
  │
  ├─ 建立 TCP 連線
  │
  ├─ 等待伺服器回應
  │
  ├─ 有 Banner？
  │      │
  │      ├─ 有 → 嘗試辨識
  │      │
  │      └─ 無 → 考慮其他 Probe
  │
  └─ 分析服務身分
```

所以 NULL Probe 的 NULL，並不是「完全沒有網路活動」。

即使沒有送出應用層資料，TCP 連線本身仍然會產生網路封包，也可能被伺服器記錄。

這是 Nmap 官方服務版本辨識文件明確描述的流程。[Nmap](https://nmap.org/book/vscan-technique.html?utm_source=chatgpt.com)

## 3.4 主動探測與被動觀察有什麼不同？

這裡可以進一步連結 CEH 的網路嗅探概念。

| 方法 | 是否產生新的目標連線 | 白話文 |
|---|---|---|
| 建立連線後等待 Banner | 是 | 我走進商店，等待店員介紹 |
| 發送 HTTP、SSH 等探測 | 是 | 我走進商店，主動詢問 |
| 分析已取得的封包紀錄 | 不一定；純離線分析則不會 | 我看先前合法取得的監視紀錄 |

前兩者屬於主動與目標互動。

第三者如果只是離線分析既有封包資料，沒有另外建立連線，就可以屬於被動觀察。

但被動不代表可以任意蒐集他人的通訊資料，仍然要符合授權及資料保護要求。

**本節重點：服務辨識有時靠等待回應，有時靠主動發送符合協定的請求。兩者都可能取得 Banner，但不應把它們視為完全不接觸目標的蒐集方式。**

# 4｜Nmap 的 SERVICE 欄位，證據從哪裡來？

這一節非常重要，因為它直接影響你如何解讀 Nmap 的掃描結果。

## 4.1 Nmap 為什麼知道 Port 22 是 SSH？

假設你執行：

```bash
nmap -p 22,80,443 127.0.0.1
```

假設得到：

```text
PORT    STATE  SERVICE
22/tcp  open   ssh
80/tcp  open   http
443/tcp open   https
```

你可能會問：

「Nmap 怎麼知道 22 是 SSH、80 是 HTTP、443 是 HTTPS？」

答案是：**有時候它並沒有實際確認服務身分，而只是查詢常見 Port 與服務名稱的對照資料庫。**

Nmap 有一份服務對照資料，稱為：

```text
nmap-services
```

裡面有許多常見的對應關係。

例如：

```text
ssh      22/tcp
http     80/tcp
https    443/tcp
```

Nmap 掃描後，可能先根據這份資料提供服務名稱。

這和你用電話號碼的區碼判斷地區很像。

看到某個區碼，你可以推測電話號碼的常見所屬地區。

但是，你不能光憑區碼，就知道接電話的是哪個人。

同樣的道理：

```text
22/tcp open ssh
```

可能只代表：

「TCP 22 開著，而 22 通常是 SSH 的連接埠。」

**它不一定代表 Nmap 已經和真正的 SSH 服務交換過識別資訊。**

這也是 Nmap 官方文件強調：Port 與服務名稱的慣例對照，不能取代真正的服務辨識。[Nmap](https://nmap.org/book/man-version-detection.html?utm_source=chatgpt.com)

## 4.2 如何讓 Nmap 進一步確認服務？

這時候就會用到：

```bash
nmap -sV -p 8080 127.0.0.1
```

這裡的 `127.0.0.1` 是你自己的電腦，適合做隔離練習。

把指令拆開：

| 指令 | 意義 |
|---|---|
| `nmap` | 執行 Nmap |
| `-sV` | 啟用服務與版本辨識 |
| `-p 8080` | 只檢查 Port 8080 |
| `127.0.0.1` | 目標是本機 |

其中，最重要的是：

```bash
-sV
```

這個參數要求 Nmap 不要只停留在常見服務名稱，而要進一步嘗試辨識真正提供服務的軟體。

例如，假設掃描結果是：

```text
PORT     STATE SERVICE VERSION
8080/tcp open  http    ExampleWeb 1.2
```

這是合成示例。

我們現在可以把它拆成四個層次：

```text
8080/tcp
    ↓
入口：TCP Port 8080

open
    ↓
狀態：這次掃描觀察為開啟

http
    ↓
服務：辨識結果為 HTTP

ExampleWeb 1.2
    ↓
產品與版本：工具辨識出的線索
```

這比只有 Port 的資訊豐富許多。

但即使啟用了 `-sV`，仍然不保證能取得精確版本。

## 4.3 Nmap 內部實際做了什麼？

可以把 `-sV` 想像成一名訓練有素的調查員。

他不會只看門牌號碼，而是根據對方的回答，逐步辨認身分。

Nmap 大致會進行以下流程：

```text
                    Nmap -sV
                        │
                        ▼
                找到待辨識的 Port
                        │
                        ▼
                嘗試與服務建立連線
                        │
                        ▼
                等待服務自行回應
                        │
               ┌────────┴────────┐
               │                 │
          收到 Banner        沒有取得足夠資訊
               │                 │
               ▼                 ▼
          特徵資料庫比對      發送適當 Probe
               │                 │
               │                 ▼
               │             分析回應
               │                 │
               └────────┬────────┘
                        │
                        ▼
                嘗試辨識服務與版本
                        │
               ┌────────┴────────┐
               │                 │
           足夠證據          證據不足
               │                 │
               ▼                 ▼
            回報結果       保留未確認資訊
```

Nmap 會使用另一份資料庫：

```text
nmap-service-probes
```

其中包含各種探測方法與回應特徵。

例如，Nmap 可能送出一段符合 HTTP 格式的請求。

當對方回覆：

```http
HTTP/1.1 200 OK
Server: ExampleWeb/1.2
```

Nmap 便嘗試比對回應特徵，判斷服務與版本。

官方文件進一步說明，Nmap 會依 Port、探測訊息的適用性及辨識結果決定後續探測流程。[Nmap](https://nmap.org/book/vscan-technique.html?utm_source=chatgpt.com)

### 4.4 什麼是 softmatch？

這是 CEH 學習時值得理解的概念。

想像你打電話給一家公司。

對方說：

「您好，這裡是客服中心。」

你現在知道：

對方可能是客服部門。

但你還不知道是哪家公司的客服。

這就是 softmatch 可以幫助理解的情況。

Nmap 可能已經取得足夠線索，初步確認這是 HTTP、SSH 或其他類型的服務。

但還無法確認精確產品或版本。

這時候，它可能依照初步辨識結果，選擇後續更合適的探測方式。

**softmatch 不是百分比信心分數，而是初步服務匹配。**

它不能直接解讀成「90% 的機率是某種服務」。

## 4.5 `-sV`、`-O`、`-A` 有什麼不同？

這三個參數很容易混淆。

| 參數 | 功能 | 主要回答的問題 |
|---|---|---|
| `-sV` | Service/Version Detection | Port 裡面是什麼服務與產品版本？ |
| `-O` | OS Detection | 這台主機可能使用什麼作業系統？ |
| `-A` | 啟用多項進階辨識功能 | 同時取得多種主機與服務資訊 |

例如：

```bash
nmap -sV -p 8080 127.0.0.1
```

主要聚焦在 Port 8080 的服務與版本辨識。

而 `-O` 則是利用網路協定堆疊的回應特徵，嘗試推測作業系統。

它們的研究對象不同。

請特別注意：

`-A` 不只是 `-sV` 的另一種寫法。它還會啟用其他功能，例如 OS 偵測、預設 NSE 腳本與 traceroute。

因此，初學時沒有必要直接使用 `-A`。

另外，Nmap 預設會排除某些可能產生非預期影響的版本探測。典型例子是部分印表機使用的 TCP 9100；某些設備可能把探測資料直接當成列印內容。

這也是為什麼資安測試必須考慮目標設備的功能與承受能力。[Nmap](https://nmap.org/book/man-version-detection.html?utm_source=chatgpt.com)

**本節重點：Nmap 可以根據 Port 名稱推測服務，也可以使用 `-sV` 主動辨識。兩者的證據強度不同。**

# 5｜為什麼看到版本，還不能直接宣布有漏洞？

這是整個 M03-05 最重要的資安判斷能力。

你需要建立一個觀念：

**發現軟體版本，不等於證明軟體存在可利用的弱點。**

假設你掃描某台伺服器。

得到：

```text
PORT    STATE SERVICE VERSION
80/tcp  open  http    ExampleWeb 1.2
```

然後你在弱點資料庫中查到：

```text
CVE-20XX-12345

受影響產品：
ExampleWeb

受影響版本：
特定 1.x 版本

漏洞類型：
可能造成遠端程式碼執行
```

這些資訊都是合成示例。

初學者可能會立刻認定：

「這台伺服器存在 CVE-20XX-12345，可以遠端執行程式碼。」

但這樣的判斷存在問題。

因為你還沒有確認：

第一，Banner 宣告的是否是真正的後端軟體。

第二，實際安裝的軟體是否屬於受影響的套件版本。

第三，供應商是否已經回補修補程式。

第四，漏洞成立所需的設定與功能是否存在。

接下來的 A、B 兩個子章節，就是要解釋最容易發生的兩種誤判。

# 5-A｜你看到的可能是前面的代理（Reverse Proxy）

## 5-A.1 什麼是反向代理？

你可以把 Reverse Proxy 想成醫院的服務櫃台。

假設病人到醫院詢問：

「我要找心臟內科醫師。」

病人不會直接跑進醫師的辦公室。

他會先到服務櫃台。

服務櫃台確認需求後，再協助聯絡真正提供服務的部門。

在網路系統中也有類似架構。

```text
                網際網路使用者
                       │
                       │ HTTPS Request
                       ▼
             ┌───────────────────┐
             │   Reverse Proxy   │
             │                   │
             │     Nginx         │
             │   對外接收請求    │
             └───────────────────┘
                       │
                       │ 轉送請求
                       ▼
             ┌───────────────────┐
             │   Backend Server  │
             │                   │
             │  Python / Node.js │
             │    真正的應用程式 │
             └───────────────────┘
                       │
                       ▼
                    Database
```

這裡有三個角色。

Client（客戶端）：發出請求的使用者。

Reverse Proxy（反向代理）：接收請求、決定如何轉送的前端服務。

Backend（後端）：實際執行應用程式業務邏輯的服務。

## 5-A.2 為什麼 Banner 可能讓我們誤判？

假設後端實際使用：

```text
Python FastAPI
```

但是前面有一個 Nginx 反向代理。

外部使用者透過 HTTP 取得：

```http
Server: nginx
```

這時候，你能確認什麼？

你可以確認：

「這次 HTTP 回應包含 nginx 的識別資訊。」

但你不能因此認定：

「整個網站的應用程式就是 Nginx，沒有其他後端服務。」

因為 Nginx 可能只是負責接收請求。

真正處理使用者登入、查詢資料、讀取資料庫的，是後端 FastAPI。

反向代理也可能移除、覆寫或轉送原本的 `Server` 標頭。

因此：

```text
外部看到的 Server Banner
               ≠
後端應用程式的完整身分
```

### 5-A.3 與 Cloudflare 有什麼關係？

這和你正在規劃的網站、子網域，以及 Cloudflare 部署架構有直接關聯。

假設你的網站採用以下架構：

```text
              Browser
                 │
                 │ HTTPS
                 ▼
        ┌─────────────────┐
        │ Cloudflare Edge │
        │                 │
        │ DNS / CDN / WAF │
        └─────────────────┘
                 │
                 │ Cloudflare Tunnel
                 ▼
        ┌─────────────────┐
        │ Ubuntu Server   │
        │                 │
        │ Nginx           │
        └─────────────────┘
                 │
                 ▼
        ┌─────────────────┐
        │ Web Application │
        │                 │
        │ Node.js / Python│
        └─────────────────┘
```

當外部使用者存取網站時，可能先和 Cloudflare 的 Edge 建立連線。

這意味著：

你從外部觀察到的 TLS、HTTP 行為與標頭，不一定反映 Ubuntu 伺服器或後端應用程式的完整狀態。

這也是為什麼：

**如果你的目的是資產盤點，只看外部掃描結果可能不夠，還需要對照內部部署架構。**

另一方面，反向代理不一定是安全保證。

它能夠提供存取控制、流量管理或其他防護功能，但仍需要正確設定，也不能替代後端的弱點修補。

# 5-B｜舊版號可能已回補安全修正（Backport）

這一節對 Ubuntu、Debian、Red Hat 等 Linux 系統的維運非常重要。

## 5-B.1 什麼是 Backport？

Backport 中文通常稱為「回補」。

用白話文來說：

**把新版軟體裡面的某項修正，移植回原本正在使用的舊版本。**

假設有一套軟體。

原始開發者推出：

```text
ExampleApp 1.0
ExampleApp 1.1
ExampleApp 1.2
ExampleApp 2.0
```

某一天，大家發現：

```text
ExampleApp 1.2
存在安全漏洞
```

開發團隊在 ExampleApp 2.0 修好了這個問題。

但有些企業不能直接升級到 2.0。

原因可能是：

新版本改變了設定格式。

某些 API 不相容。

原本的應用程式可能無法正常執行。

這時，作業系統供應商可能採取另一種做法。

```text
          原始開發團隊（Upstream）

             ExampleApp 1.2
                    │
                    │ 發現漏洞
                    ▼
             ExampleApp 2.0
                    │
                    │ 漏洞修補程式
                    │
                    ▼
         ┌──────────────────────┐
         │   取出相關安全修正   │
         └──────────────────────┘
                    │
                    │ Backport
                    ▼
            發行版維護版本

          ExampleApp 1.2-vendor3
                    │
                    ▼
             已套用安全修正
```

請注意：

舊版本的主版本號可能沒有改變。

但是軟體實際上已經包含修補程式。

所以，**舊版號不一定代表仍存在那個已知漏洞。**

Red Hat 官方安全維護文件也說明，回補是一種常見的安全更新方式，並會透過安全公告和 CVE 資訊提供修補狀態的查核依據。[Red Hat Customer Portal](https://access.redhat.com/security/updates/backporting?utm_source=chatgpt.com)

## 5-B.2 為什麼這會影響資安掃描？

假設你掃描一台 Ubuntu 伺服器。

看到：

```text
Server: ExampleWeb/1.2
```

然後找到一份漏洞公告：

```text
ExampleWeb 1.2 存在安全弱點。
```

但這台 Ubuntu 伺服器上的套件實際上是：

```text
ExampleWeb 1.2-ubuntu5.3
```

其中 `ubuntu5.3` 是合成的發行版修訂字串。

如果 Ubuntu 維護者已經把修補程式回補至這個版本，那麼你就不能只根據：

```text
ExampleWeb/1.2
```

認定它仍然存在同一個漏洞。

真正要做的是核對：

```text
外部看到的 Banner
        │
        ▼
管理端實際套件版本
        │
        ▼
供應商安全公告
        │
        ▼
漏洞修補是否已套用
        │
        ▼
執行中的服務是否已更新
        │
        ▼
確認漏洞是否仍然適用
```

## 5-B.3 在 Ubuntu 上如何查看套件版本？

假設你要檢查自己 Ubuntu 上的 OpenSSH。

可以執行：

```bash
dpkg-query -W openssh-server
```

這會查詢已安裝套件的版本資訊。

如果想知道系統目前有哪些可用的套件版本：

```bash
apt policy openssh-server
```

你可能看到：

```text
Installed: 1:9.6p1-3ubuntu13.x
Candidate: 1:9.6p1-3ubuntu13.y
```

這裡是格式示例，不是目前最新版的宣稱。

其中：

`Installed` 表示目前已安裝的套件版本。

`Candidate` 表示依目前 APT 套件來源設定，候選安裝的版本。

但請注意，`Installed` 與 `Candidate` 不同，不一定代表存在安全漏洞；相同也不保證所有弱點都已修補。

還必須根據發行版的安全公告與漏洞成立條件查核。

如果要確認系統是否啟用了相關安全更新來源，也需要檢查 APT 的套件來源設定。

對於 Ubuntu，應優先參考 Ubuntu 官方安全公告，而不是直接將上游軟體版本與 CVE 範圍做字串比對。

## 5-B.4 更新完成後，就代表問題解決了嗎？

也不一定。

例如，你已經更新某個伺服器套件。

磁碟上的檔案已經是新版本。

但正在記憶體中執行的服務程序，可能仍然載入舊版本。

這時候可能需要重新載入服務或重新啟動。

因此，完整的修補驗證應包括：

```text
確認修補公告
      │
      ▼
安裝修補套件
      │
      ▼
確認必要的服務重新載入
      │
      ▼
確認實際執行版本
      │
      ▼
確認原有功能正常
      │
      ▼
確認相關弱點已不再適用
```

其中，重新啟動服務可能造成連線中斷，因此正式環境應依維護程序處理。

**本節最重要的結論：Banner 不是修補證據；套件版本也必須連同供應商公告、回補紀錄與執行狀態一起判讀。**

# 6｜完整合成案例：把推測變成可追查紀錄

現在把前面學過的內容全部串起來。

## 6.1 假設你正在進行資安盤點

你受委託檢查一家企業的內部應用系統。

測試對象：

```text
IP: 192.0.2.10
Port: TCP 8080
```

`192.0.2.10` 是文件示例位址，不是真實測試目標。

假設在已授權的隔離環境中，Nmap 得到：

```text
8080/tcp open http
```

這是第一筆證據。

代表：

「從指定測試位置與條件觀察，TCP 8080 呈現開啟狀態。」

接著，你取得 HTTP 回應：

```http
HTTP/1.1 200 OK
Server: ExampleWeb/1.2
```

這是第二筆證據。

代表：

「這次 HTTP 回應宣告了 ExampleWeb/1.2。」

然後，你閱讀架構文件。

發現：

```text
     外部用戶
         │
         ▼
   Reverse Proxy
   ExampleWeb/1.2
         │
         ▼
     Backend
   example-app 4.0
```

這是第三筆證據。

最後，管理者查詢設備上的套件資料。

得到：

```text
example-app 4.0-vendor3
```

這是第四筆證據。

但是供應商修補公告及實際執行版本，尚未確認。

這時候，你應該怎麼寫資安報告？

## 6.2 錯誤的報告方式

```text
發現：

目標使用 ExampleWeb 1.2。

該版本存在安全漏洞。

判定為高風險弱點。
```

為什麼這樣寫有問題？

因為你把三個不同的概念混在一起。

第一，你只知道 HTTP 回應宣告了 ExampleWeb/1.2。

第二，後端實際執行的是另一個應用程式。

第三，你沒有提出足夠證據證明特定漏洞適用。

這類誤判會造成資安治理上的問題。

例如，公司可能因此投入大量資源處理不存在的弱點。

反過來說，也可能因為只檢查反向代理，忽略真正有問題的後端程式。

## 6.3 正確的報告方式

可以建立三個明確的欄位。

### 第一：Observation（觀察）

```text
在授權測試環境中：

TCP 8080 呈現 open。

HTTP 回應包含：
Server: ExampleWeb/1.2

架構文件顯示存在 Reverse Proxy。

管理端套件紀錄：
example-app 4.0-vendor3
```

這裡只記錄實際取得的資訊，不加入超出證據範圍的推測。

### 第二：Inference（推論）

```text
HTTP 回應包含 ExampleWeb 產品識別資訊。

由於前方存在 Reverse Proxy，
該字串可能來自前端服務。

因此無法僅靠該 Banner
確認後端應用程式的精確版本。

目前尚無充分證據確認
特定 CVE 是否適用。
```

這裡開始解釋證據的意義。

但是每個推論，都要有相對應的依據。

### 第三：Pending Verification（待確認）

```text
1. 核對實際執行中的後端程序。

2. 確認完整套件版本與來源。

3. 查閱供應商安全公告。

4. 確認是否已套用 Backport 修正。

5. 核對漏洞成立所需的設定。

6. 確認執行中的服務已使用修補版本。
```

如此才能形成可追查、可驗收的資安紀錄。

## 6.4 這和 CEH M05 有什麼關係？

你可以把 CEH 的研究流程分成：

```text
M03 Network Scanning
        │
        │ 找出可能開啟的入口
        │ 辨識服務及版本線索
        ▼
M04 Enumeration
        │
        │ 在授權範圍內
        │ 進一步取得服務與系統資訊
        ▼
M05 Vulnerability Analysis
        │
        │ 核對產品、版本、
        │ 設定及弱點成立條件
        ▼
確認受影響範圍與風險
        │
        ▼
制定修補與驗證計畫
```

要注意：這不是每次測試都必須照順序執行的固定程序，而是方便學習的概念關係。

**M03-05 主要幫助你建立服務身分與版本線索。M05 才會進一步分析這些資產是否受到特定弱點影響。**

# 7｜管理者如何防護，又如何留下驗收證據？

到這裡，我們已經學會如何觀察服務、辨識版本，以及避免過度推論。

接下來要換個角色。

假設你是醫院、企業或研究機構的資安管理者。

你要如何降低服務資訊暴露與相關風險？

## 7.1 第一層：先盤點真正需要的服務

假設你有一台 Ubuntu 伺服器。

它目前開啟：

```text
22/tcp
80/tcp
443/tcp
3306/tcp
```

你需要先確認每個 Port 的用途。

例如：

TCP 22 是否用於遠端管理？

TCP 80 是否應該只負責 HTTP 轉址？

TCP 443 是否提供對外網站？

TCP 3306 是否應該只供內部應用程式連線？

如果 3306 是資料庫服務，就不一定有必要對整個網際網路開放。

但要注意：不能單靠 Port 3306 就確認它一定是 MySQL；還是要核對內部設定。

在 Ubuntu 上，你可以先使用：

```bash
sudo ss -ltnp
```

其中：

`ss`：檢視 Socket 相關資訊。

`-l`：只看正在 Listen 的 Socket。

`-t`：檢視 TCP。

`-n`：以數字顯示 IP 與 Port。

`-p`：顯示相關程序資訊。

這可以幫助你回答：

「究竟是哪個程式正在我的伺服器上接聽連線？」

不過，`ss` 顯示的是本機 Socket 狀態，不能直接代表外部網路一定能連進來。

還需要考慮防火牆、路由、NAT 與其他網路存取控制。

## 7.2 第二層：減少不必要的 Banner 資訊

假設你的網站回傳：

```http
Server: nginx/1.24.0
```

這會讓外部使用者取得較具體的版本線索。

在適當情況下，你可以調整伺服器設定，減少不必要的版本揭露。

例如，在 Nginx 中：

```nginx
http {
    server_tokens off;
}
```

這通常可以讓 Nginx 在其自行產生的相關回應中，不再揭露詳細版本。

但不保證移除所有產品識別資訊，也不保證經過其他模組或代理後的標頭都會相同。

設定更改後，應先檢查設定是否有效：

```bash
sudo nginx -t
```

通過後，再依照正式環境的變更程序重新載入服務。

例如：

```bash
sudo systemctl reload nginx
```

在正式環境中，應先確認是否存在其他服務或設定相依性。

### 為什麼不能只靠隱藏 Banner？

假設某個版本確實有安全弱點。

你把：

```http
Server: nginx/1.24.0
```

改成：

```http
Server: nginx
```

這代表什麼？

只代表外部能取得的版本識別資訊減少了。

**它不代表漏洞已經修補。**

攻擊者仍可能透過其他方式推測服務，也可能在不知道版本的情況下測試某些弱點。

所以要區分：

```text
隱藏 Banner
    │
    ▼
減少資訊揭露


修補漏洞
    │
    ▼
修正安全缺陷
```

這是兩件不同的事情。

## 7.3 第三層：限制管理服務的可存取範圍

假設你有一台供研究使用的 Ubuntu 伺服器。

SSH 只需要讓特定管理者連線。

你可以透過防火牆、VPN、身分驗證或其他存取控制機制，限制管理入口的暴露範圍。

例如：

```text
                 Internet
                    │
                    ▼
               Firewall
                    │
        ┌───────────┴───────────┐
        │                       │
   未授權來源              已授權來源
        │                       │
        ▼                       ▼
    阻擋存取                允許連線
                                │
                                ▼
                          SSH Server
```

這和 M03-04 的 `filtered` 概念直接相關。

如果防火牆沒有讓掃描封包取得足夠回應，Nmap 就可能回報：

```text
22/tcp filtered ssh
```

但仍然要注意：

`filtered` 是特定掃描條件下的觀察結果，不等於已經證明整個防護配置沒有漏洞。

## 7.4 第四層：保留可驗收的證據

在真正的資安治理中，不能只說：

「我已經修好了。」

而是要能回答：

「你怎麼證明它已經修好了？」

可以建立以下驗收矩陣：

| 防護工作 | 需要確認的事項 | 驗收證據 |
|---|---|---|
| 服務盤點 | 哪些服務正在執行 | Socket、程序、資產清單 |
| Banner 管理 | 是否減少不必要資訊 | 調整前後 HTTP/SSH 回應 |
| 存取控制 | 非授權來源是否被限制 | 防火牆規則、測試紀錄 |
| 版本修補 | 安全修正是否已套用 | 套件版本、安全公告、更新紀錄 |
| 執行狀態 | 服務是否已使用修補版本 | 程序、服務狀態與必要驗證 |
| 異常監控 | 能否發現非預期探測 | 服務、代理與防火牆日誌 |

這些證據應保留測試時間、來源位置、目標與設定條件。

否則，即使兩份掃描結果不同，也不一定能知道差異是因為安全設定改變，還是因為測試環境不同。

**本節重點：有效的資安管理，不只是降低資訊暴露，而是建立能夠確認服務身分、修補狀態與防護效果的證據鏈。**

# 8｜今天的安全練習與小檢核

原始教材的練習是使用合成案例，完成「觀察、推論、待確認」三行紀錄，不需要對任何主機送出封包。

這裡另外補充一個可選的 Ubuntu 本機實驗，幫助你實際理解 Banner Grabbing。

## 8.1 實驗目標

在自己的 Ubuntu 上：

建立一個 HTTP 服務。

觀察它正在使用哪個 Port。

取得它回傳的 HTTP Banner。

最後使用 Nmap 辨識服務。

整個實驗只使用：

```text
127.0.0.1
```

也就是自己的電腦，不需要掃描外部網路。

## 8.2 步驟一：啟動 HTTP 服務

開啟第一個 Terminal。

執行：

```bash
python3 -m http.server 8080 --bind 127.0.0.1
```

這會使用 Python 內建的 HTTP Server，在本機 Port 8080 提供簡單的網頁服務。

其中：

`python3`：執行 Python。

`-m http.server`：啟用內建 HTTP Server 模組。

`8080`：指定 Port。

`--bind 127.0.0.1`：只綁定本機回送位址。

成功後，應看到伺服器開始接聽的訊息。

這個簡易服務會提供目前工作目錄中的檔案，因此不要在含有敏感文件的資料夾啟動它。

## 8.3 步驟二：確認 Port 8080 是否開啟

開啟第二個 Terminal。

執行：

```bash
ss -ltnp | grep ':8080'
```

假設看到：

```text
LISTEN 0 5 127.0.0.1:8080 ...
```

這代表什麼？

`LISTEN` 表示有 TCP Socket 正在等待連線。

`127.0.0.1:8080` 表示它綁定在本機的 TCP 8080。

這是主機內部觀察，不是 Nmap 從外部網路取得的掃描結果。

## 8.4 步驟三：使用 curl 觀察 HTTP Banner

執行：

```bash
curl -I http://127.0.0.1:8080
```

`-I` 表示要求取得 HTTP 回應標頭，curl 通常會送出 HEAD 請求。

你可能看到類似：

```http
HTTP/1.0 200 OK
Server: SimpleHTTP/0.6 Python/3.12.x
Date: ...
Content-type: text/html; charset=utf-8
```

實際內容會隨 Python 版本與環境而異。

最重要的是：

```http
Server: SimpleHTTP/0.6 Python/3.12.x
```

我們現在取得了什麼？

第一，HTTP 回應成功。

第二，回應宣告了 SimpleHTTP 的識別資訊。

第三，回應中提供了 Python 版本線索。

但要注意，`SimpleHTTP/0.6` 是 Python HTTP Server 的識別字串，不是完整的作業系統版本，也不等於某個漏洞一定成立。

這就是本章所說的 Banner Grabbing。

## 8.5 步驟四：使用 Nmap 比較有無 `-sV`

先執行：

```bash
nmap -p 8080 127.0.0.1
```

可能得到：

```text
PORT     STATE SERVICE
8080/tcp open  http-proxy
```

Nmap 在沒有實際確認服務的情況下，可能依照常見 Port 名稱，顯示 `http-proxy`。

接著執行：

```bash
nmap -sV -p 8080 127.0.0.1
```

這次 Nmap 會嘗試辨識實際服務。

你可能得到包含 HTTP 服務及 Python HTTP Server 識別資訊的結果。

精確輸出依 Nmap 版本、探測資料庫及 Python 回應而異，不需要強求與示例完全相同。

### 比較兩次掃描的差別

| 觀察項目 | 一般 Port 掃描 | 使用 `-sV` |
|---|---|---|
| Port 是否開啟 | 可以觀察 | 可以觀察 |
| 常見服務名稱 | 可能顯示 | 可能顯示 |
| 實際服務辨識 | 不一定 | 會主動嘗試 |
| 軟體版本資訊 | 通常沒有 | 可能取得 |
| 是否能確認漏洞 | 不能 | 仍然不能 |

這就是 M03-05 最重要的實作差異。

## 8.6 步驟五：觀察伺服器端紀錄

回到第一個 Terminal。

你可能會看到：

```text
127.0.0.1 - - [...] "HEAD / HTTP/1.1" 200 -
```

這表示你的 HTTP 服務收到了請求。

如果執行過 Nmap `-sV`，也可能看到其他探測請求或錯誤訊息。

這能幫助你理解：

**主動服務辨識可能會在伺服器上留下紀錄。**

這也能連結到未來學習的 IDS、網路流量監控與異常行為分析。

最後回到第一個 Terminal，按下：

```text
Ctrl + C
```

停止 Python HTTP Server。

# 九、把 M03-05 放進完整的資安知識體系

學完本章後，應該知道它與其他資安技術的關係。

| 技術 | 主要目的 | 和 Banner Grabbing 的關係 |
|---|---|---|
| Port Scanning | 找出入口與狀態 | 提供後續辨識對象 |
| Banner Grabbing | 蒐集服務識別資訊 | 提供服務身分線索 |
| Service Detection | 辨識服務類型 | Banner 是可能使用的方法之一 |
| Version Detection | 嘗試辨認產品及版本 | 可能結合 Banner 與其他探測 |
| OS Fingerprinting | 推測作業系統 | 與服務版本辨識不同 |
| Vulnerability Analysis | 判斷弱點是否適用 | 使用辨識結果作為部分證據 |
| Asset Management | 管理組織資產 | 需要把觀察結果與內部紀錄對照 |
| Detection Engineering | 建立偵測規則與機制 | 可利用服務探測產生的日誌與流量特徵 |

其中，最值得你掌握的是：

**資安掃描不是一次就得到所有真相，而是透過不同層次的證據，逐步縮小不確定性。**

例如：

```text
發現 Port 443 開啟
        │
        ▼
判斷可能是 HTTPS
        │
        ▼
確認收到 HTTP 回應
        │
        ▼
取得 Server 識別資訊
        │
        ▼
辨認前方可能有 Reverse Proxy
        │
        ▼
核對後端實際套件
        │
        ▼
核對 CVE 與安全修補公告
        │
        ▼
確認弱點適用性
        │
        ▼
修補、驗證與保留證據
```

這也是本章對資安研究與實務最大的價值。

我們不只是學會多一個 Nmap 參數，而是學會如何避免把「工具輸出」錯誤當成「已經證實的事實」。

# 十一、學習理解檢核

以下四題對應原始教材的主要理解重點。我先保留答案，讓你嘗試推理，再依你的回答檢查觀念是否正確。

### 第一題：Port 與 Service

你使用 Nmap 掃描某台主機，得到：

```text
443/tcp open https
```

請問：

這是否代表你已經確認該伺服器使用 Nginx？

為什麼？

### 第二題：NULL Probe

你使用 Nmap 的版本辨識功能。

Nmap 建立 TCP 連線後，先等待伺服器主動回傳 Banner。

請問：

這種方式是否屬於完全不接觸目標的被動蒐集？

請從 TCP 三向交握的角度解釋。

### 第三題：Reverse Proxy 與 Backport

你掃描某個網站。

得到：

```text
Server: ExampleWeb/1.2
```

你查到網路上有一筆 CVE，指出 ExampleWeb 的某些 1.x 版本存在漏洞。

但你也知道，這個網站使用了 Reverse Proxy，而且後端執行在 Ubuntu 上。

請問：

你還需要哪些證據，才能判斷這個網站是否真的受到該 CVE 影響？

### 第四題：Banner 與漏洞修補

某位系統管理員發現，網站的 HTTP Header 會洩漏 Nginx 的詳細版本。

因此，他執行：

```nginx
server_tokens off;
```

重新載入 Nginx 後，外部無法再從該欄位看到完整版本。

管理員於是宣布：

「我們已經修復 Nginx 的安全漏洞。」

請問：

這個結論正確嗎？

你會如何分別驗收「資訊揭露減少」與「安全漏洞修補」？

## 本章最重要的五個觀念

**第一，Port 不等於 Service。** 開啟的 Port 只告訴你指定測試條件下的入口狀態。

**第二，Banner 是線索，不是身分證明。** 伺服器可能宣告產品與版本，但資訊不一定完整或正確。

**第三，`nmap -sV` 會嘗試進行真正的服務版本辨識。** 它可能等待 Banner，也可能主動送出 Probe。

**第四，Reverse Proxy 與 Backport 會影響版本判斷。** 外部看到的服務不一定是後端，而較舊的上游版本號也不一定代表未修補。

**第五，漏洞判斷必須建立證據鏈。** 從掃描結果到漏洞確認，還需要核對實際執行的套件、供應商安全公告、設定及修補狀態。

**下一步建議：**先在自己的 Ubuntu 執行第 8 節的本機實驗，親眼比較 `nmap -p 8080`、`nmap -sV -p 8080` 與 `curl -I` 的結果。當你能清楚區分「Port 狀態」、「服務辨識」與「版本證據」時，就已經掌握本章的核心能力。
