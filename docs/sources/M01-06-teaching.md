# CEH M01-06｜安全控制措施與縱深防禦

Module 01：Introduction to Ethical Hacking（道德駭客入門）

建議閱讀：8～12 分鐘。這是新路線第 6 個單元；讀完教材與真正理解，仍分開確認。

## 一、先說結論：不要只問「有沒有防護」，要問「這道防護失效後，還剩什麼」

Security Controls（安全控制措施）是為了保護資料與服務，實際採取的防護做法。Defense in Depth（縱深防禦）則是把不同做法安排在不同位置，讓一道防護沒擋住時，還有其他措施能阻擋、發現、限制損害或協助復原。

今天最重要的一句話是：有安裝安全產品，不等於防護一定有效；有很多產品，也不等於已經做好縱深防禦。

想像你開了一間咖啡廳，裡面有一個放現金的保險箱。

你不會只掛一張「請勿偷竊」的牌子，就認為現金一定安全。你可能會鎖店門、限制保險箱鑰匙由誰保管、裝設警報，並安排店員接到警報後的處理方式。

門鎖是在降低別人進入的機會；警報是在提醒異常；鑰匙管理是在限制誰能碰到現金。它們不是三個名字不同、作用卻完全一樣的東西，而是分別處理不同的問題。

資安也是如此。本課用虛構案例說明設計，不需要對任何真實網站或帳號做測試。

## 二、什麼是安全控制措施？不只有防火牆或防毒軟體

前面 M01-01 認識了 CIA：機密性、完整性與可用性；M01-02 問的是資產、威脅、弱點及風險。現在要往前一步：為了降低這些風險，我們具體做什麼？

例如，教材平台保存學生的私人作答：

- 為了避免不該看的人看到，設定適當的讀取權限。
- 為了避免答案被不當修改，限制可修改的人，並保留變更紀錄。
- 為了避免資料損壞後無法繼續使用，準備受到保護的備份，並測試能否還原。

這些都可以是安全控制措施。NIST 將這個詞用來指保護系統與資訊、滿足安全需求的防護或對策，不限於某一種產品。[NIST：Security Control](https://csrc.nist.gov/glossary/term/security_control)

為了容易理解，我們先從「怎麼實作」看三個常見面向：

1. 管理與人員流程：例如規定離職時撤銷帳號、定期審查權限、訓練員工辨識可疑要求。重點是誰負責、什麼時候做、怎麼留下紀錄。
2. 技術措施：例如系統的權限檢查、登入驗證、網路連線限制、資料加密。重點是系統實際如何執行規則。
3. 實體措施：例如機房門禁、上鎖機櫃與設備防護。重點是人能不能直接接觸、帶走或破壞設備。

這是入門整理方式，不是宣稱所有標準都使用完全相同的分類。NIST 的控制目錄涵蓋存取、人員、實體環境、事件處理等多個領域；不用現在背完，先理解防護需要人、流程和技術一起運作。[NIST SP 800-53 Rev. 5](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final)

## 三、同一項措施，還要問它主要在做什麼

「怎麼實作」與「發揮什麼功能」是兩個不同問題。考題常見的三個功能是預防、偵測與矯正。

### 1. Preventive Control（預防性控制）：盡量讓不該發生的事情發生不了

例如，只有授課老師能修改成績，其他帳號的修改要求會被系統拒絕。

重點不是把「不能改成績」寫在手冊，而是系統真的檢查身分與權限，並拒絕不符合規則的要求。

多因素驗證也是常見例子。Multi-Factor Authentication，簡稱 MFA，意思是登入時需要不同類型的驗證因素，例如密碼加上你持有的安全金鑰，而不是只依靠一個密碼。

但通過登入驗證，只表示通過了該登入程序，不代表帳號可以讀取所有資料。身分驗證與資料權限仍要分開設計。

### 2. Detective Control（偵測性控制）：讓我們發現可疑或違反規則的事情

例如，系統記錄某帳號短時間內大量下載資料，並通知負責人檢查。

它可能有助於發現問題，但「有告警」不代表「已阻擋」。如果系統只發通知、沒有拒絕下載，那下載仍可能繼續。

反過來，告警也不一定代表真有攻擊。有時老師正在下載自己的合法備課資料，也可能觸發規則。這叫 False Positive（誤報），也就是把正常情況判成可疑。

### 3. Corrective Control（矯正性控制）：發現問題後，把不安全的狀態改正

例如，發現私人資料夾被錯設為公開後，修正分享權限；確認帳號遭濫用後，依程序撤銷受影響的存取並處理原因。

修正設定可以阻止某些後續存取，但不能把先前已被複製的資料「收回來」。所以修正完成，不等於事件調查已完成，也不等於風險歸零。

你也會看到 Recovery（復原）這個功能，重點是讓資料與服務恢復到可用、可信的狀態。例如從確認可用的備份還原。不同教材對矯正與復原的分類邊界可能不同，讀題時要看正在描述哪個動作，不要只靠產品名稱猜答案。

一個工具也可能同時有多種功能：只產生警告時是偵測；設定成自動拒絕特定連線時，也發揮預防作用。判斷的依據是實際設定與行為，不是它的廣告標語。

## 四、縱深防禦：把資產放在中心，沿著可能出事的路徑設計

你可以在腦中先放一個「私人作答資料」的圖像，再把可能接觸它的人、帳號、程式與電腦放在周圍。

接著沿著一條假想路徑思考：

外部人士取得某員工密碼，嘗試登入平台；如果登入成功，還會嘗試讀取或修改私人資料。

我們可以在不同位置安排不同措施：

- 登入位置：不能只靠外洩的密碼，還要符合額外的驗證要求。
- 帳號與權限位置：即使員工可以登入，也只讓他使用工作需要的功能。
- 資料位置：每次讀取或修改，都由系統再次檢查是否具有適當權限。
- 監控位置：記錄異常存取，並讓負責人收到可以處理的通知。
- 復原位置：重要資料有受到保護、能實際還原的備份。

這些不是所有系統必須照抄的固定五層，而是本課的設計示例。NIST 對縱深防禦的描述，強調結合人員、技術與營運能力，在多個層面設置不同屏障，不是只在網路外圍多放幾台設備。[NIST：Defense in Depth](https://csrc.nist.gov/glossary/term/defense_in_depth)

其中一個重要原則叫 Least Privilege（最小權限）：只給使用者或程式完成工作所需要的權限。例如處理一般客服的帳號，不需要有修改全部成績的能力。[NIST：Least Privilege](https://csrc.nist.gov/glossary/term/least_privilege)

為什麼這有幫助？因為即使一個帳號出事，也可以限制它能影響的範圍。不過「設定最小權限」也必須檢查實際例外與授權，不能只靠文件宣告。

### 多層不等於重複堆疊

假設你裝了三套監控工具，但它們都只看同一份不完整紀錄。原本沒記下來的行為，三套工具可能一起看不到。

又或者正式資料與所有備份，都能用同一個受影響的管理帳號刪除。表面上有好幾份副本，卻可能一起受害。

這些是本課的反例，用來提醒你：除了數有幾層，也要找「哪些層會一起失效」。

CISA 的勒索軟體指引提醒，應保護備份，並實際測試復原；因為攻擊者也可能刪除或加密能接觸到的備份。只是把檔案同步到另一處，不一定能保住可還原的版本。[CISA：StopRansomware Guide](https://www.cisa.gov/sites/default/files/2023-10/StopRansomware-Guide-508C-v3_1.pdf)

## 五、完整例子：Northstar 平台的一次存取嘗試

以下是假想案例，不是實際事故紀錄。

Northstar 的客服人員需要查看一般服務單，但不需要讀取學生私人答案。公司因此將客服功能與私人答案的權限分開。

某天，調查人員發現一個遭濫用的客服登入工作階段。工作階段可以想成「系統目前認得這次已登入連線」的狀態。此處先假設它已遭濫用，不推定攻擊者如何取得，也不表示 MFA 本身必然失效。

1. 對方嘗試讀取私人答案，資料服務檢查權限後拒絕。
   這是預防性控制發揮作用：能登入，不等於能讀這份資料。

2. 稽核紀錄留下帳號、目標資料、時間與拒絕結果，規則對多次異常嘗試發出告警。
   這是偵測相關措施：讓人有機會知道正在發生什麼。

3. 負責人查核後，依處理程序撤銷受影響的登入工作階段，並檢查還有沒有其他異常。
   這是處置與矯正的一部分。不能只改密碼，就假設所有既有登入狀態一定自動失效；必須查產品的實際行為。

4. 如果另有資料被修改或損壞，才依調查結果，使用經驗證的版本復原並重新檢查。
   這是有條件的後續復原，不是說這個案例已經發生資料損壞。

整個例子裡，登入這一道邊界已經不能單獨保護資料，但資料權限仍擋下了這次讀取，監控讓負責人能處理異常。這就是縱深防禦要保留的空間。

然而，結論只能寫到「已查核的這次讀取遭拒」。還需要查其他請求與系統，不能直接宣稱「完全沒有資料外洩」。

## 六、怎麼知道控制真的有效？看設定，也看結果

身為資安人員，不應只收集「我們有買什麼」的清單。你要把防護目標、實際設定和驗證證據串起來。

NIST 的控制評估方法包括檢視、訪談與測試。你可以白話地理解成：看文件與設定、問負責人實際怎麼做，以及在明確條件下檢查結果是否符合預期。[NIST：控制評估](https://csrc.nist.gov/Projects/risk-management/about-rmf/assess-step/assessment-cases-overview)、[NIST SP 800-53A Rev. 5](https://csrc.nist.gov/pubs/sp/800/53/a/r5/final)

沿用剛才的案例，在另行取得授權的隔離測試環境，可以用合成資料與測試帳號檢查：

- 客服帳號讀取私人答案，是否確實遭拒？不能只看選單上沒有按鈕。
- 合法教師是否仍可讀取自己的授課資料？全部拒絕雖然看似安全，卻可能破壞可用性。
- 異常操作是否留下正確紀錄？告警有沒有送到真正負責的人？
- 復原測試是否真的取回正確且可使用的資料？備份工作顯示成功，還不是還原成功的證明。

報告也要區分三件事：

- 觀察：測試帳號的這次讀取遭系統拒絕。
- 推論：這項權限控制可能降低同類未授權讀取的風險。
- 限制：只測了指定帳號、資料及條件，尚不能代表所有例外情境都正確。

沒有告警，不等於沒有異常；有告警，也不等於攻擊成功。先確認紀錄是否完整、規則是否涵蓋、測試條件是否合理，再下結論。

## 七、防護也有取捨：不是越多、越嚴就一定越好

每多一道措施，都可能增加成本、維護工作或操作阻力。

例如登入驗證太繁瑣，員工可能尋找不安全的捷徑；告警太多卻沒有足夠人力處理，重要通知可能被淹沒；連線限制設錯，合法服務也可能中斷。

所以設計前先問：我們在保護哪個資產、降低哪個風險？誰維護？如何知道有效？會不會妨礙必要工作？

有時原本措施暫時無法實作，會考慮 Compensating Control（補償性控制），也就是用經評估的替代措施，達到所需的防護效果。不是隨便加一條規則，就能宣布「等於修好了」或「已符合要求」；要確認適用規範、等效程度與剩餘風險。[NIST：Compensating Security Control](https://csrc.nist.gov/glossary/term/compensating_security_control)

我們在 M01-02 說過：弱點與風險不是同一件事。今天再加一句：有控制措施，不等於風險消失。控制是否適合、是否正確運作，會改變風險，但仍要保留尚未處理的部分。

## 八、今天的重點與一題小檢核

記住四句話就好：

1. 安全控制：為了保護資產，具體採取什麼做法？
2. 預防、偵測、矯正：分別是在擋住、發現，還是改正問題？
3. 縱深防禦：一道措施沒擋住時，其他措施能否繼續限制損害？
4. 有效性：不要只看產品或文件，要看授權驗證與實際證據。

小檢核：

某平台已要求 MFA，但一個已登入的員工工作階段遭到濫用。對方讀取私人答案時被權限控制拒絕，系統也發出告警。管理員因此說：「既然有 MFA 又有告警，就能證明完全沒有資料外洩；備份工作顯示成功，也不用測試還原。」

請用自己的話回答：哪一個觀察支持這次讀取有被阻擋？管理員另外兩個結論，為什麼還不能這樣說？

先想一小段就好，不必背術語。參考答案會放在網站預設收合的解答區；公布答案不代表你已作答或已學會。
